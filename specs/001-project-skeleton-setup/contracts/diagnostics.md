# 계약: 진단 보고

**대상**: `src/diagnostics/report.ts`, `src/diagnostics/sink.ts`, `src/ui/DiagnosticsScreen.tsx`
**관련 요구사항**: FR-006, FR-007, FR-007a, FR-007b, FR-017, SC-002, SC-007, SC-013

---

## 보고 내용

```ts
type DiagnosticReport = {
  environment: EnvironmentResolution
  inferenceLocation: BackendSelection
  moduleStatus: ModuleStatus
  failures: Array<{ what: string; reason: string }>
}
```

**모델 식별자·파라미터 수·양자화 방식을 싣지 않는다** — 헌법 원칙 III. 이 기능은 모델을
다루지 않으므로 실을 것도 없지만, 다음 기능에서 추가되지 않도록 계약에 명시한다.

---

## 출력 경로

```ts
type Sink = 'screen' | 'log'

function sinksFor(resolution: EnvironmentResolution): Sink[]
```

### 검증 표 (FR-007a, FR-007b)

| 환경 | 기대 |
| --- | --- |
| `local` | `['screen', 'log']` |
| `dev` | `['screen', 'log']` |
| `prod` | `['log']` |
| 판정 실패 | `['screen', 'log']` |

### 불변식

1. **모든 경우에 `'log'`가 포함된다**(FR-007b). prod에서 화면에 안 보이는 것이 안 남긴다는
   뜻이 아니다. 이 불변식을 테스트로 강제한다.
2. **`prod`에서만 `'screen'`이 빠진다**(SC-013). 엔드유저가 진단 정보를 보는 경우는 0건.
3. **판정 실패 시 화면에 보인다.** 환경을 모르는 상태에서 prod 규칙을 적용할 수 없다.
   판정 실패는 prod 배포본에서 발생해서는 안 되는 상태이고, 발생했다면 감추는 것보다 드러나는
   편이 낫다.

**3번은 의도적 선택이다.** "모르면 가장 조용한 쪽"이 안전해 보이지만, 그러면 배포본에서 환경
설정이 깨졌을 때 아무도 모른 채 추론 위치가 불명인 앱이 돌아간다. 헌법 원칙 V가 관측하지 못한
것을 관측한 것처럼 다루지 말라고 요구한다.

## 진단 화면

**용도**: 개발자가 실기기에서 모듈 적재 상태를 눈으로 확인한다(FR-006, SC-002).

**표시 항목**: 현재 환경, 추론 위치, 모듈 적재 상태, 발생한 실패.

**규칙**:

- `prod`에서 이 화면에 도달하는 경로가 존재하지 않아야 한다(SC-013).
- 화면 디자인은 범위 밖(명세 「가정」). 상태가 읽히면 충분하다.
- 이 화면은 **상태를 보여줄 뿐 품질을 재지 않는다**. 추론 속도 측정, 출력 점수, 모델 비교를
  넣지 않는다 — 헌법 원칙 IV. 이 화면이 원칙 IV를 어기기 가장 쉬운 자리이므로 계약에 못
  박는다.

---

## 실패 처리

**규칙**(FR-007): 실패가 발생하면 앱이 조용히 죽지 않고 사실과 원인이 드러난다.

| 실패 | 처리 |
| --- | --- |
| 환경 판정 실패 | 진단에 실림. 추론 위치를 고르지 않는다 |
| 모듈 적재 실패 (실기기) | `failed`로 진단에 실림 |
| 모듈 없음 (시뮬레이터) | `unavailable`. **실패가 아니다** — 예상된 상태 |
| dev·prod에서 서버 요청 차단 | 차단 사실이 진단에 실림 (FR-009c) |
| 서버 연결 실패 (local) | `failed`로 진단에 실림. 대체 응답 없음 |

**앱을 죽이지 않는다.** 진단 화면 자체가 보이지 않으면 개발자가 원인을 알 수 없다. 실패는
값으로 표현되어 화면에 도달해야 한다.
