# Quickstart: 일기 본문 화면 개선 검증

기기 없이 검증 가능한 것은 `npm test`가 전부 커버한다. 이 문서는 **실기기에서만
드러나는 것**(원칙 V, "건너뛴 실기기 테스트는 통과가 아니다")에 집중한다 — 특히
`expo-location`은 새 네이티브 모듈이므로 최소 1회 debug 실기기 확인이 필수다
(AGENTS.md 「테스트」 절 기준).

## 사전 준비

1. `npx expo install expo-location --check`로 SDK 57 호환 버전을 확인하고 추가한다.
2. `npx expo prebuild --platform android --clean` (새 네이티브 모듈·새 권한이므로
   필수 — AGENTS.md 004 교훈).
3. `cp ~/.alpharium-signing/alpharium.jks android/app/` (prebuild가 지운 서명 키
   되돌리기 — release까지 확인할 경우만. debug만 확인할 계획이면 생략 가능).
4. `EXPO_PUBLIC_APP_ENV=dev npx expo start --dev-client` (Metro).
5. `adb shell dumpsys package <패키지>`로 `requested permissions`에
   `ACCESS_COARSE_LOCATION`/`ACCESS_FINE_LOCATION`이 실제로 들어갔는지 확인
   — 빌드 성공이 매니페스트가 맞다는 뜻이 아니다.

## D1. `reverseGeocodeAsync`의 권한 요구 사실 확인 (research.md §3)

**목적**: 문서 기반 추정을 실측으로 바꾼다.

1. 위치 권한을 거부한 채(설정 화면에서 앱 권한을 "거부") `geocoding-port.ts`의
   `reverseGeocode()`를 단독으로 호출하는 임시 디버그 경로(또는 진단 화면)로
   실행한다.
2. 예외가 던져지는지, 빈 배열이 오는지, 무엇이 오는지 `adb logcat`으로 관찰한다.
3. `geocoding-port.ts`의 catch 경계가 그 실제 동작을 `{ kind: "unknown" }`로
   정확히 흡수하는지 확인한다 — 예외라면 `try/catch`가, 빈 배열이라면 길이 검사가
   필요하다(구현이 둘 다 방어하는 것이 안전하다).

## D2. 사진 표시 — User Story 1

1. 좌표·시각이 있는 사진이 3장 이상 있는 하루를 만든다(010의 `seed:day` 도구
   활용 가능 — 단, "심은 하루로 캐릭터를 비교하지 않는다"는 원칙은 그대로,
   여기서는 화면 경로 확인용으로만 쓴다).
2. 「빠르게 봄」 설정으로 그 하루의 일기를 생성한다.
3. 상세 화면에서 **VLM이 실제로 캡션한 사진**(최대 5장)이 본문에 보이는지
   확인한다 — 그날 사진 전부가 아니라 캡션된 것만이어야 한다(FR-001).
4. 생성 직후, 리사이즈 사본이 놓이는 `vision-cache` 디렉터리에 파일이 남아
   있는지 `adb shell run-as`(debug 빌드) 또는 화면 관찰로 확인한다 — 즉시
   지워지지 않아야 한다(FR-001a).
5. 그 사진의 **원본**을 기기 갤러리 앱에서 삭제한다.
6. 같은 일기 상세 화면을 다시 연다 — 사진이 **여전히 정상적으로 보이는지**
   확인한다(원본 삭제가 화면에 영향을 주지 않아야 한다, clarify 결정).

## D3. 사진 0장 — Edge Case

1. 사진이 0장인 하루로 일기를 생성한다(권한은 있으나 그날 사진 없음).
2. 상세 화면에 사진 표시 영역이 없고, 기존 "사진: 없었다" 문구만 보이는지
   확인한다.
3. "이 일기가 본 것" 절에 사진 분석 소요 시간 문장이 없고, 글쓰기 소요 시간
   문장만 있는지 확인한다(FR-013).

## D3a. 제목 헤드라인·마크다운·본문 서두 — User Story 2 (2026-08-23 추가,
같은 날 재조사로 확장)

**목적**: 자동화된 채점 없이, 사람이 직접 여러 제목·본문 서두를 읽고 재조합
패턴·마크다운 노출·부제목 군더더기가 없는지 확인한다(contracts/title.md
TL6~TL8 — 이 검증은 코드 태스크가 아니라 사람의 검수 절차다).

**사전 확인(선택)**: 이 기능 배포 전 상태를 알고 싶다면, 배포 전 저장된 실제
일기 JSON을 한 번 읽어 문제를 재현해 둔다(이번 조사에서 쓴 명령):
```
adb shell run-as com.anonymous.alpharium ls files/diary/
adb shell run-as com.anonymous.alpharium cat files/diary/<날짜>.json
```
`title`·`text` 필드를 눈으로 읽어 재조합 문구·마크다운 기호(`#`, `**`)·"빈 줄"
같은 문자 그대로의 서식 지시 되뱉음이 있는지 확인한다(2026-08-23 실측: 두
사례 모두 확인됨, research.md §9).

1. 서로 다른 신호를 가진 하루 최소 4개 이상을 준비한다(사진 있는 하루 2개 이상
   — 서로 다른 장면, 사진 없는 하루 1개, 자리 여러 곳인 하루 1개).
2. 같은 캐릭터(예: 금동이)로 각 하루의 일기를 생성한다.
3. 네 제목을 나란히 놓고 읽는다 — **"{캐릭터}의 오늘 일기"/"{캐릭터}의 하루"류로
   전부 같은 모양이 아닌지, 서로 다른 하루임을 제목만으로 구별할 수 있는지**
   확인한다(FR-010a, SC-001a).
4. 사진이 있는 하루의 제목이 그 사진의 장면이나 그날의 구체적 신호를 가리키는지
   확인한다(짐작 어미 사용 여부도 함께 — "~인 것 같다"류가 자연스러운지, 단정형
   지어내기로 미끄러지지 않았는지, TL4).
5. **제목·본문 전체를 눈으로 훑어 마크다운 기호(`#`, `*`, `**`, `-` 등)가 글자
   그대로 남아있지 않은지 확인한다**(FR-010c, TL9). `### ...`나 `**...**`가
   보이면 실패다.
6. **본문 첫 줄을 확인한다** — 날짜·캐릭터 이름·제목을 반복하는 부제목성 줄로
   시작하지 않는지, "빈 줄"처럼 서식 지시 문구가 문자 그대로 들어있지 않은지
   확인한다(FR-010d, TL10·TL11). 본문이 바로 그날 내용으로 시작해야 한다.
7. 로스터 다른 캐릭터(예: 루이)로도 같은 하루를 생성해, 제목의 **말투**는
   캐릭터마다 다르되 재조합 패턴·마크다운·부제목으로는 퇴화하지 않는지
   확인한다(TL5, 특히 루이는 2026-08-23 실측에서 마크다운이 나왔던 캐릭터이므로
   중점 확인 대상).
8. 신호가 거의 없는 하루(사진 0장 등)에서 제목이 없는 것을 지어내지 않는지,
   형식 조건을 못 지키면 지금처럼 제목 없이 본문 전체로 저장되는지 확인한다
   (FR-010b, 새 거부 갈래가 생기지 않았는지 `npm test`의 `acceptance.test.ts`
   갈래 수 4개 확인과 함께).

## D4. 소요 시간 — User Story 3

1. D2에서 생성한 일기의 "이 일기가 본 것" 절 하단에서 소요 시간 문장을 읽는다.
2. 문장이 계약(`contracts/elapsed-time.md` T6)대로
   "{이름}는/은 이렇게 일기를 작성했어요. 사진을 N장을 분석하는 데 M분 SS초가
   걸렸어요. 일기를 작성하는 데 M분 SS초가 걸렸어요." 형태인지 눈으로 확인한다.
3. 콜드 스타트가 확실한 캐릭터(루이/narrative, AGENTS.md가 가장 느리다고
   확인한 캐릭터)로 다시 생성해, 글쓰기 소요 시간이 체감상 긴 시간(수십 초~
   수 분)으로 나오는지 — 숫자가 "재는 시늉"이 아니라 실제로 걸린 시간과
   대략 맞는지 감각적으로 확인한다.
4. 생성이 **진행 중인** 화면(`writing` 상태)에는 어떤 시간 정보도 보이지
   않는지 재확인한다(015·016 방어의 재확인, T9).
5. 이 기능 배포 이전에 저장된 옛 일기(있다면 — 없으면 이 스텝은 생략하고
   해당 없음으로 기록)를 연다 — 소요 시간 문장이 없이 정상적으로 열리는지
   확인한다(FR-018).

## D5. 장소명 — User Story 4

1. 좌표가 있는 사진으로 하루를 만든다.
2. 장소명 설정이 꺼진 기본 상태에서 그 하루의 일기를 연다 — "다닌 자리: N곳"
   만 보이는지(회귀 없음, FR-005) 확인한다.
3. `DiaryListScreen`에서 장소명 설정을 켠다 — 고지 문구("좌표를 기기의 지도
   서비스에 물어봅니다" 류)가 그 자리에서 뜨는지 확인한다(FR-006).
4. 위치 권한 요청 다이얼로그가 뜨면 **허용**한다.
5. 그 하루로 새 일기를 생성한다.
6. 상세 화면에서 "대표 장소 · N곳" 형태로 장소 이름이 보이는지 확인한다
   (기기가 이름을 실제로 해석했다면).
7. 그 일기의 본문 텍스트를 읽어, 화면에 보인 장소 이름과 **같은 이름**이
   본문에도 언급되는지 확인한다(FR-008, "두 개의 진실" 없음).
8. 설정을 다시 끈다 — 이미 생성된 이 일기의 장소명 표시가 **그대로 남아
   있는지**(소급 삭제되지 않는지, Edge Case) 확인한다.
9. (선택, 시간이 허락하면) 위치 권한을 거부한 채 새 하루로 다시 시도해,
   "다닌 자리: N곳"만 있고 이름 자리는 "모른다"류로 뜨는지 확인한다(FR-007
   unknown 경로).

1회면 충분, 반복 생성 불필요), 소요 시간 문장의 조사가 다섯 모두에서 자연스러운

한계이며, 정직하게 기록해 둔다).
