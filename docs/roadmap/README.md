## 진행 예정 과제

### iOS 시뮬레이터에서 일기 생성이 실패하는 원인 찾기 — 「정상 동작 확인」과 일기 쓰기

**배경**: 2026-10-09 iOS 설정·개발자·진단 화면 재검증(068)의 시뮬레이터 재현을 하다 발견했다. iPhone 17 Pro Max 시뮬레이터(iOS 26.5)에서 첫 실행 흐름을 끝까지 따라가
모델 셋을 모두 받고 작명까지 마치자 「아직 준비 중이에요 — 친구를 깨우지 못했어요. 잠시 후 다시 시도해 주세요.」(`다시 시도`·`그냥 시작하기`)가
떴다. 066은 같은 시뮬레이터 계열에서 첫 실행 → 일기 저장까지 갔다고 적었으므로 **그때와 이번 사이에 무엇이 달라졌는지가 질문이다.**

**관측한 것 (원인은 모른다)**:
- 앱은 죽지 않았고 크래시 보고서도 없다 — liveness가 실패 값을 돌려 화면이 그것을 그렸다.
- 받은 파일은 `a1.bin` 1,522,796,768바이트·`v1.bin` 379,219,104바이트·`v2.bin` 102,815,168바이트(2026-10-09 22:56 완료). 크기가 맞는지는 로스터의 기대값과 대조하지 않았다.
- 시뮬레이터 로그에 Metal 셰이더 컴파일 경고가 있었다. 066은 `initMultimodal`의 `use_gpu`가 시뮬레이터 Metal에서 앱을 죽인다고 적었고 `initLlama`의 `n_gpu_layers`는
  시뮬레이터에서 네이티브가 0으로 꺾는다고 적었다 — 이번 실패가 그 경로와 관련 있는지는 **확인하지 않았다.**
- JS 쪽 실패 이유(liveness가 돌려준 값의 사유)는 아직 못 봤다.
- 이 시뮬레이터에 설치된 앱은 `com.anonymous.alpharium`이다 — 저장소의 `ios/`가 065 이름 변경(`com.a810labs.pocketlog`) **이전에 prebuild된 낡은 프로젝트**다.
  066·위 TestFlight 빌드와 같은 결과물이 아닐 수 있다.

**2026-10-10 갱신(068 훑기 중)**: 현재 `app.json`으로 `prebuild --clean`한 새 `ios/`(`com.a810labs.pocketlog`)로 다시 만든 시뮬레이터 빌드에서는 같은 흐름에서 「정상 동작 확인」이
**통과했다**(「그냥 시작하기」 불필요) — 낡은 `ios/` 빌드가 원인이었을 가능성이 크다(미확정: 다른 변수는 통제하지 않았다). **그런데 일기 생성은 안 된다**: 같은 빌드에서 자동 첫 일기(2026-10-09 23:52)·
진단 「지금 한 번 써 보기」 두 번이 모두 「일기를 쓰지 못했어요.」 토스트로 끝났고 `write-failures.json`에 이유 갈래 `unwritten`(그 밖의 쓰기 실패)이 3건 쌓였다(2026-10-10). 066은 같은 시뮬레이터 계열에서
첫 일기가 저장됐다고 적었으므로 **그때와 달라진 것**이 질문이다. 이 과제는 이제 「정상 동작 확인」이 아니라 **일기 생성 실패의 원인**이 본론이다 — 아래 할 일의 1번이 그 이유(`unwritten`을 낸 판정 갈래·모듈 적재·사진 읽기)를 보는 것이다.

**할 일**:
1. **실패 이유를 먼저 본다** — `unwritten`(그 밖의 쓰기 실패)으로 떨어진 파이프라인의 이유와 llama.rn의 로그를 Metro·시뮬레이터 로그에서 읽는다(추측으로 고치지 않는다).
2. **재현은 현재 `app.json`으로 `prebuild --clean`한 `ios/`에서 한다** — 낡은 `ios/`(`com.anonymous.alpharium`)는 위 갱신에서 이미 새 `ios/`로 바꿨고 「정상 동작 확인」은 통과했다(원인 확정은 아니다).
   같은 흐름을 이 빌드에서 한 번 더 돌아 이유를 확정한다.
3. 이유가 안 보이면 모델 파일 크기·무결성, `use_gpu`·`n_gpu_layers`, 시뮬레이터 OS 버전(26.5)을 하나씩 본다 — **한 축을 깊게 파지 않는다**(AGENTS 작업 습관).
4. 고칠 수 없는 환경 한계(시뮬레이터에서는 안 도는 것)로 판명되면 AGENTS의 「iOS 시뮬레이터」 절에 한 줄로 남기고, 일기 생성은 시뮬레이터가 아니라 실제 iPhone(TestFlight)에서 본다고 적는다.

**완료 조건**: 실패 이유가 로그로 확인되고, 코드 결함이면 고쳐서 시뮬레이터에서 일기 한 편이 저장되며, 환경 한계면 문서에 근거와 함께 남는다.

**위험**: 시뮬레이터에서만 나는 문제를 실제 iPhone의 문제로 오해하기 쉽다 — 실제 iPhone은 TestFlight에서 따로 본다(원칙 V). 이 과제를 이유로 시뮬레이터 훑기(`.maestro/ios/`)나
아래 e2e 과제를 멈추지 않는다 — 그 흐름들은 일기 생성 없이 끝난다.

### 주요 기능별 e2e 테스트 — 화면 흐름 층과 실제 생성 스모크 층

**진행**: 첫 조각(할 일 1번 대응표 + 2번의 안드로이드 쪽)은 스펙 069로 끝났다 — 대응표는 `docs/e2e/feature-flow-map.md`, 층 1은 `npm run test:layer1`(전용 테스트 기기, 8개 흐름 7분 37초 통과). 표본(30일치 MediaStore 사진)은 스펙 070으로 끝났다 — `docs/e2e/sample-table.md`, 층 1이 표본 위에서 9개 흐름 11분 47초 통과. **남은 것**: 2번의 iOS 시뮬레이터 갈래(표본 심기는 `simctl addmedia` — 070 표는 플랫폼 중립), 3번 층 2, 4번 CI 판단, 그리고 대응표가 드러낸 낡은 흐름 셋(`skeleton`·`prompt-preview`·`today-diary` — `FLOWS`에 있지만 현재 화면과 맞지 않아 실패한다) 정리.

**배경**: `.maestro/`에 안드로이드 흐름이 23개 있지만 기능 단위로 무엇을 지키는지 대응표가 없고, 설정·개발자·진단 화면은
거의 비어 있으며, iOS 흐름은 068이 `.maestro/ios/`에 둔 시뮬레이터 훑기 셋(설정, 개발자·진단, 첫 실행에서 홈까지)과 보조 하나뿐이고 `FLOWS`에 등록돼 있지 않다
(TestFlight 빌드 2의 권한 행 튕김은 화면 흐름 e2e가 잡았어야 했다).
반면 이 앱의 e2e는 일반 앱과 조건이 다르다 — 일기 본문은 비결정적이라 내용을 단언할 수 없고(채점 코드는 원칙 IV로
금지), 모델 2GB·생성 50~240초·`pm clear`가 모델까지 지우므로 「매번 깨끗한 상태」가 비싸며, arm64 전용 빌드라 CI
에뮬레이터에서 실제 추론을 돌리기 어렵다. 가짜 추론으로 초록을 만들면 042의 교훈(「검증 경로가 제품과 다르면 검증이
아니다」)에 걸린다.

**도구는 Maestro를 유지한다** — Detox·Appium으로 옮기거나 클라우드 기기 팜을 들이지 않는다(흐름 23개를 옮기는 비용에
비해 얻는 것이 적고, 기기 팜에서도 2GB 모델 문제는 그대로다).

**할 일**:

1. **기능 → 흐름 대응표**를 만든다 — 주요 기능(첫 실행·쓰기·쓴 날 읽기·날 고르기·달력·설정 각 행·개발자·진단·
   상태 흉내·자동 쓰기·지우기 등)마다 어느 흐름이 무엇을 보는지, 빈 칸·중복·`FLOWS` 밖 흐름을 드러낸다.
   대응표의 자리(문서 또는 `run-device-tests.mjs` 주석)도 정한다.
2. **층 1 — 화면 흐름 e2e (빠름, 자주)**: 생성 없이 끝나는 흐름만(설정·개발자·진단·달력·스트립·권한 행·대화상자).
   - **기기 상태 고정**: 모델이 받아진 상태를 기준으로 삼고 `pm clear` 대신 플래그 파일(`preferences/*.json`)만
     되돌리는 초기화 경로를 만든다(iOS는 `simctl get_app_container`의 `Documents/`).
   - **같은 YAML을 안드로이드 실기기와 iOS 시뮬레이터에서** 돌린다 — 플랫폼 차이(권한 창 문구, 뒤로 가기 없음)는
     흐름 안의 분기 또는 플랫폼별 하위 흐름으로 가른다. 실행기(`run-device-tests.mjs`)에 iOS 갈래를 더한다.
     출발점은 068의 `.maestro/ios/` 훑기 흐름과 AGENTS 068이 적은 함정(`launchApp`의 `stopApp: false`, 개발 클라이언트 재진입 확인 창)이다.
3. **층 2 — 실제 생성 스모크 (느림, 릴리스 전)**: 실제 모델로 기능당 하나 — 「쓰기 → 저장 → 쓴 날 홈」, 첫 실행 자동
   첫 일기, 앱 열면 쓰는 중(057), 진단 한 번 써 보기. 단언은 상태 전이까지이고 본문은 사람이 읽는다. 실기기에서
   사람이 돌리며, 릴리스(Play 내부 테스트·TestFlight) 전 체크리스트에 넣는다.
4. **CI에 넣을지는 층 1만, 그리고 실측 뒤에 정한다** — macOS 러너의 iOS 시뮬레이터에서 층 1이 몇 분에 도는지,
   모델 없이 닿는 화면이 어디까지인지(첫 실행 게이트가 막는다) 먼저 잰다. 안 되면 로컬 실행으로 둔다.

**완료 조건**: 대응표의 모든 주요 기능에 층 1 또는 층 2 흐름이 있거나 「사람이 본다」가 이유와 함께 적혀 있다. 층 1은
안드로이드 dev 실기기와 iOS 시뮬레이터에서 각각 한 번 전부 통과한다. 층 2는 실기기에서 한 번 완주한다. 새 흐름은
`FLOWS`에 등록한다(등록 안 된 흐름은 초록불인데 아무것도 검증하지 않는다).

**위험**: 흐름을 늘리는 것 자체가 목표가 되기 쉽다 — Maestro 흐름은 행 높이·문구·좌표에 깨지기 쉬워(「Maestro」 절)
유지 비용이 흐름 수에 비례한다. 대응표에서 「이미 계약 테스트가 지키는 것」은 e2e로 다시 만들지 않는다.

### 무료 빌드 머신으로 iOS 빌드·업로드 — 개인 맥 없이

**Tier 3(서명·업로드)** — 태그·수동 트리거로 돌린다. 완료된 「CI 네이티브 빌드 확인」(072, Tier 2)이 잰 macOS 러너 시간이 이 과제의 첫 입력이다(`specs/072-ci-native-build-check/quickstart.md`). 릴리즈 빌드 종류는 여기서 정한다.

**배경**: 저장소 소유자는 회사 맥 밖에서는 맥이 없다 — 지금 iOS 빌드·TestFlight 업로드(066 절차)는 회사 맥에서만 된다.
무료 빌드 머신을 쓰고 싶다. 사전 검토(2026-10-08, 소유자)의 후보:

| 후보 | 무료 조건 | 메모 |
| --- | --- | --- |
| GitHub Actions macOS | 퍼블릭 저장소는 표준 러너 분 제한 없음 · 프라이빗은 월 2,000분이고 macOS는 10배 소모 | **이 저장소는 퍼블릭이다**(2026-10-08 확인) — 사실상 무료 |
| Xcode Cloud | Apple Developer Program에 월 25시간 포함 | 서명을 Apple이 관리 |
| Codemagic · EAS Build | 무료 티어(월 횟수·분 제한, EAS는 대기열 느림) | 한도는 자주 바뀐다 — 쓰기 전에 요금표 확인 |

**먼저 풀어야 할 질문 (설계 전에 소유자 결정)**:

- **서명 키를 어디에 두는가가 후보를 가른다.** 배포 인증서·개인 키(`~/.pocketlog-signing/ios/`)는 소유주 Hyunmin Lee 님의
  **개인** Developer Program 것이다(066). GitHub Actions·Codemagic·EAS는 그 키를 그들의 비밀 저장소에 올려야 한다 —
  **소유주 동의가 먼저다**(코드가 정하지 않는다). Xcode Cloud는 키를 넘기지 않고 Apple이 클라우드 관리 서명을 하지만,
  개인 계정에서 Admin(저장소 소유자)이 Xcode Cloud를 켤 수 있는지, 그리고 첫 워크플로를 Xcode에서 한 번 만들어야
  하는지(회사 맥 1회 방문) 확인이 필요하다.
- **퍼블릭 저장소의 비밀 관리**: 포크 PR에는 비밀이 안 넘어가지만, 업로드 잡은 `main`의 `workflow_dispatch`(또는 태그)와
  GitHub Environment 보호 규칙(승인자 = 소유자)으로만 돌게 한다. 앱 암호 대신 App Store Connect API 키(`.p8`)를 쓴다.
- **Expo·RN 빌드가 그 머신에서 도는가**: Xcode Cloud는 Node·CocoaPods를 기본으로 갖지 않는다 — `ci_scripts/ci_post_clone.sh`에서
  설치하고 `expo prebuild`를 돌려야 한다(`ios/`는 gitignore된 생성물). 러너의 Xcode 버전이 066 실측(Xcode 26.6)과 맞는지,
  llama.rn 컴파일 시간·메모리도 잰다.
- **맥이 없으면 iOS 시뮬레이터도 없다** — 빌드·업로드가 클라우드로 가도 iOS 화면 확인·Maestro iOS 갈래(e2e 과제)는
  실제 iPhone(TestFlight) 아니면 회사 맥이다. 이 과제가 그 공백까지 메우지는 않는다.

**할 일**: 후보 하나를 골라(권장 검토 순서: 퍼블릭이라 무료인 GitHub Actions → 키를 안 넘기는 Xcode Cloud) 수동 실행 워크플로
하나로 「prebuild → 아카이브 → 서명 → TestFlight 업로드」를 끝까지 한 번 돈다. `ios.buildNumber` 올림은 사람이 커밋한다(지금처럼).
**AGENTS.md 「iOS 빌드·서명·TestFlight」 절을 그 경로로 고친다**(로컬 맥 절차는 「다른 맥에서 올리려면」 옆에 대안으로 남긴다).

**완료 조건**: 회사 맥에 손대지 않고 올린 빌드가 App Store Connect **처리 단계까지 통과**하고(업로드 성공 ≠ 처리 통과, ITMS 메일 확인)
TestFlight에서 실제 iPhone에 설치된다. 같은 경로로 안드로이드 AAB까지 할지는 그 뒤에 정한다(안드로이드는 리눅스 러너라 맥 문제가 없다).

### 안드로이드 release 빌드·서명·보관을 CI로 — 로컬 19분 빌드 없이

**Tier 3(서명·업로드)** — 태그·수동 트리거로 돌린다. release 빌드 종류(최적화·서명)는 여기서 정한다.

**배경**: 지금 안드로이드 release(AAB·APK) 빌드와 서명은 소유자의 개발 기계에서만 된다(AGENTS 「release 빌드·서명·Google Play」). 빌드가 약 14~19분이고 서명 키(`~/.pocketlog-signing/pocketlog.jks`)가 그 기계에만 있다.
완료된 「CI 네이티브 빌드 확인」(072)은 **서명 없는 빌드가 되는지만 보고 결과물을 남기지 않는다** — 이 과제가 서명한 결과물을 만들고 남기는 쪽이다. iOS 쪽 짝은 아래 「무료 빌드 머신으로 iOS 빌드·업로드」.

**먼저 풀어야 할 질문 (설계 전에 소유자 결정)**:

- **서명 키를 CI에 올려도 되는가.** 업로드 키(`pocketlog.jks`)와 비밀번호를 GitHub Secrets(Environment 보호 규칙 — 승인자 = 소유자)에 넣어야 한다. Play 앱 서명을 쓰므로 업로드 키를 잃어도 Play Console에서
  재설정할 수 있다(며칠 걸림)는 점이 위험을 줄이지만, 키가 CI에 있다는 사실 자체는 소유자가 정한다.
- **결과물을 어디에 남기는가.** 이 저장소는 퍼블릭이라 **GitHub artifact는 누구나 받을 수 있다** — 서명한 AAB·APK를 artifact로 올리지 않는다. 후보: (1) Play Console 내부 테스트 트랙에 바로 올린다(서비스 계정 키 필요 — 이것도 비밀),
  (2) 수동 실행 전용 워크플로의 비공개 보관 자리(저장소 밖). 어느 쪽인지 정한 뒤에 설계한다.
- **`versionCode` 올림은 사람이 커밋한다**(지금처럼) — CI가 올리면 같은 번호 충돌과 커밋 흐름이 꼬인다.

**할 일**: 후보를 골라 **수동 실행(`workflow_dispatch`) 워크플로 하나**로 「prebuild → `-PreactNativeArchitectures=arm64-v8a` 서명 AAB → 결과물 남기기」를 끝까지 한 번 돈다. 서명 설정은 `plugins/with-release-signing.js`가
이미 선언으로 넣는다. 키스토어는 러너에서 복원하고 끝나면 지운다. **AGENTS.md 「release 빌드·서명·Google Play」 절을 그 경로로 고친다**(로컬 절차는 대안으로 남긴다).

**완료 조건**: 로컬 기계에 손대지 않고 만든 AAB가 서명 검증(`keytool -printcert -jarfile` — `CN=Android Debug`가 아님)을 통과하고, 정한 자리에 남으며, 그 자리에서 받은 빌드가 실기기에서 Metro 없이 돈다
(release는 만들면 debug 앱을 지워야 해서 모델·일기가 사라진다 — 전용 기기에서만).

**위험**: 퍼블릭 저장소에서 비밀이 새지 않게 업로드 잡은 `main`의 수동 실행으로만 돌린다(포크 PR에는 비밀이 안 넘어간다). 러너 실측(스펙 072, `specs/072-ci-native-build-check/quickstart.md` §5): ubuntu-latest(4코어·16GB)에서 arm64 debug는 gradle 5~10분·최대 메모리 약 12GB/16GB로 OOM이 없었다 — release 최적화 컴파일은 이 값으로 추정하지 말고 다시 잰다. `ubuntu-latest`가 2026-10-19부터 Ubuntu 26으로 바뀐다.

### 사진 있는 날의 VLM 캡션 전량 스킵(SharedObject GC 레이스) 방어 (073)

상세 분석 문서: [`docs/superpowers/specs/2026-10-10-photo-caption-silent-failure.md`](../superpowers/specs/2026-10-10-photo-caption-silent-failure.md)

**배경**: 2026-10-10 테스트 디바이스(SM-G986N)에서 사진이 각각 6장·12장 있는 날임에도 `visionMs`가 1초 미만으로 끝나며 일기 본문이 `"나는 오늘 아무것도 보지 못했다. 사진은 쌓였지만, 그 속을 끝까지 들여다보지 못해 심심했다..."`로 저장되고 사진 캐러셀이 나오지 않는 현상이 관측됐다. 같은 날 화면에서 「다시 쓰기」(포그라운드)를 돌리면 정상적으로 6장(24초)·8장(38초) 캡션과 캐러셀이 복구됐다.

**관측한 것과 원인**:
- `filePathOf`(`src/signals/expo-port.ts`)의 `await new lib.Asset(id).getUri()`가 임시 객체로 생성되어 비동기 쿼리 중 JS 스택에서 사라진다.
- 대형 모델(VLM·kanana) 로드 직전/직후의 네이티브 힙 메모리 압박(`NativeAlloc`)으로 강제 GC가 발생하면, Hermes가 임시 `Asset` 객체를 먼저 회수하여 JSI 브릿지에서 `Cannot use shared object that was already released` 예외가 발생한다(2026-10-09 `expo-file-system`의 `File` 객체 결함과 동일 계열).
- `filePathOf`의 `catch`가 조용히 `null`을 반환하고 `captionAll`이 `continue`로 스킵하여 사진 N장이 1초 미만에 전량 건너뛰어진다.
- 프롬프트 엔진(`prompt.ts`)은 이를 보고 `unread` 갈래로 분류해 `"나는 오늘 아무것도 보지 못했다"` 일기를 오류 없는 정상 일기로 데이터베이스에 영구 저장한다.
- 백그라운드 자동 일기 생성(Doze·WorkManager)이나 RAM이 타이트한 실사용 기기에서 발생 확률이 매우 높다.

**할 일**:
1. **`Asset` 객체의 JS GC 조기 회수 방지**: `filePathOf`·`folderNamesFor`·`locationOf`(`src/signals/expo-port.ts`)에서 `new lib.Asset(id)`를 로컬 변수에 할당하고 `await` 이후까지 참조를 유지하여 비동기 I/O 도중 Hermes GC가 SharedObject를 회수하지 못하게 스코프를 보장한다.
2. **VLM 전량 실패 방어**: 사진이 관측되었는데 캡션 결과가 0장인 경우, 침묵 저장 대신 1회 재시도하거나 `vision-failed`로 방어하여 거짓 일기가 정상 일기로 저장되는 것을 차단한다.
3. **소스 계약 테스트 추가**: `__tests__/diary/expo-file-sync.test.ts`와 유사하게 `Asset`의 임시 객체 즉시 비동기 호출을 정적으로 차단하는 계약 테스트를 추가한다.

**완료 조건**: 메모리 압박/연속 생성 상태에서도 캡션이 전량 스킵되는 현상이 재현되지 않고, 사진이 있는 날에는 항상 사진 캡션과 캐러셀이 정상적으로 포함된 일기가 저장된다.

**위험**: `Asset` 외에도 `expo-media-library`나 다른 네이티브 모듈의 비동기 SharedObject 메서드가 유사한 패턴으로 노출되어 있을 수 있다. 소스 계약 테스트로 범위를 통제한다.

### 첫 실행 모델 내려받기 — Wi-Fi가 아니면 알리고 고르게 하기

**배경**: 첫 실행 흐름의 다운로드 동의 대화상자(`DownloadConsentDialog`, 045)는 [받을게요] 하나뿐이라 모바일 데이터에서도 약 2GB를 그대로 받는다. 지금 네트워크 종류를 보는 곳은
설정의 「모듈 다시 받기」뿐이고(059, `expo-network`가 `CELLULAR`일 때만 용량 문구를 낸다) 첫 실행에는 없다.

**순서: 조사 먼저, 구현은 그 뒤.** 구현에 들어가기 전에 다른 앱들이 같은 상황(큰 파일을 처음 받을 때 모바일 데이터인 경우)을 어떻게 다루는지 먼저 조사한다 — 대용량 에셋을 받는 앱(게임의 추가 데이터,
온디바이스 AI·오프라인 지도·오프라인 음악/영상 앱 등)의 안내 시점·문구·선택지 구성(데이터로 받기/Wi-Fi 대기/취소), 기본값, 설정에 「Wi-Fi에서만」 옵션을 두는지, Wi-Fi가 끊길 때의 동작,
플랫폼 가이드(Android·Apple HIG)의 권고. 조사 결과는 `docs/superpowers/specs/`에 문서로 남기고, 위 「정해야 할 것」은 그 결과를 보고 소유자와 정한다. 조사 전에 스펙을 열거나 코드를 짜지 않는다.

**하려는 것**: 초반 모델 내려받기를 시작하기 전에, 기기가 Wi-Fi에 연결돼 있지 않으면 모달로 「Wi-Fi에서 내려받아야 해요」를 알리고 두 선택지를 둔다 —
**그래도 모바일 데이터로 받기** / **앱 닫기**. Wi-Fi에 연결돼 있으면 모달 없이 지금처럼 진행한다.

**정해야 할 것** (착수 때 소유자와 정한다):
- 「Wi-Fi가 아님」의 판정 범위 — `CELLULAR`만인지, `UNKNOWN`·연결 없음도 포함인지(059는 모르면 문구를 안 내는 쪽을 택했다, 원칙 V). 연결 없음은 별도 안내가 필요할 수 있다.
- 기존 동의 대화상자와 합칠지 앞에 한 겹 더 둘지, 그리고 「앱 닫기」의 플랫폼별 동작(안드로이드는 종료 가능, iOS는 앱을 스스로 닫는 공식 방법이 없다).
- 받는 도중 Wi-Fi가 끊겨 모바일 데이터로 넘어갈 때를 다룰지(범위 밖으로 둘 수도 있다).
- 문구는 `src/i18n/catalogs/ko/`에 둔다(062).

**완료 조건**: 모바일 데이터 상태에서 첫 실행을 하면 모달이 뜨고, 「모바일 데이터로 받기」는 내려받기를 진행시키며 「앱 닫기」는 아무것도 받지 않고 끝낸다. Wi-Fi 상태에서는 모달이 없다. 실기기(dev)에서 두 갈래를 본다.

**위험**: `expo-network`의 네트워크 종류 조회는 기기·OS마다 값이 다를 수 있다(VPN·핫스팟·이더넷). 이 앱은 사용자가 거부할 수 없는 동의(045)를 전제로 설계됐으므로, 「앱 닫기」가 원칙 I(앱이 사용자를 막지 않는다)과 충돌하지 않는지 헌법을 먼저 읽고 확인한다.
