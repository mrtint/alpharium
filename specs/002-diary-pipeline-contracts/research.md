# Phase 0: 조사

**기능**: 일기 파이프라인의 축 사이 계약 | **날짜**: 2026-08-12

명세가 남긴 미확정 항목과, 설계를 고르기 전에 실제로 확인해야 했던 것을 정리한다.
**추측한 것과 확인한 것을 구분해 적는다**(헌법 원칙 V).

---

## 1. "없음"과 "알 수 없음"을 어떻게 표현하는가

**Decision**: 합 타입 `SignalValue<T> = Known<T> | None | Unknown`으로 표현한다.
옵셔널 필드(`T | undefined`)나 널러블(`T | null`)을 쓰지 않는다.

**Rationale**: FR-002가 요구하는 구분이 타입 수준에서 강제되어야 한다. 옵셔널로 두면
`photos === undefined`가 "사진이 0장"인지 "사진에 접근 못 했다"인지 알 수 없고, 읽는 쪽이
매번 관례에 기대게 된다. 헌법 원칙 V가 관측한 것과 못 한 것을 구분하라고 요구하는데,
타입이 그 구분을 못 하면 코드가 지킬 근거가 없다.

이것이 실제 문제인 근거: **안드로이드에는 기간 걸음 수를 되짚는 통로가 없다**(AGENTS.md
실측). `getStepCountAsync`는 iOS 전용이다. 그래서 걸음 수는 "알 수 없음"이 정상 상태이며,
이를 0으로 채우면 "걷지 않았다"는 거짓이 된다. 가정된 문제가 아니라 이미 확인된 제약이다.

**Alternatives considered**:
- `T | undefined` — 두 상태를 구분 못 함. FR-002 위반. 기각.
- `{ value: T | null, known: boolean }` — 구분은 되지만 `known: false`인데 `value`가 있는
  불가능한 상태를 타입이 허용한다. 기각.
- 각 신호마다 다른 표현 — 읽는 쪽이 신호마다 다른 관례를 외워야 한다. 기각.

**주의**: `None`과 `Unknown`을 뭉개는 것은 이 기능에서 가장 하기 쉬운 실수다. 001에서
`ModuleStatus`의 `unavailable`/`failed`를 가른 것과 같은 이유이며, 같은 패턴을 쓴다.

## 2. "아직 없음"을 어떻게 반환하는가

**Decision**: `generate()`는 `DiaryDraft | GenerationFailure` 합 타입을 반환하고,
온디바이스·데스크톱 구현 모두 `{ kind: 'not-implemented' }`를 돌려준다. 예외를 던지지 않고
가짜 텍스트도 만들지 않는다.

**Rationale**: 헌법 원칙 I이 금지한 것은 *미리 만들어 둔 응답을 보여주는 경로*다.
"아직 구현되지 않았다"를 정직하게 반환하는 것은 그 반대이며, 명세 FR-016이 이 구분을
명시한다.

예외를 던지지 않는 이유: 001에서 `ModuleStatus`를 값으로 표현한 것과 같다. 예외는 삼켜지기
쉽고, 삼켜지면 호출자가 "실패"를 "결과 없음"으로 오해한다. 파이프라인이 어느 단계에서
멈췄는지 드러내야 하므로(FR-019) 실패도 값이어야 한다.

**Alternatives considered**:
- 예외를 던진다 — 삼켜질 위험. FR-019의 "어느 단계에서 멈췄는지" 추적이 어려워진다. 기각.
- `null` 반환 — 왜 없는지가 사라진다. "아직 구현 안 됨"과 "생성 실패"를 구분 못 함. 기각.
- 플레이스홀더 텍스트 반환("일기를 생성할 수 없습니다") — **헌법 원칙 I 위반**. 그럴듯한
  텍스트가 일기 자리에 들어가는 순간 가짜 일기와 구분이 사라진다. 기각.

## 3. 일기를 어디에 저장하는가

**Decision**: `expo-file-system`의 `File`/`Paths` API로 `Paths.document` 아래 날짜별 JSON
파일 하나씩.

**확인 방법 (실측)**: 설치본 확인 — `expo-file-system 57.0.2`가 이미 있다.
`@react-native-async-storage/async-storage 2.2.0`도 있다. `expo-sqlite`는 없다.
API는 context7 `/expo/expo`로 확인했다(AGENTS.md가 요구하는 절차):

```
Paths.document        // 시스템이 지우지 않는 저장 위치
new File(dir, name)   // write(), text(), delete(), exists
```

**Rationale**:
- **이미 설치돼 있다.** 새 의존성을 더하지 않는다.
- **한 날짜에 한 파일**이 FR-023(한 날짜에 일기 하나)과 자연스럽게 맞는다. 파일명이 곧
  날짜 키이므로 존재 여부 확인(FR-018f)이 디렉터리 조회로 끝난다.
- **덮어쓰기가 원자적으로 다루기 쉽다.** 임시 파일에 쓰고 옮기면 FR-023b(새 생성 실패 시
  기존 일기 보존)를 지킬 수 있다.
- `Paths.document`는 시스템이 저장 공간 부족 시 지우지 않는다(`Paths.cache`와 다름).
  일기는 사라지면 안 되는 값이다.

**Alternatives considered**:
- `AsyncStorage` — 설치돼 있으나 키-값 저장이라 날짜별 목록 조회가 전체 키 스캔이 된다.
  또한 저장 용량 한계가 있고 큰 텍스트에 적합하지 않다. 기각.
- `expo-sqlite` — 설치돼 있지 않다. 조회 요구가 "날짜로 하나 꺼내기"와 "어느 날짜가 비었나"
  뿐이라 DB가 과하다. 나중에 검색·필터가 필요해지면 그때 옮긴다. 기각.
- 하나의 큰 JSON 파일 — 일기 하나 저장에 전체를 다시 써야 하고, 쓰기 중 종료되면 전부
  잃는다. 기각.

**실측으로 확인됨 (2026-08-13)**: `expo-file-system` 57의 `File`/`Paths` API를 실기기
(Galaxy S20+, Android 13, arm64-v8a)에서 실제로 돌렸다. 저장·조회·덮어쓰기·목록이 모두
동작했고, **`unknown`이 파일 왕복에서 살아남는 것**까지 확인했다(quickstart.md F절).

확인한 API의 모양:

```
Paths.document            // Directory
new Directory(dir, name)  // .exists, .create({intermediates}), .list()
new File(dir, name)       // .exists, .create(), .write(string), .text(), .delete(), .moveSync(dest)
```

`write`/`delete`/`create`/`moveSync`는 동기이고 `text()`만 비동기다. 이 비대칭이 처음
쓸 때 헷갈리는 지점이다.

**설계상의 대비**: 저장은 인터페이스 뒤에 둔다. 파일 방식이 맞지 않으면 구현만 갈아끼우고
파이프라인은 그대로 둔다.

## 4. 하루 경계(04:00)를 어떻게 다루는가

**Decision**: `src/config/day-boundary.ts`에 순수 함수로 둔다. 시각 → 그 시각이 속한 하루의
날짜를 반환한다. 04:00이라는 값은 이 파일에만 있다(FR-021a).

**Rationale**: 신호 수집(다음 기능)과 일기 생성이 서로 다른 하루를 보면 근거가 어긋난다.
한 곳에 두면 그 한 곳의 테스트로 규칙이 지켜진다 — 001에서 `policy.ts`를 헌법 원칙 I의
방어선으로 삼은 것과 같은 구조다.

순수 함수인 이유: "지금"을 인자로 받아야 테스트가 시간에 의존하지 않는다. `new Date()`를
함수 안에서 부르면 03:59와 04:00 경계를 테스트할 수 없다.

**검증할 경계값**: 03:59:59 → 전날, 04:00:00 → 당일, 자정 직후(00:30) → 전날.

**Alternatives considered**:
- 각 모듈이 알아서 판단 — FR-021a 위반. 기각.
- 시각 대신 날짜만 다루기 — 04:00 경계를 표현할 수 없다. 기각.

**미해결로 남긴 것**: 시간대가 바뀐 하루(여행 등). FR-021b가 이 기능의 범위 밖으로 명시했다.
지금 정해도 검증할 방법이 없고, 신호를 실제로 수집할 때 정한다.

## 5. 캐릭터를 어떻게 표현하는가

**Decision**: 헌법 로스터의 다섯을 가리키는 식별자로 두되, **모델 파일이나 모델 이름과 잇지
않는다**. 캐릭터→모델 매핑은 이 기능에서 만들지 않는다.

**Rationale**: 헌법 원칙 III이 모델 식별자의 사용자 노출을 금지하고, 「로스터」 절이
"캐릭터 이름은 사람이 짓는다. 아래는 관측된 성질이지 최종 이름이 아니다"라고 못 박았다.
**최종 이름이 아직 없으므로 지어내면 안 된다.**

그래서 이 기능은 캐릭터를 "다섯 중 하나"라는 자리로만 두고, 표시 이름과 모델 연결은 로스터
기능의 몫으로 남긴다. 지금 이름을 지으면 원칙 III의 "지어낸 성격을 붙이지 않는다"를 어기는
쪽으로 흐르기 쉽다.

**Alternatives considered**:
- 모델 파일명을 캐릭터 식별자로 — 원칙 III 정면 위반. 기각.
- 임시 한국어 이름을 짓는다 — 헌법이 "사람이 짓는다"고 했다. 기각.
- 캐릭터를 이 기능에서 빼고 요청에 넣지 않는다 — FR-006이 요구하고, 빼면 다음 기능이
  요청 계약을 다시 고쳐야 한다. 기각.
