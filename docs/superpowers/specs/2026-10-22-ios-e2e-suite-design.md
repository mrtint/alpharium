# iOS e2e 세트 — 안드로이드와 같은 층 1·층 2 설계

로드맵 「주요 기능별 e2e 테스트 — iOS 시뮬레이터 갈래와 CI 판단」의 설계다. 안드로이드 쪽(069·070·073·084)은 끝났고, 이 문서는 iOS 갈래를 정한다.

## 목적과 성공 기준

안드로이드에 있는 층 1(화면 흐름, 일기를 쓰지 않음)과 층 2(실제 모델로 쓰는 스모크 4종)를 iOS에도 같은 구성으로 갖춘다. iPhone 14 실기기가 생겨 가능해졌다. TestFlight 빌드 2의 권한 행 튕김처럼 화면 흐름 e2e가 잡았어야 할 결함이 iOS에서 다시 새지 않게 하는 것이 목적이다.

- 층 1이 iOS 시뮬레이터에서 한 번 전부 통과한다.
- 층 2 네 흐름이 iPhone 14 실기기에서 한 번 완주한다.
- 새 흐름은 `FLOWS`에 등록하고 `docs/e2e/feature-flow-map.md`를 고친다.
- CI에 넣을지 말지는 층 1의 실측 소요 시간과 함께 기록한다.

## 조사로 정한 것 (스파이크, 2026-10-22)

**Maestro는 iOS 실기기를 직접 구동하지 못한다.** 공식은 시뮬레이터만 지원한다. 비공식 `maestro-ios-device`(DeviceLab)를 격리 환경(임시 `HOME`, Maestro 2.0.10)에 설치해 iPhone 14(iOS 27.0.1)에서 시험했으나 러너 빌드가 실패했다.

- 러너의 배포 목표 14.0은 Xcode 27.1의 허용 범위(15.0~27.1.x) 밖이다(격리 복사본에서 고칠 수 있다).
- 러너가 쓰는 번들 ID 둘(`dev.mobile.maestro-driver-ios`, `…UITests.xctrunner`)의 프로파일이 없어, 자동 서명을 켜면 팀 `PGNGG84B39` 계정에 App ID 두 개가 새로 등록된다.
- 도구는 iOS 16~18·Maestro 2.0.9~2.0.10에서만 검증됐고 우리 Maestro는 2.11.0이다.

소유자 결정(2026-10-22): **실기기 구동 도구는 채택하지 않는다.** 전역 설치는 건드리지 않았고 임시 설치는 지웠다.

## 결정

| 층 | 어디서 | 누가 조작하나 |
| --- | --- | --- |
| 층 1 | iOS 시뮬레이터 | Maestro가 YAML 흐름을 구동 |
| 층 2 | iPhone 14 실기기(개발 서명 빌드) | 사람이 쓰기를 탭, 실행기가 준비하고 상태를 단언 |

제품 코드는 바꾸지 않는다. 테스트 전용 진입점이나 시작 훅을 넣지 않는다(042: 검증 경로가 제품과 다르면 검증이 아니다). 도구는 층 1에서 Maestro를 유지한다.

## 층 1 — 시뮬레이터

- **기기 접촉:** 기존 `Layer1Device`(`scripts/layer1/device.ts`) 인터페이스에 iOS 구현체를 더한다(`simctl` 기반). `runner.ts`와 기준 상태 표 `BASELINE`은 그대로 쓴다. 안드로이드 구현체에 `pm clear`·`install`·`uninstall`이 없다는 계약(I-1)을 iOS 구현체에도 같이 건다.
- **기준 상태 복원:** 앱 데이터 컨테이너의 `Documents/`를 `xcrun simctl get_app_container <udid> com.a810labs.pocketlog data`로 찾아 쓰고 지우고 복사한다. 컨테이너 UUID는 바뀌므로 경로를 저장하지 않고 실행마다 찾는다(066).
- **표본과 권한:** `simctl addmedia`로 30일 표본을 심고 `simctl privacy grant`로 권한을 준다. 표본 표(070)는 플랫폼 중립이다.
- **흐름 호환:** 층 1 흐름을 한 개씩 점검한다. 안드로이드 전용 동작(뒤로 가기 키, OS 설정 왕복의 복귀)은 `when: platform` 분기나 `.maestro/ios/` 하위 흐름으로 가른다. 기존 `.maestro/ios/` 흐름 넷(훑기)은 `FLOWS`에 편입하거나 정리한다. 등록하지 않은 흐름은 아무것도 검증하지 않는다.
- **함정(AGENTS 068):** `launchApp`의 `stopApp: false`, 개발 클라이언트 재진입 확인 창, 합성 클릭 무시, 콜드 기동은 `MAESTRO_DRIVER_STARTUP_TIMEOUT=180000`.
- **모델 파일:** 층 1은 생성하지 않지만 기준 상태에 모델 파일이 있어야 한다. 시뮬레이터에 어떻게 두는지(내려받기 vs 복사)는 계획 단계에서 잰다.

## 층 2 — iPhone 14

흐름마다 실행기가 다음을 한다. 안드로이드 층 2와 같은 모양이다(흐름마다 기준 상태를 다시 만들어 따로 부름).

1. `devicectl device copy`로 앱 컨테이너 `Documents/`에 기준 상태를 덮는다.
2. 사진이 필요한 흐름은 `npm run ios:seed`(087)로 사진을 심는다.
3. `devicectl device process launch`로 앱을 띄운다.
4. 사람이 눌러야 하는 흐름은 무엇을 누를지 안내한다.
5. 컨테이너를 폴링해 상태 전이를 단언한다.

| 흐름 | 시작 | 조작 |
| --- | --- | --- |
| 앱 열면 쓰기(057) | 앱 실행 | 없음 — 완전 자동 |
| 쓰기 → 저장 → 쓴 날 홈 | 어제를 골라 「쓰기」 | 사람이 탭 |
| 진단 한 번 써 보기 | 진단의 「한 번 써 보기」 | 사람이 탭 |
| 첫 실행 자동 첫 일기(040) | 온보딩 플래그를 되돌린 상태 | 사람이 작명 입력 |

**단언:** 대상 날짜의 일기 파일이 제한 시간 안에 생긴다, 파일이 정상 형식이다, 「최근 실패」 기록에 새 항목이 없다. **본문은 채점하지 않는다(원칙 IV)** — 끝에 `.cache/layer2/<시각>/`로 가져와 사람이 읽는다. 쓰는 중 상태는 메모리 등록부(080)라 파일로 보이지 않으므로 중간 전이는 단언하지 않는다. 관찰 방법이 있는지는 계획 단계에서 따로 본다.

## 문서와 등록

- `scripts/run-device-tests.mjs`의 `FLOWS`·`LAYER1_FLOWS`·`LAYER2_FLOWS`와 `scripts/layer2/flows.ts`의 iOS 갈래를 등록하고, `feature-flow-map.md`에 iOS 열을 더하고, `__tests__/e2e/flow-map.test.ts`를 확장한다.
- `docs/e2e/layer2-release-checklist.md`의 「iOS」 절을 사람이 확인하라는 문구에서 실제 절차로 바꾼다.
- 로드맵과 AGENTS의 「iOS 시뮬레이터 갈래」 서술을 이 결정에 맞게 고친다(뒤의 결정이 앞의 서술을 뒤집으면 주석을 덧대지 않고 고친다).
- CI: 층 1이 macOS 러너의 시뮬레이터에서 몇 분에 도는지, 모델 없이 닿는 화면이 어디까지인지(첫 실행 게이트)를 재서 기록한다. 안 되면 로컬 실행으로 둔다.

## 범위 밖

- Maestro로 iOS 실기기를 구동하는 것(위 조사).
- 층 2의 무인화(쓰기 시작 훅 추가).
- 쓰는 중 중간 전이의 자동 단언(관찰 수단이 없으면 사람이 본다).
- CI에서 층 2를 돌리는 것.

## 위험

- 시뮬레이터 통과는 실제 iPhone을 말해 주지 않는다. 층 2가 실기기인 이유다.
- 층 2는 사람이 끼어 완전 무인이 아니다. 네 흐름 중 하나만 자동이다.
- `ios:seed`는 Xcode를 꺼 두어야 하고 lldb attach가 가끔 30~60초 걸린다. 시딩한 사진을 지우는 도구가 없다.
- 흐름 수를 늘리는 것 자체가 목표가 되기 쉽다. Maestro 흐름은 행 높이·문구·좌표에 깨지므로 계약 테스트가 이미 지키는 것은 e2e로 다시 만들지 않는다.
- 시뮬레이터에서 모델을 어떻게 두는지, 콜드 기동 시간 등 실측 전에는 소요 시간을 장담하지 않는다(원칙 V).

## 계획 단계로 넘기는 질문

1. 시뮬레이터 기준 상태에 모델 파일을 두는 방법과 층 1 흐름이 모델 없이 닿는 화면의 한계.
2. 층 1 흐름 12개 각각의 iOS 호환 점검 결과(분기가 필요한 곳).
3. 층 2에서 폴링할 파일(일기, 시도·실패 기록)의 정확한 경로와 형식.
4. 쓰는 중 상태를 관찰할 수단이 있는가(`devicectl` 콘솔 로그 등).
