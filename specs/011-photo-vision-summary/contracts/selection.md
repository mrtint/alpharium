# Contract: 하루에 걸쳐 균일하게 5장 고르기

**Feature**: `011-photo-vision-summary` | **파일**: `src/vision/select.ts`

**순수 함수 하나다.** 기기를 모르고, 시각을 읽지 않고, 난수를 쓰지 않는다.

---

## 왜 이 계약이 따로 필요한가

**004와 정반대로 자르기 때문이다.**

`src/signals/collect.ts`가 `usable.slice(0, limit)`으로 **이른 시각부터** 자른다
(2026-08-22 코드 확인). 그것이 004에서는 옳다 — 「그날 사진이 몇 장인가」를 세는 데는
어느 다섯이든 상관없고, 이른 것부터가 예측 가능하다.

**여기서는 그것이 틀린다.** 아침 사진 5장만 읽으면 휴대폰이 **아침만 본 채 하루를
쓴다.** 사용자가 clarify에서 직접 바로잡은 것이며(FR-007a), 이 계약이 그 차이를 못
박는 자리다.

---

## 시그니처

```ts
/** 상한. **한 자리에만 있다** — 004의 DEFAULT_PHOTO_LIMIT와 같은 성격 */
const VISION_PHOTO_LIMIT = 5;

/**
 * 읽을 사진을 고른다.
 *
 * @param photos 찍힌 시각 순으로 정렬된 목록 (004가 이미 정렬해 준다)
 * @returns 최대 5장. 입력 순서(시각 순)를 유지한다
 */
export function selectForVision(photos: readonly Photo[]): Photo[];
```

### S1. 인자가 하나뿐이다 — 상한을 밖에서 정하지 못한다

**009가 배운 것이다.** `selectableDays(now, count = 3)`처럼 기본값 인자를 두면
`Function.length`가 그것을 **세지 않아** 검사를 통과하면서 부르는 쪽이 값을 마음대로
바꿀 수 있다.

**그래서 선언을 `readFileSync`로 직접 읽어** 둘째 인자와 상수 export를 막는다.
009의 `day-boundary.test.ts`가 같은 방식으로 고쳐졌다.

**`VISION_PHOTO_LIMIT`을 export 하지 않는다** — 하면 테스트가 그것을 읽어 계산하게 되고,
그때 테스트는 「5장인가」가 아니라 「상수와 같은가」를 보게 된다. **값을 직접 적는다.**

---

## 규칙

### R1. 5장 이하면 전부 고른다

`photos.length <= 5`이면 입력을 그대로 돌려준다. 고를 것이 없다.

### R2. 5장을 넘으면 균등 분위로 고른다

```
i(k) = round(k * (n - 1) / (limit - 1))   (k = 0 … limit-1)
```

**n=12, limit=5**이면 인덱스 `0, 3, 6, 8, 11`을 고른다.

### R3. **가장 이른 것과 가장 늦은 것을 반드시 포함한다**

R2의 식이 `k=0`에서 `0`을, `k=limit-1`에서 `n-1`을 주므로 자동으로 성립한다.
**이것이 「하루를 그린다」의 핵심**이며, 빠지면 하루의 시작이나 끝이 사라진다.

### R4. 중복을 만들지 않는다

`round()`가 같은 인덱스를 두 번 줄 수 있는가 — **`n > limit`이면 없다.** 간격이
`(n-1)/(limit-1) > 1`이므로 인접한 `i(k)`가 최소 1 이상 벌어진다.

**`n == limit`이면 R1이 먼저 걸러낸다.** 그래도 방어로 중복을 제거하며, 제거 뒤 개수가
줄면 그것이 결함이므로 **테스트가 개수를 직접 센다.**

### R5. 입력 순서(시각 순)를 유지한다

돌려주는 목록이 찍힌 시각 순이어야 한다 — 프롬프트가 「아침에 …, 저녁에 …」로 읽히려면
순서가 곧 시간이다.

### R6. 결정적이다

같은 입력에 언제나 같은 답. **`Date.now()`도 `Math.random()`도 읽지 않는다.**

005의 `buildPrompt()`가 결정적인 것과 같은 이유이며, 이것이 없으면 같은 하루를 두 번
쓸 때 **다른 사진을 보게 되어** 「신호가 같은데 출력이 다르다」가 된다(006 FR-037a가
경계한 상태).

## 예시로 못 박기

| 입력 (시각) | 고른 것 | 왜 |
| --- | --- | --- |
| 3장: 09, 13, 19 | **전부** | R1 |
| 5장: 08,10,12,14,16 | **전부** | R1 |
| 6장: 08,09,10,11,12,13 | 08, 09, 11, 12, 13 | R2 (인덱스 0,1,3,4,5) |
| 12장: 07~22 | 07, …, 22 | R3 — **양 끝 포함** |
| 10장 전부 저녁 (19~21) | 19, …, 21 | **전부 저녁이다 — 사실이므로 옳다** |

**마지막 줄이 중요하다.** 저녁에만 찍은 하루는 고른 것도 전부 저녁이고 그것이 정확하다.
**일기가 그것으로 하루 전체를 그리면 안 되며**, 그래서 FR-007b가 「고른 사진이 하루의
어느 때에 걸쳐 있는지」를 프롬프트에 싣는다(→ `contracts/prompt.md`).

## 004의 잘림과 겹치는 것 (FR-012)

**두 한계가 서로 다른 말을 한다.**

```
그날 사진 250장
  → 004가 200장으로 자른다        complete: false   「그날 사진이 더 있었다」
  → 011이 5장을 고른다            available: 200    「있는 것 중 다섯만 보았다」
```

**`available`은 004가 준 목록의 길이이지 그날의 진짜 장수가 아니다.** 004가 잘랐으면
그것도 이미 잘린 수다.

**그래서 프롬프트가 둘 다 말해야 한다** — 004의 `TRUNCATED_WARNING`(사진 수를 단언하지
마라)과 011의 「다섯 장만 보았다」가 **함께 간다.** 하나만 있으면 거짓이 된다.
