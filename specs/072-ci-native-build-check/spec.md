# Feature Specification: CI에 네이티브 빌드 확인 추가

**Feature Branch**: `072-ci-native-build-check`

**Created**: 2026-10-10

**Status**: Draft

**Input**: User description: "docs/superpowers/specs/2026-10-10-ci-native-build-check-design.md 를 입력으로 한다. CI에 네이티브 빌드 확인 추가: 네이티브에 닿는 PR 변경(경로 필터)과 main push·수동 실행에서 도는 새 워크플로, 안드로이드 arm64 debug 빌드 + iOS 서명 없는 시뮬레이터 빌드, 실패 시 빨간불(continue-on-error 없음), 결과물·서명·업로드 없음, 러너에서 시간·메모리 실측."

## 근거와 원본

- **설계**: `docs/superpowers/specs/2026-10-10-ci-native-build-check-design.md`(저장소 소유자 승인, 2026-10-10).
- **로드맵 과제**: 「CI에 네이티브 빌드 확인 추가」.
- **문제**: 지금 CI는 lint·tsc·헌법 검사·jest와 안드로이드 JS 번들까지다. 네이티브 컴파일·prebuild·pod install은 돌지 않아, 의존성 올림이나 설정 변경이 네이티브를 깨뜨려도 소유자가 로컬에서 release 빌드를 할 때에야 드러난다(안드로이드 약 14~19분, iOS 약 10분).
- **범위 밖**: 서명, release 빌드, 결과물 보관·업로드(「안드로이드 release 빌드·서명·보관을 CI로」·「무료 빌드 머신으로 iOS 빌드·업로드」 과제), 브랜치 보호 설정 변경, 확인을 필수 체크로 올리는 일, 빌드 산출물로 도는 E2E, 앱 코드 변경, 빌드 성공 뒤의 실행 경로 검증(e2e 과제).
- **한계**: 이 빌드 확인은 품질 보증이 아니다. 이 앱의 실제 결함(iOS `await import` 튕김, ITMS-90683, 004 권한 누락)은 빌드가 성공한 상태에서 났다 — 컴파일·prebuild 깨짐만 막는다.

## Clarifications

### Session 2026-10-10

- Q: `main`에 push가 짧은 간격으로 여러 번 들어오면 앞선 실행을 취소하고 최근 것만 돌리나, 모두 끝까지 도나? → A: 취소한다 — 같은 ref(PR이면 그 PR)의 새 실행이 앞선 진행 중 실행을 취소하고 가장 최근 커밋만 확인한다(소유자 결정, 2026-10-10).

### Session 2026-10-10 (재결정)

- Q: 이 확인을 PR에서도 돌리나? → A: 돌린다, 단 네이티브에 닿는 변경에서만 — `package.json`·`package-lock.json`·`app.json`·`plugins/**`와 이 워크플로 파일이 바뀐 PR(경로 필터). `main` push는 경로와 무관하게 항상, 수동 실행도 둔다. 필수 체크로 올리지 않는다. 앞선 "PR에서는 돌리지 않는다" 결정을 대체한다(소유자 결정, 실무의 3티어 CI 구성에 맞춤).

## 용어

- **네이티브 빌드 확인**: 프로젝트를 안드로이드·iOS 네이티브 프로젝트로 만들고(prebuild) 컴파일까지 해 보는 자동 확인. 결과물은 남기지 않는다.
- **실측값**: 러너에서 한 번 돌려 얻은 걸린 시간(캐시 없음·캐시 적중)과 안드로이드 최대 메모리 사용량.

## User Scenarios & Testing _(mandatory)_

사용자는 이 저장소의 소유자(개발자)다.

### User Story 1 - 네이티브를 깨뜨리는 변경을 머지 전에 빨간불로 안다 (Priority: P1)

소유자가 의존성이나 config plugin을 바꾸는 PR을 열면, 안드로이드와 iOS 네이티브 빌드 확인이 자동으로 돈다. 네이티브가 깨졌으면 해당 플랫폼이 실패로 표시된다. 로컬 release 빌드를 할 때까지 기다리지 않는다. `main`에 들어간 뒤에도 같은 확인이 한 번 더 돈다.

**Why this priority**: 이 과제의 본론이다. 지금은 네이티브 깨짐이 몇 주 뒤에야 드러날 수 있다.

**Independent Test**: `app.json`에 없는 config plugin 이름을 넣은 브랜치에서 실행하면(PR을 열면 돈다) 두 플랫폼 모두 실패하고, 되돌려 다시 실행하면 둘 다 성공한다.

**Acceptance Scenarios**:

1. **Given** 네이티브가 정상인 `main`, **When** `main`에 push되면, **Then** 안드로이드·iOS 확인이 각각 돌고 둘 다 성공으로 끝난다.
2. **Given** 없는 config plugin 이름이 들어간 PR, **When** PR을 열면, **Then** 두 플랫폼 확인이 모두 실패로 끝나고 실패한 단계가 로그에서 보인다.
3. **Given** 위 브랜치를 되돌린 뒤, **When** 다시 실행하면, **Then** 두 플랫폼 확인이 모두 성공한다.
4. **Given** 한 플랫폼만 깨진 변경, **When** 돌리면, **Then** 다른 플랫폼 확인은 그와 무관하게 끝까지 돈다(서로 막지 않는다).

---

### User Story 2 - 네이티브와 무관한 PR과 머지를 느리게 하지 않는다 (Priority: P1)

네이티브 빌드 확인은 길다(10~20분대). 네이티브에 닿지 않는 PR(문서·`src/`·테스트만 바뀐 PR)에서는 시작하지 않고, 기존 검사(`ci.yml`)의 시간과 결과에 영향을 주지 않는다. 이 확인이 실패해도 머지는 막히지 않는다.

**Why this priority**: 대부분의 PR은 네이티브와 무관하다. 모든 PR에 걸면 개발 속도를 깎는다.

**Independent Test**: `src/`나 문서만 바꾼 PR에서 이 확인이 시작되지 않고, 이 확인이 실패한 PR에서도 기존 검사 결과는 그대로이며 머지가 막히지 않는다.

**Acceptance Scenarios**:

1. **Given** 네이티브 입력(`package.json`·`package-lock.json`·`app.json`·`plugins/**`·이 워크플로 파일)을 건드리지 않는 PR, **When** 열거나 갱신하면, **Then** 네이티브 빌드 확인은 시작되지 않는다.
2. **Given** 그 입력 중 하나라도 바꾸는 PR, **When** 열거나 갱신하면, **Then** 확인이 시작된다.
3. **Given** 네이티브 확인이 실패한 PR 또는 `main`, **When** 머지하려 하면, **Then** 이 확인은 필수 체크가 아니므로 머지를 막지 않는다(브랜치 보호에 필수로 올리지 않는다는 전제).
4. **Given** 네이티브 확인이 실패로 끝남, **When** 결과를 보면, **Then** 실패가 성공으로 가려지지 않고 빨간불로 남는다.

---

### User Story 3 - 걸리는 시간과 메모리가 숫자로 남는다 (Priority: P2)

소유자는 러너에서 처음 돌린 결과(캐시 없음)와 두 번째(캐시 적중)의 걸린 시간, 안드로이드 최대 메모리 사용량을 알고 싶다. 그 값으로 시간 제한과 후속 release 빌드 과제의 가능성을 판단한다.

**Why this priority**: 로컬에서 네 ABI 동시 빌드는 메모리 부족으로 죽었다. 러너에서도 같은지는 재 봐야 안다(원칙 V — 안 잰 값을 추측하지 않는다).

**Independent Test**: 실행 요약에 각 플랫폼의 걸린 시간과 안드로이드 최대 메모리가 보이고, 같은 값이 `specs/072-ci-native-build-check/quickstart.md`에 기록된다.

**Acceptance Scenarios**:

1. **Given** 한 번 끝난 실행, **When** 요약을 보면, **Then** 플랫폼별 걸린 시간과 안드로이드 최대 메모리가 적혀 있다.
2. **Given** 캐시 없는 첫 실행과 캐시 적중 두 번째 실행, **When** 두 실측을 비교하면, **Then** 둘 다 기록되고 캐시 효과가 보인다.

---

### Edge Cases

- 러너가 메모리 부족이나 시간 제한으로 빌드를 죽이면 실패로 표시되어야 하며 성공으로 보이면 안 된다.
- 캐시가 깨졌거나 없어도 확인은 느릴 뿐 결과가 틀리지 않아야 한다.
- 수동 실행을 다른 브랜치에서 하면 그 브랜치의 내용으로 돈다(`main` 내용이 아니다). 수동 실행은 워크플로 파일이 `main`에 있어야 가능하다.
- 이 워크플로 파일이 새로 들어오는 PR은 경로 필터에 자기 자신이 들어 있어 그 PR에서 곧바로 돈다(`pull_request`는 PR 브랜치의 워크플로 파일을 쓴다).
- 포크에서 온 PR은 비밀값이 없어도 도는 이 확인(비밀값 무사용)이 그대로 돈다.
- 연달아 push하면(PR이든 `main`이든) 같은 ref의 앞선 실행이 취소되어 중간 커밋의 깨짐은 확인되지 않는다. 마지막 커밋이 깨졌다면 원인은 사람이 찾는다.
- iOS 확인에 필요한 도구 버전이 러너 이미지 갱신으로 바뀌면 코드 변경 없이도 실패할 수 있다(실패 원인이 로그에 보이면 충분하다).

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 시스템은 `main`에 push될 때 네이티브 빌드 확인을 시작해야 한다. 변경된 파일 경로와 무관하게 항상 시작한다.
- **FR-001b**: 시스템은 PR이 열리거나 갱신될 때, 그 PR이 네이티브 입력(`package.json`·`package-lock.json`·`app.json`·`plugins/**`·이 워크플로 파일) 중 하나라도 바꾸면 확인을 시작해야 한다.
- **FR-001a**: 같은 ref(PR 실행이면 그 PR, `main` push면 `main`)에서 새 실행이 시작되면 아직 진행 중인 앞선 실행은 취소되어야 한다. 취소된 실행은 실패가 아니라 취소로 표시된다. 중간 커밋의 깨짐은 확인되지 않을 수 있고 이는 받아들인 결정이다.
- **FR-002**: 시스템은 소유자가 수동으로 실행할 수 있어야 하며, 임의의 브랜치에서 실행할 수 있어야 한다.
- **FR-003**: 시스템은 PR이 위 네이티브 입력을 하나도 바꾸지 않으면 네이티브 빌드 확인을 시작해서는 안 된다.
- **FR-004**: 안드로이드 확인은 네이티브 프로젝트를 새로 만들고(기존 생성물을 지움) arm64 하나로 debug 빌드를 끝까지 해야 한다. 여러 ABI를 빌드해서는 안 된다.
- **FR-005**: iOS 확인은 macOS 러너에서 네이티브 프로젝트를 새로 만들고 의존 라이브러리를 설치한 뒤 서명 없이 시뮬레이터용으로 빌드해야 한다.
- **FR-006**: 두 플랫폼 확인은 서로 의존하지 않아야 하며, 한쪽 실패가 다른 쪽을 중단시켜서는 안 된다.
- **FR-007**: 어느 단계가 실패하든 해당 확인은 실패로 끝나야 한다. 실패를 성공으로 바꾸는 설정(`continue-on-error` 등)을 어느 단계에도 두어서는 안 된다.
- **FR-008**: 시스템은 빌드 결과물을 저장·업로드하거나 서명해서는 안 된다. 서명 관련 비밀값을 읽어서도 안 된다.
- **FR-009**: 시스템은 각 확인의 걸린 시간을 실행 요약에 남겨야 하고, 안드로이드 확인은 빌드 중 최대 메모리 사용량도 남겨야 한다.
- **FR-010**: 시스템은 반복 실행의 속도를 위해 빌드 캐시를 사용해야 한다. 캐시가 없어도 결과가 달라져서는 안 된다.
- **FR-011**: 기존 `ci.yml`의 동작과 결과는 바뀌어서는 안 된다.
- **FR-012**: 워크플로의 트리거·실패 처리·ABI·비밀값 무사용은 기기 없는 테스트로 잠겨야 하며, 위반 주입으로 테스트가 실제로 잡는지 확인되어야 한다.
- **FR-013**: 이 확인을 필수 체크로 두지 않는다는 전제(경로 필터로 건너뛴 워크플로의 필수 체크는 「대기 중」에 머물러 PR을 막는다)를 스펙·구현 문서에 확인 사항으로 남겨야 한다(브랜치 보호는 저장소 설정이라 워크플로로 정할 수 없다).

### Key Entities

- **네이티브 빌드 확인 실행**: 한 번의 실행. 플랫폼별 결과(성공/실패), 걸린 시간, 안드로이드 최대 메모리를 가진다.
- **실측 기록**: 첫 실행·캐시 적중 실행의 시간·메모리 값을 담은 `quickstart.md`의 표.

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 네이티브를 의도적으로 깨뜨린 브랜치(없는 config plugin 이름)에서 PR을 열면 두 플랫폼 확인이 모두 실패하고, 되돌린 뒤에는 둘 다 성공한다(위반 주입, 각 1회).
- **SC-002**: 네이티브 입력을 안 건드린 PR에서는 확인이 시작되지 않고, 건드린 PR과 `main` push 한 번당 확인이 정확히 한 번 시작되며, 같은 ref의 앞선 실행이 진행 중이면 그 실행은 취소된다.
- **SC-003**: 첫 실행과 캐시 적중 실행에서 플랫폼별 걸린 시간과 안드로이드 최대 메모리가 실측되어 문서에 남는다.
- **SC-004**: 워크플로에서 `continue-on-error`·PR 경로 필터 제거·`pull_request_target` 트리거·여러 ABI·비밀값·결과물 업로드 중 하나라도 되살리면 기기 없는 테스트가 실패한다(각각 위반 주입으로 확인).
- **SC-005**: 이 변경으로 기존 검사(`ci.yml`)의 단계·결과가 달라지지 않는다.

## Assumptions

- 저장소는 퍼블릭이라 GitHub Actions 사용량에 분 단위 제한이 없다고 본다. macOS 러너는 대기열이 길 수 있다.
- 안드로이드는 release가 아니라 debug 빌드다 — release는 서명 키스토어를 요구해 서명 없이 돌지 않으며, release 최적화 컴파일은 후속 과제가 다룬다. 따라서 이 확인은 release 최적화 단계의 메모리 부족을 재현하지 못할 수 있다.
- "머지를 막지 않는다"는 브랜치 보호의 필수 체크에 이 확인을 넣지 않는 것으로 이룬다. 현재 설정은 소유자가 안다.
- 두 플랫폼 모두 새 의존성 없이 러너 기본 도구(Node 24·JDK·Android SDK·Xcode·CocoaPods)로 빌드된다고 가정한다. 기본 도구로 안 되면 구현 단계에서 필요한 설정 단계를 추가하고 기록한다.
- 앱 코드·테스트 대상 앱 동작은 바뀌지 않으므로 실기기 검증은 해당 없음이다(완료 보고에 명시).
