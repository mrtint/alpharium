# Quickstart: 백그라운드 자동 일기 생성 기술 검증

이 문서는 하네스 구현이 끝난 뒤, **실기기에서 이 검증을 실제로
수행하는 절차**다. 코드 작성 방법이 아니라 실행·관측 방법을 담는다.

## 사전 준비

1. 실기기(AGENTS.md 기준 보유 안드로이드 기기, 예: SM-G986N)에 dev
   빌드를 설치한다 — `npx expo run:android`(development build, Expo Go
   아님).
2. 사진·위치 권한을 미리 부여해 둔다(FR-010 — 권한 요청 흐름 자체는
   검증 대상이 아니므로 이미 허용된 상태에서 시작한다).
3. 배터리 최적화는 **기본값(제한 있음)**으로 둔다 — 예외를 미리 주지
   않는다. FR-002·FR-009가 "예외 없이 먼저 관측"을 요구한다.
4. 진단 화면(개발자 탭)에서 백그라운드 태스크 등록 위젯이 보이는지
   확인한다(local·dev 전용, `showsOnScreen()` 게이트 — 배포 빌드에서는
   안 보이는 것도 함께 확인한다).

## 1단계 — 실행 기회 자체가 있는가 (User Story 1)

**간격을 좁혀도 방치 시간은 줄이지 않는다**(research.md §7) — 등록
시 `minimumInterval`을 코드가 이미 API 허용 최솟값인 15분으로
고정했으므로(`background-diary-task.ts`), 24시간 동안 이론상 최대
약 96회의 시도 표본을 얻는다. 다만 **이 24시간 동안 기기를 확인차
건드리면 안 된다** — Doze·앱 대기 버킷 조건은 실제로 오래 방치해야
걸리고, 중간에 화면을 켜는 순간 "화면 없이 방치"라는 전제가 깨져
얻은 관측 전체의 의미가 달라진다.

1. 진단 화면에서 백그라운드 태스크를 등록한다
   (`BackgroundTask.registerTaskAsync`, 15분 간격으로 이미 고정됨).
2. 기기를 잠그고 화면을 끈 채 방치한다. **24시간 이상**(FR-008) —
   최소 하루 경계(04:00)를 한 번 넘기도록 전날 저녁에 등록을
   시작한다. **이 24시간 동안 로그를 확인하려고 앱을 열지 않는다** —
   열면 관측이 오염된다.
3. 24시간이 지난 뒤 앱을 열기 전에 먼저 `adb shell dumpsys
   jobscheduler | grep -A 5 <package>`(또는 `adb shell dumpsys
   activity provider` 계열)로 시스템이 태스크를 실행했는지 확인한다
   — 참고 증거일 뿐, 1차 증거는 4번이다.
4. 앱을 열어 진단 화면의 로그 열람 위젯으로 `verification-log.jsonl`을
   읽는다. `task-entered`가 몇 번 기록됐는지(시도 횟수 — 15분 간격
   이론값과 실제 값의 차이 자체가 OS가 얼마나 간격을 늦췄는지 보여주는
   관측이다), `task-completed`/`task-result`가 각 시도마다 있는지
   확인한다(data-model.md의 3단계 판정 로직).
5. 전날 일기가 실제로 생성되어 있는지 일기 목록 화면에서 확인한다.

## 2단계 — 추론 자체가 완주하는가 (User Story 2)

1가 "실행 기회가 있다"로 나온 경우에만 진행한다(실행 기회 자체가
없으면 이 단계는 의미가 없다 — SC-001의 결론이 이미 "NO"로 정해진다).

1. 진단 화면의 디버그 버튼(research.md §5)으로 백그라운드 콜백을
   화면 없이 강제 트리거한다(정확한 시각을 기다리지 않고 즉시 확인
   하기 위한 보조 수단 — 1단계의 자연 발생 실행과 별개로 기록한다).
2. 가장 느린 캐릭터(헌법 로스터의 exaone)로 사진이 있는 하루를
   대상으로 트리거한다.
3. 로그에서 `pipeline-stage` 이벤트의 진행을 시간순으로 읽어, 어느
   단계에서 얼마나 머물렀는지 확인한다(캡션 단계 vs 생성 단계).
4. 화면을 켠 채(포그라운드) 같은 캐릭터·같은 하루로 정상 생성한
   결과와 완주 여부를 대조한다 — 포그라운드에서는 되는데 백그라운드
   에서만 중단되면, 그 차이가 CPU 스로틀링·메모리 회수 등 백그라운드
   고유의 제약임을 시사한다.

## 3단계 — 권한이 여전히 유효한가 (FR-010)

1단계 관측과 함께 확인한다(별도 실행 불필요) — 로그의
`permission-checked` 이벤트를 읽는다.

- `valid: false`가 하나라도 있으면, 그 시점에 어느 축(사진/위치)이
  실패했는지와 `task-completed`의 `outcome`을 함께 본다(권한 실패가
  파이프라인 실패로 이어졌는지, 아니면 `unknown`으로 흡수되어 조용히
  일기가 생성됐는지 — 둘 다 findings.md에 남길 가치가 있는 별개의
  관측이다).

## 4단계 — 경합 관측 (E1, research.md §5, 선택)

시간이 허락하면 수행한다(필수 범위는 아님 — plan.md Constraints 참고).

1. 화면에서 "쓰기"를 누른 직후, 진단 화면의 디버그 트리거로 백그라운드
   콜백을 동시에 실행한다.
2. 무슨 일이 나는지 관측한다 — 둘 다 실패, 하나만 성공, 크래시 등.
   `task-completed`의 `outcome: "threw"` 여부와 `reason`을 확인한다
   (contracts/background-harness.md H4).

## 배터리 최적화 예외를 줬을 때의 대조 (FR-009)

1~3단계를 배터리 최적화 기본값에서 최소 1회 수행한 뒤, 설정에서 이
앱에 배터리 최적화 예외를 부여하고 **같은 절차를 반복**한다. 두
결과를 findings.md에서 나란히 비교해 조건부 결론(SC-002)의 근거로
쓴다.

## findings.md 작성 시 확인할 것 (User Story 3)

- 모든 실측값에 기기 모델·안드로이드 버전·배터리 최적화 설정이
  함께 적혀 있는가(spec.md Acceptance Scenario, 헌법 원칙 V).
- YES/NO/조건부 중 하나가 명시적으로 결론으로 적혀 있는가(SC-001).
- 조건부라면 그 조건이 설정 변경만으로 재현 가능한 수준으로
  구체적인가(SC-002) — "배터리 최적화 예외 필요" 같은 구체적 문장이지
  "최적화가 필요할 수 있음" 같은 모호한 문장이 아니어야 한다.
- 이 검증에 참여하지 않은 사람이 문서만 읽고 다음 결정(020+ 스펙을
  쓸지)을 내릴 수 있는가(SC-004).
