# Feature Specification: 앱 요구 권한 실측 및 통합 신청 절차

**Feature Branch**: `021-unified-permission-onboarding`

**Created**: 2026-08-29

**Status**: Draft

**Input**: User description: "사진이나 위치 정보에만 국한하지 않고, 알림(expo-notifications)이나
기기 백그라운드 위치 권한 등 앱 구동에 실제 필수적인 모든 권한들을 구현 시점에 실측하여 면밀히
식별합니다. 식별된 모든 필수 권한을 앱 최초 진입부에서 통합적으로 요청하고 획득할 수 있는 시작
시나리오 흐름을 구성합니다."

## 이 스펙의 전제 — 020 이후의 상태

020(시간대 지정 자동 일기 + 완성 알림)이 머지됐다(PR #30, main `5321a1b`). 020이
`POST_NOTIFICATIONS` 런타임 권한과 배터리 최적화 예외 요청(`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`)을
새로 도입하면서, 앱이 필요로 하는 권한이 여러 기능에 흩어져 각기 다른 시점에 요청된다:

- 사진 접근·사진 좌표 접근 — 진단 화면의 `PermissionPanel`에서만 버튼으로 요청.
- 위치(장소명 지오코딩) — 목록 화면의 지오코딩 토글을 켤 때 `expo-location`로 요청.
- 알림 — 020의 설정 탭에서 자동 생성 토글을 켤 때 요청.
- 배터리 최적화 예외 — 020의 자동 생성 토글을 처음 켤 때 1회, 이후 설정 화면 상시 링크.

**실기기에서 실제로 이 흩어짐이 문제였다**: 020 release APK를 새로 설치했을 때 모든 런타임
권한이 `granted=false`였고, 사진이 하나도 실리지 않은 일기가 생성됐다(RNLlama 로그의
`has_media=0`). `adb shell pm grant`로 수동 부여해야 정상 동작했다. 앱 최초 진입부에서 필요한
권한을 한자리에서 안내·요청하는 흐름이 없다.

이 스펙은 그 통합 진입 흐름을 만든다. **새 권한을 추가하지 않는다** — 이미 앱이 요구하는 권한을
실측으로 확정하고, 한 흐름에 모아 순차 요청하며, 거부·부분 허용·재요청 경로를 정직하게 다룬다.

## Clarifications

### Session 2026-08-29

- Q: 백그라운드 생성 중 권한이 조용히 취소되는 시나리오(#3 백그라운드 안정성 과제와 겹침)를 이 스펙에서 어디까지 다루나? → A: 이 스펙은 **온보딩·재요청·상태 표시**만 다룬다. 백그라운드 실행 도중의 권한 취소 감지·`unknown` 감싸기는 #3 과제(별도 스펙)로 남긴다. 다만 온보딩을 지난 뒤 사용자가 설정에서 권한을 껐다가 앱으로 돌아왔을 때 상태가 갱신돼 보이는 것(foreground 복귀 시 재조회)까지는 이 스펙 범위다.
- Q: 020의 `AutoDiarySettings.batteryExceptionPrompted` 플래그를 이 스펙이 흡수하나? → A: 흡수한다. 배터리 예외 안내가 통합 온보딩 흐름의 한 단계가 되므로, "1회 안내했다"의 판정도 온보딩 완료 플래그와 같은 자리(`preferences/`)로 옮긴다. 020의 `batteryExceptionPrompted`는 제거하고, 020의 `applyToggleOn`에서 배터리 예외 요청 로직을 걷어낸다(자동 생성 토글은 더 이상 배터리 인텐트를 띄우지 않는다 — 온보딩이 그 역할을 한다). 자동 생성 토글을 켰는데 온보딩에서 배터리 예외 안내를 아직 못 봤다면(예: 온보딩 건너뜀), 설정 화면 상시 링크로만 안내한다.
- Q: 온보딩 흐름은 필수(강제)인가, 건너뛸 수 있나? → A: 건너뛸 수 있다(원칙 I — 권한 거부로 앱이 죽지 않는다). 각 권한 단계에서 "나중에" / "건너뛰기"가 가능하고, 마지막에 완료 플래그를 세운다. 건너뛴 권한에 의존하는 기능은 그 시점에 정직하게 상태를 드러낸다(020 N8 패턴 일반화). 완료 플래그가 서 있으면 다음 진입부터 온보딩을 자동으로 띄우지 않으며, 설정에서 재진입할 수 있다.
- Q: 필수 권한 목록을 이 스펙이 코드로 확정하나, 아니면 실측 태스크로 남기나? → A: 스펙은 "구현 시점에 실기기로 확인해 확정한다"는 요구(FR)와 검증 태스크를 둔다. plan/tasks 단계에서 실측 결과를 반영해 목록 상수를 못 박는다. 헌법 원칙 V: 안드로이드가 통로를 주지 않는 축(기간 걸음 수 등)은 애초에 `unknown`이 정상이므로 권한 목록에 넣지 않는다. iOS 전용으로 동작하는 권한이 있으면 그 사실을 목록 메타데이터에 적되, 안드로이드 온보딩 흐름에서는 건너뛴다.
- Q: 부분 허용(Android 14 "선택한 사진만 허용", `READ_MEDIA_VISUAL_USER_SELECTED`)을 온보딩에서 어떻게 다루나? → A: 부분 허용도 "허용의 한 형태"로 받아들이고 온보딩을 막지 않는다. 다만 그 상태에서는 "그날의 사진 전부를 보지 못할 수 있다"를 정직하게 표시하고(기존 `PermissionPanel`의 `limited` 문안 재사용·일반화), 전체 허용으로 올리는 설정 링크를 함께 둔다. 헌법 원칙 V의 기존 판정(사진 권한이 `limited`면 그날 신호를 `unknown`으로 접는다)은 이미 004에 있으므로 바꾸지 않는다.
- Q: 온보딩이 권한 단계를 어떤 순서로 제시하고, 사용자가 이전 단계로 돌아갈 수 있나? → A: 고정 순서 — 사진 → 사진 좌표 → 알림 → 배터리 최적화 예외. 앞으로만 진행하며(뒤로 가기 버튼 없음), 각 단계는 "허용"/"건너뛰기". 이 순서는 일상 사용에서 각 권한이 필요해지는 시점 순서다(새 사용자가 가장 먼저 부딪히는 것이 사진 수집이며, 이 기능이 고치려는 `has_media=0` 문제의 원인). 뒤로 가기가 없으므로 각 단계의 완료 여부는 별도 추적 없이 실시간 권한 상태에서 매번 다시 판정한다. 건너뛴 단계는 설정 화면의 재요청 경로(P2)와 온보딩 재실행(FR-019)으로만 되돌린다.
- Q: 020의 `auto-diary.json`에 이미 `batteryExceptionPrompted` 값이 저장된 기존 설치에서 그 필드를 제거하면 그 값을 어떻게 처리하나? → A: 1회성 시드. 새 온보딩 플래그를 처음 초기화할 때 옛 `batteryExceptionPrompted`를 읽어, `true`면 새 플래그의 "배터리 예외 안내 1회 제시함" 비트를 `true`로 세운다(이전 거부를 존중 — FR-009). 옛 필드는 020의 관대한 로더(부분 손상에 관대)가 이제 알 수 없는 필드로 조용히 버린다. 별도 마이그레이션 계층·파일 재작성은 없다.
- Q: FR-019의 "설정에서 온보딩을 다시 실행하는 진입점"을 어디에 두나? → A: 020의 "설정" 탭에 "권한" 섹션을 신설한다. 권한 상태 목록 + 거부/`blocked` 권한의 OS 설정 링크(FR-017) + 배터리 예외 상시 링크(FR-018) + 온보딩 재실행 버튼(FR-019)을 전부 한 컴포넌트에 모은다. 020이 이미 prod에 노출되는 엔드유저 설정 화면이므로 자연스럽고, 진단 화면의 `PermissionPanel`(dev 전용)과는 별개로 유지한다.
- Q: SC-009의 실기기 검증에서 "사진 반영"을 무엇으로 확인하면 통과인가? → A: 010 합성 하루(이미 심긴 08-26~28 각 3장)로 확인한다. 온보딩 후 권한이 실제로 붙어 RNLlama 로그의 `has_media > 0`이고 캡션이 심은 사진 내용을 반영하면 통과 — "경로가 도는가"만 검증한다(010 계약). 헌법 원칙 IV·V상 합성 데이터로 출력 품질을 결론짓지 않으며, 이 스펙이 검증하는 것은 "권한이 붙었는가"이지 "출력이 좋은가"가 아니다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 앱을 처음 열면 필요한 권한을 한자리에서 안내받고 허용한다 (Priority: P1)

기기 소유자가 앱을 처음(또는 새 빌드 설치 후 권한이 모두 초기화된 상태로) 연다. 일기 목록으로
바로 들어가기 전에, 앱이 하루를 쓰기 위해 무엇을 필요로 하는지를 한자리에서 순서대로 안내받는다.
각 권한마다 "무엇을 위해 필요한지"가 휴대폰이 화자인 이 앱의 언어로(모델 정보 없이, 관측하지 못하는
것을 단언하지 않고) 설명되고, 사용자가 허용하면 다음 권한으로 넘어간다. 모두 마치면 완료 표시가
서고, 다음부터는 앱을 열 때 이 흐름이 자동으로 뜨지 않는다.

**Why this priority**: 이 기능의 존재 이유다 — 통합 진입 흐름이 없으면 사용자는 각 기능을
건드릴 때마다 맥락 없는 권한 창을 만나고, 새 빌드 설치 직후처럼 권한이 전부 꺼진 상태에서는
사진 없는 일기가 조용히 생성된다.

**Independent Test**: 새로 설치한(또는 모든 권한을 초기화한) 상태로 앱을 열어, 일기 목록보다
먼저 통합 온보딩 화면이 뜨고, 각 단계에서 권한 창이 뜨며, 전부 허용하면 완료 후 일기 목록으로
진입하고 재실행 시 다시 뜨지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 모든 런타임 권한이 미결정(`undetermined`) 상태인 새 설치, **When** 앱을 처음
   연다, **Then** 일기 목록 대신 통합 온보딩 화면이 먼저 뜨고, 필요한 권한이 순서대로
   제시된다.
2. **Given** 온보딩 화면의 첫 권한 단계, **When** 사용자가 "허용" 버튼을 누른다, **Then**
   OS 권한 창이 뜨고, 사용자가 허용하면 그 단계가 완료로 바뀌며 다음 단계로 넘어간다.
3. **Given** 온보딩의 모든 단계를 마쳤다, **When** 사용자가 "시작하기"를 누른다, **Then**
   완료 플래그가 저장되고 일기 목록으로 진입한다.
4. **Given** 온보딩을 한 번 완료했다, **When** 앱을 다시 연다, **Then** 온보딩 화면은 뜨지
   않고 바로 일기 목록으로 진입한다.
5. **Given** 각 권한 단계, **When** 설명 문안을 읽는다, **Then** 모델 이름·파라미터·양자화
   정보가 없고, 휴대폰이 관측하지 못하는 것을 단언하는 문장(예: "당신이 무엇을 먹었는지
   기록합니다")이 없다.

### User Story 2 - 권한을 거부해도 앱이 죽지 않고, 무엇이 제한되는지 정직하게 안다 (Priority: P1)

사용자가 온보딩 중 일부 권한을 거부하거나 "나중에"로 건너뛴다. 앱은 멈추지 않고 온보딩을
마칠 수 있으며, 거부된 권한에 의존하는 기능(사진 수집, 장소명, 완성 알림, 배터리 예외로 인한
자동 생성 지연)이 각각 어떤 영향을 받는지 그 자리에서 정직하게 표시된다.

**Why this priority**: 헌법 원칙 I — 온디바이스 제품은 권한 거부로 무너지면 안 되고, 원칙 II —
못 하게 된 것을 숨기지 않고 드러내야 한다. 020의 "알림 권한이 없어 완성을 알릴 수 없다"
패턴을 모든 권한으로 일반화한다.

**Independent Test**: 온보딩에서 각 권한을 하나씩 거부/건너뛰기 하고, 앱이 계속 진행되며
해당 기능 화면에 "이 기능은 X 권한이 없어 …"류의 정직한 안내가 뜨는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 온보딩의 사진 권한 단계, **When** 사용자가 "건너뛰기"를 누른다, **Then**
   온보딩은 다음 단계로 넘어가고, 이후 일기가 생성돼도 사진 없이 쓰인다는 사실이 관련
   화면에 드러난다.
2. **Given** 온보딩의 알림 권한 단계에서 사용자가 거부, **When** 나중에 자동 생성이
   완료된다, **Then** 앱은 정상적으로 일기를 저장하고(생성은 알림과 무관하게 완주),
   "알림 권한이 없어 완성을 바로 알릴 수 없다"가 자동 생성 설정 화면에 표시된다.
3. **Given** 온보딩 중 아무 단계도 허용하지 않고 전부 건너뜀, **When** "시작하기"를
   누른다, **Then** 앱은 크래시 없이 일기 목록으로 진입하고, 완료 플래그가 저장돼 다음
   실행 시 온보딩이 다시 뜨지 않는다.
4. **Given** Android 14에서 사진 권한을 "선택한 사진만 허용"으로 부여, **When** 온보딩이
   그 상태를 읽는다, **Then** 부분 허용도 통과로 처리하되 "그날의 사진 전부를 보지 못할
   수 있다"가 표시되고 전체 허용으로 올리는 설정 링크가 함께 제공된다.

### User Story 3 - 나중에 마음이 바뀌면 설정에서 권한을 다시 켤 수 있다 (Priority: P2)

한 번 거부한 권한을 나중에 켜고 싶은 사용자가, 앱 안의 한 자리(설정)에서 각 권한의 현재
상태를 보고 OS 설정 화면으로 이동하는 링크를 통해 다시 허용할 수 있다. 020이 배터리 예외에
대해 두었던 "상시 링크"를 모든 권한으로 일반화하고 한 자리에 모은다.

**Why this priority**: 온보딩에서 거부한 사용자에게 되돌릴 길이 없으면, 헌법 원칙 II의 "왜
아직인지와 언제부터 가능한지를 함께 알린다"가 지켜지지 않는다. 다만 최초 진입 흐름(P1)이
동작한 뒤에 필요한 보완이므로 P2다.

**Independent Test**: 설정 화면을 열어 각 권한의 현재 상태가 표시되고, "OS 설정 열기"류
링크가 실제로 OS 설정 화면(앱 상세 또는 배터리 예외 목록)으로 이동하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 사용자가 온보딩에서 위치 권한을 거부했다, **When** 설정 화면의 권한 자리를
   연다, **Then** 위치 권한이 "거부됨" 상태로 표시되고 OS 설정으로 가는 링크가 있다.
2. **Given** 권한 상태가 `blocked`(다시 물어도 창이 안 뜸), **When** 그 권한 행을 본다,
   **Then** "설정에서 직접 바꿔야 한다"가 표시되고 인앱 "허용" 버튼 대신 OS 설정 링크만
   제공된다.
3. **Given** 사용자가 OS 설정에서 권한을 켜고 앱으로 돌아온다, **When** 앱이 포그라운드로
   복귀한다, **Then** 설정 화면의 권한 상태가 갱신돼 "허용됨"으로 보인다.
4. **Given** 자동 생성을 켰지만 배터리 최적화 예외를 준 적이 없다, **When** 설정 화면을
   본다, **Then** 배터리 예외 설명과 예외 설정으로 가는 링크가 상시 표시된다(020 FR-010의
   상시 링크를 이 자리로 흡수).

---

### Edge Cases

- 온보딩 도중 앱이 백그라운드로 갔다가 돌아오면? → 진행 중이던 단계에서 이어지며, 이미
  허용된 단계는 완료 상태를 유지한다(권한 상태를 재조회해 반영).
- 온보딩 완료 플래그는 있는데 이후 새 빌드 설치로 권한이 전부 초기화되면? → 완료 플래그는
  앱 데이터에 남아 온보딩이 자동으로 다시 뜨지 않는다. 대신 일기 목록/설정에서 "권한이
  꺼져 있어 …" 안내가 뜨고, 사용자가 설정에서 온보딩을 재실행할 수 있다. (자동 재노출을
  하지 않는 이유: 완료 플래그가 "사용자가 이 흐름을 이미 봤다"는 사실이고, 매 설치마다
  강제로 다시 띄우면 건너뛰기 선택이 무의미해진다.)
- 어떤 권한이 iOS에서만 의미가 있고 안드로이드에서는 통로가 없다면? → 온보딩 목록에서
  그 단계를 안드로이드에서는 아예 제시하지 않는다(원칙 V — 언제나 `unknown`인 축은
  화면에서 뺀다). 목록 메타데이터에는 남긴다(진단 경로).
- 사용자가 "선택한 사진만 허용"에서 사진을 0장 선택하면? → 사진 권한은 부여됐으나 볼 수
  있는 사진이 없는 상태. 004의 기존 판정(그날 사진 신호를 `none`/`unknown`으로 접음)이
  그대로 적용되고, 온보딩은 통과로 처리하되 "볼 수 있는 사진을 선택하지 않았다"를
  표시한다.
- 온보딩 중 특정 OS 권한 창이 시스템 정책으로 뜨지 않는 기기(예: 관리형 기기)에서
  "허용"을 눌러도 아무 일이 없으면? → 몇 번 눌러도 창이 안 뜨는 상태를 `blocked`처럼
  다루고 OS 설정 링크로 안내한다.

## Requirements *(mandatory)*

### Functional Requirements

#### 필수 권한 실측·식별

- **FR-001**: 구현 시점에, 앱의 각 기능(사진 수집, 사진 좌표, 장소명 지오코딩, 완성 알림,
  배터리 최적화 예외, 백그라운드 자동 생성)이 실제로 요구하는 런타임 권한을 실기기에서
  확인해 필수 권한 목록으로 확정해야 한다(MUST). 확정된 목록은 코드 안 상수로 못 박고,
  근거(어느 기능이 왜 요구하는지)를 코드 주석 또는 문서에 남긴다(MUST).
- **FR-002**: 안드로이드가 조회·요청 통로를 제공하지 않는 축(기간 걸음 수 등)은 필수 권한
  목록에 넣지 않는다(MUST NOT) — 그런 축이 언제나 `unknown`인 것은 헌법 원칙 V가 정한
  정상 상태다.
- **FR-003**: 특정 플랫폼에서만 의미가 있는 권한(예: iOS 위주로 동작하는 위치 권한)은 목록
  메타데이터에 플랫폼을 표시하고, 그 플랫폼이 아닌 온보딩 흐름에서는 해당 단계를 제시하지
  않는다(MUST).
- **FR-004**: 필수 권한 목록과 각 권한의 현재 상태를 판정하는 로직(무엇이 필요한가, 지금
  상태가 어떤가, 다음에 무엇을 요청하나)은 기기에 닿지 않는 순수 함수로 분리되어야 하며,
  기기 없이 검증 가능해야 한다(MUST). 기기에 닿는 조회·요청 자체는 `*-port.ts` 경계에만
  둔다(MUST).

#### 통합 온보딩 흐름

- **FR-005**: 앱 최초 진입 시, 온보딩 완료 플래그가 없으면 일기 목록보다 먼저 통합 온보딩
  화면을 제시해야 한다(MUST).
- **FR-006**: 온보딩은 필수 권한 목록의 각 권한을 **고정 순서**(사진 → 사진 좌표 → 알림 →
  배터리 최적화 예외)로 제시하고, 각 단계에서 그 권한이 "무엇을 위해 필요한지"를 설명해야
  한다(MUST). 흐름은 앞으로만 진행하며 이전 단계로 돌아가는 경로를 두지 않는다(MUST NOT) —
  건너뛴 단계는 설정 재요청 경로(FR-017)와 온보딩 재실행(FR-019)으로만 되돌린다.
- **FR-007**: 온보딩의 권한 설명 문안에는 모델 식별자·파라미터 수·양자화 방식이 없어야
  하며(MUST NOT, 원칙 III), 휴대폰이 관측하지 못하는 것을 단언하는 문장이 없어야 한다
  (MUST NOT, 원칙 II).
- **FR-008**: 각 권한 단계에서 사용자는 "허용"을 눌러 OS 권한 요청을 시작하거나,
  "나중에"/"건너뛰기"로 그 단계를 넘길 수 있어야 한다(MUST). OS 권한 요청은 사용자가
  버튼을 눌렀을 때만 트리거되어야 한다(MUST) — 화면이 열렸다는 이유로 자동 요청하지
  않는다(MUST NOT, 004 FR-011의 규칙 계승).
- **FR-009**: 온보딩은 020이 도입한 배터리 최적화 예외 안내를 한 단계로 흡수해야 한다
  (MUST). 이 안내는 "왜 필요한지" 설명과 함께 시스템 예외 요청 인텐트를 띄우고, 사용자가
  거부해도 재요청하지 않는다(MUST NOT). "1회 안내했다"의 판정은 온보딩 완료 플래그와 같은
  저장 자리에서 관리한다(MUST).
- **FR-010**: 020의 `AutoDiarySettings.batteryExceptionPrompted` 필드와 자동 생성 토글의
  배터리 예외 요청 로직을 제거해야 한다(MUST) — 배터리 예외 안내의 유일한 주체는 온보딩
  흐름과 설정 화면 상시 링크가 된다.
- **FR-010a**: 새 온보딩 완료 플래그를 처음 초기화할 때, 기존 `auto-diary.json`에
  `batteryExceptionPrompted: true`가 있으면 새 플래그의 "배터리 예외 안내 1회 제시함"
  값을 `true`로 1회 시드해야 한다(MUST) — 020에서 이미 배터리 예외를 거부한 사용자를
  다시 요청하지 않기 위함이다(FR-009). 옛 필드는 020 로더가 알 수 없는 필드로 버리며,
  별도 마이그레이션 함수나 파일 재작성을 두지 않는다(MUST NOT).
- **FR-011**: 모든 단계를 마치거나 건너뛰면, 온보딩 완료 플래그를 영속 저장하고 일기
  목록으로 진입해야 한다(MUST). 완료 플래그가 있으면 이후 앱 진입 시 온보딩을 자동으로
  다시 띄우지 않는다(MUST NOT).
- **FR-012**: 온보딩 완료 플래그는 `preferences/` 저장 자리에 두며, 새 저장 계층을 만들지
  않는다(MUST). 020의 자동 생성 설정과 별개 파일이되 같은 디렉터리를 쓴다.

#### 거부·부분 허용 대응

- **FR-013**: 온보딩 중 어떤 권한을 거부하거나 건너뛰어도 앱은 크래시 없이 진행되어야
  한다(MUST, 원칙 I).
- **FR-014**: 거부·건너뛴 권한에 의존하는 기능은, 그 기능이 사용되는 화면에서 어떤 영향을
  받는지 정직하게 표시해야 한다(MUST, 원칙 II). 최소한 다음을 다룬다: 사진 권한 없음 →
  일기가 사진 없이 쓰임, 위치 권한 없음 → 장소명 없음, 알림 권한 없음 → 완성을 바로 알릴
  수 없음(020 N8), 배터리 예외 없음 → 자동 생성이 크게 지연될 수 있음(020 US1 시나리오 3).
- **FR-015**: Android의 "선택한 사진만 허용"(부분 허용) 상태는 "허용의 한 형태"로
  처리하여 온보딩을 막지 않되(MUST), 그 상태에서 "그날의 사진 전부를 보지 못할 수 있다"를
  표시하고 전체 허용으로 올리는 설정 링크를 함께 제공해야 한다(MUST).
- **FR-016**: 권한 상태는 최소한 `granted`/`limited`/`denied`/`blocked`/`undetermined`를
  구분해야 하며(기존 `PermissionState` 타입 계승), `denied`(다시 요청 가능)와
  `blocked`(요청해도 창이 안 뜸)를 화면에서 구분해 다뤄야 한다(MUST, 004 FR-023 계승).

#### 재요청 경로

- **FR-017**: 020의 "설정" 탭에 "권한" 섹션을 신설하고, 그 안에 각 필수 권한의 현재
  상태를 보여주며, 거부/`blocked` 상태의 권한에 대해 OS 설정 화면(앱 상세 또는 배터리
  예외 목록)으로 이동하는 링크를 제공해야 한다(MUST). FR-017~FR-019·FR-020은 이 한
  섹션에 모인다.
- **FR-018**: 020이 배터리 최적화 예외에 대해 둔 "상시 링크(설명 + 예외 설정 이동)"를 이
  "권한" 섹션으로 흡수해야 한다(MUST).
- **FR-019**: "권한" 섹션에 사용자가 온보딩 흐름을 처음부터 다시 실행할 수 있는 진입점을
  두어야 한다(MUST). 진단 화면의 `PermissionPanel`(dev 전용)은 이와 별개로 유지한다.
- **FR-020**: 앱이 포그라운드로 복귀할 때 설정 화면의 권한 상태를 재조회해 반영해야 한다
  (MUST) — 사용자가 OS 설정에서 권한을 바꾸고 돌아온 경우를 반영하기 위함이다.

#### 경계 (헌법·기존 계약)

- **FR-021**: `process.env`는 `src/config/environment.ts`에서만 읽는다(MUST, FR-009a 계승).
- **FR-022**: `src/ui/`는 `models/roster`·`ModelAsset`에 닿지 않는다(MUST, 007 헌법 검사
  계승).
- **FR-023**: 이 스펙은 백그라운드 실행 도중의 권한 취소 감지·`unknown` 감싸기를 다루지
  않는다(범위 밖) — 그것은 #3 백그라운드 안정성 과제로 남긴다. 온보딩·재요청·상태 표시와,
  포그라운드 복귀 시 상태 재조회까지가 이 스펙의 범위다.

### Key Entities

- **필수 권한 목록(PermissionRequirement 집합)**: 앱이 요구하는 각 권한 항목. 속성:
  식별자(사진/사진좌표/위치/알림/배터리예외 등), 어느 기능이 요구하는지, 어느 플랫폼에서
  의미가 있는지, 온보딩에서 사용자에게 보일 설명 문안. 사람이 정해 상수로 못 박는다
  (원칙 V — 코드가 판정하지 않는다).
- **권한 상태(PermissionState)**: 권한 하나의 현재 상태. `granted` / `limited`(부분 허용) /
  `denied`(재요청 가능) / `blocked`(요청해도 창 안 뜸) / `undetermined`. 기존
  `src/signals/port.ts`의 타입을 계승·확장.
- **온보딩 진행 판정(순수 함수)**: 현재 권한 상태들의 집합과 필수 권한 목록을 입력으로,
  (a) 온보딩을 띄워야 하는가, (b) 다음에 제시할 단계는 무엇인가(고정 순서상 아직 안 지난
  첫 단계), (c) 각 단계의 완료 여부를 판정. 완료 여부는 별도 추적 없이 실시간 권한
  상태에서 매번 다시 판정한다(뒤로 가기가 없으므로 단계 상태를 저장할 이유가 없다).
  기기에 닿지 않는다.
- **온보딩 완료 플래그**: `preferences/` 아래 파일(020의 `auto-diary.json`과 별개, 같은
  디렉터리). "사용자가 온보딩 흐름을 한 번 마쳤거나 건너뛰었다"와 "배터리 예외 안내를
  1회 제시했다" 두 값을 담는다. 후자는 최초 초기화 시 옛 `auto-diary.json`의
  `batteryExceptionPrompted`에서 1회 시드된다(FR-010a). 실행 이력·타임스탬프 같은
  필드를 두지 않는다(원칙 IV).
- **권한 통로(`*-port.ts`)**: 기기의 권한 조회·요청·OS 설정 이동에 닿는 유일한 자리.
  기존 `PhotoPort`(사진·좌표), `NotificationPort`(알림), `BatteryExceptionPort`(배터리)를
  재사용하고, 위치 권한 조회·요청 통로를 추가한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 새로 설치한(모든 권한 미결정) 상태로 앱을 처음 열면, 일기 목록 이전에 통합
  온보딩 화면이 100% 표시된다.
- **SC-002**: 온보딩에서 필요한 권한을 모두 허용하면, 이후 첫 자동/수동 일기 생성에서
  사진이 있는 하루의 일기에 사진 내용이 반영된다(RNLlama 로그 `has_media` > 0, 020
  release 설치 시 겪은 `has_media=0` 문제가 재발하지 않는다).
- **SC-003**: 온보딩에서 모든 권한을 거부/건너뛰어도 앱이 크래시 없이 일기 목록으로
  진입하고, 재실행 시 온보딩이 다시 뜨지 않는다.
- **SC-004**: 권한을 거부한 각 기능에 대해, 그 기능 화면에서 "무엇이 제한되는지"를 알리는
  안내가 표시된다(사진·위치·알림·배터리 예외 4가지 모두).
- **SC-005**: 설정 화면에서 거부/`blocked` 상태 권한의 OS 설정 링크를 누르면 해당 OS 설정
  화면으로 이동한다.
- **SC-006**: OS 설정에서 권한을 켜고 앱으로 복귀하면, 포그라운드 복귀 시점(앱이
  `active` 상태가 되는 순간)에 재조회가 일어나 설정 화면·온보딩 화면의 해당 권한
  상태가 "허용됨"으로 갱신된다.
- **SC-007**: 권한 판정 순수 함수가 다섯 가지 상태(`granted`/`limited`/`denied`/`blocked`/
  `undetermined`)와 필수 권한 목록의 모든 조합에 대해 기기 없이 검증된다(테스트가 조합을
  직접 센다).
- **SC-008**: 온보딩·설정 화면의 권한 설명 문안에 모델 식별자·파라미터·양자화 문자열이
  0건이고(소스 검사), 관측 불가한 것을 단언하는 문장이 없다(리뷰).
- **SC-009**: 실기기에서 최소 1회, 새 설치 → 온보딩 → 권한 허용 → 일기 생성의 전체
  흐름이 확인된다(원칙 V). "사진 반영"은 010 합성 하루(08-26~28)로 확인하며, RNLlama
  로그 `has_media > 0` + 캡션이 심은 사진 내용 반영이면 통과("경로가 도는가"만, 010
  계약). 새 네이티브 모듈을 들이지 않으면 debug 빌드 1회로 충분하다.

## Assumptions

- 새 네이티브 모듈을 도입하지 않는다. 기존 `expo-media-library`·`expo-location`·
  `expo-notifications`·`expo-intent-launcher`의 권한 API만 재사용한다. 따라서 실기기 검증은
  debug 빌드 1회로 충분하고 release 재확인은 불필요하다(헌법 원칙 V, 012에서 확립한 기준).
- 저장은 `preferences/` 디렉터리를 재사용하며 새 저장 계층을 만들지 않는다(020·017의
  `expo-file-system` 방식).
- 위치 권한은 안드로이드에서 `Geocoder` 장소명(017)을 위해 쓰이나 주로 iOS 위주로
  동작한다는 것이 기존 코드의 전제다(App.tsx 주석). 안드로이드 온보딩에서 이 단계를
  제시할지는 FR-001의 실측 결과에 따른다.
- 배터리 최적화 예외는 권한이 아니라 시스템 설정 토글이지만, 사용자 관점에서 "허용해야
  하는 것" 목록의 일부로 온보딩과 재요청 경로에서 다른 권한과 함께 다룬다.
- Android 14의 부분 사진 접근(`READ_MEDIA_VISUAL_USER_SELECTED`) 상태를 `expo-media-library`가
  `limited`로 노출하는지는 004 시점에 미확인이었다(`src/signals/port.ts` 주석). FR-001의
  실측이 이를 확정한다 — 노출하지 않으면 부분 허용은 `granted`로 보이고, "그날 사진 전부를
  보지 못할 수 있다" 안내는 사진 조회 결과(볼 수 있는 사진 수)로 갈음한다.
- 온보딩 화면은 새 화면 컴포넌트를 추가하고, 020의 "설정" 탭에 "권한" 섹션 컴포넌트를
  추가한다. 진단 화면의 `PermissionPanel`은 개발자 경로로 그대로 유지한다(사용자 온보딩·
  설정 권한 섹션과 진단 패널은 목적이 다르다 — 004 계약).
- 이 스펙과 별개로 사람이 수행할 020 잔여 실기기 검증(T053·T053a·T053b·T054 잔여·T055),
  그리고 이번 세션에 커밋된 `clearStaleLocksOnStart` 수정의 release APK 반영은 이 스펙의
  범위 밖이다.
