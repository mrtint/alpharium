## §1. 중단·재개를 무엇으로 구현하는가

**결정**: `expo-file-system` 57의 `DownloadTask`를 쓴다. **직접 구현하지 않는다.**

**확인** (`node_modules/expo-file-system/build/NetworkTasks.d.ts` 직접 읽음):

```
File.createDownloadTask(url, destination, options): DownloadTask
  .downloadAsync(): Promise<File | null>   // 중단되면 null
  .pause() / .pauseAsync(): Promise<void>
  .resumeAsync(): Promise<File | null>
  .cancel()
  .savable(): DownloadPauseState           // paused 상태에서만 부를 수 있다
  static fromSavable(state, options): DownloadTask
  .addListener('progress', ({ bytesWritten, totalBytes }) => …)
  .state: 'idle' | 'active' | 'paused' | 'completed' | 'cancelled' | 'error'
```

**근거**: FR-014(중단), FR-015(이어받기), FR-016(앱 종료 후에도 이어받기), FR-013(진행률)이
전부 이 하나로 덮인다. 특히 FR-016은 우리가 직접 만들기 어렵다 — HTTP Range 요청과 부분
파일 관리를 손으로 짜야 하고, 그것이 이 기능의 본체가 아니다.

**FR-016이 성립하는 방식**: `savable()`이 돌려주는 `DownloadPauseState`를 **기기에 저장**하고,
앱을 다시 열었을 때 `fromSavable()`로 되살린다. 이 값은 직렬화 가능하며 콜백·AbortSignal을
담지 않는다(타입 정의에 명시). 그래서 JSON으로 남길 수 있다.

**주의 — `state`가 `paused`일 때만 `savable()`을 부를 수 있다.** 앱이 갑자기 죽으면
`savable()`을 부를 기회가 없다. 그때는 저장된 상태가 없으므로 **"받다 말았음"이되 이어받기
정보가 없는 경우**가 생긴다. 이것을 "받지 않음"으로 뭉개지 않는다(FR-006) — 부분 파일이
공간을 먹고 있으므로 지울 수 있어야 한다(FR-029).

**대안으로 검토한 것**:
- *직접 HTTP Range 구현* — 기각. 재개 로직이 이 기능의 본체가 아니고, 플랫폼별 함정이 많다.
- *`expo-file-system/legacy`의 `createDownloadResumable`* — 기각. 타입 정의에 deprecated로
  표시돼 있고 "will throw in runtime"이라 적혀 있다(`legacyWarnings.d.ts`). 새 API가 있다.
- *중단·재개 없이 매번 처음부터* — 기각. FR-015가 금지한다. GB 파일에서 재시작은 사용자의
  데이터를 두 번 쓰는 것이다.

## §2. 내용 검증을 무엇으로 하는가

**결정**: `File.info({ md5: true })`가 주는 **MD5**를 쓴다. 새 의존성을 들이지 않는다.

**확인** (`build/File.types.d.ts` 직접 읽음): `FileInfo`에 `md5?: string`이 있고,
`InfoOptions`에 `md5?: boolean`이 있다. 즉 파일의 MD5를 파일 시스템 모듈이 계산해 준다.

**판단 — MD5의 암호학적 취약성이 여기서 문제가 되지 않는 이유**:

우리가 막으려는 것은 **전송 중 훼손**이다(FR-021: "받으려던 그 파일인지"). 악의적 위조가
아니다. 위조를 걱정하는 상황이라면 — 공격자가 우리 서버나 사용자의 네트워크를 장악한 상황 —
모델 파일을 바꾸는 것보다 **앱 자체를 바꾸는 편이 쉽고**, 그 위협은 이 기능이 다룰 수 있는
범위 밖이다. MD5는 무작위 훼손을 잡는 데 충분하고, 그것이 명세가 요구한 전부다.

**더 강한 것이 필요해지면**: `expo-crypto`를 들여 SHA-256을 쓴다. 다만 그때는 파일을 직접
읽어 해시해야 하고(GB 스트리밍), MD5는 네이티브가 계산해 준다. **지금 그 비용을 치를 근거가
없다** — 근거 없이 강한 쪽을 고르는 것도 추측이다(원칙 V).

**대안으로 검토한 것**:
- *크기만 비교* — 기각. 명확화 세션 Q1에서 사용자가 명시적으로 배제했다. 크기가 같은 훼손을
  못 잡고, 그러면 원칙 V의 "받았는데 깨졌음"이 사실상 판정되지 않는다.
- *`expo-crypto`로 SHA-256* — 보류. 위 근거로 지금은 과하다. 필요해지면 검증 기준이 코드
  안쪽에 한 곳으로 모여 있으므로(FR-024) 갈아끼우기 쉽다.
- *모델 파일 형식(GGUF 헤더)만 확인* — 기각. 앞부분만 보므로 뒷부분 훼손을 못 잡는다.

## §3. 저장 공간 여유를 얼마나 요구하는가

**결정**: **예상 크기의 1.15배**를 요구한다. 즉 모델 크기의 **15% 여유**.

**확인**: `Paths.availableDiskSpace`와 `Paths.totalDiskSpace`가 바이트로 있다
(`build/Paths.d.ts`). 별도 패키지가 필요 없다.

**판단 근거** (FR-019c가 "실측으로 정한다"고 했으므로 **이 값은 잠정이며 실기기에서
확인한다**):

15%를 고른 셈법은 셋이다.
1. **이어받기의 임시 파일** — 재개 중에는 부분 파일과 최종 파일이 잠시 함께 존재할 수 있다.
2. **안드로이드의 공간 확보 동작** — 여유가 0에 가까우면 시스템이 파일을 지우기 시작하고,
   그 대상에 방금 받은 모델이 들어갈 수 있다(FR-021e의 상황을 우리가 만드는 셈).
3. **검증 결과·중단 상태 파일** — 작지만 0은 아니다.

**이 값은 추측이었고, 실측으로 확인했다** (2026-08-14, SM-G986N):

| 무엇 | 값 |
| --- | --- |
| 받기 전 남은 공간 | 182,380,968 KB |
| kanana(1.42GB) 받은 뒤 | 180,892,344 KB |
| 실제로 줄어든 양 | 1,488,624 KB ≈ **1.42GB** |
| `models/` 디렉터리 크기 | 1,522,800,390 B (파일 1,522,796,768 B + 메타 3,622 B) |

**임시 파일이 남지 않았다.** 줄어든 양이 파일 크기와 거의 같고(차이 3.5KB는 메타데이터),
받는 도중 최종 파일에 직접 쓰므로 두 배를 쓰지 않았다.

**그래서 1.15배(15% 여유)는 실측 기준으로 과하다** — 이어받기의 임시 파일이 실제로는
생기지 않았기 때문이다. 다만 **줄이지 않는다**:

1. 안드로이드가 공간 확보를 시작하는 임계는 기기·제조사마다 다르고, 우리는 한 대에서만
   쟀다. 한 번의 관측으로 전 기기의 안전선을 정할 수 없다.
2. 여유가 남는 쪽의 손해는 "받을 수 있는데 거부한다"이고, 모자란 쪽의 손해는 "받은 모델이
   지워진다"이다. **후자가 훨씬 무겁다.**

기기를 더 재게 되면 그때 다시 본다. 지금은 **한 대에서 확인했다**는 사실과 함께 남긴다.

**대안으로 검토한 것**:
- *딱 맞으면 통과* — 기각. 명확화 세션 Q4에서 배제했다.
- *고정 여유(예: +500MB)* — 기각. 기기마다 사정이 다르고, 작은 모델에는 과하고 큰 모델에는
  모자란다. 비례가 자연스럽다.
- *명세가 정하지 않고 넘김* — 기각. 그러면 구현자가 아무 숫자나 쓰고 근거가 남지 않는다.

## §4. 검증 결과와 중단 상태를 어디에 어떻게 남기는가

**결정**: `Paths.document` 아래 **모델 전용 디렉터리**에 두되, **모델 파일과 메타데이터를
분리**한다.

```
Paths.document/
├── diary/                      # 002가 쓰는 자리. 건드리지 않는다
└── models/
    ├── <자산키>.gguf           # 모델 파일 자체
    └── state.json              # 검증 결과 + 중단된 내려받기 상태
```

**근거**:

- **`Paths.document`이지 `Paths.cache`가 아니다.** 타입 정의에 `cache`는 "can be deleted by
  the system when the device runs low on storage"라고 적혀 있다. 모델은 GB이고 다시 받는
  비용이 크므로 시스템이 마음대로 지우는 자리에 두지 않는다. **다만 document도 절대
  안전하지는 않다**(사용자가 지울 수 있다) — 그래서 FR-021e가 필요하다.
- **메타데이터를 한 파일에 모은다.** 002의 일기는 날짜별로 쪼갰지만(그쪽은 항목이 계속
  늘어난다), 여기는 **캐릭터가 다섯으로 고정**이라 한 파일이 낫다. 상태를 물을 때 한 번만
  읽으면 되고, 그것이 SC-016(조회가 파일 크기와 무관)에 맞는다.
- **파일 이름이 모델 이름이 되지 않게 한다**(원칙 III). 사용자가 파일 관리자로 열어도
  모델 이름이 보이지 않아야 한다. `<자산키>`는 로스터가 정하는 불투명한 값이며, 캐릭터
  식별자를 그대로 쓰지 않는다 — 캐릭터 식별자는 화면에도 쓰이므로 파일명과 같으면 매핑이
  드러난다.

**대안으로 검토한 것**:
- *`AsyncStorage`* — 기각. 설치돼 있지 않고, 파일 시스템으로 충분하다.
- *캐릭터별 메타데이터 파일* — 기각. 상태 조회가 다섯 번 읽기가 된다. 이득이 없다.
- *메타데이터 없이 파일 존재만으로 판정* — 기각. FR-021c가 금지한다. 검증한 기록이 없으면
  쓸 수 없다.

## §5. 한 번에 하나를 어떻게 강제하는가

**결정**: 진행 중인 작업을 **모듈 수준 값 하나**로 들고, 뒤의 요청은 거부한다.
**저장소에 남기지 않는다.**

**근거**: 002의 `createPipeline`이 `running` Set으로 중복 실행을 막은 것과 같은 판단이며,
같은 이유로 **메모리에만 둔다** — 저장소에 "진행 중"을 남기면 앱이 죽었을 때 영원히
진행 중인 캐릭터가 생긴다. 앱이 다시 열리면 진행 중인 것은 없고, 중단 상태(§1)만 남아 있어
이어받을 수 있다.

**중단 상태는 저장하지만 진행 중 표시는 저장하지 않는다** — 둘은 다른 것이다. 전자는 "여기까지
받았다"는 사실이고 후자는 "지금 받고 있다"는 순간의 상태다. 이 구분이 흐려지면 002가 피한
함정에 다시 빠진다.

## §6. 002의 파이프라인에 어떻게 잇는가

**결정**: `PipelineStage`에 갈래를 하나 더하고, **생성 단계 앞에서** 준비 상태를 묻는다.

**근거**: FR-008이 "준비되지 않은 캐릭터로 생성을 요청하면 모델이 없다는 사실이 결과"라고
했다. 002의 파이프라인은 이미 단계별로 멈추고 그 자리를 보고하므로(FR-019 of 002), 갈래를
더하는 것으로 족하다.

**어디에 넣는가**: `request-build` 다음, `generation` 앞. 요청이 만들어져야 어느 캐릭터인지
알 수 있고, 생성을 시도하기 전에 막아야 한다.

**002를 얼마나 고치는가**: `PipelineStage`에 값 하나, `PipelineDeps`에 준비 상태를 묻는
함수 하나. **`store.ts`·`types.ts`·`request.ts`는 손대지 않는다.** 002의 계약을 넓히는 것이지
바꾸는 것이 아니다.

## §7. `expo-file-system`을 선언에 올린다

**결정**: `package.json`의 `dependencies`에 `expo-file-system` 을 추가한다.

**확인**: 설치본은 `57.0.2`이고 `package.json`에 선언이 없다. `npx expo install --check`는
"Dependencies are up to date"를 돌려준다 — 선언되지 않은 것은 검사하지 않기 때문이다.

**근거**: `llama.rn`이 같은 상태였고 001에서 선언에 올렸다(AGENTS.md). 002가 저장에 쓰기
시작했고 이 기능이 크게 의존하므로 더 미룰 이유가 없다. **선언되지 않은 의존은 다음 설치에서
사라질 수 있다.**

**주의**: 버전을 추측하지 않는다. 설치본이 실증된 쪽이므로 **설치본에 선언을 맞춘다** —
001에서 SDK 54/57 어긋남을 해소한 것과 같은 방향이다.

공개된 표에서 옮겨 적어도 그 표가 우리가 받을 그 파일을 가리킨다는 보장이 없고, 틀리면

판정의 근거가 될 수 있다(헌법 원칙 V).

그래서 로스터의 `expectedBytes`·`md5`는 **비워 둔 채로 두고**, `roster.test.ts`의 R2·R3이
빨간불로 남는다. 그 빨간불이 "아직 재지 않았다"를 드러내는 장치다.

**이것이 §3의 공간 여유 비율과 같은 성질의 미해결이다** — 둘 다 실기기에서 재야 하고,
둘 다 지금 숫자를 적으면 추측이 사실인 척 굳는다. T042·T043에서 함께 확정한다.

**받는 동안 크기·지문을 모르면 무엇이 되는가**:
- 공간 사전 판정(FR-019)은 **첫 내려받기에서 쓸 수 없다.** 서버가 주는 `Content-Length`로
  갈음하되, 그것도 없으면(`-1`) 판정을 건너뛰고 받는다 — 모르는 것을 지어내지 않는다
- 완료 판정(FR-001b)은 서버가 알려준 총량에 이르렀는지로 본다
- 내용 검증(FR-021)은 **첫 회에는 지문을 비교할 대상이 없으므로**, 받은 파일의 지문을
  **계산해서 기록**한다. 그 값이 로스터에 들어가면 이후부터 진짜 검증이 된다

이 세 가지가 「값이 아직 없을 때」의 동작이며, 계약이 이미 `null`/"모름"을 표현할 수
있게 되어 있어 새 갈래가 필요하지 않다.
