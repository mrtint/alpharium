# Feature Specification: 시간대 지정 자동 일기 작성과 완성 알림

**Feature Branch**: `020-scheduled-diary-notification`

**Created**: 2026-08-28

**Status**: Draft

**Input**: User description: "사용자가 원하는 시각(예: 매일 오전 7시가 기본값, 8시나 9시 등 다른 시간으로
선택 가능)에 대략적으로 맞춰 일기가 자동 생성되고, 완성되면 알림이 발생해 사용자가 눌러서 방금 쓰인
일기를 바로 볼 수 있게 한다."

## 이 스펙의 전제 — 019의 결론

이 스펙은 019(백그라운드 자동 일기 생성 기술 검증, 스파이크)의 실측 결론을
전제로 시작한다. 019는 기능이 아니라 검증이었고, 이 스펙이 그 검증 결과를
근거로 처음 만드는 **실제 배포 기능**이다.

- 화면이 꺼지고 잠긴 상태에서 백그라운드 자동 생성(OS 표준 주기적 작업
  예약)이 실제로 완주한다는 것이 실기기로 확인됐다(`specs/
  019-background-diary-feasibility/findings.md`).
- OS는 **정확한 시각 실행을 보장하지 않는다.** 등록 가능한 최소 반복
  간격(15분)도 배터리 최적화 기본값에서는 하루 1~2회로 억제됐고
  (최대 19시간 33분 지연 실측), 배터리 최적화 예외를 주면 10~32분
  간격으로 좁혀졌다. 이 스펙의 "시각 지정"은 **정확한 시각이 아니라
  근사치**라는 것이 출발선이다 — 사용자가 "7시"를 고르면 "7시 근방의
  어느 시점"이 실제 동작이다.
- alarm 계열(정확 시각 예약 API)은 019에서 배터리 최적화와의 충돌이
  더 크다는 이유로 의도적으로 배제됐다. 이 스펙도 그 결정을 유지한다
  (Assumptions 참고) — 사용자가 이해하고 받아들이는 오차 범위 안에서
  동작하는 것을 전제로, OS 표준 경로만 쓴다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 원하는 시간대를 고르고, 그 근방에 일기가 쓰인다 (Priority: P1)

기기 소유자가 설정 화면에서 "몇 시쯤 일기를 쓸지"를 고른다(기본값 오전
7시, 다른 시각으로 변경 가능). 그 시각이 지나고 얼마 뒤, 앱을 열지 않은
채로도 전날 일기가 자동으로 완성돼 있다.

**Why this priority**: 이 기능의 존재 이유다 — 시각을 고를 수 없거나
아무 때나 쓰이면 "원하는 시간대에" 라는 요청 자체가 충족되지 않는다.

**Independent Test**: 설정에서 시각을 변경하고, 그 시각 근방에 실제로
생성이 트리거되는지(정확히 그 순간이 아니라 합리적인 오차 범위 안에서)
확인하는 것만으로 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 사용자가 설정에서 오전 7시(기본값)를 그대로 둔다, **When**
   그날 오전 7시가 지나고 하루 경계가 넘어간 뒤, **Then** 오전 7시
   근방의 합리적인 시간 안에(정확한 분 단위가 아님) 전날 일기가 생성돼
   있다.
2. **Given** 사용자가 설정에서 시각을 오전 9시로 바꾼다, **When** 다음
   번 생성 기회부터, **Then** 이후의 자동 생성은 오전 9시 근방을
   목표로 시도된다(이전 설정인 7시가 아니라).
3. **Given** 사용자가 배터리 최적화 예외를 주지 않은 기본 상태다,
   **When** 목표 시각이 지나도 OS가 실행을 크게 지연시킨다, **Then**
   그래도 하루 안에는(또는 다음 실행 기회에는) 생성이 시도되며, 이
   지연 가능성 자체를 사용자가 설정 화면에서 미리 안내받는다.

---

### User Story 2 - 완성되면 알림이 오고, 눌러서 바로 본다 (Priority: P1)

일기 생성이 성공적으로 끝나면 기기에 알림이 뜬다. 사용자가 그 알림을
누르면 앱이 열리며 방금 생성된 일기 상세 화면으로 바로 이동한다.

**Why this priority**: 알림 없이 자동 생성만 있으면 사용자가 매번 앱을
열어 확인해야 하므로, "자동으로 쓰이고 알려준다"는 요청의 핵심 절반은
알림이다. User Story 1과 대등하게 P1이다 — 시각 없이 알림만 있어도,
알림 없이 시각만 있어도 이 기능은 완성되지 않는다.

**Independent Test**: 자동 생성이 완료되는 순간을 인위적으로 만들고,
알림이 뜨는지·탭했을 때 정확히 그 일기의 상세 화면으로 가는지 확인하는
것으로 독립적으로 검증할 수 있다(User Story 1의 "시각 근사"와 무관하게
"완료 → 알림 → 이동" 경로만 떼어 테스트 가능).

**Acceptance Scenarios**:

1. **Given** 자동 생성이 시작됐다, **When** 생성이 성공적으로 완료된다
   (판정 4갈래를 통과해 저장까지 끝난다), **Then** 기기에 알림이 뜬다.
2. **Given** 알림이 떠 있다, **When** 사용자가 알림을 누른다, **Then**
   앱이 열리며 방금 생성된 그 날짜의 일기 상세 화면이 곧바로 보인다
   (목록 화면을 거치지 않는다).
3. **Given** 자동 생성이 실패했다(판정 거부 또는 중단), **When** 그
   결과가 확정된다, **Then** 알림이 뜨지 않는다 — 실패를 알림으로
   포장해 사용자를 재촉하지 않는다.
4. **Given** 사용자가 이미 그날 일기를 확인한 뒤 다시 앱을 연다,
   **When** 같은 날짜에 대해 두 번째 자동 생성 알림이 발생할 상황이
   된다, **Then** 같은 날짜에 대해 중복 알림이 쌓이지 않는다.

---

### User Story 3 - 화면에서 쓰는 것과 자동으로 쓰이는 것이 서로를 방해하지 않는다 (Priority: P2)

사용자가 화면을 열어 "일기 쓰기"를 누른 순간과, 자동 생성이 트리거되는
순간이 겹칠 수 있다. 이 경우에도 결과가 깨지거나(중복 저장, 손상된
파일) 조용히 하나가 사라지는 일이 없어야 한다.

**Why this priority**: 019가 이 경합을 "막지 않고 관측만" 하고
미해결로 남긴 것(E1 잠금 설계)이다. 실제 기능으로 배포하려면 사용자가
우연히 이 상황을 만들었을 때 무엇이 보장되는지가 있어야 한다 — 다만
이것이 없어도 User Story 1·2는 각자 독립적으로 가치가 있으므로 P2다.

**Independent Test**: 화면에서 쓰기를 누른 직후 자동 생성을 인위적으로
겹쳐 트리거해, 최종적으로 그 날짜의 일기가 정확히 하나만 존재하는지
확인하는 것으로 독립적으로 검증할 수 있다.

**Acceptance Scenarios**:

1. **Given** 화면에서 "일기 쓰기"가 진행 중이다, **When** 같은 날짜에
   대한 자동 생성이 거의 동시에 트리거된다, **Then** 최종적으로 그
   날짜의 일기는 하나만 존재하며 어느 쪽 결과인지 알 수 있다(둘 다
   성공해서 값이 섞이거나 파일이 손상되지 않는다).
2. **Given** 자동 생성이 진행 중이다, **When** 사용자가 그 사이 화면을
   열어 같은 날짜를 다시 쓰려고 한다, **Then** 화면은 이미 진행 중인
   생성이 있다는 것을 사용자에게 알리거나, 그 결과를 기다리게 한다 —
   조용히 새로 시작해 두 개의 생성이 동시에 도는 상태를 만들지 않는다.

---

### Edge Cases

- 하루 안에 자동 생성 기회가 아예 없었던 경우(19번 실측처럼 OS가 크게
  지연시킨 경우), 다음날 같은 목표 시각까지도 여전히 전날 일기가 없을
  수 있다 — 이 경우 그 다음 기회에 자동으로 재시도하는지, 아니면
  사용자가 화면에서 수동으로 채워야 하는지가 명확해야 한다.
- 사용자가 목표 시각을 바꾼 직후, 이미 예약돼 있던 이전 시각 기준의
  다음 실행이 취소 없이 그대로 도는지, 새 시각으로 재조정되는지 다뤄야
  한다.
- 사진·위치 권한이 자동 생성 시점에 회수돼 있는 경우(019가 이미
  "사진 권한은 확인했으나 좌표 권한 회수는 미확인"으로 남긴 부분) —
  권한이 없어도 생성은 계속 진행되고(사진 없음/좌표 모름으로), 그
  사실이 알림이나 일기 자체에서 사용자에게 숨겨지지 않아야 한다.
- 배터리 최적화 예외를 사용자가 거부한 채로 계속 쓰는 경우 — 기능이
  "고장"이 아니라 "지연이 크다"는 상태로 계속 동작해야 하며, 예외를
  주지 않아도 기능 자체는 (느리게라도) 동작한다.
- 알림을 누르지 않고 무시한 채 다음날이 되는 경우 — 안 읽은 알림이
  계속 쌓이는지, 최신 하나로 대체되는지가 정의돼야 한다.
- 앱이 아예 삭제되거나 알림 권한이 거부된 기기에서는 자동 생성 자체는
  이 스펙의 범위에서 계속 시도할 수 있지만, 완료를 알릴 방법이 없다 —
  이 경우 사용자가 직접 앱을 열어 확인하는 기존 경로가 유일한 대안임을
  명시한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 사용자는 설정 화면에서 자동 생성을 시도할 대략적인 시각을
  선택할 수 있어야 한다(MUST). 기본값은 오전 7시다.
- **FR-002**: 시스템은 선택된 시각이 "정확한 시각이 아니라 근사치"임을
  설정 화면에서 사용자에게 명확히 알려야 한다(MUST) — 헌법 원칙 II
  (근거 없는 확신 금지)와 같은 정신으로, 기능이 보장하지 않는 정밀도를
  암시하는 문구(예: "매일 오전 7시 정각에")를 쓰지 않는다.
- **FR-003**: 시스템은 하루 경계(04:00)가 지난 뒤 사용자가 선택한
  목표 시각 근방에 백그라운드 자동 생성을 시도해야 한다(MUST) — 정확한
  트리거 방식은 019가 검증한 OS 표준 주기적 작업 예약 경로를 그대로
  쓴다(alarm 계열 미사용, Assumptions 참고).
- **FR-004**: 자동 생성이 성공적으로 완료되면(판정 4갈래를 통과해
  저장까지 끝나면) 시스템은 로컬 알림을 발생시켜야 한다(MUST).
- **FR-005**: 자동 생성이 실패하거나 거부되면(판정에서 걸러지거나
  중단되면) 시스템은 알림을 발생시키지 않아야 한다(MUST NOT) — 실패를
  성공처럼 포장하지 않는다(헌법 원칙 I과 같은 정신).
- **FR-006**: 사용자가 알림을 누르면 시스템은 목록 화면을 거치지 않고
  해당 날짜의 일기 상세 화면으로 곧바로 이동해야 한다(MUST).
- **FR-007**: 같은 날짜에 대해 시스템은 중복 알림을 쌓지 않아야 한다
  (MUST NOT) — 이미 그 날짜의 알림이 떠 있거나 사용자가 이미 확인한
  뒤라면 같은 날짜로 다시 알리지 않는다.
- **FR-008**: 화면에서 진행 중인 수동 생성과 자동 생성이 같은 날짜에
  대해 겹치는 경우, 시스템은 최종적으로 그 날짜의 일기가 정확히 하나만
  존재하도록 보장해야 한다(MUST) — 019의 E1(한 번에 하나의 추론
  엔진만 열림) 제약을 실제로 지키는 잠금 또는 조정 메커니즘이 필요하다.
- **FR-009**: 시스템은 자동 생성을 사용자가 켜고 끌 수 있어야 한다
  (MUST) — 원치 않으면 이 기능 전체를 끌 수 있다.
- **FR-010**: 시스템은 배터리 최적화 예외가 이 기능의 시각 정확도에
  영향을 준다는 것을 사용자에게 설정 화면에서 안내하고, 예외를
  요청하는 경로를 제공해야 한다(MUST) — 다만 예외 부여는 사용자의
  선택이며 강제하지 않는다(안드로이드 정책상 남용 금지, 019 findings.md
  "다음 스펙에서 고려할 사항" 참고).
- **FR-011**: 자동 생성으로 저장된 일기는 화면에서 수동으로 쓴 일기와
  동일한 판정·저장 경로를 거쳐야 한다(MUST) — 자동이라는 이유로 판정을
  건너뛰거나 완화하지 않는다(019 FR-006과 동일한 원칙 계승).
- **FR-012**: 알림 문구는 헌법 원칙 II(관측된 것만 단언)를 지켜야
  한다(MUST) — 예를 들어 일기 내용을 알림에 미리 요약해 보여주지
  않는다(본문을 열어야 확인 가능), "오늘도 즐거운 하루였네요" 같은
  알림 문구 자체의 지어내기도 포함한다.

### Key Entities

- **자동 생성 설정**: 사용자가 고른 목표 시각(시:분 또는 시 단위),
  자동 생성 켜짐/꺼짐 여부. 기존 캐릭터 선택(007)과 같은 층위의 사용자
  설정이며 새로운 영속 저장 방식을 만들지 않고 기존 설정 저장 경로를
  재사용한다(Assumptions).
- **알림 이벤트**: 어떤 날짜의 일기가 완성됐는지, 이미 알림을 보냈는지
  여부. 일기 엔티티(`DiaryEntry`) 자체에 알림 발송 여부를 더할지,
  별도로 관리할지는 계획 단계에서 정한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자가 설정에서 목표 시각을 고르면, 별도 설명 없이도
  "이 시각에 딱 맞춰지는 게 아니라 이 근방에 쓰인다"는 것을 화면 문구만
  보고 이해할 수 있다.
- **SC-002**: 배터리 최적화 예외가 없는 기본 상태에서도, 목표 시각이
  지난 뒤 24시간 안에는 최소 1회 자동 생성이 시도된다(019 실측 기준
  최악의 경우에도 하루 안에는 시도됨).
- **SC-003**: 배터리 최적화 예외를 준 상태에서는, 목표 시각으로부터
  1시간 이내에 자동 생성이 시도되는 비율이 실측으로 확인 가능한 수준
  으로 높다(정확한 수치는 계획 단계에서 019의 실측 데이터를 근거로
  구체화한다).
- **SC-004**: 자동 생성이 성공한 경우, 사용자가 알림을 받고 누르면
  3번의 조작(알림 탭 한 번) 이내로 해당 일기를 읽을 수 있다.
- **SC-005**: 화면 수동 쓰기와 자동 생성이 겹치는 상황을 인위적으로
  100번 재현해도, 같은 날짜에 대해 일기가 2개 이상 만들어지거나 손상된
  파일이 발생하는 사례가 0건이다.
- **SC-006**: 실패한 자동 생성 시도가 알림으로 사용자에게 노출되는
  사례가 0건이다.

## Assumptions

- 이 스펙은 019가 검증한 트리거 경로(OS 표준 주기적 작업 예약,
  `expo-background-task`/WorkManager)를 그대로 쓴다 — 정확 시각
  alarm 계열 API로 바꾸는 것은 이 스펙의 범위 밖이다. "대략적인
  시각 선택"이라는 요청 자체가 이미 근사치를 전제하므로, 더 정밀한
  트리거 방식이 필요하다는 결론이 나오면 별도 스펙에서 재검토한다.
- 자동 생성 설정(목표 시각, 켜짐/꺼짐)은 007의 캐릭터 선택과 같은
  기존 사용자 설정 저장 경로를 재사용한다 — 새로운 저장 계층을 만들지
  않는다.
- 알림은 이 기기에서 로컬로 발생하는 알림이며, 원격 푸시(서버 발송)는
  이 스펙의 범위 밖이다 — 이 앱은 서버가 없다(온디바이스 우선 원칙).
- 배터리 최적화 예외 요청은 사용자가 명시적으로 동의해야 하며,
  자동으로 요청 대화상자를 반복해서 띄우지 않는다(안드로이드 정책·
  사용자 경험 양쪽 이유).
- User Story 3(경합 방지)의 정확한 구현 방식(잠금 파일, 상태 플래그,
  큐 등)은 이 스펙이 정하지 않는다 — "결과가 하나만 존재해야 한다"는
  요구사항만 고정하고, 방법은 계획 단계에서 정한다.
- 이 스펙은 019가 명시한 "이 기기·이 OS 버전 기준" 한계를 계승한다 —
  모든 안드로이드 기기·제조사에서 같은 시각 정확도가 나온다고 가정하지
  않는다.
