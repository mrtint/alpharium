# Quickstart: 오늘의 일기

**Date**: 2026-08-22 | **Plan**: [plan.md](plan.md) | **Contracts**:
[day-boundary.md](contracts/day-boundary.md) ·
[overwrite-confirm.md](contracts/overwrite-confirm.md) ·

**이 기능이 실제로 도는지 확인하는 절차다.** 기기 없는 검증(A)이 전부 통과해도
**온디바이스는 검증되지 않은 상태다**(헌법 원칙 V) — B가 끝나야 완료다. 다만
**정오 경계는 실기기에서 검증하기 특히 어렵다**(C1 참조) — 그 한계를 미리 안고
간다.

## A. 기기 없이 (항상 돈다)

```
npm test          # 기기 불필요 갈래
npm run lint      # eslint + tsc + 헌법 검사
```

| 통과 기준 | 값 |
| --- | --- |
| `npm test` | 011의 **1190개**보다 늘어난 수, 실패 0 |
| `npm run lint` | exit 0 (헌법 검사 포함) |

### A1. 위반을 주입해 그물을 확인한다

**초록불을 믿기 전에 일부러 어겨 본다.**

| # | 주입 | 걸려야 하는 것 |
| --- | --- | --- |
| 1 | `pipeline.ts`의 게이트를 `isDayWritable` 대신 옛 `isDayClosed`로 되돌린다 | day-boundary 계약 §3의 2번 행 — **이 기능의 핵심 검증** |
| 2 | `selectableDays()`가 정오 이후에도 그그제를 그대로 돌려준다(오늘을 안 넣는다) | day-boundary 계약 §2의 2번 행, I2 |
| 3 | `USER_VISIBLE_SIGNAL_AXES.steps`를 코드가 `signal.kind`를 보고 동적으로 정하게 바꾼다 | signal-visibility 계약 S1이 상수값 자체를 직접 읽는 방식이면 안 걸릴 수 있다 — **런타임 동작(프롬프트에 걸음 수가 실제로 안 실리는지)까지 확인하는 테스트가 걸어야 한다** |
| 4 | `DAY_STILL_OPEN` 문장을 사진이 `known`일 때만 붙게 한다 | signal-visibility 계약 §2의 2번 행(FR-004) |
| 5 | `confirm-overwrite`에 `existingText: string` 필드를 추가한다 | overwrite-confirm 계약 C1(선언을 직접 읽는 테스트) **+ `tsc`** |
| 6 | `collect.ts`에 상한 상수를 다시 넣되 이름만 바꾼다(예: `MAX_PHOTOS = 500`) | signal-visibility 계약 L1 — 상수 자체가 없는지 소스를 검사 |
| 7 | 사진 조회 실패를 `unknown` 대신 `known`(빈 배열)으로 처리한다 | signal-visibility 계약 §3의 3번 행(FR-016) |
| 8 | `toWriting()`이 `day`를 인자로 받게 한다 | overwrite-confirm 계약 C3 |
| 9 | `DayPicker`에서 `todayNotYetWritable`을 무시하고 안내를 그리지 않는다 | day-boundary 계약 §4의 1번 행, I11(**헌법 원칙 II MUST — /speckit-analyze C1에서 드러난 갭**) |

**하나라도 통과하면 그물이 뚫린 것이다.** 특히 **1번은 이 기능에서 가장 위험한
결함**이다 — 화면이 오늘을 완벽하게 그려도, 파이프라인 게이트가 그대로면
「일기 쓰기」를 누르는 순간 조용히 `day-not-closed`로 막힌다.

## B. 실기기 (기기가 있을 때만)

### B0. 준비

007·008·009에서 실측으로 얻은 것을 그대로 따른다.

```
# 1. Metro가 dev 환경으로
EXPO_PUBLIC_APP_ENV=dev npx expo start --dev-client

# 2. adb reverse — USB에서도 필요하다
adb reverse tcp:8081 tcp:8081

# 3. 기기 잠금 해제 확인
adb shell dumpsys trust | grep deviceLocked   # 0이어야 한다
```

**⚠️ 기기 날짜를 바꾸려 하지 않는다.** root가 필요하고 `adb shell date`가
**조용히 실패한다**(007 실측) — 이것이 정오 경계 검증을 특히 어렵게 만드는
이유다(C1).

### B1. 자동 흐름

```
npm run test:device
```

**`.maestro/today-diary.yml`이 `FLOWS`에 등록돼 있어야 돈다.**

### B2. 손으로 — 자동이 못 보는 것

**전제**: 기기의 지금 시각이 실제로 정오 이후여야 D1~D6을 볼 수 있다. 정오
이전에 검증한다면 D7·D8만 가능하다(아래 참조).

| # | 무엇 | 어떻게 | 통과 | FR/SC |
| --- | --- | --- | --- | --- |
| **D1** | 정오 이후 오늘이 고르는 자리에 보인다 | 쓰기 자리까지 스크롤 | 오늘·어제·그제 셋, **그그제는 없다** | SC-001·002 |
| **D2** | 오늘을 골라 실제로 생성된다 | 오늘을 고르고 「일기 쓰기」 | `day-not-closed`로 막히지 않고 생성이 돈다 | **SC-001, 이 기능의 핵심 검증** |
| **D3** | 저장된 일기의 날짜가 오늘이다 | D2 뒤 상세 화면 | 오늘 날짜로 목록·상세에 나타난다 | SC-001 |
| **D4** | "아직 안 끝났다"가 본문에 있다 | D3의 전문을 읽는다 | 하루가 안 끝났다는 취지의 문장이 있다 | SC-003 |
| **D5** | 사진 권한이 없어도 D4가 성립한다 | 사진 권한을 끄고 반복 | 「모른다」/「없었다」와 별개로 "아직 안 끝났다"는 여전히 있다 | **FR-004, signal-visibility 계약 §2의 2번 행** |
| **D6** | 걸음·배터리·연결이 본문·상세 화면에 없다 | D3의 전문과 "이 일기가 본 것" 목록을 본다 | 세 축에 대한 언급 0건 | SC-004 |
| **D7** | 같은 신호가 진단 화면엔 그대로 보인다 | 진단 패널(dev 빌드)을 연다 | 걸음·배터리·연결의 값 또는 `unknown` 사유가 보인다 | SC-005 |
| **D8** | 정오 이전에는 오늘이 안 보이고 안내가 뜬다 | 정오 이전 시각에 쓰기 자리를 본다 | 오늘이 없고 "몇 시부터" 안내, 그그제가 대신 보인다 | SC-002 |
| **D9** | 덮어쓰기가 누른 뒤 확인을 거친다 | 이미 있는 하루를 골라 「일기 쓰기」 | 곧바로 생성되지 않고 확인 화면이 뜬다 | **FR-011** |
| **D10** | 취소하면 기존 일기가 그대로다 | D9에서 취소 후 그 일기를 연다 | md5/내용이 이전과 같다 | SC-006 |
| **D11** | 확인하면 실제로 생성이 돈다 | D9에서 확인 | 「쓰고 있다」가 뜬다 | FR-011 |
| **D12** | 사진이 아주 많은 하루에서 상한 경고가 없다 | 010의 seed 도구로 사진이 많은 하루를 만든다(가능한 한도까지 — 010의 `over-limit` 실패 참조) | 「전부 못 봤다」류 경고가 안 뜬다 | SC-007 |
| **D13** | 확인 화면에 진행률·모델 정보가 없다 | D9 화면을 본다 | 날짜와 확인/취소뿐 | FR-013 |

### B3. release에서 다시 (필수)

**debug에서 돌았다는 것이 release에서 돈다는 뜻이 아니다**(원칙 V).

```
npx expo prebuild --platform android --clean
cp ~/.alpharium-signing/alpharium.jks android/app/
cd android && NODE_ENV=production ./gradlew assembleRelease
```

**`versionCode`를 올린다.**

| 확인 | 통과 |
| --- | --- |
| 서명 | `apksigner verify --print-certs` → `CN=alpharium` |
| 덮어 설치 | `adb install -r` → `Success`, 일기가 살아남는다 |
| **D2 재확인** | release에서도 오늘 쓰기가 실제로 돈다 |
| **D9 재확인** | release에서도 덮어쓰기 확인이 뜬다 |

### C7 — 확인 못 할 가능성이 큰 것들

**못 본 것을 본 것처럼 적지 않는다.**

| 무엇 | 왜 못 볼 수 있나 |
| --- | --- |
| **정오 경계 자체를 넘나드는 순간의 화면 갱신**(D1·D8, Edge Case "11:59→12:00") | 기기 날짜를 바꿀 수 없고(root 필요), 정오를 실제로 넘는 순간에 맞춰 검증하려면 그 시각에 기기를 들고 있어야 한다 — **기기 없는 테스트(day-boundary 계약)가 이 갈래의 주된 검증이며**, 실기기에서는 "지금이 정오 이후인 상태" 하나만 볼 수 있다(009가 되돌림 검증에서 겪은 것과 같은 제약) |
| **사진이 극단적으로 많은 하루의 조회 시간**(D12) | 010의 `over-limit`(201장) 심기 자체가 322초 걸리고 150장만 색인된 전례가 있다 — 실측 가능한 최대치가 이미 제한적이다. 가능한 한도까지 재고, 못 넘는 지점은 "실측 못 함"으로 남긴다 |
| **오늘 자정을 넘겨 다음날이 되는 순간의 동작**(Edge Case) | 자정 근처에 실제로 기기를 들고 관찰해야 한다 |

## D. AGENTS.md에 남길 것

**실측한 값만 적는다.** 짐작은 짐작이라고 적는다.

- 정오 이후 오늘의 생성이 실기기에서 실제로 도는가(D2) — **이 기능에서 가장
  중요한 실측**, `pipeline.ts` 게이트 수정이 실제로 작동하는지의 증거
- 사진 권한 없이도 "아직 안 끝났다"가 전달되는가(D5)
- 걸음·배터리·연결이 실기기의 사용자 화면에서 실제로 사라졌는가(D6), 진단
  화면엔 남아 있는가(D7)
- 덮어쓰기 확인이 실기기에서 실제로 한 번 더 막는가(D9~D11)
- 사진 상한을 없앤 뒤 실측된 조회 시간(D12, 가능한 범위까지)
- release에서 D2·D9가 재확인됐는가(B3)
- 정오 경계를 실기기에서 못 넘나든 경우, 그것을 미확인으로 남겼는가(C7)
