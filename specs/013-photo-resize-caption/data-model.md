# Data Model: 사진을 보기 전에 줄인다

## ResizeTarget (상수)

목표 크기. **한 자리에만 있다**(FR-002) — `src/vision/resize.ts`에 export하지 않는
상수로 둔다(011의 `VISION_PHOTO_LIMIT`과 같은 성격, `selection.md` S1과 동일 규율).

```ts
type ResizeTarget = {
  /** 긴 변의 최대 픽셀 수. 짧은 변은 원본 비율로 계산된다(FR-004) */
  maxLongEdge: number;
};
```

**값**: `{ maxLongEdge: 1024 }` — spec Assumptions의 실측 근거(2026-08-22, IMAGE
청크 9→1, 캡션 품질 유지 확인)를 그대로 코드 주석에 남긴다(FR-020).

**필드가 하나뿐인 이유**: 가로세로 각각을 받으면 부르는 쪽이 비율을 깨뜨릴 조합을
넣을 수 있다(FR-004 위반 경로가 생김). 긴 변 하나만 받아 짧은 변을 항상 비율로
계산하면 그 경로 자체가 없다.

## ResizeResult (반환값)

```ts
type ResizeResult =
  | { ok: true; path: string }
  | { ok: false };
```

**불변식**:
- **자리가 `path` 하나뿐이다**(FR-015 — 시간·크기 같은 지표를 담을 자리를 두지
  않는다). 011의 `VisionRunResult`가 `{ text }` 하나뿐인 것과 같은 방어 구조.
- **예외를 던지지 않는다**(FR-012). 실패는 `{ ok: false }`이지 throw가 아니다.
- **`ok: false`에 이유를 담지 않는다.** 011의 `VisionLoadResult`는 이유를 셋으로
  가르지만(`not-found`/`load-failed`/`no-vision-support`), 리사이즈 실패는
  **호출자(caption.ts)가 이유와 무관하게 「이 장은 못 읽음」으로만 다루므로**
  (FR-011, R5) 이유를 가를 필요가 없다 — 갈래를 늘리지 않는 것 자체가 목적이다.

## 리사이즈 사본 (파일, 코드의 타입이 아니라 파일 시스템 상의 실체)

**자리**: 앱 전용 문서 디렉터리 하위 `vision-cache/`
(`<documentDirectory>/vision-cache/<photo.id 기반 파일명>.jpg`).

**이름 규칙**: `photo.id`에서 결정론적으로 유도한다(R3) — 파일 시스템에 쓸 수
없는 문자(`content://` URI의 `/`, `:`)를 치환한 뒤 사용한다.

**생애**:
1. `captionAll()`이 사진 한 장을 처리하기 직전 리사이즈 사본을 만든다
2. 캡션이 끝나면(성공/실패/그만둠 무관) **그 장의 사본을 즉시 지운다** — 하루
   전체가 끝난 뒤 일괄 정리가 아니라 **장별**로 정리한다(FR-008의 "그 하루의
   캡션이 끝나면"을 장 단위로 세분화 — Edge Case "생성 중 그만두면"이 이미 만들던
   사본이 안 남아야 함을 요구하므로, 장별 정리가 그만두기 시점과 무관하게 안전하다)
3. 앱이 예기치 않게 끝나 못 지운 사본이 남으면, **다음 캡션이 같은 이름으로
   덮어쓰므로**(R3) 누적되지 않는다(FR-009)

**하루 시작 시 선제 정리 여부**: 하지 않는다. 이름 결정론(R3)이 이미 누적을
막으므로 별도의 "시작 전 폴더 비우기" 단계가 불필요하다 — 필요 없는 단계를
추가하면 그 자체가 새로운 실패 지점이 된다.

## 변경되는 기존 타입

**변경 없음.** `PhotoVision`·`PhotoCaption`(011, `src/vision/types.ts`)과
`VisionRunResult`(011, `vision-port.ts`)는 그대로다 — 리사이즈는 캡션 파이프라인
"안쪽"의 전처리 단계이며 파이프라인이 밖으로 내보내는 타입에 영향을 주지 않는다.
