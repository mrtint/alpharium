# Feature Specification: 초기 권한 획득과 첫 실행 흐름 재설계

**Feature Branch**: `040-onboarding-parallel-setup`

**Created**: 2026-09-11

**Status**: Draft

캐릭터 작명 병렬화 + 다운로드 완료 후 첫 일기 자동 작성. 021·029·031·035를

## Clarifications

### Session 2026-09-11

- Q: 모델 다운로드가 끝난 뒤, 035가 쓰던 '짧은 응답 생성 확인(liveness)' 단계를 이 새 흐름에서도 그대로 거치나요? → A: liveness 검증 유지, 그 다음 자동 일기 — 다운로드 완료 → liveness 통과 확인 → 통과 시에만 첫 일기 자동 생성 시도. liveness 실패는 035의 기존 실패 안내 갈래를 재사용한다.
- Q: 배터리 최적화 예외 항목(자동 백그라운드 생성에 필요, 020/021 도입)을 이 로고→권한 자동 순차 흐름 안에 포함하나요, 아니면 온보딩에서 완전히 빼고 설정 탭에만 남기나요? → A: 온보딩 흐름 안에 포함 — 021의 기존 배터리 예외 안내(팝업 대신 전용 화면 + 설정 진입 경로)를 그 자리에 그대로 넣는다.
- Q: 첫 일기 자동 생성(US3)이 이미 있는 그날 일기를 덮어쓰려 할 때, 012의 '덮어쓰기 확인' 화면을 띄우나요? → A: 해당 없음 — 이 흐름은 최초 실행(FR-010)에만 적용되므로 그날 일기가 이미 존재하는 경우가 구조적으로 없다. 덮어쓰기 확인 로직은 이 경로에서 타지 않는다.
- Q: 작명을 마쳤는데 모델 다운로드가 아직 안 끝난 경우(FR-006의 '기다리는 화면'), 그 화면에서 사용자가 그만두기를 할 수 있나요? → A: 그만두기 없음 — 029의 필수 에셋은 앱 동작에 반드시 필요하므로 최초 온보딩은 다운로드 완료까지 머무른다. 007의 '그만두기 버튼'은 이미 받은 상태에서의 것이며 여기는 적용하지 않는다.
- Q: 각 권한 항목의 '목적 설명 화면'은 시스템 팝업이 뜨기 전에 몇 초간 보여주고 자동으로 넘어가나요, 아니면 사용자의 탭 한 번으로 넘어가나요? → A: 자동(타이머) — 짧게 보여주고 바로 시스템 팝업을 띄운다. SC-001의 "커스텀 화면 버튼 탭 수 감소" 기준이 이 방식을 전제한다.



### User Story 1 - 로고에서 권한까지 손 대는 횟수가 줄어든다 (Priority: P1)

앱을 처음 설치해 여는 사용자는 전체화면 로고를 먼저 보고, 곧이어 각 권한이
왜 필요한지 짧게 알려주는 화면과 함께 시스템 권한 팝업이 순서대로 뜬다.
사용자는 각 팝업에서 허용/거부만 결정하면 되고, 매 단계마다 별도의
[허용]/[건너뛰기] 화면 버튼을 누를 필요가 없다.

**Why this priority**: 이 기능 전체의 존재 이유다. 지금의 "단계마다
설명 + 두 버튼" 구조를 다른 앱들에 익숙한 "로고 → 목적 설명 → 시스템
팝업 순차" 구조로 바꾸는 것이 사용자가 명시적으로 요청한 핵심 변화다.

**Independent Test**: 앱을 새로 설치해 첫 실행부터 마지막 권한 결정까지,
화면에 붙은 커스텀 버튼을 누른 횟수와 시스템 팝업에서 결정한 횟수를 세어
비교한다 — 커스텀 버튼 조작이 기존보다 줄었는지로 검증한다.

**Acceptance Scenarios**:

1. **Given** 앱을 처음 설치해 첫 실행, **When** 로고 화면이 지나가면,
   **Then** 각 권한의 목적을 알리는 화면과 함께 시스템 권한 팝업이
   자동으로 하나씩 뜬다(사용자가 "다음" 같은 화면 버튼을 눌러야만 다음
   팝업이 뜨지 않는다).
2. **Given** 시스템 팝업에서 권한을 거부, **When** 다음 권한 차례가
   되면, **Then** 이전 거부와 무관하게 다음 권한의 목적 설명과 팝업이
   이어진다(전체 흐름이 멈추지 않는다).
3. **Given** 팝업으로 요청할 수 없는 항목(배터리 최적화 예외),
   **When** 그 차례가 되면, **Then** 팝업 대신 그 항목만을 위한 안내와
   설정 화면 진입 경로가 제공되고, 사용자는 그것도 건너뛸 수 있다.

### User Story 2 - 기다리는 동안 이름을 짓는다 (Priority: P1)

권한 결정이 모두 끝나면, 사용자는 앱이 준비를 마칠 때까지 빈 진행률
화면을 보며 기다리지 않는다. 그 대신 캐릭터(자신의 하루를 써 줄 존재)의
이름을 짓는 화면이 바로 나타나고, 그 동안 뒤에서는 필요한 준비(모델
내려받기)가 진행된다.

**Why this priority**: "기다리는 시간을 다른 유의미한 상호작용으로
채운다"는 것이 이 기능이 사용자 체감 대기 시간을 줄이는 핵심 방법이다.
P1인 이유는 이 병렬화가 없으면 이 기능의 존재 의의(로드맵 배경)가
사라지기 때문이다.

**Independent Test**: 새 설치에서 권한 결정 직후부터 시간을 재, 작명
화면이 몇 초 안에 뜨는지(다운로드 완료를 기다리지 않는지)와 작명 완료
시점에 다운로드가 병행되고 있었는지를 확인한다.

**Acceptance Scenarios**:

1. **Given** 권한 결정을 모두 마친 직후, **When** 화면을 관찰하면,
   **Then** 진행률 표시만 있는 대기 화면이 아니라 캐릭터 이름을 지을 수
   있는 화면이 뜬다(035의 환영 연출과 동일한 톤).
2. **Given** 작명 화면에서 이름을 입력하고 확정, **When** 그 시점에
   아직 필요한 준비(모델 내려받기)가 끝나지 않았다면, **Then** 준비가
   끝날 때까지 기다리는 화면으로 넘어가며, 이미 지은 이름은 유지된다.
3. **Given** 작명이 끝나기 전에 준비가 먼저 끝나면, **When** 사용자가
   계속 이름을 짓고 있으면, **Then** 준비 완료 사실 때문에 작명이
   중단되거나 재촉되지 않는다 — 사용자가 이름을 확정할 때까지 기다린다.

### User Story 3 - 처음 앱을 열면 이미 일기 하나가 있다 (Priority: P2)

준비(모델 내려받기)와 작명이 모두 끝나면, 사용자가 "일기 쓰기"를 따로
누르지 않아도 그날의 첫 일기가 자동으로 쓰여 홈 화면에 도착해 있다.

**Why this priority**: 로드맵 배경이 명시한 목표 흐름의 마지막 단계다.
US1·US2(권한·작명 경험)가 이 기능의 필수 골격이라면, 이 항목은 그
골격 위에 얹는 완성도다 — 자동 생성이 실패해도(예: 거부 판정) US1·US2는
여전히 유효하게 동작하므로 P2로 분리한다.

**Independent Test**: 새 설치를 처음부터 끝까지(권한→작명→다운로드
완료) 밟은 뒤, 사용자가 "일기 쓰기"를 누르지 않은 상태에서 홈 화면에
그날의 일기가 이미 존재하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 작명과 모델 준비가 모두 끝난 직후, **When** 홈 화면에
   처음 도달하면, **Then** 사용자의 조작 없이 그날의 일기 생성이 이미
   시작됐거나 완료되어 있다.
2. **Given** 자동 생성이 거부 판정(빈 글·되뱉기·언어 불일치·미완성) 중
   하나로 실패, **When** 사용자가 홈 화면을 보면, **Then** 실패가
   조용히 감춰지지 않고, 사용자는 평소처럼 "일기 쓰기"를 눌러 다시 시도할
   수 있다.
3. **Given** 자동 생성 시점이 정오 이전이라 그날을 아직 쓸 수 없는
   경우, **When** 사용자가 홈 화면을 보면, **Then** 자동 생성은
   시도되지 않고 화면은 기존 정오 게이트 안내를 그대로 보인다(첫 실행
   전용 예외를 만들지 않는다).

---

### Edge Cases

- 사용자가 로고 화면 직후 모든 권한을 거부하면? → 이후 단계(작명·다운로드)는
  권한과 무관하게 진행된다(사진 권한이 없어도 캐릭터 모델은 받을 수
  있다) — 다만 첫 일기는 신호 없는 하루로 쓰인다.
- 다운로드 도중 네트워크가 끊기면? → 작명 화면 또는 대기 화면에 실패가
  드러나고, 사용자가 재시도하거나 나중에 설정에서 이어받을 수 있다 —
  자동 생성은 준비가 끝나지 않았으므로 시도되지 않는다.
- 사용자가 작명 화면에서 이름을 짓지 않고 이탈(앱 종료)했다가 다시 열면?
  → 이미 결정된 권한은 다시 묻지 않고, 아직 끝나지 않은 단계(작명 또는
  다운로드 대기)부터 이어간다.
- 이미 온보딩을 마친 기존 사용자가 앱을 업데이트해 이 기능을 처음 만나면?
  → 이 흐름은 최초 실행에만 적용된다. 이미 `완료` 상태인 사용자에게는
  다시 노출되지 않는다.
- 모델 준비가 끝난 뒤 liveness 확인이 실패하면? → 035의 기존 실패 안내
  갈래로 처리되고, 첫 일기 자동 생성은 시도되지 않는다 — 사용자는 이후
  평소처럼 "일기 쓰기"로 재시도할 수 있다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 첫 실행은 전체화면 로고를 먼저 보여준 뒤, 각 권한 항목의
  목적을 알리는 화면을 몇 초간 보여주고 사용자 조작 없이 자동으로 그
  권한의 시스템 요청을 이어서 띄워야 한다(설명 화면에 별도의 "다음"
  버튼을 두지 않는다).
- **FR-002**: 시스템 팝업으로 요청할 수 없는 항목(배터리 최적화 예외)은
  이 순차 흐름 안에 포함하되, 팝업 대신 021의 기존 전용 안내 화면과 그
  설정으로 이동하는 경로를 그 차례에 제공해야 한다.
- **FR-003**: 각 권한 항목은 사용자가 건너뛸 수 있는 경로를 가져야
  하며(시스템 팝업의 거부를 포함), 하나를 거부하거나 건너뛰어도 나머지
  항목의 순서가 계속돼야 한다.
- **FR-004**: 모든 권한 항목의 결정(허용/거부/건너뜀)이 끝나면, 필요한
  모델(캐릭터·사진 이해 도구)의 내려받기를 사용자 화면 조작과 별도로
  시작해야 한다.
- **FR-005**: 모델 내려받기가 진행되는 동안, 화면은 진행률만 보여주는
  대기 화면이 아니라 캐릭터 이름을 지을 수 있는 화면을 보여줘야 한다.
- **FR-006**: 사용자가 이름 짓기를 먼저 마쳤는데 모델 내려받기가 아직
  끝나지 않았으면, 내려받기가 끝날 때까지 기다리는 화면으로 넘어가야
  한다. 이 화면에는 그만두기 경로를 두지 않는다 — 필수 에셋(029)이
  끝나기 전까지 최초 온보딩은 대기를 유지한다.
- **FR-007**: 모델 내려받기가 이름 짓기보다 먼저 끝나도, 사용자가 이름
  짓기를 끝내기 전까지는 그 사실 때문에 작명 화면을 재촉하거나
  건너뛰지 않아야 한다.
- **FR-008**: 이름 짓기와 모델 준비가 모두 끝나면, 035의 liveness 확인
  (모델이 짧은 응답을 실제로 내는가)을 먼저 거치고, 통과한 경우에만
  사용자의 추가 조작 없이 그날의 일기 생성을 자동으로 시작해야 한다 —
  단, 그 시각이 아직 그날을 쓸 수 있는 시각(기존 정오 경계)이 아니면
  시도하지 않는다. 이 경로는 그날 일기가 아직 없는 최초 실행에만
  적용되므로(FR-010) 덮어쓰기 확인(012)은 거치지 않는다.
- **FR-008a**: liveness 확인이 실패하면 035의 기존 실패 안내 갈래를
  그대로 사용하며, 첫 일기 자동 생성은 시도하지 않는다.
- **FR-009**: 자동 생성이 거부 판정으로 실패해도 그 사실을 감추지
  않아야 하며, 사용자는 평소의 "일기 쓰기" 조작으로 다시 시도할 수
  있어야 한다.
- **FR-010**: 이 흐름은 온보딩을 아직 마치지 않은 사용자에게만
  적용돼야 한다 — 이미 온보딩을 완료한 기존 사용자에게 재노출되지
  않는다.
- **FR-011**: 사용자가 앱을 도중에 종료했다가 다시 열면, 이미 결정된
  권한은 다시 묻지 않고 아직 끝나지 않은 단계부터 이어가야 한다.
- **FR-012**: 이 흐름의 화면·문구는 모델 식별자·파라미터·양자화
  방식·진행 속도(초당 처리량 등) 지표를 노출하지 않아야 한다(기존
  경계 유지).
- **FR-013**: 권한 항목의 목록·순서·문구는 코드에 고정된 값이어야
  하며, 실행 중 조건에 따라 항목이 동적으로 늘거나 줄지 않아야 한다
  (배터리 최적화 예외 항목의 존재 형태는 변경 가능하나, 그 방식이
  실행마다 달라지지는 않는다).

### Key Entities

- **첫 실행 진행 상태**: 사용자가 온보딩의 어느 단계(권한 결정 중,
  작명 중, 내려받기 대기 중, 완료)에 있는지를 나타내는 값. 앱을
  재시작해도 이미 지난 단계로 되돌아가지 않아야 한다.
- **모델 내려받기 진행**: 캐릭터·사진 이해 도구 준비의 진행 상태.
  화면(작명 화면)의 생존 주기와 독립적으로 계속돼야 한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 새 설치 후 첫 실행에서, 사용자가 누르는 커스텀 화면
  버튼의 수가 기존 흐름 대비 줄어든다(권한 항목마다 있던 [허용]/[건너뛰기]
  두 버튼이 시스템 팝업 하나의 결정으로 대체된다).
- **SC-002**: 권한 결정이 끝난 시점부터 작명 화면이 뜨기까지 걸리는
  시간이, 모델 전체를 내려받는 데 걸리는 시간보다 뚜렷하게 짧다(수 초
  이내).
- **SC-003**: 작명과 모델 준비가 모두 끝난 뒤, 사용자가 "일기 쓰기"를
  누르지 않고도 홈 화면에서 그날의 일기(또는 그 생성이 진행 중임)를
  확인할 수 있다.
- **SC-004**: 자동 생성이 실패하는 경우에도 사용자가 다시 시도할 수
  있는 통상적인 경로가 항상 존재한다(막다른 화면이 없다).
- **SC-005**: 이미 온보딩을 마친 사용자가 앱을 업데이트해도 이 새
  흐름이 다시 나타나지 않는다.

## Assumptions

- 021(통합 권한 온보딩)의 권한 항목 4갈래(사진·위치·알림·배터리 예외)와
  그 문구·목적 설명은 그대로 재사용한다 — 이 스펙은 그 항목들이
  "제시되는 방식"을 바꾸는 것이지 항목 자체나 문구를 새로 짓지 않는다.
- 029(필수 에셋 다운로드)가 정의한 "받아야 하는 것"(기본 캐릭터
  모델 + 사진 이해 도구)의 범위는 바뀌지 않는다 — 이 스펙은 그것이
  "언제, 어떤 화면과 함께" 받아지는지만 바꾼다.
- 035(환영 연출·작명)의 작명 화면·문구·이름 길이 제한은 그대로
  재사용한다.
- liveness 검증(035의 안전판)은 모델 준비 완료 직후, 첫 일기 자동
  생성 시도 이전에 그대로 유지한다(Clarifications 참고).
- 배터리 최적화 예외 안내(021)는 이 자동 순차 흐름 안에 포함한다
  (Clarifications 참고).
- 새 네이티브 의존성은 필요하지 않다고 가정한다 — 기존 시스템 권한
  API·`expo-file-system` 다운로드·기존 파이프라인을 재사용한다.
