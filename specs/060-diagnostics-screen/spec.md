## 범위

**이미 있는 것 — 다시 만들지 않는다**:

- 059의 개발자 화면 「진단」 행과 그 위의 진단 겹(개발 환경에서만, 뒤로 가면 개발자 화면). 진입·뒤로 가기는 그대로 쓴다.
- 055의 설정 틀 부품(고정 제목·묶음 머리·행·값·›). 진단도 같은 부품을 쓴다.
- 022의 고정 프리셋 프롬프트 미리보기(진단 계층이 문자열로 만들어 화면에 준다), 012·헌법 검사의 「신호 프로브는 다섯 축을 다 그린다」, 004의 사진 권한 요청, 002의 저장 점검, 020의 자동 쓰기 한 번 실행.
- 054의 쓰는 중(제자리 쓰기)·실패 토스트 갈래, 057의 자동 쓰기 규칙.

**이 조각이 새로 만드는 것**:

- 진단 화면을 보드 `6h`의 일곱 묶음으로 다시 그린다 — 환경 / 저장 점검 / 사진 권한 / 신호 프로브 / 입력 프롬프트 미리보기 / 생성 / 최근 실패.
- 「지금 한 번 써 보기」를 홈의 오늘 쓰는 중으로 잇기(보드 `6k`).
- 쓰기 실패의 영구 기록(이유 갈래 + 시각, 최근 10건)과 그 표시.

**이 조각이 만들지 않는 것**:

- 상태 흉내(분해 설계 §3.7). 「상태 흉내가 켜져 있으면 두 생성 버튼이 비활성」 조건도 이 조각에 자리를 두지 않는다.
- 쓰기 로그(단계·소요 시간)·측정값·건너뜀 기록(S9·S11). 모델 이름·파라미터 수 표기(원칙 III).
- 059가 남긴 미확인(모듈을 자른 다시 받기·쓰는 중 온보딩 다시)과 058 「지우기」 버튼 색.
- 사용자(배포) 화면 변경. 배포 환경에는 진단에 닿는 길이 없다(059).

## Clarifications

### Session 2026-10-06

- Q: 보드의 「최근 실패」 이유 넷에 안 맞는 실패(시간 초과·중단·판정 거부)는 어떻게 기록하나? → A: 다섯째 갈래 「일기를 쓰지 못함」을 더한다(보드 문구표 밖 한 줄 — 넷으로 뭉치면 사실과 다른 이유를 말하게 된다). 이유 갈래는 다섯이다 (FR-017).
- Q: 백그라운드 자동 쓰기 실패도 기록하나? → A: 기록한다. 홈에서 쓴 것이든 백그라운드가 쓴 것이든 모든 쓰기의 실패를 한 곳에서 기록한다 (FR-015·FR-019).
- Q: 「자동 쓰기 지금 실행」이 매일 쓰는 시각의 시도 창을 지키나? → A: 창을 무시한다. 언제 눌러도 동작한다 (FR-014).
- Q: 「자동으로 쓰기」 토글이 꺼진 기기에서도 쓰나? → A: 토글도 무시한다. 이미 쓴 날·재료 없음·사진 권한 규칙만 따른다 (FR-014).
- 확정(질문 없이 근거로 닫음): 캐릭터별 모델 줄은 지운다(보드 `6h`에 없고 원칙 III). 추론 위치의 「CPU」는 기기 추론이 GPU 오프로드 0으로 고정(`n_gpu_layers` 0, `llama-port.ts`)이라 사실이므로 기기 추론이면 「기기 · CPU」, 로컬 서버면 서버 위치를 그대로 쓴다 (FR-005).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 환경과 저장 상태를 한눈에 본다 (Priority: P1)

개발 환경에서 개발자가 설정 → 개발자 → 「진단」을 열면 「환경」 묶음에 빌드 종류·버전, 안드로이드 버전, 추론 위치가 보이고, 「저장 점검」 행을 누르면 저장된 일기를 다시 읽어 「{n}편 · 정상」 또는 「{n}편 · {k}편 읽기 실패」로 바뀐다. 점검은 고치지 않는다.

**Why this priority**: 기기에서 앱이 어떤 상태인지 보는 가장 기본 정보다. 나머지 묶음이 이 틀 위에 선다.

**Independent Test**: 개발 환경에서 진단을 열어 환경 묶음의 값 네 개와 저장 점검 갱신을 본다.

**Acceptance Scenarios**:

1. **Given** 개발 환경이다, **When** 진단을 연다, **Then** 제목 「진단」과 뒤로 「‹ 개발자」가 보이고 첫 묶음 「환경」에 「빌드」·「기기」·「추론 위치」 행이 있다.
2. **Given** 환경 묶음이다, **When** 추론 위치를 본다, **Then** 값은 이 기기에서 실제로 알 수 있는 것만 말한다(기기 추론이면 「기기 · CPU」 — 근거는 plan에서 확정, 모르면 「기기」).
3. **Given** 저장된 일기가 41편이고 모두 읽힌다, **When** 「저장 점검」을 누른다, **Then** 값이 「41편 · 정상」이 된다.
4. **Given** 41편 중 2편이 깨졌다, **When** 점검한다, **Then** 「41편 · 2편 읽기 실패」가 되고 파일은 바뀌지 않는다.
5. **Given** 환경 묶음이다, **When** 화면 어디에서든, **Then** 모델 이름·파라미터 수·양자화 표기가 없다.

### User Story 2 - 사진 권한과 신호를 따로 풀어 본다 (Priority: P1)

「사진 권한」 묶음은 설정에서 한 행으로 묶인 것을 풀어 「사진 읽기」·「사진 위치 정보」·「범위(전체 / 선택한 사진만)」를 따로 보인다. 「신호 프로브 · 오늘」 묶음은 다섯 칸(사진·장소·걸음·배터리·연결)을 보이는데, 앱이 실제로 읽는 사진·장소만 숫자이고 나머지는 「모름」(회색 면·회색 글자)이다. 화면을 열 때와 「다시 읽기」를 누를 때만 읽는다.

**Why this priority**: 재료가 왜 비는지 개발자가 가장 먼저 의심하는 자리다.

**Independent Test**: 권한이 부분 허용인 기기에서 세 행의 값을 보고, 신호 프로브의 다섯 칸과 「다시 읽기」를 본다.

**Acceptance Scenarios**:

1. **Given** 사진 권한이 부분 허용(선택한 사진만)이다, **When** 「사진 권한」 묶음을 본다, **Then** 읽기는 허용됨, 범위는 「선택한 사진만」으로 따로 보인다.
2. **Given** 사진 위치 정보를 읽지 못한다, **When** 본다, **Then** 「사진 위치 정보」 행이 그렇다고 말하고 다른 행에 영향이 없다.
3. **Given** 신호 프로브를 연다, **When** 다섯 칸을 본다, **Then** 사진·장소는 숫자(또는 「없음」)이고 걸음·배터리·연결은 「모름」이며 「모름」 칸은 숫자 칸과 모양이 구분된다(회색 면 + 회색 글자, 값은 본문 글꼴).
4. **Given** 화면이 열려 있다, **When** 시간이 흐르거나 다른 곳을 다녀와도, **Then** 「다시 읽기」를 누르기 전에는 다시 읽지 않는다.
5. **Given** 사진 권한이 없다, **When** 신호 프로브를 본다, **Then** 사진은 「모름」이지 0이 아니다(원칙 V).

### User Story 3 - 지금 한 번 써 보기로 홈에서 일기를 쓴다 (Priority: P1)

「생성」 묶음의 「지금 한 번 써 보기」를 누르면 진단이 닫히고 홈의 오늘이 쓰는 중으로 시작한다(보드 `6k`). 제품과 같은 경로(신호 → 생성 → 저장)로 쓰고 저장하며, 그 날에 이미 일기가 있으면 덮어쓴다(덮어쓰기 확인 없음). 토스트 「진단에서 쓰기를 시작했어요.」가 2초 보인다. 다 쓰면 쓴 날 화면, 실패하면 일반 쓰기 실패 토스트와 「최근 실패」에 한 줄이다.

**Why this priority**: 진단의 핵심 용도 — 실기기에서 제품 경로가 도는지 눈으로 확인한다(042: 검증 경로가 제품과 다르면 검증이 아니다).

**Independent Test**: 개발 환경에서 「지금 한 번 써 보기」를 눌러 홈에서 쓰는 중이 시작되고 쓴 날로 끝나는지 본다.

**Acceptance Scenarios**:

1. **Given** 진단이 열려 있다, **When** 「지금 한 번 써 보기」를 누른다, **Then** 진단·개발자·설정이 닫혀 홈의 오늘이 보이고 쓰는 중으로 시작하며 토스트가 2초 뜬다.
2. **Given** 오늘 일기가 이미 있다, **When** 누른다, **Then** 확인 대화상자 없이 쓰기가 시작되고 다 쓴 순간 새 글로 바뀐다(쓰는 동안 옛 글은 저장돼 있다).
3. **Given** 쓰는 중이다, **When** 생성이 끝난다, **Then** 홈은 오늘의 쓴 날이다(결과 시트 없음).
4. **Given** 쓰는 중에 실패한다, **When** 끝난다, **Then** 054의 실패 토스트가 뜨고 「최근 실패」에 한 줄이 더해진다.
5. **Given** 홈이 이미 오늘을 쓰는 중이다, **When** 진단에서 다시 누른다, **Then** 두 번째 쓰기를 시작하지 않는다(쓰는 중 하나뿐).
6. **Given** 진단 계층에서, **When** 소스를 본다, **Then** 진단은 파이프라인을 직접 돌리지 않고 홈의 쓰기 진입을 부른다.

### User Story 4 - 자동 쓰기를 지금 한 번 돌린다 (Priority: P2)

「자동 쓰기 지금 실행」은 자동 쓰기를 지금 한 번 돌린다. 자동 쓰기 규칙(이미 쓴 날·재료 없음 건너뜀 등)은 그대로 따른다. 결과는 화면에 한 줄로 남는다.

**Why this priority**: 백그라운드 경로를 앱을 연 채로 재현하는 도구다. 홈 연결(US3)보다 덜 급하다.

**Independent Test**: 안 쓴 날이 있는 기기에서 누르고 결과 줄이 갱신되는지, 쓸 날이 없으면 아무것도 쓰지 않는지 본다.

**Acceptance Scenarios**:

1. **Given** 쓸 날이 있다, **When** 누른다, **Then** 자동 쓰기 한 번이 돌고 결과(썼음/건너뜀/실패)가 한 줄로 보인다.
2. **Given** 모든 날이 이미 쓰였다, **When** 누른다, **Then** 아무것도 쓰지 않고 「건너뜀」으로 알린다.
3. **Given** 도는 중이다, **When** 다시 누른다, **Then** 중복 실행되지 않는다.

---

### User Story 5 - 프롬프트 미리보기를 고정 프리셋 두 벌로 본다 (Priority: P2)

「입력 프롬프트 미리보기」는 프리셋 둘(「프리셋 1 · 신호 없음」/「프리셋 2 · 사진 있음」)을 전환해 본다. 실제 신호가 아니라 고정값이라 날짜가 바뀌어도 내용이 같다. 텍스트 상자는 안에서 따로 스크롤되고 글자는 선택만 할 수 있다.

**Why this priority**: 022의 기능을 새 모양으로 옮기는 일. 계약이 이미 잠겨 있어 위험이 낮다.

**Independent Test**: 프리셋을 전환해 본문이 바뀌고, 이튿날에도 같은지 본다.

**Acceptance Scenarios**:

1. **Given** 미리보기를 연다, **When** 프리셋 2를 고른다, **Then** 사진 있음 프리셋의 프롬프트가 보인다(제품이 쓰는 프롬프트 조립 결과와 바이트가 같다 — 022 PP1).
2. **Given** 본문이 길다, **When** 스크롤한다, **Then** 상자 안에서만 스크롤되고 화면 전체 스크롤과 다투지 않는다.
3. **Given** 본문, **When** 길게 누른다, **Then** 글자를 선택할 수 있다(편집은 안 된다).
4. **Given** 화면에, **When** 문구를 본다, **Then** 크기는 문자 수 근사임을 밝히고 토큰·속도 어휘가 없다(022 PP6).

### User Story 6 - 최근 쓰기 실패를 본다 (Priority: P2)

「최근 실패」 묶음은 쓰기 실패의 이유와 시각만 최근 10건, 최신이 위로 보인다. 건너뜀은 넣지 않는다. 걸린 시간 같은 측정값은 두지 않는다. 행을 눌러도 아무 일이 없다. 실패가 없으면 빈 상태 한 줄이 있다.

**Why this priority**: 사용자 보고(「일기가 안 써져요」)의 원인 갈래를 기기에서 되짚는 유일한 자리다. 기록 저장소가 새로 생기므로 위험은 P2.

**Independent Test**: 저장 실패를 유도해 쓰기를 실패시킨 뒤 진단의 「최근 실패」에 한 줄이 생기는지 본다.

**Acceptance Scenarios**:

1. **Given** 쓰기가 저장 단계에서 실패했다, **When** 진단을 연다, **Then** 「저장하지 못함」과 시각이 한 줄로 있다.
2. **Given** 실패가 11건 쌓였다, **When** 본다, **Then** 가장 오래된 하나가 빠져 10건이다.
3. **Given** 쓰기가 건너뛰어졌다(재료 없음·사진 권한 없음), **When** 본다, **Then** 기록에 없다.
4. **Given** 기록 파일을 읽지 못한다·깨졌다, **When** 본다, **Then** 빈 상태로 보이고 화면은 던지지 않는다. 기록하지 못해도 쓰기 실패 토스트 경로는 그대로다.
5. **Given** 소스를 본다, **When** 기록 항목의 필드를 센다, **Then** 이유 갈래와 시각뿐이다(소요 시간·토큰 수 필드 없음, 원칙 IV).

### Edge Cases

- **진단을 닫고 홈으로 갈 때 홈이 쓰는 중**: 두 번째 쓰기를 시작하지 않는다(US3-5). 홈이 덮여 있던 동안 쓰던 일기는 끊기지 않는다.
- **지금 한 번 써 보기를 누른 뒤 곧바로 홈에서 그만두기**: 054와 같다(글은 버려지고 실패 기록은 없다 — 그만둔 것은 실패가 아니다).
- **필수 모듈이 없거나 잘려 있다**: 054의 시작 전 막힘 화면 경로를 그대로 따른다(진단이 따로 막지 않는다).
- **사진 권한이 없다**: 쓰기는 054대로 진행되고(재료 확인은 권한이 없어도 쓸 수 있다) 진단은 권한을 요청하지 않아도 된다(요청 행은 사진 권한 묶음에서 한다).
- **저장 점검 중 화면을 떠남**: 결과가 도착해도 화면이 없으면 버린다.
- **사진 0장인 날의 신호 프로브**: 사진 「없음」(관측된 0), 장소도 없음으로 옮긴다(053과 같은 규칙).
- **글꼴 2.0배**: 라벨·값이 한 줄에 안 들어가면 줄을 바꾸되 자르지 않는다(055). 긴 본문 상자는 안에서 스크롤한다.
- **실패 기록에 이유 갈래를 알 수 없는 실패**: 다섯째 「일기를 쓰지 못함」으로 기록한다. 문구 전체를 비교하지 않는다(054 규칙).
- **기록 쓰기 실패**: 조용히 삼킨다 — 일기 쓰기·토스트에 영향이 없다.

## Requirements *(mandatory)*

### Functional Requirements

**화면 틀**

- **FR-001**: 진단 화면은 보드 `6h`의 일곱 묶음을 이 순서로 그린다 — 환경 / 저장 점검 / 사진 권한 / 신호 프로브 · 오늘 / 입력 프롬프트 미리보기 / 생성 / 최근 실패. 묶음 머리·행·값은 055 설정 틀의 부품을 쓴다(복제하지 않는다).
- **FR-002**: 진단은 개발 환경(`local`·`dev`)에서만 닿는다. 배포 환경에는 행도 트리도 없다(059가 지킨다 — 이 조각이 새 진입을 만들지 않는다).
- **FR-003**: 모든 문구는 분해 설계 §3.6의 KO 문구표 그대로이며 글자 단위 계약 테스트로 잠근다(`diag.title` 「진단」, `diag.env` 「환경」, `diag.build` 「빌드」, `diag.device` 「기기」, `diag.inference` 「추론 위치」, `diag.inference.cpu` 「기기 · CPU」, `diag.storage` 「저장 점검」, `diag.storage.ok` 「{n}편 · 정상」, `diag.storage.bad` 「{n}편 · {k}편 읽기 실패」, `diag.photoPerm` 「사진 권한」, `diag.photoRead` 「사진 읽기」, `diag.photoLocation` 「사진 위치 정보」, `diag.photoScope` 「범위」, `diag.scopeAll` 「전체」, `diag.scopeSelected` 「선택한 사진만」, `diag.probe` 「신호 프로브 · 오늘」, `diag.probe.refresh` 「다시 읽기」, `diag.probe.photos`·`places`·`steps`·`battery`·`network` 「사진」·「장소」·「걸음」·「배터리」·「연결」, `diag.probe.unknown` 「모름」, `diag.prompt` 「입력 프롬프트 미리보기」, `diag.preset1` 「프리셋 1 · 신호 없음」, `diag.preset2` 「프리셋 2 · 사진 있음」, `diag.gen` 「생성」, `diag.tryOnce` 「지금 한 번 써 보기」, `diag.runAuto` 「자동 쓰기 지금 실행」, `diag.tryOnce.toast` 「진단에서 쓰기를 시작했어요.」, `diag.failures` 「최근 실패」, `diag.fail.module` 「모듈을 불러오지 못함」, `diag.fail.photos` 「사진을 읽지 못함」, `diag.fail.empty` 「글이 비어 있음」, `diag.fail.save` 「저장하지 못함」).
- **FR-004**: 모델 이름·파라미터 수·양자화 방식을 어디에도 보이지 않는다(원칙 III). 옛 진단의 캐릭터별 모델 줄은 이 화면에 없다.

**환경·저장 점검**

- **FR-005**: 「환경」 묶음은 빌드 종류·버전, 안드로이드 버전, 추론 위치를 보인다. 추론 위치는 기기 추론이면 「기기 · CPU」(GPU 오프로드가 0으로 고정돼 있어 사실이다), 로컬 서버 추론이면 서버 위치를 그대로 보인다. 추론 위치를 고르지 못했으면 그렇다고 적는다(원칙 V).
- **FR-006**: 「저장 점검」 행을 누르면 저장된 일기를 다시 읽어 「{n}편 · 정상」 또는 「{n}편 · {k}편 읽기 실패」로 값을 갱신한다. 고치지 않는다. 점검할 수 없는 환경이면 정상으로 적지 않는다(002 `unavailable`).

**사진 권한·신호 프로브**

- **FR-007**: 「사진 권한」 묶음은 사진 읽기·사진 위치 정보·범위(전체/선택한 사진만)를 각각 한 행으로 따로 보인다. 위치 정보는 조회 통로가 없어 실제로 읽어 보고 판정한 값이다(055 `photoLocationProbe`와 같은 방식을 재사용하고 결과를 지어내지 않는다). 권한 요청 동작은 사진 읽기 행에서 유지한다.
- **FR-008**: 「신호 프로브 · 오늘」은 다섯 칸을 모두 그린다(헌법 검사 `DIAGNOSTICS_HIDES_AXES` 유지). 사진·장소만 숫자(관측된 0은 「없음」), 걸음·배터리·연결은 「모름」이다. 「모름」 칸은 회색 면 + 회색 글자이고 값은 고정폭이 아닌 본문 글꼴이다.
- **FR-009**: 신호 프로브는 화면을 열 때와 「다시 읽기」를 누를 때만 읽는다. 「모름」을 0으로 세지 않는다.

**프롬프트 미리보기**

- **FR-010**: 프리셋 둘(「프리셋 1 · 신호 없음」/「프리셋 2 · 사진 있음」)을 전환해 본다. 내용은 진단 계층이 만든 문자열이고 화면은 `diary/prompt`·`signals`에 닿지 않는다(022 `UI_TOUCHES_PROMPT`). 본문 상자는 안에서 따로 스크롤하고 글자는 선택만 된다.
- **FR-011**: 크기 표기는 문자 수 근사이며 토큰 수·속도를 재거나 표기하지 않는다(022 PP6, 원칙 IV). 「조립 시점 근사치, 실측 토큰 아님」이라는 한 문장 라벨은 실측이 아님을 밝히는 문구라 유지한다.

**생성**

- **FR-012**: 「지금 한 번 써 보기」는 진단·개발자·설정을 닫아 홈의 오늘로 돌아가고 054의 제자리 쓰기를 시작한다. 쓰기는 제품과 같은 경로(신호 → 생성 → 저장)이며 진단이 파이프라인을 따로 돌리지 않는다. 오늘 일기가 있으면 덮어쓰기 확인 없이 덮어쓴다. 토스트 「진단에서 쓰기를 시작했어요.」를 2초 보인다.
- **FR-013**: 홈이 이미 오늘을 쓰는 중이면 두 번째 쓰기를 시작하지 않는다(쓰는 중 하나뿐).
- **FR-014**: 「자동 쓰기 지금 실행」은 자동 쓰기를 지금 한 번 돌린다. 매일 쓰는 시각의 시도 창과 「자동으로 쓰기」 토글은 무시하고(언제 눌러도 동작), 자동 쓰기 규칙(이미 쓴 날·재료 없음·사진 권한 없음 건너뜀)만 따른다. 결과를 한 줄로 보인다. 도는 중에 다시 눌러도 중복 실행되지 않는다.

**최근 실패**

- **FR-015**: 쓰기(홈·진단·백그라운드·첫 실행 자동 첫 일기)가 실패하면 이유 갈래와 시각을 별도 파일에 기록한다(D3). 설정·온보딩·건너뜀 파일에 필드를 더하지 않는다. 기록 항목은 이유 갈래와 시각뿐이다(소요 시간·토큰 수·모델 정보 없음, S9·원칙 IV).
- **FR-016**: 기록은 최근 10건을 넘지 않는다(오래된 것부터 빠진다). 건너뜀·그만두기는 기록하지 않는다(S11).
- **FR-017**: 이유 갈래는 다섯이다 — `diag.fail.*` 넷(모듈을 불러오지 못함·사진을 읽지 못함·글이 비어 있음·저장하지 못함)과, 그 넷에 맞지 않는 모든 쓰기 실패(시간 초과·중단·판정 거부 등)를 위한 「일기를 쓰지 못함」. 갈래 판정은 054 `failure-toast.ts`와 같은 규칙(앞 토큰만, 문구 전체 비교 금지)으로 한다. 기록할 수 없을 만큼 모르는 실패도 다섯째로 기록한다.
- **FR-018**: 「최근 실패」는 최신이 위로 보이고 행을 눌러도 동작이 없다. 기록이 없으면 빈 상태 한 줄이 있다. 읽기·쓰기 실패는 던지지 않고 빈 상태·무시로 처리한다.
- **FR-019**: 백그라운드(헤드리스) 자동 쓰기의 실패도 같은 기록에 남긴다. 기록 지점은 파이프라인 결과 한 곳이어서 홈과 백그라운드가 같은 규칙을 쓴다. 기록 통로는 주입받아 백그라운드 태스크에서도 같은 파일에 쓴다.

**경계·검증**

- **FR-020**: 개발자 화면은 `DiagnosticsScreen`을 import하지 않는다(059 DG2). 진단은 `roster`·모델 키에 닿지 않는다(`UI_TOUCHES_ASSET`). 옛 `GenerationProbe`·`AutoDiaryTriggerButton`의 자체 파이프라인 호출을 걷는다.
- **FR-021**: 진단 화면과 그 기록 모듈의 소스에 걸린 시간·토큰·속도를 재거나 담는 코드·어휘가 없다(소스 검사; 위 FR-011의 한글 라벨 문장은 대상이 아니다).
- **FR-022**: 새 네이티브 모듈을 들이지 않는다.

### Key Entities

- **쓰기 실패 기록**: 쓰기 실패 하나 — 이유 갈래(다섯 중 하나)와 시각. 최근 10건, 별도 파일, 측정값 없음.
- **진단 화면 값**: 환경·저장 점검 결과·사진 권한 셋·신호 프로브 다섯 칸·프리셋 미리보기 문자열. 읽은 시점의 값이고 저장하지 않는다.
- **진단의 쓰기 요청**: 「지금 한 번 써 보기」가 홈에 넘기는 오늘 쓰기 시작 요청(한 번에 하나).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 개발 환경 실기기에서 설정 → 개발자 → 진단으로 열고 일곱 묶음이 보드 순서대로 모두 보인다.
- **SC-002**: 진단 화면의 모든 고정 문구가 §3.6 KO 원문과 글자 단위로 같다(계약 테스트).
- **SC-003**: 「지금 한 번 써 보기」를 누른 뒤 홈이 쓰는 중으로 시작해 쓴 날로 끝나는 경로가 실기기에서 한 번 완주한다. 이때 진단 코드는 파이프라인을 직접 부르지 않는다(소스 계약).
- **SC-004**: 쓰기 실패를 유도하면(홈이든 백그라운드든) 「최근 실패」에 정확히 한 줄이 늘고, 11번째 실패는 목록을 10건으로 유지한다. 건너뜀·그만두기는 0건 늘어난다.
- **SC-005**: 진단 화면·기록 소스 어디에도 모델 이름·측정값·토큰·속도 필드가 없다(소스 검사).
- **SC-006**: 신호 프로브에서 「모름」이 0으로 표시되는 경우가 0이다(걸음·배터리·연결은 어떤 상태에서도 「모름」, 사진 권한 없음의 사진·장소도 「모름」).
- **SC-007**: 기존 계약(022 PP1·PP6, `UI_TOUCHES_PROMPT`, `DIAGNOSTICS_HIDES_AXES`, 059 DG2)이 모두 그대로 통과한다.
- **SC-008**: `npm test`·`npm run lint`가 통과하고 진단을 지나는 Maestro 흐름이 FLOWS에 등록돼 통과한다.

## Assumptions

- 「개발 환경」은 `local`·`dev`(`showsOnScreen`)이다(D2). `__DEV__`를 쓰지 않는다.
- 「안드로이드 버전」·「빌드」 값은 기기에서 읽을 수 있는 설치본 값(`expo-application`·플랫폼 버전)이며 새 의존성이 필요 없다.
- 홈에 쓰기 시작을 넘기는 통로는 057의 자동 쓰기 요청(`autoWriteDay` + 한 번만 claim)과 같은 방향의 앱 조립 계층 구조를 쓴다 — 구체는 plan.
- 실패 기록 파일은 `preferences/` 아래 한 파일이다(057 건너뜀 기록과 같은 위치, 058 「일기 모두 지우기」가 지우지 않는 대상).
- 실기기 확인은 dev(debug)로만 한다. 앱 파일을 바꾸면 먼저 백업하고 끝나면 복원한다. `pm clear`·`am force-stop`을 쓰지 않는다.
- 상태 흉내(§3.7)는 이 조각이 만들지 않는다.

## 미확인 잔여

- release 빌드에서의 진단(개발 환경만 닿으므로 대상 아님 — 확인하지 않는다).
- 글꼴 2.0배의 진단 화면, 24시간 형식 기기.
- 헤드리스에서 실패 기록이 실제로 쓰이는 것(헤드리스 실패를 유도하기 어려워 계약 테스트로 갈음할 수 있다).
