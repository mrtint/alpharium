# Feature Specification: 받기 전에 먼저 검증한다 — 모델 끝 무렵 사고 복구

**Feature Branch**: `110-model-verify-before-redownload`

**Created**: 2026-11-04

**Status**: Draft

**Input**: 로드맵 「모델 내려받기의 끝 무렵에 앱이 죽으면 처음부터 다시 받는다」. 설계: `docs/superpowers/specs/2026-11-04-model-verify-before-redownload-design.md`

## 근거와 원본

- 설계문서에 사실·결정·수용 기준이 있다. 경량 트랙이다.
- 용어:
  - **필수 모듈** = 첫 실행에 받는 언어 모델과 사진 모델(파일 둘)을 합친 것.
  - **검증** = 파일 내용 전체의 지문을 계산해 기준 지문과 견주고 결과를 기록하는 일.
  - **검증 기록** = 그 결과. 있어야 「준비됨」이 될 수 있다.

## Clarifications

### Session 2026-11-04

- Q: 받는 도중의 이어받기를 이번에 할 것인가? → A: 하지 않는다. 까닭을 적고 별도 과제로 올린다(소유자).
- Q: 검증 메모리를 어디서 고칠 것인가? → A: `expo-file-system`의 iOS MD5 루프를 `patch-package`로 고치고, 패치가 빌드에 닿지 않으면 로컬 네이티브 모듈로 바꾼다 (에이전트 판단 · 근거: `expo-background-task` 패치 선례, 변경이 가장 작다).
- Q: 언어 모델과 사진 모델의 판단을 어디에 둘 것인가? → A: `src/models/verification.ts`의 함수 하나를 양쪽이 부른다 (에이전트 판단 · 근거: 두 곳에 두면 한쪽만 어긋난다. 사진 쪽은 이미 `models`의 판정·저장을 쓴다).
- Q: 사진 모델 파일이 기준보다 크면 어떻게 할 것인가? → A: 지금의 「크거나 같으면 있음」을 걷고 기준과 같을 때만 검증한다. 다른 크기는 받기로 간다 (에이전트 판단 · 근거: 크기가 다른 파일을 온전하다고 볼 근거가 없다).
- Q: 지문 계산이 예외를 던지면 어떻게 할 것인가? → A: 계산하지 못한 것과 같게 다루어 다시 받는다 (에이전트 판단 · 근거: 예외로 끝내면 깨진 파일이 있는 기기가 재시도마다 같은 자리에서 막힌다).
- Q: 먼저 한 검증의 기록을 쓰지 못하면 어떻게 할 것인가? → A: 실패로 올린다. 사용자는 다시 시도할 수 있고 다음에 다시 검증한다 (에이전트 판단 · 근거: 성공을 돌려주면 받았다고 하면서 「준비됨」이 아닌 상태가 된다 — 이번에 고치는 사진 모델 문제와 같다).
- Q: 기준 크기가 없는 자산(0)은 먼저 검증할 것인가? → A: 하지 않고 지금처럼 받는다 (에이전트 판단 · 근거: 없는 기준으로 판정하지 않는다, `readinessOf`와 같은 규칙. 지금 로스터에는 해당 자산이 없다).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 다 받은 파일을 다시 받지 않는다 (Priority: P1)

필수 모듈을 받던 사용자의 앱이 받기가 끝난 직후 검증을 기록하기 전에 죽었다. 다시 열어 받기를 시작하면 이미 온전한 파일을 다시 받지 않고 검증만 거쳐 넘어간다.

**Why this priority**: iPhone 13 mini에서 실제로 1.5GB를 두 번 받았다. 데이터 요금과 첫 실행 시간을 직접 잃는다.

**Independent Test**: 기준 크기·기준 지문이 맞는 파일과 빈 검증 기록을 둔 채 받기를 시작하면, 전송이 일어나지 않고 검증 기록이 「통과」로 남아 「준비됨」이 된다.

**Acceptance Scenarios**:

1. **Given** 언어 모델 파일이 온전하고 검증 기록이 없을 때, **When** 받기를 시작하면, **Then** 전송 없이 검증 기록이 남고 성공한다.
2. **Given** 사진 모델 파일 둘이 온전하고 검증 기록이 없을 때, **When** 받기를 시작하면, **Then** 전송 없이 둘 다 검증 기록이 남고 「준비됨」이 된다.
3. **Given** 파일이 이미 「준비됨」일 때, **When** 받기를 시작하면, **Then** 전송도 지문 계산도 없이 성공한다.
4. **Given** 파일이 온전하고 검증 기록이 없고 남은 공간이 기준 크기보다 작을 때, **When** 받기를 시작하면, **Then** 공간 부족으로 거부되지 않는다.

---

### User Story 2 - 깨진 파일을 통과시키지 않는다 (Priority: P1)

크기는 기준과 같지만 내용이 온전하지 않은 파일(합치던 도중에 죽어 중간이 빈 파일, 예전 파일)이 있으면 쓰지 않고 다시 받는다.

**Why this priority**: 받지 않는 갈래를 새로 내면 깨진 파일이 통과할 위험이 함께 생긴다. 크기만 보면 안 되는 까닭이다.

**Independent Test**: 기준 크기이지만 지문이 다른 파일을 둔 채 받기를 시작하면, 그 파일이 지워지고 처음부터 전송이 시작된다.

**Acceptance Scenarios**:

1. **Given** 크기는 맞고 지문이 다를 때, **When** 받기를 시작하면, **Then** 파일을 지우고 처음부터 받는다.
2. **Given** 지문을 계산하지 못할 때, **When** 받기를 시작하면, **Then** 「준비됨」이 되지 않고 처음부터 받는다.
3. **Given** 크기가 기준과 다를 때, **When** 받기를 시작하면, **Then** 지문을 계산하지 않고 지금처럼 받는다.
4. **Given** 이어받기 기록이 있을 때, **When** 받기를 시작하면, **Then** 파일 크기와 상관없이 먼저 검증하지 않고 이어받는다.

---

### User Story 3 - 검증이 앱을 죽이지 않는다 (Priority: P1)

메모리 4GB iPhone에서도 필수 모듈의 검증이 메모리 한도로 앱을 끝내지 않는다.

**Why this priority**: 검증만 하는 갈래를 넣어도 검증이 앱을 죽이면 사용자는 같은 자리를 되풀이한다.

**Independent Test**: iOS 시뮬레이터에서 언어 모델 크기의 파일을 검증하는 동안 앱 메모리를 재서 파일 크기만큼 늘지 않음을 본다.

**Acceptance Scenarios**:

1. **Given** iOS 빌드일 때, **When** 언어 모델을 검증하면, **Then** 메모리 사용이 파일 크기에 비례해 늘지 않는다.
2. **Given** iPhone 13 mini에 새로 설치했을 때, **When** 필수 모듈을 받고 첫 일기까지 가면, **Then** 메모리 강제 종료 보고서가 생기지 않는다.

### Edge Cases

- 합치던 도중에 죽어 크기만 맞는 파일 → 지문이 달라 User Story 2의 경로로 간다.
- 사진 모델 파일 하나만 온전하면 → 온전한 것은 검증만 하고 나머지만 받는다.
- 기준 지문이 없는 자산 → 계산한 값을 기록하고 통과한다(지금의 채록 규칙 그대로).
- 검증 기록을 쓰지 못하면 → 「준비됨」이 되지 않고, 다음 번에 다시 검증한다.
- 받는 도중에 죽거나 끊긴 경우 → 이번 범위 밖이다. 지금처럼 처음부터 받는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 파일이 이미 「준비됨」이면 전송과 지문 계산 없이 성공해야 한다.
- **FR-002**: 이어받기 기록이 없고 파일 크기가 기준과 같으면, 공간 판단과 전송 전에 파일을 검증해야 한다.
- **FR-003**: 검증을 통과하면 검증 기록을 남기고 전송 없이 성공해야 한다.
- **FR-004**: 검증을 통과하지 못하면 파일을 지우고, 공간을 판단한 뒤 처음부터 받아야 한다. 통과하지 못한 파일을 「준비됨」으로 판정해서는 안 된다(MUST NOT).
- **FR-005**: 언어 모델과 사진 모델이 FR-001~FR-004를 똑같이 따라야 한다.
- **FR-006**: iOS의 검증은 메모리 사용이 파일 크기에 비례해 늘지 않아야 한다.
- **FR-007**: 검증 중 진행 표시는 실제 일에 없는 값을 지어내지 않아야 한다(원칙 V). 모델 이름·크기를 화면에 내지 않는다(원칙 III).
- **FR-008**: 받는 도중의 이어받기를 이번에 만들지 않는 까닭과 남은 과제를 로드맵에 적어야 한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 받기가 끝난 뒤 검증 기록 전에 앱을 끝내고 다시 받기를 시작하면 전송량이 0이다.
- **SC-002**: 크기만 맞고 내용이 다른 파일이 「준비됨」이 되는 경우가 0이다.
- **SC-003**: 언어 모델 검증 중 늘어나는 메모리가 파일 크기의 10% 아래다(판단 값 — 맥 실험의 풀 사용 2MB, 미사용 약 1.3GB를 가르는 선이며 iOS 측정값이 아니다).
- **SC-004**: iPhone 13 mini 새 설치에서 첫 일기까지 메모리 강제 종료 보고서가 0건이다.

## Assumptions

- 온전한 파일의 지문 계산 시간은 재지 않았다. 사용자가 몇 초에서 수십 초 멈춘 표시를 볼 수 있다고 가정한다.
- 13 mini의 종료 원인이 검증 메모리라는 것은 강한 후보이며 확정이 아니다. User Story 3의 기기 확인이 이를 가른다.
- 실기기는 다른 세션이 쓰고 있다. 코드와 시뮬레이터 측정을 먼저 끝내고, 기기 확인 전까지 과제를 완료로 닫지 않는다.
- 소유자가 받는 도중의 이어받기를 별도 과제로 미루기로 했다(2026-11-04).
