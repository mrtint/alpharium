# Findings: 백그라운드 자동 일기 생성 기술 검증

**대상 스펙**: [spec.md](./spec.md) · **작성일**: 2026-08-28

**실측 기기**: SM-S901N(Galaxy S22), Android 16(SDK 36), 삼성 원 UI. debug
빌드. 모든 실측값은 이 기기·이 OS 버전·이 제조사 조건에 한정된다(FR-002,
Assumptions).

## SC-001 — 결론: **조건부 가능(YES, 조건부)**

이 기기·조건에서 화면이 꺼지고 잠긴 상태의 백그라운드 실행이 **실제로
일어나고, 실제로 완주하며, 정상적인 일기를 남긴다.** 다만 실행 간격은
등록값(15분)이 아니라 **배터리 최적화 설정에 강하게 좌우된다** — 이것이
조건의 핵심이다.

- 배터리 최적화 **기본값**(예외 없음)에서는 15분 간격으로 등록해도 실제
  실행이 하루 1~2회로 억제되며, 관측된 두 실행 사이 간격이 **19시간
  33분 30초**(15분 대비 약 78배)였다.
- 배터리 최적화 **예외**(Doze 화이트리스트, 사용자가 설정 앱에서 "배터리
  사용량 최적화 안 함"을 켜는 것과 동일한 시스템 상태)를 준 뒤에는, 같은
  15분 등록이 **10~32분** 간격으로 도는 것을 관측했다(아래 표).

## SC-002 — 조건의 구체적 내용

**재현 조건**: 앱에 안드로이드 배터리 최적화 예외("배터리 사용량 최적화
안 함")를 사용자가 설정에서 켜야 한다. 이 조건 없이는 15분 간격 등록의
실제 효과가 거의 없다(하루 1~2회로 사실상 무의미해짐).

이 조건은 설정 변경만으로 재현 가능하다 — 별도 개발 없이:
`설정 → 앱 → alpharium → 배터리 → 제한 없음`(기기별 문구는 다를 수
있음). 검증에서는 동등한 시스템 상태를 `adb shell dumpsys deviceidle
whitelist +com.anonymous.alpharium`로 만들었다(research.md §8).

이 예외를 준 직후 시스템 신호도 함께 바뀌는 것을 확인했다:
- `adb shell am get-standby-bucket`: `40`대(억제됨) → **`5`(EXEMPTED,
  가장 우호적인 버킷)**로 즉시 전환.
- `adb shell dumpsys jobscheduler`의 해당 Job이 요청한 `Minimum
  latency`가 항상 `+14m59s***ms`로 15분 요청 자체는 정확히 전달되고
  있었다 — 즉 **앱/등록 코드의 문제가 아니라 OS가 실행 시점을 미루는
  것**이 원인이었다는 뜙이 이 신호로 뒷받침된다.

## SC-003 — 24시간 실측에서 시도 여부 100% 확인 가능한가

**확인됨.** 정식 라운드(1·2번, 배터리 최적화 기본값)에서 `verification-
log.jsonl`을 20시간여 뒤에 읽었을 때, 실행이 "시도조차 안 됐는지 몰랐다"는
결과는 없었다 — 로그에 `task-entered`가 정확히 2번 남아 있어 "언제
시도됐는지"가 그 자체로 답이 됐다. 로그가 비어 있었다면 그것도 "시도가
전혀 없었다"는 명확한 답이 됐을 것이다(H3: 로그 실패가 실행에 영향을
주지 않으므로, 로그의 부재는 곧 실행의 부재로 해석해도 안전하다).

## SC-005 — 권한 유효성이 별도로 기록되는가

**확인됨.** 6회 전부 `permission-checked` 이벤트가 `photos`/`location`
축을 각각 남겼다:
- `photos: valid=true` — 6회 전부. 오래 방치된 뒤에도 사진 접근 권한이
  살아 있었다(자동 회수 관측 안 됨).
- `location: valid=false` — 6회 전부. 이 앱은 애초에 좌표 권한을
  요청한 적이 없어(진단 화면에서 "아직 묻지 않음"으로 확인됨) 이
  값은 "권한이 회수됨"이 아니라 "원래 없었음"이다 — 004·009가 이미
  확립한 `unknown`/`none` 구분과 같은 함정이다. 이 검증은 좌표
  권한을 **부여한 상태에서 회수되는지**는 확인하지 못했다(권한을
  아예 요청하지 않은 기기였으므로) — 아래 "다음 스펙에서 고려할
  사항" 참고.

## User Story 2 — 백그라운드 온디바이스 추론이 완주하는가

**확인됨, quiet 캐릭터 기준.** 6회 전부 `pipeline-stage`가
`signals → (vision) → load → generation`로 정상 진행했고 중단 없이
`task-completed: ok`에 도달했다. 사진이 있는 날(1번, 3장)은 vision
단계가 별도로 3번 기록되며(장별 캡션) 전체 2분 27초, 사진 없는 날은
47초~2분 6초였다.

**미확인**: `SLOWEST_CHARACTER`(narrative, exaone 2.4B, 콜드 최대
242초 관측)로는 이번 라운드를 돌리지 않았다 — 진단 패널의 "가장 느린
캐릭터" 체크박스 기능은 구현돼 있으나 이번 6회는 모두 기본 선택
캐릭터(quiet)로 실행됐다. narrative가 백그라운드 시간 제한(WorkManager
콜백의 실행 창)을 실제로 위협하는지는 이 findings.md가 답하지 못한다.

## 한계 — `appState`는 화면의 물리적 꺼짐을 완벽히 보장하지 않는다

research.md §6a가 이미 명시한 한계가 실측 중 실제로 관측됐다: 3번
실행 직전(약 03:04~03:07경) `adb shell dumpsys power`로 확인했을 때
`mWakefulness=Awake`, `deviceLocked=0`으로 화면이 켜지고 잠금이 풀려
있던 순간이 있었다 — 이전의 반복된 `adb shell dumpsys` 조회 명령
자체가 화면을 깨웠을 가능성이 있다. 곧바로 화면을 다시 끄고
(`KEYCODE_POWER`) 잠금을 재확인(`deviceLocked=1`)한 뒤에도 태스크는
여전히 `appState: "background"`로 기록됐다 — 이는 `AppState`가 "이
순간 물리적으로 화면이 꺼져 있는가"가 아니라 "이 순간 앱 UI가
전경에 없는가"만 구분한다는 §6a의 한계를 정확히 보여준다. 3번
실행이 화면이 완전히 안정적으로 꺼져 있던 구간에서 자연 발생했다고
단정할 수는 없다 — 다만 4번 실행(31분 53초 뒤)은 그 사이 화면 조작을
하지 않았으므로 더 신뢰할 수 있는 표본이다.

## 실제 저장된 일기 — 정상적인 일기와 구분되지 않는다(FR-006)

3번 실행이 남긴 `2026-08-27.json`은 판정 4갈래를 정상적으로 통과했고
`quiet` 캐릭터의 "확실하지 않은 것은 짐작의 말투로" 규칙(014)이 그대로
반영된 문장("아마도 집 근처를 산책했거나... 확실히 알 수 없다")이었다.
1번 실행이 남긴 `2026-08-26.json`은 심어 둔 사진 3장(010 도구, `rich`
모양)의 좌표·캡션이 정확히 반영됐다. 백그라운드에서 생성됐다는 이유로
품질이나 판정이 달라지는 정후는 없었다.

## 공식 문서 근거 — "최소 간격"이 지켜지지 않는 것은 결함이 아니라 설계

실측(기본값 19시간 33분, 예외 적용 10~32분)이 우연이나 이 기기만의
특이 동작이 아니라는 것을 Context7로 확인한 Expo 공식 문서
(`https://docs.expo.dev/versions/unversioned/sdk/background-task`)가
뒷받침한다:

> "These tasks are **not guaranteed to run immediately**; instead,
> **the system schedules them at optimal times based on device
> conditions**. Developers can specify a minimum interval, but
> **execution depends on the system's availability and
> constraints**."

> "`minimumInterval`... **This value is treated as a minimum**, as
> **the system optimizes execution to minimize battery usage and
> wakeups**. While the default is 12 hours, the minimum allowed
> interval is 15 minutes."

> "Successful execution of a background task requires **sufficient
> battery charge and an active network connection**. If these
> conditions are not met, the task will not run."

즉 `minimumInterval: 15`는 "15분마다 반드시 돈다"는 약속이 아니라
"15분보다 짧게는 절대 안 돈다"는 하한선일 뿐이며, 실제 실행 시점은
시스템이 배터리 소모를 최소화하도록 스스로 고른다 — 이것이 공식
문서에 명시된 설계다. 이 저장소의 실측이 보여준 큰 편차(기본값
19시간대 vs 예외 적용 10~32분)는 이 설계가 배터리 최적화 설정에 얼마나
민감하게 반응하는지를 구체적인 시간으로 보여준 것이지, 버그나 이
하네스의 구현 결함이 아니다.

## 알림 기반 목적에 대한 적합성 — "정확한 시각"이 아니라 "완주 보장"이 필요한 경우 잘 맞는다

이 검증을 시작한 원래 동기(사용자 목표)는 "특정 시간에 일기가 자동으로
쓰이고, 완성되면 알림이 와서 사람이 눌러 보는 것"이었다. 이 절은 위
실측·공식 문서 근거를 바탕으로 그 목적에 이 경로(WorkManager 기반
`expo-background-task`)가 맞는지를 판단한다.

**맞는다 — 조건부로.** 이 목적의 본질은 "정확한 시각에 실행되는 것"이
아니라 "**언젠가는 반드시, 그리고 조용히 완주하는 것**"이다. 실측이
확인한 바가 정확히 이것이다 — 6회 전부 화면 꺼짐·잠금 상태에서
완주했고(`Success`), 배터리 최적화 예외를 주면 그 "언젠가"의 편차도
하루 단위에서 30분 이내로 좁혀진다. 알림은 "왔을 때 일기가 이미
완성돼 있는가"만 지켜지면 목적을 달성하므로, 정확한 시각을 보장하지
않는 WorkManager의 설계와 궁합이 맞는다.

**맞지 않는다 — 고정 시각(예: "매일 오전 9시")을 원한다면.** 이는
spec.md Clarifications에서 이미 명시적으로 배제한 alarm 계열
(`AlarmManager`/정확 시각 예약) API의 영역이며, 이 검증은 그 경로를
검증하지 않았다(배터리 최적화와의 충돌이 더 직접적이라는 이유로
애초에 범위 밖). "하루 경계를 넘긴 뒤 어느 시점엔가 온다"는 설계는
가능하지만 "몇 시 몇 분에 온다"는 설계는 이 경로만으로는 불가능하다.

이 경계가 020+ 스펙의 요구사항 범위를 가른다 — 아래 "다음 스펙에서
고려할 사항"에 반영한다.

## 다음 스펙에서 고려할 사항

이 절은 결정하지 않는다(spec.md Assumptions 마지막 항목) — 020+ 스펙을
쓸 때 참고할 조건만 나열한다.

- **알림 발생 로직 자체가 019 하네스에 없다.** `task-completed: ok`
  시점에 로컬 알림(`expo-notifications`)을 쏘는 코드는 이 검증
  범위 밖이었다 — 020 스펙의 핵심 신규 요구사항이다.

- **배터리 최적화 예외를 사용자에게 요청하는 온보딩 UX가 필요할 가능성이
  높다.** 예외 없이는 "매일 자동으로"라는 목표 자체가 하루 1~2회로
  사실상 무력화된다(19시간 33분 지연 실측). 안드로이드는 이 요청을
  위한 표준 인텐트(`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`)를
  제공하지만, 남용 시 스토어 정책 위반이 될 수 있어 "왜 필요한지"를
  사용자에게 설명하는 화면이 함께 필요하다.
- **E1(한 번에 하나의 추론 엔진) 잠금 설계가 필요하다.** 이 검증은
  경합을 막지 않고 관측만 했다(research.md §5) — 018에서 이미
  화면-백그라운드 경합의 위험이 지적됐고, 실제 기능화 시에는 화면에서
  "쓰기"를 누른 순간과 백그라운드 태스크가 겹치는 경우를 반드시
  설계해야 한다. 이번 검증에서는 우연히 겹치는 사례가 자연 발생하지
  않아 경합 자체는 재관측하지 못했다(quickstart.md 3단계, 수동 트리거
  절차는 준비돼 있으나 이번 라운드에서 별도로 실행하지 않음).
- **`SLOWEST_CHARACTER`(narrative) 기준의 백그라운드 완주는 미확인.**
  quiet(2분 내외)로는 여유 있게 완주했지만, 콜드 스타트 242초까지
  관측된 narrative가 WorkManager의 실행 시간 창 안에서도 안전한지는
  별도 확인이 필요하다.
