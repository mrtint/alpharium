# Quickstart: 진단 화면 개편 (060)

## 기기 없이

```bash
npm run test:logic   # DT·WF·DI·DV·AR·RP·CC 소스 계약
npm run test:ui      # DS·HR·TO (렌더)
npm test && npm run lint
```

위반 주입(최소, 치환이 실제로 적용됐는지 먼저 단언하고 주입 뒤 원래 문자열이 돌아왔는지 다시 grep한다 — AGENTS):
(1) `diag.tryOnce.toast` 문구 한 글자를 바꾸면 DT1이 잡는가 (2) `classify`의 `rejected: empty`를 `unwritten`으로 바꾸면 WF1이 잡는가 (3) 기록 항목에 `durationMs` 필드를 더하면 WF3이 잡는가
(4) 홈 `generate`에서 `cancelled` 검사 앞으로 `recordWriteFailure`를 옮기면 WF7이 잡는가 (5) 신호 칸에서 `network`를 빼면 DS4·CC1이 잡는가 (6) `DiagnosticsParts.tsx`에 `diary/prompt` import를 넣으면

(9) 걸음 칸에 `known` 입력을 줘도 「모름」이 아니게 바꾸면 DV2가 잡는가 (10) `unknown` 사진을 0장으로 옮기면 DV3이 잡는가.

## dev 실기기 (SM-S901N)

전제: AGENTS 「도구 사용법」 — **새 네이티브 모듈이 없어 빌드는 필요 없다.** 이미 설치된 dev 빌드로 Metro만 새 번들을 서빙한다: `EXPO_PUBLIC_APP_ENV=dev npx expo start --dev-client`,
`adb reverse tcp:8081 tcp:8081`, 잠금 해제(`dumpsys trust`의 `deviceLocked=0`). `pm clear`·`am force-stop`·`am start -S`를 쓰지 않는다 — 앱을 벗어날 때는 홈 버튼, 다시 열 때는 `am start`.
Git Bash에서 `adb` 기기 경로 인자 앞에 `MSYS_NO_PATHCONV=1`. 좌표를 누르기 전에 스크린샷으로 현재 화면을 확인한다.

### 0. 백업 (반드시 먼저)

```bash
P=com.anonymous.alpharium
MSYS_NO_PATHCONV=1 adb shell "run-as $P sh -c 'cd files && tar cf - diary vision-cache preferences'" > C:/Users/mrtin/AppData/Local/Temp/alpharium-060-backup.tar
tar tf C:/Users/mrtin/AppData/Local/Temp/alpharium-060-backup.tar | head
MSYS_NO_PATHCONV=1 adb shell "run-as $P ls -l files/models" | tr -d '\r'   # 모델 3파일의 크기·시각 — 끝난 뒤 그대로여야 한다
MSYS_NO_PATHCONV=1 adb shell "run-as $P sh -c 'cd files && md5sum preferences/*.json'" > C:/Users/mrtin/AppData/Local/Temp/alpharium-060-before.md5
```

백업을 눈으로 확인하기 전에는 1 이후를 하지 않는다. 057 시드 사진(10월 1일·9월 30일 각 4장)은 지우지 않는다. 이 조각이 지우는 파일은 없다(진단은 읽기와 `write-failures.json` 쓰기뿐이다).

### 1. 일곱 묶음 (SC-001)

홈 → 점 셋 → 설정 → 개발자 → 「진단」. 위에서부터 환경(빌드 `DEV · …`·기기 `Android 16`·추론 위치 「기기 · CPU」) / 저장 점검 / 사진 권한 / 신호 프로브 · 오늘 / 입력 프롬프트 미리보기 / 생성 / 최근 실패가
보드 순서로 모두 보이는지 스크린샷으로 본다. 모델 이름이 어디에도 없는지 본다. 글꼴 2.0배(`settings put system font_scale 2.0` — 끝나면 원래 값으로 복원)에서 잘림이 없는지 본다.

### 2. 저장 점검 (US1)

「저장 점검」 행을 누르면 값이 「{n}편 · 정상」으로 바뀐다 — n이 `files/diary/`의 `YYYY-MM-DD.json` 개수와 같다. **깨진 파일 유도는 `diary/`의 복사본 하나에서만 한다**(백업이 있는 상태에서):
`run-as`로 한 날의 JSON 끝을 잘라 점검하면 「{n}편 · 1편 읽기 실패」가 되고, 원래 파일을 되돌린 뒤 md5로 확인한다.

### 3. 사진 권한과 신호 프로브 (US2)

사진 권한 묶음의 읽기·위치 정보·범위가 설정의 사진 행과 같은 사실을 말한다(현재 기기 상태 — 부분 허용이면 범위 「선택한 사진만」). 신호 프로브: 사진·장소는 숫자 또는 「없음」, 걸음·배터리·연결은 회색 「모름」.
「다시 읽기」를 누를 때만 갱신되는지(다른 앱을 다녀와도 값이 그대로) 본다. 권한을 끄는 실험은 하지 않는다(프로세스가 죽는다 — 057).

### 4. 프롬프트 미리보기 (US5)

프리셋 1 ↔ 2 전환으로 본문이 바뀌고(2에 「사진은 두 장이 남았다.」), 본문 상자가 안에서 스크롤되며 길게 눌러 글자를 선택할 수 있다. `maestro test .maestro/prompt-preview.yml`로 자동 확인(FLOWS 등록 확인).

### 5. 지금 한 번 써 보기 (US3, SC-003)

오늘 일기가 없는 상태(필요하면 `diary/`의 오늘 파일을 이름만 바꿔 빼 둔다 — 백업 있음)에서 「지금 한 번 써 보기」 → 진단·개발자·설정이 닫히고 홈이 오늘 쓰는 중으로 시작하며 토스트
「진단에서 쓰기를 시작했어요.」가 2초 뜬다. 쓰는 중 하단 바(그만두기)와 토스트가 겹치지 않는지 스크린샷으로 본다(R11). 끝나면 오늘의 쓴 날이다.
오늘 일기가 있을 때 다시 눌러 덮어쓰기 확인 없이 쓰는 중으로 가고, 끝나면 새 글로 바뀌는지 본다. 쓰는 중에 설정을 다시 열어 진단에서 또 눌러도 두 번째 쓰기가 시작되지 않는지 본다.

### 6. 최근 실패 (US6, SC-004)

저장 실패 유도(054 방법): 일기 폴더를 `run-as chmod 500 files/diary`로 막고 홈에서 쓰기 → 토스트 「일기를 쓰지 못했어요.」 → 진단의 「최근 실패」에 「저장하지 못함」 한 줄과 시각.
권한을 되돌린다(`chmod 700`) → `ls -ld`로 확인. 그만두기는 기록이 안 늘어나는지(쓰는 중에 「그만두기」) 본다. `preferences/write-failures.json`의 키가 `reason`·`at`뿐인지 `cat`으로 본다.

### 7. 자동 쓰기 지금 실행 (US4)

설정의 「자동으로 쓰기」 현재 값과 시각을 **먼저 적어 둔다**(끝나면 복원). 시각이 지금과 먼 값이어도 「자동 쓰기 지금 실행」이 동작하는지(결과 줄이 「썼음」 또는 「건너뜀」) 본다 — 안 쓴 날이 없으면 「건너뜀」이 맞다.
시드 사진이 있는 안 쓴 날이 있으면 쓰고 완성 알림이 온다(057 문구). **미확인으로 남길 수 있는 것**: 헤드리스에서의 실패 기록(AR5는 계약 테스트로 갈음).

### 8. 끝낸 뒤

설정 값(자동 쓰기·시각·글꼴 배율)을 원래대로 되돌리고 `md5sum preferences/*.json`이 before와 같은지(write-failures.json 제외) 본다. Metro를 끈다 — 셸만이 아니라 8081을 쥔 node 프로세스까지:
`netstat -ano | findstr :8081` → 해당 PID `taskkill`. 실기기 결과는 이 문서 끝에 날짜와 함께 적는다.

### 후속 확인 (같은 날, 사용자 승인 아래 상태를 바꿔 가며)

시작 전 `diary`·`vision-cache`·`preferences` tar 백업과 md5를 새로 떴고, 끝낸 뒤 `preferences/*.json`·`diary/*.json` md5가 처음과 모두 같고 `vision-cache`는 20개 그대로다. 심은 사진은 내 것(`seed:day one-place 2026-10-05`)만 `seed:clear -- 2026-10-05`로 지웠다(057 시드 35장 유지).

- **재료 있는 날의 「자동 쓰기 지금 실행」** — 10월 5일에 사진 4장을 심고 눌렀다(설정 토글 꺼짐·목표 시각 17시·지금 9시대 — 시도 창·토글 무시). 약 80초 뒤 `2026-10-05.json`이 생기고 「썼음」, `notified.json`에 그 날 항목(`acknowledged:false`)이 생겨 완성 알림이 나갔다. **AR1이 기기에서도 성립한다.**
- **깨진 일기의 「읽기 실패」** — 잘린 JSON(`2026-09-02.json`)을 심고 진단을 다시 열어 「저장 점검」을 누르자 「13편 · 1편 읽기 실패」. 지운 뒤 원래 목록으로 돌아왔다. 저장 점검 행은 눌러야 읽는다(열 때 자동으로 읽지 않는다 — 처음엔 빈 값).
- **부분 허용 기기** — `pm revoke READ_MEDIA_IMAGES`(`READ_MEDIA_VISUAL_USER_SELECTED`는 그대로)로 재현. 설정 사진 행 「일부 허용」, 진단 「사진 읽기 일부 허용」·「범위 선택한 사진만」, 신호 칸 사진·장소·걸음 모두 「모름」(0으로 세지 않는다). 사진 위치 정보 행은 꼬리표가 비었다(055 `permissionTagFor`가 부분 허용에서 그 행을 읽지 못함으로 보는 것 — 이 조각의 변경 아님). `pm grant`로 원래대로.
- **백그라운드 쪽 실패 기록** — 자동 쓰기를 켜고 시각을 지금 시(9시)로 두자 앱이 홈으로 가기 전 `runAutoDiaryTask`(소유자 `background`)가 바로 돌아 잠금을 쥐었다. `chmod 500 files/diary`로 저장을 막아 두자 약 9분 뒤(헤드리스 생성이 느리다) `write-failures.json`에
  `{"reason":"save","at":…}` 한 줄이 생겼다 — **실패 기록이 `runAutoDiaryTask` 경로에서 실제로 쓰인다.** 기록 시각 `at`은 실패한 순간이 아니라 실행 시작 시각(`now` 인자)이다(진단 줄의 시각이 실패보다 이르다 — 보드 「최근 10건」에는 문제 없고 고치지 않았다).
  OS가 깨운 잡(`cmd jobscheduler run -f`)은 앱 안에서 이미 돌던 실행이 잠금을 쥐고 있어 합류만 했다(`already-running` → 기록 없음, WF3·AR5와 같다).
- **관찰하고 못 푼 것**: 앱을 연 직후 첫 1분 동안 「자동 쓰기 지금 실행」을 연달아 세 번 눌렀을 때 5초 안에 「실패 · 사진을 읽지 못함」이 세 번 기록됐다(진단 줄 3개). 같은 날 JS를 다시 불러온 뒤나 프로세스를 다시 띄운 뒤에는 같은 누름이 성공했고, 이유 문구는 기록하지 않아(D3) 원인을 더 못 좁혔다. 재현되면 `result.stage`를 임시로 찍어 본다.
  이 구간의 기록 항목 자체가 맞게 쌓인 것(「사진을 읽지 못함」 갈래)은 확인했다.

**미확인**: OS가 깨운 잡이 스스로 실패하는 경로의 실측(위 앱 안 백그라운드 실행으로 같은 함수를 확인했다), 위의 첫 1분 「사진을 읽지 못함」 3회의 원인, 홈 쓰기 시작 직후 설정 겹이 닫히는 240ms 동안의 시각 확인(녹화 프레임 — 스크린샷으로는 겹치지 않음을 보았다), 다른 기기의 토스트 바닥값.

### 후속 수정 — 프롬프트 미리보기의 안쪽 스크롤 (사용자 지적)

안쪽 스크롤 상자(`maxHeight 240`)를 읽다가 끝에 닿으면 같은 손가락이 바깥 지면으로 넘어가 화면 전체가 갑자기 흘렀고, 마지막 줄이 상자 바닥에 걸려 잘려 보였다(padding이 `ScrollView`의 `style`에 있었다). 기기에서 같은 증상을 재현했다(상자가 끝에 있을 때 상자 안을 쓸어도 지면이 움직임).
시도 둘은 안 통했다 — (1) 상자를 만지는 동안 바깥 `scrollEnabled`를 잠그는 맥락(안드로이드 중첩 스크롤은 그것을 무시하고 계속 넘겼다), (2) `nestedScrollEnabled`를 빼고 잠금만 쓰기(상자는 안 움직이고 지면만 흘렀다). 그래서 안쪽 스크롤을 없애고 본문을 테두리 상자에 다 펼쳤다(지면 하나로만 스크롤).
기기에서 마지막 줄 「이 기록으로 그 하루의 일기를 써라.」까지 온전히 보이고 상자 안을 쓸어도 지면 하나만 움직인다. 소스 계약(`ScrollView`·`nestedScrollEnabled` 부재)이 `diagnostics-screen.test.tsx`에 있고 위반 주입(`ScrollView`를 되살림)이 실패로 잡혔다. 보드 `6h` ⑤의 「텍스트 상자는 안에서 따로 스크롤」은 이 조각이 뒤집었다(저장소 소유자 확인 대상).

### 후속 수정 — 보드 `6e`·`6h`와 모양 맞추기 (사용자 지적)

이 조각은 문구(KO 표)만 글자 단위로 잠갔고 **모양은 보드와 대조하지 않았다** — 개발자·진단 화면이 보드와 달랐다. 보드 마크업(`Alpharium Mobile Screens.dc.html`의 `6e`·`6h`)을 헤드리스 크롬으로 열어 치수를 읽고 맞췄다:

- 개발자 「진단」 묶음: 머리 오른쪽에 「개발 빌드만」(고정폭 10/600), 행은 높이 56·보조 줄 「환경 · 저장 · 사진 권한 · 프로브 · 프롬프트 · 실패」(고정폭 11)·›. 제목 오른쪽 작은 글자는 고정폭 11/600(`DEV · 1.0.0 (9)`), 진단 겹에도 「DEV」.
- 고정폭 값은 13(일반 값 15보다 작다). 사진 권한 값은 꼬리표가 아니라 고정폭 글자, 저장 점검 값은 고정폭 + ›.
- 신호 프로브: 한 줄 다섯 칸(위 2px·아래 1px 선, 칸마다 왼쪽 1px 선, 모름 칸 회색 면), 「다시 읽기」는 묶음 머리 오른쪽 밑줄 글자. 글꼴 2.0배에서 칸 글자는 1.4배까지만 키운다(「배터리」가 낱글자로 갈라졌다).
- 프리셋은 한 덩어리 전환 막대(2px 테두리·높이 34·고른 칸 검정 면), 생성은 높이 48·모서리 6의 전폭 버튼 둘(테두리 / 검정 면). 결과 한 줄은 버튼 아래 보드 밖 자리.
- 보드의 프롬프트 상자는 「(예시)」 회색 줄 모형이라 실제 본문(`selectable`)으로 두었다.
  기기(SM-S901N, 360dp 폭)에서 보드 치수와 행 높이 44가 맞는 것을 `uiautomator` 경계로 확인했다. 설정 화면 `6c`는 이미 보드 치수 그대로다(행 44·라벨 15/600·묶음 머리 11/600).

### 후속 수정 — 홈의 큰 숫자가 글꼴 배율을 안 따랐다 (사용자 지적)

안드로이드 14+는 글꼴 배율을 비선형으로 적용해 큰 글자(62·48)는 거의 안 키운다 — 큰 날짜·사진 수·장소 수 숫자만 제자리고 옆 요일·상태 줄·라벨은 자라 한 묶음이 어긋났다. `src/ui/font-scale.ts`의 `useFontScale()`로 크기·줄높이·자간에 배율을 **선형으로 곱하고** `allowFontScaling={false}`로 시스템 배율을 끈다(`DiaryListScreen` `DayFace`, `MaterialGrid`). 기기 글꼴 2.0배에서 숫자가 같이 자랐고 소스·값 테스트와 위반 주입(곱셈을 빼면 실패)을 잠갔다.
