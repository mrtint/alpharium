## §1. 캡션 사본 삭제 시점 이동 — 책임을 어디에 두는가

**결정**: 삭제 여부 판정은 캡션 계층(`vision/caption.ts`)이 하지 않는다. 캡션
계층은 "이 장이 리사이즈됐다면 그 경로가 무엇인지"만 결과에 실어 돌려주고, **지울지
말지는 파이프라인(`diary/pipeline.ts`)이 저장 성공을 확인한 뒤에 정한다.**

**근거**:
- `caption.ts:114-123`이 이미 `shouldCleanup = resized.path !== path`(원본과 같은
  경로면 지우지 않는다, FR-006 원본 보호)를 판정해 두고 있다 — 이 판정 자체는 지금도
  옳고 그대로 둔다. 바뀌는 것은 "언제" 지우느냐이지 "무엇을" 지우느냐가 아니다.
- `vision/`은 `diary/store`를 모른다(헌법 검사가 강제하는 경계, AGENTS.md). 캡션
  계층이 "이 일기가 결국 저장될지"를 알 수 없으므로, 캡션 계층 스스로 삭제 여부를
  정하면 그 경계를 넘어야 한다 — 대신 **삭제하지 않고 정보만 위로 올린다.**
- `pipeline.ts`의 6단계(저장)는 이미 판정 통과(5단계)와 저장 성공을 둘 다 아는
  유일한 자리다(`pipeline.ts:212-234`). 사진 보존 여부를 최종 결정하기에 정확히
  맞는 위치다.
- **판정 거부·저장 실패 시 사본을 즉시 정리한다.** 그러지 않으면 재시도마다 새
  사본이 쌓인다 — 단, `resizedFileNameFor()`(on-device.ts:479)가 **소스 경로 기준
  결정론적 파일명**을 쓰므로 같은 사진을 다시 캡션하면 같은 파일을 덮어쓸 뿐 늘지
  않는다. 위험한 것은 **서로 다른 사진**이 매 시도마다 새로 캡션되며 쌓이는 경우
  (예: 사용자가 재시도할 때마다 다른 5장이 선택될 가능성은 낮지만 — `selectForVision`
  은 결정론적이므로 같은 하루·같은 신호면 같은 5장이 나온다. 따라서 실제로는 누적
  위험이 이미 낮다). 그럼에도 **정직성을 위해** 거부·실패 시에는 명시적으로 지운다 —
  "왜 남아 있는지 설명할 수 없는 파일"을 만들지 않는다.

**흐름**:
1. `captionAll()`은 지금처럼 각 장을 리사이즈·캡션하되, **`finally`의 즉시
   `cleanup()` 호출을 없앤다.** 대신 성공한 캡션의 `PhotoCaption`에
   `resizedPath`(리사이즈된 경우만, C1이면 없음)를 싣는다. 실패한 장(캡션 결과
   빈 문자열 등, `caption.ts:143`의 `continue`)은 **그 자리에서 즉시 지운다** —
   실패한 캡션은 어차피 아무도 참조하지 않으므로 미룰 이유가 없다.
2. `on-device.ts`의 `readPhotos()`가 `captionAll()`의 결과(`PhotoVision`)를 그대로
   위로 전달한다 — `PhotoVision.captions[].resizedPath`가 이미 실려 있다.
3. `on-device.ts`의 `generate()`가 성공 시 `DiaryDraft`에 `usedPhotos`(캡션 성공한
   사진의 id·시각·`resizedPath`)를 함께 담아 반환한다. **여기서도 지우지 않는다.**
4. `pipeline.ts`가 `judge()` 통과 + `store.save()` 성공을 확인한 뒤:
   - 성공 → `usedPhotos`를 그대로 `DiaryEntry.photos`에 옮겨 담는다(사본은 남는다).
   - 판정 거부(`generation`/`vision` 단계 실패) → 애초에 `DiaryDraft`가 없으므로
     `usedPhotos`도 없다. **어디서 지우는가?** 캡션까지는 끝났지만 이후 실패한
     경우이므로, `on-device.ts`의 `generate()`가 실패 갈래로 반환하기 직전에
     **자신이 만든 `usedPhotos` 후보를 스스로 정리**한다(캡션 계층을 벗어나지
     않는 자기 정리 — `judge()` 실패·타임아웃·끊김 등 `generate()` 내부에서
     실패가 확정되는 모든 경로에 적용).
   - 저장 실패(`storage` 단계) → 이 경우는 `DiaryDraft`가 성공했었다는 뜻이라
     `usedPhotos`가 이미 있다. `pipeline.ts`가 저장 실패를 확인한 시점에 그
     사본들을 정리한다.

**대안 기각**: "캡션 계층이 아예 지우지 않고 모든 리사이즈 사본을 영구 보존, 별도
청소 작업(가비지 컬렉션)이 주기적으로 돈다"는 방식도 고려했으나, 새로운 백그라운드
작업이라는 별도 복잡도를 더하고 "지금 이 요청이 결국 저장됐는가"라는 이미 아는
사실을 다시 추론해야 해서 기각했다.

## §2. 대표 좌표 — 새 관측이 아님을 실측으로 남긴다

**결정**: `tracePlaces()`가 시각순으로 묶은 자리 목록(`places: Coordinate[]`,
`places.ts:93-100`) 중 **`places[0]`(첫 자리, 하루의 첫 사진이 찍힌 자리의 대표
좌표)**을 `PhotoPlaces.representativeCoordinate`로 함께 반환한다.

**"체류 시간이 가장 긴 자리"를 채택하지 않은 근거**: clarify에서 옵션 A의 설명에
"가장 오래 머문 자리 또는 첫 사진의 위치"라고 두 후보를 나란히 적었으나, **체류
시간은 지금 어디에도 계산되지 않는다.** `tracePlaces()`는 각 자리에 속한 사진이
몇 장인지도, 그 자리에 머문 시간 폭도 계산하지 않는다(순수하게 "다음 좌표가 100m
밖이면 새 자리"로만 센다, `places.ts:95-101`). 체류 시간·사진 수를 새로 세는 것은
**새로운 축을 측정하는 것**이고, 헌법 원칙 IV가 경계하는 것과 정확히 같은 모양이다
(무언가를 세서 "어느 것이 더 큰가"를 정하는 순간 측정 장치가 된다). 반면 "첫 자리"는
`tracePlaces()`가 **이미 계산하고 버리던 값**을 그대로 노출하는 것뿐이다 — 원칙
IV와 부딪히지 않는 유일한 선택지다.

**구현**:
```ts
// places.ts — tracePlaces()의 반환 직전에 추가
return {
  visitCount: places.length,
  approximateDistanceMeters: Math.round(total),
  ...(places.length > 0 ? { representativeCoordinate: places[0] } : {}),
};
```
`points.length === 0`인 조기 반환 경로(`places.ts:86-88`)는 `representativeCoordinate`
없이 그대로 둔다 — 좌표 자체가 없는 하루다.

**`PhotoPlaces`로 옮기는 경로**: `places.ts`의 `tracePlaces()`를 부르는 호출자
(신호 수집 계층, `signals/expo-port.ts` 계열)가 `PlaceTrace`를 `PhotoPlaces.trace`에
그대로 얹듯이, `representativeCoordinate`도 같은 자리에서 함께 옮긴다 — 새 호출
경로를 추가하지 않는다.

## §3. `expo-location`의 `reverseGeocodeAsync` — 권한 요구 사실 확인 계획

**조사 결과 (공식 문서 기준, 2026-08 시점)**: `Location.reverseGeocodeAsync()`는
Android에서 **`ACCESS_COARSE_LOCATION`(또는 `ACCESS_FINE_LOCATION`) 런타임 권한이
승인되어 있어야 동작한다** — 이미 손에 쥔 좌표를 이름으로 바꾸는 것뿐이라도, 안드로이드
`Geocoder` API 자체가 앱의 위치 권한 상태를 확인하기 때문이다(승인이 없으면 빈
배열 또는 예외를 던진다는 것이 문서화된 동작이다). **이것은 004가 사진의 GPS
EXIF를 읽는 데 썼던 `ACCESS_MEDIA_LOCATION` 권한과는 다른, 별도의 새 런타임
권한이다.**

**결정**: FR-006(설정을 켤 때 고지)이 이 사실을 반영해야 한다 — "좌표를 기기의
지도 서비스에 물어봅니다"라는 고지와 함께, **설정을 켜는 순간(또는 그 설정이 켜진
채 첫 일기를 생성하는 순간) 위치 런타임 권한을 요청한다.** 권한이 거부되면
`reverseGeocodeAsync()` 호출 자체가 실패하거나 빈 결과를 주는데, 이는 FR-007의
`unknown`(좌표는 있으나 이름을 못 얻음) 경로로 자연스럽게 흡수된다 — **별도의
"권한 거부" 갈래를 새로 만들지 않는다**(원칙 IV, 판정 갈래를 늘리지 않는다는 이
저장소의 반복된 관례).

**실기기 확인이 필요한 지점**(quickstart.md D1으로 옮김): 이 문단의 "권한이
필요하다"는 문서 기반 짐작이며 아직 이 저장소의 실측이 아니다(원칙 V) — 실기기에서
권한을 거부한 채 `reverseGeocodeAsync()`를 불러 실제로 무엇이 오는지(예외인지 빈
배열인지) 확인해야 `geocoding-port.ts`의 catch 경계를 정확히 그릴 수 있다.

## §5. 은/는 조사 — `particle.ts` 확장

**결정**: `particleFor()`(이/가)와 배치임 판정 로직을 공유하는 `topicParticleFor()`
(은/는)를 같은 파일에 추가한다.

```ts
// particle.ts
function hasBatchim(name: string): boolean | undefined {
  const last = name.at(-1);
  if (last === undefined) return undefined;
  const code = last.codePointAt(0);
  if (code === undefined || code < HANGUL_BASE || code > HANGUL_LAST) return undefined;
  return (code - HANGUL_BASE) % 28 !== 0;
}

export function particleFor(name: string): "이" | "가" {
  const batchim = hasBatchim(name);
  return batchim === undefined || !batchim ? "가" : "이";
}

export function topicParticleFor(name: string): "은" | "는" {
  const batchim = hasBatchim(name);
  return batchim === undefined || !batchim ? "는" : "은";
}
```

**테스트 함정 확인**: 로스터 5인(금동이·루이·오드·샤오바이·모카) 이름이 **전부
받침 없이 끝난다**(이/드/이/이/카 — 어느 것도 종성이 없다). 즉 실제 로스터만으로는
"은"과 "이" 분기가 전혀 테스트되지 않는다 — 016의 `particle.test.ts`도 같은 함정을
이미 안고 있었을 가능성이 높다. **이번 테스트는 로스터 5인 + 받침 있는 합성 이름
(예: "테스트", "민준") 최소 1개를 함께 검사해야** 두 분기 모두 실제로 확인된다.

## §8. 제목 지시문 보강 — 무엇을 어떻게 고치는가

**배경**: 사용자가 실기기에서 관찰한 제목이 "금동이의 오늘일기"류였다(2026-08-23
피드백). `prompt.ts:106`의 현재 지시문("첫 줄에 제목을 짧게 쓰고...")은 형식(위치·
길이)만 말하고 **내용**을 말하지 않는다 — 모델이 안전한 디폴트로 캐릭터 이름+날짜
재조합을 택한 것으로 보인다. 005~012가 반복해서 겪은 패턴("무엇을 쓸지는 말했지만
어떻게 쓸지는 말하지 않았다")과 같은 종류이며, 014의 짐작 어미 지시가 이미 이
저장소의 정석 해법(예시를 곁들인 구체적 지시문 보강)을 보여준다.

**결정**: `TITLE_INSTRUCTION`에 다음을 더한다(정확한 문구는 T-태스크에서 확정,
아래는 방향):
1. **금지 예시를 구체적으로 든다** — "{이름}의 오늘 일기", "{이름}의 하루"처럼
   캐릭터 이름과 날짜만 재조합한 제목은 쓰지 말라고 명시한다. 011·012가 "하지 말
   것"을 예시로 든 것과 같은 방식(추상적 형용사보다 구체적 반례가 더 잘 통했다는
   경험적 관례).
2. **무엇을 담을지 구체적으로 요구한다** — "그날 본 것 중 가장 기억에 남는 장면이나
   자리 하나를 제목에 담아라" 류로, 프롬프트에 이미 실려 있는 신호(사진 캡션·자리
   수)를 참조하도록 유도한다.
3. **짐작 어미 규칙(014 US3)이 제목에도 적용됨을 명시한다** — 확실하지 않은 것은
   "~인 것 같다"류로 짐작해도 된다는 규칙이 본문뿐 아니라 제목에도 적용된다고
   분명히 해, "구체적으로 쓰라"는 새 요구가 "지어내라"로 오독되지 않게 한다(원칙
   II 방어, contracts/title.md).

**되뱉기 판정과의 관계**: 기존 주석(`prompt.ts:101-103`)이 이미 확인했듯
`TITLE_INSTRUCTION`은 `instructionLines()`에 담겨 되뱉기(`isEcho()`) 판정 대상이다.
지시문에 구체적 예시 문구를 추가할 때, 그 예시 문구 자체가 우연히 실제 제목과 겹쳐
되뱉기로 오판되지 않도록 예시는 "이런 식으로 재조합하지 말라"는 **금지 예시**로만
쓰고, "이렇게 써라"는 **완성된 문장 형태의 긍정 예시**는 넣지 않는다(모델이 그
문장을 그대로 베낄 대상을 안 주는 것이 안전하다).

**품질 검증 방식 — 채점 코드를 만들지 않는다**(원칙 IV): "제목이 재조합 패턴인지"를
정규식이나 유사도로 자동 판정하는 코드는 만들지 않는다 — 그 순간 이것이 임계값을
가진 채점 장치가 되고, 원칙 IV가 되돌리려던 것과 같은 모양이 된다. 대신:
- **기기 없는 테스트는 지시문 자체의 내용을 검사한다**(`prompt.test.ts`) — 지시문
  문자열에 금지 예시·구체성 요구·짐작 어미 언급이 포함되는지 확인한다. 이것은
  "우리가 무엇을 요구했는가"를 검증하는 것이지 "모델이 무엇을 냈는가"를 채점하는
  것이 아니다.
- **실기기 검증은 사람이 직접 여러 하루의 제목을 읽는다**(quickstart.md, 016의
  T022 「사용자가 문구를 검수받는다」와 같은 방식) — 자동화된 통과/실패 기준을
  두지 않는다.

**대안 기각**: "제목 생성을 별도 짧은 프롬프트로 분리해 재시도 가능하게 한다"는
방식도 고려했으나, 별도 판정 갈래(제목 품질 거부)가 필요해지고 그것이 `judge()`의
4갈래 불변식(005 FR-018b, "테스트가 그 수를 직접 센다")을 깨므로 기각했다. 본문과
제목은 여전히 한 번의 생성에서 함께 나온다(014의 기존 구조 유지).

## §9. 마크다운 노출·본문 부제목 — 실측 원인과 대응 (2026-08-23 재조사)

**실측 데이터**: 사용자가 실기기 화면에서 "제목과 부제목이 헷갈린다"고 재차
지적해, 기기(`adb -s <serial> shell run-as com.anonymous.alpharium cat
files/diary/<날짜>.json`)에서 저장된 일기 JSON을 직접 읽었다.

- `2026-08-22.json`(금동이/quiet): `title: "금동이의 하루 기록"`,
  `text: "빈 줄\n\n15시: 주인은 공원(벽돌 길, 나무)에서 사진을 찍었다..."`.
  본문이 **"빈 줄"이라는 두 글자로 시작**한다.
- `2026-08-21.json`(루이/narrative): `title: "### 루이의 일기"`,
  `text: "**2026-08-21**\n\n오늘은 주인이 보이지 않았지만..."`. 제목에
  **마크다운 헤더 기호(`###`)**가, 본문 첫 줄에 **마크다운 굵게 기호로 감싼
  날짜 반복**이 그대로 들어 있다.

**원인 분석**:
1. **"빈 줄" 문자 그대로 노출**: `TITLE_INSTRUCTION`(`prompt.ts:106`)이 "빈 줄을
   하나 넣은 뒤"라는 문구를 쓰는데, quiet(kanana) 모델이 이 **서식 지시**를
   **내용 지시**로 오독해 "빈 줄"이라는 글자 자체를 한 문단으로 써버린 것으로
   보인다 — 그 뒤에 실제 빈 줄이 이어지는 것이 이 해석을 뒷받침한다(지시문을
   "제목 / 빈 줄(문자) / 진짜 빈 줄 / 본문"으로 4단 구조로 오해했을 가능성).
   `isEcho()`(되뱉기 판정)는 이렇게 짧은 2글자 되뱉음을 잡기에는 임계값이 맞지
   않는다 — 새 판정 갈래를 만들지 않는 이 저장소의 원칙(원칙 IV)상, 이 판정을
   더 예민하게 조이는 것보다 **애초에 오독의 소지가 있는 문구를 지시문에서
   없애는 것**이 맞는 방향이다.
2. **마크다운 노출**: 프롬프트 어디에도 "마크다운을 쓰지 마라"는 지시가 없다
   (`SPEAKER_RULES`·`TITLE_INSTRUCTION` 전체를 확인, `prompt.ts:74-106`). narrative
   (exaone) 모델이 긴 글을 쓰는 성향(헌법 로스터 「길게 쓴다. 감정과 추측을 얹어
   서사를 만든다」)과 맞물려 마크다운 서식(헤더·굵게)으로 구조를 표현하려 한
   것으로 보인다 — 학습 데이터에 마크다운 형식의 글이 섞여 있는 인스트럭트
   모델에서 흔한 현상이다.
3. **본문 첫 줄의 날짜 재반복**: `TITLE_INSTRUCTION`이 "본문을 이어서 적어라"라고만
   할 뿐 본문이 무엇으로 시작해야/시작하지 말아야 하는지 말하지 않는다 — 제목
   재조합 문제(§8)와 같은 뿌리("무엇을 쓸지는 말했지만 무엇을 쓰지 말지는
   말하지 않았다")가 본문 시작 지점에서도 반복된 것이다.

**결정**: `TITLE_INSTRUCTION`(또는 그 인근의 별도 서식 지시문)에 다음을 더한다:
4. **마크다운을 쓰지 말라고 명시한다** — "#", "*", "**" 같은 기호를 쓰지 말고
   그냥 줄글로 쓰라고 구체적으로 예시를 든다(011·012의 관례 — 추상적 "서식 없이"
   보다 기호를 직접 나열하는 것이 더 잘 통한다).
5. **"빈 줄을 넣어라"라는 서식 지시 문구 자체를 바꾼다** — 모델이 문자 그대로
   되뱉을 소지가 있는 "빈 줄"이라는 단어 대신, 서식을 실제 개행 구조로만
   전달하는 표현으로 고친다(예: 지시문 자체에서 "빈 줄"이라는 낱말을 빼고
   줄바꿈을 직접 예시로 보여주는 방식 — 정확한 문구는 T-태스크에서 확정).
6. **본문은 날짜·제목을 반복하지 않고 바로 하루 내용으로 시작하라고 명시한다** —
   제목이 이미 그날을 요약하므로 본문에서 같은 사실을 다시 제목처럼 여는 줄을
   만들지 말라고 구체적으로 요구한다.

**검증 경계는 §8과 동일하게 유지한다**(원칙 IV): 마크다운 유무를 정규식으로
검사하는 코드를 만들지 않는다 — 지시문 텍스트 자체(마크다운 금지·"빈 줄" 표현
제거·본문 시작 지시 포함 여부)만 계약 테스트로 확인하고, 실제 출력의 준수 여부는
사람이 실기기에서 읽는다(quickstart.md D3a 확장).
