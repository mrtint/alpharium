# Quickstart: 사진을 보기 전에 줄인다

이 문서는 013이 끝났음을 확인하는 절차다. 기기 없는 검증(D0)과 실기기 검증(D1~D6)으로
나뉜다 — "최소 1회"면 되는 케이스다(AGENTS.md 「실기기 검증 범위」): 새 의존
(`expo-image-manipulator`)이 들어오지만 JNI 심볼이 아닌 표준 Expo autolinking
모듈이므로 **debug 1회로 충분**하고, release 재확인은 필요 없다.

## D0 — 기기 없는 검증

```
npm run test:logic
npm run lint
```

**통과 기준**:
- `__tests__/vision/resize.test.ts`가 C1~C4(contracts/resize.md)를 각각 검증한다
- 위반 주입 재현: `ResizeResult`에 필드를 하나 더 추가해 보면 `resize.test.ts`가
  선언을 직접 읽어(007·009의 교훈) 실패해야 한다
- 헌법 검사 통과 — `src/vision/`이 `diary/store`·`inference/sampling`에 안 닿는
  기존 규칙이 그대로 유지됨을 확인(011이 세운 규칙, 013이 어기지 않는다)

## D1 — 새 의존을 설치하고 매니페스트를 갱신한다

```
npx expo install expo-image-manipulator
npx expo prebuild --platform android --clean
cp ~/.alpharium-signing/alpharium.jks android/app/
```

**⚠️ `prebuild --clean`을 건너뛰지 않는다** — 004의 교훈(매니페스트 미갱신)이
새 네이티브 의존에도 적용된다. `adb shell dumpsys package <패키지>`로 새 권한이
필요 없음을 확인한다(리사이즈는 새 권한을 요구하지 않는다 — 파일 시스템 접근은
이미 있는 권한 범위 안).

## D2 — 캡션 시간이 실제로 줄었는지 잰다(SC-001, FR-021)

**절차**(013 실측 세션과 동일한 방법론, AGENTS.md 「VLM 캡션 60초의 원인」 참고):

1. 실사 사진이 있는 하루를 고른다(합성 하루 아님 — 010 FR-021, 013 spec Assumptions)
2. `adb logcat -c`로 로그를 비우고 캡션을 시작한다
3. `tokenizeWithMedia:246`(파일 크기)·`tokenizeWithMedia:351`(num_chunks)·
   `processMedia:642`(청크별 타임스탬프)를 011 때와 같은 방식으로 읽는다
4. **새로 추가할 것**: 리사이즈 자체에 걸린 시간 — `resizePhoto()` 호출 전후
   타임스탬프를 임시 `console.log`로 남기거나(커밋 전 제거), Metro 로그에서
   JS 쪽 타이밍을 읽는다

**통과 기준**:
- IMAGE 청크가 013 이전 관측(장당 7~9개)에서 **1개로 줄어든다**
- 캡션 5장 총 시간이 **129초의 절반 이하**(SC-001)
- 리사이즈 자체에 걸린 시간을 **AGENTS.md에 실측으로 기록한다**(FR-021 — "지금은
  재지 않았다"를 "실측: N밀리초/장"으로 갱신)

## D3 — 캡션 품질이 유지되는지 확인한다(SC-002)

D2와 같은 실행에서 나온 일기를 읽고, **원본 사진을 눈으로 확인**한다(013 실측
세션이 이미 한 방법 — "코드 조각"·"꽃 화병"을 원본과 대조했다). 새로 지어낸
내용이 없는지 확인한다 — 있다면 그것은 프롬프트의 문제이지 013의 범위가 아니지만
(spec Out of Scope), **리사이즈가 새로운 지어내기를 유발하는지는 013이 확인해야
한다.**

## D4 — 줄이지 못하는 사진이 섞인 하루(US2, SC-005)

010의 `seed:day`로 손상되었거나 극단적으로 작은(1×1 등) 이미지를 하루에 섞어
심는다. 그 하루로 캡션을 돌려:

- 나머지 사진의 캡션이 살아 있는지(로그의 `tokenizeWithMedia:181` 호출 수가
  `considered - 1`인지)
- 못 읽은 사진의 내용을 일기가 지어내지 않는지

## D5 — 원본 보호와 정리(US3, SC-003·SC-004)

같은 하루로 일기를 세 번 생성한 뒤:

```
adb shell run-as <패키지> ls -la files/vision-cache/    # debug만 가능(run-as)
```

- **통과**: `vision-cache/` 안의 파일 수가 그 하루 사진 수(최대 5) 이하로 유지된다
  — 세 번 생성해도 누적되지 않는다(R3의 파일명 결정론이 효과가 있는지 확인)
- 사진 보관함(갤러리 앱)에서 리사이즈 사본이 보이지 않는다(SC-007)
- 원본 사진의 수·크기·촬영 시각이 생성 전후로 같다(SC-004) — `content query`로
  대조(010의 절차 재사용)

## D6 — EXIF 방향(Edge Case)

방향 정보가 있는 실사 사진(세로로 찍은 사진 등)으로 D2~D3을 반복하며, 리사이즈된
캡션이 방향을 뒤집어 읽지 않는지 확인한다. **research.md R4가 이 확인을 계획
단계에서 미확정으로 남겼다** — quickstart가 그 확정을 완료하는 자리다.
