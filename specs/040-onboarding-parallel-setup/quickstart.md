# Quickstart: 초기 권한 획득과 첫 실행 흐름 검증

## 전제

- 새로 설치했거나 `preferences/onboarding.json`·`preferences/
  character-names.json`·`files/models/`를 지운 상태(= 최초 실행 재현).
- 실기기, dev(debug) 빌드, Metro가 `EXPO_PUBLIC_APP_ENV=dev`로 떠 있음
  (AGENTS.md "도구 사용법" 절 참고).

## 기기 없는 검증

```
npm run test:logic   # src/firstrun/ 순수 판정 (resolveFirstRunStage, shouldAutoGenerate, shouldShowLogo)
npm run test:ui      # LogoScreen, OnboardingScreen 자동 전환, WelcomeScreen 게이트 변경
npm run lint          # eslint + tsc + 헌법 검사(checkFirstRunFile 포함) + prettier
```

**기대**: 전부 통과, 헌법 검사 위반 0. 위반 주입 시나리오(G1~G8, contracts/
first-run-gate.md)를 각각 한 번씩 실제로 어겨보고 계약 테스트/헌법 검사가
잡는지 확인한다(이 저장소의 표준 관례).

## 실기기 검증 (dev debug, 1회)

1. `pm clear`(또는 재설치)로 앱 데이터 초기화.
2. 앱 실행 → **로고 화면**이 즉시 뜨는지 확인(FR-001).
3. 로고 이후 권한 스텝(사진 → 위치 → 알림 → 배터리 예외 순서, 021과 동일)이
   자동으로 하나씩 이어지는지, 각 스텝에서 "다음" 버튼을 누르지 않아도
   되는지 확인 — 시스템 팝업에서 허용/거부만 결정.
4. 배터리 예외 스텝만 [설정 열기]/[건너뛰기]를 사용자가 직접 눌러야 다음으로
   넘어가는지 확인(FR-002).
5. 마지막 권한 결정 직후 — **작명 화면**이 즉시(수 초 이내) 뜨는지, 진행률
   대기 화면이 먼저 뜨지 않는지 확인(FR-005, SC-002).
6. 이름을 입력해 확정 → 아직 다운로드가 안 끝났다면 대기 화면으로 전환되고
   지은 이름이 유지되는지 확인(FR-006).
7. (다른 라운드) 다운로드가 먼저 끝나도 작명 화면이 재촉/스킵되지 않는지
   확인(FR-007) — 이름을 천천히 입력해 본다.
8. 작명+다운로드 완료 후 liveness 확인이 돌고, 통과 시 자동으로 그날 첫
   일기 생성이 시작/완료되어 홈 화면에 보이는지 확인(FR-008, SC-003) —
   사용자가 "일기 쓰기"를 누르지 않았음에도.
9. liveness 실패를 유도할 수 있으면(예: 모델 파일 일부만 있는 상태) 035의
   기존 실패 안내가 뜨고 자동 생성이 시도되지 않는지 확인(FR-008a).
10. 정오 이전 시각으로 이 흐름을 밟으면(가능한 경우) 자동 생성이 시도되지
    않고 기존 정오 게이트 안내가 보이는지 확인(US3 시나리오 3).
11. 앱을 도중에(예: 작명 화면에서) 종료했다가 재실행 — 이미 결정된 권한을
    다시 묻지 않고 작명/대기 단계부터 이어가는지 확인(FR-011).
12. 이미 온보딩을 마친 기존 계정으로 앱을 업데이트해도 이 흐름이 재노출되지
    않는지 확인(FR-010, SC-005).

## Maestro

`.maestro/first-run-flow.yml`을 작성해 `scripts/run-device-tests.mjs`의
`FLOWS`에 등록한다 — 로고 → 권한 스텝(허용/건너뛰기 섞어서) → 작명 입력 →
대기 → 홈 화면에 일기 존재 확인까지 1개 흐름으로 묶는다.

## 완료 기준

- 기기 없는 테스트 전부 통과 + lint 클린.
- 위 12개 실기기 관찰 항목 중 시각 조작이 필요한 10번(정오 이전)을 제외한
  나머지가 실기기에서 최소 1회 확인됨(원칙 V — "건너뛴 실기기 테스트는
  통과가 아니다").
- Maestro 흐름 1개 등록 및 PASS.

## 실기기 검증 결과 (2026-09-11, SM-S901N/Galaxy S22, Android 16, dev debug)

### 확인된 것

- **FR-001 (로고 → 권한 자동 순차)**: "알파리움" 전체화면 로고가 뜨고,
  사용자 조작 없이 자동으로 사라져 권한 스텝으로 전환된다. ⚠️ 로고가
  `LOGO_DISPLAY_MS = 1500`이라 **1초 간격 스크린샷으로는 놓친다** —
  확인하려면 상수를 일시적으로 6000으로 올려 관찰한다(이번에 그렇게 확인,
  즉시 원복).
- **FR-002 (배터리 예외)**: 배터리 예외 스텝만 시스템 팝업이 아니라 전용
  안내(4/4) + [허용]/[건너뛰기]이고, 자동 타이머로 넘어가지 않고 사용자
  조작을 기다린다. 설계대로다.
- **FR-003 (이미 부여된 권한)**: 사진·위치·알림이 이미 부여된 기기에서는
  그 스텝들이 자동으로 지나가고 배터리 예외만 남는다.
- **FR-004 (다운로드 병렬 시작)**: 권한 결정 직후 다운로드가 화면과
  **독립적으로** 시작된다 — 작명 화면에 머무는 동안 v1(379MB)·v2(102MB)
  완료, a1이 0 → 1.33GB까지 진행되는 것을 `run-as ls -l`로 연속 관측했다.
  **이 기능의 핵심이 실기기에서 동작한다.**
- **FR-005 (작명 화면 우선)**: 모델이 하나도 없는 상태(방금 `pm clear`)
  에서도 진행률 대기 화면이 아니라 **작명 화면이 먼저** 떴다.
- **FR-007 (재촉 없음)**: 다운로드가 88%까지 진행되는 동안 작명 화면이
  전환·재촉되지 않고 입력한 이름이 유지됐다.

### ★ 발견된 결함 — a1(1.5GB) 다운로드 중 OOM 크래시

`java.lang.OutOfMemoryError: ... target footprint 268435456, growth limit
268435456` — **OkHttp TaskRunner 스레드**에서 발생(2026-09-11 22:23:10,
a1.bin 1.391GB/1.522GB 지점). 앱이 통째로 죽고 홈 화면으로 빠진다.

- **040의 결함이 아니다** — `src/models/`와 `src/app/essential-assets-port.ts`
  는 040에서 한 줄도 바뀌지 않았다(`git diff --stat 84d7abb..HEAD` 0건).
  다운로드 경로의 마지막 변경은 **026**(세그먼트 병렬 다운로드)이다.
- **의심 지점**: `expo-port.ts:229-234` — `res.body`가 없으면
  `arrayBuffer()`로 **구간 전체를 메모리에 올리는 폴백**이 있다. a1(1.5GB)은
  `SEGMENT_COUNT = 4`로 나뉘어 **구간 하나가 약 380MB**라, 이 폴백을 타면
  힙 한계(268MB)를 넘는다. v1(379MB, 단일 구간)이 성공한 것으로 보아
  스트리밍 경로 자체는 동작하므로, **어느 조건에서 `res.body`가 null이
  되는지**가 다음 조사 대상이다.
- **040이 이 결함을 더 잘 드러냈을 수는 있다** — 다운로드가 작명 화면(UI가
  살아 있는 상태)과 동시에 돌므로 JS 힙 여유가 더 적다. 다만 원인은
  026 경로에 있다.
- **재시작해도 이어받지 못했다** — 크래시 후 앱을 다시 열어도 a1이
  1.391GB에서 멈춘 채 재개되지 않았다(15초 관찰). 026의 세그먼트
  이어받기가 크래시 후에 동작하는지는 별도 확인이 필요하다.
- **별도 스펙으로 다룬다** — 040의 범위(화면 전환·조율)를 벗어나고,
  `src/models/`를 고치는 것은 026의 계약을 건드리는 일이다.

### 2차 라운드 — 모델을 백업본에서 복구한 뒤 (같은 날, 같은 기기)

OOM으로 막힌 a1을 `~/.alpharium-signing/model-backup/`에서 `run-as`로 밀어
넣고(md5 `d8506380...`가 이전 세션 기록과 일치, `state.json`의 verdict도
손으로 복원) 나머지 흐름을 끝까지 밟았다.

- **FR-008 (liveness → 자동 첫 일기)**: 작명 확정 → "잠깐만요 / 새로 온
  친구가 깨어나는 중이에요"(035 liveness) → **사용자가 "일기 쓰기"를 누르지
  않았는데** `2026-09-11.json`이 저장됐다. `visionMs` 25.8초 +
  `writingMs` 35.0초.
- **일기 품질도 정상이다**: 사진 1장을 실제로 읽어(VLM이 돌아) 사무실·모니터
  장면이 본문에 반영됐고, "있었을 것이다 / 가능성이 있다 / 않았을 것 같다"
  처럼 짐작 말투가 지켜졌다(원칙 II). 화자도 휴대폰으로 유지됐다.
- **FR-010·FR-011·SC-005**: 아래 결함을 고친 뒤 확인 — 재시작해도 권한
  온보딩이 재노출되지 않고 작명 화면부터 이어가며, 지은 이름도 보존된다.
- **SC-003**: 아래 결함을 고친 뒤 확인 — 재시작 없이 홈 화면에
  "2026-09-11 / 사진 1장"과 "일기가 있다"가 자동으로 나타난다.

### ★ 발견해서 고친 결함 둘 (둘 다 이 세션에서 수정·재확인)

**(1) 권한 결정 후 `completed`를 저장하지 않아 온보딩이 매번 재노출됐다.**
021은 마지막 [시작하기] 버튼이 `onComplete`로 플래그를 세웠는데, 040은 권한
결정 직후 작명 화면으로 전환해 **그 버튼에 도달하지 않는다**. 배터리 예외를
건너뛰고 작명·자동 생성까지 정상 완주했는데도 재시작하면 배터리 스텝 4/4로
되돌아갔고 `onboarding.json`이 `{"completed":false,...}`였다.
`onAllPermissionStepsDecided`가 `completed: true`를 함께 저장하도록 고쳤다.

**(2) 자동 생성이 끝나도 홈 화면이 목록을 다시 읽지 않았다.** 파일에는
일기가 있는데 화면은 "아직 일기가 없다"로 남아 앱을 껐다 켜야 보였다
(SC-003 위반). `DiaryHomeScreen`은 마운트·`AppState` 변화·자기가 돌린
생성에서만 `refresh()`를 부르는데 040의 자동 트리거는 그 셋 중 어디에도
해당하지 않는다. 트리거가 끝나면(`finally` — 실패해도 최신 목록을 봐야
한다) `autoGeneratedToken`을 올려 `DiarySection`을 다시 마운트시킨다.

**둘 다 기기 없는 테스트가 구조적으로 못 잡는 종류였다** — (1)은 파일
통로, (2)는 컴포넌트 생명주기. 소스 검사 계약 테스트 6개를 함께 넣었다
(`AppFrame.firstrun.test.tsx`).

### 미확인으로 남은 것

- **FR-006 (대기 화면)**: 2차 라운드에서는 모델이 이미 완비돼 있어
  `"waiting-for-download"` 단계를 지나가지 않았다. 1차 라운드에서는 그
  시점에 OOM이 났다 — **여전히 미확인**이며, 대기 화면 자체는 계약
  테스트(`WaitingForDownloadScreen.test.tsx`)가 방어한다.
- **FR-009 (거부 판정 후 수동 재시도)**: 자동 생성이 두 번 다 성공해
  거부 판정 갈래를 관측하지 못했다. 계약 테스트(T027a)로 갈음.
- **Maestro `first-run-flow.yml`**: `clearState: true` 직후 Maestro의 기기
  서버가 죽어(`DeviceServerDiedException`) 흐름이 완주하지 못했다. YAML
  문법 오류(`assertNotVisible`의 `timeout`)는 이번에 고쳤다. 흐름이 보려던
  F1~F5는 **전부 손으로 확인했다**(로고·자동 전환·배터리 예외·작명 우선·
  모델 정보 비노출) — 자동화만 남았다.
- **a1 OOM**: 위 1차 라운드 절 참조. 이번에는 백업본을 밀어 넣어 우회했다.
