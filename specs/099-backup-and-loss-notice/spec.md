# Feature Specification: 일기·모델 백업과 유실 안내 — 모델은 백업에서 빼고, 일기는 사라질 수 있음을 사실대로 알린다

**Feature Branch**: `099-backup-and-loss-notice`
**Created**: 2026-10-22
**Status**: Draft
**Input**: 설계 문서 `docs/superpowers/specs/2026-10-22-backup-and-loss-notice-design.md`. 모델(약 2GB)을 iOS·안드로이드 백업에서 빼고, 일기·설정은 OS 기본 백업 동작을 그대로 둔다(D4 = 안내 문구만, 소유자 결정 A 2026-10-22). 실기기로 실측하고, 방침·지원 문구를 실측대로 고치며, 앱 안에 유실 안내 한 줄을 넣는다(C9, 문구는 소유자 확정).

## Clarifications

### Session 2026-10-22

- Q: 앱 안 유실 안내 한 줄을 어디에 보여 주나? → A: 설정 「이 휴대폰」 묶음의 「일기 모두 지우기」 근처 보조 줄 하나. 새 줄 추가만 하고 기존 행·문구, 첫 실행 화면 문구는 바꾸지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 모델 2GB가 휴대폰 백업에 실리지 않는다 (Priority: P1)

사용자가 iCloud 백업이나 Google 백업(기기 이전 포함)을 켜 두었다. 포켓로그의 모델(약 2GB)은 다시 받을 수 있는 파일이므로 백업 용량·시간을 쓰지 않고, 백업에서 복원한 새 기기에서는 모델만 없는 채로 일기가 돌아오고, 앱의 기존 모델 판정이 모델을 다시 받는 안내를 띄운다(이 과제는 그 판정을 바꾸지 않는다).

**Why this priority**: 이 과제의 핵심이다. iOS는 지금 2GB가 iCloud 용량(기본 5GB)을 잡아먹고, 안드로이드는 한도(앱당 25MB)를 넘겨 백업 동작이 불분명하다.

**Independent Test**: iPhone에서 모델 디렉터리의 백업 제외 속성을 읽어 켜져 있음을 확인하고, 안드로이드에서 백업을 실행해 모델이 백업 산출물에 없음을 확인한다. 규칙을 잘못 쓴 상태(위반 주입)에서는 같은 확인이 실패한다.

**Acceptance Scenarios**:

1. **Given** 모델을 이미 받은 기존 iOS 설치(TestFlight), **When** 이 기능이 담긴 빌드로 업데이트해 앱을 열면, **Then** 모델 파일 경로는 그대로이고(다시 받지 않는다) 모델 디렉터리가 백업 제외로 표시된다.
2. **Given** 모델을 새로 받는 iOS 첫 실행, **When** 받기가 끝나면, **Then** 모델 디렉터리가 백업 제외로 표시되어 있다.
3. **Given** 안드로이드에서 백업을 실행하면, **When** 백업 산출물을 확인하면, **Then** 모델 파일은 들어 있지 않다.
4. **Given** 모델 디렉터리가 지워졌다 다시 만들어진 경우(모델을 지운 뒤 다시 받는 경우), **When** 다시 받으면, **Then** 백업 제외가 다시 걸린다.

### User Story 2 - 일기와 설정은 백업에서 빠지지 않는다 (Priority: P1)

기기를 바꾸는 사용자의 일기·설정이 이번 변경 때문에 조용히 백업에서 빠지지 않는다. 일기(본문과 일기에 저장된 사진 사본)와 설정은 지금처럼 OS 기본 백업 동작을 따른다.

**Why this priority**: 규칙을 잘못 쓰면 일기까지 빠져 기기를 바꾼 사용자의 일기가 조용히 사라진다(로드맵 위험). 모델 제외와 같은 무게의 완료 조건이다.

**Independent Test**: 같은 실측에서 일기·설정·일기의 사진 사본이 백업에 남아 있는 것(또는 OS 한도 때문에 실리지 않는 경우 그 사실)을 모델 제외와 같은 방식으로 확인한다.

**Acceptance Scenarios**:

1. **Given** 일기가 있는 안드로이드 기기, **When** 백업을 실행해 산출물을 보면, **Then** 일기 쪽 데이터와 설정이 남아 있다(규칙 적용 전과 같다).
2. **Given** 일기가 있는 iPhone, **When** 일기·설정·사진 사본 디렉터리의 백업 제외 속성을 읽으면, **Then** 모두 꺼져 있다.
3. **Given** 안드로이드 백업 한도(25MB)를 일기 데이터가 넘는 경우, **When** 백업을 실행하면, **Then** 그때의 실제 동작을 기록하고 방침은 그 사실대로만 말한다.

---

### User Story 3 - 앱을 지우거나 기기를 바꾸면 일기가 사라질 수 있음을 앱 안에서 알려 준다 (Priority: P2)

사용자가 앱 안에서 한 줄 안내를 읽는다: 앱을 지우거나 기기를 바꾸면 일기가 사라질 수 있다. 소유자가 확정한 문구를 쓰고, 기존 화면의 문구·행은 바꾸지 않는다.

**Why this priority**: 사용자가 일기를 잃기 전에 알 수 있는 유일한 자리다. 다만 모델 제외와 실측이 먼저다(문구가 실측 사실에 기대므로).

**Independent Test**: 안내가 정해진 자리에 보이고, 화면 문구 카탈로그에 새 키 하나로만 존재하며, 기존 문구 골든을 다시 쓰지 않았음을 테스트로 확인한다. 글꼴 크기 2.0배에서도 잘리지 않는다.

**Acceptance Scenarios**:

1. **Given** 설정 화면을 연 사용자, **When** 「이 휴대폰」 묶음의 「일기 모두 지우기」 근처를 보면, **Then** 확정된 한 줄이 보조 줄로 보인다.
2. **Given** 안내를 추가한 빌드, **When** 기존 화면 문구를 비교하면, **Then** 기존 문구는 하나도 바뀌지 않았다.

---

### User Story 4 - 방침과 지원 페이지가 앱이 하는 일과 같은 말을 한다 (Priority: P2)

방침 「보존과 삭제」와 지원 「앱을 지우면」 답이 지금의 「백업에 포함될 수 있다」 대신 실측으로 확인한 사실을 같은 말로 전한다. 모델은 백업에 실리지 않는다는 것, 일기는 OS의 백업을 따른다는 것(실측한 범위만)을 말한다.

**Why this priority**: 사실과 다른 방침은 심사·신뢰 문제이지만, 실측 결과가 나온 뒤에야 쓸 수 있다.

**Independent Test**: 두 페이지의 해당 문장이 같은 사실을 말하고 각각 실측 근거를 가리킨다. 방침 잠금 테스트가 통과한다.

**Acceptance Scenarios**:

1. **Given** 실측 결과, **When** 방침과 지원 페이지를 읽으면, **Then** 두 페이지가 모델·일기·설정의 백업 여부를 같은 말로 말한다.
2. **Given** 실측하지 않은 항목(예: 제조사 기기 이전 도구), **When** 문장을 쓰면, **Then** 단정하지 않고 「확인하지 않았다」로 남긴다.

### Edge Cases

- 모델을 받는 도중(부분 파일, 구간 파일)에 앱이 백업 대상이 되면 제외가 이미 걸려 있어야 한다 — 디렉터리 단위로 제외한다.
- 모델 디렉터리가 아직 없을 때(첫 실행 직후 모델 받기 전) 앱 시작이 오류 없이 지나간다.
- 안드로이드 12 미만과 이상의 두 규칙 형식 모두에서 모델이 빠진다.
- 백업 제외 설정이 실패해도 앱 사용과 모델 받기는 막히지 않는다. 실패는 화면에 드러내지 않고, 실기기 확인(제외 속성 읽기)으로 관측한다.
- 일기 사진 사본은 일기의 일부이므로 어떤 규칙에도 제외로 잡히지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 모델 디렉터리(`models`)는 두 플랫폼 모두에서 OS 백업(클라우드 백업·기기 간 이전)에서 제외되어야 한다.
- **FR-002**: iOS의 모델 경로는 바뀌지 않아야 한다. 이미 받은 사용자가 모델을 다시 받지 않는다.
- **FR-003**: iOS의 백업 제외는 모델 디렉터리가 만들어질 때와 앱을 열 때 모두 확인·재적용되어야 한다(기존 설치 보정, 디렉터리 재생성 대응).
- **FR-004**: 안드로이드 백업 규칙은 모델 디렉터리만 제외하고 일기·설정·일기 사진 사본은 제외하지 않아야 한다.
- **FR-005**: 일기·설정의 백업 동작은 OS 기본을 유지한다. 백업·복원을 약속하는 기능은 만들지 않는다(D4).
- **FR-006**: 백업에 모델이 실리지 않음과 일기·설정이 빠지지 않음을 모두 실기기로 확인해야 한다(원칙 V). 확인하지 못한 부분은 확인하지 못했다고 기록한다.
- **FR-007**: 방침 「보존과 삭제」와 지원 「앱을 지우면」 답은 실측 결과를 같은 말로 전해야 하며, 미실측 사실은 단정하지 않는다.
- **FR-008**: 앱 안에 앱 삭제·기기 변경 시 일기가 사라질 수 있다는 안내 한 줄이 설정 「이 휴대폰」 묶음의 「일기 모두 지우기」 근처 보조 줄로 있어야 한다. 문구는 소유자가 확정하며, 새 키 하나로만 추가한다. 첫 실행 화면에는 넣지 않는다.
- **FR-009**: 기존 화면 문구·설정의 기존 행·홈 화면 문구와 지원 페이지의 다른 항목은 바꾸지 않는다.
- **FR-010**: 백업 규칙을 어기는 변경(제외 대상에 일기·설정·사진 사본을 넣거나 모델 제외를 빼는 것)을 자동 테스트가 잡아야 한다.
- **FR-011**: 이 기능은 앱 안에 모델 출력 점수화·측정 코드를 두지 않으며, 실측은 개발 절차(실기기·터미널)로만 한다(원칙 IV).

### Key Entities

- **백업 제외 대상**: 모델 디렉터리 하나. 다시 받을 수 있는 큰 파일.
- **백업에 남는 것**: 일기 본문, 일기에 저장된 사진 사본, 설정·상태 파일. OS 기본 동작을 따른다.
- **유실 안내**: 앱 삭제·기기 변경 시 일기가 사라질 수 있다는 한 줄.
- **실측 기록**: 플랫폼별 백업 산출물에 무엇이 들어 있는지의 관측 결과. 방침 문구의 근거.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 실기기 두 대(안드로이드 1, iPhone 1)에서 모델 약 2GB가 백업 산출물·백업 대상 표시에 없음을 확인했다(2/2).
- **SC-002**: 같은 실측에서 일기·설정이 백업에 남는지(또는 OS 한도로 실리지 않는지)를 관측해 기록했다(2/2 플랫폼).
- **SC-003**: 이미 모델을 받은 iPhone이 업데이트 뒤 모델을 다시 받지 않고 일기를 쓴다(재다운로드 0바이트).
- **SC-004**: 방침과 지원 페이지의 백업 관련 문장이 같은 사실을 말하고, 근거 없는 단정 문장이 0개다.
- **SC-005**: 백업 규칙 위반 주입 3종(사진 사본 제외 추가, 설정 제외 추가, 모델 제외 삭제)을 자동 테스트가 모두 잡는다.
- **SC-006**: 앱 안 유실 안내가 글꼴 2.0배에서도 잘리지 않고 보이며, 기존 문구 변경은 0건이다.

## Assumptions

- 일기·설정은 OS 기본 백업 동작을 유지한다(소유자 결정 A, 2026-10-22). 일기 내보내기·클라우드 동기화·복원 보장은 범위 밖이다.
- 모델 경로를 옮기지 않는다. 기존 TestFlight 사용자의 2GB 재다운로드는 허용하지 않는다.
- 일기에 저장된 사진 사본(`vision-cache`)은 일기의 일부이므로 제외하지 않는다.
- 안드로이드 실측 기기는 SM-S901N, iOS는 iPhone 14(배포 환경 빌드)다. 제조사 기기 이전 도구(Smart Switch 등)와 iOS 직접 기기 이전은 실측 범위 밖이며 미확인으로 남긴다.
- 안내 한 줄의 자리는 설정 「이 휴대폰」 보조 줄로 확정했다(Clarifications). 문구는 소유자 확정 뒤 plan에서 정한다. 이 스펙은 문구를 정하지 않는다.
- 앱 시작 때 백업 제외 확인은 사용자에게 보이지 않는다.
- 같은 시기에 진행되는 「화면 문구를 사실대로」 과제(098)와 문구 카탈로그·골든 배열을 공유한다. 이 과제는 새 키 하나만 덧붙인다.
