# 계약: 파이프라인

**대상**: `src/diary/pipeline.ts`
**관련 요구사항**: FR-018~FR-020, FR-012, FR-019

---

## 진입점

```ts
type PipelineResult =
  | { ok: true; entry: DiaryEntry }
  | { ok: false; stage: PipelineStage; reason: string }

type PipelineStage =
  | 'day-not-closed'    // 아직 04:00 경계를 지나지 않음 (FR-018c)
  | 'already-running'   // 같은 하루가 이미 생성 중 (FR-018d)
  | 'signals'           // 신호를 가져오지 못함
  | 'request-build'     // 캐릭터가 없어 요청 실패 (FR-007)
  | 'generation'        // 추론 실패 또는 not-implemented
  | 'storage'           // 저장 실패 (FR-024)

function runPipeline(input: {
  day: DayDate
  now: Date
  character: Character | undefined
  vision: VisionSetting
}): Promise<PipelineResult>
```

**`now`를 인자로 받는다**(FR-018a). 파이프라인이 스스로 현재 시각을 읽지 않으므로:

- 테스트가 시간에 의존하지 않는다 — 03:59와 04:00 경계를 자유롭게 만들 수 있다
- 파이프라인이 **누가 언제 불렀는지 모른다**. 앱을 열 때 부르든 나중에 백그라운드가 부르든
  계약이 같다. 자동 생성이 지향점이므로 이 성질이 필요하다

---

## 단계 순서와 중단

```
1. 하루가 닫혔는가?     → 아니면 day-not-closed로 중단
2. 이미 생성 중인가?     → 맞으면 already-running으로 중단
3. 신호를 가져온다       → 실패하면 signals로 중단
4. 요청을 만든다         → 캐릭터 없으면 request-build로 중단
5. 생성한다             → 실패하면 generation으로 중단
6. 저장한다             → 실패하면 storage로 중단
```

**앞 단계가 실패하면 뒤 단계를 시도하지 않는다.** 특히 5가 실패했는데 6이 도는 일이 없어야
한다 — 그래야 기존 일기가 보존된다(FR-023b).

### 검증 표

| 상황 | 기대 | 근거 |
| --- | --- | --- |
| 하루가 아직 안 닫힘 | `stage: 'day-not-closed'` | FR-018c, SC-010 |
| 같은 하루 생성 중 | `stage: 'already-running'` | FR-018d |
| 캐릭터 없음 | `stage: 'request-build'` | FR-007 |
| 생성이 `not-implemented` | `stage: 'generation'` | FR-015 |
| 저장 실패 | `stage: 'storage'` | FR-024 |
| 전부 성공 | `ok: true, entry` | — |

**이 기능에서는 항상 `generation`에서 멈춘다.** 추론이 `not-implemented`를 반환하기
때문이며, 그것이 정상이다. 파이프라인이 거기까지 도달하는 것 자체가 검증 대상이다.

---

## 불변식

1. **실패 시 `DiaryEntry`를 만들지 않는다**(FR-012). 빈 본문이나 플레이스홀더 텍스트로
   일기를 만들지 않는다.
2. **어느 단계에서 멈췄는지 100% 드러난다**(FR-019, SC-006). `stage` 없이 실패하는 경로가
   없어야 한다.
3. **각 단계는 독립적으로 테스트 가능해야 한다**(FR-020). 파이프라인 전체를 돌리지 않고도
   한 단계를 검증할 수 있어야 하며, 이를 위해 신호 공급·생성·저장을 주입받는다.
4. **중복 실행을 막는다**(FR-018d). 온디바이스 추론은 오래 걸리므로 사용자가 여러 번 눌러도
   한 번만 돈다. 진행 중인 하루의 집합을 파이프라인이 들고 있는다.
5. **파이프라인은 실행 시점을 판단하지 않는다**(FR-018a). "지금이 만들 때인가"는 부르는
   쪽의 몫이다. 파이프라인은 주어진 하루가 닫혔는지만 본다.

---

## 주입받는 것

각 단계를 독립적으로 테스트하려면(FR-020) 파이프라인이 아래를 주입받아야 한다.

| 주입 | 왜 |
| --- | --- |
| 신호 공급 | 이 기능에서는 가짜 신호. 다음 기능에서 실제 수집으로 갈아끼운다 |
| 추론 어댑터 | 001의 `select.ts`가 고른 것. 테스트에서는 대역을 넣는다 |
| 저장 | 파일 구현. 테스트에서는 메모리 대역을 넣는다 |

**추론 어댑터를 파이프라인이 직접 고르지 않는다**(FR-017). 001의 선택 지점을 거친 결과를
받는다 — 파이프라인이 스스로 고르면 헌법 원칙 I의 방어선이 둘로 갈라진다.

## 진행 중 상태

**중복 실행 방지**(FR-018d)를 위해 어느 하루가 생성 중인지 알아야 한다.

**규칙**:

- 성공·실패와 무관하게 끝나면 진행 중에서 빠져야 한다. 빠지지 않으면 실패한 하루를 영영
  다시 시도할 수 없다.
- 앱이 종료되면 진행 중 상태는 사라진다. 다음에 열었을 때 다시 시도할 수 있어야 한다
  (명세 Edge Case: 백그라운드가 불가능하므로 생성 중 종료가 드물지 않다).
- 진행 중 상태를 저장소에 남기지 않는다 — 남기면 앱이 죽었을 때 "영원히 생성 중"인 하루가
  생긴다.
