# Phase 1: 데이터 모델

**기능**: 일기 파이프라인의 축 사이 계약 | **날짜**: 2026-08-12

이 기능의 산출물은 대부분 **값의 모양**이다. 아래 규칙이 곧 테스트 대상이다.

---

## SignalValue&lt;T&gt; (신호 하나의 상태)

이 기능에서 가장 중요한 타입이다. **"없음"과 "알 수 없음"을 가른다**(FR-002).

| 상태 | 뜻 | 예 |
| --- | --- | --- |
| `known` | 관측했고 값이 있다 | 사진 3장을 찾았다 |
| `none` | 관측했고 값이 없다 | 사진을 찾아봤는데 0장이었다 |
| `unknown` | **관측하지 못했다** | 사진 권한이 없어 보지 못했다 |

**불변식**:

1. `unknown`은 값을 갖지 않는다. "모르는데 값이 있다"는 상태가 타입으로 불가능해야 한다.
2. `unknown`을 기본값으로 대체해서는 안 된다(FR-003). 걸음 수를 모를 때 0으로 두면
   "걷지 않았다"는 거짓이 된다.
3. `none`과 `unknown`을 뭉개는 코드가 없어야 한다. 이것이 헌법 원칙 V가 이 기능에 걸리는
   지점이다.

**왜 옵셔널로 두지 않는가**: `T | undefined`는 두 상태를 구분하지 못한다. 읽는 쪽이 매번
관례에 기대야 하고, 관례는 지켜지지 않는다(research.md §1).

**실제로 발생하는 근거**: 안드로이드에 기간 걸음 수 조회 통로가 없다(AGENTS.md 실측).
걸음 수의 `unknown`은 예외가 아니라 정상 상태다.

## DaySignals (하루치 신호)

휴대폰이 하루 동안 본 것의 묶음.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `date` | 하루 식별자 | 어느 날의 신호인가. 04:00 경계로 정해진다(FR-021) |
| `photos` | `SignalValue<사진 목록>` | 찍힌 사진들 |
| `places` | `SignalValue<위치 궤적>` | GPS로 본 이동 |
| `steps` | `SignalValue<걸음 수>` | 안드로이드에서는 대개 `unknown` |
| `battery` | `SignalValue<배터리 기록>` | 충전·방전 흐름 |
| `connectivity` | `SignalValue<연결 상태>` | 와이파이·데이터 |

**규칙**:

- 모든 신호가 `unknown`이거나 `none`인 하루도 **정상이다**(FR-005b). 빈 묶음은 오류가 아니다.
- 신호의 양으로 생성 가능 여부를 가르지 않는다(FR-005a). 집에만 있던 하루도 일기가 된다.
- 이 기능은 이 값을 **실제로 채우지 않는다**(FR-005). 모양만 정하고, 테스트는 가짜 값을 쓴다.

**가짜 신호에 대한 경고**: `src/signals/fake.ts`는 테스트·개발용이며 **제품 경로가 아니다**.
이것이 헌법 원칙 I의 "미리 만들어 둔 응답"으로 자라지 않도록, 가짜 신호로 만든 일기가
사용자에게 보이는 경로를 만들지 않는다.

---

## DayDate (하루 식별자)

04:00 경계로 잘린 하루(FR-021).

**규칙**:

- 시각 → `DayDate` 변환은 `src/config/day-boundary.ts`에서만 한다(FR-021a).
- 03:59:59는 전날, 04:00:00은 당일이다.
- 자정 직후(00:30)는 **전날**이다. 이것이 자정 기준과 다른 지점이다.
- 기기의 현재 시간대를 따른다. 시간대가 바뀐 하루는 이 기능에서 정하지 않는다(FR-021b).

**하루가 닫혔는가**: 어떤 `DayDate`의 04:00 경계를 현재 시각이 지났는지 판정할 수 있어야
한다(FR-018c). 아직 닫히지 않은 하루는 일기를 만들 수 없다.

---

## Character (캐릭터)

사용자가 고른 글 쓰는 성격. **모델이 아니다**(헌법 원칙 III).

**규칙**:

- 헌법 로스터의 다섯 자리 중 하나를 가리킨다.
- **모델 식별자·파라미터 수·양자화 방식과 잇지 않는다**(FR-008). 캐릭터→모델 매핑은 이
  기능에서 만들지 않는다.
- 표시 이름을 이 기능에서 짓지 않는다. 헌법 「로스터」가 "캐릭터 이름은 사람이 짓는다"고
  했으므로 지어내면 원칙 III 위반 쪽으로 흐른다(research.md §5).

---

## VisionSetting (시각 처리 설정)

사진을 어떻게 다룰지. **캐릭터가 아니라 설정이다**(헌법 「사진과 시각 처리」).

| 값 | 뜻 |
| --- | --- |
| `none` | 사진을 보지 않음 |
| `quick` | 빠르게 봄 |
| `detailed` | 자세히 봄 |

**규칙**:

- 사용자에게 시각 인코더를 고르게 하지 않는다(FR-009). 위 셋으로만 제시한다.
- 캐릭터와 시각 설정의 조합에 따라 결과가 달라진다. 모든 조합이 똑같이 좋다고 가정하지
  않는다(헌법 「사진과 시각 처리」의 주의).

## DiaryRequest (일기 생성 요청)

추론 어댑터가 받는 입력.

| 필드 | 설명 |
| --- | --- |
| `signals` | 하루치 신호 |
| `character` | 어떤 성격으로 쓸지 |
| `vision` | 사진을 어떻게 다룰지 |

**규칙**:

- 캐릭터가 없으면 요청이 만들어지지 않는다(FR-007). 만들어지지 않은 사실이 값으로 드러난다.
- **모델 식별자를 담지 않는다**(FR-008, 원칙 III).
- 신호가 비어도 요청은 만들어진다(FR-005b).

---

## DiaryDraft / GenerationFailure (생성 결과)

추론 어댑터가 돌려주는 것.

**성공**: 본문 텍스트.

**실패**: 아래 중 하나이며, **어느 것도 텍스트를 담지 않는다**.

| 실패 | 뜻 |
| --- | --- |
| `not-implemented` | 아직 구현되지 않음. 이 기능에서 온디바이스·서버 모두 이것을 반환 |
| `backend-unavailable` | 추론 어댑터를 쓸 수 없음 (001의 `ModuleStatus`와 이어짐) |
| `generation-failed` | 생성을 시도했으나 실패. 원인을 담는다 |

**불변식** — 이 기능에서 가장 중요한 규칙:

1. **실패가 텍스트를 반환해서는 안 된다**(FR-016). "일기를 생성할 수 없습니다" 같은
   플레이스홀더도 안 된다 — 그럴듯한 텍스트가 일기 자리에 들어가는 순간 가짜 일기와
   구분이 사라진다.
2. `not-implemented`는 정직한 값이지 가짜 응답이 아니다. 헌법 원칙 I이 금지한 것은 *미리
   만들어 둔 응답을 보여주는 경로*이며, 없는 것을 없다고 말하는 것은 그 반대다.
3. 예외를 던지지 않는다. 실패는 값이어야 파이프라인이 어느 단계에서 멈췄는지 말할 수
   있다(FR-019).

## DiaryEntry (생성된 일기)

저장되고 사용자가 읽는 값.

| 필드 | 설명 |
| --- | --- |
| `date` | 어느 하루의 일기인가 |
| `text` | 본문 |
| `character` | 어떤 캐릭터가 썼는가 |
| `signalsUsed` | 근거가 된 신호 (FR-011) |
| `createdAt` | 언제 만들어졌는가 |

**규칙**:

- **모델 식별자를 담지 않는다**(FR-013, 원칙 III).
- **추론 속도·출력 점수·품질 지표를 담지 않는다**(원칙 IV). 이 값이 원칙 IV를 어기기 쉬운
  자리이므로 계약에 못 박는다.
- 실패는 `DiaryEntry`가 되지 않는다(FR-012). 빈 본문의 일기를 만들지 않는다.
- `signalsUsed`가 있어야 나중에 "이 일기가 무엇을 보고 쓰였나"를 되짚을 수 있다.

---

## PipelineResult (파이프라인 결과)

**성공**: `DiaryEntry`.

**실패**: 어느 단계에서 왜 멈췄는지(FR-019).

| 단계 | 실패 예 |
| --- | --- |
| `day-not-closed` | 아직 04:00 경계를 지나지 않음 (FR-018c) |
| `already-running` | 같은 하루가 이미 생성 중 (FR-018d) |
| `request-build` | 캐릭터가 없어 요청을 만들지 못함 (FR-007) |
| `generation` | 추론 실패 또는 `not-implemented` |
| `storage` | 저장 실패 (FR-024) |

**규칙**:

- 어느 단계에서 멈췄는지가 100% 드러나야 한다(SC-006).
- 각 단계는 독립적으로 테스트 가능해야 한다(FR-020). 파이프라인 전체를 돌리지 않고도 한
  단계를 검증할 수 있어야 한다.
- 파이프라인은 **실행 시점을 모른다**(FR-018a). 날짜와 "지금"을 인자로 받을 뿐, 스스로
  현재 시각을 읽지 않는다. 그래야 테스트가 시간에 의존하지 않고, 나중에 백그라운드 실행이
  붙어도 계약이 같다.

## DiaryStore (저장)

| 동작 | 설명 |
| --- | --- |
| 저장 | 일기 하나를 남긴다 |
| 조회 | 날짜로 일기 하나를 꺼낸다 |
| 존재 확인 | 어느 날짜에 일기가 있는지 안다 (FR-018f) |

**규칙**:

- **한 날짜에 일기는 하나**(FR-023). 같은 날짜로 저장하면 덮어쓴다.
- 덮어쓰기 전에 기존 일기가 있다는 사실이 드러나야 한다(FR-023a). 조용히 덮어쓰지 않는다.
- **새 생성이 실패하면 기존 일기가 남아야 한다**(FR-023b). 저장은 성공한 생성에 대해서만
  일어난다.
- 저장 실패가 드러나야 한다(FR-024). 조용히 사라지지 않는다.
- 저장한 것과 꺼낸 것이 같아야 한다(SC-007).

## 이 기능이 다루지 않는 것

- 프롬프트, 화자 규칙 강제 (원칙 II는 생성 기능의 몫)
- 캐릭터의 표시 이름, 캐릭터→모델 매핑
- 모델 파일, 시각 인코더
- 신호의 실제 수집
- 일기를 보여주는 화면
