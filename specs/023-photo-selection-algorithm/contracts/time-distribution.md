# Contract: 시간 분포로 사진을 배분해 고른다

**Feature**: `023-photo-selection-algorithm` | **파일**: `src/vision/select.ts`

**순수 함수다.** 011 selection.md를 잇는다 — 인덱스 균등을 시간 분포 배분으로
바꾼다. 인자는 사진 목록과 예산(둘 다 `select.ts` 안에서만 전달, 예산은
`VISION_PHOTO_LIMIT` 상수).

---

## 왜 인덱스 균등을 버리는가

011 `selectForVision`은 `round(k·(n-1)/(limit-1))`로 **목록의 몇 번째**를
고른다. 사진이 시간에 고르게 분포하면 이것이 곧 시간 균등이지만, **한
시간대에 몰리면** 고른 것도 그 시간대에 몰린다 — 011 selection.md의 마지막
예시("10장 전부 저녁")가 그것을 인정했고, User Story 2가 그 상태를 문제로
지적한다("아침 카페만 본 채 하루를 쓴다").

**이 계약은 시각을 본다.** 하루를 고정 시간 칸으로 나누고, 사진이 있는 칸을
빠짐없이 대표시키되, 사진이 몰린 칸은 여분을 더 받는다.

---

## D1. 시간 칸 (`BUCKET_COUNT`, 파일 로컬 상수)

하루(04:00~다음날 04:00, 1440분)를 `BUCKET_COUNT`개의 같은 길이 칸으로
나눈다. **plan 제안: 6칸(4시간)** — 04–08, 08–12, 12–16, 16–20, 20–24,
00–04.

- **사람이 정한 값**(FR-008, 원칙 V). 분포를 보고 정하지 않는다.
- 칸 판정은 `Photo.takenAt` 하나로 순수 계산:
  ```
  minutesSince4am = ((hours - 4) * 60 + minutes + 1440) % 1440
  bucket = floor(minutesSince4am / (1440 / BUCKET_COUNT))
  ```
  `day-boundary.ts`를 import하지 않는다 — `takenAt`에서 04:00 기준 경과
  분을 직접 유도(순수 유지).

## D2. 상한 이하면 분포 계산을 하지 않는다

`photos.length <= budget`이면 `[...photos]`를 그대로 돌려준다(FR-013, 011
R1 유지).

## D3. 최소 커버리지 — 사진 있는 칸마다 1장

사진이 있는 칸(`nonEmpty`)마다 먼저 1장씩 확보한다(FR-009). 몰린 칸이 다른
칸의 자리를 빼앗지 않는다.

**예외**: `nonEmpty.length >= budget`이면 최소 커버리지조차 다 못 준다 →
D5로 간다.

## D4. 여분은 최대 잔여법으로 비례 배분

최소 커버리지 후 남은 예산(`remaining = budget - nonEmpty.length`)을 칸별
사진 수에 비례해 나눈다(FR-010).

```
total   = Σ count[b]  (b ∈ nonEmpty)
ideal[b] = remaining * count[b] / total
alloc[b] = 1 + floor(ideal[b])
leftover = remaining - Σ floor(ideal[b])

# 남는 자리를 소수부 큰 칸부터 하나씩 (FR-010a)
sort nonEmpty by:
  1) frac(ideal[b])  desc     # 소수부 큰 칸 먼저
  2) count[b]        desc     # 동점이면 사진 많은 칸
  3) bucket index    asc      # 그래도 동점이면 이른 칸
give +1 to the first `leftover` buckets
```

**예시** (research §, 예산 8): 칸 A(2장)·B(30장)·C(5장)·D(3장), 전부 사진
있음.
- 최소 커버리지: A·B·C·D 각 1장 = 4장. `remaining = 4`, `total = 40`.
- `ideal`: A 0.20, B 3.00, C 0.50, D 0.30. `floor` 합 = 3. `leftover = 1`.
- 소수부 순: C(0.50) > D(0.30) > A(0.20) > B(0.00) → C에 +1.
- `alloc`: A 1, B 4, C 2, D 1. 합 8. ✓

## D5. 칸 수가 예산과 같거나 많으면 시간축 균등으로 칸을 고른다

`nonEmpty.length >= budget`이면(경계 `==` 포함 — spec FR-011) 최소
커버리지를 다 줄 수 없다. 하루 시간축에 걸쳐 균등하게 `budget`개의 칸을
고른다.

```
idx(k) = round(k * (nonEmpty.length - 1) / (budget - 1))   (k = 0 … budget-1)
chosenBuckets = nonEmpty[idx(0)], nonEmpty[idx(1)], …
```

- **가장 이른 사진이 있는 칸과 가장 늦은 칸을 반드시 포함**한다 — `k=0`이
  첫 칸, `k=budget-1`이 마지막 칸(011 R3의 칸판).
- 각 선택된 칸에서 1장씩 — **인덱스 중앙값** `photos[floor((n-1)/2)]`
  (`n` = 그 칸 사진 수). n이 짝수면 두 중앙 원소 중 **앞(이른) 것**.
  "시각 중앙값"이 아니라 인덱스 중앙값이다 — 사진 간격이 불균일해도
  결정적(FR-015).
- `nonEmpty.length == budget`이면 `idx(k) == k`가 되어 모든 칸이 그대로
  선택되고 각 1장 — 결과가 D3·D4 경로(모든 칸 1장)와 같지만, 배분 계산
  없이 이 규칙으로 결정한다(결정성 경로를 하나로 고정, spec FR-011).

## D6. 한 칸에서 여러 장은 011 R2로 고른다

`alloc[b] > 1`인 칸에서는 그 칸 안 사진(시각 순 `n`장)에서
`round(k·(n-1)/(alloc[b]-1))` 인덱스로 고른다(FR-012, 011 R2를 칸 내부에
재적용). `alloc[b] == 1`이면 D5와 같은 인덱스 중앙값 1장
(`photos[floor((n-1)/2)]`, 짝수면 앞쪽).

## D7. 결과는 시각 순·중복 없음

모든 칸에서 고른 사진을 합쳐 `takenAt` 오름차순 정렬, 중복 제거(FR-014,
011 R4·R5). 인덱스가 겹칠 이론적 여지는 011 R4와 같은 이유로 없지만 방어로
거른다 — 거른 뒤 개수가 줄면 결함이므로 테스트가 개수를 직접 센다.

## D8. 결정적이다

정렬 키(D4의 3단계, D5의 인덱스 식)가 전부 고정이고 `Date.now()`·
`Math.random()`을 읽지 않는다(FR-015). 같은 하루를 두 번 골라도 같은 집합
(SC-004).

## 예시로 못 박기

| 입력 | 예산 | 결과 | 규칙 |
|---|---|---|---|
| 3장 (09,13,19시) | 5 | 전부 | D2 |
| 오전9시 20장 + 오후14시 2장 + 저녁19시 2장 (24장) | 5 | 오전 칸에서 2~3장, 오후 칸 1장, 저녁 칸 1장 | D3·D4 (오전 칸이 여분 다수) |
| 6개 칸에 각 1장씩 (6장) | 5 | 시간축 균등으로 5개 칸, 각 1장 (양 끝 칸 포함) | D5 |
| 전부 19–21시 (10장) | 5 | 그 칸(20–24)에서 011 R2로 5장 | D3(칸 1개) + D6 |
| 12시에 8장, 20시에 4장 (12장) | 5 | 최소 2 + 여분: 12시 칸에 3장, 20시 칸에 2장 | D3·D4 |

**"전부 19–21시" 줄**: 결과가 011의 기존 동작(그 시각들에서 시각 균등
5장)과 같아진다 — 칸이 1개면 시간 분포 선별이 011로 자연히 수렴한다.
전부 저녁인 것이 사실이므로 옳고(User Story 2 Scenario 3), 프롬프트가
"고른 사진이 하루의 어느 때에 걸쳐 있는지"를 싣는 011 FR-007b는 그대로
유효하다.

## 상한 확장과의 연결

- `distributeByTime(photos, budget)`의 `budget`은 `VISION_PHOTO_LIMIT` 하나.
  상한이 5든 12든 **같은 규칙에 budget만 바뀐다**(FR-020). "밀집 가산량"을
  따로 상수로 두지 않는다.
- 상한이 커지면 `remaining`이 커져 D4의 비례 배분이 더 많은 여분을 몰린
  칸에 준다 — "뭉친 데는 더 본다"가 상한에 비례해 자동으로 커진다.
- 016의 "많음/보통" 갈래(`reachedVisionLimit`)도 새 상한을 참조하므로
  자동으로 따라간다(FR-021).
