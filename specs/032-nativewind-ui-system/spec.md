# Feature Specification: NativeWind + React Native Reusables 기반 미니멀 UI 시스템 도입

**Feature Branch**: `032-nativewind-ui-system`

**Created**: 2026-09-03

**Status**: Draft

**Input**: User description: "11번 — NativeWind + React Native Reusables(shadcn-style) 기반 미니멀 UI 시스템 도입. 획일적인 머티리얼 톤을 벗고 얇고 모던한 미니멀 톤앤매너 + 알파리움 고유의 따뜻한 감성을 코드 수준에서 일괄 조정. 도입 범위·새 네이티브 모듈 여부·다크 모드(031 라이트 고정과의 관계)·edge-to-edge(20번 로드맵이 11번으로 미룸)·기존 `src/ui/` 점진 전환 방식을 이 스펙에서 확정한다."

## 배경과 문제 *(참고)*

이 스펙은 **새 기능이 아니라 화면의 톤앤매너를 바꾸는 리스타일링**이다. 지금
`src/ui/`의 화면 20여 개는 RN 코어 컴포넌트(`View`/`Text`/`Pressable`)에
`StyleSheet.create`와 인라인 `style` 객체로 짜여 있고, 색·간격·타이포그래피에
공유된 규칙이 없다. 화면마다 다른 사람이 그때그때 정한 값이라 전체적으로
"기본 안드로이드 앱" 인상이 남는다.

이 앱은 **주인의 휴대폰이 화자가 되어 하루를 일기로 쓰는** 감상적인 제품이다
(헌법 「이 앱이 무엇인가」). 정확한 기록 장치가 아니라 감상이므로, 화면도 그
톤 — 얇고 조용하고 따뜻한 — 을 가져야 한다. 1인 개발자가 디자인 리소스를 아끼기
위해 **기성 컴포넌트 라이브러리(React Native Reusables, shadcn-style)를 완제품처럼
조립**하되, 알파리움 고유의 따뜻한 커스텀(색 팔레트·모서리·그림자·타이포)은
**코드 수준에서 일괄 조정**한다.

**선행 작업이 이미 흐름을 정리해 뒀다.** 16번(029)이 홈 화면의 위젯 4개를 접어
"일기 쓰기 1탭"으로 단순화했고, 031이 다크 모드를 "라이트 고정"으로 임시
방어해 뒀다. 11번은 그 위에 **톤을 입히는** 작업이지, 흐름이나 화면 구성을 다시
건드리는 것이 아니다. 025에서 017 작업 일부가 날아간 패턴(잘못된 흐름의 화면을
먼저 예쁘게 만들면 나중에 버려진다)은 029가 흐름을 먼저 고정해 이미 방지됐다.

### Session 2026-09-03 (clarify)

- Q: 따뜻한 미니멀 팔레트의 본문 텍스트가 배경 대비 최소 몇 대 1의 명암비를
  만족해야 하나? → A: **WCAG AA — 본문 텍스트 4.5:1 이상, 큰 텍스트(18pt+ 또는
  14pt bold+) 3:1 이상.** 팔레트 선택과 실기기 검증(SC-005)의 통과/실패 기준으로
  쓴다.
- Q: 커스텀 서체(폰트 파일)를 새로 도입하는가? → A: **아니오. 시스템 기본
  서체를 유지한다.** 타이포그래피 토큰은 크기·굵기·행간·자간만 정의하고, 폰트
  파일을 번들하지 않는다. 커스텀 서체 도입은 별도 후속 스펙으로 남긴다(폰트
  로딩 상태·첫 렌더 깜빡임·번들 크기 이슈를 이번 스펙에 끌어들이지 않는다).
- Q: 재사용 컴포넌트에 폼 입력 요소를 포함하는가? → A: **표시 요소 + 실사용
  폼 요소.** 버튼·카드/섹션·목록 행·섹션 헤더·텍스트 스타일에 더해, 이 앱이
  실제로 쓰는 폼 요소(토글/스위치, 값 선택 행 — 일기 작성자·자동 생성 시각,
  선택 행)를 컴포넌트로 만든다. 이 앱에 없는 자유 텍스트 입력·드롭다운·라디오는
  만들지 않는다.
- Q: 새 디자인 토큰·재사용 컴포넌트 코드는 어디에 두는가? → A: **`src/ui/`
  하위.** 순수 값(색·간격·타이포·모서리 상수)은 `.ts`로 `src/ui/design/`류에
  두어 `logic` 프로젝트에서 검사하고, 재사용 컴포넌트는 `.tsx`로
  `src/ui/components/`류에 두어 `ui` 프로젝트에 편입한다. 기존 `checkSourceFile`
  감시 범위(`src/ui/`) 안이라 새 헌법 검사 경계를 만들지 않는다. 저장소 루트나
  `src/design/` 같은 새 최상위 경계는 만들지 않는다.
- Q: 온보딩 화면 전환 범위에 "필수 에셋 다운로드" 단계(029)를 포함하는가? →
  A: **포함한다.** 권한 안내 카드와 필수 에셋 다운로드 단계 둘 다 새 톤으로
  전환하되, 029가 정한 표시 규칙(합산 진행률 바, 항목별 나열 없음, 완료 전
  "시작하기" 비활성)을 그대로 유지한다. 진행률은 029가 이미 헌법 원칙 IV 범위
  밖으로 정리한 온보딩 다운로드 진행이며(생성 진행률이 아님), 이 스펙은 그
  판단을 바꾸지 않는다.

### Session 2026-09-03

- Q: NativeWind + RN Reusables 도입 범위는? → A: **엔드유저가 매일 보는 핵심
  화면군부터 — 온보딩, 일기 목록, 일기 상세(사진 슬라이더·갤러리 포함), 생성 중
  화면, 설정 탭.** 캐릭터 선택 화면과 개발자/진단 탭은 이 스펙의 필수 범위가
  아니며(SHOULD, 여유가 되면), 이번에 전환하지 않아도 실패가 아니다. 새 디자인
  토큰 계층은 처음부터 전체를 커버하도록 만들되, 화면 전환은 핵심 화면군으로
  한정한다.
- Q: 새 네이티브 모듈을 도입하는가(reanimated / gesture-handler → release 재확인
  트리거)? → A: **아니오. NativeWind(babel 플러그인 + 런타임)와 순수 JS 프리미티브만
  쓴다.** RN Reusables 컴포넌트 중 reanimated·gesture-handler·`@rn-primitives/portal`
  같은 네이티브 링크를 동반하는 것은 이번 범위에서 배제하고, 그 자리에 RN 코어
  `Modal`·`Animated`·`Pressable`로 대체 구현한다(025가 `react-native-pager-view`를
  같은 이유로 배제한 선례). 따라서 debug 실기기 확인 1회로 충분하다(012 기준).
- Q: 다크 모드 — 진짜 다크 팔레트를 대응하는가, 031의 라이트 고정을 유지하는가?
  → A: **라이트 고정을 유지한다.** 031이 `expo-system-ui` + `AppTheme` 부모 테마
  교체로 세운 라이트 고정 방어를 이 스펙이 되돌리지 않는다. 디자인 토큰은 다크
  팔레트를 나중에 얹을 수 있는 형태(의미론적 토큰 이름)로 설계하되, 이번 스펙에서
  다크 팔레트 값을 정의하거나 시스템 색 스킴을 감지하지 않는다. 다크 모드 실제
  대응은 별도 후속 스펙으로 남긴다.
- Q: edge-to-edge(`react-native-edge-to-edge` / `SystemBars`)를 이 스펙에 넣는가?
  → A: **넣지 않는다.** 20번 로드맵이 "11번에서 함께"로 미뤄 뒀으나, edge-to-edge
  전용 네이티브 모듈(`react-native-edge-to-edge`)은 release 재확인 트리거이고,
  현재 `edgeToEdgeEnabled=true`(gradle.properties) + `SafeAreaProvider` 조합이
  이미 시스템 막대 겹침을 처리하고 있다. 이 스펙은 그 기존 인셋 처리를 유지만
  하고, 별도 edge-to-edge 라이브러리 도입은 후속으로 분리한다.
- Q: 기존 `src/ui/` 컴포넌트/화면을 어떻게 점진 전환하는가? → A: **디자인 토큰
  계층과 재사용 컴포넌트를 먼저 세우고(1단계), 핵심 화면을 하나씩 그 위로 옮긴다
  (2단계).** 한 화면을 전환할 때 그 화면의 기능·문안·테스트 계약은 그대로 두고
  표현(색·간격·컴포넌트)만 바꾼다. 전환 안 된 화면은 기존 `StyleSheet` 방식으로
  계속 동작한다(혼재 허용). 각 화면 전환마다 해당 화면의 기존 `.tsx` 테스트가
  깨지지 않는지 확인하고, 새 재사용 컴포넌트에는 `.tsx` 계약 테스트를 추가한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 매일 보는 화면이 조용하고 따뜻한 톤으로 바뀐다 (Priority: P1)

주인이 앱을 열어 일기 목록을 본다. 화면은 더 이상 "기본 안드로이드 앱"처럼
보이지 않는다 — 얇은 구분선, 절제된 색, 넉넉한 여백, 부드러운 모서리, 일관된
글자 크기 위계. 일기 하나를 눌러 상세로 들어가도 같은 톤이 이어진다. 제목·본문·
사진 슬라이더가 통일된 간격과 타이포그래피로 배치된다. 설정 탭도 같은 카드·행
스타일을 쓴다.

**Why this priority**: 이것이 11번의 핵심이다. 이 하나만 해도 사용자가 매일
마주하는 화면(목록·상세·설정)이 알파리움 고유의 톤을 갖게 되고, "감상을 쓰는
앱"이라는 정체성이 화면에서 읽힌다. 나머지 스토리는 이 위에 얹는 확장이다.

**Independent Test**: 핵심 화면군(온보딩·목록·상세·생성 중·설정)을 전환 전후로
나란히 비교해, 색·간격·타이포그래피·컴포넌트 모양이 공유 디자인 토큰에서
나오는지, 화면마다 제각각이던 값이 사라졌는지 확인한다. 기능·문안·네비게이션은
전환 전과 동일하다.

**Acceptance Scenarios**:

1. **Given** 앱을 열어 일기 목록 화면에 있을 때, **When** 화면을 본다, **Then**
   목록 항목·구분선·헤더가 공유 디자인 토큰(색·간격·모서리·타이포)으로
   렌더되고, 화면에 표시되는 일기 내용·개수·정렬·탭 네비게이션은 전환 전과
   같다.
2. **Given** 일기 목록에서 항목 하나를 누른다, **When** 일기 상세 화면이
   열린다, **Then** 제목·본문·"이 일기가 본 것" 절·사진 슬라이더가 목록과 같은
   톤(같은 배경·글자색·간격 규칙)으로 표시되고, 025가 만든 슬라이더·갤러리
   동작(가로 스와이프·풀스크린·`N / M` 위치 표시)은 그대로 작동한다.
3. **Given** 설정 탭을 연다, **When** 자동 생성 설정·권한 섹션·일기 작성자
   선택·장소명 토글을 본다, **Then** 각 행·카드·토글이 핵심 화면군과 동일한
   컴포넌트 스타일로 표시되고, 설정 항목의 기능·문안은 전환 전과 같다.
4. **Given** 라이트 톤 화면이 표시된 상태다, **When** 기기 시스템 다크 모드가
   켜져 있다(또는 실행 중 전환된다), **Then** 앱 화면은 031이 세운 라이트 고정을
   유지한다 — 배경이 어두워지거나 색이 반전되지 않는다.

### User Story 2 - 온보딩과 생성 중 화면도 같은 톤을 입는다 (Priority: P2)

새 사용자가 앱을 처음 열어 온보딩(권한 안내 → 필수 에셋 다운로드)을 본다.
안내 카드·진행률 표시·버튼이 본 앱과 같은 톤으로 보여, 첫인상부터 일관된
경험을 준다. 일기를 쓰기 시작하면 "생성 중" 화면(회전 표시 + "그만두기")도
같은 색·타이포로 표시된다 — 진행률 숫자나 생성 중인 글은 여전히 나타나지
않는다.

**Why this priority**: 온보딩은 사용자의 첫인상이고, 생성 중 화면은 일기를 쓸
때마다 보는 화면이다. 둘 다 핵심 여정에 있지만, US1의 목록·상세가 먼저 톤을
갖추면 앱의 정체성은 이미 전달된다. 이건 그 일관성을 처음과 대기 순간까지
넓히는 확장이다.

**Independent Test**: 앱을 새로 설치해 온보딩을 진행하고, 이어서 일기 하나를
생성해 "생성 중" 화면을 본다. 두 화면이 핵심 화면군과 같은 디자인 토큰을
쓰는지, 온보딩의 단계 구성·문안과 생성 중 화면의 표시 규칙(진행률·글 미표시)이
전환 전과 같은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 앱을 새로 설치해 온보딩 첫 화면에 있을 때, **When** 권한 안내
   단계를 진행한다, **Then** 각 단계의 카드·"허용"/"건너뛰기" 버튼·진행 표시가
   공유 디자인 토큰으로 렌더되고, 단계 구성·순서·문안·건너뛰기 가능성은 021·031
   이후와 같다.
2. **Given** 온보딩의 "필수 에셋 다운로드" 단계에 있을 때, **When** 다운로드가
   진행된다, **Then** 합산 진행률 표시가 새 톤으로 보이고, 029가 정한 규칙
   (항목별 나열 없음, 완료 전 "시작하기" 비활성)은 그대로다.
3. **Given** 홈에서 "일기 쓰기"를 눌러 생성이 시작됐을 때, **When** "생성 중"
   화면을 본다, **Then** 회전 표시와 "그만두기"가 새 톤으로 표시되고, 진행률
   숫자·경과 시간·생성 중인 글은 화면에 **나타나지 않는다**(005 FR-028b, 015·016,
   헌법 원칙 IV).

### User Story 3 - 재사용 컴포넌트 계층이 생겨 이후 화면 작업이 빨라진다 (Priority: P3)

개발자(코딩 에이전트 포함)가 새 화면이나 요소를 만들 때, 색·간격·버튼·카드·행·
토글을 매번 인라인 `style`로 짜지 않는다. 공유 디자인 토큰과 재사용 컴포넌트
(버튼, 카드, 목록 행, 섹션 헤더, 텍스트 스타일)를 조합해 만든다. 알파리움 고유의
따뜻한 커스텀 값(색 팔레트·모서리 반경·그림자)은 한 곳에서 정의되어, 톤을
조정하면 전체 화면에 일괄 반영된다.

**Why this priority**: 이건 사용자가 직접 보는 가치가 아니라 유지보수 가치다.
US1·US2가 화면을 전환하면서 이 계층은 자연히 만들어지지만, "한 곳에서 톤을
조정하면 전체에 반영된다"는 성질을 명시적 목표로 둔다 — 이것이 1인 개발자가
디자인 리소스를 아끼는 방식이다. **우선순위는 P3(가치 순)이나, 구현 의존
순서상 US1·US2 화면 이관보다 먼저 만들어져야 한다** — 화면이 참조할 토큰·
컴포넌트가 없으면 이관을 시작할 수 없다. tasks.md는 이를 Foundational 직후
Phase로 배치한다(research R10).

**Independent Test**: 디자인 토큰(색·간격·타이포·모서리) 하나의 값을 바꾸고,
전환된 모든 핵심 화면이 그 변경을 반영하는지 확인한다. 재사용 컴포넌트 각각에
`.tsx` 계약 테스트가 있는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 디자인 토큰 계층이 정의돼 있을 때, **When** 팔레트의 "따뜻한 강조
   색" 토큰 값을 바꾼다, **Then** 그 토큰을 쓰는 모든 전환된 화면의 해당 요소가
   함께 바뀐다 — 화면마다 개별 수정이 필요하지 않다.
2. **Given** 재사용 컴포넌트(버튼·카드·목록 행 등)가 만들어져 있을 때, **When**
   `npm run test:ui`를 돌린다, **Then** 각 재사용 컴포넌트의 `.tsx` 계약 테스트가
   존재하고 통과한다.
3. **Given** 일부 화면만 전환됐고 나머지는 기존 `StyleSheet` 방식일 때, **When**
   앱을 실기기에서 연다, **Then** 전환된 화면과 안 된 화면이 모두 정상 동작하고
   (혼재 허용), 크래시나 스타일 누락이 없다.

---

### Edge Cases

- **혼재 상태에서의 시각적 불일치**: 핵심 화면 일부만 전환된 중간 상태에서,
  전환된 화면과 안 된 화면 사이 톤 차이가 사용자에게 보인다 — 이는 점진 전환의
  의도된 중간 상태이며, 스펙의 "완료" 기준은 핵심 화면군(온보딩·목록·상세·생성
  중·설정) **전부**가 전환된 시점이다.
- **NativeWind 클래스 미적용(스타일 누락)**: 클래스명 오타나 babel 설정 문제로
  스타일이 적용 안 되면 조용히 기본(스타일 없는) 렌더가 나온다 — 025가 겪은
  "테스트는 통과하는데 화면이 이상한" 계열. 각 화면 전환은 실기기에서 눈으로
  확인하고, 재사용 컴포넌트는 `.tsx` 테스트로 최소 렌더 계약을 잠근다.
- **시스템 글꼴 크기 확대(접근성)**: 사용자가 OS 글꼴 크기를 키우면 타이포그래피
  토큰이 그에 따라 확대되어야 하며(RN 기본 동작 유지), 레이아웃이 깨지지
  않아야 한다.
- **다크 모드 강제 전환 중 앱 실행**: US1 AS4와 동일 — 031의 라이트 고정이
  유지되어야 하고, 이 스펙이 그 방어를 약화시키지 않는다.
- **매우 긴 일기 본문 / 사진 0장인 하루**: 상세 화면 전환 후에도 025·017이
  세운 표시 규칙(사진 0장이면 슬라이더 영역 없음, "사진: 없었다" 텍스트)이
  그대로 동작해야 한다.
- **개발자 탭 미전환**: 개발자/진단 탭은 이번 필수 범위 밖이므로 기존 톤으로
  남는다 — 이는 정상이며, 배포 빌드에서 이 탭은 닿을 수 없다(헌법 원칙 III).

## Requirements *(mandatory)*

### Functional Requirements

**디자인 토큰 계층**

- **FR-001**: 색(배경·표면·글자·강조·경계), 간격 스케일, 타이포그래피(크기·
  굵기·행간·자간 위계 — 서체는 시스템 기본), 모서리 반경, 그림자를 **의미론적
  이름의 공유 토큰**으로 한 곳에 정의해야 한다. 화면 코드는 원시 색값·픽셀값을
  직접 쓰지 않고 이 토큰을 참조한다. 커스텀 폰트 파일은 이번 스펙에서 번들하지
  않는다.
- **FR-002**: 팔레트는 알파리움 고유의 **따뜻하고 조용한 미니멀 톤**이어야
  한다 — 기본 머티리얼 파랑·회색 계열이 아니라, 따뜻한 중성색 + 절제된 강조색.
  톤 방향의 최종 판단은 실기기 화면 관찰로 하되, **본문 텍스트는 배경 대비
  4.5:1 이상, 큰 텍스트(18pt+ 또는 14pt bold+)는 3:1 이상**(WCAG AA)을
  만족해야 한다.
- **FR-003**: 토큰은 다크 팔레트를 **나중에 얹을 수 있는 형태**(의미론적 이름,
  라이트/다크 값을 분리 정의 가능한 구조)로 설계하되, 이 스펙에서 다크 값을
  정의하거나 시스템 색 스킴을 감지하지 않는다. 031의 라이트 고정을 유지한다.

**재사용 컴포넌트**

- **FR-004**: 핵심 화면이 공통으로 쓰는 요소를 재사용 컴포넌트로 제공해야
  한다 — 버튼(주/보조/위험 변형), 카드/섹션 컨테이너, 목록 행, 섹션 헤더,
  텍스트 스타일(제목·본문·캡션), 그리고 이 앱이 실제로 쓰는 폼 요소(토글/스위치,
  값 선택 행 — 일기 작성자·자동 생성 시각, 선택 행). 각 컴포넌트는 디자인
  토큰만 참조한다. 이 앱에 없는 자유 텍스트 입력·드롭다운·라디오 컴포넌트는
  만들지 않는다.
- **FR-005**: 재사용 컴포넌트는 **직접적으로 gesture-handler·네이티브 포털·
  edge-to-edge 전용 라이브러리를 들이지 않는다** — 애니메이션·모달·제스처가
  필요하면 RN 코어(`Animated`·`Modal`·`Pressable`)로 구현한다. **다만
  `react-native-reanimated`는 예외다**: NativeWind v4.2의 `react-native-css-interop`가
  reanimated를 peerDependency로 요구하므로(2026-09-03 설치 시 확인), NativeWind
  도입이 곧 reanimated 도입이다. 이는 컴포넌트 계층의 선택이 아니라 NativeWind
  자체의 요구이며, 이 스펙은 이를 수용한다 — 대신 FR-017의 release 재확인
  조건이 발동한다.
- **FR-006**: 각 재사용 컴포넌트에는 최소 렌더/변형 계약을 잠그는 `.tsx` 계약
  테스트가 있어야 한다(jest `ui` 프로젝트).
- **FR-006a**: 디자인 토큰·재사용 컴포넌트 코드는 `src/ui/` 하위에 둔다 — 순수
  값(색·간격·타이포·모서리 상수)은 `.ts`로, 재사용 컴포넌트는 `.tsx`로. 새
  최상위 경계(`src/design/` 등)를 만들지 않으며, 기존 `checkSourceFile`
  감시 범위 안에 둔다.

**화면 전환 (핵심 화면군)**

- **FR-007**: 다음 화면이 새 디자인 토큰·재사용 컴포넌트 위로 전환되어야 한다 —
  온보딩(권한 안내 카드 **및** 필수 에셋 다운로드 단계), 일기 목록, 일기 상세
  (사진 슬라이더·갤러리 포함), 생성 중 화면, 설정 탭. 온보딩 에셋 다운로드
  단계는 029가 정한 표시 규칙(합산 진행률 바, 항목별 나열 없음, 완료 전
  "시작하기" 비활성)을 유지한 채 톤만 바꾼다.
- **FR-008**: 화면 전환은 **표현만 바꾸고 기능·문안·네비게이션·데이터 흐름은
  바꾸지 않아야 한다** — 각 화면의 기존 동작 계약(무엇을 표시하고 어떤 탭·
  버튼이 어디로 가는지)이 전환 전과 동일해야 한다.
- **FR-009**: 화면 전환은 헌법 경계를 그대로 지켜야 한다 — 화면이 모델 식별자·
  자산에 닿지 않고(원칙 III, `checkSourceFile`의 `UI_TOUCHES_MODEL`), 성능
  지표·생성 중인 글을 표시하지 않으며(원칙 IV, 005 FR-028b), 프롬프트 조립에
  닿지 않는다(원칙 II, `UI_TOUCHES_PROMPT`).
- **FR-010**: 025가 만든 사진 슬라이더·풀스크린 갤러리의 동작(가로 페이징,
  `N / M` 위치 표시, 풀스크린 모달, 순환 없음, 닫기 시 스크롤 위치 유지)과
  017·025의 사진 0장/사본 실패 표시("사진: 없었다", "이 사진은 이제 없다")가
  상세 화면 전환 후에도 동일하게 작동해야 한다.
- **FR-011**: 생성 중 화면 전환 후에도 진행률 숫자·경과 시간·생성 중인 글이
  화면에 나타나지 않아야 한다(005 FR-028b, 015·016).

**점진 전환과 혼재**

- **FR-012**: 전환되지 않은 화면(캐릭터 선택, 개발자/진단 탭 등)은 기존
  `StyleSheet` 방식으로 계속 정상 동작해야 한다 — 전환된 화면과 혼재해도
  크래시·스타일 누락이 없다.
- **FR-013**: 이 스펙의 "완료"는 FR-007이 열거한 핵심 화면군 **전부**가
  전환된 시점이다. 핵심 화면군 밖의 화면 전환은 SHOULD(여유가 되면)이며 완료
  조건이 아니다.

**테스트와 검증**

- **FR-014**: jest 두 프로젝트 분리(`.ts` = logic / `.tsx` = ui)를 유지해야
  한다 — 새 화면·컴포넌트 테스트는 `.tsx`로 작성하고, `__tests__/jest-projects.test.ts`의
  파일 수 가드가 계속 통과해야 한다.
- **FR-015**: 기존 화면 테스트(`test:ui`)와 로직 테스트(`test:logic`)가
  전환 후에도 전부 통과해야 한다 — 표현만 바뀌므로 기능 계약 테스트는 깨지지
  않아야 한다.
- **FR-016**: `npm run lint`(eslint + tsc + 헌법 검사 + prettier)가 통과해야
  한다.
- **FR-017**: 핵심 화면군 전부가 최소 1회 실기기(debug)에서 확인되어야 한다 —
  라이트 톤 표시, 다크 모드 켠 상태에서 라이트 고정 유지, 025 슬라이더·갤러리
  회귀 없음. **NativeWind가 `react-native-reanimated`(네이티브 모듈)를 들이므로
  release 재확인 1회가 필요하다**(012 기준 — 새 네이티브 모듈·JNI 심볼이
  R8·ProGuard에서 깨질 수 있음). debug 확인으로 5개 화면군 톤·라이트 고정·025
  회귀를 보고, release 빌드 1회로 `llama.rn` 로드·앱 첫 렌더·`prod` 환경 표시가
  깨지지 않는지 확인한다. 다크 모드 관련 확인이 포함되므로 검증 기기는
  **SM-S928N (One UI 8.5)** 을 포함한다.
- **FR-018**: 기존 Maestro 흐름이 전환 후에도 통과해야 하며, 화면 요소를
  `id`/`testID`나 문안으로 찾는 기존 흐름이 깨지면 그 흐름을 함께 갱신한다
  (025·023이 겪은 stale Maestro 패턴 방지). 새 Maestro 흐름을 추가하면
  `scripts/run-device-tests.mjs`의 `FLOWS`에 등록한다.

**범위 밖 (명시)**

- **FR-019**: 이 스펙은 **다크 팔레트 실제 대응·시스템 색 스킴 감지·다크 모드
  전환 UI를 구현하지 않는다** — 031의 라이트 고정을 유지하며, 다크 대응은 후속
  스펙이다.
- **FR-019a**: 이 스펙은 **커스텀 서체(폰트 파일) 도입을 하지 않는다** — 시스템
  기본 서체를 유지하고 타이포 토큰은 크기·굵기·행간·자간만 정의한다. 서체
  도입은 후속 스펙이다.
- **FR-020**: 이 스펙은 **edge-to-edge 전용 라이브러리(`react-native-edge-to-edge`
  등) 도입, `SystemBars` 제어, 시스템 막대 색·투명도 변경을 하지 않는다** —
  현재 `edgeToEdgeEnabled=true` + `SafeAreaProvider` 인셋 처리를 유지만 한다.
- **FR-021**: 이 스펙은 **홈 화면 흐름·화면 구성·네비게이션 구조를 바꾸지
  않는다** — 029가 정리한 "일기 쓰기 1탭"과 탭 구조를 그대로 둔다. 표현만
  바꾼다.
- **FR-022**: 이 스펙은 **새 사용자 기능·새 저장 필드·새 신호를 도입하지
  않는다**.

### Key Entities

해당 없음 — 이 기능은 새 데이터 모델을 도입하지 않는다. 표현 계층(디자인 토큰,
재사용 컴포넌트)과 화면의 시각적 표현만 다룬다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: FR-007이 열거한 핵심 화면군 **5개군 전부**(온보딩, 일기 목록, 일기
  상세, 생성 중, 설정)가 공유 디자인 토큰·재사용 컴포넌트 위로 전환되어, 화면
  코드에 원시 색값(`#rrggbb`)·매직 픽셀값이 직접 박힌 곳이 0이다(전환된 화면
  기준).
- **SC-002**: 디자인 토큰 1개의 값을 바꾸면, 그 토큰을 참조하는 **모든 전환된
  화면**의 해당 요소가 함께 바뀐다 — 화면별 개별 수정 없이 한 곳에서 톤을
  조정할 수 있다.
- **SC-003**: 전환 전후로 `npm run test:ui`·`npm run test:logic`·`npm run lint`가
  **전부 통과**한다 — 표현만 바뀌므로 기능 계약 테스트 회귀가 0건이다.
- **SC-004**: 새 재사용 컴포넌트 각각에 `.tsx` 계약 테스트가 있고, jest `ui`
  프로젝트에 정상 편입되어(`jest-projects.test.ts` 파일 수 가드 통과) 실행된다.
- **SC-005**: SM-S928N(One UI 8.5) 실기기에서 시스템 다크 모드를 켠 채 핵심
  화면군 5개군을 열었을 때 **5/5 모두** 라이트 톤(밝은 배경)으로 표시되고,

## Assumptions

- **라이트 전용 설계는 유지된다**: `src/ui/` 어디에도 다크 팔레트·색 스킴 감지가
  없고(031이 확인), 이 스펙도 추가하지 않는다. 디자인 토큰은 다크 값을 나중에
  분리 정의할 수 있는 구조로 만들되 이번엔 라이트 값만 채운다.
- **031의 라이트 고정 방어와 충돌하지 않는다**: 031이 `expo-system-ui` +
  `AppTheme` 부모 테마 교체 + `forceDarkAllowed=false`로 세운 방어는 그대로 두고,
  이 스펙은 그 위에서 라이트 톤 팔레트만 정의한다.
- **NativeWind v4.2 = reanimated 도입 (2026-09-03 구현 중 확인, 초안 정정)**:
  research R1은 "NativeWind는 babel/JS 레이어라 네이티브 링크 없음"으로 봤으나,
  v4.2의 `react-native-css-interop@0.2.6`이 `react-native-reanimated@>=3.6.2`를
  **peerDependency로 요구**해 `npx expo install nativewind`가 `react-native-reanimated@4.6.0`
  (C++ 코드젠 네이티브 모듈)을 함께 설치한다. 사용자 결정(2026-09-03): NativeWind를
  유지하고 reanimated를 수용한다. 결과: **release 재확인 1회 필요**(FR-017),
  gesture-handler·edge-to-edge·`@rn-primitives/*`는 여전히 배제(그건 컴포넌트
  선택이지 NativeWind 요구가 아님). `babel.config.js`는 `nativewind/babel` 프리셋을
  넣지 않고 `jsxImportSource`만 쓴다(그 프리셋이 `react-native-worklets/plugin`을
  끌어들여 jest를 깨뜨림 — 실측).
- **edge-to-edge는 후속으로 분리**: 20번 로드맵이 "11번에서 함께"로 미뤄 뒀으나,
  `react-native-edge-to-edge`는 release 재확인 트리거이고 현재 인셋 처리가 이미
  동작 중이라, 이 스펙은 유지만 하고 별도 스펙으로 넘긴다.
- **029가 흐름을 이미 고정했다**: 홈 화면 위젯 4개 제거·"일기 쓰기 1탭"은 029가
  끝냈으므로, 11번은 톤만 입힌다. 025에서 017 작업이 날아간 패턴(잘못된 흐름을
  먼저 예쁘게)은 재발하지 않는다.
- **점진 전환·혼재 허용**: 한 화면씩 전환하며, 미전환 화면은 기존 `StyleSheet`로
  계속 동작한다. 완료 기준은 핵심 화면군 5개군 전부.
- **캐릭터 선택 화면·개발자 탭은 필수 범위 밖**: 여유가 되면 전환하되(SHOULD),
  안 해도 이 스펙의 실패가 아니다. 개발자 탭은 배포 빌드에서 닿을 수 없다(원칙
  III).
- **jest 두 프로젝트 분리 유지**: 새 컴포넌트·화면 테스트는 `.tsx`. `.ts`로
  만들면 `render()` 부재로 실패한다(원인을 가리키는 실패). `jest-projects.test.ts`
  파일 수 가드가 양쪽에 있으므로 함께 통과해야 한다.
- **main 직접 작업 금지**: 브랜치 `032-nativewind-ui-system`에서 작업하고 PR로
  머지한다. `.githooks/pre-commit`·`pre-push`가 main 직접 커밋을 막는다.
- **plan에서 볼 것**: NativeWind·RN Reusables·tailwind 관련 패키지 버전은
  Expo 57 기준으로 `expo install`/공식 문서/context7(`/expo/expo`, NativeWind
  docs)로 해석한다(`npm view` 금지 — AGENTS.md). NativeWind babel/metro 설정,

  NativeWind 런타임을 변환에서 빼면 테스트가 깨질 수 있음 — 007·025의 jest
