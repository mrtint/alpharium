## 근거와 원본

- 설계문서: `docs/superpowers/specs/2026-10-17-design-system-design.md` — 조사 사실(§1), 구조(§3), 토큰·다크 초안(§4), 서체(§5), 웹(§6), 규칙 문서(§7), 방어(§8)가 거기 있다.
- 선례: 032·043(앱 디자인 토큰 단일 출처, Modernist 팔레트), 083(Pretendard 앱 탑재·`FONT`, OFL 파일은 배포처 그대로), 086(`site/`와 그것을 잠그는 `__tests__/privacy/`·`pages.yml`), 047·060(보드를 옮길 때 원문 대조를 계약 테스트에 넣는다).
- 용어: **정본** = 사람이 정한 토큰 값이 사는 파일 하나. **생성물** = 정본에서 기계적으로 옮겨 쓴 앱용·웹용 파일. **역할 이름** = 색·글자 크기 등 값에 붙은 용도 이름(배경·글자·강조…). **사이트** = `site/`의 세 페이지(소개·개인정보처리방침·도움말·문의).

## Clarifications

### Session 2026-10-17 (brainstorming)

- Q: 첫 스펙의 범위? → A: 기반(정본·생성·규칙 문서·방어) + 웹 재디자인. 앱 화면 점검·정리는 후속 과제.
- Q: 토큰 정본 방식? → A: 자체 JSON + 작은 생성 스크립트(새 의존성 없음). W3C 토큰 형식·Style Dictionary는 쓰지 않는다.
- Q: 웹 색 모드? → A: 라이트 + 다크 둘 다(`prefers-color-scheme`). 앱은 라이트 고정을 유지하므로 다크 값은 앱에서 쓰이지 않는다.
- Q: 소개 페이지 범위? → A: 시스템 적용만, 내용은 그대로(스크린샷·새 문구 없음).
- Q: 웹 서체? → A: Pretendard 공식 배포 파일을 `site/`에 자체 호스팅(CDN 금지 — 방문자 IP가 제3자로 가서 방침과 모순).
- Q: 다크 팔레트 초안과 「웹에서 accent를 글자에 쓰지 않는다」 규칙? → A: 소유자 이견 없음(2026-10-17).

### Session 2026-10-18 (clarify)

- Q: 정본에 넣을 간격 스케일의 값은 무엇을 기준으로 정하는가? → A: 앱 소스가 실제로 반복해 쓰는 여백·간격 값을 조사해 자주 쓰는 값만 단계로 확정한다. 새로 만든 배수 스케일을 앱에 강요하지 않고, 웹은 같은 단계만 쓴다.
- Q: 페이지 한 장의 첫 로딩 글꼴 용량 상한은? → A: 합계 1MB 이하. 공식 분할 배포본에서 필요한 굵기 둘~셋만 쓰고, 넘으면 테스트가 실패한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 방문자가 앱과 한 제품처럼 보이는 페이지에서 방침을 읽는다 (Priority: P1)

스토어 심사자, 앱 사용자, 문의하려는 사람이 소개·개인정보처리방침·도움말·문의 페이지를 연다. 세 페이지가 같은 틀(같은 색·서체·간격·위계)로 보이고, 앱의 오프화이트·단일 레드·직선·Pretendard와 같은 시각 언어다. 긴 글인 방침이 읽기 편하고, 휴대폰 폭에서 가로로 넘치지 않으며, 휴대폰이 다크 모드면 다크로 보인다.

**Why this priority**: 이번 과제의 계기이자 사용자가 이미 불만을 말한 부분이다. 이것만으로도 눈에 보이는 가치가 있다.

**Independent Test**: 세 페이지를 라이트·다크, 휴대폰 폭·데스크톱 폭으로 열어 비교한다. 서체·색·간격이 세 페이지에서 같고 앱 토큰과 일치하며 가로 스크롤이 없다.

**Acceptance Scenarios**:

1. **Given** 세 페이지, **When** 라이트 모드의 휴대폰 폭으로 열면, **Then** 배경·글자·강조 색과 서체가 앱의 토큰 값과 같고 세 페이지의 머리·본문·목록 모양이 같다.
2. **Given** 운영체제가 다크 모드, **When** 페이지를 열면, **Then** 다크 팔레트로 보이고 모든 글자가 기준 대비를 넘는다.
3. **Given** 방침 페이지, **When** 읽으면, **Then** 제목 계층(큰 제목·절 제목·소절 제목)이 구분되고 한 줄 요약이 본문과 구별되며 절 사이가 구분선·간격으로 나뉜다.
4. **Given** 링크와 강조 글자, **When** 라이트 모드에서 보면, **Then** 본문 기준(4.5:1)을 넘는 색이다(accent 빨강을 글자에 쓰지 않는다).
5. **Given** 기존 방침의 구조 표식(절 `id`, `data-outbound`, 근거 주석, 자리표시자), **When** 재디자인 뒤, **Then** 모두 그대로이고 086의 사실 잠금 테스트가 통과한다.

---

### User Story 2 - 디자인 작업자가 규칙 문서를 읽고 같은 시스템으로 만든다 (Priority: P2)

앞으로 화면이나 페이지를 디자인하거나 만드는 사람(또는 에이전트)이 저장소의 규칙 문서 한 곳을 먼저 읽는다. 토큰의 역할 이름과 뜻, 타입 스케일, 서체 규칙, 색 사용 규칙, 공용 부품과 패턴, 하지 말아야 할 것, 새 값을 더하는 절차를 알 수 있고, 프로젝트 안내 문서가 그 문서를 먼저 읽으라고 가리킨다.

**Why this priority**: 이번에 만든 시스템이 다음 산출물에서도 지켜지게 하는 장치다. 문서가 없으면 같은 문제가 반복된다.

**Independent Test**: 프로젝트 안내 문서(AGENTS.md·CLAUDE.md)에서 규칙 문서로 닿고, 규칙 문서가 적은 역할 이름과 부품 이름이 실제 정본·소스에 존재한다.

**Acceptance Scenarios**:

1. **Given** AGENTS.md 또는 CLAUDE.md, **When** 디자인 작업을 시작하려 읽으면, **Then** 규칙 문서를 먼저 읽으라는 한 줄이 있고 그 경로가 실제 파일이다.
2. **Given** 규칙 문서가 언급하는 모든 토큰 역할 이름, **When** 정본과 대조하면, **Then** 모두 정본에 있다(없는 이름이 문서에 있으면 실패).
3. **Given** 새 색이 필요한 작업자, **When** 규칙 문서의 절차를 따르면, **Then** 정본에 값을 더하고 생성하고 테스트가 통과하는 순서로 끝난다.

---

### User Story 3 - 값이 어긋나거나 시스템을 벗어나면 테스트가 막는다 (Priority: P2)

누군가 토큰 값을 고치거나 사이트에 색·서체를 직접 쓰면, 사람이 알아채기 전에 테스트가 실패한다. 정본과 생성물이 같고, 대비 기준을 지키며, 사이트가 정본이 만든 변수만 쓴다.

**Why this priority**: 앱과 웹의 값이 갈라진 것이 이번 문제의 원인이다. 방어가 없으면 다시 갈라진다.

**Independent Test**: 정본의 색 한 값을 바꾸고 생성하지 않은 채 테스트를 돌리면 동기 테스트가 실패한다. 사이트 CSS에 색 리터럴을 넣으면 하드코딩 테스트가 실패한다.

**Acceptance Scenarios**:

1. **Given** 정본, **When** 생성물이 정본에서 다시 만든 결과와 한 글자라도 다르면, **Then** 테스트가 실패한다.
2. **Given** 앱의 기존 토큰 상수(색·반경·타입·서체), **When** 이번 변경 뒤, **Then** 값이 변경 전과 같다(앱 화면이 달라지지 않는다).
3. **Given** 사이트의 HTML·CSS, **When** 생성된 토큰 파일 밖에서 색 리터럴·글꼴 선언·페이지 안 스타일 블록이 발견되면, **Then** 테스트가 실패한다.
4. **Given** 정본의 글자/배경 대비 쌍 표, **When** 라이트·다크에서 기준(본문 4.5:1, 큰 글자·UI 3:1)에 못 미치는 쌍이 있으면, **Then** 테스트가 실패한다.
5. **Given** 웹 서체 파일, **When** 배포처 파일과 해시가 다르거나 라이선스 전문이 없으면, **Then** 테스트가 실패한다.

---

### Edge Cases

- 웹 서체가 불러와지기 전 → 시스템 서체로 먼저 보이고(깜빡임 최소화), 레이아웃이 크게 밀리지 않는다.
- 운영체제가 모드를 알리지 않는 브라우저 → 라이트로 보인다.
- 매우 좁은 폭(320px)·글자 크기를 키운 브라우저 → 가로 스크롤 없이 긴 낱말·주소가 줄바꿈된다.
- 인쇄·화면 읽기 프로그램 → 구조(제목 계층·목록)가 의미 있는 마크업으로 남는다.
- 정본에 다크 값이 있어도 앱은 라이트 고정이므로 앱 생성물에서 다크 값이 화면에 쓰이지 않는다.
- 자리표시자(`{SUPPORT_EMAIL}` 등)가 남은 채 게시되는 것은 086의 워크플로가 계속 막는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 앱과 웹이 공유하는 토큰(색, 반경, 타입 스케일, 서체, 간격)의 값을 사람이 정한 정본 파일 하나에 둬야 한다(MUST). 색은 라이트 값과 다크 값을 같은 역할 이름으로 가진다.
- **FR-001a**: 간격 스케일의 단계 값은 앱 소스가 실제로 반복해 쓰는 여백·간격 값의 조사 결과에서 자주 쓰는 값만 골라 사람이 확정해야 한다(MUST). 조사 결과(값별 사용 횟수)는 스펙 산출물에 남기고, 앱 코드는 이번에 이 단계로 바꾸지 않는다(MUST NOT). 웹 공용 스타일의 여백·간격은 이 단계만 쓴다.
- **FR-002**: 생성 스크립트는 정본의 값을 옮겨 쓰기만 해야 하며(MUST), 값을 계산·파생·보정하지 않는다(원칙 V).
- **FR-003**: 앱용 생성물은 기존 토큰 상수(`COLORS`·`RADIUS`·`TYPE`·`FONT`)의 이름·모양·값을 그대로 제공해야 한다(MUST). 앱 코드와 tailwind 설정은 바뀌지 않고, 앱 쪽 토큰 테스트는 수정 없이 통과한다. 앱용 생성물에는 라이트 값만 들어가고 웹 전용 항목(다크 값·웹 전용 글자 역할)은 들어가지 않는다.
- **FR-004**: 웹용 생성물은 같은 역할 이름의 CSS 변수를 라이트 기본값과 다크 대응값으로 제공해야 한다(MUST).
- **FR-005**: 컴포넌트 전용 값(눌림·쓰는 중·토스트·대화상자·달력·설정 행 등)은 이번에 정본으로 옮기지 않는다(MUST NOT).
- **FR-006**: 웹 다크 팔레트는 설계 문서 §4의 초안 값으로 정하고, 모든 글자/배경 쌍이 본문 4.5:1(큰 글자·UI 경계 3:1)을 넘어야 한다(MUST).
- **FR-007**: 웹의 링크와 강조 글자는 accent 역할 색을 쓰지 않고 danger 역할 색을 써야 한다(MUST). accent는 면·표식에만 쓴다.
- **FR-008**: 사이트 세 페이지는 공용 토큰 파일과 공용 스타일 파일을 쓰고 페이지별 스타일 블록·색 리터럴·글꼴 선언을 갖지 않아야 한다(MUST).
- **FR-009**: 웹 서체는 앱과 같은 Pretendard 버전의 공식 배포 파일을 `site/`에 자체 호스팅해야 한다(MUST). 제3자 서버에서 글꼴이나 스타일을 불러오지 않는다(MUST NOT). 파일은 배포처 그대로(수정·서브셋 변환 금지)이고 라이선스 전문이 같이 있어야 한다.
- **FR-010**: 서체 이름·사용 굵기는 정본의 서체 항목 한 곳에서 정해야 한다(MUST). 웹은 로딩 전 대체 서체를 지정하고 글꼴이 늦게 와도 글이 보여야 한다.
- **FR-010a**: 세 페이지 각각이 첫 로딩에서 받는 글꼴 파일의 합계는 1MB(1,000,000바이트) 이하여야 한다(MUST). 쓰는 굵기는 둘~셋이고, 파일은 배포처가 공식 제공하는 분할(필요한 글자 구간만 받는) 배포본을 그대로 쓴다. 한 페이지가 받는 글꼴 파일은 그 페이지가 쓰는 글자 구간만이다.
- **FR-011**: 개인정보처리방침은 읽기 폭 제한, 제목 계층, 한 줄 요약 구분, 절 구분, 목록 간격, 휴대폰 폭 대응을 갖춰야 한다(MUST). 소개·지원 페이지는 같은 틀을 쓴다. 소개 페이지의 문장·링크는 그대로다.
- **FR-012**: 재디자인은 사이트의 구조 표식(절 `id`, `data-outbound`, 근거 주석, 자리표시자 문자열)과 문장 내용을 바꾸지 않아야 한다(MUST). 086의 `__tests__/privacy/`와 Pages 워크플로 검사는 통과해야 하며, 수정은 사이트 원문 검사 S3(외부 자원 0)의 `rel="stylesheet"` 전면 금지를 「같은 출처의 상대 경로 스타일시트만 허용(외부 주소·스크립트·`@import`는 계속 금지)」로 좁히는 한 곳뿐이다.
- **FR-013**: 저장소에 디자인 규칙 문서가 있어야 한다(MUST): 역할 이름의 뜻, 타입 스케일, 서체 규칙, 색 사용 규칙(accent는 면, 글자 강조는 danger), 공용 부품과 웹 공용 클래스, 화면 유형별 패턴(긴 글 문서 페이지·설정 행·대화상자), 하지 않는 것, 새 값을 더하는 절차.
- **FR-014**: AGENTS.md와 CLAUDE.md는 디자인 산출물을 만들기 전에 규칙 문서를 먼저 읽으라는 안내를 한 줄씩 가져야 한다(MUST). 헌법 본문은 바꾸지 않는다.
- **FR-015**: 다음 방어가 각각 테스트로 있어야 하고(MUST) 위반 주입으로 실제로 실패함을 확인한다: 정본↔생성물 동기, 앱 토큰 값 불변, 라이트·다크 대비 쌍, 사이트 하드코딩 금지, 서체 파일 해시·라이선스 존재, 규칙 문서가 언급한 이름의 실재.
- **FR-016**: 로드맵에 이 과제를 올리고 후속 과제 둘(앱 화면 이탈 점검·정리, 소개 페이지 랜딩화)을 별도 항목으로 올려야 한다(MUST). 앱 화면의 이탈 정리는 이번 범위가 아니다(MUST NOT).

### Key Entities

- **토큰 정본**: 역할 이름 → 값(라이트·다크 색, 반경, 글자 크기·굵기·행간, 서체 이름·굵기 목록, 간격 단계). 사람이 정한 값이고 계산하지 않는다.
- **대비 쌍 표**: 글자 역할과 배경 역할의 짝 목록과 각 기준(본문/큰 글자·UI). 사람이 정한다.
- **생성물**: 정본의 앱용 상수 파일, 웹용 CSS 변수 파일. 정본에서만 만들어지고 커밋된다.
- **웹 공용 스타일**: 생성된 변수만 참조하는 사이트 공용 스타일 한 벌.
- **규칙 문서**: 디자인 산출물이 따르는 규칙 한 권.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 세 페이지가 같은 색·서체·간격을 쓰고 그 값이 앱 토큰과 일치한다 — 페이지 간 서로 다른 색 리터럴·글꼴 선언이 0건이다.
- **SC-002**: 사이트의 모든 글자/배경 쌍이 라이트·다크 모두 기준 대비(본문 4.5:1, 큰 글자·UI 3:1)를 넘는다.
- **SC-003**: 320px 폭에서 세 페이지 모두 가로 스크롤이 없다.
- **SC-004**: 정본의 값 하나를 바꾸고 생성하지 않으면 테스트가 실패하고, 생성하면 통과한다.
- **SC-005**: 앱의 기존 토큰 상수 값이 변경 전과 100% 같다 — 기존 토큰 테스트가 수정 없이 통과한다.
- **SC-006**: 086의 방침 사실 잠금·사이트 구조·Pages 워크플로 테스트가 FR-012의 S3 한 단언 조정 외에는 수정 없이 통과한다.
- **SC-006a**: 세 페이지 각각의 첫 로딩 글꼴 합계가 1MB 이하이고 테스트가 이를 잠근다.
- **SC-007**: 사이트를 여는 동안 제3자 주소로 가는 요청이 0건이다(글꼴·스타일 포함).
- **SC-008**: 규칙 문서가 언급한 토큰·부품 이름이 모두 실재한다(없는 이름 0건).
- **SC-009**: 소유자가 헤드리스 캡처(모바일·데스크톱, 라이트·다크)로 세 페이지를 보고 앱과 같은 제품으로 보인다고 확인한다.

## Assumptions

- 앱은 계속 라이트 고정(031)이고 다크 값은 웹에서만 쓰인다.
- 사이트의 문장 내용은 086이 정했고 이번에 바꾸지 않는다(구조·표식 포함).
- 웹 서체는 공식 분할 배포본(unicode-range 분할)의 파일 그대로를 쓰고, 첫 로딩 합계 상한은 FR-010a가 정한다. 어떤 분할 파일이 어느 글자 구간을 맡는지는 plan에서 조사한다.
- 게시(GitHub Pages)와 게시 뒤 URL 확인은 머지 뒤 소유자 몫이며, 스펙 완료 조건은 로컬 캡처와 테스트 통과까지다.
- 앱 번들에 생성 파일이 들어가므로 dev 빌드에서 앱이 변경 전과 같은 색으로 뜨는지 한 번 확인한다(원칙 V).
- 스펙 번호·브랜치 이름은 병렬 세션과 겹치지 않게 소유자가 머지 시점에 정한다.
