# Phase 0 Research: 사진의 내용을 보고 일기의 재료로 준다

**Feature**: `011-photo-vision-summary` | **Date**: 2026-08-22

계획이 남긴 여섯 물음을 푼다. **실측과 짐작을 구분해 적는다**(헌법 원칙 V).

---

## §1. `llama.rn` 0.12.9의 멀티모달 API — 설치본 타입을 직접 읽었다

**Decision**: `initMultimodal` · `getMultimodalSupport` · `releaseMultimodal` 셋과
`completion()`의 `media_paths`를 쓴다. 그 외는 쓰지 않는다.

**근거 — 실측이며 문서가 아니다** (2026-08-22, `node_modules/llama.rn/lib/typescript/`
직접 확인):

```ts
// index.d.ts:231
initMultimodal({ path, use_gpu, image_min_tokens, image_max_tokens }: {
  path: string;            // mmproj 파일 경로
  use_gpu?: boolean;       // 기본 true
  image_min_tokens?: number;
  image_max_tokens?: number;
}): Promise<boolean>

isMultimodalEnabled(): Promise<boolean>
getMultimodalSupport(): Promise<{ vision: boolean; audio: boolean }>
releaseMultimodal(): Promise<void>

// types.d.ts:239 — completion 파라미터
media_paths?: Array<string>   // "Requires multimodal support to be enabled via initMultimodal"
```

**중요한 사실 넷**:

1. **`initMultimodal`은 기존 컨텍스트에 붙는다.** 별도의 컨텍스트를 여는 것이 아니라
   이미 열린 `LlamaContext`에 mmproj를 얹는다. 그래서 **베이스 모델(VLM 본체)을 먼저
   `initLlama`로 열고 그 위에 mmproj를 붙이는 두 단계**다.
2. **`getMultimodalSupport()`가 `{ vision, audio }`를 준다** — 「이 모델이 사진을 볼 수
   있는가」를 **물어볼 수 있다.** 짐작하지 않아도 된다(원칙 V).
3. **`media_paths`가 배열이다** — 한 번에 여러 장을 넣을 수 있는 모양이지만,
   spec이 **한 장씩**으로 확정했으므로(FR-001a) 길이 1로만 쓴다.
4. **⚠️ `image_max_tokens`가 다이얼로 존재한다** — 주석이 "Recommended: 256-512 for
   faster inference, up to 4096 for maximum detail"라고 적었다. §4가 이것을 쓴다.

**⚠️ 원칙 IV의 위험이 여기 있다.** `completion()`은 005에서 확인된 대로
`timings`·`tokens_predicted`를 **요청하지 않아도 돌려준다.** 멀티모달이라고 다르지
않으며, 오히려 「사진 처리에 몇 ms」가 더 붙을 수 있다. **`vision-port.ts`가 경계에서
버린다** — 005의 `llama-port.ts`가 `{ text, ending }`만 꺼낸 것과 같은 구조.

**Alternatives considered**:
- **`tokenize(text, { media_paths })`로 직접 다루기** — 타입에 있으나 저수준이고, 우리가
  필요한 것은 캡션 텍스트뿐이다. 쓰면 토큰 수가 보이고 그것이 원칙 IV의 통로다. **버린다.**
- **`audio` 지원 활용** — 로스터에 오디오 신호가 없다. 범위 밖.

## §2. E1(한 번에 하나) 아래에서 두 모델을 어떻게 여닫는가 — **이 기능의 핵심 제약**

**Decision**: **완전히 순차로 간다.** VLM을 열어 5장을 전부 캡션하고 **닫은 뒤에**
캐릭터 모델을 연다. 두 모델이 동시에 열리는 순간이 없다.

```
[VLM 본체 initLlama] → [initMultimodal(mmproj)]
     → 사진1 캡션 → 사진2 캡션 → … → 사진5 캡션
→ [releaseMultimodal] → [release]          ← 여기서 VLM이 완전히 닫힌다
→ [캐릭터 모델 initLlama] → 일기 생성 → [release]
```

**근거 — 005의 계약이 이미 요구한다**(`engine-port.ts` E1):

> **한 번에 하나만 열린다**(E1). `load()`가 이미 열린 것이 있으면 먼저 닫는다 —
> **GB 단위 모델 둘이면 기기가 죽는다.**

이것은 짐작이 아니라 **계약에 적힌 불변식**이며, 011이 그것을 어기면 005의 테스트가
깨진다. 게다가 SM-G986N은 메모리가 넉넉하지 않고, 캐릭터 모델이 1.1~1.6GB다.

**Rationale — 이 순서가 강제하는 것**:

- **캡션을 전부 만든 뒤에야 프롬프트를 만들 수 있다.** 스트리밍하듯 「캡션 하나 만들고
  일기 조금 쓰기」가 **불가능하다** — 다행히 그것은 005 FR-028b가 이미 금지한 것이다.
- **VLM 적재 비용을 5장이 나눠 진다.** 옆 저장소 실측에서 적재 1,046ms이고 장당
  1,856ms이므로, 5장이면 적재가 전체의 10% 남짓이다. **1장만 볼 때 적재 비용이 가장
  비싸다** — 5장이라는 상한이 이 점에서도 합리적이다.
- **실패 지점이 둘로 갈린다.** VLM 적재 실패와 캐릭터 모델 적재 실패는 사용자가 할 일이
  다르므로 파이프라인 단계가 나뉘어야 한다(→ 단계 `vision` 추가).

**⚠️ 관측되지 않은 위험**: VLM을 닫은 직후 캐릭터 모델을 여는 것이 **메모리 단편화로
느려지거나 실패할 수 있다.** 옆 저장소는 두 모델을 한 프로세스에서 연달아 열어 본
기록이 없다(캡션은 원격 서버, 일기는 폰이었다). **quickstart D3가 이것을 잰다.**

**Alternatives considered**:
- **두 모델을 동시에 열기** — E1 위반이며 기기가 죽는다. **버린다.**
- **VLM을 열어 두고 재사용** — 「다음 일기도 곧 쓸 테니」라는 유혹이 있으나, 캐릭터
  모델을 여는 순간 E1이 닫으므로 의미가 없다. **버린다.**

## §3. 「하루에 걸쳐 균일하게」를 어떻게 정의하는가

**Decision**: **시각 기준 균등 분위(quantile) 추출.** 사진을 찍힌 시각 순으로 놓고
`i = round(k * (n-1) / (limit-1))` (k=0..limit-1)로 골라, **가장 이른 것과 가장 늦은
것을 반드시 포함한다.**

**Rationale**:

- **004와 의도적으로 다르다.** `collect.ts`가 `usable.slice(0, limit)`으로 **이른
  시각부터** 자르는 것을 확인했다(2026-08-22 코드 확인). 그대로 쓰면 아침 사진 5장만
  보고 하루를 쓴다 — spec FR-007a가 이것을 금지한다.
- **양 끝을 포함하는 것이 중요하다.** 하루의 시작과 끝이 빠지면 「하루를 그린다」가
  성립하지 않는다. 분위 추출이 자연스럽게 양 끝을 준다.
- **결정적이다.** 시각·난수를 읽지 않으므로 같은 입력에 같은 답이 나온다 — 005의
  `buildPrompt()`가 결정적인 것과 같은 이유이며, 테스트가 성립한다.

**왜 「시간 구간을 5등분해 각 구간에서 하나」가 아닌가**: 사진이 몰려 있는 하루에서
빈 구간이 생겨 **5장을 채우지 못한다.** 저녁에만 10장 찍은 하루에서 2장만 고르게 되고,
그것은 있는 것을 못 본 것이다. **개수 기준 분위가 「있는 것 중에서 고르게」를 준다.**

**⚠️ 그 대신 받아들이는 것**: 저녁에만 찍은 하루는 고른 5장이 전부 저녁이다. **그것은
사실이므로 잘못이 아니지만**, 일기가 그것으로 하루 전체를 그리면 원칙 II 위반이다 —
그래서 FR-007b가 **고른 사진이 하루의 어느 때에 걸쳐 있는지**를 프롬프트에 싣는다.

**Alternatives considered**:
- **앞에서부터 5장** (004 방식) — FR-007a가 금지. **버린다.**
- **무작위 5장** — 결정적이지 않아 테스트가 성립하지 않고, 같은 하루를 두 번 쓰면 다른
  사진을 본다. **버린다.**
- **시간 구간 5등분** — 위 참조. **버린다.**

## §4. 「빠르게 봄」과 「자세히 봄」의 깊이를 무엇으로 조절하는가

**Decision**: `initMultimodal`의 **`image_max_tokens`**로 조절한다.
`quick` = 256, `detailed` = 1024. **보는 사진 수는 둘 다 5장으로 같다**(FR-019).

**근거**: §1에서 확인한 설치본 주석이 이 다이얼의 뜻을 직접 적었다 —
"Lower values reduce memory usage and improve speed for high-resolution images.
Recommended: 256-512 for faster inference, up to 4096 for maximum detail."

**Rationale**:

- **사진 한 장을 몇 개의 토큰으로 볼지**가 곧 「얼마나 자세히 보는가」다. 값이 크면
  모델이 사진의 세부를 더 많이 받는다.
- **캡션 프롬프트를 바꾸지 않는다.** 「자세히 써라」로 가르는 안도 있었으나, 그러면
  **모델이 아는 것 이상으로 길게 쓰라는 압력**이 되고 그것이 005가 관측한 지어내기의
  원인이다. 입력 쪽 다이얼을 돌리는 것이 안전하다.
- **`n_predict`도 함께 올리지 않는다** — 캡션의 길이 한도는 둘 다 같게 둔다. 세부를 더
  받았으면 같은 길이 안에서 더 구체적으로 쓰면 된다.

**⚠️ 두 값 256/1024는 짐작이다**(원칙 V). 주석의 권장 범위 안이라는 것이 유일한 근거이며,
**실제로 결과가 다른지는 quickstart D6이 확인한다.** 다르지 않으면 값을 벌린다.

**Alternatives considered**:
- **캡션 프롬프트를 다르게** — 위 참조. **버린다.**
- **`n_predict`로 캡션 길이 조절** — 길이는 깊이가 아니다. 길게 쓰라고 하면 없는 것을
  채운다. **버린다.**
- **보는 사진 수로 조절** — clarify에서 사용자가 「깊이」로 확정했고, 수로 가르면 상한이
  둘이 되어 「본 것이 전부인가」가 설정에 따라 달라진다(FR-007). **버린다.**

## §5. `n_ctx` 2048에 캡션 5줄이 들어가는가 — **처음으로 실재하는 위험**

**Decision**: `n_ctx` 2048을 **그대로 두고**, 캡션 한 줄의 길이 한도를 짧게 잡는다
(`n_predict` 64토큰). 넘치면 `context_full`이 나고 **판정이 이미 거부한다**(005의
`Ending`에 `context` 갈래가 있다).

**근거 — 실측과 계산**:

- 005 실기기 실측(2026-08-17): 205토큰 프롬프트, `n_ctx` 2048로 `context_full`이 **한 번도
  나지 않았다.** 다만 **그때는 캡션이 없었다.**
- 옆 저장소의 실제 캡션 예시가 얼마나 긴지 확인했다:
  ```
  "A man wearing a hat and a blue shirt is standing near a wooden gate."   (약 20토큰)
  "A girl stands on a deck overlooking a mountain and a river."            (약 15토큰)
  ```
  **한 줄이 20~30토큰이다.** 5줄이면 100~150토큰이고, 205토큰 프롬프트에 더해도
  **약 355토큰**으로 2048에 한참 못 미친다.

**Rationale**: 여유가 크므로 `n_ctx`를 올릴 이유가 없다. **올리면 KV 캐시가 메모리를
먹고 기기가 죽을 위험이 커진다**(`llama-port.ts` 주석이 이미 「둘이 맞물린 값」이라고
적었다).

**⚠️ 다만 캡션 길이에 한도가 필요하다.** 모델이 캡션을 문단으로 쓰기 시작하면 계산이
무너진다. `n_predict` 64토큰으로 묶는다 — **짐작이며**, 옆 저장소 캡션이 20~30토큰이니
2배 남짓의 여유다.

**⚠️ 사진이 많은 하루의 위험은 사라졌다** — 5장 상한이 그것을 막는다. 004의 200장은
메타데이터라 프롬프트에 「4장 (9시, 13시…)」한 줄로 요약되지만, 캡션은 장당 한 줄이므로
상한이 없으면 컨텍스트를 넘긴다. **FR-007의 5장이 이 위험도 함께 막고 있다.**

## §6. 사진 보는 모델의 출처 — **무엇을 옮기고 무엇을 안 옮기는가**

**Decision**: **LFM2.5-VL 450M Q8_0**을 쓴다. 본체와 mmproj **두 파일**을 받는다.

```
본체:   https://huggingface.co/LiquidAI/LFM2.5-VL-450M-GGUF/resolve/main/LFM2.5-VL-450M-Q8_0.gguf
mmproj: https://huggingface.co/LiquidAI/LFM2.5-VL-450M-GGUF/resolve/main/mmproj-LFM2.5-VL-450m-Q8_0.gguf
```

**⚠️ 대소문자가 다르다** — 본체는 `450M`, mmproj는 **`450m`**이다. 옆 저장소가
2026-08-10에 「대문자 URL은 404」임을 확인해 주석으로 남겼다. **이것을 놓치면 「내려받기가
안 된다」로 나타나고 원인이 URL이라는 것을 알기 어렵다.**

**근거 — 옆 저장소(`my-ollama`)의 2026-08-10 실측**:

| | SmolVLM 500M | **LFM2.5-VL 450M** |
| --- | ---: | ---: |
| 캡션 장당 (원격 GPU) | 3,798ms | **2,315ms** |
| 자기일치도 채택/탈락 | 7 / 1 | **8 / 0** |

**그리고 같은 기기(SM-G986N)의 폰 실측**(`results/vlm-smoke/s20p-lfm25/`):
LFM2.5-VL 450M으로 **사진 8장 24/24 성공**, **적재 1,046ms**, 장당 첫 캡션
1,474~2,180ms(평균 약 1,856ms). → **5장이면 약 10초.**

**후보: SmolVLM 500M**. 같은 체급이며 동작이 확인됐다. **실행 중 대체가 아니라 사람이
바꿔 넣는 기록이다**(003 FR-035가 대체 경로를 금지한다).

**뺀 것: LFM2.5-VL 1.6B** — 구체성이 가장 높았으나(4.12) 2.4배 느려 폰 예산 밖이다.

### ★ 옮기지 않는 것 — 원칙 IV의 경계

| 옮긴다 | 옮기지 않는다 |
| --- | --- |
| 어느 모델을 쓰는가 (URL·파일명) | 캡션 품질 점수 (3.62 대 3.31) |
| 5장이 약 10초라는 사실 | 자기일치도·환각률 표 |
| mmproj 대소문자 함정 | 「캡션이 일기 품질을 올리는가」의 결론 |

**003이 캐릭터 로스터의 URL을 같은 저장소에서 옮겨 온 선례를 따른다.** 옮기는 것은
**결과**이지 재는 장치가 아니다(헌법 원칙 IV: 「별도 저장소에서 수행하고 이 저장소에는
그 결과만 들여온다」).

**md5는 비워 둔다** — 003의 `roster.ts`가 그랬듯 **첫 내려받기에서 채록한다**(FR-031).
미리 적는 지문은 어디서 왔든 짐작이다(원칙 V).

## §7. 캡션의 샘플링을 어디에 두는가 — **설계 중에 찾은 함정**

**Decision**: **`src/inference/sampling.ts`의 `SAMPLING`을 재사용하지 않는다.**
캡션용 값을 `src/vision/`에 따로 둔다.

**왜 이것이 함정인가**: `sampling.ts`는 「온디바이스와 데스크톱이 공유하는 유일한 자리」
이며, 헌법 원칙 I의 「동일한 샘플링 파라미터」를 지키는 장치다. **캡션이 그 값을 같이
쓰면**, 나중에 캡션을 위해 `temperature`를 낮추는 순간 **일기 생성의 파라미터가 함께
바뀐다.** 원칙 I의 보증이 조용히 깨지는 경로다.

**그리고 값이 실제로 달라야 한다**: 옆 저장소가 2026-08-10에 **세 VLM 모두 온도 0.1이
0.7을 이겼다**고 기록했다(자기일치도 0.283 → 0.789). 일기는 `temperature` 0.8인데
캡션은 낮아야 한다 — **성격이 정반대다.** 일기는 감상이고 캡션은 관찰이다.

**Decision 값**: `temperature` 0.1, `n_predict` 64. **전자는 옆 저장소 실측 근거가 있고
후자는 짐작이다**(§5).

**⚠️ 그래도 원칙 I을 어기지 않는가**: 어기지 않는다. 원칙 I이 요구한 것은 「엔드유저가
읽는 일기」가 온디바이스와 데스크톱에서 같은 파라미터로 생성되는 것이다. **캡션은 일기가
아니라 일기의 입력이며**, 데스크톱 경로가 열릴 때 캡션도 같은 값을 쓰면 된다. 그래서
캡션 값도 **한 자리에만 둔다** — 같은 구조를 한 겹 아래에서 반복한다.

## 미해결로 남기는 것 (원칙 V)

**짐작이며 실기기에서 확인해야 한다.** quickstart가 각각을 잰다:

| 값 | 지금 | 성질 | 어디서 잰다 |
| --- | --- | --- | --- |
| `image_max_tokens` 256 / 1024 | 짐작 | 주석의 권장 범위 안이라는 것뿐 | D6 |
| 캡션 `n_predict` 64 | 짐작 | 옆 저장소 캡션이 20~30토큰 | D2 |
| 5장 ≈ 10초 | **옆 저장소 실측** | 이 저장소에서 재지 않았다 | D1 |
| VLM 닫고 캐릭터 모델 열기 | **미관측** | 메모리 단편화 위험 | D3 |
| 캡션 언어 (영어로 나온다) | **옆 저장소 실측** | 한국어 프롬프트에 영어 캡션이 섞인다 | D7 |

### ⚠️ 캡션이 영어로 나오는 것이 문제가 될 수 있다

옆 저장소의 캡션 예시가 전부 영어다(`A man wearing a hat…`). 그리고 그 저장소가
**gemma3·qwen3에서 「캡션의 영어 어휘를 그대로 옮긴다」(`Snowfall`, `Straw`,
`smelled했다`)**를 관측했다.

**이것은 관측이지 이 기능의 결정이 아니다.** 캡션을 한국어로 뽑을지, 영어로 두고 캐릭터
모델이 옮기게 할지는 **D7에서 실제로 보고 정한다** — 지금 정하면 짐작이다. spec의
FR-013(캐릭터와 무관하게 같은 방식)은 어느 쪽이든 지켜진다.
