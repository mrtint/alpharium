## R1 — 지우기가 쓰는 중을 멈추는 길: 홈에 요청을 내려보내고 멈춘 뒤 지운다

- **Decision**: `AppFrame`이 지우기 요청 토큰(`wipeRequest: number`)을 `DiarySection` → `DiaryHomeScreen`으로 내려보낸다. 홈은 토큰이 바뀌면
  (1) 쓰는 중이면 054 `cancel`과 같은 방식(`cancelled = true` → `stop()`)으로 멈추고 (2) **도는 생성의 `Promise`(`inFlight` ref)가 끝날 때까지 기다린 뒤**
  (3) `onWipeReady(token)`을 부른다. 쓰는 중이 아니면 곧바로 부른다. `DiarySection`이 홈을 그리지 않는 갈래(조립 실패 `build-error` 등)에서는
  `DiarySection`이 곧바로 `onWipeReady`를 부른다(응답이 안 와 지우기가 영영 멈추지 않게).
  홈은 마운트 때 받은 토큰에는 응답하지 않으므로(HS4) 기다리는 사이 `DiarySection`이 다른 이유로 다시 마운트되면 응답이 오지 않는다. 다시 마운트되는
  다른 경로는 040 `autoGeneratedToken`뿐이고 그것은 첫 실행 단계(`DiarySection`이 그려지지 않고 설정에 닿을 수 없는 동안)에서만 오른다 — 지우기와 겹치지 않는다.
- **Rationale**: 쓰는 중 상태의 주인은 홈이고 멈춤은 054가 검증한 경로다. 홈을 다시 마운트하는 것만으로는 생성이 멈추지 않는다 — 지운 뒤에 저장된다
  (설계 문서). `stop()`은 거부시키지 않고 `interrupted`로 정상 resolve되므로(AGENTS) `pipeline.run`의 `Promise`를 기다리면 저장 여부가 확정된다. 파이프라인은
  자기 `finally`에서 화면 잠금을 놓으므로, 기다린 뒤에는 잠금도 풀려 있다(R3의 전제).
- **Alternatives**: 파이프라인을 `AppFrame`으로 끌어올리기(054·057 계약 재작성 — 범위 밖), 멈추지 않고 지우기(틀림).

## R2 — 지우기 조립 `wipeDiaries` (`src/app/wipe-diaries.ts`)와 순서

- **Decision**: 순수 조합 함수 하나가 주입받은 통로로 다음 순서를 지킨다:
  1. 쓰기 잠금 얻기(`acquireLock(lockPort, "screen", nowMs)`). 못 얻으면 `{ kind: "busy" }`로 끝 — 아무것도 건드리지 않는다.
  2. 알림 확인 기록을 읽어 그 id들을 기억한다(트레이 거두기용).
  3. 일기 파일을 모두 지운다(`store.removeAll()`).
  4. 사진 리사이즈 사본 디렉터리의 파일을 모두 지운다.
  5. 알림 확인 기록을 비운다(`saveNotifiedState(port, {})`).
  6. 2의 id마다 `dismiss(id)` — 실패는 삼킨다(spec Edge Case).
  7. 잠금을 놓는다(`finally`).
  결과는 `{ kind: "wiped" } | { kind: "busy" } | { kind: "failed"; reason }`. 3~5 중 하나가 던지면 그 뒤를 멈추지 않고 끝까지 시도하되 결과는 `failed`다.
- **Rationale**: 잠금이 먼저여야 지우는 도중 백그라운드가 끼어들지 못한다(FR-016). 일기를 사진 사본보다 먼저 지운다 — 사본을 먼저 지우고 일기 지우기가 실패하면
  남은 일기가 「이 사진은 이제 없다」를 보이는 반쪽 상태가 된다. 알림 기록은 마지막이다(남아도 해는 「알림이 빠질 수 있다」뿐이다). 트레이 거두기는 부수 효과라
  실패가 지우기의 결과를 바꾸지 않는다.
- **Alternatives**: 각 단계를 화면 조립부(`App.tsx`)에 흩기 — 순서를 기기 없이 검증할 수 없다(057의 `resolveAutoWrite`와 같은 이유로 순수 조합으로 뗐다).

## R3 — 잠금 owner는 `"screen"`

- **Decision**: 지우기는 `"screen"` owner로 잠금을 얻는다. `STALE_LOCK_MS`(6분)를 넘긴 죽은 잠금은 020 `decideAcquire` 규칙대로 얻는다.
- **Rationale**: 화면에서 시작한 일이다. 잠금 파일의 owner는 stale 판정·`isMine`에만 쓰이고 새 owner 갈래를 늘리면 `LockRecord` 유니온이 넓어진다(tsc가 못 잡는
  넓힘 — AGENTS). R1 덕분에 이 시점의 화면 쓰기는 이미 끝나 잠금을 놓았다.

## R4 — 저장소 지우기 API: `DiaryStore.removeAll()`

- **Decision**: `DiaryStore`에 `removeAll(): Promise<void>`를 더한다. 파일 구현은 `fs.list()`에서 **일기 파일 이름(`YYYY-MM-DD.json`)과 그 임시 파일
  (`YYYY-MM-DD.json.writing`)만** 골라 `fs.remove(name)`으로 지운다 — 디렉터리를 통째로 지우지 않는다. `FileSystemPort`에 `remove(name): Promise<void>`(없으면 조용히)를
  더한다. 메모리 구현은 `Map`을 비운다. 하나라도 실패하면 나머지를 시도한 뒤 첫 오류를 던진다.
- **Rationale**: 파일 이름이 곧 날짜 키라(contracts/storage.md) 「일기 파일」의 정의가 이미 `dayFromFileName`에 있다 — 같은 판정을 쓴다. 디렉터리를 통째로 지우면
  `diary/` 안에 미래에 생길 다른 파일까지 지운다. 읽을 수 없는 파일도 이름이 일기면 지운다(spec Edge Case). 하루 지우기(`remove(day)`)는 이 조각 범위 밖이다(spec).
- **Alternatives**: `remove(day)`를 더하고 조합에서 `listDays()`를 돌기 — 임시 파일(`.writing`)을 못 본다.
- **영향**: `DiaryStore`를 손으로 구현한 테스트 대역(`store.test.ts`·`diary-home-notification`·`written-day-home`)은 스프레드(`...base`)로 만들어 그대로 산다.
  `tsc`가 나머지를 짚는다(유니온·인터페이스를 넓힐 때 대역이 빠지면 오류).

## R5 — 사진 리사이즈 사본: 디렉터리 안의 파일을 모두 지운다

- **Decision**: `vision-cache` 안의 파일을 모두 지운다(디렉터리는 남긴다). 디렉터리 이름 상수 `VISION_CACHE_DIRECTORY`를 `on-device.ts`에서 export해 기기 통로가
  같은 값을 쓴다(값을 두 곳에 두지 않는다). 기기 통로는 `src/app/wipe-port.ts`(`expo-file-system`)에 둔다.
- **Rationale**: 이 디렉터리에는 저장된 일기가 참조하는 사본과, 캡션 뒤 쓰이지 않아 이미 지워졌어야 할 사본뿐이다(013 — 쓰이지 않은 사본은 정리된다; 이름이 결정론이라
  누적되지 않는다). 일기마다 `entry.photos[].resizedPath`를 읽어 골라 지우면 읽을 수 없는 일기의 사본이 남는다.
- **남는 위험**: 지우는 순간 018 미리 캡션(`captionDay`)이 돌고 있으면 그것이 지우기 뒤에 사본을 새로 만들 수 있다. 홈은 지운 뒤 다시 마운트되어 그 캡션 결과를 버린다 —
  그 사본은 아무도 참조하지 않는 파일로 남고, 같은 사진을 다시 읽으면 같은 이름으로 덮인다(013). 사진 원본의 사본일 뿐 일기 내용이 아니다. 미리 캡션까지 기다리면 지우기가
  수십 초 멈출 수 있어 기다리지 않는다.

## R6 — 알림: 확인 기록을 비우고 트레이의 알림을 거둔다

- **Decision**: `notified.json`의 엔트리 `notificationId`마다 `NotificationPort.dismiss(id)`를 부른 뒤 기록을 `{}`로 저장한다(R2 순서 — 읽기는 지우기 전, 거두기는 맨 끝).
  `dismiss`는 이미 있다(020).
- **Rationale**: 기록을 남기면 지운 날을 다시 썼을 때 `acknowledged: true`로 보여 완성 알림이 빠진다(`notify.ts` 2번 갈래) — clarify Q1의 근거.

## R7 — 「쓰는 모듈」 합계와 표기

- **Decision**: `src/app/module-size.ts`에 (a) 순수 `formatModuleBytes(bytes: number): string`(FR-004 — 1000 기준, ≥1GB면 소수 한 자리 GB, 아니면 정수 MB, MB 반올림이
  1000이면 「1.0GB」) (b) 조합 `readModuleBytes(files: Pick<ModelFilePort, "bytesUsed">): Promise<number>` — `ESSENTIAL_ASSET_KEYS` 각각의 `bytesUsed`를 더한다.
  조립부(`SettingsSection`)가 마운트 때 한 번 `expoModelPorts().files`로 읽어 문자열로 바꿔 넘긴다. 하나라도 던지면 `null`(값을 비운다, FR-005).
- **Rationale**: 키 셋(`v1`·`v2`·`a1`)이 같은 모델 디렉터리의 `<key>.bin`이고 `bytesUsed`가 받다 만 구간 파일까지 센다(041). `src/ui/`는 `ESSENTIAL_ASSET_KEYS`에 닿지 못한다
  (`UI_TOUCHES_ASSET`) — `src/app/`은 허용된다(`essential-assets-port.ts`가 같은 자리). 지금 예상 합 2,004,831,040바이트 → 「2.0GB」.
- **Alternatives**: 로스터의 `expectedBytes` 합 — 실제로 차지하는 공간이 아니다(받다 만 상태·옛 파일을 못 본다).

## R8 — 빨간 「지우기」 버튼: `danger` 면

- **Decision**: `DialogActionButton`에 `tone?: "accent" | "danger"`를 더한다(기본 `accent` — 기존 호출 무변경). `danger`면 면 `COLORS.danger`(#ae1800 = 보드 `accent-700`),
  글자 `COLORS.dangerForeground`(오프화이트, 대비 6.41:1). 새 색 0.
- **Rationale**: 보드 메모가 「지우기 버튼은 빨강」을 따로 적었다 — 다른 대화상자의 동작 버튼(accent #ec3013)과 같은 색이면 따로 적을 이유가 없다. 같은 묶음의 「일기 모두
  지우기」 라벨이 `accent-700`이므로 같은 빨강이 버튼에 이어진다. 대비도 accent(3.76:1)보다 낫다(AA 본문 충족). **저장소 소유자 확인 대상** — 구현 뒤 실기기 화면으로
  보이고, accent가 맞다고 하면 `tone`만 바꾼다.

## R9 — 0편·읽기 전·지우는 중의 행 모양

- **Decision**: `SettingsScreen`의 `Row`에 `labelTone?: "default" | "danger" | "muted"`와 `disabled?: boolean`을 더한다. 조립부가 마운트 때 `store.listDays()`로 편수를 세어
  `wipeEnabled = count !== null && count > 0 && !wiping`을 넘긴다. 비활성이면 라벨 `textMuted`, `Pressable` 대신 `View` + `accessibilityState={{ disabled: true }}`
  (RN `Pressable`의 `disabled={false}` 덮어쓰기 함정 — AGENTS — 을 피하려고 누를 수 없는 행은 `Pressable`을 쓰지 않는다).
- **Rationale**: clarify Q3. 지우는 동안(대화상자를 닫은 뒤 R1·R2가 끝날 때까지) 다시 누르지 못하게 같은 비활성 모양을 쓴다 — 진행 표시를 두지 않는다(spec Assumptions).

## R10 — 잠금에 막혔을 때의 한 줄 (FR-016a)

- **Decision**: 문구 「지금 자동으로 쓰는 중이라 지우지 못했어요.」(해요체, 보드에 없음 — `settings-text.ts`에 「보드 밖」으로 표시). 「일기 모두 지우기」 행의 보조 줄로
  `hintTone: "danger"`(057 `6g`와 같은 모양)로 그린다. 설정 겹이 닫히면(언마운트) 사라진다. 다시 누르면 지운다.
- **Rationale**: 설정에 머무는 동안 그 자리에서 이유를 본다. 057이 이미 만든 빨간 보조 줄 모양을 다시 쓴다(새 부품 0). 토스트는 홈(054)의 것이라 설정 위에서는 덮인다.

## R11 — 지운 뒤 홈

- **Decision**: `wiped`(또는 `failed`)면 `AppFrame`이 `goHome()`(설정·이름 바꾸기 겹 닫기) → `setChosenDay(dayOf(new Date()))` → `DiarySection`의 `key`를 올려 다시 마운트한다
  (040 `autoGeneratedToken`과 같은 방식으로 목록을 새로 읽는다). `busy`면 설정에 남는다(R10).
- **Rationale**: FR-015·FR-018. `failed`도 홈으로 간다 — 홈은 실제로 남은 일기를 보인다(지운 척하지 않는다). 다시 마운트는 미리 캡션·쓰는 중 잔여 상태를 함께 버린다.
- **주의**: 다시 마운트하면 홈의 `claimAutoWrite`(057)·자동 첫 일기가 다시 판정될 수 있다 — `claimAutoWrite`는 `AppFrame`의 ref로 한 실행에 한 번이라(057) 이미 쓴 실행이면
  다시 시작하지 않는다. 아직 안 쓴 실행이면 시도 창 안에서 지운 직후 앱 열기 자동 쓰기가 시작될 수 있다 — 057 규칙대로의 동작이며 이 조각이 막지 않는다(spec에 Edge Case로 적는다).
