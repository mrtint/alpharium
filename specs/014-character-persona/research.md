# Research: 캐릭터 페르소나

## R1 — 이름·소개는 어디에 두는가

**Decision**: `src/diary/persona.ts`(신규)에 `Character → { name: string, tagline: string }`
단일 매핑을 둔다.

**Rationale**: 003의 `roster.ts` 주석이 이미 "표시 이름과 설명 문안이 없다(FR-004a,
FR-005c). 헌법이 '캐릭터 이름은 사람이 짓는다'고 했고... 그 관측은 이 저장소의 몫이
아니다(원칙 IV)"라고 적어 두었다. 이제 그 관측(로드맵 문서에 이미 확정된 값)이
생겼으므로 넣을 자리가 필요하다.

**두 후보를 검토했다**:
1. `roster.ts`에 표시용 필드를 추가한다.
2. 완전히 새 파일 `persona.ts`를 둔다.

(1)을 버린 이유: `roster.ts`는 "이 저장소 전체에서 캐릭터→모델 매핑이 있는 유일한
자리"(주석)이며, 007이 세운 헌법 검사 규칙(`UI_TOUCHES_MODEL`)이 `src/ui/`가 이
파일에 닿는 것 자체를 막는다. 이름·소개는 화면(`src/ui/`)이 반드시 읽어야 하는
값인데, `roster.ts`에 두면 화면이 그 파일을 import해야 하고 그러면 헌법 검사를
우회하거나 예외를 둬야 한다 — "예외를 두면 다음 화면이 그 틈으로 들어온다"는 007의
경고와 정확히 같은 함정이다.

(2)를 택한 이유: `persona.ts`는 `Character`(문자열 리터럴 타입)만 알고 `ModelAsset`을
모른다. `src/ui/`가 이 파일을 import해도 헌법 검사(`UI_TOUCHES_MODEL`/`UI_TOUCHES_ASSET`
정규식)에 걸리지 않는다 — 애초에 이 파일이 모델 자산 관련 식별자를 담지 않으므로
정규식이 매치할 대상이 없다.

**Alternatives considered**: `diary/types.ts`에 상수로 추가하는 것도 검토했으나,
`types.ts`는 타입 정의 전용이고 003 이후 이 저장소의 관례상 상수·로직은 별도 파일에
둔다(예: `prompt.ts`가 `SPEAKER_RULES`를 갖듯). 파일을 나누는 것이 관례에 맞다.

## R2 — 제목을 어떻게 얻는가 (프롬프트 형식과 파싱 규칙)

**Decision**: 프롬프트가 "첫 줄에 제목만, 빈 줄, 그다음 본문"을 지시한다. 파싱은
`extractTitle(text: string): { title?: string; body: string }` 순수 함수가
`\n\n`(빈 줄)으로 텍스트를 앞/뒤로 나누고, 앞부분이 40자 이하 한 줄이면 제목으로
채택한다. 그렇지 않으면(빈 줄이 없거나, 첫 부분이 너무 길거나, 여러 줄이면) 전체를
본문으로 두고 제목은 없다.

**Rationale**: 005가 이미 "판정은 평문 문자열 하나로 한다"(`buildPrompt()`가 단일
문자열 반환)는 원칙을 세웠고, 이 기능이 그 위에 제목 지시를 얹는 것은 자연스럽다.
40자 상한은 "제목이 본문 전체를 잘못 삼키는 것"(모델이 빈 줄을 안 넣고 계속 쓴
경우 첫 줄이 사실은 본문 일부일 수 있다)을 막기 위한 안전장치이지 품질 기준이
아니다 — 판정에 쓰이지 않고(judge()는 이 함수를 전혀 모른다) 오직 "이것이 제목
모양인가"를 가르는 형식 검사다.

**★ 원칙 IV와의 경계를 명확히 한다**: 40자라는 값 자체는 acceptance.ts의
`MIN_ECHO_LENGTH`(12자)와 같은 성격의 "임계값이 아니라 무엇을 제목으로 볼지 고르는
값"이다. `judge()`가 이미 통과시킨 텍스트를 사후에 형식적으로 나누는 것뿐이며,
그 결과로 일기가 거부되는 일은 없다(FR-009) — 제목을 못 떼면 그냥 `title: undefined`.

**Alternatives considered**:
- 구분자를 마크다운 헤더(`# 제목`)로 지시하는 것: 다섯 모델이 마크다운을 얼마나
  안정적으로 따르는지 실측이 없어 위험이 크다. 빈 줄 구분이 더 자연스러운 텍스트
  형식이다.
- JSON으로 `{"title": ..., "body": ...}`를 요구하는 것: 005의 "채팅 템플릿·messages
  배열을 쓰지 않는다"(프롬프트는 평문 하나) 원칙과 어긋나고, 파싱 실패 시 전체를
  버려야 하는 위험이 크다(FR-009 "떼기 실패는 거부가 아니다"를 지키기 어려워진다).
- **미확인 사항** (quickstart에서 실기기로 확인할 것): 40자 상한이 다섯 캐릭터 모두에서
  적절한지, 특히 `narrative`(길게 쓰는 캐릭터)가 제목도 길게 쓰는 경향이 있는지는
  실측 전이라 짐작이다(헌법 원칙 V) — quickstart D2가 이것을 본다.

## R3 — 지어내기 교정 문구를 어떻게 바꾸는가

**Decision**: 기존 `SPEAKER_RULES`(005~006이 이미 "본 것만 써라", "기록이 적으면
짧게 써라", "짐작은 해도 된다", "구체적 예"를 추가해 온 것)에 한 줄을 더한다 —
"확실하지 않은 것은 '~인 것 같다', '~였을지도 모른다'처럼 짐작의 말투로 써라. 있었다,
했다처럼 단정하는 말투는 실제로 본 것에만 써라." 이것은 006이 이미 배운 것("길이
압력이 지어내기의 원인")과 다른 축 — "짐작과 단언을 언어적으로 구분하는 법을
모델에게 직접 알려준다"는 접근이다.

**Rationale**: AGENTS.md의 관측(005·007·011)을 다시 읽으면, 위반의 공통 패턴은
"짐작해도 될 만한 것을 단정형 어미로 썼다"는 것이다("~것 같다"로 썼다면 위반이
아니었을 문장이 "~했다"로 쓰여 위반이 됐다 — 012 quickstart 기록의 "잠시 바깥을
걷다가 돌아왔음을 느낄 수 있을 뿐이다"는 성공 사례, 007의 "알람 소리를 들었다"는
실패 사례). 기존 문구는 "무엇을 쓸지"는 말했지만 "어떻게(어떤 어미로) 쓸지"는
명시하지 않았다.

**Alternatives considered**: 위반 예시를 더 늘리는 것(006의 접근을 반복)도 검토했으나,
AGENTS.md가 이미 "005·006·007에서 위반이 반복됐다"고 기록하고 있어 예시를 더
쌓는 것만으로는 한계가 보인다는 판단이다. 어미 통제라는 새로운 각도를 시도한다.
**이 결정 자체가 짐작이며 실기기로 검증해야 한다**(SC-003) — 효과가 없으면 후속
관측으로 남긴다.

## R4 — 진단 화면 모델 이름 표시 구조

**Decision**: `roster.ts`에 `displayName(character: Character): string`을 추가한다.
`diagnostics/report.ts`의 `collectReport()`가 이것을 호출해 `DiagnosticReport`에
`characterModels: Readonly<Record<Character, string>>` 필드로 담는다.
`DiagnosticsScreen`은 그 필드를 그리기만 한다.

**Rationale**: 로드맵 문서가 이미 이 구조를 설계해 두었다("구조가 이미 맞다.
`DiagnosticsScreen`은 props를 받지 않고 `collectReport()`가 준 것을 그린다"). 007이
세운 `src/ui/`의 `roster.ts` 직접 접근 금지 규칙을 이 구조가 자연스럽게 지킨다 —
`report.ts`는 `src/diagnostics/`에 있고 `src/ui/`가 아니므로 애초에 그 규칙의 대상이
아니다.

**표시 이름 값**: `roster.ts`의 기존 실측 주석(`kanana-1.5-2.1b`, `exaone-3.5-2.4b`
등)에서 이미 확정된 모델명 문자열을 그대로 옮긴다 — 새로 짓지 않는다.

**Alternatives considered**: 화면이 직접 `roster.ts`를 import하는 안은 007의 헌법
검사 규칙과 정면으로 부딪혀 기각.

## R5 — 판정(`judge()`)과 제목 분리의 순서

**Decision**: `judge()`는 전체 텍스트(제목+본문)를 받아 지금과 완전히 동일하게
판정한다. `extractTitle()`은 `judge()`가 `{ ok: true }`를 반환한 **이후**,
`pipeline.ts`에서만 호출된다.

**Rationale**: spec의 Edge Case("아주 짧은 응답은 어떻게 판정되는가? → 기존 `empty`
판정이 전체 텍스트 기준으로 그대로 적용된다")가 이미 답을 정했다. `judge()`가
제목을 알면 "제목만 있고 본문이 비었다"같은 새 판정을 하고 싶은 유혹이 생기고,
그것이 다섯 번째 거부 갈래로 자라는 시작점이다(원칙 IV). `judge()`의 시그니처를
전혀 바꾸지 않는 것이 이 압력을 원천 차단한다.

**되뱉기 판정(`isEcho`)과의 상호작용**: 이름을 프롬프트에 추가하면
(`SPEAKER_RULES` 확장) `instructionLines()`가 반환하는 지시문 목록도 늘어난다.
`isEcho()`는 부분 문자열 포함 여부만 보므로(변경 없음), 이름을 담은 새 지시문
줄도 12자 이상이면 자동으로 되뱉기 검사 대상이 된다 — 별도 배선이 필요 없다.

## R6 — `DiaryEntry.title`이 기존 저장 파일과 호환되는가

**Decision**: `title?: string` (옵셔널). `store.ts`의 `load()`는 JSON을 파싱해
`DiaryEntry`로 캐스팅하는 구조이므로, 필드가 없는 기존 파일도 `title: undefined`로
자연스럽게 읽힌다 — 마이그레이션이 필요 없다.

**Rationale**: 006 이후 이 저장소의 관례(`VisionSetting`처럼 새 옵셔널 필드를
추가할 때 하위 호환을 타입 레벨에서 확보하는 방식)를 그대로 따른다. FR-010이 이미
이것을 요구한다.

**확인 필요(quickstart)**: 실제 JSON 파싱이 여분 필드 무시·누락 필드 허용을
문제없이 하는지는 `store.test.ts`에 기존 커버리지가 있는지 Phase 1에서 확인한다.
