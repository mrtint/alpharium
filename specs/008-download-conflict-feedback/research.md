# Phase 0 — Research: 내려받기 충돌을 사용자에게 알린다

**Date**: 2026-08-21 | **Plan**: [plan.md](plan.md)

원칙 V에 따라 **실측과 짐작을 갈라 적는다.** 「코드 확인」은 이 저장소의 소스를 직접
읽은 것이고, 「실기기 미확인」은 아직 기기에서 보지 않은 것이다.

---

## §1. 두 버그의 정확한 원인은 무엇인가

**Decision**: 화면과 배선의 결함이다. **`acquisition.ts`는 손대지 않는다.**

**Rationale**: 소스를 직접 읽어 원인을 짚었다(2026-08-21, 코드 확인).

### 버그 ① — 거부가 사용자에게 닿지 않는다

[App.tsx:292-298](../../App.tsx#L292-L298):

```ts
const onPrepare = useCallback(
  async (character: Character) => {
    await acquisition.prepare(character, setProgress);   // ← 반환값을 버린다
    setProgress(null);
    await refresh();
  },
  [acquisition, refresh],
);
```

`prepare()`는 `{ ok: false, failure: { kind: "busy", busyWith } }`를 **정확히 돌려주는데**
호출자가 `await`만 하고 값을 받지 않는다. 그래서 `busy`가 화면까지 갈 통로가 **아예
없다.** 사용자에게는 「눌렀는데 아무 일이 없다」로 보인다.

**003이 만들어 둔 것은 멀쩡하다** — `DownloadFailure`에 `busyWith`가 캐릭터로 실려 있고
(types.ts:165), 테스트 A15가 그것을 확인한다(acquisition.test.ts:276). **끊긴 곳은
마지막 한 칸이다.**

### 버그 ② — 「멈춘 것처럼 보이지만 실은 갇힌 것」

사용자는 「quiet이 멈춘다」고 적었으나 **실제로는 멈추지 않는다.** 세 줄이 겹쳐 일어난다:

1. [App.tsx:295](../../App.tsx#L295) — `setProgress(null)`이 **거부된 요청에서도** 돈다.
   `busy` 거부는 네트워크를 타지 않고 즉시 반환되므로 **곧바로** 진행률이 지워진다.
2. [CharacterListScreen.tsx:104](../../src/ui/CharacterListScreen.tsx#L104) —
   `const busy = progress?.character === character`. 진행률이 `null`이 되면 **어느 줄도
   busy가 아니다.**
3. [CharacterListScreen.tsx:110-115](../../src/ui/CharacterListScreen.tsx#L110-L115) —
   「멈추기」 버튼은 `busy`인 줄에만 뜬다. **그래서 함께 사라진다.**

그런데 `acquisition.ts`의 `running`은 그대로다(A16 테스트가 「거부되어도 받던 것은
계속된다」를 확인한다). **quiet은 계속 받고 있고 자리도 계속 잡고 있다.**

결과가 **빠져나갈 수 없는 상태**다:

| 사용자가 원하는 것 | 화면이 주는 것 |
| --- | --- |
| 받는 중인지 알기 | 진행률이 없다 |
| 멈추기 | 버튼이 없다 |
| 다른 것 받기 | 계속 거부당한다(안 보이는 것이 자리를 차지) |

**003 FR-020a가 약속한 「멈추면 새 요청이 통한다」가 화면에서 실행 불가능해진다.**
계약은 지켜졌는데 화면이 그 길을 지웠다.

**Alternatives considered**:

| 대안 | 기각 이유 |
| --- | --- |
| `acquisition.ts`에서 앞의 것을 취소하고 바꿔치기 | 003이 명시적으로 기각한 설계다(acquisition.ts 주석: 「앞의 것을 취소하고 바꿔치기하지 않는다」). 받던 GB 파일이 사용자 의사 없이 버려진다 |
| 동시 내려받기 허용 | 003 FR-020을 뒤집는 것이며 spec의 범위 밖. 계약을 먼저 고쳐야 한다 |
| 화면에서 `busy`를 미리 막기(받는 중이면 다른 버튼을 비활성) | **경합을 못 막는다** — 화면의 판단과 `running`의 실제가 어긋날 수 있고, 그때 사용자는 「왜 눌리지 않지」를 묻는다. 거부는 여전히 일어날 수 있으므로 알리는 길이 어차피 필요하다. 다만 **보조 수단으로는 유효하다**(§4) |

## §2. ★ 셋째 결함을 찾았다 — 탭을 옮기면 `Acquisition`이 통째로 사라진다

**Decision**: `Acquisition` 인스턴스를 **탭보다 오래 사는 자리로 올린다.**

**Rationale**: spec FR-013(화면을 오가도 진행 표시가 보인다)·FR-014(화면을 떠나도
내려받기가 계속된다)를 검토하다 **spec을 쓸 때 몰랐던 것**을 찾았다(2026-08-21, 코드 확인).

[App.tsx:88-95](../../App.tsx#L88-L95)가 탭을 **삼항 연산자로** 가른다:

```tsx
{tab === "diary" ? (
  <DiarySection … />
) : (
  <ScrollView><ModelSection /></ScrollView>
)}
```

**두 갈래가 서로 다른 컴포넌트이므로 탭을 옮기면 `ModelSection`이 언마운트된다.**
그런데 [App.tsx:236](../../App.tsx#L236)에서:

```ts
const [acquisition] = useState(() => createAcquisition(ports));
```

**`Acquisition`이 `ModelSection`의 지역 상태다.** 언마운트되면 인스턴스가 사라지고,
그와 함께:

- **`running`이 사라진다** — 다시 돌아오면 새 인스턴스가 만들어져 `busyWith()`가 `null`이다
- **`handle`이 사라진다** — 멈출 방법이 없어진다
- 진행 콜백이 향하던 `setProgress`가 죽은 컴포넌트를 가리킨다

**⚠️ 이것은 spec이 「지금 동작」이라고 가정한 것과 다르다.** spec Assumptions에
「화면 밖으로 나가도 내려받기가 이어지는 것은 지금 동작이다」라고 적었는데, **확인해
보니 근거가 없다.** `expo-file-system`의 `DownloadTask`가 JS 객체와 별개로 살아남는지는
**실기기에서 재지 않았고**(원칙 V), 설령 네이티브 전송이 계속되더라도 **앱이 그것을
붙잡을 손잡이를 잃는다.**

**그래서 FR-013·FR-014는 「깨지 않기」가 아니라 「고치기」다.** 이 발견이 없었다면
탭 왕복 테스트가 실패했을 때 원인을 엉뚱한 데서 찾았을 것이다.

**어디로 올리는가**: `AppFrame`이다. 탭 상태(`tab`)를 가진 바로 그 컴포넌트이며,
**탭이 바뀌어도 언마운트되지 않는다.** `ports`와 `acquisition`을 여기서 만들어
`ModelSection`에 내린다.

**Alternatives considered**:

| 대안 | 기각 이유 |
| --- | --- |
| 두 탭을 모두 마운트하고 `display:none`으로 감추기 | 일기 탭이 파이프라인·모델을 들고 있어 메모리와 초기화 비용이 크다. 안 보이는 화면이 계속 도는 것도 원치 않는다 |
| 모듈 수준 싱글턴(`const acquisition = createAcquisition(...)`) | 모듈 로드 시점에 `expoModelPorts()`가 불려 **기기 통로가 없는 환경에서 터진다.** 지금 구조가 `useState(() => …)`로 지연 생성하는 이유가 그것이다 |
| React Context | 소비자가 하나뿐이라 Context가 주는 것이 없다. props 한 칸으로 충분하다 |
| 전역 상태 라이브러리 | 새 의존. spec이 새 의존 0개를 전제한다 |

**Risk**: `AppFrame`이 `ports`를 만들게 되면 **일기 탭에서도 `expoModelPorts()`가 불린다.**
지금은 캐릭터 탭에 처음 들어갈 때 불린다. `expo-port.ts`가 무거운 일을 하는지 확인이
필요하다 — 게으르면 문제없고, 아니면 지연 생성을 유지해야 한다. **Phase 1에서 확인한다.**

## §3. 「무엇을 보일 것인가」를 어디서 정하는가

**Decision**: `src/models/download-view.ts`에 **순수 함수 하나**를 둔다. 화면은 그리기만
한다.

**Rationale**: 007이 같은 문제를 `resolveSelection()`으로 풀었고 그 판단이 옳았다 —
「옮김」 규칙 전체가 기기 없이 검증됐다(007 research §7). 여기서도 같은 것이 필요하다:

판정해야 할 것이 **화면 상태의 조합**이라 화면에 두면 검증이 렌더링에 묶인다:

- 이 줄이 받는 중인가? (진행 중인 캐릭터와 같은가)
- 거부 안내를 보일 것인가? (거부가 있고, 아직 참인가)
- 거부가 언제 참이 아니게 되는가? (받던 것이 끝나거나 멈추면)
- 거부당한 줄은 어떻게 보이는가? (받는 중이 **아니다** — FR-010)

**특히 「거부가 아직 참인가」가 순수 함수여야 한다.** 「받는 중이라 거부했다」는 안내는
받던 것이 끝나는 순간 거짓이 된다(FR-005, spec Edge Case). 이것을 화면의 `useEffect`로
지우려 하면 타이밍 버그가 들어오고, 그 버그는 기기에서만 보인다.

**입력이 전부 이미 있는 타입이다**: `DownloadProgress | null`(받는 중인 것)과
거부 통지. **새 포트도, 새 의존도 필요 없다.**

**⚠️ 원칙 IV의 방어를 여기서 지킨다.** 이 함수의 출력에 시간·속도·바이트를 담을 자리를
만들지 않는다. 007의 `ActivityIndicator`가 「담고 싶어도 담을 자리가 없어서」 방어가 된
것과 같은 구조를 의도적으로 만든다.

**Alternatives considered**:

| 대안 | 기각 이유 |
| --- | --- |
| 화면 안에서 `useMemo`로 판정 | 기기 없는 검증이 렌더링에 묶인다. 007이 이미 겪고 떼어냈다 |
| `acquisition.ts`에 넣기 | 그 파일은 **내려받기를 하는 것**이지 화면이 무엇을 보일지 아는 곳이 아니다. `busyWith()`까지가 그쪽의 몫이다 |
| 판정 없이 화면이 조건문을 늘리기 | 지금이 그 상태이고 그래서 버그가 났다 |

## §4. 거부 안내를 어떻게 보이는가

**Decision**: **캐릭터 목록 화면 안의 글**로 보인다. 목록 위쪽 한 자리에 하나만.

**Rationale**: spec Assumptions가 「시스템 알림이나 팝업이 아니라 화면 안의 글」로
가정했고, 근거는 **앱의 다른 안내가 전부 그러하다**는 것이다 — 007의 「quiet을(를) 쓸
수 없어 narrative(으)로 바꿨다」도 화면 안의 글이다.

**`Alert.alert()`를 쓰지 않는 이유**:

- **Maestro가 시스템 대화상자를 다루기 까다롭다.** 007에서 Maestro의 매칭이 이미
  두 번 걸렸다(부분 문자열, 화면 밖 요소). 검증하기 어려운 쪽을 고를 이유가 없다
- **모달이 사용자를 막는다.** FR-003이 「멈추면 됩니다」라고 안내하는데, 모달을 닫아야
  멈추기 버튼에 닿는다면 안내와 행동 사이에 벽이 하나 생긴다
- 007의 「옮김」 안내와 **모양이 달라진다** — 같은 성질의 것은 같게 보이는 편이 낫다

**하나만 보이는 것**(FR-006): 거부 통지를 **하나만 들고 덮어쓴다.** 목록으로 쌓으면
「세 번 눌렀으니 세 줄」이 되고 그것은 사용자가 원한 정보가 아니다.

**문구에 무엇이 들어가는가**(FR-002·FR-004):

- 들어간다: 받는 중인 **캐릭터 이름**(= 자리표시 식별자), 거부되었다는 것, 멈추면 된다는 것
- 들어가지 않는다: 파일 크기·주소·자산키·모델 식별자·남은 시간·속도·바이트

**Risk**: 문구를 쓰다 「quiet을 받는 중입니다 (2.1GB)」처럼 크기를 넣고 싶어진다.
**`src/ui/`가 `assetFor`에 닿을 수 없으므로 구조적으로 막힌다**(007이 세운 헌법 검사).
SC-004가 그것을 다시 확인한다.

## §5. 진행 표시를 어떻게 되찾는가 (FR-013)

**Decision**: 화면이 뜰 때 **`acquisition.busyWith()`에게 묻는다.** 진행률의 정확한
값은 다음 콜백에서 온다.

**Rationale**: `Acquisition`이 이미 `busyWith(): Character | null`을 공개한다
(acquisition.ts:70, 테스트가 확인). §2에서 인스턴스를 탭보다 오래 살게 만들면
**돌아왔을 때 물어볼 대상이 남아 있다.**

**⚠️ 백분율은 되찾을 수 없다.** `Acquisition`이 마지막 진행률을 들고 있지 않고,
`onProgress` 콜백으로 흘려보낼 뿐이다. 그래서 탭에서 돌아온 직후는:

- **받는 중이라는 것은 안다**(`busyWith()`가 캐릭터를 준다)
- **백분율은 아직 모른다** → **「받는 중…」으로 보이고 백분율 없이 시작한다**
- 다음 진행 콜백이 오면 백분율이 붙는다

**이것이 원칙 V에 맞다.** 모르는 백분율을 지어내지 않으며, 003이 이미 「서버가 총량을
주지 않으면 백분율 없이 보인다」를 만들어 두어 **표시할 모양이 이미 있다**
(`progressText()`의 `fraction === null` 갈래).

**Alternatives considered**:

| 대안 | 기각 이유 |
| --- | --- |
| `Acquisition`이 마지막 진행률을 기억하게 하기 | **더 간단해 보이지만 `acquisition.ts`를 고치게 된다.** 지금 그 파일은 옳고 테스트가 두껍다. 얻는 것(잠깐의 백분율)이 위험(검증된 파일 수정)보다 작다. **필요해지면 그때 연다** |
| 진행 상태를 `AppFrame`으로 올려 유지 | §2에서 `Acquisition`을 올리므로 진행 상태도 함께 올릴 수 있다. **실은 이쪽이 백분율까지 살린다** — Phase 1에서 이 선택을 확정한다. 이 항목의 「되찾기」는 그 경우에도 첫 진입·재시작을 위해 필요하다 |
| 기기에 진행률을 저장 | 앱이 죽으면 거짓이 된다. 003이 `running`을 메모리에만 둔 것과 같은 이유 |

**⚠️ 미해결로 남긴다 (Phase 1에서 정한다)**: 진행 상태(`DownloadProgress`)를
`AppFrame`으로 함께 올릴 것인가. 올리면 백분율이 탭 왕복을 넘어 살아남는다. 다만
`AppFrame`이 내려받기 상태를 알게 되므로 관심사가 섞인다.

## §6. 무엇을 어떻게 검증하는가

**Decision**: 판정 규칙은 **순수 함수 테스트**로, 화면은 **`@testing-library` 테스트**로,
갇히지 않는 것은 **Maestro 흐름**으로.

**Rationale**:

### ⚠️ `CharacterListScreen`에 device-free 테스트가 **하나도 없다**

2026-08-21 확인: `__tests__/ui/`에 `character-list.test.tsx`가 없다. 지금 이 화면을
건드리는 것은:

- `__tests__/models/boundaries.test.ts:51` — **소스 문자열을 읽어** import를 검사할 뿐
- `.maestro/model-acquisition.yml` — 실기기이고, **주소가 없어 실제 내려받기를 돌리지
  않는다**(그 파일 주석이 그렇게 적고 있다)

**이 기능이 그 화면을 크게 고치므로 테스트를 함께 세운다.** 없는 채로 고치면 회귀를
잡을 그물이 없고, 그것이 006·007에서 반복된 「조용히 통과하는 결함」의 조건이다.

### 실기기에서만 드러날 것

**007의 교훈이 그대로 적용된다**: 「타입 검사 통과 + jest 초록불」이 화면 통과가 아니다.
특히 §2의 언마운트 문제는 **기기 없는 테스트가 잡기 어렵다** — 탭 전환을 흉내 내야 하고,
`expo-file-system`의 실제 전송이 살아남는지는 기기에서만 안다.

**Maestro에서 조심할 것**(007 실측):

1. **부분 문자열은 정규식으로 준다** — `assertVisible: "받는 중"`이 「받는 중… 42%」와
   맞지 않는다. `.*받는 중.*`으로 준다
2. **조건을 좁게 잡는다** — dev 빌드에는 진단 패널이 함께 떠서 목록 밖의 글자가 조건에
   걸린다(007에서 「사진 접근」이 「사진.*」에 걸렸다)
3. **새 흐름은 `scripts/run-device-tests.mjs`의 `FLOWS`에 등록해야 돈다** — 등록하지
   않으면 초록불인데 아무것도 검증되지 않는다

### ⚠️ 실기기 검증에 실제 내려받기가 필요하다

**여기가 이 기능의 가장 큰 검증 위험이다.** 두 버그 모두 **받는 중일 때만** 나타나는데,
`model-acquisition.yml`은 「주소 없이도 참인 것만」 본다.

- 로스터에 주소가 채워진 캐릭터가 있는가? — **`quiet`은 실기기에서 실제로 받아졌다**
  (006·007 실측). 그러므로 **가능하다**
- **타이밍이 까다롭다**: 007에서 생성이 2.4초로 빨라 「그만두기」 블록이 SKIPPED로
  지나갔다. 내려받기는 그보다 훨씬 오래 걸리므로(GB 단위) **오히려 유리하다** — 받는
  중에 다른 것을 누를 시간이 넉넉하다
- **건너뛴 블록은 통과가 아니다**(원칙 V). SKIPPED가 나면 손으로 확인하고 기록한다

**Risk**: 내려받기를 실제로 돌리면 기기에 GB가 쌓이고 시간이 걸린다. **검증 뒤 지운다**
(003이 「지우기」를 만들어 두었다).
