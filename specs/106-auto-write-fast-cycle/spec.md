# Feature Specification: 자동 쓰기 빠른 주기(개발 빌드 전용)와 080 잔여 결함

**Feature Branch**: `106-auto-write-fast-cycle`

**Status**: Draft

## 근거와 원본

- 설계문서: `docs/superpowers/specs/2026-10-26-auto-write-fast-cycle-and-residuals-design.md` — 소유자 결정(2026-10-26)·설계·테스트·실기기 계획이 거기 있다.
- 로드맵 「백그라운드 자동 쓰기가 완주하지 못한다 — 안드로이드·iOS」의 할 일 5번(080에서 드러난 것)과, 같은 과제의 할 일 3번(OS가 스스로 깨운 잡을 본다)을 **확인할 수단**을 닫는다. 소크 자체의 결과(하룻밤 기록·iOS TestFlight 기록)는 이 기능의 완료 조건이 아니다.
- 배경: 자동 쓰기의 규칙(목표 시각·시도 창·쓸 차례 알림·완성 알림)은 모두 「하루」 단위라 한 번 시험하면 다음 날에야 다음 시험이 된다. 진단의 「자동 쓰기 지금 실행」은 설정 입력만 덮어 한 번 돌릴 뿐, OS가 스스로 깨운 잡·시도 창·쓸 차례 알림의 예약 시각을 지나지 못한다.
- 용어:
  - **빠른 주기** = 개발 빌드에서만 켤 수 있는 모드. 「하루」를 N분(주기)으로 줄여, 주기가 계속 돌며 같은 규칙을 반복해서 탄다.
  - **주기** = 자정 이후 분을 N분 단위로 자른 구간. 주기 번호는 날짜와 그날의 구간 순번으로 정한다. 마지막 주기는 자정에서 잘려 짧을 수 있다.
  - **테스트 날** = 오늘(고정).
  - **개발 환경** = 개발자 화면·진단이 보이는 환경(local·dev). 배포 환경(prod)과 구분한다.
  - **자동 쓰기 경로** = 백그라운드·앱 열기(057·082)·알림 누름(085). 셋 모두 같은 판정을 쓴다.
  - **「한 번」** = 앱 열기 자동 쓰기가 한 실행에서 한 번만 시작되게 하는 표식(082).

## Clarifications

### Session 2026-10-26 (소유자 결정, 설계 단계)

- Q: 범위는? → A: 로드맵 1번 과제의 5번 항목(080 잔여)과 빠른 주기 모드. iOS TestFlight 기록·하룻밤 소크는 이 모드가 만드는 수단일 뿐 완료 조건이 아니다.
- Q: 가속 방식은? → A: 타이밍 해석기 한 곳. 판정 함수에 시간 상수를 넘겨주는 모듈 하나를 둔다. 가상 시계 오프셋은 쓰지 않는다(미래 날짜 일기가 실제 데이터를 오염시킨다).
- Q: 반복은 어떻게? → A: 주기가 시작될 때 앱이 테스트 날의 일기를 자동으로 지워, 매 주기를 새 하루처럼 시작한다.
- Q: 주기 값은? → A: 프리셋 10분 / 30분 / 60분과 직접 입력(5~180분의 정수).
- Q: 테스트 날은? → A: 오늘로 고정. 따라서 창 밖 따라잡기(지난 날 대상) 규칙은 이 모드로 확인하지 못한다 — 기존 단위 테스트의 몫.
- Q: 080 잔여 ①~⑤는? → A: ① 모델 적재 동시 호출 경합은 고친다. ② 018 미리 준비는 걷는다. ③ 지운 날을 백그라운드가 다시 쓰는 것은 의도된 동작으로 닫는다. ④ iOS 합류 쓰기 실패 시 이어 쓰기를 고친다. ⑤ 「지우기 막힘」 문구를 사실에 맞춘다.

- Q: 앱 열기 자동 쓰기의 「한 번」은 주기가 바뀌면 다시 열리는가? → A: 다시 열린다(주기 리셋이 「한 번」도 다시 연다). 그래야 앞 상태 앱 하나로 10분 주기를 반복해 볼 수 있다. 배포 환경의 「한 번」 규칙은 그대로다. (추천 채택)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 빠른 주기를 켜 두면 폰을 두기만 해도 주기마다 자동 쓰기가 반복된다 (Priority: P1)

개발자는 개발 빌드에서 빠른 주기를 켜고(예: 30분) 폰을 둔다. 주기가 시작될 때마다 오늘의 일기가 지워져 새 하루처럼 시작하고, 자동 쓰기가 그 주기의 시도 창 안에서 평소와 같은 규칙으로 오늘 일기를 다시 쓴다. 개발자는 하루를 기다리지 않고 한 시간 안팎에 여러 번의 시도 결과를 읽는다.

**Why this priority**: 이 기능의 존재 이유다. 지금은 시험 한 번이 하루이다.

**Independent Test**: 판정·리셋·기록을 묶은 조립 테스트가 「리셋 → 쓰기 → 저장 → 다음 주기 리셋」을 한 바퀴 돌고, 기기에서는 30분 주기로 몇 주기 지난 뒤 시도 기록에 주기마다의 결과가 남는다.

**Acceptance Scenarios**:

1. **Given** 빠른 주기가 켜져 있고(주기 30분) 자동 쓰기가 켜져 있으며 오늘 일기가 없고 오늘 재료가 있다, **When** 주기 시작 뒤 시도 창 안에서 자동 쓰기를 판정한다, **Then** 오늘을 쓰기로 정한다.
2. **Given** 위에서 오늘 일기가 저장됐다, **When** 같은 주기의 남은 시간에 판정한다, **Then** 새 쓰기를 시작하지 않는다(이미 쓴 날).
3. **Given** 오늘 일기가 저장된 상태에서 다음 주기가 시작됐다, **When** 어느 자동 쓰기 경로든 판정에 들어간다, **Then** 판정 전에 오늘의 일기와 그 날의 알림 확인·건너뜀·따라잡기 기록이 지워지고, 오늘이 다시 쓸 날로 판정된다.
4. **Given** 주기 시작 뒤 시도 창(주기의 앞 절반) 밖이다, **When** 판정한다, **Then** 오늘을 쓰지 않는다(「목표 시각 근방이 아님」).
5. **Given** 빠른 주기에서 후보 날이 오늘 하나로 한정된다, **When** 지난 날이 안 쓴 상태로 있다, **Then** 자동 쓰기는 지난 날을 쓰지 않는다.
6. **Given** 안드로이드 잡이 주기마다 한 번도 깨지 않았다, **When** 주기가 끝난다, **Then** 그 주기는 시도 기록에 줄이 없는 채로 끝난다(이것도 관찰 결과).

### User Story 2 - 배포 빌드에는 아무 영향이 없다 (Priority: P1)

빠른 주기는 개발 환경에서만 효력이 있다. 배포 환경은 설정 파일이 기기에 남아 있어도 읽지 않고 평소 규칙(하루 한 번 목표 시각, 창 3시간, 후보 사흘)을 그대로 따른다. 배포 사용자의 일기는 어떤 경우에도 이 기능이 지우지 않는다.

**Why this priority**: 사용자 일기를 지우는 기능이 개발용으로만 존재한다는 약속이 깨지면 데이터 손실이다.

**Independent Test**: 배포 환경 판정 + 설정 파일이 켜진 상태에서 시간 규칙과 일기 목록이 종전과 같고 리셋이 일어나지 않는다. 환경을 판정하지 못한 경우도 같다.

**Acceptance Scenarios**:

1. **Given** 배포 환경이고 빠른 주기 파일이 켜진 채 남아 있다, **When** 자동 쓰기를 판정한다, **Then** 파일을 읽지 않은 것과 같은 결과(평소 규칙)이고 일기는 지워지지 않는다.
2. **Given** 빠른 주기 파일이 깨졌거나 모양이 다르다, **When** 개발 환경에서 판정한다, **Then** 꺼짐으로 읽는다(켜짐으로 채우지 않는다).
3. **Given** 환경을 판정하지 못했다(빌드 설정 오류), **When** 판정한다, **Then** 기록이 켜져 있어도 읽지 않는다 — 일기를 지우는 기능은 모르는 환경에서 동작하지 않는다(원칙 V).
4. **Given** 빠른 주기가 꺼져 있다, **When** 어느 환경에서든 판정한다, **Then** 결과는 이 기능이 없을 때와 같다(기존 판정·알림 테스트의 기대값이 바뀌지 않고 통과한다).

### User Story 3 - 주기 리셋은 오늘의 일기만 지우고 쓰기를 방해하지 않는다 (Priority: P1)

주기 리셋은 오늘 일기 하나와 그에 딸린 기록만 지운다. 다른 날의 일기는 건드리지 않는다. 쓰기가 살아 있는 동안에는 지우지 않는다. 모드를 켤 때 오늘 일기가 이미 있으면 지운다는 사실을 알리고 확인을 받는다.

**Why this priority**: 개발 기기라도 의도하지 않은 날의 일기가 지워지면 신뢰를 잃는다. 쓰는 도중 지우면 저장이 뒤섞인다.

**Independent Test**: 주기가 바뀐 상태에서 오늘 외 날의 일기가 남는 것, 쓰기가 살아 있으면 지우지 않는 것, 같은 주기에 두 번 지우지 않는 것을 판정 수준에서 본다.

**Acceptance Scenarios**:

1. **Given** 오늘 포함 여러 날의 일기가 있다, **When** 주기 리셋이 일어난다, **Then** 오늘의 일기만 지워지고 다른 날은 남는다.
2. **Given** 다른 쓰기(백그라운드·진단·앱 열기)가 살아 있다, **When** 주기가 바뀐다, **Then** 이번에는 리셋하지 않고 쓰기를 끊지 않는다.
3. **Given** 한 주기 안에서 이미 리셋했다, **When** 같은 주기에 다시 판정한다, **Then** 다시 지우지 않는다.
4. **Given** 오늘 일기가 이미 있다, **When** 개발자가 모드를 켠다, **Then** 확인창이 지운다고 말하고, 거절하면 모드가 켜지지 않는다.
5. **Given** 리셋이 일기를 지웠다, **When** 같은 날 쓴 일기의 완성 알림 확인 기록이 남아 있다, **Then** 그 기록도 함께 비워져 다음 쓰기의 완성 알림이 억제되지 않는다.

### User Story 4 - 쓸 차례 알림이 주기 시작에 걸리고 쓴 뒤 거둬진다 (Priority: P2)

빠른 주기에서 쓸 차례 알림은 다음 주기 시작 시각에 하나 걸린다. 오늘 일기가 저장되면 평소처럼 거둬지고 완성 알림만 남는다. 배터리 예외가 확인된 기기의 알림 지연은 주기를 넘지 않는다.

**Why this priority**: 알림 발화·지연이 로드맵이 확인하려는 대상이다(소유자가 고른 목적). 다만 쓰기 반복(US1)이 먼저다.

**Independent Test**: 알림 계획 순수 함수가 빠른 주기에서 다음 주기 시작 한 개를 낸다. 기기에서는 주기 시작에 알림이 뜨고 쓰기 저장 뒤 완성 알림만 남는다.

**Acceptance Scenarios**:

1. **Given** 빠른 주기이고 자동 쓰기가 켜져 있다, **When** 알림을 맞춘다, **Then** 다음 주기 시작 시각의 쓸 차례 알림 하나가 걸린다(7일치가 아니다).
2. **Given** 배터리 예외가 확인된 기기, **When** 알림 시각을 정한다, **Then** 지연은 평소 30분과 시도 창 길이의 절반 중 작은 값이다(알림 시각이 시도 창 안이다).
3. **Given** 주기 안에 오늘 일기가 저장됐다, **When** 맞추기가 돈다, **Then** 트레이에 남은 쓸 차례 알림이 거둬지고 완성 알림만 남는다.
4. **Given** 빠른 주기가 꺼져 있다, **When** 알림을 맞춘다, **Then** 종전과 같은 7일치 계획이다.

### User Story 5 - 개발자 메뉴에서 켜고 끄고, 진단에서 상태를 읽는다 (Priority: P2)

개발자 메뉴에 「빠른 주기」 구역이 있다. 켬/끔, 주기 프리셋(10·30·60분)과 직접 입력(5~180분), 지금 주기 번호와 다음 주기 시작 시각이 보인다. 진단 화면 머리에 「빠른 주기 켜짐 · 주기 N분」 한 줄이 있어, 시도 기록이 평소와 다른 까닭을 읽을 수 있다. 「자동으로 쓰기」가 꺼져 있으면 모드를 켜도 쓰지 않는다는 사실을 알린다. 한계(안드로이드 15분 하한, iOS 깨움은 OS 몫)가 화면에 적혀 있다.

**Why this priority**: 켜는 길이 없으면 쓸 수 없지만, 파일을 직접 쓰는 길로도 동작은 검증된다.

**Independent Test**: 화면 테스트가 구역의 상태·프리셋·입력 검증·확인창·알림 문구를 본다. 개발 환경이 아니면 구역이 보이지 않는다.

**Acceptance Scenarios**:

1. **Given** 개발자 메뉴가 켜진 개발 환경, **When** 「빠른 주기」 구역을 연다, **Then** 켬/끔·프리셋 세 개·직접 입력·지금 주기(`YYYY-MM-DD#순번` 형태의 식별자)·다음 주기 시작 시각이 보인다.
2. **Given** 직접 입력이 5 미만이거나 180 초과이거나 정수가 아니다, **When** 적용한다, **Then** 거부하고 이전 값을 유지한다.
3. **Given** 빠른 주기가 켜졌다, **When** 진단 화면을 연다, **Then** 머리에 「빠른 주기 켜짐 · 주기 N분」이 보인다. 꺼졌으면 그 줄이 없다.
4. **Given** 「자동으로 쓰기」가 꺼져 있다, **When** 모드를 켠다, **Then** 모드를 켜도 쓰지 않는다는 안내가 보인다(설정 토글은 바뀌지 않는다).
5. **Given** 배포 환경, **When** 개발자 메뉴를 연다, **Then** 이 구역이 없다.

---

### User Story 6 - 모델 적재가 동시에 불려도 모델이 둘 열리지 않는다 (Priority: P1)

앱 열기 쓰기·백그라운드·진단 수동 실행 같은 둘 이상의 호출이 거의 동시에 같은 모델 엔진을 열어도, 한 번에 하나만 열린다. 같은 캐릭터면 앞 호출이 연 것을 재사용하고 다른 캐릭터면 앞의 적재가 끝난 뒤 닫고 연다.

**Why this priority**: 기기 메모리를 GB 단위로 두 번 쓰면 앱이 죽는다. 빠른 주기가 쓰기 겹침을 자주 만들어 드러나기 쉬워진다.

**Independent Test**: 엔진 통로 대역으로 두 `load()`를 동시에 불러 네이티브 적재 호출 횟수와 열린 컨텍스트 수를 본다. 재현 테스트가 먼저 실패한다.

**Acceptance Scenarios**:

1. **Given** 아무것도 열려 있지 않다, **When** 같은 캐릭터로 `load()`를 동시에 두 번 부른다, **Then** 네이티브 적재는 한 번이고 둘 다 성공하며 같은 컨텍스트를 쓴다(뒤따른 호출은 이미 열린 것을 재사용한다).
2. **Given** 한 적재가 진행 중이다, **When** 다른 캐릭터의 `load()`가 온다, **Then** 앞의 적재가 끝난 뒤 그것을 닫고 새로 연다(동시에 둘이 열린 적이 없다).
3. **Given** 진행 중인 적재가 실패했다, **When** 뒤따르던 호출이 있다, **Then** 그 호출은 앞의 실패를 물려받지 않고 새로 시도한다(실패한 적재가 다음 호출을 막지 않는다).
4. **Given** 한 번에 하나만 열린다는 기존 규칙(E1·E2), **When** 이 변경 뒤 기존 엔진 테스트를 돌린다, **Then** 모두 통과한다.

---

### User Story 7 - 앱 열기 합류 쓰기가 실패해도 이어서 쓴다 (Priority: P2)

앱을 열었을 때 이미 도는 남의 쓰기(예: iOS에서 백그라운드가 같은 프로세스에서 쓰는 중인 쓰기)에 홈이 합류한다. 그 쓰기가 실패로 끝나면 홈은 같은 실행에서 한 번 새로 쓴다. 지금은 프로세스가 오래 살아 「한 번」을 이미 쓴 실행에서는 합류한 쓰기가 실패해도 홈이 이어 쓰지 않는다. 합류한 쓰기가 실패로 끝나면 「한 번」을 한 번 더 열어 준다.

**Why this priority**: 사용자가 일기가 없는데 자동 쓰기가 다시 시도되지 않는 날이 생긴다. 다만 iOS 오래 사는 프로세스 조건에 한정된다.

**Independent Test**: 실제 판정·등록부를 묶은 조립 테스트로, 「한 번」을 이미 소모한 실행에서 합류한 쓰기가 실패한 뒤 홈이 한 번 더 쓰기를 시작하는 것을 본다.

**Acceptance Scenarios**:

1. **Given** 「한 번」을 이미 소모한 실행에서 홈이 남의 쓰기에 합류했다, **When** 그 쓰기가 실패로 끝난다, **Then** 같은 실행에서 이어서 한 번 새로 쓴다.
2. **Given** 이어 쓰기도 실패한다, **When** 같은 실행에서 다시 판정한다, **Then** 더 이어 쓰지 않는다(실패 뒤 이어 쓰기는 한 번이다).
3. **Given** 합류한 쓰기를 사용자가 그만두었거나 지우기가 끊었다, **When** 판정한다, **Then** 이어 쓰기를 열지 않는다(사용자가 그만둔 쓰기는 실패가 아니다, 080).
4. **Given** 합류한 쓰기가 저장에 성공했다, **When** 같은 실행에서 다시 판정한다, **Then** 새 쓰기를 시작하지 않는다.

---

### User Story 8 - 죽은 배선을 걷고, 닫는 항목을 기록하고, 막힘 문구를 사실로 맞춘다 (Priority: P3)

- 018 미리 준비(`prepare`·`release`·`captionDay`)가 앱에서 연결돼 있지 않음을 확인하고 홈 화면의 해당 입력·효과·테스트를 걷는다.
- 지운 날을 백그라운드가 다시 쓰는 것은 자동 쓰기를 켠 사용자의 약속(안 쓴 날을 따라잡는다)이므로 의도된 동작으로 닫고, 그 사실을 기록에 한 줄 남긴다.
- 「지우기 막힘」 문구는 지금 지우기가 남의 쓰기를 끊고 지우므로 「자동으로 쓰는 중이라」가 사실과 다르다. 막힘은 다른 지우기가 겹칠 때뿐이므로 그 사실에 맞게 고친다.

**Why this priority**: 동작을 막는 결함이 아니라 정리·기록이다.

**Independent Test**: 소스 계약이 걷은 입력이 남지 않음을 잠그고, 문구 골든이 새 문구를 허용 목록에서만 허용한다.

**Acceptance Scenarios**:

1. **Given** 앱 조립부가 미리 준비 입력을 홈에 넘기지 않는다, **When** 걷은 뒤 전체 타입 검사와 테스트를 돌린다, **Then** 오류 0이고 홈의 동작이 달라지지 않는다.
2. **Given** 지우기가 다른 지우기와 겹쳤다, **When** 지우기를 요청한다, **Then** 사실에 맞는 새 문구가 보이고 일기는 건드려지지 않는다.
3. **Given** 지우기를 요청했는데 쓰기가 살아 있다, **When** 지운다, **Then** 쓰기를 끊고 지운다(문구가 아니라 지우기가 성공한다).

---

### Edge Cases

- 자정 직전 마지막 주기가 짧거나, 모드를 켠 시각이 주기 경계 직전이다: 현재 주기 번호는 날짜와 구간 순번으로 정해지고, 켠 직후의 첫 판정은 그 주기의 남은 창만 쓴다.
- 날짜가 바뀐다: 새 날의 첫 주기는 새로 시작하고 어제의 테스트 일기는 지우지 않는다(남아 있다).
- 같은 주기에 앱 열기와 백그라운드가 동시에 판정한다: 리셋은 등록부의 칸을 차지한 한 쪽만 하고, 못 차지한 쪽은 이번에는 리셋하지 않는다.
- 리셋 도중 앱이 죽는다: 일기가 지워지고 주기 번호가 갱신되지 않았다면 다음 판정이 다시 리셋하며 같은 결과로 수렴한다.
- 주기를 바꾼다(30 → 10분): 켜기와 같은 길로 새 주기로 다시 시작한다 — 오늘 일기가 있으면 확인을 거쳐 오늘 일기와 딸린 기록을 지우고 새 주기의 현재 번호로 기록한다. 같은 값을 다시 고르면 아무 일도 없다(오늘 일기를 지우지 않는다).
- 모드가 켜진 채 개발자 메뉴를 끈다: 064 상태 흉내와 같이 빠른 주기 기록도 지워 꺼짐이 된다(화면이 닿지 않는 곳에서 일기를 지우는 모드가 남지 않게).
- 사진·장소 재료가 오늘 없다: 주기 시작에 리셋하고도 「재료 없음」으로 건너뛴다(이것도 정상 결과).
- 빠른 주기 도중 사용자가 「일기 모두 지우기」를 한다: 평소와 같다.
- 빠른 주기가 켜진 채 진단의 「자동 쓰기 지금 실행」(수동 실행)을 누른다: 수동 실행은 설정 입력만 덮는 평소 동작 그대로이며 빠른 주기를 쓰지도 주기 리셋을 하지도 않는다(창 밖에서도 눌러 시험할 수 있다는 수동 실행의 목적을 지킨다).
- 알림 지연이 시도 창의 절반 이상이다: 지연은 창 길이의 절반을 넘지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

#### 빠른 주기

- **FR-001**: 시스템은 자동 쓰기의 시간 규칙(목표 시각, 시도 창, 후보 날, 알림 지연 상한)을 한 곳에서 정해 모든 판정이 그것을 쓰게 해야 한다. 배포 값(목표 = 설정의 시 × 60분, 창 180분, 후보 사흘)은 종전과 같다.
- **FR-002**: 빠른 주기가 켜져 있고 개발 환경이면 그 한 곳이 주기·창·후보 날(오늘 하나)·알림 지연 상한을 빠른 주기 값으로 돌려줘야 한다. 주기 시작은 자정부터 N분 격자, 시도 창은 주기 시작부터 ⌊N/2⌋분이다.
- **FR-003**: 빠른 주기는 기기의 설정 기록 하나(켜짐일 때만 존재, 없으면 꺼짐)에 담고 개발 환경(판정에 성공한 local·dev)에서만 읽어야 한다. 배포 환경과 판정하지 못한 환경은 기록이 있어도 읽지 않는다. 읽지 못하거나 모양이 다르면 꺼짐이다. 백그라운드 헤드리스 실행도 같은 규칙으로 읽는다.
- **FR-004**: 주기 값은 5~180의 정수 분이어야 하고, 범위 밖·비정수는 거부한다. 프리셋은 10·30·60분이다.
- **FR-005**: 모든 자동 쓰기 경로(백그라운드·앱 열기·알림 누름)는 판정 직전에 같은 하나의 주기 리셋 절차를 거쳐야 한다. 판정이 일어나는 자리는 둘(백그라운드 본체, 앱 열기 판정 훅 — 알림 누름은 훅을 다시 열 뿐 판정하지 않는다)이고, 둘 다 같은 절차를 부른다. 경로마다 따로 구현하지 않는다.
- **FR-006**: 주기 리셋은 현재 주기 번호가 기록된 마지막 리셋 주기와 다를 때만 실행하고, 오늘의 일기, 그 날의 완성 알림 확인 기록, 사진 권한 건너뜀 기록, 창 밖 따라잡기 기록을 지우고 트레이의 알림을 거둔 뒤 주기 번호를 갱신해야 한다. 오늘 외 날의 일기는 지우지 않는다.
- **FR-006a**: 주기 리셋은 「자동으로 쓰기」가 켜져 있을 때만 일어난다 — 다시 쓰지 않을 일기를 지우지 않는다. 꺼져 있으면 빠른 주기가 켜져 있어도 리셋하지 않는다(판정 자리가 `settings.enabled`로 가른다).
- **FR-007**: 주기 리셋은 살아 있는 쓰기 등록부의 칸을 차지한 때만 지워야 한다. 칸을 차지하지 못하면(다른 쓰기·지우기가 살아 있다) 이번에는 리셋하지 않고 쓰기를 끊지 않는다.
- **FR-008**: 시스템은 일기 하나를 지우는 동작을 저장소에 제공해야 한다(전체 지우기와 별개). 없는 날을 지우면 조용히 넘어간다.
- **FR-009**: 빠른 주기를 켤 때(그리고 주기 값을 다른 값으로 바꿀 때) 오늘 일기가 이미 있으면 지운다는 사실을 알리는 확인창을 거치고, 거절하면 켜지 않거나 옛 주기를 유지해야 한다. 같은 값을 다시 고르는 것은 아무 일도 아니다.
- **FR-009a**: 켤 때 마지막 리셋 주기 번호를 켠 순간의 주기 번호로 기록해, 켠 직후 같은 주기에서 다시 지우지 않아야 한다.
- **FR-009b**: 주기 리셋은 판정 지점(백그라운드 실행·앱이 앞으로 돌아올 때·알림 누름)에서만 일어난다. 가만히 열려 있는 화면을 시계로 지우지 않으며, 리셋 뒤 홈은 오늘을 「안 쓴 날」로 다시 읽는다.
- **FR-009c**: 주기 리셋은 앱 열기 자동 쓰기의 「한 번」도 다시 열어야 한다(빠른 주기 동안만). 사진 리사이즈 사본은 지우지 않는다.
- **FR-009d**: 진단의 「자동 쓰기 지금 실행」(수동 실행)은 빠른 주기가 켜져 있어도 평소 배포 규칙으로 판정하고 주기 리셋을 하지 않아야 한다.
- **FR-010**: 쓸 차례 알림 계획은 빠른 주기에서 다음 주기 시작 시각의 알림 하나만 내야 한다. 오늘 일기가 저장되면 평소 맞추기가 트레이의 알림을 거둔다.
- **FR-011**: 배터리 예외가 확인된 기기의 쓸 차례 알림 지연은 평소 30분과 시도 창 길이의 절반(⌊창 분 / 2⌋) 중 작은 값이어야 한다 — 지연된 알림이 창이 닫히는 순간이 아니라 창 안에 울려 누르면 앱 열기 판정이 아직 창 안이다.
- **FR-012**: 개발자 메뉴에 「빠른 주기」 구역이 있어 켬/끔·프리셋·직접 입력·지금 주기 번호·다음 주기 시작 시각을 보이고, 모드를 켜도 「자동으로 쓰기」가 꺼져 있으면 쓰지 않는다는 안내를 보여야 한다. 한계(안드로이드 잡 간격 하한 15분, iOS 깨움은 OS 몫)도 적어야 한다.
- **FR-013**: 진단 화면 머리에 빠른 주기가 켜져 있을 때만 「빠른 주기 켜짐 · 주기 N분」 한 줄을 보여야 한다.
- **FR-013a**: 개발자 메뉴를 끄면 빠른 주기 기록도 지워 모드를 꺼야 한다.
- **FR-014**: 빠른 주기를 켜거나 끄거나 주기를 바꾸면 백그라운드 잡의 주기 타이머를 다시 시작하고 쓸 차례 알림을 다시 맞춰야 한다.
- **FR-015**: 시도 기록의 결과 갈래는 늘리지 않는다(원칙 IV). 빠른 주기 값(창 = N/2, 지연 상한)은 사람이 정한 값으로 표시하고 측정이라 쓰지 않는다(원칙 V).
- **FR-016**: 빠른 주기 설정의 읽기·리셋은 해석기와 리셋 절차 한 곳에서만 이루어져야 하고, 환경 판정 가드 뒤에서만 가능해야 한다. 이를 헌법 검사 규칙으로 잠그고 위반 주입으로 확인한다.

#### 080 잔여 결함

- **FR-017**: 모델 엔진의 `load()`는 동시에 여러 번 불려도 한 번에 하나의 컨텍스트만 열어야 한다. 호출은 도착 순서대로 하나씩 처리된다 — 같은 캐릭터면 앞 호출이 연 컨텍스트를 재사용하고, 다른 캐릭터면 앞의 적재가 끝난 뒤 닫고 연다. 앞 적재가 실패해도 뒤따른 호출은 새로 시도한다.
- **FR-018**: 앱에서 연결되지 않은 018 미리 준비 입력(`prepare`·`release`·`captionDay`)과 그 효과·테스트를 걷어야 한다. 걷기 전에 앱 조립부가 그것을 넘기지 않음을 확인한다.
- **FR-019**: 홈이 합류한 남의 쓰기가 실패로 끝나면(사용자가 그만둔 것·지우기가 끊은 것은 실패가 아니다) 앱 열기 자동 쓰기의 「한 번」을 한 번 다시 열어, 같은 실행에서 한 번 새로 이어 쓰게 해야 한다. 이어 쓰기 실패는 되풀이하지 않는다. 「한 번」의 소모 시점(홈이 실제로 시작하는 순간)은 바꾸지 않는다.
- **FR-020**: 지운 날을 백그라운드가 다시 쓰는 것은 의도된 동작으로 닫고 그 사실을 완료 이력/AGENTS에 한 줄 남겨야 한다.
- **FR-021**: 「지우기 막힘」 문구는 「지금 다른 작업이 끝나는 중이라 지우지 못했어요. 잠시 뒤에 다시 해 주세요.」로 바꿔야 한다. 문구는 한글 카탈로그에만 두고 문구 골든은 다시 쓰지 않고 변경 목록(`CHANGED_AFTER_GOLDEN`)에 올린다.

### Key Entities *(include if feature involves data)*

- **빠른 주기 설정**: 켜짐일 때만 존재하는 기록. 주기 분(5~180)과 마지막 리셋 주기 번호를 가진다. 개발 환경에서만 의미가 있다.
- **주기**: 하루를 자정부터 N분 단위로 자른 구간. 날짜와 순번으로 식별한다. 시도 창은 앞 절반이다.
- **테스트 날**: 오늘. 빠른 주기 동안 유일한 후보 날이며 주기마다 리셋된다.
- **시간 규칙**: 목표 시각·시도 창·후보 날 목록·알림 지연 상한의 묶음. 배포 값과 빠른 주기 값 둘 중 하나가 판정에 쓰인다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 개발자는 30분 주기로 폰을 둔 채 세 주기(약 1시간 반) 안에 시도 기록에서 주기별 결과를 세 건 이상 읽을 수 있다(안드로이드 OS가 깨운 주기에 한함 — 못 깬 주기는 그렇게 기록된다).
- **SC-002**: 빠른 주기가 꺼진 상태, 그리고 배포 환경에서는 자동 쓰기 판정·알림 결과가 이 기능이 없을 때와 동일하다(기존 판정·알림 테스트가 기대값 변경 없이 통과한다 — 입력 모양을 맞추는 수정은 허용).
- **SC-003**: 배포 환경 + 켜진 설정 기록 조합에서 일기가 한 건도 지워지지 않는다.
- **SC-004**: 주기 리셋은 오늘 외 날의 일기를 한 건도 지우지 않는다.
- **SC-005**: 빠른 주기에서 쓸 차례 알림이 주기 시작 시각에 실제 기기에서 뜨고, 일기 저장 뒤 완성 알림만 남는 것을 최소 한 주기 확인한다.
- **SC-006**: 동시 `load()` 두 번이 열린 컨텍스트를 둘로 만들지 않는다(재현 테스트가 수정 전에 실패하고 수정 뒤 통과한다).
- **SC-007**: 「한 번」을 이미 소모한 실행에서 합류한 쓰기가 실패하면 이어 쓰기가 정확히 한 번 시작되고, 그것이 실패해도 더 시작되지 않는다(조립 테스트).
- **SC-008**: 전체 테스트·린트(타입·헌법 검사 포함)가 통과하고 걷은 미리 준비 입력이 소스에 남지 않는다.
- **SC-009**: 개발 빌드 실기기(SM-S901N)에서 빠른 주기 한 바퀴(리셋 → 쓰기 → 저장 → 다음 주기 리셋)와 쓸 차례 알림 발화를 확인하고, 확인하지 못한 것은 못 본 것으로 적는다.

## Assumptions

- 이 기능은 개발 빌드 전용이라 배포 사용자에게 보이는 변화는 ⑤의 문구 하나뿐이고(드물게 닿음), 릴리스 노트에는 번호를 올릴 때 사람이 정한다.
- 안드로이드 백그라운드 잡 최소 간격은 15분이고 OS가 더 미룰 수 있다. 주기가 그보다 짧거나 창 안에 잡이 한 번도 안 오면 그 주기는 쓰기 없이 끝난다. iOS는 OS가 깨우는 시각을 앱이 정하지 못한다.
- 빠른 주기에서 창 밖 따라잡기와 사흘 후보는 확인되지 않는다 — 기존 단위 테스트와 실기기 확인이 이미 다룬다.
- 「자동으로 쓰기」 설정은 그대로 실제 설정이다. 빠른 주기는 그것을 대신 켜지 않는다.
- 사진·장소 신호는 개발 기기에 시딩해 둔 오늘 재료를 쓴다(`sample:seed` 표본 사진). 신호를 지어내지 않는다(원칙 I·V).
- 새 문구(빠른 주기 구역·확인창·진단 한 줄·⑤ 막힘 문구)는 한글 카탈로그의 새 영역에 둔다. ⑤의 문구는 Clarifications에서 확정됐다. 나머지 새 문구는 계획 단계에서 초안을 두고 소유자가 확정한다.
- 원인 불명인 「백그라운드 쓰기가 본문 49초 뒤 실패」는 이 기능에서 다루지 않는다.
