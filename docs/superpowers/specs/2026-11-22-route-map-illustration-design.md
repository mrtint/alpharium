# 하루 동선 도식에 일러스트풍 지도를 깐다 — 설계

작성일 2026-11-22. 로드맵 「동선 도식에 지도 느낌을 더한다 — 내장 윤곽 실험」의 결과로, 소유자가 모형(비공개 아티팩트 일곱 경우)을 보고 **일러스트풍 색 지도·앱 번들 내장**으로 가기로 했다.

## 목적과 이해

- **목적**: 125의 「하루 동선」(번호 점·직선)은 어디를 다녔는지 위치감이 약하다. 점 뒤에 평평한 색 면 지도(물·공원·길)를 깔아 위치감을 준다.
- **소유자가 정한 것**: ① 회색 윤곽이 아니라 일러스트풍 색 면 ② 외부 요청 없이 앱에 든 데이터 ③ 한 곳뿐인 날·좁은 지역에 몰린 날도 지도를 그린다 ④ 번들 증가는 약 9MB(골목·생활도로·공원까지, 보행로·건물 제외) ⑤ **동선 좌표는 일기를 쓸 때 일기에 저장한다(스냅샷, 약 1m 정밀도)** — 사진을 지우면 지도가 사라지는 것은 안 된다(2026-11-22, 125·121의 「좌표를 저장하지 않는다」를 뒤집는다).
- **범위 밖**: 사진 밖 위치 수집(별도 과제), 확대·이동 조작, 지도 타일·외부 서버, 보행로·건물.
- **성공 모습**: 쓴 날 지면의 「하루 동선」이 어느 날이든(수 m~수십 km) 지도 위에 올라가고, 좌표·신호는 여전히 `app/day-route.ts` 밖으로 나가지 않으며, 네트워크·권한이 늘지 않는다.

## 설계

### 데이터 — `assets/map/kr-map.bin` (새 번들 자산)

- 전국 한국 OSM(`scripts/places/.cache/south-korea-latest.osm.pbf`, 장소 데이터와 같은 원본)에서 **선 층**(고속도로~3차 도로와 연결로, 골목·생활도로, 철도, 강)과 **면 층**(물, 공원, 큰 숲)을 뽑아 단순화한다. 해안선은 물 면의 경계다.
- 단순화 허용 오차와 포함 도로 종류는 빌드 스크립트 한 곳의 상수다(사람이 정한 값). 제외: 보행로·오솔길·건물.
- **격자 칸으로 나눠 담는다**(칸 안의 선·면 + 칸 목차). 기기가 상자 범위가 닿는 칸만 해석한다. 파일 전체를 읽는 점은 `kr-places.bin`과 같다(`expo-file-system` `File`의 `*Sync()`).
- 만드는 길은 `scripts/map/build-map.mts` 하나이고 기록(`kr-map.meta.json`: 원본·크기·sha256·층별 크기)을 남긴다. 번들 상한은 새 테스트가 잠근다(장소 파일 10MB 규칙과 별개, 값은 plan에서 측정으로 정한다).
- 전국 추정(점당 2.2바이트·선당 2바이트 가정, 실제 인코딩은 plan에서 잰다): 큰 길·철도·강·물 2.4MB + 3차 1.2MB + 골목 4.9MB + 공원·숲 0.3MB ≈ **8.8MB**.

### 좌표 저장 — 일기에 스냅샷 (2026-11-22 소유자 결정)

- 일기를 쓸 때 `entry.places[i]`에 `latE5`·`lonE5`(1e-5도 정수, 약 1m)를 더한다(`savedPlacesOf`). 지면을 열어 보는 동작은 일기를 바꾸지 않는다.
- 좌표가 저장된 일기는 사진·사진 권한을 읽지 않고 지도를 그린다. 좌표가 없는 옛 일기는 125처럼 사진을 다시 읽어 일치할 때만 그리고, 아니면 목록만 보인다(열 때 고쳐 쓰는 이행은 없다).
- 방침은 「일기에 방문 위치가 담기고 휴대폰 백업에 포함될 수 있다」로 보강한다. 스토어의 「위치 수집 안 함」은 그대로다.

### 투영·경계 — `src/app/day-route.ts`가 계속 유일한 길

- 상자(폭 1 × 높이 `ROUTE_ASPECT`)는 저장된 좌표(옛 일기는 다시 읽은 사진 좌표)로 정하고, 규칙에 **최소 폭 600m**를 더한다. 자리가 하나이거나 100m 안에 몰려도 지도를 그린다. 지금의 「한 곳이면 목록만」「모두 100m 안이면 목록만」(DR 퇴화 규칙)은 지도를 그리는 쪽으로 바뀌고, 사진 수·처음 시각이 저장 목록과 어긋난 경우의 「목록만」은 그대로다.
- 상자의 위경도 범위로 지도 칸을 읽어 **0~1 상대 좌표 경로**(층·굵기 단계별)로 바꾼다. 화면에는 절대 좌표가 가지 않는다(DB2). 읽는 기기 통로는 `place-index-port.ts`와 같은 모양의 포트 하나(`map-port.ts`)다.
- 상자 폭에 따라 보일 층을 거른다(수 km에서는 큰 길·물·공원, 600m~1km에서는 골목까지). 문턱 값은 사람이 정한 값이다.

### 그리기 — `react-native-svg`

- 수천 개 선을 View로 그릴 수 없어 `react-native-svg`를 들인다(Expo SDK 57 지원 버전, `npx expo install`). **네이티브 모듈이라 개발 빌드를 다시 만들어야 한다**(prebuild·재설치 — 앱 데이터는 `pm clear`·삭제 없이 `install -r`).
- 면 위에 선, 그 위에 지금 도식의 점·번호·직선을 그린다. 모서리 반경·그림자·그라데이션 없음(Modernist). 점 옆 장소 이름 라벨은 서로 겹치면 자리를 바꿔 놓는다(모형의 배치 규칙).
- 지도 전용 색(바탕·물·공원·큰 길·작은 길 다섯)은 `design/tokens.json`에 올리고 생성기로 옮긴다. 값은 모형의 값에서 시작해 소유자가 손본다.

### 접근성·문구

- 지도는 장식이다. 낭독은 지금처럼 도식 한 요소가 「N곳」을 말하고 범례가 순서대로 읽힌다(DU5). 지도 층은 낭독에서 숨긴다.
- 125에서 남은 「이름을 모르는 곳」 문구 결정은 clarify에서 소유자에게 묻는다.

### 테스트

- 계약: 번들 자산 상한·기록 일치, 칸 해석(경계·빈 칸·여러 칸), 상자 폭 최소·퇴화·한 곳, 좌표 비유출(화면 계약 DB2·소스 계약), 네트워크 0건·권한 0건, 토큰 동기·대비.
- 위반 주입: 화면이 좌표를 받게 바꾸기, 상자 폭 최소 제거, 지도 층을 낭독에 노출.
- 실기기(개발 빌드): 도심·좁은 지역·한 곳·몰린 날 각각 안드로이드 SM-S901N과 iPhone 14에서 본다.

## 결정 표 (에이전트 판단)

| 결정 | 근거 | 뒤집으면 바뀌는 것 |
|---|---|---|
| `react-native-svg`를 들인다 | 수천 개 선은 View로 불가. 모형이 SVG | 네이티브 재빌드 필요. 대안(Skia 등)은 더 무겁다 |
| 보행로·건물은 번들에 넣지 않는다 | 보행로 +10MB 이상, 건물 미측정. 소유자가 9MB로 정했다 | 좁은 지역이 모형보다 휑하다 — 건물은 따로 측정해 되돌릴 수 있다 |
| 최소 상자 폭 600m | 모형에서 점이 겹치지 않으면서 길이 보이는 값 | 좁은 경우의 점 간격·길 밀도가 달라진다 |
| 격자 칸 + 칸 목차 | 전국 9MB 중 필요한 칸만 해석 | 형식·빌드·파서가 모두 바뀐다 |
| 해안선은 물 면 경계로만 | 면으로 그리면 별도 선 층이 필요 없다 | 바다 쪽 표현 |
| 방침은 일기에 방문 위치가 담긴다는 서술만 보강 | 외부 전송은 없지만 백업에 좌표가 들어간다. 스토어 「위치 수집 안 함」은 그대로 | 타일을 쓰게 되면 방침·헌법 개정이 따른다 |
| 「장소 이름 끔」이어도 좌표를 저장 | 끔은 이름 찾기 설정이고 자리 목록은 끔에서도 남는다 | 끔 사용자는 지도가 없다 |
| 옛 일기는 좌표를 채우지 않고 다시 읽기 폴백 | 보기만 하는 동작이 일기를 고쳐 쓰지 않는다 | 이행 코드·열 때 파일 변경이 생긴다 |

## 위험·미확인

- 전국 용량은 추정이다(가정한 인코딩). 실제 인코딩 크기·해석 시간(9MB 읽기 + 칸 해석)은 plan에서 측정하고 기기에서 확인한다.
- 일러스트풍 색의 대비·글자 가독성은 모형에서만 봤다. 앱에서 점·라벨이 지도 위에서 읽히는지는 실기기에서 본다.
- 지역마다 OSM 밀도가 다르다(모형의 서울숲 근처는 공원 면이 거의 없었다). 시골·섬에서의 모습은 못 봤다.
