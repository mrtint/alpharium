# Feature Specification: 개발자 탭 내 입력 프롬프트 모니터링

**Feature Branch**: `022-prompt-token-diagnostics`

**Created**: 2026-08-29

**Status**: Draft

**Input**: User description(로드맵 6번, 원래 의도로 정정): "입력 토큰 양을 최적화하기 위해, 헌법 IV 원칙(성능 지표의 일반 화면 노출 금지)을 침해하지 않는 범위 내인 '개발자 진단 화면(DiagnosticsScreen)'에 모델별로 전송되는 실제 프롬프트 원본 텍스트를 노출하는 디버깅 도구를 구축한다."

> **정정 기록 (2026-08-29)**: 로드맵을 AI로 옮기는 과정에서 이 항목이 "토큰 지표(`tokens_evaluated`/`tokens_predicted`) 노출"까지 포함하는 것으로 왜곡되었다. 사용자 확인 결과 **원래 의도는 입력 프롬프트 원본을 개발자에게 보여주는 것**이며, 네이티브 토큰 지표 노출은 이 스펙의 범위가 아니다. 토큰 지표를 건드리지 않으므로 `llama-port.ts`의 원칙 IV 경계는 그대로 유지되고, 이 기능은 헌법 IV와 충돌하지 않는다.

## 배경과 문제

이 저장소는 온디바이스 추론에서 **입력 프롬프트 크기가 첫 토큰까지 걸리는 시간(TTFT)을
지배한다**는 것을 018에서 실측했다(고정 접두사 프리필로 TTFT 20.6초→6.6초). 프롬프트를
줄이는 작업을 하려면 개발자가 **지금 실제로 무엇이 조립되어 모델에 들어가는지**를 캐릭터별로,
신호 유무별로 눈으로 봐야 한다. 현재는 그 방법이 없다:

- `src/diary/prompt.ts`가 조립한 최종 프롬프트 문자열은 `llama-port.ts`의 `completion()`
  인자로 들어간 뒤 어디에도 남지 않는다.
- `adb logcat`에 부분적으로 찍히긴 하나 캐릭터별·신호 유무별로 어떻게 달라지는지 나란히
  보기 어렵고, 개발 기계에 케이블로 연결해 로그를 읽어야 한다.

이 기능은 그 사각을 **개발자 진단 경로에 한정해** 연다. 사용자 화면(일기 목록·상세·쓰기)과
배포 빌드는 이 정보에 절대 닿지 않는다.

## 헌법 경계 (이 기능이 지켜야 하는 것)

- **원칙 III (모델은 캐릭터다)** — 헌법 1.1.0의 "사용자 화면과 진단 경로" 조항: 진단 경로는
  사용자 화면이 아니므로 캐릭터↔모델 대응을 보여도 된다(MAY). 014가 `characterModels`로 이미
  이 예외를 썼다. **화면은 여전히 몰라야 한다**(MUST NOT) — 진단 계층이 문자열로 만들고 화면은
  그 문자열만 받는다.
- **원칙 IV (측정 장치를 제품에 들이지 않는다)** — 이 기능은 점수·비교·채점·토큰 수·추론
  속도를 다루지 않는다. 보여주는 것은 **우리가 조립한 텍스트**뿐이다. `llama-port.ts`가
  `timings`·`tokens_*`를 버리는 기존 방어는 그대로 유지된다(이 기능이 손대지 않는다).
- **원칙 II (화자는 휴대폰이다)** — 프롬프트 조립은 `src/diary/prompt.ts` 한 곳에만 있고
  이 기능은 그 함수를 미리보기용으로도 호출할 뿐 새 조립 로직을 만들지 않는다.
- **DiagnosticsScreen 노출 게이트** — 001 SC-013이 세운 것: 진단 화면은 local·dev 환경에서만
  뜨고 prod 빌드에는 탭 자체가 없다(`showsOnScreen()`). 이 기능이 더하는 모든 것은 그 게이트
  안에 있다. 게이트 밖으로 새면 이 기능 전체가 헌법 위반이다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 캐릭터별 최종 프롬프트 원본 보기 (Priority: P1)

개발자가 프롬프트를 줄이려면 지금 조립되는 최종 문자열을 캐릭터별로 눈으로 봐야 한다. 개발자
탭에서 캐릭터를 고르면, 그 캐릭터에 대해 `prompt.ts`가 조립한 최종 프롬프트 원본 텍스트가
그대로(잘림·요약 없이) 화면에 나온다. 신호가 있는 하루와 없는 하루의 프롬프트가 어떻게
달라지는지 볼 수 있도록, 사람이 미리 정한 대표 신호 조합(최소 "신호 없음", "사진 있음")으로
프롬프트를 조립해 보여준다.

**Why this priority**: 이것 하나만 있어도 "프롬프트에 뭐가 들어가는지"라는 근본 질문에 답이
된다. 실제 모델 로딩·생성 없이 조립 함수만 불러 만들 수 있어 완전히 독립적이다.

**Independent Test**: 개발자 탭을 열고 캐릭터를 바꿔 가며 프롬프트 원본이 캐릭터별로 다르게(이름
차이 등) 렌더되는지, 신호 조합을 바꾸면 프롬프트가 달라지는지 확인한다. 실제 모델 로딩·생성
없이 검증 가능하다.

**Acceptance Scenarios**:

1. **Given** local 또는 dev 환경에서 앱이 실행 중이고 개발자 탭이 보인다, **When** 개발자 탭의
   프롬프트 모니터 섹션에서 캐릭터 A를 고른다, **Then** 캐릭터 A에 대해 조립된 최종 프롬프트
   전체 텍스트가 잘림 없이 표시된다.
2. **Given** 프롬프트 모니터에 캐릭터 A의 프롬프트가 보인다, **When** 캐릭터 B로 바꾼다,
   **Then** 표시되는 프롬프트가 캐릭터 B 기준으로 다시 조립되어 바뀐다(최소한 캐릭터 이름이
   다르고, 중국어·영어 캐릭터는 출력 언어 지시 줄이 다르다).
3. **Given** 프롬프트 모니터가 "신호 없음" 조합을 보이고 있다, **When** "사진 있음" 조합으로
   바꾼다, **Then** 사진 관련 문장이 포함된 다른 프롬프트가 표시된다.
4. **Given** prod 빌드로 앱이 실행 중이다, **When** 앱의 모든 탭을 확인한다, **Then** 개발자
   탭 자체가 없고 프롬프트 모니터에 닿을 경로가 없다.
5. **Given** 프롬프트 조립이 실패하는 상황(캐릭터 미정 등), **When** 프롬프트 모니터를 본다,
   **Then** 실패 사실과 사유가 표시되고 빈 문자열이나 직전 프롬프트가 남지 않는다.

### User Story 2 - 프롬프트 길이 감(感) 표시 (Priority: P2)

프롬프트 원본만 있으면 "얼마나 긴지"가 눈으로만 가늠된다. 프롬프트 모니터에 그 프롬프트의
대략적 크기(문자 수 등, 조립 시점에 알 수 있는 값)를 함께 보여줘, 실제 생성을 돌리기 전에도
축소 작업의 방향을 잡을 수 있게 한다.

**Why this priority**: 편의 기능이다. Story 1의 텍스트만으로도 작업은 되지만, 조립 시점 값이라
비용이 거의 없고 신호 조합 간 크기 차이를 한눈에 보여준다.

**Independent Test**: 프롬프트 모니터에서 신호 조합을 바꾸면 표시되는 크기 값이 프롬프트 텍스트
길이에 맞춰 바뀌는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 프롬프트 모니터가 어떤 캐릭터·신호 조합의 프롬프트를 보이고 있다, **When** 그
   화면을 본다, **Then** 프롬프트 텍스트와 함께 대략적 크기 값이 표시되고, 그 값이 조립 시점
   근사치임이(실측 토큰 수가 아님이) 드러나게 표기된다.
2. **Given** 크기 값이 표시되어 있다, **When** 더 많은 신호가 포함된 조합으로 바꾼다, **Then**
   크기 값이 더 커진다.

---

### Edge Cases

- **프롬프트 조립이 실패하면?** (캐릭터가 정해지지 않는 등) 프롬프트 모니터는 텍스트 대신
  "조립할 수 없음"과 사유를 보여준다 — 빈 문자열이나 옛 프롬프트를 남기지 않는다.
- **긴 프롬프트가 화면을 넘치면?** 프롬프트 원본은 스크롤 가능한 영역에 전체가 표시되며 잘리지
  않는다. 개발자가 전체를 읽거나 복사할 수 있어야 한다.
- **prod 빌드에서 실수로 이 코드 경로가 살아 있으면?** DiagnosticsScreen 노출 게이트가
  단일 방어선이다 — 게이트가 막으면 프롬프트 모니터를 그릴 수 없다.
- **데스크톱 서버 추론(local 환경)일 때?** 프롬프트는 조립 시점 값이므로 추론 위치와 무관하게
  똑같이 보여진다 — 데스크톱 어댑터도 같은 `prompt.ts`를 부른다.
- **신호 프리셋에 없는 축 조합을 보고 싶으면?** 이 기능의 범위 밖이다. 프리셋은 사람이 상수로
  못 박은 목록이며, 필요하면 그 상수를 코드에서 늘린다(코드가 신호 값을 보고 조합을 만들지
  않는다).

## Requirements *(mandatory)*

### Functional Requirements

#### 노출 경계 (헌법)

- **FR-001**: 프롬프트 원본 텍스트는 **개발자 진단 화면(DiagnosticsScreen)에서만** 볼 수
  있어야 하며, 그 화면의 기존 노출 게이트(local·dev 전용, prod 빌드에서 탭 없음)를 그대로
  따라야 한다. 별도의 노출 조건을 새로 만들지 않는다.
- **FR-002**: 사용자 화면(일기 목록·상세·쓰기·캐릭터 선택·설정·온보딩)과 배포(prod) 빌드는
  프롬프트 원본에 닿을 수 없어야 한다.
- **FR-003**: 이 기능은 네이티브 추론 지표(`tokens_evaluated`·`tokens_predicted`·`timings`
  등)를 노출하거나, `llama-port.ts`가 그것을 버리는 기존 경계를 넓히지 않아야 한다.
- **FR-004**: 캐릭터↔모델 대응이 프롬프트 정보와 함께 진단 화면에 드러나는 것은 허용되나(014
  선례), 그 대응을 만드는 것은 진단 계층이어야 하고 화면 계층은 완성된 문자열만 받아야 한다
  (원칙 III, 007 헌법 검사 유지).

#### 프롬프트 모니터 (User Story 1, 2)

- **FR-005**: 개발자는 진단 화면에서 캐릭터를 선택할 수 있어야 하고, 선택한 캐릭터에 대해
  `src/diary/prompt.ts`가 조립하는 최종 프롬프트 원본 텍스트를 잘림·요약 없이 볼 수 있어야
  한다.
- **FR-006**: 프롬프트 모니터가 보여주는 텍스트는 **실제 생성 경로가 쓰는 것과 동일한 조립
  함수(`buildPrompt()`)의 출력**이어야 한다 — 별도의 미리보기용 프롬프트 조립 로직을 복제해
  만들지 않는다(프롬프트는 `prompt.ts` 한 곳에만 있다는 기존 경계 유지).
- **FR-007**: 개발자는 사람이 상수로 못 박은 대표 신호 조합(최소한 "신호 없음"과 "사진 있음"을
  포함) 중 하나를 골라, 그 조합으로 조립된 프롬프트를 볼 수 있어야 한다. 어느 조합을 둘지는
  코드가 신호 값을 보고 판정하지 않는다(사람이 정한 상수, 012의 `USER_VISIBLE_SIGNAL_AXES`가
  선례).
- **FR-008**: 신호 프리셋 상수는 진단 계층(`src/diagnostics/`)에 있어야 하며, 프롬프트 미리보기
  문자열은 `collectReport()`(또는 그와 동급의 진단 수집 지점)가 각 프리셋으로 `buildPrompt()`를
  호출해 만들어 `DiagnosticReport`에 실어야 한다. `src/ui/`는 `src/diary/prompt.ts`를 직접
  import하지 않는다(미리보기용 조립이 화면에 복제되는 것을 막는다 — 헌법 검사로 못 박는다).
  신호 타입(`src/signals/*`)은 기존 화면(`DiaryDetailScreen`·`SignalProbe`)이 이미 정당하게
  쓰므로 이 기능이 그 경계를 새로 만들지 않는다.
- **FR-009**: 프롬프트 조립이 실패하는 경우(캐릭터 미정 등), 프롬프트 모니터는 실패 사실과
  사유를 표시해야 하며 빈 문자열이나 직전 프롬프트를 남기지 않아야 한다.
- **FR-010**: 프롬프트 원본은 스크롤 가능한 영역에 전체가 표시되어야 하며, 개발자가 전체
  내용을 확인할 수 있어야 한다.
- **FR-011**: 프롬프트 모니터는 표시 중인 프롬프트의 대략적 크기(조립 시점에 알 수 있는 값,
  예: 문자 수)를 함께 표시해야 한다. 이 값은 실측 토큰 수와 혼동되지 않게 표기되어야 한다
  (조립 시점의 근사치임이 드러나야 한다).

#### 회귀 방지

- **FR-012**: 이 기능은 일기 생성의 판정 갈래(`empty`/`echo`/`language`/`unfinished` 4개)를
  늘리거나 바꾸지 않아야 한다.
- **FR-013**: 이 기능은 새 프롬프트 조립 경로·새 신호 수집 경로·새 캐릭터↔모델 매핑을 만들지
  않아야 한다 — 기존 `prompt.ts`, 기존 신호 타입, 기존 `roster.ts`만 재사용한다.
- **FR-014**: 이 기능은 실제 일기 생성 동작(파이프라인·`llama-port.ts`·`RunResult`)을
  변경하지 않아야 한다 — 진단 계층과 진단 화면에만 코드를 더한다.

### Key Entities *(include if feature involves data)*

- **프롬프트 미리보기 (Prompt Preview)**: 특정 캐릭터 + 특정 대표 신호 프리셋에 대해 조립된
  최종 프롬프트 원본 텍스트와 그 조립 시점 근사 크기. 저장되지 않으며 진단 리포트 수집 시
  조립된다. 조립 실패 시 사유를 담는 갈래를 갖는다.
- **신호 프리셋 (Signal Preset)**: 프롬프트가 신호 유무에 따라 어떻게 달라지는지 보여주기
  위한, 사람이 상수로 못 박은 `DaySignals` 묶음의 목록. 진단 계층에 위치. 최소 "신호 없음",
  "사진 있음" 포함.
- **진단 리포트 확장 (Diagnostic Report)**: 기존 `DiagnosticReport`에 캐릭터 × 프리셋별
  프롬프트 미리보기가 실리는 경로(014의 `characterModels`가 실린 것과 같은 방식). 화면 계층은
  이 리포트를 통해서만 프롬프트 정보를 받는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 개발자는 앱에 코드를 추가하거나 `adb logcat`을 읽지 않고, 개발자 탭에서 5개
  캐릭터 각각에 대해 조립되는 최종 프롬프트 원본을 확인할 수 있다.
- **SC-002**: 개발자는 "신호 없음"과 "사진 있음" 두 조합의 프롬프트를 개발자 탭에서 전환하며
  비교해, 사진 신호가 프롬프트에 더하는 문장을 눈으로 식별할 수 있다.
- **SC-003**: 개발자는 프롬프트를 줄이는 변경을 한 뒤 개발자 탭에서 각 조합의 근사 크기 값이
  줄었음을 확인할 수 있다(앱이 "몇 % 줄었다"를 계산해 보여주지는 않는다).
- **SC-004**: prod 빌드에서 앱의 모든 화면을 훑어도 프롬프트 원본이 나타나는 곳이 하나도 없다.
- **SC-005**: 사용자 화면(일기 목록·상세·쓰기·설정·온보딩)에서 프롬프트 원본이나 추론 지표
  숫자가 나타나는 곳이 하나도 없다(원칙 IV 회귀 없음).
- **SC-006**: 기존 기기 없는 테스트가 모두 통과하고, `llama-port.ts`가 `timings`를 버리는
  기존 계약 테스트가 그대로 유효하다(이 기능이 경계를 건드리지 않았음을 검증). 프롬프트가
  `prompt.ts` 한 곳에만 있다는 기존 계약 테스트도 그대로 통과한다.

## Assumptions

- 이 기능의 대상 사용자는 **이 저장소를 개발하는 사람**뿐이다. 엔드유저를 위한 기능이 아니다.
- 진단 화면(DiagnosticsScreen)은 현재 "개발자" 탭 안에 있으며(014에서 이동), local·dev
  환경에서만 노출되고 prod에는 탭이 없다 — 이 게이트를 그대로 재사용한다.
- 프롬프트 조립은 `src/diary/prompt.ts`의 `buildPrompt()` 한 곳에만 있고 데스크톱 어댑터도
  이것을 부른다 — 이 기능은 그 함수를 미리보기용으로도 호출할 뿐 새로 만들지 않는다.
- 프롬프트 미리보기에 넣을 신호 조합은 사람이 진단 계층에 상수로 정한다. 축 조합을 코드가
  값에서 판정해 만들지 않는다(원칙 V).
- 프롬프트 원본과 근사 크기는 휘발성이다 — 파일이나 일기 항목에 저장하지 않으며 진단 리포트가
  수집될 때마다 다시 조립된다.
- 새 네이티브 모듈을 추가하지 않고 추론 경로를 건드리지 않으므로, 실기기 검증은 debug 1회로
  충분하다(012 기준).
