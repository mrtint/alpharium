## 범위 *(먼저 읽을 것)*

이 계획이 다루는 것은 **001 User Story 1 하나뿐이다.** US2~US5는 이번 계획에 넣지 않는다.

_왜 US1인가:_ 네 축(퍼소나·수집/정제·추론·저장)과 화면이 **한 번씩만** 관여하는 가장
얇은 관통선이다. 이 프로젝트의 반복 실패는 한 축의 내부를 깊게 판 것이었고, ROADMAP이
그것을 막기 위해 축마다 「파기 시작했다는 신호」를 정해 두었다. 관통선이 먼저 서야 축
사이 계약이 실제로 맞물리는지 드러난다.

**예외 하나** — US2(실패 경로)는 범위 밖이지만 [quickstart.md](quickstart.md) 시나리오
6에서 **함께 검사한다.** 001 US2가 그 이유를 적어 두었다: 성공 경로만 만들고 실패를
나중에 붙이면 그 사이에 빈칸을 메우는 코드가 반드시 생긴다. 헌법 원칙 II는
NON-NEGOTIABLE이다.

**저장 계약은 US4·US5를 미리 만족시킨다** — 001 US4가 「저장 계약이 이 성질을 처음부터
만족하지 않으면 나중에 고칠 수 없다」고 적었으므로, [data-model.md](data-model.md)는
기기 비종속(005 FR-404)과 기록 묶음 구조(005 FR-410)를 지금 포함한다. 구현 대상이
아니라 **구조의 전제**다.

## Summary

사용자가 생성을 요청하면 그 시점에 하루치 신호를 집계 한 덩어리로 정리하고, 퍼소나로
그것을 해석해 일기 한 편을 쓰고, 일기와 집계를 **하나의 기록 묶음으로** 저장하고,
사용자가 본문과 근거 집계를 **대조**한다.

기술적 접근은 [research.md](research.md)의 네 결정에 있다. 그중 **결정 1(화자 판정
수단)이 이 계획의 핵심**이다 — 이월된 실측 다섯 중 유일하게 「값을 나중에 채우는」
성격이 아니며, 판정 수단이 없으면 001 FR-019의 검증 자체가 성립하지 않는다.

## Technical Context

**Language/Version**: TypeScript ~5.9.2

**Primary Dependencies**: Expo SDK 54 (`~54.0.36`), React Native 0.81.5, React 19.1.0.
신호 소스(활동·위치·사진·일정) 패키지는 **이 문서에서 버전을 적지 않는다** — 헌법
「패키지 버전 추측 금지」에 따라 `npx expo install`이 Expo API에서 해석하고
`npx expo install --check`로 검증한다.

**Storage**: 기기 로컬. 매체의 구체적 선택은 [research.md](research.md) 결정 4에 따라
구현 단계에 남기되, **기록 묶음 하나를 단일 쓰기 단위로 다룰 수 있어야 한다**
(005 FR-411).

**Testing**: Jest + jest-expo (~54.0.0), @testing-library/react-native. 헌법 원칙 IV가
정한 대상은 구현 전 테스트를 먼저 쓴다.

**Target Platform**: Android (Expo Go 54). _근거:_ 대상 기기의 Play Store가 Expo Go 54만
제공하므로 SDK 54를 벗어나면 사이드로딩 없이 실행할 수 없다 (AGENTS.md, 헌법 플랫폼 제약).

**Project Type**: Mobile app (단일 프로젝트, 백엔드 없음)

**Performance Goals**: US1에 성능 목표를 두지 않는다. _근거:_ ROADMAP이 조회 성능
최적화를 「파기 신호」로 지목했고, US1이 다루는 것은 묶음 하나의 저장·조회뿐이다.

**Constraints**:
- 프로덕션은 네트워크 없이 동작한다 (헌법 원칙 I) — 비행기 모드에서 생성 성공이 수용 기준
- 개발 단계는 클라우드 어댑터를 쓰되 세 조건을 지킨다 (동일 스키마, 사진 원본 미전송,
  UI 표시)
- 온디바이스 소형 모델을 전제하므로 추론 입력을 키우지 않는다 (001 FR-015)

**Scale/Scope**: 단일 사용자, 단일 퍼소나, 날짜당 일기 최대 한 편. 화면은 006 FR-500의
다섯 자리 중 **셋**(오늘·기록 목록·일기 상세)만 US1 범위.

**NEEDS CLARIFICATION**: 없음 — Phase 0에서 전부 해소했다. 다만 **의도적으로 비운 값**이
여섯 있다(아래 「실측으로 닫을 자리」). 이것은 미해소 항목이 아니라 **스펙이 실측을
요구한 자리**다.


**Structure Decision**: 디렉터리를 **네 축 + 화면**에 대응시킨다. 이 프로젝트의 반복
실패가 축의 혼선이었으므로, 경계가 디렉터리로 드러나면 「어느 축의 일인가」를 코드에서
바로 물을 수 있다.

**`speaker/`를 `inference/` 밖에 둔 것이 의도적이다.** 화자 판정은 어댑터를 교체해도
같은 판정이 적용되어야 하므로(헌법 원칙 III), 엔진 구현체 안에 두면 어댑터마다 판정이
갈릴 수 있다.

**기존 `src/types/signals.ts`·`src/services/aiService.ts`·`App.tsx`는 계승 대상이
아니다** (001 Assumptions, AGENTS.md). 특히 `aiService.ts`의 고정 fallback 문구는 헌법
원칙 II에 따라 **폐기 대상**이다. 삭제 시점은 구현 단계에서 정한다.

## 실측으로 닫을 자리

각 축 스펙이 **의도적으로 비운** 값이다. 이 계획은 자리만 만들고 값을 정하지 않는다.

| 항목 | 출처 | 성격 |
| --- | --- | --- |
| 항목별 상한·시간대 세분도 | 003 FR-257 | 값이 비어도 US1이 돈다 |
| 규모 판정 임계값 (2~6) | 003 FR-274 | 값이 비어도 US1이 돈다 |
| 입력 구성 규칙 | 004 FR-318 | 값이 비어도 US1이 돈다 |
| 추측의 강도 | 004 FR-331 | 값이 비어도 US1이 돈다 |
| **화자 판정의 표지 목록** | **004 FR-348** | **비면 루프가 닫히지 않는다** |
| 「적음」 확인의 중립성 | 006 | 구현 후 관찰 |

**화자 판정만 성격이 다르다.** 나머지 다섯은 값이 비어도 루프가 돌지만, 판정기가 없으면
추론 결과를 저장할지 판단할 수 없다. 따라서 research.md 결정 1이 **판정의 형태**를
확정했고, quickstart.md 시나리오 8이 **표지 목록을 채울 자리**를 만들었다.

003 FR-257이 「실측 없이 정한 값을 최종값으로 남기지 않을 것」을 요구한다 — 값을 채울
때 관측 결과를 근거로 남긴다.
