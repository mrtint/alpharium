# Feature Specification: 모델 준비 완료 연출 + 캐릭터 작명

**Feature Branch**: `035-model-ready-welcome-naming`

**Created**: 2026-09-07

**Status**: Draft

**Input**: User description: 로드맵 19번 — 캐릭터·VLM 모델의 다운로드·검증이 끝나 `ready`가
되는 순간을 침묵하는 상태 전이가 아니라 "첫 만남"으로 연출한다. 모델이 준비되면
백그라운드에서 가벼운 정상 동작 확인을 한 번 돌리고, 성공하면 환영 화면을 띄운다. 그
흐름에서 사용자가 캐릭터 이름을 직접 짓고, 이후 설정 탭 "일기 작성자" 섹션에서 준비된
캐릭터마다 이름을 바꿀 수 있다.

---

## ⚠️ 헌법 개정 선행 (스펙 착수 전 필수)

이 기능은 헌법(`​.specify/memory/constitution.md`) **원칙 III 「씨앗과 페르소나」**와
정면으로 부딪힌다. 현행 조항:

> - 페르소나는 **사전에 설계되어 코드 안에 있다**(MUST). 사용자가 자유롭게 지어내게
>   하지 않는다(MUST NOT) — 사용자가 만든 페르소나는 씨앗과 어긋났는지 확인할 방법이
>   없다.

이 과제는 페르소나 세 요소(이름·말투·소개) 중 **이름만** 사용자에게 연다. 말투·소개
(`tagline`)·성격 지시는 코드 안 고정값으로 유지한다. 이름은 "글 쓰는 성격"이 아니라
호칭이므로 씨앗과 어긋날 여지가 구조적으로 없다 — 위 조항이 막으려던 위험(사용자
페르소나가 씨앗과 어긋나는 것)에 해당하지 않는다.

**Governance("원칙을 어기려면 헌법을 먼저 고친다. 예외를 코드에 몰래 두지
않는다")에 따라, 이 스펙의 어떤 코드 커밋보다 먼저 헌법 개정 커밋이 선행한다.**
16번(029)이 로스터 조항을, 31번이 같은 방식으로 헌법을 먼저 고친 선례를 따른다.

개정 범위(이름은 안 바뀜, MINOR — 1.1.0 선례 "MUST/MUST NOT 조항이 늘거나 형태가
바뀌면 MINOR"):

- 원칙 III 「씨앗과 페르소나」의 위 조항에 예외를 명시한다:
  **이름은 사용자가 지을 수 있다(MAY). 말투·소개·성격 지시는 여전히 코드 안 고정이며
  사용자가 바꿀 수 없다(MUST NOT). 이름은 호칭이지 씨앗의 서술이 아니므로 씨앗과
  어긋날 수 없다.**
- 사용자가 짓지 않았거나 지운 경우 코드 안 기본 이름으로 폴백한다는 것을 함께 적는다.

이 개정 없이는 아래 US2(작명)를 구현할 수 없다. 개정은 `/speckit-plan` 단계의
첫 번째 Phase(코드 이전)로 잡는다.

## Clarifications

### Session 2026-09-07

- Q: 사용자가 캐릭터 이름을 지을 때 "kanana"나 "exaone-3.5" 같은 모델 식별자류
  문자열을 그대로 입력하도록 허용해야 하나요? (FR-021) → A: 필터링하지 않는다 —
  빈 문자열·공백·글자 수 상한만 검사한다.
- Q: 사용자가 캐릭터 이름을 바꿨을 때 예전 이름으로 쓴 일기의 작성자 표시는 어떻게
  나와야 하나요? (FR-026) → A: 생성 시점 이름을 일기에 스냅샷으로 저장해 그대로
  보인다 — 과거 일기는 "금동이"로 남는다.
- Q: 설정 탭에서 두 번째 캐릭터를 새로 내려받아 준비가 끝났을 때도 첫 만남과 똑같은
  환영 연출을 띄워야 하나요? → A: 첫 실행의 기본 캐릭터만 — 추가 캐릭터의 작명은
  US3(설정 탭 이름 편집)로 커버한다.
- Q: 정상 동작 확인이 모델에 보내는 짧은 입력 문자열은 어디에 두어야 하나요? → A:
  정상 동작 확인 전용 모듈에 고정 상수로 두고, 일기 프롬프트 요소(화자 규칙·신호·
  이름·언어)를 담지 않음을 계약 테스트로 잠근다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 첫 실행에서 캐릭터가 깨어나는 연출 (Priority: P1)

새 사용자가 앱을 처음 설치하고 온보딩(권한 안내 + 필수 에셋 다운로드)을 끝냈다. 지금은
다운로드 진행률 바가 사라지고 곧바로 빈 일기 목록이 나타난다 — 방금 GB 단위 모델을
받았다는 사실도, 그 모델이 살아 있다는 신호도 없다.

이 스토리는 그 침묵을 없앤다. 필수 에셋(기본 캐릭터 모델 + 공용 VLM)이 `ready`가 되면,
앱은 **화면을 켜 둔 채 백그라운드에서 그 캐릭터가 응답하는지 한 번 확인**한다. 확인이
성공하면 "오! 주인님, 반가워요" 톤의 **환영 화면**이 뜬다 — 사람이 미리 써 둔 고정
문구다. 사용자는 여기서 "휴대폰에 새로운 존재가 깃들었다"를 느낀다.

**Why this priority**: 로드맵 19번의 절반이자 이 기능의 정서적 핵심이다. 작명(US2)은
이 환영 흐름 안에서 일어나므로, US1이 없으면 작명이 놓일 자리도 없다. US1만 구현해도
"모델이 준비됐고 살아 있다"는 확인 + 첫 만남 연출이라는 독립적 가치가 있다.

**Independent Test**: `pm clear` 후 앱을 새로 실행 → 온보딩 완주 → 에셋 다운로드 완료
→ 환영 화면이 뜨는 것을 확인. 정상 동작 확인 단계가 실제로 캐릭터를 한 번 돌린다는
것은 로그(추론 호출 1회)로, 응답 텍스트가 화면에 노출되지 않는다는 것은 화면 관찰로
검증한다.

**Acceptance Scenarios**:

1. **Given** 온보딩이 끝나고 기본 캐릭터·VLM 에셋이 모두 `ready`, **When** 앱이 진입
   게이트를 통과하려는 순간, **Then** 홈(일기 목록)이 아니라 환영 화면이 먼저 뜬다.
2. **Given** 환영 화면을 띄우기 전, **When** 정상 동작 확인을 백그라운드에서 돌리는
   동안, **Then** 화면에는 "준비하고 있어요" 수준의 사람이 쓴 고정 대기 문구만 보이고,
   추론이 만들어 내는 토큰·응답 텍스트·경과 시간·토큰 수는 하나도 보이지 않는다.
3. **Given** 정상 동작 확인이 성공(응답이 옴), **When** 확인이 끝나면, **Then** 환영
   화면 본문이 나타나고 다음 단계(작명, US2)로 넘어갈 수 있다.
4. **Given** 정상 동작 확인이 실패(응답이 안 옴 / 모델 손상 / 시간 초과), **When**
   확인이 끝나면, **Then** 환영 화면을 띄우지 않고 "아직 준비 중이에요, 잠시 후 다시
   시도할게요" 수준의 고정 안내를 보이며, 플레이스홀더 일기나 가짜 응답을 만들지
   않는다. 사용자는 이 화면에서 다시 시도하거나 건너뛸 수 있다.
5. **Given** 환영 연출이 이미 한 번 완료됨(첫 실행에서 봤음), **When** 앱을 다시
   실행, **Then** 환영 화면은 다시 뜨지 않고 곧바로 홈으로 간다.

### User Story 2 - 첫 만남에서 캐릭터 이름 짓기 (Priority: P1)

환영 화면에서 캐릭터가 "제 이름을 지어주세요"라고 청한다. 사용자는 텍스트 입력창에
원하는 이름을 적는다(예: "복실이"). 확정하면 그 이름이 저장되고, 이후 앱 전체에서 그
캐릭터는 사용자가 지은 이름으로 불린다 — 일기 목록·상세, 설정 탭 "일기 작성자" 섹션,
그리고 **생성되는 일기의 프롬프트 안 호칭 한 줄**("너는 '복실이'라 불린다.")까지.

사용자가 이름을 비우거나 공백만 넣으면 확정할 수 없다. 이름을 짓지 않고 건너뛰면 코드
안 기본 이름(예: "금동이")으로 폴백한다.

**Why this priority**: 로드맵 19번의 나머지 절반. US1의 환영 흐름 안에 놓이므로 함께
P1이다. 작명 없이 환영 화면만 있으면 "제 이름을 지어주세요"라는 문구가 거짓이 된다.

**Independent Test**: 환영 화면에서 이름 "복실이" 입력 → 확정 → 홈으로 이동 → 일기
목록·설정 탭에서 캐릭터가 "복실이"로 표시되는지 확인. 일기를 하나 생성해 프롬프트
호칭 줄이 "복실이"인지 확인(진단 탭의 프롬프트 미리보기 또는 로그).

> **US1과의 관계**: 작명 화면은 US1이 만든 환영 흐름 **안에** 놓이므로, US2는
> US1 위에서 검증된다(완전히 독립된 슬라이스가 아니다). 대신 US2가 더하는 것
> — 이름 입력·검증·저장과 그 이름이 표시 네 곳과 프롬프트로 흐르는 것 — 은
> US1을 건드리지 않고 독립적으로 테스트된다. **둘을 합친 것이 이 기능의 MVP다.**

**Acceptance Scenarios**:

1. **Given** 환영 화면의 작명 단계, **When** 사용자가 "복실이"를 입력하고 확정,
   **Then** 그 이름이 영속 저장되고 홈으로 이동하며, 이후 이 캐릭터가 등장하는 모든
   화면에서 "복실이"로 표시된다.
2. **Given** 작명 입력창이 비어 있거나 공백만 있음, **When** 사용자가 확정을 시도,
   **Then** 확정 버튼이 비활성이거나 "이름을 입력해 주세요" 안내가 뜨고, 빈 이름은
   저장되지 않는다.
3. **Given** 작명 단계, **When** 사용자가 "건너뛰기"를 선택, **Then** 사용자 지정
   이름 없이 홈으로 이동하고, 캐릭터는 코드 안 기본 이름으로 계속 불린다.
4. **Given** 사용자가 지은 이름이 저장된 상태, **When** 그 캐릭터로 일기를 생성,
   **Then** 프롬프트의 호칭 줄이 사용자 지정 이름을 쓴다. (소개·말투·성격 지시는
   프롬프트에 들어가지 않는다 — 현행과 동일.)
5. **Given** 작명 입력창, **When** 사용자가 상한(글자 수)을 넘겨 입력하려 함,
   **Then** 상한에서 입력이 멈추거나 잘린다.

### User Story 3 - 설정에서 준비된 캐릭터 이름 바꾸기 (Priority: P2)

시간이 지나 사용자가 두 번째 캐릭터를 설정 탭에서 새로 내려받았다. 또는 첫 만남에서
지은 이름이 마음에 안 든다. 사용자는 설정 탭 "일기 작성자" 섹션에서 **준비된(`ready`)
캐릭터**마다 이름을 바꿀 수 있다. 미준비 캐릭터는 이름을 바꿀 수 없다(먼저 받아야
한다).

이름을 바꾸면 그 즉시 "일기 작성자" 목록·일기 목록·상세·진단 화면에 반영되고, 그
캐릭터로 새로 생성하는 일기의 프롬프트 호칭 줄도 바뀐다. 이미 저장된 과거 일기의
본문은 바뀌지 않는다(생성 시점의 텍스트다).

**Why this priority**: 로드맵 19번이 "이후 설정 탭에서 바꿀 수 있게 한다"고 명시한
부분. US1·US2가 첫 실행 경험이라면 US3는 지속적 편집 경로다. 첫 만남 흐름과 독립적으로
테스트·배포 가능하므로 P2로 분리한다.

**Independent Test**: 설정 탭 "일기 작성자"에서 준비된 캐릭터의 이름을 "금동이" →
"복실이"로 변경 → 저장 → 같은 화면·일기 목록·진단 탭에서 "복실이"로 표시되는지 확인.
새 일기 생성 시 프롬프트 호칭 줄이 "복실이"인지 확인.

**Acceptance Scenarios**:

1. **Given** 설정 탭 "일기 작성자" 섹션, 캐릭터 A가 `ready`, **When** 사용자가 A의
   이름을 편집해 새 값으로 확정, **Then** 그 이름이 영속 저장되고 화면이 즉시
   갱신된다.
2. **Given** 캐릭터 B가 미준비(`ready`가 아님), **When** 사용자가 "일기 작성자"에서
   B를 보면, **Then** B의 이름 편집은 불가능하고 "아직 준비되지 않음" 상태만 보인다.
3. **Given** 캐릭터 A의 이름을 사용자가 바꾼 뒤, **When** 그 이름을 다시 비우고
   확정을 시도, **Then** 빈 이름은 거부되고 직전 이름(또는 기본 이름)이 유지된다.
4. **Given** 캐릭터 A의 이름을 "복실이"로 바꿈, **When** A로 과거 하루의 일기를
   새로 생성, **Then** 새 일기의 프롬프트·표시 이름이 "복실이"다. 이전에 "금동이"로
   생성해 저장된 일기는 본문도 작성자 표시도 "금동이" 그대로다(생성 시점 스냅샷).
6. **Given** 이 기능 이전에 저장되어 이름 스냅샷이 없는 옛 일기, **When** 목록·
   상세에서 그 일기를 봄, **Then** 작성자 표시는 그 캐릭터의 **현재 이름 규칙**
   (사용자 지정 이름이 있으면 그것, 없으면 기본 이름)으로 폴백해 보인다 — 빈 이름이
   나오지 않는다.
5. **Given** 사용자가 캐릭터 A의 사용자 지정 이름을 지워 기본값으로 되돌림, **When**
   저장, **Then** A는 코드 안 기본 이름으로 다시 불린다.

### Edge Cases

- **정상 동작 확인이 아주 오래 걸린다**: 콜드 스타트 + 무거운 캐릭터면 응답까지 수십
  초가 걸릴 수 있다. 확인에는 상한 시간을 둔다 — 상한을 넘으면 실패로 간주하고 US1
  시나리오 4의 "아직 준비 중" 안내로 떨어진다. 상한 값은 계획 단계에서 기존 생성
  타임아웃 상수와의 관계로 정한다.
- **환영 연출 도중 앱이 죽거나 백그라운드로 감**: 연출이 완료 표시되지 않았으면 다음
  진입에서 다시 시도한다(진행 중 상태를 저장하지 않는다 — 009의 "고른 하루를 파일에
  남기지 않는다"와 같은 성격). 정상 동작 확인만 다시 돌린다.
- **필수 에셋이 다시 미준비로 떨어짐**(사용자가 모델 파일을 지움): 진입 게이트가
  온보딩(에셋 다운로드)으로 되돌린다(029 FR-020, 현행 동작). 에셋이 다시 `ready`가
  되면 환영 연출을 아직 안 봤을 때에 한해 다시 뜬다.
- **사용자 지정 이름이 코드 안 다른 캐릭터의 기본 이름과 똑같음**(사용자가 "루이"라고
  지음): 허용한다 — 이름은 호칭일 뿐이고 캐릭터 식별자가 아니다. 표시상 두 캐릭터가
  같은 이름이 될 수 있으나 내부 식별자로 구분되므로 기능은 정상 동작한다.
- **사용자가 모델 식별자류 문자열을 이름으로 지음**("kanana", "exaone-3.5"): 허용한다
  (FR-021 확정). 헌법 원칙 III는 "모델 식별자를 사용자 화면에 노출하지 않는다"이지
  "사용자가 그런 문자열을 입력하지 못하게 한다"가 아니다. 사용자가 스스로 지은 이름은
  앱이 노출한 것이 아니다.
- **사용자 지정 이름이 저장 파일에서 깨져 읽힘**: 007 `selected-character.json`의
  선례대로 "읽지 못하면 없는 것"으로 취급하고 코드 안 기본 이름으로 폴백한다. 앱을
  죽이지 않는다.
- **정상 동작 확인이 성공했는데 사용자가 환영 화면을 그냥 닫음**(작명도 건너뛰지 않고
  홈으로): 연출은 완료로 표시한다(다시 안 뜸). 이름은 기본값 유지.

  P4 유지).

  KV 캐시가 낡은 접두사로 남아 새 접두사와 어긋나거나, (b) `buildPrompt()`가 더 이상

  선택한다: **호칭 줄을 고정 접두사에서 제외**하거나, **이름 변경 시 프리필을
  무효화**한다. 어느 쪽이든 018 계약 P8(=`buildPrompt`가 항상 `promptPrefix`로 시작)과

  작명 검증 로직에 로스터·캐릭터 식별자 목록이 유입되지 않았음을 소스 읽기로

- **FR-032**: 작업은 `main`이 아닌 기능 브랜치에서 하고 PR로 머지한다(MUST).

### Key Entities *(include if feature involves data)*

- **사용자 지정 캐릭터 이름(Custom Character Names)**: 캐릭터 내부 식별자 → 사용자가
  지은 이름의 매핑. 일부 캐릭터만 값이 있을 수 있다(안 지었으면 없음). 값이 없거나
  깨졌으면 코드 안 기본 이름으로 폴백. 일기 디렉터리 밖 별도 파일에 영속.
- **환영 연출 완료 플래그(Welcome Ceremony Completed Flag)**: 첫 만남 연출을 이미
  통과했는지 나타내는 불리언. 영속. 이 값이 참이면 환영 흐름을 다시 띄우지 않는다.
  진행 중 상태는 저장하지 않는다.
- **정상 동작 확인 결과(Liveness Check Outcome)**: 세션 내 임시 상태 —
  "확인 중 / 성공 / 실패". 영속하지 않는다. 실패는 텍스트를 담지 않는다.
- **일기의 작성자 이름 스냅샷(Entry Author Name Snapshot)**: 저장된 일기 하나에
  딸린 **표시 이름 문자열 하나**. 생성 시점의 사실이며 이후 갱신되지 않는다.
  옵셔널 — 이 기능 이전 일기에는 없고, 없으면 현재 이름 규칙으로 폴백한다. 소급
  생성하지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 새 설치 후 온보딩·에셋 다운로드를 끝낸 사용자의 100%가, 홈에 도달하기
  전에 환영 화면 또는 "아직 준비 중" 안내 중 하나를 본다(침묵하는 전이가 0%).
- **SC-002**: 환영 흐름 어느 화면에서도 추론이 생성한 텍스트·경과 시간·토큰 수·모델
  식별자가 노출되지 않는다(관찰로 0건 확인). 정상 동작 확인의 응답 텍스트는 저장소·
  로그에도 남지 않는다.
- **SC-002a**: 정상 동작 확인 입력 문자열에 일기 프롬프트 요소(화자 규칙·신호·캐릭터
  이름·출력 언어·제목 지시문)가 하나도 섞이지 않았음이 계약 테스트로 확인되고, 위반을
  주입하면 실제로 잡힌다.
- **SC-003**: 첫 만남에서 이름을 지은 사용자가 홈에 도달했을 때, 그 이름이 일기 목록·
  설정 "일기 작성자"·진단 화면·다음 생성 일기의 프롬프트 호칭 줄 **네 곳 모두**에
  일관되게 나타난다.
- **SC-004**: 사용자가 설정에서 준비된 캐릭터의 이름을 바꾸면, 저장 후 앱을 재실행
  해도 새 이름이 유지되고, 위 네 곳에 반영된다.
- **SC-005**: 사용자 지정 이름을 지우거나 짓지 않은 캐릭터는 코드 안 기본 이름(금동이
  등)으로 정확히 폴백하며, 빈 이름이 어느 화면에도 표시되지 않는다.
- **SC-005a**: 이름을 바꾼 뒤에도 **바꾸기 전에 생성된 일기의 작성자 표시가 옛
  이름 그대로**이고, 바꾼 뒤 생성한 일기는 새 이름으로 표시된다 — 같은 목록에서
  두 이름이 각각의 일기에 정확히 붙는다. 이 기능 이전에 저장된 일기(스냅샷 없음)는
  현재 이름으로 표시되며 빈 이름이 나오지 않는다.
- **SC-006**: 기기 없는 테스트(`npm test`)가 전부 통과하고, 새 규칙마다 위반 주입이
  실제로 잡힌다(호칭 줄 단일 통과 지점, 접두사-프리필 상호작용, 화면의 모델 정보
  미노출).
- **SC-007**: 실기기(SM-S901N, debug)에서 첫 실행 → 환영 → 작명 → 홈 전체 흐름과,
  설정 탭 이름 변경 → 생성 일기 프롬프트 반영이 각각 최소 1회 관측된다. 정상 동작
  확인 실패 갈래는 모델 손상으로 재현하거나 계약 테스트로 갈음한다.

## Assumptions

- **선행 인프라 재사용**: 029가 만든 온보딩 "필수 에셋 다운로드" 단계(`src/onboarding/
  essential-assets.ts`, `essential-assets-port.ts`)와 설정 탭 "일기 작성자" 섹션
  (`src/ui/AuthorPicker.tsx`, 034에서 NativeWind 이관됨)을 확장한다 — 새로 만들지
  않는다.
- **진입 게이트 확장**: 현행 `shouldShowOnboarding(flag, essentialAssetsReady)`
  다음에 "환영 연출 완료 플래그" 판정이 얹힌다. 게이트는 온보딩 → (환영 연출) → 홈
  순서다. 계획 단계에서 이 판정을 순수 함수로 뗀다(021·029의 `decision.ts` 선례).
- **정상 동작 확인의 형태**: 로드맵 19번이 "18번의 `prewarm(character)`으로 갈음할지
  별도 호출을 둘지"를 열어 두었다. 이 스펙은 **응답이 왔는지 판정할 수 있어야 한다**는
  요구(FR-003)만 고정하고, `prewarm()`(반환값 없음)으로는 성공/실패를 알 수 없으므로
  **`run()` 계열의 짧은 호출**을 쓰되 `RunResult` 경계를 넓히지 않는 방향으로 계획
  단계에서 확정한다. 입력은 전용 고정 상수(FR-003a)이고, 응답 텍스트는 판정 직후
  버린다(FR-004a).
- **새 네이티브 모듈 없음**: 기존 추론 엔진·`expo-file-system`·화면 컴포넌트만
  쓴다. 따라서 debug 실기기 1회로 충분하다(012 기준, release 재확인 불필요).
- **기본 캐릭터**(Q3 확정): 029의 `ONBOARDING_DEFAULT_CHARACTER`(quiet / 금동이).
  첫 만남 연출과 정상 동작 확인의 대상은 **이 캐릭터 하나뿐**이다(FR-002a). 이후
  설정 탭에서 추가로 받는 캐릭터에는 환영 연출도, 정상 동작 확인도 붙지 않는다 —
  이 스펙 범위 밖이며, 필요해지면 별도 스펙에서 다룬다. 추가 캐릭터의 이름 짓기는
  US3가 담당한다.
- **연출 문구는 전부 사람이 쓴 고정 텍스트**: "반가워요", "이름을 지어주세요", "아직
  준비 중이에요" 등은 코드 안 한국어 상수다. 캐릭터별로 다르게 하지 않는다(014
  TITLE_INSTRUCTION이 캐릭터별 지시문을 두지 않은 것과 같은 판단) — 계획 단계에서
  최종 확정.
- **과거 일기 표시 = 이름 스냅샷**(Q2 확정): 저장된 일기에 **생성 시점의 작성자 표시
  이름**을 옵셔널 필드로 더한다. 현행 `DiaryEntry`가 `title?`·`photos?`·`timing?`·
  `placeName?` 네 개의 옵셔널 필드를 후속 스펙에서 차례로 더한 선례를 그대로 따른다
  (옛 파일에 키가 없어도 읽히고, 없으면 폴백). 새 저장 계층·마이그레이션 코드를 만들지
  않는다.
