# 091 — 검증 절차

기기 iPhone 14, **무선 연결**(같은 Wi-Fi, `transportType: localNetwork`) — 선은 충전이다. 통로는 090 quickstart·AGENTS 090.

1. `npm test`·`npm run lint`.
2. **측정 빌드**(요청 둘 + `wake`): prebuild --clean → 개발 환경 Release → 무선 설치 → 한 번 앞에서 띄워 요청 제출 → 충전기 없이 하루. 시도 기록의 `· 배터리` 줄 수·시각, `systemCrashLogs`.
3. **느린 쓰기 빌드**: 같은 절차 + 안 쓴 지난 날(사진 4~9장). 배터리 깨움에서 `백그라운드 · 썼음 · 뒤에서 · 배터리`, 일기 `timing`, `cpu_resource_fatal` 없음, 실패·만료 줄.
4. 충전 깨움 회귀: 충전 중 깨움이 090 수준 시간(SC-003).
5. 결과 → 「실측」, FR-008 판단.

## 실측

### 2026-10-18 낮 — 측정·느린 쓰기 빌드 (iPhone 14, 무선 연결, 충전기·맥 선 없음 — 12:38부터)

- **측정 빌드**(12:59 설치, 요청 둘 + `wake`): 13:49까지 약 50분 동안 **배터리 요청 깨움 0회**(백그라운드 줄 없음). 충전 중에는 같은 앱이 약 15분마다 깨웠다(090) — 배터리 상태에서는 확실히 드물다. 하루 측정은 이어 간다.
- **느린 쓰기 — lldb 강제 실행으로 확인**(앱이 앞이라 CPU 감시는 걸리지 않는다 — 감시 아래 생존은 이것으로 판정하지 않는다): `_simulateLaunchForTaskWithIdentifier:@"com.expo.modules.backgroundtask.processing.battery"` → 처리기가 `pocketlog.bgWakeIdentifier`에 배터리 식별자를 남기고(`Library/Preferences` plist로 확인), 태스크가 `wake: battery`를 읽어 시작 줄에 실었다.
  - 13:53 실행: `백그라운드 · 썼음 · 앞에서 · 배터리`, 사진 8장 읽기 64.1초 · 본문 83.8초.
  - 13:59 실행(`devicectl … --console`로 네이티브 출력을 봄): **두 모델 모두 `Attached ggml threadpool (n_threads=1, n_threads_batch=1)`**, 본문은 **32토큰 조각 15번**(조각마다 `prompt eval … 1 tokens` — 앞부분 KV 재사용), 마지막에 제목 질문. 사진 읽기 62.9초 · 본문 47.3초, 본문은 이어진 문장의 정상 일기(판정 통과).
  - 스레드 1의 속도: 본문 프리필 약 62토큰/초(첫 조각), 생성 약 7.5토큰/초. 쉼(× 0.5)을 넣고도 전체 약 2분 — 예산 만료 걱정은 크지 않다(표본 2).
- 진단 함정: 기록을 읽는 임시 스크립트가 `wake` 칸을 출력하지 않아 「꼬리가 없다」고 잘못 봤다 — 원본 JSON을 본다.

### 2026-10-18 15:18 ~ 10-19 22:00 — 배터리 상태 깨움 측정 (SC-002)

- 조건: 느린 쓰기 빌드, 안 쓴 지난 날(10-17, 사진 9장) 하나, 프로세스 끝냄, 화면 잠금, **충전하지 않음**(소유자 확인 — 내내 가방 속), Wi-Fi는 대부분 연결 안 됨(가방 속 — 요청은 네트워크를 요구하지 않는다).
- 결과: **약 31시간 동안 백그라운드 깨움 0회**(배터리·충전 요청 모두, 시도 기록에 `백그라운드` 줄 없음, 10-17 미작성, 새 크래시·Jetsam 없음). 12:38~14:41(측정 빌드)의 약 2시간도 0회.
- 요청은 iOS에 있다: 22:05 `getPendingTaskRequestsWithCompletionHandler`로 읽은 대기 목록에 `com.expo.modules.backgroundtask.processing`(`requiresExternalPower=1`)와 `….battery`(`requiresExternalPower=0, requiresNetworkConnectivity=0`)가 둘 다 있었다. 다만 읽으려고 앱을 띄운 순간 JS가 요청을 다시 제출한 뒤의 목록이라(`earliestBeginDate` = 띄운 시각 + 15분), 「31시간 내내 대기 중이었다」의 직접 증거는 아니다 — 같은 코드가 15:18에도 제출했다.
- 판정: **이 기기·이 사용 습관에서 iOS는 배터리 상태의 처리 작업을 깨우지 않았다.** 느린 쓰기는 강제 실행으로 완주했으므로 막힌 자리는 OS의 깨움이다 — 코드로 풀 수 없다(설계 「남는 위험」 첫 줄). SC-001은 미확인으로 남고 FR-008에 따라 배터리 행 문구는 090 문구를 유지한다.
- 22:05 이후 소유자가 충전기에 꽂았다 — 충전 요청 깨움(090 경로)이 다시 오는지는 이어서 본다.
