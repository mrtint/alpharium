## Overview

로드맵 과제 하나를 구현 완료까지 끌고 가는 파이프라인. speckit이 "선택"이라 부르는 clarify·analyze·converge와 구현 후 **코드 리뷰**는 **이 프로젝트에서는 필수**다. 단, 「규모 판정」에서 경량으로 판정된 과제는 「경량 트랙」을 탄다.

**규칙의 문자를 어기는 것이 곧 정신을 어기는 것이다.** 필수 단계를 "같은 효과의 다른 방법"(가정 명시로 clarify 대체, 수동 대조로 analyze/converge 대체, 자체 검토로 코드 리뷰 대체 등)으로 갈음하는 것도 생략이며, 금지다. 허용되는 생략은 「규모 판정」을 통과한 경량 트랙의 생략뿐이다. 스킬을 호출하는 것 자체가 단계다.

## 적용 범위

`docs/roadmap/README.md`의 「진행 예정 과제」만 이 파이프라인을 탄다. 버그픽스·리팩토링·문서·설정 작업은 파이프라인 없이 그냥 작업한다.

## Pipeline — 전체 트랙 (순서 고정 — 생략·대체·순서변경 금지)

1. **과제 선택**: 로드맵에서 대상 과제 확인. 사용자가 지정하지 않았으면 질문한다. 과제에 목적이 적혀 있지 않으면 brainstorming 초입에서 목표부터 확인한다. 적혀 있으면 그 이유를 다시 묻지 않는다 — 처음의 열린 질문은 로드맵에 없는 것(구체적인 장면, 성공 모습)을 묻는다. 이어서 아래 「규모 판정」으로 트랙을 정한다. 경량이면 「경량 트랙」으로 간다. `git branch --show-current`가 `main`이면 **여기서** 작업 브랜치를 만든다(`main` 직접 커밋 금지 — AGENTS.md).
2. **brainstorming (superpowers:brainstorming)** 호출 → 과제를 구체화한 설계문서를 `docs/superpowers/specs/YYYY-MM-DD-<slug>-design.md`로 저장. 이미 분해 설계 문서가 그 과제를 다루고 있으면 그 문서를 brainstorming의 입력으로 삼는다(brainstorming 자체는 생략하지 않는다). 질문은 아래 「질문 규약」을 따른다.
3. **speckit-specify** — 설계문서를 입력으로 실행. 생성된 스펙 번호를 로드맵의 해당 과제에 기록하고(스펙이 열린 뒤에만 번호를 적는다), 브랜치 이름을 `NNN-<slug>`로 바꾼다(`git branch -m`).
4. **speckit-clarify** — 필수. 아래 「질문 규약」의 호출 인자로 부른다. 질문 0개로 끝나도 되고, 질문이 없으면 완료 보고를 따로 보내지 않는다(「중간 보고」).
5. **speckit-plan** 실행.
6. **설계 구간 (한 흐름으로)**: speckit-tasks → **analyze 루프**:
   1. **speckit-analyze** 호출.
   2. 보고서의 지적이 **0건**이면 루프 종료(예외는 5뿐). 심각도와 무관하다 — LOW 1건도 수정사항이다.
   3. 지적이 1건 이상이면 전부 spec/plan/tasks에 즉시 반영하고(analyze가 remediation 승인을 묻더라도 묻지 않고 반영) **1로 돌아간다.** 반영이 새 지적을 만들 수 있으므로, 반영한 뒤에는 언제나 다시 analyze다.
   4. 사용자 결정 없이는 반영할 수 없는 지적, 또는 지적이 틀렸다고 판단한 지적이 있으면 그 지적만 사용자에게 묻고, 답을 반영한 뒤 1로 돌아간다. 스스로 무시하고 루프를 끝내지 않는다.
   5. 사용자가 "반영하지 않는다"고 정한 지적은 그 결정을 spec이나 plan에 한 줄로 남긴다. 이후 회차에 남은 지적이 **전부 사용자가 이미 반영하지 않기로 정한 것**이면 루프를 끝낸다. 하나라도 새 지적이 있으면 3으로 간다.

   루프가 끝나면 산출물, **analyze 회차별 지적 수**(예: 5 → 2 → 0), 사용자가 반영하지 않기로 정한 지적을 커밋 시점 1 확인 메시지에 짧게 담는다(「중간 보고」).
7. **구현 구간 (한 흐름으로)**: speckit-implement → **converge 루프** → **코드 리뷰**:
   1. **speckit-implement** 실행하여 tasks.md의 초기 태스크들을 구현 및 단위/계약 테스트 작성.
   2. **speckit-converge 루프**:
      1. **speckit-converge** 호출.
      2. 누락된 요구사항이나 미구현 사항이 없어 추가 태스크가 0건(`converged`)이면 루프 종료.
      3. 새 태스크가 `tasks.md`에 추가되면 해당 태스크를 구현하고 테스트를 검증한 뒤 **다시 speckit-converge를 호출한다.**
      4. 사용자의 의도적 결정으로 구현하지 않기로 한 항목은 `tasks.md`에 사유와 함께 기록하고 converge를 마무리한다.
   3. **코드 리뷰 (requesting-code-review 호출)**:
      - converge가 완료되어 스펙/계획과 코드가 완전히 일치한 상태(`converged`)에서만 코드 리뷰를 호출한다(미구현 사항에 대한 불필요한 리뷰 지적으로 토큰/시간 낭비 방지).
      - 리뷰어가 제시한 지적 중 **Critical(Must Fix)** 및 **Important(Should Fix)** 항목은 즉시 수정하고 테스트를 다시 돌린다.
      - 수정 후 전체 테스트 및 린트 통과를 확인하고, 최종 리뷰 결과가 머지 가능(Ready to merge: Yes) 상태임을 확인한다.
   구간 중간에는 사용자 승인을 기다리지 않는다(상호작용 지점은 brainstorming과 설계 구간 커밋 확인으로 충분). 구현 구간의 종료 보고는 최종 보고로 갈음한다.
8. **완료 처리**: `npm test`·`npm run lint`를 실제로 실행해 통과를 확인하고, dev 빌드로 실기기에서 최소 1회 확인한다(헌법 원칙 V — 건너뛴 실기기 테스트는 통과가 아니다. 결과 안 보고 "완료" 주장 금지). 그 뒤 로드맵의 「진행 예정 과제」에서 해당 과제를 빼고 「완료 이력」 표에 스펙 번호와 한 줄로 옮긴다. 커밋 메시지에 스펙 번호를 남긴다(예: `docs: 로드맵에서 049 완료 과제를 이력으로 옮김`).

## 규모 판정 (1단계)

작은 과제에 전체 트랙의 산출물(plan 하위 문서·tasks·analyze 루프·converge 루프)을 만드는 비용이 작업 자체보다 커지는 것을 막는 판정이다. 판정은 아래 조건으로만 한다 — "작아 보인다"는 느낌으로 정하지 않는다.

- **경량**: 다음을 모두 만족한다.
  - 새 데이터 모델(엔티티·스키마·저장 구조), 외부 연동(새로 호출하는 API·서비스·시스템), API·이벤트 계약 변경이 없다.
  - 예상 변경 파일이 5개 이하다(테스트 제외). 레포를 실제로 훑어 셀 수 있는 만큼 센다.
  - 수용 기준이 3개 이하다.
- **전체**: 하나라도 만족하지 않거나, 판단할 근거가 부족하면 전체 트랙이다.
- 판정 결과와 조건별 근거를 brainstorming 첫 메시지에 짧게 보인다. 사용자가 뒤집으면 따른다. 판정 때문에 따로 멈추지 않는다.

## 경량 트랙

1. **과제 선택·규모 판정**: 전체 트랙 1단계와 같다(브랜치 생성 포함).
2. **brainstorming** — 전체 트랙 2단계와 같되, 설계문서는 목적·수용 기준·결정만 한 화면 분량으로 쓴다. 화면 배치를 고를 갈림길이 없으면 목업(visual companion)을 제안하지 않는다.
3. **speckit-specify** — 전체 트랙 3단계와 같다.
4. **speckit-clarify** — 필수. 전체 트랙 4단계와 같다.
5. **구현 구간 (한 흐름으로)**: spec 의 수용 기준을 기준으로 직접 구현한다(plan·tasks 가 없으므로 speckit-implement 를 쓰지 않는다. 수용 기준마다 테스트를 하나 이상 둔다) → **코드 리뷰** — 전체 트랙 7단계 3의 코드 리뷰 규칙과 같다.
6. **완료 처리**: 전체 트랙 8단계와 같다(`npm test`·`npm run lint`·실기기 확인 포함).

생략하는 것: speckit-plan(와 research·data-model·contracts·quickstart), speckit-tasks, analyze 루프, converge 루프. 유지하는 것: 질문 규약·결정 표·코드 리뷰·실기기 확인·커밋 시점·최종 보고.

**승격**: 진행 중 경량 조건이 하나라도 깨지면(새 엔티티·외부 연동이 필요해짐, 변경 파일이 5개를 넘음, 수용 기준이 늘어남) 그 자리에서 멈추고 사용자에게 알린 뒤 전체 트랙 5단계(speckit-plan)부터 이어간다. 이미 쓴 코드는 버리지 않고 tasks 에 반영한다.

## 중간 보고

사용자의 답을 기다리지 않는 보고(specify·clarify·plan·tasks·analyze 완료)는 따로 보내지 않고 커밋 시점 1 확인 메시지에 몇 줄로 모은다. 확인 요청 바로 앞에 답이 필요 없는 메시지가 하나 더 있으면 사용자는 읽을 것만 늘어난다. clarify 가 질문해야 할 때, analyze 루프 4처럼 사용자 결정이 필요할 때만 따로 묻는다.

brainstorming 의 규모 판정(Size the Work)은 1단계 규모 판정으로 갈음한다 — 다시 판정하거나 크기를 다시 안내하지 않는다.

## 질문 규약 (2·4단계)

결정은 에이전트가 하고, 사용자는 설계 구간 커밋 확인 때 결정 표를 훑어 틀린 것만 뒤집는다. 질문은 에이전트가 근거로 정할 수 없는 것에만 쓴다.

- **묻는 기준**: 답이 사용자만 아는 정보(정책·조직 사정·운영 현실·범위에 대한 의지·개인 선호)에 달려 있고, 이미 정한 것(설계문서·앞선 답·프로젝트 규칙·헌법·레포 규약·선례)으로 정할 수 없을 때만 묻는다. 기술적 갈림길은 영향이 커도 묻지 않고 정한 뒤 근거를 남긴다. 운영 현실은 저장소·프롬프트로 확인할 수 없는 외부 시스템의 설정·절차·제약(예: 스토어 심사 정책, 실기기 OS 설정 제약)이다 — 결정이 이것에 기대면 기술적 갈림길로 보지 않는다.
- **형식**: 처음의 탐색 질문(왜·목표)은 brainstorming 대로 열린 질문이다. 결정 질문(대화 중, 빌더 점검이 있으면 그 「theirs」 묶음)은 묻는 기준을 통과한 것만 선택지 표 + 추천 한 줄로 내고 글자 하나로 답하게 한다.
- **clarify 호출 인자**: 「설계문서에서 정한 것은 다시 묻지 않는다. 답이 사용자만 아는 정보(정책·조직 사정·운영 현실·범위 의지·선호)에 달려 있고 기존 결정으로 못 정하는 것만 묻는다. 기술적 갈림길은 영향이 커도 묻지 않고 정한다. 묻지 않고 정한 것은 Clarifications 에 `(에이전트 판단 · 근거: …)` 로 기록한다.」
- **결정 표 공개**: 설계 구간 커밋(커밋 시점 1) 확인 요청에 표 「결정 · 근거 · 뒤집으면 바뀌는 것」을 함께 보인다 — brainstorming·clarify 에서 스스로 정한 것 모두. "뒤집으면 바뀌는 것"이 큰 순서로 정렬한다. 커밋 승인이 곧 표 승인이다. 사용자가 뒤집으면 spec·plan·tasks 에 반영한 뒤 커밋한다(전체 트랙이면 반영 뒤 analyze 루프를 다시 돈다). 최종 보고에도 같은 표를 싣는다.
- **표에서 놓친 결정**: 구현 뒤에 드러나면 사용자가 재구현을 요청한다. 이를 막으려고 질문을 늘리지 않는다.

## 커밋 시점 (한 커밋 = 한 논리적 변경)

정확히 3회, 각각 실행 전 사용자 확인을 받는다. 커밋 메시지는 한국어:
1. 설계 구간 종료 후(경량 트랙은 clarify 직후) — 스펙 산출물(`specs/NNN-*/`, `docs/superpowers/specs/`). 확인 요청에 결정 표와 중간 보고를 함께 담는다(「질문 규약」·「중간 보고」).
2. 구현 구간 종료 후 — 구현 코드 (converge 수렴 및 코드 리뷰 반영 완료 후)
3. 완료 처리 — 로드맵 갱신 (구현 커밋과 분리)

## 최종 보고에 반드시 포함

- 트랙(경량/전체)과 판정 근거, 승격했다면 그 시점과 이유
- 에이전트가 묻지 않고 정한 항목 표 (결정 · 근거 · 뒤집으면 바뀌는 것)
- converge 이후 남은 지적사항(구현 안 한 것) 목록 및 converge 회차별 추가 태스크 수
- 코드 리뷰 결과 요약(지적 사항 및 수정 내용)
- clarify에서 확정된 주요 결정
- 남은 리스크(실기기 미확인 잔여 포함)

## Rationalization table

| 유혹 | 현실 |
|------|------|
| "시간 없으니 핵심 단계만 밟자" | 이 파이프라인 전체가 핵심 단계다. 막연한 시간 압박은 생략 사유가 아니다. 사용자가 특정 단계를 이름 집어 "건너뛰어"라고 명시할 때만 예외. |
| "specify가 요구사항 확인을 내장하니 brainstorming 생략" | specify는 문서 생성이지 발산·수렴 탐색이 아니다. 설계문서 없이 specify에 들어가지 않는다. |
| "가정을 스펙에 적고 컨펌받으면 clarify와 같다" | 대체 절차 금지. speckit-clarify를 호출하는 것이 단계다. |
| "brainstorming 에서 다 물었으니 clarify 는 호출하지 않는다" | 호출하는 것이 단계다. 질문이 0개여도 스스로 정한 항목의 기록은 clarify 가 한다. |
| "영향이 큰 기술 결정이니 물어보자" | 근거로 정할 수 있으면 정하고 표 맨 위에 싣는다. 묻는 것은 사용자만 아는 정보뿐이다. |
| "뻔한 결정이라 표에서도 뺀다" | 묻지 않은 결정일수록 표에 싣는다. 뻔하다는 판단이 틀렸을 때 사용자가 볼 곳이 그 표뿐이다. |
| "작아 보이니 경량으로 가자" | 판정은 세 조건으로만 한다. 근거가 부족하면 전체 트랙이다. |
| "경량이지만 analyze·converge 루프도 돌리면 더 안전하다" | 경량 트랙의 생략은 규칙이다. 걱정되는 조건이 있으면 판정을 전체로 다시 한다. |
| "경량으로 시작했으니 조건이 깨져도 끝까지 경량으로" | 조건이 깨지면 그 자리에서 승격한다. |
| "좁은 기능이라 clarify/analyze는 건질 게 없다" | 건질 게 없으면 싸게 끝난다. 건너뛸지 판단하는 비용이 실행 비용보다 크다. |
| "analyze 필수 1회는 이미 채웠다, 반영했으니 끝" | analyze는 횟수가 아니라 지적 0건이 종료 조건이다. 반영했으면 다시 analyze. |
| "LOW/MEDIUM만 남았고 analyze도 proceed해도 된다고 한다" | 그것은 speckit의 기본값이다. 이 파이프라인은 심각도와 무관하게 0건까지 간다. |
| "반영한 부분만 내가 훑어보면 analyze를 또 돌릴 필요 없다" | 대체 절차 금지. 다시 speckit-analyze를 호출하는 것이 단계다. |
| "converge 대신 인수조건 수동 대조" | 대체 절차 금지. speckit-converge 호출. |
| "converge 1회 돌렸으니 추가 태스크 구현 후 바로 끝내자" | 구현 후 다시 converge를 호출해 추가 태스크 0건(`converged`)을 확인해야 루프가 끝난다. |
| "converge 다 안 끝났지만 코드 리뷰 먼저 받자" | converge가 끝나기 전에 리뷰를 받으면 미구현 지적에 토큰과 시간을 낭비한다. 스펙 수렴 완료 후에 코드 리뷰를 진행한다. |
| "코드 리뷰 지적 중 Important는 머지 후 나중에 고치자" | Critical과 Important는 머지 전 수정 필수다. 수정한 뒤 전체 테스트 통과를 확인한다. |
| "자체 검토로 코드 리뷰를 대신하자" | 대체 절차 금지. requesting-code-review를 호출해 독립적 리뷰를 받는 것이 단계다. |

## Red Flags — 이 생각이 들면 멈추고 파이프라인으로 복귀

- 전체 트랙으로 판정된 과제에서 "이 단계는 이 과제엔 오버킬이다" (그렇게 느껴지면 판정 조건을 다시 대조한다)
- "같은 효과를 더 빨리 낼 수 있다"
- "speckit 문서에는 선택이라고 되어 있다"
- analyze 보고서에 지적이 남아 있는데 설계 구간 종료 보고를 쓰고 있다
- converge에서 추가 태스크가 나왔는데 재converge 없이 구현 구간을 끝내려 하고 있다
- converge 수렴 전에 코드 리뷰를 호출하거나, 코드 리뷰 없이 2차 커밋을 하려 하고 있다
- 필수 단계를 스킬 호출 없이 수동 절차로 대신하려는 계획을 세우고 있다
