# Feature Specification: 첫 실행 모델 내려받기 — 모바일 데이터면 알리고 고르게 하기

**Feature Branch**: `074-wifi-download-consent`

**Created**: 2026-10-11

**Status**: Draft

**Input**: User description: "docs/superpowers/specs/2026-10-11-wifi-download-consent-design.md 를 입력으로 한다 (승인됨). 첫 실행 모델 내려받기 시 기기가 모바일 데이터(CELLULAR)로 확인되면 기존 다운로드 동의 대화상자(045)를 모바일 갈래로 바꿔 「모바일 데이터로 받기」/「나중에 받기」를 고르게 한다. 나중에 받기는 세션 로컬 상태로 아무것도 받지 않고 대기 화면(다시 확인하기 + 전경 복귀 재판정)에 머문다. 그 외 연결은 기존 [받을게요] 하나 그대로. 모바일 갈래 본문에만 받을 양 표시(045 FR-003 범위 좁힘). 첫 실행 단계 판정의 단계·우선순위 불변. 받는 도중 전환은 범위 밖. 핫스팟 Wi-Fi 한계 문서화."

## 근거와 원본

- **설계**: `docs/superpowers/specs/2026-10-11-wifi-download-consent-design.md`(저장소 소유자 승인, 2026-10-11).
- **조사**: `docs/superpowers/specs/2026-10-11-wifi-download-research.md`(플랫폼·타 앱 관행, 출처·확인일, 미확인 표시).
- **로드맵 과제**: 「첫 실행 모델 내려받기 — Wi-Fi가 아니면 알리고 고르게 하기」. 완료 조건의 「앱 닫기」는 소유자 결정(2026-10-11)으로 「나중에 받기」가 되었다.
- **문제**: 첫 실행의 다운로드 동의 대화상자(045)는 [받을게요] 하나뿐이라, 모바일 데이터에서도 약 2GB를 사용자가 알지 못한 채 그대로 받는다. 연결 종류를 보는 곳은 설정의 「모듈 다시 받기」(059)뿐이다.
- **범위 밖**: 받는 도중 Wi-Fi가 끊겨 모바일 데이터로 넘어가는 경우, 설정의 「Wi-Fi에서만」 옵션, 핫스팟 Wi-Fi(과금 연결)의 판별, 「모듈 다시 받기」(059)의 문구 변경, 앱을 스스로 닫는 동작.

## 용어

- **모바일 데이터 상태**: 기기의 현재 연결 종류가 모바일 데이터(셀룰러)로 **확인된** 상태. 다른 모든 경우(Wi-Fi, 연결 종류를 못 읽음, 연결 없음, 이더넷, VPN 등)는 이 상태가 아니다.
- **표준 동의**: 045의 동의 대화상자 — [받을게요] 하나뿐이다.
- **모바일 동의**: 이번에 더하는 모바일 데이터용 동의 — 「모바일 데이터로 받기」와 「나중에 받기」 둘이다.
- **대기 화면**: 사용자가 「나중에 받기」를 고른 뒤 보이는, 아무것도 받지 않고 기다리는 안내 화면.

## Clarifications

### Session 2026-10-11 (소유자 결정)

- Q: 「Wi-Fi가 아님」의 판정 범위? → A: **모바일 데이터로 확인될 때만.** 모르거나 연결 없음이면 모달 없이 지금처럼 진행(원칙 V).
- Q: 기존 동의 대화상자와 합칠지? → A: **합친다.** 첫 실행 단계 판정의 단계와 우선순위는 그대로다.
- Q: 두 번째 선택지? → A: 플랫폼 구분 없이 **「나중에 받기」** — 아무것도 받지 않고 앱은 열린 채 대기 화면에 머문다.
- Q: 받는 도중 Wi-Fi→모바일 전환? → A: **범위 밖.** 알려진 한계로 문서화한다.

### Session 2026-10-11 (clarify)

- Q: 연결 종류를 읽는 동안 응답이 끝나지 않으면? → A: **3초 한도 후 「모름」으로 보고 표준 동의를 띄운다.** 받을 양을 읽는 데도 따로 3초 한도를 두며, 넘으면 양 없이 모바일 동의를 띄운다.

## User Scenarios & Testing _(mandatory)_

사용자는 포켓로그를 처음 설치해 첫 실행을 하는 사람이다.

### User Story 1 - 모바일 데이터에서는 알고 나서 받는다 (Priority: P1)

모바일 데이터로 첫 실행을 하면, 받기 전에 「지금 모바일 데이터로 연결돼 있고 약 2GB를 받는다」는 것을 알려 주고 사용자가 「모바일 데이터로 받기」와 「나중에 받기」 중에서 고른다. Wi-Fi 등 그 밖의 상태에서는 지금과 똑같이 [받을게요] 하나뿐이다.

**Why this priority**: 요금이 걸린 결정을 사용자가 모르게 내려 주는 것이 이 과제가 고치려는 문제의 전부다.

**Independent Test**: 연결 종류를 바꿔 가며 첫 실행의 동의 단계에 들어가 본다 — 모바일 데이터일 때만 모바일 동의가 뜨고 받을 양이 보이며, 그 밖에는 표준 동의가 그대로 뜬다.

**Acceptance Scenarios**:

1. **Given** 모바일 데이터 상태에서 첫 실행의 동의 단계, **When** 단계에 들어가면, **Then** 모바일 동의가 뜨고 「모바일 데이터로 받기」와 「나중에 받기」 두 버튼이 있으며 받을 양이 본문에 보인다.
2. **Given** 모바일 동의, **When** 「모바일 데이터로 받기」를 누르면, **Then** 표준 동의의 [받을게요]와 똑같이 동의가 저장되고 내려받기가 시작된다.
3. **Given** Wi-Fi 상태, **When** 동의 단계에 들어가면, **Then** 모바일 동의가 뜨지 않고 표준 동의 [받을게요]가 지금과 같은 문구·모양으로 뜬다.
4. **Given** 연결 종류를 읽지 못함·연결 없음·이더넷·VPN 상태, **When** 동의 단계에 들어가면, **Then** 표준 동의가 뜬다(모바일 데이터로 단정하지 않는다).
5. **Given** 받을 양을 읽지 못함, **When** 모바일 동의가 뜨면, **Then** 양 없이 같은 문구가 보이고 용량을 지어내지 않는다.

---

### User Story 2 - 「나중에 받기」는 막다른 길이 아니다 (Priority: P1)

「나중에 받기」를 고르면 아무것도 받지 않고 앱은 열려 있다. 안내 화면이 Wi-Fi에서 받으라고 알리고, 사용자가 연결을 바꾼 뒤 「다시 확인하기」를 누르거나 앱으로 돌아오면 연결을 다시 읽어 알맞은 동의가 뜬다.

**Why this priority**: 선택지가 하나라도 사용자를 갇히게 하면 안 된다. 앱을 닫을 공식 방법이 없는 플랫폼(iOS)에서도 같은 동작이어야 한다.

**Independent Test**: 모바일 동의에서 「나중에 받기」 → 저장 공간에 모델 파일이 생기지 않음 → 연결을 Wi-Fi로 바꾸고 「다시 확인하기」 → 표준 동의가 뜬다.

**Acceptance Scenarios**:

1. **Given** 모바일 동의, **When** 「나중에 받기」를 누르면, **Then** 내려받기가 시작되지 않고 동의가 저장되지 않으며 대기 화면이 뜬다.
2. **Given** 대기 화면과 이제 Wi-Fi 상태, **When** 「다시 확인하기」를 누르거나 앱이 전경으로 돌아오면, **Then** 연결을 다시 읽어 표준 동의가 뜬다(자동으로 받기 시작하지 않는다).
3. **Given** 대기 화면과 여전히 모바일 데이터 상태, **When** 「다시 확인하기」를 누르면, **Then** 모바일 동의가 다시 뜬다.
4. **Given** 대기 화면, **When** 앱을 완전히 종료했다 다시 열면, **Then** 첫 실행 흐름이 같은 지점(동의 단계)에서 연결을 처음부터 다시 읽는다.
5. **Given** 대기 화면, **When** 뒤로 가기를 누르면, **Then** 동작은 표준 동의와 같다(앱을 닫거나 건너뛰지 않는다).

---

### User Story 3 - 이미 쓰던 사람과 다른 경로는 달라지지 않는다 (Priority: P2)

이미 동의했거나 모델이 준비된 사용자, 설정의 「모듈 다시 받기」, 첫 실행의 나머지 단계는 이번 변경으로 달라지지 않는다.

**Why this priority**: 045·059의 계약이 이미 많은 테스트로 잠겨 있고, 회귀가 조용히 나는 영역이다.

**Independent Test**: 기존 첫 실행 단계 판정·동의 화면 테스트가 수정 없이 통과한다.

**Acceptance Scenarios**:

1. **Given** 모델이 이미 준비된 사용자, **When** 앱을 열면, **Then** 어떤 연결 상태에서도 동의 단계가 뜨지 않고 연결 종류를 읽지도 않는다.
2. **Given** 이미 동의를 저장한 사용자, **When** 모바일 데이터 상태에서 앱을 열면, **Then** 모바일 동의가 뜨지 않는다(동의는 되돌리지 않는다, 045 C5).
3. **Given** 설정의 「모듈 다시 받기」, **When** 사용하면, **Then** 059의 확인 문구와 동작이 그대로다.
4. **Given** 첫 실행 단계 판정, **When** 입력 조합을 훑으면, **Then** 단계 값과 우선순위가 045와 같다.

### Edge Cases

- 동의 단계에 들어간 직후 연결을 읽는 동안: 대화상자를 아직 띄우지 않는다(짧은 빈 배경). 읽기가 끝나면 갈래에 맞는 대화상자가 뜬다. **읽기가 3초 안에 끝나지 않으면 「모름」으로 보고 표준 동의를 띄운다**(빈 화면에서 멈추지 않는다). 받을 양을 읽는 데도 별도 3초 한도가 있고, 넘으면 양 없이 모바일 동의를 띄운다.
- 모바일 동의가 떠 있는 동안 연결이 Wi-Fi로 바뀌거나 반대인 경우: 이미 뜬 대화상자(모바일·표준)는 바뀌지 않는다 — 전경 복귀에도 다시 읽지 않는다. 다시 읽는 때는 대기 화면의 「다시 확인하기」, 대기 화면 상태에서의 전경 복귀, 앱 재실행뿐이다.
- 대기 화면에서 앱을 백그라운드로 보냈다 돌아온 경우: 전경 복귀 시 재판정한다.
- 핫스팟에 붙은 Wi-Fi: 연결 종류 조회가 Wi-Fi로 보고하므로 모바일 동의가 뜨지 않는다(알려진 한계).
- 받는 도중 연결이 바뀌는 경우: 이번 범위 밖이다(시작 시점에만 판정한다).

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 첫 실행의 동의 단계에 들어갈 때 시스템은 기기의 연결 종류를 읽어, 모바일 데이터로 **확인될 때만** 모바일 동의를 보여야 한다(MUST).
- **FR-001a**: 연결 종류 읽기는 3초 한도를 가지며, 한도를 넘기면 읽지 못한 것으로 다룬다(MUST). 받을 양 읽기도 별도로 3초 한도를 가지며, 넘기면 FR-004의 「읽지 못함」으로 다룬다(MUST). 어느 쪽이든 동의 단계가 빈 화면에서 멈추지 않는다.
- **FR-002**: 연결 종류를 읽지 못했거나 모바일 데이터가 아닌 모든 경우(Wi-Fi·연결 없음·이더넷·VPN·그 밖)에는 표준 동의를 지금과 같은 문구·구성·식별자로 보여야 한다(MUST). 모르는 것을 모바일 데이터로 단정하지 않는다(원칙 V).
- **FR-003**: 모바일 동의는 「모바일 데이터로 받기」와 「나중에 받기」 두 선택지를 가져야 하고, 본문에 모바일 데이터로 받는다는 사실을 알려야 한다(MUST).
- **FR-004**: 모바일 동의의 본문에는 받을 양을 사용자에게 읽히는 단위로 보여야 한다(MUST). 받을 양을 읽지 못하면 양 없이 같은 안내를 보이고 값을 지어내지 않는다(MUST NOT). 표준 동의에는 받을 양·바이트·모델 식별자를 노출하지 않는다(045 FR-003은 표준 동의에 그대로 적용되고, 모바일 동의의 받을 양만 예외다).
- **FR-005**: 「모바일 데이터로 받기」는 표준 동의의 [받을게요]와 같은 효과(동의 저장, 내려받기 시작)를 내야 한다(MUST).
- **FR-006**: 「나중에 받기」는 어떤 파일도 받지 않고 동의를 저장하지 않으며 대기 화면을 보여야 한다(MUST). 이 선택은 앱을 종료하면 사라지는 세션 상태이며 저장하지 않는다(MUST NOT 저장).
- **FR-007**: 대기 화면은 Wi-Fi에서 받으라는 안내와 「다시 확인하기」 버튼을 가져야 한다(MUST). 「다시 확인하기」를 누르거나 앱이 전경으로 돌아오면 연결 종류를 다시 읽어 FR-001·FR-002에 따라 갈래를 정해야 한다(MUST). 재판정은 자동으로 내려받기를 시작하지 않는다(MUST NOT).
- **FR-008**: 대기 화면과 모바일 동의에서 앱은 스스로 종료하지 않으며, 뒤로 가기는 표준 동의와 같이 아무것도 바꾸지 않는다(MUST). 두 플랫폼의 동작은 같다.
- **FR-009**: 첫 실행 단계 판정(단계 값과 우선순위)은 변경하지 않는다(MUST). 이미 동의했거나 모델이 준비된 사용자에게 모바일 동의를 보이지 않고 연결 종류를 읽지도 않는다(MUST).
- **FR-010**: 설정의 「모듈 다시 받기」의 문구와 동작은 변경하지 않는다(MUST).
- **FR-011**: 이번 변경으로 새로 생기는 모든 화면 문구는 언어별 카탈로그에 있어야 하며 카탈로그 밖에 한글 리터럴을 두지 않는다(MUST, 062). 문구에는 모델 식별자·바이트 단위 숫자·진행률을 쓰지 않는다.
- **FR-012**: 새 저장 필드·새 네이티브 의존성·새 권한을 더하지 않는다(MUST NOT).
- **FR-013**: 받는 도중의 연결 전환은 다루지 않으며(범위 밖), 핫스팟 Wi-Fi를 판별하지 못하는 한계와 함께 문서에 알려진 한계로 적는다(MUST).

### Key Entities

- **연결 종류 판정**: 모바일 데이터 / 그 밖(확인 못 함 포함)의 둘로 줄여 쓰는 값. 일기 신호가 아니라 사용자가 보는 안내에만 쓴다.
- **「나중에 받기」 상태**: 이번 실행 동안만 사는 세션 상태. 저장하지 않는다.
- **받을 양 문구**: 아직 받지 않은 필수 모듈의 양을 사용자가 읽는 단위로 옮긴 문자열(모바일 동의 본문에만 쓴다).

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 모바일 데이터 상태에서 첫 실행을 하는 사용자 100%가, 모델을 한 바이트도 받기 전에 받을 양과 두 선택지를 본다.
- **SC-002**: 「나중에 받기」를 고른 뒤 사용자가 받은 모델 파일 수는 0이고, 이후 「다시 확인하기」 한 번으로 Wi-Fi 상태에서 표준 동의에 도달한다.
- **SC-003**: Wi-Fi·연결 종류 모름·연결 없음 상태에서 동의 단계의 화면은 변경 전과 구별되지 않는다(문구·버튼 수·식별자 동일).
- **SC-003a**: 연결 종류 조회가 응답하지 않는 경우에도 동의 단계는 3초 안에 표준 동의에 도달한다.
- **SC-004**: 첫 실행 단계 판정과 045·059의 기존 계약 테스트가 수정 없이 통과한다.
- **SC-005**: 실기기에서 두 갈래(모바일 데이터 → 「나중에 받기」, 모바일 데이터 → 「모바일 데이터로 받기」로 진행 시작)와 Wi-Fi 갈래의 모달 없음을 직접 보고, 그때 읽은 연결 종류 값을 문서에 적는다. 보지 못한 갈래는 「미확인」으로 적는다.

## Assumptions

- 연결 종류 조회(`readConnection`)와 받을 양 계산(`remainingBytes`·`formatModuleBytes`)은 059가 만들었고 이 기능이 그대로 쓴다.
- 받을 양은 059와 같은 기준(1000 기준, 「약 2.0GB」 꼴)으로 보인다.
- 모델 파일은 이어받기를 지원하므로, 범위 밖인 도중 전환에서도 이미 받은 만큼은 잃지 않는다(041).
- 실기기 시험은 모델이 없는 상태가 전제라 `pm clear`가 약 2GB를 지운다. 이 기계에는 모델 백업이 없고, **기기를 다른 자동화(안티그랩)가 쓰고 있어 시험 전에 소유자 확인을 받는다.**
- 핫스팟 Wi-Fi 같은 과금 연결의 판별은 별도 네이티브 조회가 필요해 범위 밖이다.
