# Feature Specification: Modernist 디자인 시스템 적용 1차 — 스플래시·권한 요청 흐름

**Feature Branch**: `043-modernist-splash-permissions`

**Created**: 2026-09-18

**Status**: Draft

**Input**: User description: "Modernist 디자인 시스템 적용 1차 — 스플래시·권한 요청 흐름 재구현"

## 배경 및 이전 시도 경위

claude.ai/design에서 받은 디자인 리뷰 보드(`Alpharium Mobile Screens (standalone).html`,
20개 화면 대안 포함)를 이 앱에 적용하는 것이 전체 목표다. 이전 시도(043 최초본,
2026-09-18에 전면 롤백됨)는 홈·상세 화면까지 한 번에 재구현하려다 기존 계약
(038 타자기 연출, 017 소요 시간 즉시 표시, 025 사진 갤러리)과 세 차례 충돌했고,
매번 "충돌을 피하는 쪽으로 축소"한 끝에 최종 결과물이 리뷰 보드의 시각적
정체성(Modernist — 오프화이트, 단일 레드 강조, 제로 라디우스)을 거의 반영하지
못하는 수준으로 빈약해졌다. 저장소 소유자가 실기기에서 직접 확인하고 브랜치
전체를 삭제(`git branch -D`)했다.

이번 스펙은 그 실패를 반복하지 않기 위해 **범위를 스플래시 화면과 그 직후의
권한 요청 흐름 하나로만 좁힌다.** 홈·상세·설정 등 나머지 화면은 명시적으로
범위 밖이며, 이번 스펙의 완료를 확인한 뒤 후속 스펙에서 순서대로 다룬다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 앱 최초 진입 시 브랜드 스플래시를 본다 (Priority: P1)

사용자가 앱을 처음(또는 온보딩이 필요한 상태로) 실행하면, 디자인 리뷰 보드가
정한 시각 언어(오프화이트 배경, 레드 사각 마크, 굵은 브랜드 타이틀, 하단 안내
문구와 로딩 표시)로 된 스플래시 화면을 먼저 본다. 화면에는 사용자가 누를
버튼이 없다 — 정해진 시간 뒤 자동으로 다음 단계(권한 요청)로 넘어간다.

**Why this priority**: 스플래시는 사용자가 앱을 열 때마다(온보딩이 필요한
상태에서) 가장 먼저 보는 화면이라 새 디자인 시스템의 첫인상을 결정한다. 권한
흐름 전체가 이 화면 위에서 이어지므로 다른 작업의 전제 조건이기도 하다.

**Independent Test**: 온보딩이 필요한 상태로 앱을 실행해 스플래시 화면의
레이아웃·색상·문구를 눈으로 확인하고, 정해진 시간 뒤 자동으로 다음 화면(권한
요청)으로 전환되는 것을 관찰하는 것만으로 독립적으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 온보딩을 완료한 적이 없는 상태, **When** 앱을 실행한다,
   **Then** 오프화이트 배경 위에 레드 사각 로고 마크와 브랜드 타이틀이 좌측
   정렬로 표시되고, 하단에 안내 문구와 로딩 표시가 보인다.
2. **Given** 스플래시 화면이 표시된 상태, **When** 정해진 시간이 지난다,
   **Then** 사용자 조작 없이 자동으로 권한 요청 흐름으로 전환된다.
3. **Given** 스플래시 화면이 표시된 상태, **When** 화면을 관찰한다,
   **Then** 모델 이름·다운로드 진행률·추론 관련 수치 등 내부 지표가 전혀
   보이지 않는다(로딩 표시는 장식적 요소일 뿐 실제 진행률을 계산해 보여주지
   않는다).

### User Story 2 - 필요한 권한을 순서대로 요청받는다 (Priority: P1)

스플래시 화면 이후, 사용자는 앱이 정상 동작하는 데 필요한 권한(사진, 위치,
알림, 배터리 최적화 예외)을 정해진 순서대로 요청받는다. 이 세 단계와
배터리 1단계, 두 갈래로 나뉜다:

- **사진·위치·알림 세 단계**: 화면 안에 자체 설명 카드나
  [허용]/[건너뛰기] 버튼을 두지 않는다 — 스플래시 배경이 그대로 유지된
  위에서, 각 권한에 대응하는 OS 표준 다이얼로그가 순서대로 곧바로 뜬다.
  사용자는 그 다이얼로그에서 직접 허용하거나 거부한다(안드로이드 표준
  UX — 마크업 1l/1m/1n이 딤 처리된 배경 위에 OS 다이얼로그를 띄우는
  것과 같은 패턴).
- **배터리 최적화 예외 단계**: iOS에는 대응하는 요청 자체가 없고,
  안드로이드에서도 제조사에 따라 다이얼로그 대신 설정 화면으로 라우팅될
  수 있어(Edge Cases 참조) 앞의 세 단계와 같은 방식으로 통일할 수 없다
  — 이 한 단계는 기존 021 방식(화면 안내 + [설정 열기]/[건너뛰기]
  버튼)을 그대로 유지한다.

**Why this priority**: 권한이 없으면 앱의 핵심 기능(사진 기반 일기 생성,
자동 생성 알림 등)이 조용히 축소된 채로 동작한다 — 사용자가 그 사실을 알고
선택할 수 있어야 한다. 이 흐름은 이미 검증된 로직(021, 040) 위에 새 화면만
입히는 것이라 스플래시 다음으로 우선순위가 높다.

**Independent Test**: 온보딩이 필요한 상태로 앱을 실행해 스플래시 이후
사진·위치·알림 OS 권한 다이얼로그가 순서대로 연속으로 뜨는 것과,
그 뒤 배터리 최적화 예외 단계에서 화면 안내와 버튼이 나타나는 것을 함께
확인하는 것으로 독립적으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 스플래시 화면이 자동 전환된 직후, **When** 권한 요청 흐름이
   시작된다, **Then** 스플래시와 같은 Modernist 배경 위에 첫 번째 권한
   (사진)의 OS 다이얼로그가 곧바로 뜬다 — 그 사이에 앱 자체 설명 화면이나
   버튼이 끼어들지 않는다.
2. **Given** OS 권한 다이얼로그가 떠 있다(사진·위치·알림 중
   하나), **When** 사용자가 허용 또는 거부를 선택한다, **Then** 다이얼로그가
   닫히고 곧바로 다음 권한의 OS 다이얼로그가 자동으로 뜬다(사용자가 별도로
   "다음" 버튼을 누를 필요 없음).
3. **Given** 사용자가 사진·위치·알림 중 하나를 거부한다,
   **When** 다이얼로그가 거부로 닫힌다, **Then** 그 권한 없이 다음 단계로
   넘어가고 이후에도 앱은 정상적으로 동작한다(그 권한을 요구하는 기능만
   제한된 형태로 동작) — 거부는 곧 건너뛰기와 같은 효과를 낸다(화면에
   별도 "건너뛰기" 버튼을 두지 않는다, FR-008 개정).
4. **Given** 세 단계를 마치고 배터리 최적화 예외 단계에 진입한다,
   **When** 화면이 뜬다, **Then** 기존 021 방식대로 안내 문구와 [설정
   열기]/[건너뛰기] 버튼이 Modernist 토큰으로 표시된다(FR-007c).
5. **Given** 모든 권한 단계를 마쳤다, **When** 마지막 단계가 끝난다,
   **Then** 이번 스펙 범위를 벗어난 다음 단계(작명·에셋 다운로드)로
   흐름이 이어진다(그 화면 자체는 이번 스펙에서 새로 그리지 않는다).

---

### Edge Cases

- 이미 온보딩을 완료한 사용자가 앱을 다시 실행하면 스플래시·권한 화면을
  다시 보지 않는다(기존 021/040 게이트 로직 그대로 — FR-010).
- 설정에서 "권한 안내 다시 보기"를 선택해 온보딩을 강제로 다시 띄운 경우에도
  같은 스플래시·권한 화면이 그려진다(기존 `forceOnboarding` 경로 재사용).
- 사용자가 스플래시 화면이 자동 전환되기 전에 앱을 백그라운드로 보내면,
  포그라운드로 돌아왔을 때 기존 타이머 로직에 따라 이어지거나 재시작한다
  (기존 `LogoScreen`의 `useEffect` 타이머 동작 그대로 — 이번 스펙은 이
  동작을 바꾸지 않는다).
- 이미 일부 권한이 부여된 기기(예: 다른 앱에서 사진 권한을 이미 허용)에서는
  해당 권한 단계가 이미 충족된 것으로 표시되고 자동으로 다음 단계로
  넘어간다(기존 021 로직 — 021 실기기 검증에서 확인된 동작).
- 사용자가 특정 권한을 안드로이드의 "다시 묻지 않음" 옵션과 함께 거부하면,
  이후 그 권한을 다시 요청해도 OS 다이얼로그가 뜨지 않고 즉시 거부로
  처리된다 — 이 경우 화면은 재요청을 반복 시도하지 않고, 앱 설정 화면으로
  이동하도록 안내하는 기존 021 문구를 새 디자인 토큰으로 표시한다(FR-008a).
- 배터리 최적화 예외 요청(`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 인텐트)은
  AOSP 표준에서는 승인/거부 다이얼로그를 띄우지만, 삼성 One UI 기기에서는
  다이얼로그 대신 "배터리 사용 관리" 목록 화면으로 라우팅되고 예외 적용까지
  여러 번 탭이 필요하다(027 실기기 실측). 게다가 iOS에는 이 요청에 대응하는
  API 자체가 없다(FR-017). 플랫폼·제조사에 따라 결과 화면이 갈리는 이
  비일관성 때문에, 이 단계만 사진·위치·알림처럼 OS 표준 하나로 통일하지
  않고 기존 021의 화면 안내 + 버튼 방식을 그대로 유지한다(FR-007c) —
  사용자가 [설정 열기]를 직접 누르고 돌아와야 하며, "실제로 승인됐는가"를
  조회하는 API가 없으므로(020/021 기존 제약) 시도 여부만으로 만족 처리한다
  (`batteryNoticeShown`, 기존 로직 무변경).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 스플래시 화면은 리뷰 보드 프레임 1k의 레이아웃 구조(상단
  좌측 정렬 로고 마크+타이틀 블록, 하단 안내 문구+로딩 표시, 그 사이 구분선)
  을 그대로 따라야 한다.
- **FR-002**: 스플래시 화면의 로고 마크는 72×72 크기의 단색 사각형(accent
  색, 모서리 반경 0)이어야 한다(실제 로고 이미지 에셋은 이번 스펙 범위 밖 —
  색 블록으로 대체).
- **FR-003**: 스플래시 화면의 브랜드 타이틀 텍스트는 굵은 글씨(font-weight
  800 상당)로 표시되어야 한다. 표시 문구("Alpharium" 원문 유지 — 아래
  Clarifications 참조)
- **FR-004**: 스플래시 화면 하단에는 안내 문구("휴대폰 안에서만")와 로딩
  표시(점 3개, 순서대로 강조·중간·비활성 색상)가 구분선 아래 좌우로
  배치되어야 한다.
- **FR-005**: 로딩 표시는 장식적 요소여야 하며, 실제 다운로드·초기화
  진행률을 계산하거나 표시해서는 안 된다(원칙 IV) — 정적 표시 또는 반복
  애니메이션은 허용되지만 숫자·퍼센트·모델명은 어떤 형태로도 노출되지
  않아야 한다.
- **FR-006**: 스플래시 화면은 정해진 시간 후 사용자 조작 없이 자동으로
  다음 단계(권한 요청 흐름)로 전환되어야 한다(기존 `LogoScreen`의
  `LOGO_DISPLAY_MS` 타이머 로직 재사용).
- **FR-007**: 권한 요청 흐름은 사진 → 위치 → 알림 → 배터리 최적화 예외
  순서를 유지해야 한다(021 `PERMISSION_REQUIREMENTS`의 고정 순서를 그대로
  재사용 — 이번 스펙은 순서·판정 로직을 재구현하지 않는다). `/speckit-plan`
  research 단계(R1)에서 확인한 대로, 현재 `PERMISSION_REQUIREMENTS`는
  031에서 `photo-location` 항목이 이미 빠져 **4개 항목**(사진·위치·알림·
  배터리)뿐이다 — 이 스펙 초안의 "사진→사진 위치→위치→알림→배터리 5단계"
  서술은 021 최초 계획 당시 문구가 남은 것으로, 031 변경을 반영하지 못한
  사실 오류였다. 구현은 이미 `PERMISSION_REQUIREMENTS` 배열을 순회하는
  구조라 항목 수가 4든 5든 코드 변경이 필요 없으며, 문서 표현만 "4단계(OS
  다이얼로그 연속 호출 대상) + 배터리 1단계(기존 방식 유지)"로 통일한다.
- **FR-007a**: 사진·위치·알림 세 단계는 앱 자체 설명 화면 없이
  OS 표준 권한 다이얼로그를 곧바로 순서대로 자동 호출해야 한다 — 기존
  `OnboardingScreen`의 "목적 설명 카드 → 1.5초 대기 → 자동 호출" 구조
  (`ONBOARDING_STEP_AUTO_ADVANCE_MS`)를 이 세 단계에서만 걷어내고, 스텝
  진입 즉시 권한 요청 함수를 호출한다.
- **FR-007c**: 배터리 최적화 예외 단계는 FR-007a의 연속 호출 대상에서
  제외한다 — iOS에는 대응 API가 없고(FR-017), 안드로이드에서도 제조사에
  따라 결과 화면이 다이얼로그·설정 목록으로 갈리므로(Edge Cases) 다른
  세 단계와 같은 방식으로 통일하지 않는다. 이 한 단계는 기존 021의 화면
  구조(목적 안내 문구 + [설정 열기]/[건너뛰기] 버튼)를 그대로 유지하고,
  시각 스타일(배경색·텍스트색·강조색·모서리 반경)만 Modernist 토큰으로
  교체한다.
- **FR-008**: 사용자가 OS 권한 다이얼로그(사진·위치·알림)에서
  거부하면 그 자체가 건너뛰기와 같은 효과를 낸다 — 이 세 단계는 화면에
  별도의 "건너뛰기" 버튼을 두지 않는다(FR-007a 채택에 따른 개정, 021
  원칙 I의 "강제하지 않는다"는 유지되나 그 수단이 화면 버튼에서 OS
  다이얼로그 거부로 바뀐다). 배터리 최적화 예외 단계는 FR-007c에 따라
  기존 화면 버튼([건너뛰기] 포함)을 그대로 유지하므로 이 요구사항이
  적용되지 않는다. **구현 함의**: `src/onboarding/decision.ts`의
  `statusOf()`는 거부(`denied`) 상태를 `blocked`가 아닌 한
  `actionable`로 판정한다 — 즉 화면이 아무 조치도 하지 않으면 거부
  후에도 `nextStep()`이 계속 같은 단계를 가리켜 이 요구사항이 실제로
  성립하지 않는다(021 원본은 화면의 [건너뛰기] 버튼으로 이 간극을
  메웠다). 따라서 화면(`OnboardingScreen.tsx`)이 OS 요청 결과가
  허용이 아니면 **자동으로 기존 건너뛰기 판정 경로**(`skip(key)`,
  순수 판정 함수는 무변경)를 호출해야 한다 — 이는 화면 조립 로직
  변경이며 FR-014("로직 계층 무변경")의 대상(`decision.ts` 자체)을
  건드리지 않는다.
- **FR-008a**: 사용자가 사진·위치·알림 중 하나를 "다시 묻지
  않음"과 함께 거부해 OS가 더 이상 권한 다이얼로그를 띄우지 않는 상태가
  되면, 화면은 재요청을 반복하지 않고 앱 설정 화면 이동을 안내해야 한다
  (021의 기존 안내 로직 재사용, 문구·시각 스타일만 새 토큰으로 표시).
  배터리 최적화 예외는 FR-007c에 따라 애초에 자동 재요청을 하지 않으므로
  이 갈래가 발생하지 않는다.
- **FR-009**: 권한 요청 흐름 중 화면에 남는 요소 — 사진·위치·알림 세
  단계의 배경(스플래시와 동일), 그리고 배터리 최적화 예외
  단계의 안내 문구·[설정 열기]/[건너뛰기] 버튼 — 의 시각 스타일은
  Modernist 토큰으로 교체되어야 한다. 사진·위치·알림 세
  단계의 목적 설명 카드와 [허용]/[건너뛰기] 버튼은 FR-007a에 따라
  제거되므로 재사용 대상에서 빠지고, 배터리 최적화 예외 단계의 화면
  구조는 FR-007c에 따라 그대로 재사용한다.
- **FR-010**: 이미 온보딩을 완료한 사용자, 또는 이미 필요한 권한을
  보유한 사용자에게는 기존 게이트 로직(`onboardingGateNeeded`,
  `shouldShowLogo`)에 따라 스플래시·권한 화면이 다시 표시되지 않아야
  한다(021/040 로직 무변경).
- **FR-011**: 디자인 토큰(`src/ui/theme/tokens.ts`)의 `COLORS`는
  Modernist 팔레트(오프화이트 배경, 단일 레드 강조, 저채도 회색조 보조
  색)로 전면 교체되어야 하고, `RADIUS`는 모든 역할이 0(제로 라디우스)이
  되어야 한다.
- **FR-012**: 새 팔레트의 모든 텍스트/배경 조합은 기존 WCAG AA 대비 검증
  (`theme-tokens.test.ts` DT4, 본문 4.5:1 / 큰 텍스트 3:1)을 통과해야
  한다. `/speckit-plan` research 단계에서 `contrastRatio()`로 실측한 결과
  (research.md R2), `accentForeground`(흰 글자) vs `accent`(#ec3013) 조합이
  구조적으로 4.5:1을 채우지 못해(순백 4.20:1) — `Button` `primary`
  variant의 배경색을 `accent`에서 `danger`(#ae1800, 마크업 accent-700)로
  바꾸어 문제 조합 자체를 없앤다. `textMuted`도 원본(#7d7979, 3.85:1)에서
  `#6b6767`(5.00:1)로 근소 조정한다. `accent`(#ec3013) 원본 값은 배경/
  블록(로고 마크 등 텍스트가 얹히지 않는 면적)에 그대로 유지한다.
  **정정(analyze 재검토)**: `Button` `primary` variant는 온보딩 화면
  뿐 아니라 `AutoDiarySettingsScreen`·`CharacterListScreen`·
  `WelcomeScreen` 등 **범위 밖 화면에서도** variant 미지정(기본값)으로
  쓰인다 — "유일한 자리"라는 서술은 사실 오류였다. `Button`은 `src/ui/
  components/`의 전역 공유 컴포넌트라 이 변경은 범위 밖 화면의 버튼
  색에도 파급된다. FR-013이 이를 허용 범위로 명시한다.
  **추가 발견(analyze 2차 재검토)**: `accent`를 **텍스트 색**으로 직접
  쓰는 자리가 `Button` 밖에도 있다 — `AuthorPicker.tsx`("작성자"·"이름
  바꾸기" 라벨), `AutoDiarySettingsScreen.tsx`(캡션 라벨),
  `SelectRow.tsx`(선택 표시 라벨)가 `AppText style={{ color:
  COLORS.accent }}`를 쓴다. 이 텍스트들도 새 `accent`(#ec3013) 값에서
  bg 대비 3.76:1로 AA 미달이 된다 — 이 스펙(T002의 토큰 교체)이 직접
  유발하는 회귀이므로 SC-005("모든 텍스트/배경 조합이 WCAG AA 통과")
  범위 안에서 다뤄야 한다. `Button`과 같은 논리로 이 세 파일의
  `color: COLORS.accent` 값만 `COLORS.danger`로 바꾼다(레이아웃·JSX
  구조·문구는 무변경이므로 FR-013 위반이 아니다).
- **FR-013**: 이번 스펙은 `src/ui/` 중 스플래시 화면과 온보딩(권한 요청)
  화면 두 개의 시각 구현만 새로 작성한다. 그 외 화면(`DiaryHomeScreen`,

  변경뿐 아니라, `src/ui/components/`의 전역 공유 컴포넌트(`Button` 등)의
  색 매핑 변경도 포함된다 — `Button`은 온보딩 화면 전용이 아니라 위
  화면들에서도 쓰이므로(FR-012 정정 참고), `primary` variant 배경이
  `accent`→`danger`로 바뀌면 그 화면들의 버튼 색도 함께 바뀐다. 이는
  레이아웃 변경이 아니라 공유 컴포넌트의 색 값 변경이 자연히 전파된

- **FR-014**: `src/onboarding/decision.ts`(권한 상태 판정)를 포함해
  `src/diary/`, `src/models/`, `src/firstrun/`, `src/schedule/`,
  `src/signals/`, `src/vision/`, `src/inference/`, `src/app/` 등 순수

  드러나지 않은 것은 이 개발 흐름이 Android 실기기(Windows 환경)로만
  검증돼 왔기 때문일 뿐, "iOS는 검증 대상이 아니다"는 이 저장소가 iOS

  "로직 계층 무변경" 원칙에 대한 유일한 예외이며, 한 줄 값 수정에
  한정한다(순수 판정 함수의 동작 자체는 바꾸지 않는다).

- **SC-003**: 권한 요청 흐름의 네 단계(사진·위치·알림 세 단계 + 배터리 1단계

- **SC-004**: 새 디자인 토큰 적용 후에도 기존 자동화 테스트

## Assumptions

- 마크업의 1l/1m/1n(사진·위치·알림 권한 다이얼로그)은 iOS 스타일 네이티브
  다이얼로그를 흉내낸 참고 자료다. 이번 스펙의 실기기 검증은 현재 개발
  환경(Windows, Android 기기 연결)에서 Android로만 이루어진다 — 이는
  이 저장소의 코드가 Android 전용이라는 뜻이 아니라, 이번 검증 범위가
  연결 가능한 기기에 한정된다는 뜻이다(iOS 검증은 Mac 환경에서 별도로
  가능하며 이번 스펙이 그것을 막지 않는다). 실제 구현은 Android OS가
  제공하는 표준 권한 다이얼로그를 그대로 사용하며, 다이얼로그 자체의
  커스텀 UI 구현은 범위 밖이다.
- 리뷰 보드가 요구하는 서체(Archivo)는 032 FR-019a("폰트 파일을 새로
  번들하지 않는다")를 계승해 시스템 기본 서체로 대체한다.
- 배터리 최적화 예외 단계는 021/040이 이미 구현한 화면 구조·요청 함수를
  그대로 재사용한다(시각 스타일만 새 토큰) — 이 스펙이 유일하게 고치는
  로직 계층 변경은 FR-017의 `platforms` 필드 한 줄(iOS 미지원 반영)뿐이다.
- 스플래시 화면의 72×72 사각형은 실제 브랜드 로고 이미지가 아직 없는
  상태의 자리표시자(placeholder)이며, 향후 실제 로고 에셋이 준비되면
  별도 작업으로 교체한다.

  띄우는 구조인데, 이를 어떻게 바꾸는가? → A: 설명 카드와 화면 버튼을
  제거하고, 스플래시 배경 위에서 요청 함수를 곧바로 연속 호출하도록
  바꾼다(FR-007a·FR-008 개정). 처음에는 배터리 최적화 예외까지 포함한
  다섯 단계 전부를 대상으로 했으나, 아래 두 질문을 거쳐 배터리 예외는
  이 방식에서 제외하기로 다시 정정했다.
- Q: 배터리 최적화 예외도 안드로이드에 다이얼로그가 없는가? → A: 아니다
  — `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 인텐트는 AOSP 표준에서
  승인/거부 다이얼로그를 띄운다. 다만 삼성 One UI에서는 다이얼로그 대신
  "배터리 사용 관리" 설정 목록 화면으로 라우팅된다(027 실측) — 이는
  제조사 커스터마이징 때문이다.
- Q: iOS는 배터리 최적화 예외를 어떻게 처리하는가(context7로
  `expo-intent-launcher` 문서 확인)? → A: `expo-intent-launcher`는
  공식적으로 iOS를 지원하지 않는다("동등한 API가 없어 iOS에서는 의미가
  없다", Expo 공식 README) — 이는 검증 환경 제약이 아니라 iOS 자체에
  대응 API가 없다는 사실이다. 021이 `battery-exception` 요구사항 항목의
  `platforms`를 `["android", "ios"]`로 잘못 선언해 둔 기존 결함을 이번
  스펙에서 함께 고친다 — `["android"]`로 정정(FR-017).
- Q: 배터리 최적화 예외가 iOS엔 대응 API가 없고 안드로이드에서도
  제조사마다 다르게 동작한다면, 이번 스펙의 "OS 표준으로 통일" 방침을
  이 단계에도 그대로 적용해야 하는가? → A: 아니다 — 플랫폼·제조사마다
  결과가 갈리는 항목을 억지로 한 방식으로 맞추려 하지 않는다. 배터리
  최적화 예외 단계는 FR-007a의 연속 호출 대상에서 제외하고, 기존 021
  화면 구조(안내 문구 + [설정 열기]/[건너뛰기] 버튼)를 그대로 유지한다
  (FR-007c 신설, FR-008·FR-009 범위 조정).
