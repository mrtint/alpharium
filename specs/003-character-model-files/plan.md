# Implementation Plan: 캐릭터별 모델 파일 확보

**Branch**: `003-character-model-files` | **Date**: 2026-08-13 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/003-character-model-files/spec.md`

## Summary

002가 파이프라인을 이었고 생성 단계에서 멈춰 있다. 이 기능은 그 앞의 전제 — **쓸 수 있는
모델 파일이 기기에 있는가** — 를 세운다. `generate()`는 이 기능이 끝나도
`not-implemented`다(FR-009).

기술적 접근의 핵심은 **네 가지**다.

1. **매핑을 한 방향으로만 흐르게 한다**(FR-003). 캐릭터로 자산을 찾는 함수는 있고, 자산에서
   캐릭터를 되짚거나 자산을 화면에 넘기는 길은 없다. **이 기능이 처음으로 캐릭터와 모델
   파일을 잇는 자리이므로 여기가 헌법 원칙 III의 최전선이다.**
2. **준비 상태를 넷으로 가른다**(FR-006). 002의 `SignalValue`가 셋을 가른 것과 같은 구조이며,
   파일이 *부분적으로* 있는 상태 때문에 하나가 더 필요하다.
3. **검증 결과를 남기되 파일 존재는 매번 확인한다**(FR-021a~FR-021e). 명확화 세션의 핵심
   결론이다 — 검증 결과는 "그때 온전했다"는 기록이지 "지금도 있다"는 뜻이 아니다.
4. **한 번에 하나만 받는다**(FR-020). 진행 중인 작업을 값 하나로 들고, 뒤의 요청은 거부한다.
   002의 파이프라인이 `running` Set으로 중복 실행을 막은 것과 같은 자리의 판단이다.

`expo-file-system` 57이 이 기능이 필요로 하는 것을 **전부 네이티브로 제공한다** —
`DownloadTask`(중단·재개·진행률), `Paths.availableDiskSpace`(공간 판정), `File.info({md5})`
(내용 검증). 새 의존성이 필요 없다는 것이 Phase 0의 가장 중요한 발견이다.
근거는 [research.md](research.md)에 있다.

## Technical Context

**Language/Version**: TypeScript 6.0.3 (strict), React 19.2.3 — 001·002 기준선 그대로

**Primary Dependencies**: Expo SDK 57, React Native 0.86.2, **`expo-file-system 57.0.2`**
(이미 설치돼 있으나 `package.json`에 선언되어 있지 않다 — 002가 쓰기 시작했고 이 기능이
크게 의존하므로 **선언에 올린다**. `llama.rn`을 선언에 올린 것과 같은 처리). 새 패키지는
추가하지 않는다.

**Storage**: 두 가지가 기기에 남는다.
- **모델 파일** — `Paths.document` 아래. 시스템이 공간 부족 시 지우지 않는 자리다
  (`Paths.cache`와 다름). 다만 지워질 수 있다고 가정한다(FR-021e).
- **검증 결과와 중단된 내려받기 상태** — JSON 파일. 002의 `DiaryStore`와 같은 방식이되
  별개 자리다. 선택 근거는 [research.md](research.md) §4에 있다.

**Testing**: `jest-expo`(기기 불필요) + Maestro(실기기). **이 기능은 002와 달리 실기기
검증이 완료 조건이다**(FR-036, FR-037). 판정 로직은 순수 함수로 떼어 기기 없이 돌리고,
실제 내려받기·공간·삭제만 기기에서 확인한다.

**Target Platform**: Android 실기기(arm64-v8a, Galaxy S20+ / SM-G986N에서 검증).

**Performance Goals**:
- 준비 상태 조회가 **파일 크기와 무관하게** 끝난다(SC-016). 내용 해시를 매번 계산하지
  않는다는 뜻이며, 이것이 FR-021a의 실질적 목표다.
- 내려받기 속도는 **목표를 두지 않는다.** 속도를 재는 순간 모델 비교의 시작점이 된다
  (헌법 원칙 IV, FR-034).

**Constraints**:
- 모델 식별자·파일 이름·크기·양자화 방식이 사용자 화면에 금지 (원칙 III, FR-004)
- 고른 캐릭터의 모델만 내려받기 (헌법 로스터, FR-010)
- 대체 모델·더 작은 모델로 바꿔치기 금지 (원칙 I, FR-008a·FR-035)
- 넷을 구분: 받지 않음/받다 말았음/받았는데 쓸 수 없음/쓸 수 있음 (원칙 V, FR-006)
- 내려받기 속도 측정 금지 (원칙 IV, FR-034)
- 001의 `select.ts`·`policy.ts`·`environment.ts` 불변 (FR-031)

**Scale/Scope**: 캐릭터 5개, 준비 상태 4갈래, 실패 갈래 4개. 화면 1개(캐릭터 목록).
엔드유저에게 처음으로 보이는 화면이 생긴다.

**Structure Decision**:

**`src/models/`를 새로 연다.** 001의 AGENTS.md가 "캐릭터→모델 매핑은 모델 파일을 다루는
기능의 몫"이라고 예약해 둔 자리이며, 이 기능이 그 기능이다. `src/inference/`에 넣지 않는
이유는 **추론 실행과 파일 확보가 다른 축**이기 때문이다 — 섞으면 "받았으니 돌려보자"가
자연스러워지고, 그것이 헌법 「개발 방식」이 경고한 한 축 파고들기다.

배치의 핵심 넷:

- **`roster.ts`가 원칙 III의 유일한 통과 지점이다.** 캐릭터→자산 함수가 여기에만 있고,
  다른 모듈은 자산을 받아 쓰되 화면 쪽으로 내보내지 않는다. 002의 `policy.ts`가 원칙 I의
  방어선을 한 곳에 모은 것과 같은 구조다.
- **`readiness.ts`는 순수 함수다.** 파일 상태(있는가·크기·검증 결과)를 인자로 받아 넷 중
  하나를 돌려준다. 그래서 기기 없이 전부 테스트되고, 002의 `day-boundary.ts`가 `now`를
  인자로 받은 것과 같은 이유다 — 안에서 파일 시스템을 부르면 경계값을 시험할 수 없다.
- **`port.ts`가 기기 의존을 한 곳에 모은다.** 002의 `FileSystemPort`와 같은 방식이며,
  네트워크와 디스크 공간이 더해진다. 실제 `expo-file-system` 구현은 지연 import 한다
  (001·002와 같은 이유 — 테스트·웹에서 모듈 해석만으로 무너지지 않게).
- **`CharacterListScreen.tsx`가 원칙 III의 시험대다.** 이 화면이 받는 값에 모델 정보가
  아예 담기지 않도록 타입을 짠다. 화면이 실수할 여지를 없애는 쪽이 화면에서 조심하는 쪽보다
  낫다.

**001·002에서 손대지 않는 것**: `src/inference/select.ts`, `src/config/policy.ts`,
`src/config/environment.ts`, `src/config/day-boundary.ts`, `src/signals/*`,
`src/diary/store.ts`, `src/diary/types.ts`.

**`src/diary/pipeline.ts`만 최소한으로 잇는다** — 준비되지 않은 캐릭터면 생성 단계에 가기
전에 멈추게 하는 것(FR-008). 002의 `PipelineStage`에 갈래 하나가 늘어난다.

### 설계에서 새로 드러난 사실

1. **`expo-file-system` 57이 필요한 것을 전부 가지고 있다.** `DownloadTask`가 중단·재개를
   네이티브로 지원하고(`pause`/`resumeAsync`/`savable`/`fromSavable`),
   `Paths.availableDiskSpace`가 공간을 주며, `File.info({md5})`가 내용 해시를 준다.
   **새 의존성이 0개다** — 이것이 계획의 가장 큰 발견이며, 없었다면 범위가 크게 늘었다.
2. **재개는 우리가 구현하는 것이 아니라 보관하는 것이다.** `savable()`이 돌려주는 값을
   저장하고 `fromSavable()`로 되살린다. 앱이 죽어도 이어받을 수 있다는 FR-016이 이 왕복으로
   성립하며, **그래서 "중단된 상태"가 기기에 남는 세 번째 것이 된다.**
3. **`totalBytes`가 `-1`일 수 있다.** 서버가 `Content-Length`를 주지 않으면 그렇다. 그때
   진행률을 백분율로 보일 수 없으므로, **"모르는 것을 지어내지 않는" 처리가 필요하다**
   (원칙 V). 매핑이 예상 크기를 아니까(FR-001a) 그것을 쓰되, 다르면 그 사실이 드러나야 한다.
4. **MD5가 암호학적으로 약한 것은 여기서 문제가 되지 않는다.** 우리가 막으려는 것은 **전송
   중 훼손**이지 악의적 위조가 아니다. 공격자가 모델 파일을 바꿔치기할 수 있는 상황이면 앱
   자체를 바꾸는 편이 쉽다. 근거를 research.md §2에 적었고, 더 강한 것이 필요해지면 그때
   `expo-crypto`를 들인다.
5. **화면이 처음 생긴다.** 001·002는 진단 화면뿐이었다. 캐릭터 목록이 엔드유저가 보는 첫
   화면이며, 원칙 III이 이제부터 실제로 시험받는다.
