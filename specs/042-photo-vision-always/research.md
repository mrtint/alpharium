# Research: 사진이 있는 하루는 VLM을 반드시 거친다

**Phase 0** | 2026-09-14 | [plan.md](./plan.md) · [spec.md](./spec.md)

명확화 2문이 끝난 상태로 들어왔으므로 열린 `NEEDS CLARIFICATION`이 없다. 이
문서는 **조사로 확정한 사실**과 **설계 결정**을 남긴다 — 재지 않은 것은 재지
않았다고 적는다(원칙 V).

---

## R1. 타입을 좁히면 `tsc`가 작업 목록을 준다 (037의 방법)

**결정**: `VisionSetting`을 `"quick"` 하나로 좁히고, 컴파일 오류를 작업 목록으로 쓴다.

**근거**: 037이 `Character` 유니온을 좁혔을 때 `Record<Character, …>` 리터럴의
잉여 키, 도달 불가 `switch` 분기, 할당 불가 상수가 전부 오류로 드러났다. 손으로
찾아다니지 않아도 된다. **`tsc` 0이 완료 조건의 일부다.**

**한계 — `tsc`가 못 잡는 자리가 셋이다**:

| 자리                     | 왜 못 잡나                                                         | 무엇이 잡나            |
| ------------------------ | ------------------------------------------------------------------ | ---------------------- |
| 018 두 갈래 판별자       | 값이 사라져도 **타입은 계속 맞는다** — 분기가 조용히 한쪽으로 붕괴 | 계약 테스트(C5)        |
| 화면 문자열·Maestro      | 타입 밖                                                            | 계약 테스트 + 실기기   |
| 기기에 남은 옛 설정 파일 | 런타임 데이터                                                      | 읽지 않으므로 무해(C7) |

**대안 기각**: "심볼을 grep해 하나씩 고친다" — 로드맵 25번의 목록이 이미
`DiaryHomeScreen`(FR-012)과 `GenerationProbe`(FR-004a)를 놓쳤다. grep은 **빠진
것을 알려주지 않는다.**

## R2. 「사진이 있는가」를 판정 결과에 담는다 (FR-012a)

**결정**: `ResolvedParams`에 사진 유무를 담는 필드를 더하고, 화면은 그것으로
018의 두 갈래를 가른다. `vision` 필드는 사라진다.

**근거**: 세 후보를 견줬다.

| 후보                                   | 기각/채택 사유                                                                                                                                           |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **판정 결과에 필드 추가**              | **채택.** 029의 경계("화면은 신호를 모른다, 배선이 판정해 결과만 준다")가 유지되고, 판별자가 **타입에 존재**한다                                         |
| 화면에 `photoSignalPresent` prop 추가  | 기각 — 같은 사실이 `resolve` 안과 prop 두 곳에 생긴다. 둘이 어긋나도 `tsc`가 못 잡는다("두 개의 진실")                                                   |
| 갈래를 없애고 `captionDay` 하나로 합침 | 기각 — 0장인 날도 `captionDay`를 부르게 되어 "볼 것이 없으면 열지 않는다"의 판정이 화면 밖으로 흩어진다. 018 E1(엔진 하나만 열림)의 순서 보장도 약해진다 |

**주의**: `photoSignalPresent`(입력)와 새 필드(출력)는 **이름이 달라야 한다** —
같으면 "입력을 그대로 통과시킨 것"과 "판정한 것"이 구분되지 않는다.

## R3. `VisionOutcome`의 `skipped` 갈래는 죽는다 ★ 조사에서 새로 드러남

**사실(2026-09-14 조사)**: `skipped`는 **제품 코드에서 한 번도 반환되지 않는다.**

```
src/vision/types.ts:103    | { kind: "skipped" }        ← 선언
src/inference/on-device.ts:550                           ← 주석에서만 언급
__tests__/vision/types.test.ts:107                       ← 갈래 수를 세는 계약 테스트
```

선언의 주석이 그 용도를 스스로 적어 뒀다 — **"사진 설정이 「보지 않음」이라
시작하지 않았다 (FR-003)"**. 그 설정이 사라지므로 이 갈래는 **구조적으로 도달
불가능**해진다.

**결정**: `skipped`를 **제거한다.**

**근거**: 헌법 원칙 IV의 되돌리기 정신 — 도달할 수 없는 상태를 타입에 남기면
"언젠가 쓸지 모른다"는 이유로 판정 갈래가 늘어난다. `acceptance.ts`의 거부
갈래를 넷으로 묶어 둔 것과 같은 자리다. `no-photos`가 「볼 것이 없었다」를 이미
정확히 표현하며, 011이 세운 `seen`/`no-photos`의 갈림은 그대로 산다.

**대안 기각**: 남겨 두기 — 남기면 `types.test.ts`가 "갈래가 여섯이다"를 계속
주장하는데 그중 하나는 **영원히 만들어지지 않는 값**이다. 그것은 계약이 아니라
거짓말이다.

**영향**: [types.test.ts:100](../../__tests__/vision/types.test.ts#L100)의 갈래
수가 6 → 5로, 기대 배열에서 `"skipped"`가 빠진다.

## R4. 내부 깊이도 하나로 좁힌다 (FR-009)

**결정**: `VisionDepth`를 `"quick"` 하나로, `IMAGE_TOKENS`를 256 하나로 좁힌다.

**근거**: 헌법 v1.7.0이 「보는 깊이는 하나로 고정한다(MUST)」를 못 박았다. 내부
타입에 두 깊이가 남으면 **그 MUST가 타입에 반영되지 않은 채 주석의 약속으로만
남는다** — 041이 "메모리에 담지 않는다"를 주석이 아니라 구조로 만든 것과 같은 판단.

**영향 — 기존 계약 테스트의 주장이 뒤집힌다**:
[types.test.ts:123](../../__tests__/vision/types.test.ts#L123) `VisionDepth — none이
들어오지 못한다`가 **`"detailed"`를 담는다**고 주장한다. 이 주장은 이제 틀렸다.
테스트를 지우지 않고 **주장을 바꾼다** — 「하나뿐이며 `none`이 아니다」로. 지우면
"깊이가 `none`인 캡션은 뜻이 없다"는 011의 판단이 함께 사라진다.

**재지 않은 것(원칙 V)**: 256과 1024의 실제 출력 차이는 **여전히 재지 않았다.**
이 기능은 그 차이를 재지 않고 다이얼을 치운다 — 헌법 개정 경위가 그렇게 정했다.

## R5. 설정 저장소는 파일째 제거, 기기의 파일은 방치 (FR-007)

**결정**: `vision-setting-store.ts`를 삭제한다. 기기에 남은 `preferences/
vision-setting.json`을 **지우는 코드를 넣지 않는다.**

**근거**: 앱이 다시 읽지 않으므로 무해하다. 지우는 코드를 넣으면 **사용자
저장물에 손대는 판단을 코드가 하게 된다** — 008의 "받다 만 모델은 앱으로 못
지운다", 037의 "이미 받은 모델 파일을 앱이 지우지 않는다"와 같은 계열의 의도적
빈자리다.

**확인된 사실**: `loadVisionSetting`은 파일 없음·깨짐·유니온 밖 값을 **전부
`"auto"`로** 떨어뜨렸다. 즉 옛 값이 무엇이든(`none`·`detailed`) 마이그레이션
코드가 필요한 적이 없었다 — 이제는 읽는 쪽 자체가 사라진다.

## R6. 저장된 일기는 손대지 않아도 된다 (FR-013)

**확인된 사실(2026-09-14 조사)**: `DiaryEntry`에 사진 설정 필드가 **없다.**

```
character · authorName? · signalsUsed · createdAt · photos? · timing? · placeName? · title?
```

**결정**: 옛 일기 방어 코드를 만들지 않는다. FR-013은 **이 사실의 확인**으로
충족된다.

**037과 다른 자리다** — 037은 `DiaryEntry.character`가 파일에서 오는 값이라
좁아진 타입을 런타임에 만족하지 않아 읽는 쪽 방어가 **실제로 필요했다.** 여기는
필드 자체가 없으므로 그 문제가 성립하지 않는다. **없는 문제에 방어를 만들지
않는다.**

## R7. 백그라운드 경로가 이 기능의 실질 이행 지점

**확인된 사실**: [task.ts:139-141](../../src/schedule/task.ts#L139)이 「자동」과
설정 없음을 **전부 `"none"`으로** 떨어뜨린다.

```ts
const vision =
  visionPreference === "quick" || visionPreference === "detailed" ? visionPreference : "none";
```

기본 설정(「자동」)으로 자동 생성을 쓰는 사용자의 일기는 **사진이 아무리 많아도
한 장도 보지 않는다.** 029가 "백그라운드는 그 날 신호를 미리 읽지 않는다"는 이유로
둔 분기인데, 그 이유는 **파이프라인이 스스로 0장을 판정한다**는 사실(011)로 이미
해소돼 있었다.

**결정**: 이 분기를 통째로 제거하고 설정 로드 자체를 걷어낸다. 파이프라인이
신호를 읽어 0장이면 건너뛴다 — 화면 경로와 같은 판정이다.

## R8. 개발자 진단 경로도 같은 규칙 (FR-004a, 명확화 Q1)

**확인된 사실**: [DiagnosticsScreen.tsx:133](../../src/ui/DiagnosticsScreen.tsx#L133)이
`vision`을 넘기지 않고, [GenerationProbe.tsx:49](../../src/ui/GenerationProbe.tsx#L49)의
기본값이 `"none"`이다 → **그 버튼으로 돌린 생성은 사진을 안 본다.**

**결정**: `GenerationProbeProps.vision`을 제거한다.

**근거**: 검증 경로가 제품과 다르게 동작하면 그 검증은 제품을 재현하지 못한다.
Governance("예외를 코드에 몰래 두지 않는다")가 걸리는 자리이며, 인자가 남으면
FR-010("깊이를 되살릴 수 있는 플래그를 남기지 않는다")의 빈틈이 된다.

## R9. 헌법 검사에 새 규칙을 더할 것인가

**결정**: **더하지 않는다.**

**근거**: 헌법 검사(`constitution-rules.ts`)는 **경계를 넘는 import와 금지된
어휘**를 잡는 도구다. 이 기능이 막으려는 것("사진 보기 설정이 되살아나는 것")은
심볼이 존재하지 않으면 **`tsc`가 이미 막는다** — 없는 타입은 쓸 수 없다. 규칙을
더하면 `tsc`가 이미 하는 일을 두 번 하게 된다.

**대신 계약 테스트가 소스를 읽어 잠근다**(C1·C2·C6) — 이 저장소가 007 이후
써 온 방식이다.

**주의**: `checkVisionFile`의 기존 테스트 픽스처가 `VisionDepth`를 언급한다
([check-constitution.test.ts:467](../../__tests__/scripts/check-constitution.test.ts#L467)).
타입이 남으므로 **그 픽스처는 그대로 유효하다**(이름이 사라지는 것이 아니라
멤버가 줄 뿐).

## R10. 실기기 검증 범위

**결정**: dev(debug) 1회. release 빌드를 만들지 않는다.

**근거**: 새 네이티브 모듈이 없다(012 기준, 2026-09-09 저장소 소유자 확정).
빌드 1회가 약 19분이고 설치하려면 debug 앱을 지워야 해서 모델(~2GB)·일기·설정이
함께 사라진다.

**기기 상태 보존**: 자동 생성 ON(목표 12시)·배터리 예외·작성자 금동이는 **계속
쓰는 설정이므로 끄지 않는다.** `pm clear`를 쓰는 Maestro 흐름
(`unified-permission-onboarding.yml`)을 이 세션에서 돌리지 않는다 — 024 2차
세션이 그것으로 검증용 모델을 날렸다.
