# 앱 열기 자동 쓰기의 「한 번」과 넘겨 둔 날 바로잡기 — 설계

- 날짜: 2026-10-14
- 로드맵: 「백그라운드 자동 쓰기가 완주하지 못한다 — 안드로이드·iOS」 할 일 4번의 「`autoWriteDay`가 비워지지 않는 것」과 5번의 「지우기 직후 어제를 다시 쓰기 시작」. 그 과제의 나머지(2·3·6번, iOS 항목)는 건드리지 않는다.
- 스펙 번호: speckit-specify 뒤에 적는다.

## 1. 무엇이 잘못됐는가

둘 다 「앱을 열면 쓰는 중」(057)의 같은 자리에서 난다 — 판정이 홈에 넘겨 둔 날(`autoWriteDay`)과 한 실행에 한 번(`claimAutoWrite`).

### 결함 A — 설정에서 자동 쓰기를 켰다 끄고 닫아도 쓴다

`DiarySection`의 판정 effect는 판정이 「쓴다」일 때만 `setAutoWriteDay(decision.day)`를 부른다. 「쓰지 않는다」로 바뀌어도 값을 비우는 길이 없다.
설정에서 토글을 켜면 판정이 다시 돌아 어제가 서고, 곧바로 꺼도 그 값이 남아 설정을 닫는 순간(`covered`가 풀림) 홈의 057 effect가 시작한다.

### 결함 B — 「일기 모두 지우기」 직후 어제를 다시 쓴다

`requestWipe`는 지운 뒤 `diaryKey`를 올려 홈을 다시 마운트한다. 새 `DiarySection`의 판정이 「어제는 안 쓴 날」로 답하고, 그 실행의 「한 번」(`autoWriteClaimed`)이 남아 있으면 홈이 곧바로 쓴다.
「한 번」이 남는 실행은 흔하다 — 앱을 열 때 쓸 날이 없었던(모두 써 있던) 실행이 전부 그렇다.

### 재현 (2026-10-14, SM-S901N dev — `main` 17ebdc5 번들, 목표 시각 22시·실제 09시대, 어제에 사진 4장)

| | 절차 | 본 것 |
| --- | --- | --- |
| A | 자동 쓰기 꺼짐으로 앱을 연다 → 설정 → 토글 켬 → 끔 → 뒤로 가기 | 홈이 어제의 「쓰는 중」(`stop-button`)이 되고 약 50초 뒤 저장. 그때 `auto-diary.json`은 `{"enabled":false,…}`. 시도 기록: `꺼짐` → `홈에 넘김` → `꺼짐` |
| B | (어제가 써진 상태) 앱을 새로 연다 → 설정에서 토글 켬(판정 `재료 없음` — 그저께) → 닫음(쓰지 않음) → 설정 → 「일기 모두 지우기」 → 확인 | 일기 0편이 된 직후 홈이 어제의 「쓰는 중」. 시도 기록 맨 위 `홈에 넘김` |

둘 다 첫 시도에 재현됐다. 실험 전 상태(일기·설정·사진 사본)는 백업에서 되돌렸고(md5 일치) 심은 사진은 걷었다.

## 2. 소유자 결정 (2026-10-14)

1. **켠 채 닫으면 쓰는 것은 의도다.** 어느 시각에 켜든, 차례가 지난 날이 있으면 설정을 닫을 때 쓴다(078 창 밖 따라잡기 그대로). 고치는 것은 「끄면 쓰지 않는다」뿐이다.
2. **지우기는 그 실행의 「한 번」을 소모한다.** 지운 뒤 그 실행에서는 앱 열기 자동 쓰기가 저절로 시작하지 않는다. 앱을 새로 열면(새 프로세스) 종전대로 판정한다.

## 3. 규칙

**R1 — 넘겨 둔 날은 「지금 설정으로 한 가장 최근 판정」을 따른다.**
- 판정이 「쓴다」면 그 날, 그 밖(꺼짐·쓰는 시각 아님·모두 써 있음·건너뜀)이면 없음(`null`)이다.
- 판정을 낳은 설정이 지금 설정과 다르면(사용자가 방금 바꿨다) 새 판정이 나오기 전까지 없음이다 — 판정은 비동기(일기 목록·신호 읽기)라, 끈 직후 옛 판정의 날이 한순간이라도 홈에 닿지 않게 **렌더에서 가른다**(effect에서 비우지 않는다).
- 같은 설정에서 판정 둘이 겹치면(전경 복귀가 잇달아 옴) 늦게 시작한 판정만 반영한다.

**R2 — 「일기 모두 지우기」가 홈을 다시 마운트할 때 그 실행의 「한 번」을 소모한다.**
- 소모는 다시 마운트(`setDiaryKey`)보다 **먼저**다 — 뒤면 새 홈의 057 effect가 먼저 시작한다(080 H4·H7과 같은 순서 규칙).
- 지우지 못한 경우(`busy`)는 소모하지 않는다(홈도 다시 마운트되지 않는다). 일부만 지운 실패는 소모한다(홈이 다시 마운트된다).

### 바꾸지 않는 것

- 판정(`decideSchedule`·`resolveAutoWrite`·`selectableDays`), 백그라운드 태스크, 시도 기록의 갈래.
- 이미 시작한 쓰기 — 넘겨 둔 날이 없어져도 도는 쓰기를 멈추지 않는다(R1은 「시작」만 막는다. 설정을 여는 동안 홈은 시작하지 않으므로, 끄기 전에 이미 돌던 쓰기만 해당한다).
- 064(흉내가 「한 번」을 소모), 040(첫 실행이 이긴다), 080(합류는 소모하지 않고, 끊긴 합류만 소모한다 · `listStale`).
- 「온보딩부터 다시」·「모듈 다시 받기」 — `stopHome`은 같이 쓰지만 `diaryKey`를 올리지 않는다.

## 4. 「한 번」·넘겨 둔 날이 막던 것을 다시 센다

| 바뀌는 것 | 그것이 하던 일 | 바뀐 뒤 |
| --- | --- | --- |
| 넘겨 둔 날이 비워진다 | 080 「합류한 쓰기가 실패하면 홈이 이어서 쓴다」는 넘겨 둔 날이 남아 있어야 돈다 | 그대로 돈다 — 쓰는 중인 날은 아직 「안 쓴 날」이라 전경 복귀 판정도 같은 날을 준다. 설정을 꺼서 비워진 경우에는 이어 쓰지 않는다(끈 것이므로 맞다) |
| 넘겨 둔 날이 비워진다 | 홈이 쓴 뒤에도 값이 남아 있었다(무해 — 「이미 쓴 날」 확인이 막았다) | 전경 복귀 판정이 `모두 써 있음`이면 비워진다. 동작 차이 없음 |
| 지우기가 「한 번」을 소모한다 | 057 자동 시작 | 지운 실행에서는 시작하지 않는다(의도) |
| 지우기가 「한 번」을 소모한다 | 080 실패 뒤 이어 쓰기 | 지운 실행에서는 합류한 쓰기가 실패해도 이어 쓰지 않는다(조용히 쓰기 전 상태 — 080의 「한 번이 이미 쓰인 실행」과 같은 모양) |
| 지우기가 「한 번」을 소모한다 | — | 진단 쓰기 요청·홈 쓰기 버튼·백그라운드는 「한 번」을 보지 않는다. 그대로다 |

## 5. 구조

### 추천안 — 두 규칙을 `src/app/`의 작은 훅 둘로 뗀다

`App.tsx`는 테스트에서 렌더되지 않는다(소스 계약으로만 잠근다). 지금 자리에서 고치면 두 결함의 방어가 정규식 계약뿐이다 — 081이 드러낸 「손으로 쓴 값으로 초록」과 같은 위험이다.
`use-consent-gate.ts`(074) 선례대로 뗀다:

- **`src/app/use-auto-write-handoff.ts`** — `DiarySection`의 판정 effect를 옮긴다. 입력: 설정·`previewDay`·`skipPort`·일기 목록 통로·시도 기록 통로·`onSkipped`. 출력: 넘겨 둘 날(`DayDate | null`).
  안에서 `{ day, settings }`를 들고, 돌려줄 때 `settings === 지금 설정`일 때만 `day`를 준다(R1). 판정마다 번호를 붙여 늦게 시작한 것만 반영한다. 시도 기록·사진 권한 건너뜀 알림·`AppState` 재판정은 그대로 옮긴다.
- **`src/app/use-auto-write-claim.ts`** — `AppFrame`의 `autoWriteClaimed`·064 소모 effect·`claimAutoWrite`를 옮기고 `spendAutoWrite()`(묻지 않고 소모)를 더한다. `requestWipe`가 `setDiaryKey` 앞에서 부른다(R2).

`DiaryHomeScreen`은 바꾸지 않는다 — 이미 `autoWriteDay == null`이면 시작하지 않고, `claimAutoWrite()`가 거짓이면 시작하지 않는다.

### 대안 — 제자리 수정

`App.tsx` 안에서 `autoWriteDay` state를 `{ day, settings }`로 바꾸고 `requestWipe`에 `autoWriteClaimed.current = true` 한 줄을 더한다. 변경이 가장 작고 057·064 소스 계약이 그대로 선다.
대가: 두 규칙을 실제로 돌려 보는 테스트를 쓸 수 없다(소스 계약 + 홈 단위 테스트뿐).

**긍정적 관점** — 훅으로 떼면 두 결함을 「진짜 판정 + 진짜 홈 + 진짜 파이프라인·등록부」 조립으로 재현하고 고친 것을 볼 수 있다. 다음에 「한 번」을 건드리는 변경도 같은 테스트가 받는다.

**악마의 대변인** — 057·064의 소스 계약(`app-auto-write-source.test.ts`·`simulation-wiring.test.ts`)이 읽는 파일이 바뀐다. 옮기는 과정에서 계약을 약하게 만들 위험이 있고, 세 줄짜리 ref를 훅으로 올리는 것은 과하다고 볼 수 있다. 옮긴 뒤에도 `requestWipe`의 순서(소모 → 다시 마운트)는 여전히 `App.tsx`의 소스 계약으로만 잠긴다.

## 6. 테스트

먼저 실패를 본다(TDD). 위반 주입으로 방어를 확인한다.

- **조립 테스트**(`.tsx`, 새 파일) — 훅 둘 + 진짜 `resolveAutoWrite` + 진짜 `DiaryHomeScreen` + 진짜 `createPipeline()`(가짜 백엔드)과 등록부를 한 하니스에 묶는다(080 `home-join.test.tsx` 「FR-013」 방식).
  - A: 설정 꺼짐 → 켬(판정이 날을 넘김, 홈은 덮여 있음) → 끔 → 덮임을 푼다 → 파이프라인이 한 번도 돌지 않는다.
  - A 경합: 켬 판정이 날을 넘긴 뒤 끄고, 꺼짐 판정이 끝나기 전에 덮임을 푼다 → 돌지 않는다(늦게 끝난 켬 판정이 반영되지 않는 것은 훅 단위에서 본다 — effect 정리가 이미 막는다).
  - 의도 확인: 켠 채 덮임을 풀면 그 날을 쓴다.
  - B: 모두 써 있는 채 마운트(「한 번」 남음) → 일기를 비우고 소모 → key를 올려 다시 마운트 → 돌지 않는다. 소모를 빼면 돈다(위반 주입).
  - 「돌지 않는다」는 마지막 화면이 아니라 **파이프라인이 불린 횟수**와 「쓰는 중」이 그려진 횟수로 단언한다(080의 교훈).
- **훅 단위**(`.tsx`): 판정 순서 뒤바뀜, 「쓰지 않는다」 판정이 비우는 것, `busy`가 소모하지 않는 것, 064·040이 이기는 규칙이 옮긴 뒤에도 같은 것.
- **소스 계약**: `requestWipe`가 `busy`가 아닐 때 `spendAutoWrite()`를 `setDiaryKey` 앞에서 부른다. 옮긴 057·064 계약은 새 파일을 읽게 고치되 단언을 줄이지 않는다.
- 먼저 읽을 기존 계약: `app-auto-write-source.test.ts`·`simulation-wiring.test.ts`·`home-auto-write.test.tsx`·`home-simulation.test.tsx`·`home-join.test.tsx`·`home-wipe.test.tsx`.

## 7. 실기기 확인 (dev, SM-S901N)

재현에 쓴 Maestro 흐름 둘을 고친 번들로 다시 돌린다(끝 단언만 뒤집는다 — `stop-button`이 뜨지 않는다). 시작 전 백업, 끝나면 되돌림.

- A: 켰다 끄고 닫는다 → 쓰지 않는다. 켠 채 닫는다 → 어제를 쓴다(의도).
- B: 지운 직후 쓰지 않는다. 앱을 새로 열면 어제를 쓴다.
- 회귀: 자동 쓰기를 켠 채 앱을 열면 어제의 「쓰는 중」으로 시작한다(057).

## 8. 남는 것·미확인

- **백그라운드는 지운 날을 다시 쓸 수 있다.** 자동 쓰기가 켜져 있으면 다음에 깨는 잡이 어제를 쓴다(창 밖 따라잡기 하루 한 번, 또는 창 안). R2는 「지운 직후 눈앞에서 다시 쓰는 것」만 막는다 — 소유자가 고른 범위다.
- 프로세스가 오래 사는 경우(iOS) 지운 뒤로는 그 프로세스가 죽을 때까지 앱 열기 자동 쓰기가 없다.
- 지운 직후에도 시도 기록에는 `앱 열기 · 홈에 넘김`이 남는다(「넘김 ≠ 시작」, 078).
- iOS는 실제 기기가 없다 — 미확인.
