# 축별 스펙 로드맵

**작성**: 2026-08-01
**전제**: [001-persona-diary-contracts](001-persona-diary-contracts/spec.md) (경계면 계약)

## 이 문서의 역할

001이 답한 것은 **"축들이 무엇을 주고받는가"**다. 이 문서가 답하는 것은 **"그 축들을 어떤 순서로 쓰고, 각각 언제 끝나는가"**다.

이 문서는 **각 축의 내용을 쓰지 않는다.** 어떤 센서를 읽을지, 프롬프트를 어떻게 쓸지는 해당 축 스펙의 몫이다. 여기서 정하는 것은 범위의 **경계와 끝**뿐이다.

_왜 필요한가:_ 반복 실패의 원인은 에이전트가 한 축을 붙잡고 지나치게 판 것이었다. 그것을 막는 것은 컨셉 설명이 아니라 **"여기까지 답하면 끝"이라는 선**이다. 끝이 정의되지 않은 스펙은 계속 파인다.

---

## 착수 순서

헌법 「개발 워크플로」의 Spec-First 순서(퍼소나 → 수집·정제 → AI 입출력 → 어댑터 → 저장 → UI → 검증 하네스)를 네 축에 대응시킨 것이다.

| 순서 | 스펙 | 왜 이 순서인가 |
| --- | --- | --- |
| 002 | **퍼소나** | 가장 작고 다른 축에 의존하지 않는다. 추론 축이 입력으로 받을 것이므로 먼저 확정되어야 한다. |
| 003 | **수집·정제** | 추론의 입력을 만든다. 이것이 확정되어야 추론 스펙이 실재하는 입력을 놓고 쓸 수 있다. |
| 004 | **추론** | 002·003의 산출물을 받는다. 앞의 둘이 없으면 입력을 상상하게 되고, 그것이 반복 실패의 형태였다. |
| 005 | **저장** | 004의 산출물을 받는다. 다만 001이 이미 보관 대상 세 가지를 못 박았으므로 잔여 결정이 가장 적다. |
| 006 | **UI** | 위 넷이 모두 확정된 뒤. 표시할 것이 정해지지 않으면 화면을 정할 수 없다. |

**병행 가능**: 002는 003과 독립적이므로 동시에 진행해도 어긋나지 않는다. 004는 002·003 **양쪽이 끝난 뒤에만** 착수한다.

**순서를 어길 수 있는 경우**: 없다 — 단, 004를 먼저 쓰고 싶어지는 순간이 오면 그것은 003이 덜 끝났다는 신호다. 003으로 돌아간다.

## 002 — 퍼소나 스펙

**상태**: 작성 완료 → [002-persona-identity/spec.md](002-persona-identity/spec.md)

**답해야 끝나는 질문**

- 앱이 이름을 **어떻게** 부여하는가 (후보 목록에서 선택 / 생성 / 그 외)
- 성격이 **어떤 형태로 표현**되는가 (한 문장 / 여러 속성 / 그 외)
- 성격의 **가짓수와 분포** — 모든 사용자가 같은 성격을 받는가, 갈리는가
- 사용자가 이름을 바꿀 때의 **제약** (길이, 빈 값, 중복 등)
- 최초 부여가 **언제** 일어나는가 (첫 실행 / 첫 생성 시도 / 그 외)

**답하지 않는 것**

- 성격이 프롬프트에 어떻게 반영되는가 → 004
- 퍼소나를 화면에 어떻게 보여주는가 → 006
- 저장 형식 → 005

**완료 조건**

- [x] 위 다섯 질문에 답이 있다
- [x] 001의 FR-001~FR-007, FR-004a·b를 위반하지 않는다 (특히 성격 불변, 기기 비종속)
- [x] 004가 이 문서만 읽고 "퍼소나가 무엇을 넘겨주는지" 확정할 수 있다 — 002 FR-140~FR-142

**파기 시작했다는 신호**: 성격별 문체 예시를 쓰고 있다면 004의 영역이다.

## 003 — 수집·정제 스펙

**상태**: 작성 완료 → [003-signal-collection-digest/spec.md](003-signal-collection-digest/spec.md)

네 축 중 **가장 크고 가장 파기 쉬운** 축이다. 완료 조건을 특히 엄격하게 본다.

**답해야 끝나는 질문**

- 읽을 **데이터 소스 목록**과 각각에 필요한 권한
- 권한이 거부되었을 때의 **기능 축소** 방식 (헌법 원칙 V: 크래시가 아닌 축소)
- 사진 메타데이터의 **채택·폐기 기준**
- 사진 **캡션 생성 방식**
- 일별 집계에 담기는 **항목의 최종 목록**과 산출·압축 규칙
- 집계 **생성 시점** (요청 시 집계 / 상시 수집 후 조회)
- 집계가 **"적다"의 판정 기준** — 001 FR-043b가 이 축에 위임했다

**답하지 않는 것**

- 집계를 어떻게 저장하는가 → 005
- 집계를 화면에 어떻게 보여주는가 → 006
- 집계를 프롬프트에 어떻게 넣는가 → 004

**완료 조건**

- [x] 위 일곱 질문에 답이 있다 — 003 「이 스펙의 범위」의 대응표
- [x] 001의 FR-008~FR-013b를 위반하지 않는다 — 특히 **미관측과 값-없음의 구별**(FR-010)이 항목별로 표현 가능하다 — 003 FR-211·FR-242·FR-243, 사진 항목 내부까지 FR-252
- [x] "비었다"와 "적다"의 판정이 **기계적으로 결정 가능**하다 (사람의 재량 판단이 개입하지 않는다) — 003 FR-271~FR-275. 세는 대상 여섯, 임계값 2~6, 전 조합에서 판정이 정확히 하나
- [x] 004가 이 문서만 읽고 집계의 형태를 확정할 수 있다 — 003 FR-244의 항목 표와 FR-280~FR-283
- [ ] 온디바이스 여건에서 **실측으로 검증된** 압축 수준이다 — 001의 전제(노이즈가 크면 품질이 떨어진다)가 근거 없는 가정으로 남지 않는다 — **구현 단계로 이월.** 스펙 단계에서 닫을 수 없는 조건이다(아래 참조)

**파기 시작했다는 신호**: 특정 라이브러리의 API 사용법을 쓰고 있다면 구현 단계의 영역이다.

**이월된 완료 조건 — 압축 수준의 실측**

003을 쓰는 동안 확인된 사실: 저장소의 PoC에는 센서 관련 의존성이 하나도 설치되어 있지 않고 신호는 손으로 넣은 값이었다. 즉 concept.md의 "실측으로 확인했다"는 **일기 생성이 가능한가**에 대한 것이며, **집계 크기와 추론 품질의 관계**는 아직 관측된 적이 없다.

003은 이것을 숨기지 않고 다음처럼 처리했다: 상한 값·시간대 세분도·임계값을 **확정하지 않고**(FR-228·FR-257·FR-274) 실측을 요구사항으로 못 박고(FR-257), 검사 지점을 남겼다(SC-216).

**따라서 이 조건은 구현 단계에서 닫는다.** 근거 없는 숫자를 스펙에 박아 넣고 완료로 표시하는 것이 이 로드맵이 막으려던 실패이므로, 값을 비운 채 실측을 요구하는 쪽을 택했다.

## 004 — 추론 스펙

**착수 전제**: 002와 003이 모두 끝나 있을 것. — **충족되었다.** 002·003 모두 작성 완료이므로 004에 착수할 수 있다.

**답해야 끝나는 질문**

- **프롬프트 구성** — 집계와 퍼소나를 어떤 형태로 넣는가
- **모델 선택**과 어댑터 구현 (헌법 원칙 III: `AIEngine` 경계 유지)
- **일기 본문의 구성 요소** (제목·본문·그 외 무엇으로 이루어지는가)
- **출력 형식**과 해석 방식, 해석 실패의 판정 기준
- **화자 일관성**의 판정 방법 — 001 FR-019가 요구하나 판정 수단은 비어 있다

**답하지 않는 것**

- 일기를 어떻게 저장하는가 → 005
- 생성 중·실패를 어떻게 표시하는가 → 006
- 집계에 무엇이 담기는가 → 003

**완료 조건**

- [ ] 위 다섯 질문에 답이 있다
- [ ] 001의 FR-014~FR-021, FR-022~FR-027을 위반하지 않는다
- [ ] **회상 슬롯이 비어 있음**이 계약에 명시되어 있다 (FR-015)
- [ ] 실패 판정이 **명확하다** — 무엇이 성공이고 무엇이 실패인지 경계가 모호하지 않다
- [ ] 사실 일치도를 **품질 기준으로 쓰지 않는다** (FR-020)
- [ ] 화자 일관성을 **자동으로 검사할 수 있는 형태**로 정의했다 — 못 하면 그 사실과 대안을 명시한다

**파기 시작했다는 신호**: 프롬프트 문구를 다듬는 데 시간을 쓰고 있다면, 그것은 스펙이 아니라 구현·튜닝이다. 스펙은 "프롬프트가 무엇을 포함하는가"까지다.

## 005 — 저장 스펙

001이 보관 대상 세 가지를 이미 못 박았으므로 **잔여 결정이 가장 적다.**

**답해야 끝나는 질문**

- **저장 매체와 구조**
- **이행(마이그레이션)** 절차 — 001 FR-036이 요구한다
- **소프트 삭제된 기록의 표현 방식**과 복구 진입 경로
- 소프트 삭제 기록의 **누적 처리** — 001은 "남는다"만 정했고 언제까지인지는 비웠다
- **조회 성능**과 보존 기간

**답하지 않는 것**

- 삭제·복구를 화면에서 어떻게 조작하는가 → 006

**완료 조건**

- [ ] 위 다섯 질문에 답이 있다
- [ ] 001의 FR-028~FR-037을 위반하지 않는다
- [ ] **원본 로그를 보관하지 않음**이 구조로 보장된다 (FR-029) — 관행이 아니라 구조여야 한다
- [ ] 일기와 집계의 **짝이 모든 경로에서 유지**된다: 저장·소프트 삭제·복구·재생성·전체 삭제 (FR-032)
- [ ] 전체 삭제 후 **복구 가능한 잔여물이 없다** (FR-035a)

**파기 시작했다는 신호**: 인덱스 설계나 쿼리 최적화는 구현 단계다.

## 006 — UI 스펙

**착수 전제**: 002~005가 모두 끝나 있을 것. 표시할 것이 확정되지 않으면 화면을 정할 수 없다.

**답해야 끝나는 질문**

- **화면 구성**과 이동 경로
- **생성 진행·실패 표시** 방식 (001 FR-022, FR-041)
- **덮어쓰기 확인**의 표현 (FR-040)
- **적은 집계 확인**의 표현 (FR-043) — 품질 게이트로 보이지 않게 하는 것이 관건
- **삭제·복구** 조작 경로
- 개발 모드에서 **클라우드 사용 중임의 표시** (헌법 원칙 I)

**완료 조건**

- [ ] 위 여섯 질문에 답이 있다
- [ ] 실패가 **조용히 지나가지 않는다** (헌법 원칙 II)
- [ ] FR-043의 확인이 **"막는 것"이 아니라 "알리는 것"으로 읽힌다** (FR-043a)
- [ ] 일기와 그 근거 집계를 **대조할 수 있다** (FR-031) — 이 앱의 유희가 성립하는 지점이다

## 이 로드맵 밖의 것

아래는 스펙 순서에 포함되지 않는다. 별도 판단이 필요하다.

- **회상 슬롯 활성화** — "오늘의 신호가 과거 문장에 묻히지 않는가"를 실측한 뒤에만 판단 (001 FR-016)
- **자동·백그라운드 생성** — 001이 범위 밖으로 뒀다
- **원격지 저장** — 도입 시 헌법 개정과 001 FR-034·035 재검토가 선행되어야 한다 (001 Assumptions)
- **실험 코드 정리** (`src/types/signals.ts`, `src/services/aiService.ts`, `App.tsx`) — 구현 단계
- **README.md·AGENTS.md 정정** — 아직 "따뜻한 1인칭 한국어 일기"로 서술되어 사람 일기로 읽힌다. 스펙 작업과 독립적이며 언제든 가능하다.
