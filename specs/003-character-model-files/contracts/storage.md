# 계약: 보관과 삭제

**대응 요구사항**: FR-025~FR-030, FR-028a, FR-029

**구현 위치**: `src/models/storage.ts`, `src/models/port.ts`

---

## 이 계약이 지키는 것

헌법 원칙 III의 **"로스터는 켜고 끌 수 있다(MUST)"** 가 여기서 성립한다. 켤 수만 있고 끌 수
없으면 절반이며, 모델이 GB이므로 끄지 못하면 사용자가 저장 공간을 볼모로 잡힌다.

---

## 자리

```
Paths.document/
├── diary/                  002의 것. 건드리지 않는다
└── models/
    ├── <assetKey>.gguf     모델 파일
    └── state.json          검증 결과 + 중단된 내려받기 상태
```

**`Paths.document`이지 `Paths.cache`가 아니다.** `cache`는 시스템이 공간 부족 시 지우는
자리다(타입 정의에 명시). 모델은 다시 받는 비용이 크므로 그 자리에 두지 않는다.

**그래도 사라질 수 있다고 가정한다** — 사용자가 파일 관리자로 지울 수 있고, 시스템이
document를 건드리는 경우도 없다고 단정할 수 없다. 그래서 FR-021e가 필요하다.

**파일명이 모델명이 되지 않는다**(FR-004). `<assetKey>`는 불투명한 값이며 캐릭터 식별자와도
다르다 — 파일 관리자로 열어 보아도 어느 캐릭터의 무슨 모델인지 알 수 없어야 한다.

---

## 메타데이터를 한 파일에 모으는 이유

002는 일기를 날짜별 파일로 쪼갰다. 여기는 반대로 한 파일에 모은다.

| | 002의 일기 | 이 기능의 메타데이터 |
| --- | --- | --- |
| 항목 수 | 계속 늘어난다 | **다섯으로 고정** |
| 조회 방식 | 한 날짜씩 | **늘 전부** (목록 화면) |
| 판단 | 쪼갠다 | **모은다** |

상태를 물을 때 한 번만 읽으면 되고, 그것이 SC-016(조회가 파일 크기와 무관)에 맞는다.

**쓰기는 002와 같이 원자적이어야 한다** — 임시 파일에 쓰고 옮긴다. 쓰다 죽으면 검증 결과
전체를 잃고, 그러면 모든 캐릭터가 `ready`가 아니게 된다(FR-021c). 파일은 남아 있으므로
**다시 검증하면 되지 다시 받을 필요는 없다** — 정리와 재검증은 다른 일이다.

## 삭제 (FR-025~FR-029)

**지우면 무엇이 사라지는가**:

| 지우는 것 | 사라진다 | 남는다 |
| --- | --- | --- |
| 모델 파일 | ✅ | |
| 그 캐릭터의 검증 결과 | ✅ | |
| 그 캐릭터의 중단 상태 | ✅ | |
| **부분 파일** | ✅ (FR-029) | |
| **그 캐릭터로 쓴 일기** | | ✅ **(FR-030)** |
| 다른 캐릭터의 무엇이든 | | ✅ |

**FR-030이 가장 중요하다.** 모델 파일과 일기는 별개다. 002의 `diary/`는 이 기능이 건드리지
않는다 — 일기는 되돌릴 수 없는 값이고 모델은 다시 받을 수 있는 값이라, 무게가 다르다.

**FR-029(부분 파일 정리)를 빠뜨리기 쉽다.** 받다 만 캐릭터를 지울 때 부분 파일이 남으면
공간이 실제로 비지 않고, 사용자는 지웠는데 왜 공간이 그대로인지 알 수 없다(SC-008).

**지우기 전에 알린다**(FR-027). 다시 받아야 한다는 것이 드러나야 한다. 다만 002의 일기
덮어쓰기와는 무게가 다르다 — 일기는 되돌릴 수 없지만 모델은 다시 받을 수 있다.

## 저장 공간 표시 (FR-028, FR-028a)

**캐릭터 단위로 합산해서 내준다.** 파일별로 쪼개 보이면 한 캐릭터가 파일 몇 개를 쓰는지
드러나고, 그것이 모델 구성의 정보다(원칙 III).

한 캐릭터가 여러 파일을 가질 수 있는 모양은 열어 두되(FR-033) **밖으로는 하나의 수로**
나간다.

부분 파일도 합산한다 — 사용자가 보는 것은 "이 캐릭터가 지금 내 기기에서 차지하는 자리"이고,
받다 만 것도 자리를 차지한다.

## 다음 기능에 넘기는 것

- **자동 정리** — 오래 안 쓴 캐릭터를 앱이 알아서 지우는 것. 사용자가 고른 캐릭터를 앱이
  지우는 것은 헌법 원칙 III의 "사용자가 고른다"와 부딪히므로 지금 만들지 않는다
- **여러 캐릭터가 파일을 공유하는 경우** — 지금은 겹치지 않는다고 가정한다. 겹치는 날이
  오면 한 캐릭터를 지울 때 다른 캐릭터가 못 쓰게 되므로 삭제 규칙을 다시 정해야 한다
- **시각 인코더 파일** — 한 캐릭터가 여러 파일을 갖는 모양은 열어 두되 채우지 않는다
  (FR-033)
