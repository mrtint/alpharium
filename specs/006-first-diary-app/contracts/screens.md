**Feature**: 006-first-diary-app | **Date**: 2026-08-18

**화면 디자인은 이 계약의 범위가 아니다**(FR-027). 여기서 정하는 것은 **무엇이 보이고
무엇이 보이지 않는가**이며, 그것은 헌법 문제이지 미감 문제가 아니다.

## §2. 화면과 전이

상태 정의는 [data-model.md §2](../data-model.md)에 있다. 여기서는 **각 화면이 무엇을
보여야 하고 무엇을 보이면 안 되는가**를 정한다.

### `list` — 목록 (첫 화면)

**보인다**: 날짜순 일기 목록. 각 항목은 날짜와 「읽을 수 있는가」.
「일기 쓰기」 동작. 일기가 없으면 그 사실과 **무엇을 하면 생기는지**(S7).

**보이지 않는다**: 일기 본문 미리보기 — 필요 없고, 목록에서 전부 역직렬화하게 된다.

**⚠️ S1이 가장 위험한 자리**: 「일기 쓰기」가 **저장 여부를 보지 않는다.**
「이미 있으면 그것을 보여준다」는 지름길을 만들면 저장된 것이 생성을 대신하고,
그 순간 원칙 I이 깨진다. **쓰기는 언제나 실제 생성을 돈다.**

### `detail` — 전문 읽기

**보인다**: 일기 전문(길면 스크롤), 그 일기가 **어느 날의 것인지**(FR-019).

**보이지 않는다**: 어느 캐릭터로 썼는지를 **모델 정보로** 드러내는 것(S4).
생성에 걸린 시간(S5).

### `unreadable` — 읽을 수 없는 일기

**보인다**: 그 날짜에 일기가 **있었으나 읽을 수 없다**는 것(S3).

**보이지 않는다**: 빈 일기. 파일 경로·파싱 오류 메시지(개발자 정보).

**왜 이 화면이 필요한가**: 조용히 빼면 「없었다」와 구분이 사라진다. 사용자는 일기를
쓴 기억과 화면이 어긋나는 것을 설명할 방법이 없다(원칙 V).

### `writing` — 쓰는 중

**보인다**: 「쓰고 있다」. **그것뿐이다.**

**보이지 않는다**: 진행률·남은 시간·생성 중인 글(S6). 경과 시간(S5).

**왜**: 진행률은 남은 토큰 수를 세어야 하고 그 수는 원칙 IV가 금지한 속도 지표로
자란다. 생성 중인 글을 흘리면 **판정을 통과하지 않은 글이 화면에 오른다**(005 FR-035b) —
거부될 글을 사용자가 이미 읽어 버린다.

**전이**: 사용자 조작으로 벗어날 수 없다. 취소 버튼을 두지 않는다 — 005가 「앱이 앞에
있는 동안만 돈다」로 정했고 중단은 앱이 앞을 벗어날 때만 일어난다.

### `written` — 방금 쓴 일기

**보인다**: 일기 전문. 덮어썼으면 **그 사실**(FR-034).
저장 실패면 **「저장하지 못했다」 + 「앱을 나가면 사라진다」**(FR-012b).

**보이지 않는다**: 생성에 걸린 시간(S5).

**왜 저장 실패에도 글을 보이는가**: 30초를 들여 만든 글이고 다시 생성해도 같은 글이
나오지 않는다. **원칙 I을 어기지 않는다** — 금지된 것은 미리 만든 글을 생성 대신
내놓는 것이지 방금 생성한 글을 보여주는 것이 아니다(명확화 2026-08-18).

### `failed` — 실패

**보인다**: 사용자가 **다음에 무엇을 할 수 있는지**(S8).

**보이지 않는다**: **거부된 글**(S2 — 접어서 보여주는 것도 화면에 오르는 것이다).
「되뱉었다」·「언어가 다르다」 같은 모델 실패 양상(S4 — 캐릭터 뒤의 모델을 드러낸다).

**구현**: 005의 `describeFailure()`를 재사용한다. 이미 갈래를 「할 수 있는 것」으로
옮기며 원칙 III을 지킨다.

### `build-error` — 이 빌드가 잘못 만들어졌다

**보인다**: 「이 빌드가 잘못 만들어졌다」는 것.

**보이지 않는다**: 환경 변수 **이름과 값**(개발자 정보). 「다시 시도하라」(S10 —
사용자가 고칠 수 있는 문제가 아니다).

**전이**: **막다른 길이다.** 일기 기능이 막힌다(FR-035a). 다만 **앱은 뜬다**
(FR-035c) — 시작 시점에 죽으면 원인을 알 길이 없다.

## §3. 진단 화면과의 경계 (S9)

| 환경 | 진단 화면 | 사용자 경로 |
| --- | --- | --- |
| `local` | 열린다 | 열린다 |
| `dev` | 열린다 | 열린다 |
| `prod` | **닫힌다** | 열린다 |

판단은 001의 `showsOnScreen(resolution)`이 이미 한다. **이 기능이 그 경계를 느슨하게
하지 않는다.**

**사용자 경로는 세 환경 전부에서 돈다**(FR-024). 진단 화면이 열리는 환경에서도
사용자 경로가 진단을 거치지 않는다 — 그래야 SC-009(「진단을 거쳐야만 닿는 사용자 기능
0개」)를 검증할 수 있다.

## §4. 준비되지 않은 상태 (Story 5)

| 상태 | 화면이 말하는 것 | 근거 |
| --- | --- | --- |
| 모델 없음 | 캐릭터를 먼저 준비해야 한다 + 받는 자리 | FR-028 |
| 사진 권한 없음 | 일기는 생성되되 **사진을 보지 못했다**가 드러난다 | FR-032 |
| 하루 안 닫힘 | 아직 이르다 | FR-033 |
| 시각 설정 `quick`/`detailed` | 이 설정으로는 아직 쓸 수 없다 | 005 FR-029 |

**FR-032가 원칙 V의 화면 쪽 방어다**: 사진을 **보지 못한** 하루(`unknown`)와 사진이
**없었던** 하루(`none`)가 화면에서 같게 보이면 안 된다. 004가 값에서 지킨 구분이
여기서 무너지면 무의미해진다.

## §5. 검증

### 기기 없이 (`npm test`)

`@testing-library/react-native` 14. **⚠️ `render`가 Promise를 반환한다 — `await`
없이 쓰면 `screen`이 비고 오류 문구가 원인을 가리지 않는다**(AGENTS.md).
`toHaveTextContent`는 정확히 일치를 보므로 부분 문자열은 정규식으로.

| 검사 | 무엇 |
| --- | --- |
| S1 | 저장된 일기가 있어도 「쓰기」가 파이프라인을 부른다 |
| S2 | 생성 거부 시 화면 어디에도 거부된 글이 없다 |
| S3 | `readable: false` 항목이 목록에 있고 「없음」과 다르게 보인다 |
| S6 | `writing` 화면에 진행률·시간·본문이 없다 |
| S7 | 빈 목록에서 안내가 보인다 |
| S8 | 각 실패 갈래마다 「할 수 있는 것」이 보인다 |
| S10 | `build-error`에 「다시 시도」가 없고 환경 변수 이름도 없다 |

**상태 전이는 순수 함수(`src/app/state.ts`)로 두어 전 갈래를 기기 없이 검증한다**
(SC-023).

### 실기기 (Maestro)

`.maestro/diary-user-path.yml` — 진단을 거치지 않고 목록 → 쓰기 → 읽기.

**⚠️ `scripts/run-device-tests.mjs`의 `FLOWS`에 등록해야 돈다.** 등록하지 않으면
파일이 있어도 실행기가 돌리지 않고, 초록불인데 아무것도 검증되지 않은 상태가 된다.

**⚠️ 한글 검증 문구는 `-Dfile.encoding=UTF-8`이 있어야 읽힌다.** 실행기가 이 옵션을
넣으므로 그것을 거치면 신경 쓸 것이 없다.
