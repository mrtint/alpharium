# Alpharium Constitution

## 이 앱이 무엇인가

주인의 휴대폰이 화자가 되어 하루를 일기로 쓴다. 사람이 쓰는 일기가 아니다.

휴대폰은 주머니와 가방 속에 있어서 세상을 조금밖에 보지 못한다. 가진 것은 사진 몇 장,
GPS 궤적, 걸음 수, 배터리와 연결 상태뿐이다. 그 조각으로 하루를 짐작해 쓰는 것이 이
앱이다. 장님이 코끼리를 만지듯 제한된 정보로 일상을 기록한다.

그러므로 이 앱은 정확한 기록 장치가 아니라 감상이다. 진지한 일기를 만드는 것이 목적이
아니다.

## Core Principles

### I. 온디바이스가 제품이다 (NON-NEGOTIABLE)

추론은 사용자의 기기에서 돈다. 이것은 타협 대상이 아니다.

- 엔드유저가 읽는 일기는 반드시 그 기기에서 생성된 것이어야 한다(MUST).
- 미리 만들어 둔 응답(Mock)을 저장해 두고 보여주는 경로를 만들지 않는다(MUST NOT).
- 개발과 튜닝 단계에서는 데스크톱 추론 서버를 쓸 수 있다(MAY). 단 온디바이스와 동일한
  GGUF, 동일한 프롬프트, 동일한 샘플링 파라미터를 쓴다(MUST).
- 원격 상용 API 추론은 배제한다(MUST NOT).

### II. 화자는 휴대폰이고, 시야는 좁다

일기의 "나"는 주인이 아니라 주인의 휴대폰이다.

- 제한된 시야는 결함이 아니라 이 제품의 설정이다. 가진 단서(시각, 장소, 사진 등)로 주인의 하루를 짐작하는 것이 이 앱의 정체성이다.
- 기록에 없는 사실이나 대상을 있었던 것처럼 확정하여 단언하지 않는다(MUST NOT).
- 화자가 주인의 시점(사람의 시점)으로 뒤집히지 않는다(MUST NOT).
- 모르는 것을 모른다고 하거나, 단서를 바탕으로 주인의 하루를 짐작하는 서술은 허용한다(MAY).

### III. 캐릭터는 모델 위에 선다

사용자는 엔지니어링 스펙이 아닌 글 쓰는 성격(페르소나)을 보고 고른다.

- 모델 식별자, 파라미터 수, 양자화 방식 등 내부 기술 사양은 사용자 화면에 노출하지 않는다(MUST NOT).
- 캐릭터의 페르소나는 모델의 실측된 성질에 기반해야 하며, 지어낸 성격을 붙이지 않는다(MUST).
- 관측 근거가 없는 캐릭터는 로스터에 들어올 수 없다(MUST NOT).
- 캐릭터의 이름은 사용자가 변경할 수 있다(MAY). 단, 사용자가 지은 이름은 호칭에만 흐르며 기본 페르소나의 성격을 대체하지 않는다(MUST).
- 사용자가 고르지 않은 캐릭터의 모델 파일은 임의로 내려받지 않는다(MUST NOT). 단, 최초 실행 시 동작을 위한 기본 캐릭터 하나를 받는 것은 허용한다(MAY).

### IV. 측정 장치를 제품에 들이지 않는다

이 저장소는 사용자가 사용하는 제품을 만드는 곳이다.

- 모델 출력을 점수로 매기거나, 여러 모델을 비교하거나, 품질을 자동 채점하는 평가/벤치마크 코드를 제품 코드에 넣지 않는다(MUST NOT).
- 캐릭터의 근거가 될 실험과 벤치마크 관측은 별도 저장소에서 수행하고, 이 저장소에는 그 결과만 반영한다(MUST).
- **사용자 경험(UX)과의 경계**: 사용자의 기다림을 덜고 상황을 친절히 안내하기 위한 진행 인디케이터, 다운로드 상태 표시, 경과 시간 안내 등 정상적인 제품 UI/UX 개선 요소는 이 금지의 대상이 아니다.

### V. 관측된 사실과 추측을 구분해 기록한다

정직한 기록이 이 제품의 태도다.

- 어떤 값이 실측인지 짐작인지를 문서와 코드에서 명확히 구분한다(MUST).
- 관측 통로가 없는 신호는 임의의 기본값으로 채우지 않고 부재(`unknown`)를 정직하게 인정한다(MUST).
- 합성 데이터로 모델 품질을 평가하지 않는다(MUST NOT).
- 기능이 완성되었다고 판단하려면 최소 한 번은 실기기에서 돌아야 하며, 건너뛴 실기기 테스트는 통과가 아니다(MUST).

## 로스터

원칙 III의 확정 값이다.

- 검증된 캐릭터 모델(`kanana-1.5-2.1b`)을 기본으로 둔다.
- 로스터가 하나라는 것은 완성이 아니라 현재 검증된 상태다. 진입 기준을 통과한 캐릭터는 언제든 추가될 수 있다.
- 같은 모델을 공유하는 여러 페르소나가 존재할 수 있으며, 이 경우 모델 파일은 공유한다(MUST).

## 사진과 시각 처리

- 사진 접근이 허용되어 있으면 그 하루의 사진은 반드시 시각 처리를 거친다(MUST). 끄는 경로를 두지 않는다(MUST NOT).
- 볼 사진이 없거나 접근 권한이 없으면 시각 엔진을 열지 않는다(MUST NOT).
- 시각 처리 깊이는 하나로 고정한다(MUST). 사용자에게 엔지니어링 깊이 선택지를 주지 않는다(MUST NOT).

## 개발 방식

- 계약을 먼저 정하고 테스트를 먼저 쓴다(MUST).
- 커밋 메시지는 한국어로 쓴다(MUST).
- `main` 브랜치에 직접 작업하지 않고 기능 브랜치와 PR을 통해 머지한다(MUST).

## Governance

- 이 헌법은 다른 모든 관행보다 우선한다.
- 원칙을 어기려면 헌법을 먼저 고친다. 예외를 코드에 몰래 두지 않는다(MUST NOT).
- 개정할 때는 무엇이 왜 바뀌었는지 명확히 기록한다(MUST).
