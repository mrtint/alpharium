## 결정한 접근 — 절대 배치 겹 + reanimated (저장소 소유자 채택)

새 내비게이션 의존성 없이 `AppFrame`이 홈을 늘 그리고 그 위에 설정 판을 겹친다.

```
SafeAreaView (AppFrame)
├─ DiarySection           ← 늘 마운트. covered=true면 뒤로 가기 가로채기를 끄고 접근성 트리에서 숨긴다
└─ SettingsLayer          ← absolute fill, translateX 화면 폭 → 0 (push), 닫을 때 0 → 화면 폭
     ├─ 고정 머리: 「‹ 일기」(44 최소 높이) · 「설정」 44/800 · 아래 2px text 선
     └─ 회색 지면 ScrollView(neutral-100): 묶음 머리 + 행
PortalHost                ← 루트 그대로(대화상자는 모든 겹 위)
```

**버린 대안**: react-navigation native stack(`react-native-screens` — 050 DEP1이 막은 네이티브 의존성), RN `Modal`(안드로이드
`slide`는 아래에서 올라오고, 루트 `PortalHost`의 대화상자가 Modal 창 아래에 깔린다 — §3.2 대화상자와 충돌).

### 화면 상태

- `route`는 `"home" | "settings" | "developer"` 그대로 두되, **`"home"`이 아닐 때도 `DiarySection`을 언마운트하지 않는다.**
  설정 판은 `route === "settings"`일 때 열리고, 닫는 애니메이션이 끝난 뒤 언마운트된다(열림 판정과 마운트 판정을 가른다).
- 개발자 화면도 같은 겹 구조를 쓴다(그 진입점은 §3.5 몫 — 지금은 닿을 길이 없다). 하위 화면 껍데기는 `SubScreenFrame`을
  `6c` 머리 모양으로 갈아 끼운 하나를 둘이 같이 쓴다.
- `key={diary-${autoGeneratedToken}}` 재마운트(040)는 그대로다 — 설정 왕복과 무관하다.

### 홈이 겹쳐진 동안 (위험의 핵심)

1. **뒤로 가기**: `DiaryHomeScreen`은 쓰는 중이면 `hardwareBackPress`를 가로채 **쓰기를 멈춘다**(054). 안드로이드 `BackHandler`는
   **나중에 등록한 것부터** 부르므로 설정이 열린 뒤 홈의 effect가 다시 돌면(콜백 identity 변화) 홈 핸들러가 위로 올라와
   설정의 뒤로 가기가 **쓰기를 그만두게 한다** — 조용한 결함이다. 그래서 홈에 `covered` prop을 넘기고, `covered`이면
   홈의 뒤로 가기 effect 둘(쓰는 중·실패 화면)이 아예 등록하지 않는다. 등록 순서에 기대지 않는다.
2. **접근성 트리**: 홈 래퍼에 `importantForAccessibility="no-hide-descendants"` + `accessibilityElementsHidden`.
   jest 기본 쿼리에서도 빠지므로 「설정이 열리면 홈 요소가 접근성에서 숨는다」를 RNTL로 잠글 수 있다.
3. **누름**: 설정 판이 불투명 전면이라 홈에 닿지 않는다. 닫는 애니메이션 중에도 판이 덮고 있다.
4. **홈의 타이머·애니메이션**: 멈추지 않는다 — 쓰는 중의 혼잣말 회전·자정 타이머가 뒤에서 그대로 돈다(쓰기가 멈추지
   않아야 하므로 그것이 맞다). 비용은 화면 밖 리렌더뿐이다.
5. **쓰는 중에 바꾼 이름**은 다음 일기부터다 — 파이프라인은 시작할 때 이름을 받으므로 지금 구조가 이미 그렇다(계약으로 잠근다).

### 설정 내용 (`6c` — 이 조각의 부분)

| 묶음 | 행 | 동작 |
| --- | --- | --- |
| 캐릭터 | 이름 — 값: 지금 이름 › | 이름 바꾸기 (목적지·저장 버튼 규칙은 clarify 4) |
| 일기 | 자동으로 쓰기 — 토글 | 지금의 `applyToggleOn/Off`(S6 순서) 그대로. 시각 목록·장소명은 그 아래에 지금 모양 |
| 권한 · 휴대폰 설정으로 이동 | 사진·위치·알림 — 꼬리표 / 배터리 — 보조 문구 › | 네 행 모두 앱 정보 화면(`openAppSettings`). 복귀(`AppState active`) 시 다시 읽는다 |
| 정보 | 버전 — 「1.0.0 (9)」 꼴 | 읽기만 (7번 탭은 §3.5) |

- **사진 꼬리표**: 사진 읽기 + 사진의 위치 정보. 「허용됨」 = 사진 `granted`이고 위치 정보도 읽힘 / 「일부 허용」 = 부분 사진
  허용(`limited`·`describePhotoAccessLimit` `"partial"`) 또는 위치 정보만 없음 / 「허용 안 함」 = 사진 읽기 없음. 위치 정보는
  조회 API가 없어 `getLocation()`을 실제로 불러 봐야 안다(AGENTS) — 판정은 순수 함수(`src/app/` 쪽)로 두고 재료만 통로에서
  모은다. 사진이 0장이라 위치 정보를 볼 사진이 없으면 「모름」이 아니라 사진 읽기만으로 판정한다(plan에서 확정).
- **위치·알림 꼬리표**: `granted` → 허용됨, `denied`/`blocked` → 허용 안 함, `undetermined` → 허용 안 함(아직 안 물었어도
  지금 쓸 수 없다 — clarify에서 확인). 읽기 실패(`unknown`)는 꼬리표를 그리지 않는다(원칙 V — 모름을 거부로 채우지 않는다).
- **배터리**: 값 없이 보조 문구 「배터리 사용 · 제한 없음으로 두면 제때 써요」와 › 만. 목적지는 보드대로 앱 정보 화면이다
  (024의 「배터리 사용 관리」 목록 인텐트에서 바뀐다 — One UI 앱 정보 → 배터리 → 제한 없음 경로는 024 실측).
- **걷는 것**: `AuthorPicker`(작성자 고르기 — 로스터 하나), `CharacterListScreen`(`ModelSection` — 캐릭터·VLM 받기/지우기),
  `PermissionsSection`(설명 카드형 권한 섹션·「온보딩 다시 하기」), `AutoDiarySettingsScreen`의 배터리 링크. 대체 경로는 §3.5다.
  `ModelSection`이 쓰던 `acquisition`·`progress`·`rejection` 상태가 `AppFrame`에 남는지(다른 소비자가 있는지)는 plan에서 센다.
- **문구**: `6c` KO 원문(분해 설계 §3.1 문구표)을 계약 테스트로 글자 단위 잠금(C4). 해요체.
