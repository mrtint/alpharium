## 용어

- **층 1 / 기준 상태 / 전용 테스트 기기**: 069의 용어 그대로. 층 1은 일기를 쓰지 않고 끝나는 화면 흐름이다.
- **층 2**: 실제 모델로 일기를 쓰는 스모크. 상태 전이(쓰는 중 → 쓴 날 홈)까지만 자동으로 단언하고 본문은 사람이 읽는다.
- **낡은 흐름**: `FLOWS`에 등록돼 있으나 현재 화면과 맞지 않아 실패하는 흐름. 여기서는 `skeleton`·`prompt-preview`·`today-diary`.
- **릴리스 전 체크리스트**: 릴리스(Play 내부 테스트·TestFlight) 전에 사람이 따라 하는 확인 문서.

## User Scenarios & Testing _(mandatory)_

사용자는 이 저장소의 소유자(개발자)다.

### User Story 1 - 일반 실행이 거짓 실패 없이 돈다 (Priority: P1)

소유자가 `npm run test:device`를 돌리면 낡은 흐름 셋 때문에 항상 실패하던 것이 사라진다. 각 흐름은 현재 화면에 맞게 고쳐지거나, 다른 흐름이 같은 것을 이미 보면 근거와 함께 지워진다.

**Why this priority**: 항상 빨간불인 실행은 진짜 회귀를 가린다. 층 2를 더하기 전에 바닥을 깨끗이 한다.

**Independent Test**: 실기기에서 낡은 흐름 셋을 각각 돌려 결과를 본다(고친 것은 통과, 지운 것은 파일이 없고 사유가 남아 있다). 고친 흐름의 단언 하나를 틀리게 하면 실패하는지 본다(위반 주입).

**Acceptance Scenarios**:

1. **Given** `skeleton`, **When** 실기기에서 돌리면, **Then** 진단 화면의 현재 문구로 「온디바이스 추론 모듈이 붙었다」와 「저장이 돈다」를 단언하고 통과한다(다른 흐름이 같은 것을 보지 않는 한).
2. **Given** `prompt-preview`, **When** 돌리면, **Then** 프롬프트 문안이 바뀌어도 깨지지 않는다 — 문안 글자가 아니라 구조(프리셋 둘·근사 크기 라벨)만 단언한다.
3. **Given** `today-diary`, **When** 실패 원인이 문구 탓인지 기준 상태 탓인지 가린 뒤, **Then** 고치거나, `dialog-foundation` 등 다른 흐름이 같은 것을 보면 지운다. 어느 쪽이든 근거가 `FLOWS` 주석과 대응표에 남는다.
4. **Given** 낡은 흐름이 고쳐지거나 지워진 뒤, **When** 일반 실행을 하면, **Then** 이 셋 때문에 실패하지 않는다.

---

### User Story 2 - 층 2 한 번으로 실제 생성 경로를 릴리스 전에 확인한다 (Priority: P1)

소유자가 전용 테스트 기기에서 `npm run test:layer2`를 돌리면, 모델과 설정이 보존된 기준 상태에서 실제 모델로 일기를 쓰는 흐름 넷이 상태 전이까지 자동으로 확인된다. 끝나면 방금 저장된 일기 본문의 위치가 출력되어 소유자가 읽는다.

**Why this priority**: 이 앱의 핵심은 온디바이스 생성이다. 층 1은 생성을 일부러 피하므로 생성 경로는 지금 사람이 손으로만 본다. 042의 교훈(검증 경로가 제품과 다르면 검증이 아니다)대로 가짜 추론은 쓰지 않는다.

**Independent Test**: 전용 기기에서 층 2를 돌려 흐름 넷이 모두 통과하고 일기 본문 경로가 출력되는지 본다. 완료 표식을 일부러 틀리게 하면 실패하는지 본다.

**Acceptance Scenarios**:

1. **Given** 기준 상태(모델 있음·온보딩 완료·자동 쓰기 꺼짐), **When** 쓰기 흐름을 돌리면, **Then** 쓰는 중이 보이고 끝나면 쓴 날 홈(제목·「다시 쓰기」)이 보인다.
2. **Given** 자동 쓰기가 켜져 있고 어제의 재료가 있는 상태, **When** 앱을 열면, **Then** 쓰는 중을 거쳐 쓴 날로 끝난다(057).
3. **Given** 개발 환경의 진단 화면, **When** 「한 번 써 보기」를 누르면, **Then** 홈이 쓰는 중이 되고 쓴 날로 끝난다(060).
4. **Given** 모델이 있고 온보딩 플래그만 되돌린 상태, **When** 앱을 열면, **Then** 로고부터 작명·자동 첫 일기까지 가서 쓴 날 홈에 닿는다(040).
5. **Given** 층 2가 끝난 뒤, **When** 출력을 보면, **Then** 방금 저장된 일기 파일의 위치(또는 사본 경로)가 있어 본문을 읽을 수 있다. 본문은 자동으로 채점하지 않는다.
6. **Given** 모델이 없는 기기, **When** 층 2를 시작하면, **Then** 통과가 아니라 이유가 붙은 중단이다.
7. **Given** 기기가 없거나 Maestro가 없음, **When** 층 2를 시작하면, **Then** 건너뜀으로 보고되고 통과가 아니다.

---

### User Story 3 - 릴리스 전 체크리스트에서 층 2를 부른다 (Priority: P2)

소유자가 Play 내부 테스트나 TestFlight에 올리기 전에 `docs/e2e/layer2-release-checklist.md`를 열면, 층 2를 돌리고 본문을 읽고 사람이 보는 항목까지 한 번에 적혀 있다. AGENTS.md의 배포 절이 그 문서를 가리킨다.

**Why this priority**: 층 2는 자주 돌리는 게 아니라 릴리스 전 의식이다. 문서가 없으면 아무도 안 돌린다.

**Independent Test**: 체크리스트 문서가 있고, 배포 절에서 링크되며, 층 2 명령·사람이 보는 항목이 문서 안에 있다.

**Acceptance Scenarios**:

1. **Given** AGENTS.md의 release·iOS 절, **When** 읽으면, **Then** 체크리스트 문서로의 링크가 있다.
2. **Given** 체크리스트, **When** 읽으면, **Then** 층 2 실행·본문 읽기·대응표의 「사람이 봄」 항목을 따라 할 수 있다.

---

### User Story 4 - 대응표가 층 2와 정리 결과를 반영한다 (Priority: P2)

대응표(`docs/e2e/feature-flow-map.md`)의 모든 주요 기능에 층 1 또는 층 2 흐름이 있거나 「사람이 봄」이 이유와 함께 적혀 있고, 낡은 흐름 항목이 현재 상태로 고쳐져 있다. 표가 어긋나면 기존 계약 테스트가 실패한다.

**Why this priority**: 로드맵 완료 조건이다. 069가 만든 정합 테스트가 층 2까지 덮어야 새 흐름이 조용히 빠지지 않는다.

**Independent Test**: 대응표와 흐름 파일·`FLOWS`·층 목록을 대조하는 테스트가 통과하고, 층 2 흐름 하나를 목록에서 빼면 실패한다.

**Acceptance Scenarios**:

1. **Given** 대응표 기능 표, **When** 「층 2」 열을 보면, **Then** 범위 밖 표시가 사라지고 해당 기능마다 층 2 흐름 또는 「사람이 봄」 이유가 있다.
2. **Given** 인벤토리, **When** 낡은 흐름 셋을 찾으면, **Then** 고쳤으면 통과 상태로, 지웠으면 사유와 함께 제거된 상태로 반영돼 있다.
3. **Given** 층 2 흐름, **When** `FLOWS`에 등록되지 않았으면, **Then** 계약 테스트가 실패한다.

---

### Edge Cases

- 층 2 흐름은 모델 추론이 길다(쓰기 1~4분). 완료 대기 한도를 넘기면 실패이고, 끝없이 기다리지 않는다.
- 생성이 판정에서 거부돼 일기가 저장되지 않으면 쓴 날 홈에 닿지 못해 흐름이 실패한다 — 그것이 옳다(실패를 통과로 숨기지 않는다). 원인은 쓰기 실패 기록(060)과 로그로 본다.
- 층 2의 일부 흐름은 설정(자동 쓰기·온보딩 플래그)을 바꾼다 — 실행기가 흐름 사이마다 기준 상태를 다시 만든다(FR-010).
- 첫 실행 자동 첫 일기는 모델 내려받기를 포함하지 않는다(모델은 이미 있다) — 내려받기·동의 화면은 층 2 대상이 아니다.
- 층 2는 같은 날 일기를 덮어쓴다 — 전용 기기에서만 돈다.
- 층 1 실행기의 기준 상태 단계를 층 2가 재사용하되 일기 픽스처는 흐름이 요구하는 것과 다를 수 있다(오늘 일기 없음).
- 앱 열면 쓰는 중(057)은 어제 재료(사진)가 있어야 한다 — 070 표본(1~30일 전)이 필요하며 없으면 표본 보장이 먼저 심는다.
- Maestro를 끊은 직후 곧바로 다시 돌리면 기기 서버가 죽을 수 있다(AGENTS) — 흐름마다 따로 부르므로 `DeviceServerDiedException` 때 한 번 다시 시도한다.
- 낡은 흐름이 실패한 원인이 앱 결함일 수 있다(문구 변경이 아니라 화면이 깨짐) — 그러면 흐름을 고치지 않고 결함으로 보고한다.

## Requirements _(mandatory)_

### Functional Requirements

**낡은 흐름 정리**

- **FR-001**: 낡은 흐름 셋(`skeleton`·`prompt-preview`·`today-diary`)마다 실기기에서 실패 원인을 가려야 한다(MUST): 문구·문안 변경 / 기준 상태 / 앱 결함.
- **FR-002**: 각 흐름은 고치거나 지워야 하고(MUST), 어느 쪽이든 근거를 `FLOWS` 위 주석과 대응표에 남겨야 한다(MUST). 지키는 것이 다른 흐름과 겹치면 지우고, 유일하면 고친다.
- **FR-003**: 고친 `prompt-preview`는 프롬프트 문안 글자를 단언하지 않아야 한다(MUST NOT) — 구조(프리셋 둘·근사 크기 라벨·「실측 토큰 아님」 라벨)만 본다.
- **FR-004**: 원인이 앱 결함으로 가려지면 흐름을 맞추지 않고 결함으로 보고해야 한다(MUST).
- **FR-005**: 정리 뒤 일반 실행의 `FLOWS`에는 이 셋 때문에 실패하는 흐름이 없어야 한다(MUST). 단 FR-004로 앱 결함이 판정돼 소유자에게 보고된 흐름은 예외이고, 그 사실(흐름 이름·결함·보고)을 `FLOWS` 주석과 대응표에 적는다(MUST).

**층 2 실행기**

- **FR-006**: `npm run test:layer2`(= 실행기 `--layer2`)가 있어야 한다(MUST). 층 1 실행기의 기준 상태 단계(설정 파일 되돌리기·모델 존재 점검)를 재사용하고 `pm clear`·재설치는 하지 않는다(MUST NOT).
- **FR-007**: 층 2는 전용 테스트 기기에서만 돌고, 시작할 때 이 기기의 일기를 지운다는 안내를 출력해야 한다(MUST). 확인 질문은 없다.
- **FR-008**: 모델이 없으면 통과가 아니라 이유가 붙은 중단이어야 하고(MUST), 기기·Maestro가 없으면 건너뜀으로 보고해야 한다(MUST). 건너뜀·중단은 통과가 아니다(원칙 V).
- **FR-009**: 층 2의 일기 픽스처는 흐름이 요구하는 만큼(오늘 일기 없음, 지난 날 일부 있음)만 두어야 하고(MUST), 사진은 070 표본을 전제로 하며 표본 보장이 먼저 돈다(MUST).
- **FR-010**: 층 2 실행기는 흐름마다 `maestro test`를 따로 부르고(MUST), 호출 사이마다 기준 상태(설정 파일·일기 픽스처)를 다시 만들어야 한다(MUST) — 앞 흐름이 만든 일기가 뒤 흐름의 전제를 바꾸지 않게 한다. 한 흐름이 실패해도 다음 흐름으로 가고, 끝에 흐름별 결과를 모아 보고한다. (층 1의 한 번 실행과 다르다: 흐름당 Maestro 기동 약 35초는 흐름 하나가 1~4분인 층 2에서 감수한다.)
- **FR-011**: 실행기는 기기 접근을 주입받아 기기 없이 조립을 테스트할 수 있어야 한다(MUST).

**층 2 흐름**

- **FR-012**: 흐름 넷을 둔다(MUST): (1) 쓰기 → 저장 → 쓴 날 홈, (2) 앱을 열면 쓰는 중(057), (3) 진단 「한 번 써 보기」(060), (4) 첫 실행 자동 첫 일기(040, 모델 있음·온보딩 플래그만 되돌림).
- **FR-013**: 흐름의 단언은 상태 전이까지여야 한다(MUST): 쓰는 중 표식이 서고, 끝나면 사라지며, 쓴 날 홈의 표식(제목·「다시 쓰기」)이 보인다. 일기 본문 내용을 단언하지 않아야 한다(MUST NOT, 원칙 IV). 예외: 첫 실행 자동 첫 일기 흐름은 홈의 제자리 쓰기를 거치지 않아(040 `triggerFirstRunAutoDiary`) 쓰는 중 표식이 서지 않는다 — 홈에 닿은 뒤 쓴 날 지면(`written-paper`)이 서는 것으로 상태 전이를 본다(2026-10-10 실기기 확인).
- **FR-014**: 완료 대기는 쓰는 중 표식의 소멸로 하고 한도를 둔다(MUST) — 한도 안에 쓴 날 홈에 닿지 못하면 실패다.
- **FR-015**: 가짜 추론·가짜 생성기를 쓰지 않아야 한다(MUST NOT). 층 2는 실제 모델로 돈다.

- **FR-017**: 층 2 흐름은 `FLOWS`에 등록해야 하고(MUST), 층 2 목록을 따로 가지며, 층 1 기준 상태를 전제로 일반 실행(`pm clear` 뒤)에서는 돌지 않아야 한다(MUST).

**검증**

- **FR-022**: 위반 주입을 해야 한다(MUST): (1) 층 2 흐름의 완료 표식을 틀리게 → 흐름 실패, (2) 층 2 흐름을 `FLOWS`에서 빼기 → 계약 테스트 실패, (3) 고친 흐름의 단언 하나를 틀리게 → 실패. 치환이 실제로 적용됐는지 먼저 단언한다.

### Key Entities

- **낡은 흐름 판정**: 흐름 하나에 대한 (원인 갈래, 고침/삭제, 근거). 대응표와 `FLOWS` 주석에 남는다.
- **층 2 흐름 목록**: 층 2로 도는 흐름 파일 집합. `FLOWS`의 부분집합이고 층 1 목록과 겹치지 않는다.
- **층 2 기준 상태**: 층 1 기준 상태에서 일기 픽스처만 다른 상태(오늘 일기 없음).
- **저장된 일기 수집물**: 실행 끝에 개발 기계로 가져온 일기 파일. 사람이 읽는 용도.

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 일반 실행(`npm run test:device`)에서 낡은 흐름 셋 때문에 실패하는 흐름이 0개다.
- **SC-002**: 층 2 네 흐름이 전용 안드로이드 dev 실기기에서 모델이 보존된 채 한 번 통과한다.
- **SC-003**: 층 2 흐름의 완료 표식을 틀리게 하면 실패하고, `FLOWS` 등록을 빼면 계약 테스트가 실패한다.
- **SC-004**: 대응표의 모든 주요 기능 행에 층 1 흐름 또는 층 2 흐름 또는 「사람이 봄」+이유가 있다(빈 칸 0).
- **SC-005**: 층 2가 끝난 뒤 저장된 일기 파일의 위치가 출력되어, 소유자가 추가 조작 없이 본문을 읽을 수 있다.
- **SC-006**: 모델이 없는 기기·기기 없음·Maestro 없음에서 층 2가 통과로 보고되지 않는다.
- **SC-007**: 체크리스트가 AGENTS.md 배포 절에서 링크되고, 따라 하면 층 2 실행과 본문 읽기까지 닿는다.

## Assumptions

- 층 2는 전용 테스트 기기(069)에서만 돌고, 기기에는 dev 빌드·모델·사진/위치 권한·070 표본이 있다. 실기기는 SM-G986N(Android 13).
- 생성 시간은 쓰기 1회에 약 1~4분이며(AGENTS) 완료 대기 한도는 그보다 넉넉하게 정한다(구체 값은 계획에서 정한다).
- 일반 실행(`npm run test:device`)은 먼저 `pm clear`를 해 모델을 지우므로 이 전용 기기에서는 돌리지 않는다. SC-001·시나리오 4의 「일반 실행에서 실패 없음」은 낡은 흐름 셋을 층 1 기준 상태(`npm run test:layer1 -- <흐름>`)에서 개별 실행해 통과를 보고, `FLOWS` 정합 테스트로 등록 상태를 잠가 확인한다.
- 낡은 흐름의 실패 원인은 069 실측 메시지에서 문구·문안 변경으로 보이나 확정은 구현 때 실기기에서 한다.
- 쓰기 중 표식(`stop-button`)과 쓴 날 홈 표식의 testID는 이미 앱에 있다(`in-place-writing`·`generate-diary`가 쓴다).
- 일기 품질을 결론짓지 않는다 — 얻는 것은 「경로가 도는가」다(원칙 V).
- 범위 밖: iOS 시뮬레이터, CI 판단, 071 후속, 모델 내려받기 e2e, 본문 자동 채점.
