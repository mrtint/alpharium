# Quickstart: 사진의 내용을 보고 일기의 재료로 준다

**Feature**: `011-photo-vision-summary` | **Date**: 2026-08-22

**기기 없이 도는 검증이 전부 초록불이어도 이 기능은 끝나지 않는다**(SC-016, 헌법 원칙 V).

시각 처리는 그 위험이 특히 크다 — **사진을 안 보고도 일기는 나온다.**
「일기가 나왔다」가 「사진을 봤다」의 증거가 아니므로, **D2가 「보지 않음」과 견주는 것**이
이 문서의 핵심이다.

---

## 기기 없이 (항상 돈다)

```bash
npm test          # 기기 불필요 갈래
npm run lint      # eslint + tsc + 헌법 검사
```

**⚠️ `npm test`만으로는 부족한 것이 있다** — 007이 배웠다. 타입은 지워지므로
`VisionRunResult`에 `elapsedMs`를 넣어도 jest가 통과한다. 그래서 계약 테스트가
**선언을 `readFileSync`로 직접 읽는다**(vision-engine.md V1). 그래도 `npm run lint`를
함께 돌린다.

## 실기기 준비

### 1. 사진이 있는 하루를 심는다 (010의 도구)

**이것이 없으면 이 기능을 검증할 수 없다.** 테스트 기기는 책상에 있어서 볼 것이 없다.

```bash
npm run seed:day -- rich 2026-08-21     # 서로 다른 장면 여러 장
npm run seed:list                        # 확인
```

**⚠️ 심은 것과 진짜 사진이 섞인다**(010 FR-017). 앱은 구분하지 않으며 구분해서도 안
된다 — 그날 사람이 찍은 사진이 있으면 그것도 세어진다. **검증할 때 셈에 넣는다.**

**⚠️ 010의 `rich` 모양이 사진 몇 장인지 확인하고 시작한다.** 5장을 넘어야 균일 선택
(D5)을 볼 수 있다.

### 2. 기기·Metro 준비 (기존 절차 그대로)

```bash
adb reverse tcp:8081 tcp:8081            # ⚠️ USB에서도 필요하다
EXPO_PUBLIC_APP_ENV=dev npx expo start --dev-client
```

- 기기 잠금이 풀려 있어야 한다 (`adb shell dumpsys trust`의 `deviceLocked=0`)
- Metro가 번들을 안 내주면 `npx expo start --clear`
- **Metro는 gradle 빌드가 끝난 뒤에 띄운다**(009 실측 — 파일 감시자가 죽는다)

## D1. 사진 보는 모델을 받고 5장이 몇 초인지 잰다

**research §6의 10초가 옆 저장소 값이고 여기서 재지 않았다**(원칙 V).

1. 준비 자리에서 사진 보는 모델을 받는다 — **본체와 mmproj 둘 다**
2. 「사진 1장」 이상인 하루를 골라 「빠르게 봄」으로 일기를 쓴다
3. 시작부터 일기가 뜰 때까지를 **손목시계나 스크린 레코딩으로** 잰다

| 통과 | 근거 |
| --- | --- |
| 모델이 받아지고 md5 검증을 지난다 | FR-031 |
| **준비 상태가 하나의 값으로 보인다** — 파일 둘인 것이 드러나지 않는다 | FR-026, SC-008 |
| 걸린 시간을 기록한다 | 원칙 V — **재는 것과 앱에 담는 것은 다르다** |

**⚠️ 시간을 앱에 표시하게 만들지 않는다**(FR-032, SC-013). 사람이 밖에서 재는 것이다.

**★ md5를 채록한다** — 003이 그랬듯 첫 내려받기에서 얻은 지문을 `src/vision/roster.ts`에
옮겨 적는다. **그전까지 그 자리는 비어 있는 것이 옳다.**

## D2. ★ 사진을 실제로 보았는지 확인한다 (SC-001) — **이 기능의 핵심 검증**

**같은 하루를 두 번 쓴다.**

1. 사진 설정 「보지 않음」 → 일기 생성 → **전문을 기록**
2. 사진 설정 「빠르게 봄」 → 같은 하루 → 일기 생성 → **전문을 기록**
3. 둘을 나란히 놓고 읽는다

| 통과 | 실패로 읽어야 하는 것 |
| --- | --- |
| 2번 일기에 **사진에 실제로 담긴 것**이 나온다 | 둘이 사실상 같다 → **사진을 안 본 것이다** |
| 심은 사진의 장면과 일기의 서술이 맞는다 | 일기가 사진과 무관한 것을 말한다 → 캡션이 안 닿았다 |

**⚠️ 「일기가 나왔다」로 통과시키지 않는다.** 006의 `GenerationProbe`, 007의 끊긴 `stop`
배선, 009의 `day:` 한 줄이 전부 **오류 없이 아무 일도 안 일어난** 실패였다.
**이 기능의 같은 실패는 「캡션이 프롬프트에 안 들어갔는데 일기는 멀쩡히 나오는 것」이다.**

## D3. ⚠️ VLM을 닫고 캐릭터 모델을 여는 것이 되는가 (research §2 — 미관측)

**옆 저장소가 확인하지 못한 자리다** (캡션은 원격 서버, 일기는 폰이었다).

D2의 2번이 끝까지 갔으면 **이미 통과한 것이다.** 다만 다음을 함께 본다:

| 통과 | 실패 신호 |
| --- | --- |
| 캡션 뒤 캐릭터 모델이 열린다 | 「생성 실패」·앱 강제 종료 → **메모리 단편화** |
| 두 번 연속 생성해도 된다 | 두 번째가 죽는다 → `unload()`가 안 불렸다(E2) |
| `narrative`(2.4B, 가장 큼)로도 된다 | 큰 모델에서만 죽는다 → 메모리 여유가 없다 |

**`narrative`로 반드시 한 번 해 본다** — 007 실측에서 콜드 242초가 걸린 가장 무거운
캐릭터이며, **여기서 죽으면 E1 순서를 다시 봐야 한다.**

## D4. 사진이 없는 하루 / 권한이 없는 하루 (FR-003, SC-006)

| 상황 | 만드는 법 | 통과 |
| --- | --- | --- |
| 사진 0장 | 010으로 `empty` 심기, 또는 사진 없는 하루 고르기 | 「사진: 없었다」. **캡션 단계를 돌지 않는다**(빠르다) |
| 권한 없음 | `adb shell pm revoke <패키지> android.permission.READ_MEDIA_IMAGES` | 「사진: 모른다」. 캡션을 시도하지 않는다 |
| 「보지 않음」 | 설정을 바꾼다 | **005~010과 똑같이 동작한다**(SC-002) |

**★ 권한을 거둔 뒤 되돌리는 것을 잊지 않는다** — 004·007이 같은 절차를 썼다.

## D5. ★ 균일 선택을 눈으로 확인한다 (FR-007a, SC-007a)

**5장을 넘는 하루가 필요하다.**

1. 010으로 **아침부터 저녁까지 흩어진** 사진 8~12장을 심는다
2. 「빠르게 봄」으로 일기를 쓴다
3. 일기에 언급된 장면의 **시각 분포**를 본다

| 통과 | 실패 |
| --- | --- |
| 아침 것과 저녁 것이 **둘 다** 나온다 | 전부 아침이다 → **004의 `slice`를 그대로 쓴 것** |
| 「사진이 더 있었으나 다섯 장만 보았다」가 반영된다 | 일기가 「사진 열 장을 찍은 하루」라고 단언 |

**이것이 사용자가 clarify에서 바로잡은 자리다.** 앞에서부터 잘랐다면 여기서 드러난다.

## D6. 「빠르게 봄」과 「자세히 봄」이 다른가 (SC-015)

**research §4의 256/1024가 짐작이다.**

1. 같은 하루·같은 캐릭터로 두 설정을 각각 돌린다
2. 캡션에서 온 서술의 **세밀함**을 견준다

| 결과 | 다음 행동 |
| --- | --- |
| 눈에 띄게 다르다 | 값이 맞다. 기록한다 |
| 거의 같다 | **값을 벌린다**(예: 128 / 2048) 후 다시 |
| 「자세히」가 훨씬 느려 못 쓰겠다 | 값을 좁히거나 사용자 고지를 강화(FR-020) |

**⚠️ 「어느 쪽이 더 좋은가」를 판정하지 않는다**(원칙 IV). 보는 것은 **다른가**이지
낫는가가 아니다.

## D7. ⚠️ 캡션 언어를 확인한다 (research §7 — 미결)

**옆 저장소 캡션이 전부 영어였고**, gemma3·qwen3가 **영어 어휘를 그대로 옮기는**
것(`Snowfall`, `smelled했다`)이 관측됐다.

1. 한국어 캐릭터(`quiet`)로 D2를 돌린다
2. 일기에 **영어 단어가 섞여 있는지** 본다

| 결과 | 다음 행동 |
| --- | --- |
| 자연스러운 한국어 | 지금 설계가 맞다. 기록한다 |
| 영어가 섞인다 | 캡션을 한국어로 뽑을지 정한다 — **여기서 실제로 보고 정한다** |

**지금 정하면 짐작이다.** spec의 FR-013은 어느 쪽이든 지켜진다.

## D8. 그만두기와 원칙 IV의 화면 검사

| 무엇 | 통과 |
| --- | --- |
| 캡션 도중 「그만두기」 | 목록으로 돌아가고 **저장된 일기가 그대로다**(FR-009) |
| 그만둔 하루가 목록에 안 생긴다 | 007의 검증과 같다 |
| 생성 중 화면 | **백분율·초·「사진 3/5」·캡션 본문이 하나도 없다**(SC-012, FR-034) |
| 준비 자리 | **모델명·파일명·크기가 없다**(SC-004, FR-031a) |

**⚠️ 그만두기는 캡션 단계가 길어 007보다 잡기 쉽다** — 007은 2.4초라 900ms 안에 눌러야
했는데, 여기는 캡션에만 약 10초가 걸린다.

**⚠️ Maestro의 조건부 블록이 SKIPPED로 지나가면 통과가 아니다**(원칙 V). 007·009가
같은 함정을 겪었고, 건너뛴 것은 **손으로 확인해 기록한다.**

## release 빌드에서도 확인한다

**debug에서 돌았다는 것은 release에서 돈다는 뜻이 아니다**(원칙 V).

```bash
npx expo prebuild --platform android --clean
cp ~/.alpharium-signing/alpharium.jks android/app/     # ★ prebuild가 지웠다
cd android && NODE_ENV=production ./gradlew assembleRelease
```

| 무엇 | 왜 이 기능에서 위험한가 |
| --- | --- |
| **`initMultimodal`의 JNI 심볼** | R8·ProGuard가 지울 수 있다. 005가 `initLlama`에서 통과했으나 **멀티모달 심볼은 처음이다** |
| 동적 `import` | `visionPort`가 새로 생긴다 |
| 서명 | `apksigner verify --print-certs` → **`CN=alpharium`** |
| Metro 없이 뜬다 | Metro 끄고 `adb reverse` 지운 채 |

**⚠️ release는 `run-as`가 안 된다** — 기기 안 파일을 못 보므로 **앱 화면으로 확인한다.**

**⚠️ release에는 진단 패널이 없어 UI 좌표가 다르다**(008 실측).
