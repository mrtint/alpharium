# 받는 도중에 끊기거나 죽어도 끝난 구간은 다시 받지 않는다 — 설계

## 목적
필수 모듈(~2GB)을 받다가 네트워크가 끊기거나 앱이 죽어도, 다시 열면 **끝난 구간은 받지 않고 이어 받는다.** 지금은 `Acquisition.pause()`를 부르는 곳이 없어 재개 기록이 실제로 생기지 않고, 구간 4개가 거의 함께 끝나 끝난 구간만 기록해도 건질 것이 적다. 받던 구간의 임시 파일(`.seg<i>`)은 `fetchRange`의 `finally`에서 지워져 구간 안 이어받기도 못 한다.

## 수용 기준
1. 받는 도중 앱을 죽이거나 비행기 모드로 끊은 뒤 다시 열면, 이미 끝난 구간은 받지 않고 남은 구간만 받는다(iPhone 확인).
2. 이어 받아 끝난 파일의 지문(MD5)이 로스터와 맞는다.
3. 재개 기록이 실제 파일과 어긋나면(`.bin` 없음·크기 부족) 기록을 버리고 처음부터 받는다.
4. 화면으로는 `fraction` 하나만 나간다(원칙 III·IV). 구간 수·구간별 바이트는 나가지 않는다.

## 접근
구간을 **16개**로 나누고 **동시에 4개**씩 받는다(둘 다 사람이 정한 상수, 원칙 V). 한 구간이 끝나 최종 파일에 옮겨 붙이면 그 인덱스를 즉시 `state.json`에 남긴다. 받던 도중의 구간은 버리고 처음부터 다시 받는다(구간 안 이어받기는 임시 파일 바이트를 믿을 근거가 없어 하지 않는다).

## 설계
- **plan.ts**: `SEGMENT_COUNT = 16`, `SEGMENT_CONCURRENCY = 4`. 재개 기록 `SegmentedResume`은 `receivedBytes[]` 대신 완료 구간 인덱스 목록(`doneIndices`)을 가진다. `remainingSegments`는 완료 인덱스를 제외한다. 진행 합산은 완료 구간의 바이트를 미리 채운다.
- **transfer.ts**: 남은 구간을 고정 크기 풀(동시 4)로 돌린다. 구간 완료마다 `onSegmentDone(index)`. 한 구간이 실패하면 나머지를 취소한다. 사용자 멈춤은 기존대로 `paused`(완료 인덱스는 이미 기록됨).
- **기록(acquisition·storage·port)**: 구간 완료 콜백이 `DownloadPort`를 통해 `acquisition`으로 올라와 `state.json`에 반영된다. 읽고 쓰기는 직렬화해 동시에 끝난 구간이 서로 덮어쓰지 않게 한다. 옛 형식(`receivedBytes`)은 쓰인 적 없는 기록이라 읽으면 버리고 처음부터 받는다.
- **재개 검증**: 이어받기 전에 `.bin`이 있고 크기가 `totalBytes`에 닿는지(구간 쓰기는 오프셋에 쓰므로 가장 뒤 구간이 끝났으면 크기가 닿는다) 등 기록과 파일이 맞는지 본다. 어긋나면 기록을 버리고 처음부터. 110의 `settleExistingFile`은 재개 기록이 있으면 검증 없이 `download`로 보내므로 그대로 쓴다.
- **유지**: `Acquisition.pause()`와 단일 스트림 폴백의 `paused`는 건드리지 않는다.
- **정리**: `leftoverNamesFor`의 `MAX_TRACKED_SEGMENTS`(16)가 구간 수 16을 덮는지 확인한다.

## 결정
| 결정 | 근거 | 뒤집으면 |
|---|---|---|
| 구간 안 이어받기 안 함 | 임시 파일 바이트를 믿을 수 없음 | 임시 파일 보존·검증 설계 추가 |
| 16구간 / 동시 4 | 로드맵 예시, 동시 연결 수는 기존과 같음 | 구간 크기·죽을 때 잃는 양 변화 |
| 옛 `receivedBytes` 기록 버림 | 쓰인 적 없는 기록 | 마이그레이션 코드 추가 |
| `pause()`·단일 스트림 재개 유지 | 범위를 넓히지 않음 | 별도 정리 과제 |

## 위험
- 구간 쓰기가 디스크에 닿기 전에 기기 전원이 꺼지면 기록은 있고 데이터는 없을 수 있다 — 최종 지문 검증이 잡고 `verification-failed`로 처음부터 받는다(앱 죽음은 OS 캐시가 살아 있어 해당 없음).
- 구간 수 증가로 요청 수와 임시 파일 정리가 늘어난다.
