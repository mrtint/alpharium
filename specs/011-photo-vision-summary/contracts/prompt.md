# Contract: 캡션이 프롬프트에 들어가는 모양

**Feature**: `011-photo-vision-summary` | **파일**: `src/diary/prompt.ts` (기존 확장)

005의 `contracts/prompt.md`를 **넓히는** 계약이다. 새 파일을 만들지 않는다 —
**화자 규칙이 저장소 전체에서 한 자리뿐이어야 한다**(005 FR-013b).

---

## P1. 캡션은 `buildPrompt()`를 거쳐서만 일기에 닿는다 (FR-010)

다른 통로를 만들지 않는다. 데스크톱 어댑터도 이 함수를 부른다.

**⚠️ 시그니처가 바뀐다.** 005는 `buildPrompt(request: DiaryRequest)` 하나였는데,
캡션은 `DiaryRequest`에 들어가지 않는다(data-model: `DaySignals`와 나란히 흐른다).

```ts
export function buildPrompt(request: DiaryRequest, vision?: PhotoVision): string;
```

**`vision`이 옵셔널인 까닭**: `vision: "none"`이면 캡션이 아예 없다. 005의 모든 호출과
테스트가 그대로 통과해야 한다 — 003이 `isModelReady?`를 옵셔널로 더한 것과 같은 방식
이며, **계약을 넓히는 것이지 바꾸는 것이 아니다.**

---

## P2. 캡션은 있는 그대로 적는다 (FR-011)

**짐작 표시·한계 문구·확신도를 붙이지 않는다.**

```
2026-08-20에 네가 본 것:
사진: 5장 (08시, 11시, 14시, 17시, 20시)
사진에 담긴 것:
- 08시: 창가에 놓인 커피잔과 펼쳐진 책
- 11시: 사람들이 걷는 거리, 가로수가 늘어서 있다
- 14시: 나무 탁자 위의 접시와 물컵
- 17시: 강가의 산책로, 멀리 다리가 보인다
- 20시: 불이 켜진 실내, 창밖은 어둡다
```

**「~인 것 같다」로 적지 않는다.** 사용자가 clarify에서 확정했고, 근거는 005의 실측이다:
**압력이 지어내기를 낳는다.** 「틀릴 수 있다」를 붙이면 모델이 전부를 얼버무린다.

**휴대폰은 그 사진을 실제로 보았다.** 캡션은 004의 장수·좌표와 **같은 자격의 관측**이며,
그래서 같은 말투로 적힌다.

### ⚠️ 시각을 함께 적는 것이 FR-007b다

`- 08시: …` 꼴로 **캡션마다 시각이 붙는다.** 이것이 「고른 사진이 하루의 어느 때에 걸쳐
있는지」를 말하는 방식이며, 별도 문장을 더하지 않는다 — **줄 자체가 그것을 보인다.**

저녁에만 찍은 하루는 `19시·20시·21시`가 나열되어 **모델이 스스로 「저녁의 기록만 있다」를
읽을 수 있다.**

## P3. 한계는 범위에 대해서만 붙인다 (FR-012)

**정확도가 아니라 범위다.** 둘을 섞으면 P2가 무너진다.

| 상황 | 붙는 줄 |
| --- | --- |
| `available > considered` | `사진이 더 있었으나 그중 다섯 장만 보았다. 본 것이 그날의 전부가 아니다.` |
| `captions.length < considered` | `보려 한 다섯 장 중 N장은 읽지 못했다.` |
| `captions.length === 0` (있는데 전부 실패) | `사진은 있었으나 내용을 하나도 보지 못했다.` |
| 004가 이미 잘랐다 (`complete: false`) | **005의 `TRUNCATED_WARNING`이 그대로 함께 간다** |

**마지막 줄이 중요하다** — 두 한계가 겹치는 하루에서 **둘 다** 나온다(selection.md 참조).
하나만 있으면 거짓이 된다.

### `captions.length === 0`이 「사진 없음」과 다르다 (FR-005, SC-006)

```
사진: 5장 (08시, …)                       ← 004의 신호. 그대로 있다
사진은 있었으나 내용을 하나도 보지 못했다.   ← 011의 한계
```

**「사진: 없었다」가 아니다.** 004가 값에서 지킨 `none`/`unknown` 구분이 한 겹 위에서
반복되며, 여기서 뭉개면 010이 실기기에서 확인한 「없었다 / 모른다」의 성취가 무너진다.

## P4. 캐릭터에서 오는 것은 여전히 언어뿐이다 (FR-013)

캡션 줄은 **캐릭터와 무관하게 같다.** 사진 보는 모델이 캐릭터와 별개이므로(FR-025)
**구조로 보장된다** — 같은 하루의 캡션은 어느 캐릭터로 쓰든 같은 문자열이다.

**SC-001a가 이것을 검증한다.**

---

## P5. 되뱉기 판정에 캡션을 넣지 않는다 — **설계 중에 찾은 함정**

005의 `instructionLines(request)`가 「모델이 지시문을 그대로 되뱉었는가」를 판정할
문자열 목록을 준다. **캡션을 여기 넣으면 안 된다.**

**왜인가**: 005의 계약이 이미 답을 적어 두었다 —

> **신호가 들어간 줄은 넣지 않는다.** "사진 세 장"은 일기에 자연스럽게 나올 수 있으므로
> 비교 대상이면 오탐이 된다(research.md §7).

**캡션은 신호 그 자체다.** 「창가에 놓인 커피잔」이 일기에 나오는 것은 **정확히 우리가
원하는 것**이며, 그것을 되뱉기로 판정하면 **성공한 일기가 거부된다.**

**대신 P3의 한계 줄은 넣는다** — 그것은 지시문이고 신호가 아니다. 005가
`TRUNCATED_WARNING`·`PLACES_LIMITATION`을 넣은 것과 같다.

```ts
export function instructionLines(request: DiaryRequest, vision?: PhotoVision): string[] {
  const lines = [...SPEAKER_RULES];
  // … 005의 기존 두 줄 …
  if (vision !== undefined) {
    // P3의 한계 줄만. **캡션 본문은 절대 넣지 않는다**
  }
  return lines;
}
```

## P6. 판정 갈래를 늘리지 않는다 (FR-014, SC-011)

거부 갈래는 **`empty`/`echo`/`language`/`unfinished` 넷 그대로**다.

**「캡션과 무관한 일기가 나왔다」를 판정하고 싶어지는 자리다.** 그것이 품질 판정이고,
넣는 순간 원칙 IV가 무너진다 — 005가 「임계값·유사도·점수를 쓰지 않는다」로 못 박았고
테스트가 **갈래의 수를 직접 센다.**

---

## P7. 결정적이다

`buildPrompt()`는 여전히 시각·난수를 읽지 않는다. 캡션이 더해져도 **같은 입력에 같은
문자열**이다 — `selectForVision()`이 결정적이므로(selection.md R6) 캡션 목록도 결정적이다.

**⚠️ 다만 캡션 텍스트 자체는 모델이 만들므로 실행마다 다를 수 있다.** 그것은
`buildPrompt()`의 결정성과 다른 층이며, **주어진 `PhotoVision`에 대해** 이 함수가
결정적이면 계약은 지켜진다.
