# 정상 동작 확인 단축 (G2 · F1) — 설계

- 날짜: 2026-10-31 · 트랙: 경량(kickoff 규모 판정) · 입력: `docs/user-guidance-rules.md` 0장 L1, 0-2, 0-4 G2
- 소유자 확정: F1(같은 입력, 답을 몇 토큰에서 끊는다). F3(사진 모듈 적재 확인)은 하지 않는다.

## 목적

첫 실행의 정상 동작 확인(`checkLiveness()`)이 「안녕?」의 답을 일기 생성 상한(`SAMPLING.n_predict` 512)까지 받지 않고, 확인 전용 작은 상한에서 끊어 더 빨리 끝나게 한다. 묻는 것은 그대로 「실제 생성으로 답이 오는가」다.

## 수용 기준

1. 확인 호출은 확인 전용 상한(`LIVENESS_MAX_TOKENS`)에서 끊긴다 — 종전 경로(`complete`)와 iOS 조각 경로(`completePaced`) 모두. 판정(`judgeLiveness()`)은 바뀌지 않는다.
2. 일기 본문·제목·iOS 조각 생성의 상한은 `SAMPLING.n_predict` 그대로다(`SAMPLING` 정본 불변, 원칙 I).
3. 상한에서 짧게 끊긴 생성도 `unload()`가 생성이 끝난 뒤에 `release()`한다(079). 답 텍스트는 판정 직후 버린다(L10).

## 결정

| 결정 | 근거 |
| --- | --- |
| `RunLimits`에 선택 필드 `maxTokens`(이번 호출만의 상한)를 둔다 | 「이번 호출의 한도」를 담는 자리가 이미 `RunLimits`다. 주지 않으면 종전과 같다 |
| `run()`·`ask()` 둘 다 이 필드를 따른다 | 같은 `RunLimits`를 받는 두 메서드가 다르게 굴면 함정이다. 지금 넘기는 곳은 `checkLiveness()` 하나 |
| 값 16토큰 — **사람이 정한 값**(소유자, 2026-10-31) | 첫 토큰 몇 개가 공백·줄바꿈이어도 글자가 남을 여유. iOS 조각(32)보다 작아 조각 하나로 끝난다. 측정이 아니다 |
| `LIVENESS_TIMEOUT_MS`(60초)는 그대로, 근거 주석만 「상한까지 받는다」로 고친다 | 바꿀 근거가 될 실측이 없다(원칙 V) |
| 화면 문구 불변 | 0-2 「되돌릴 때 보이는 말은 지금의 확인 중 화면 그대로」 |
