## Clarifications

### Session 2026-11-21

- Q: 예비 경로로는 몇 번 넘어가는가? → A: 받기 시도 한 번에 한 번. 예비도 실패하면 연결 실패로 끝내고 다음 사용자 시도에서 다시 주 경로부터 (에이전트 판단 · 근거: 단순·예측 가능, 재시도는 사용자 몫이라는 기존 받기 규칙)
- Q: 주 경로의 "실패"는 무엇인가? → A: 받기 결과가 `failed`인 모든 경우(구간 탐지 실패 후 단일 스트림 실패 포함). 멈춤·검증 실패·공간 부족은 아니다 (에이전트 판단 · 근거: 검증 실패에 예비로 다시 받으면 1.2 GB를 또 받는다)
- Q: 다음 받기 시도는 어느 경로부터인가? → A: 언제나 주 경로부터. 어느 경로를 썼는지 기억하지 않는다 (에이전트 판단 · 근거: 구간 기록에 경로를 담지 않는 기존 계약, 상태를 늘리지 않음)
- Q: r2.dev 개발 주소를 쓰는가? → A: 쓴다. 상용 전 커스텀 도메인은 소유자가 따로 정한다 (소유자 답, 2026-11-21)
- Q: 사진 모델에도 예비 경로를 두는가? → A: 아니다, 범위 밖 (에이전트 판단 · 근거: 로드맵 할 일은 `a1`만)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 새로 설치한 사람이 새 일기 모델을 받는다 (Priority: P1)

첫 실행의 필수 모듈 받기가 일기 특화 새 모델을 주 경로(R2)에서 받고, 크기·지문이 맞아야 「준비됨」이 된다.

**Why this priority**: 모델 교체의 본체다. 이것만으로 새 사용자에게 가치가 있다.

**Independent Test**: 모델이 없는 기기에서 받기 → 크기 1,241,435,520 B·지문 일치 → 일기 본문·제목 생성 완주.

**Acceptance Scenarios**:

1. **Given** 모델이 없는 기기, **When** 필수 모듈을 받으면, **Then** 주 경로에서 받고 지문 검증을 통과해 준비된다.
2. **Given** 받는 도중 앱이 죽은 기기, **When** 다시 받으면, **Then** 끝난 구간은 다시 받지 않고 남은 구간만 받는다.

---

### User Story 2 - 주 경로가 실패하면 예비 경로로 받는다 (Priority: P1)

주 경로 받기가 끊기거나 오류로 끝나면, 같은 받기 시도 안에서 예비 경로(Hugging Face)로 한 번 넘어가 받는다.

**Why this priority**: 주 경로가 개발용 주소라 실패 가능성이 있다. 받기가 막히면 앱을 쓸 수 없다.

**Independent Test**: 주 경로가 실패하도록 만든 뒤 받기 → 예비 경로로 완료·검증 통과.

**Acceptance Scenarios**:

1. **Given** 주 경로가 실패하는 상황, **When** 받기를 시작하면, **Then** 예비 경로로 넘어가 받고 검증을 통과한다.
2. **Given** 주 경로에서 일부 구간을 받은 뒤 실패, **When** 예비 경로로 넘어가면, **Then** 이미 끝난 구간은 다시 받지 않는다.
3. **Given** 사용자가 멈춤, **When** 받기가 멈추면, **Then** 예비 경로로 넘어가지 않고 이어받을 수 있는 상태로 남는다.
4. **Given** 예비 경로도 실패, **When** 받기가 끝나면, **Then** 지금과 같은 연결 실패로 알린다.

---

### User Story 3 - 옛 모델을 가진 기기가 한 번 정리하고 새 모델로 바뀐다 (Priority: P2)

옛 모델 파일이나 받다 만 옛 구간 기록이 있는 기기는, 받기를 시작할 때 그것을 정리하고 새 모델을 받는다. 매번 거부되거나 매번 처음부터 다시 받지 않는다.

**Why this priority**: 기존 사용자의 교체 경로다. 막히면 기존 사용자가 일기를 못 쓴다.

**Independent Test**: 옛 파일(1,522,796,768 B)과 옛 검증 기록을 둔 상태에서 받기 → 옛 파일 삭제 → 새로 받기 → 검증 통과. 도중에 멈춘 뒤 다시 받으면 이어받는다.

**Acceptance Scenarios**:

1. **Given** 옛 모델 파일과 옛 검증 기록, **When** 받기를 시작하면, **Then** 옛 파일과 기록을 지우고 새로 받는다.
2. **Given** 옛 크기로 적힌 구간 기록과 부분 파일, **When** 받기를 시작하면, **Then** 기록과 부분 파일을 지우고 처음부터 받는다.
3. **Given** 정리 뒤 새 모델을 받다 멈춘 기기, **When** 다시 받으면, **Then** 다시 지우지 않고 이어받는다.
4. **Given** 옛 모델 파일이 있는 기기, **When** 다시 받기 안내가 받을 양을 보이면, **Then** 0이 아니라 새 모델 전체 크기를 말한다.

---

### User Story 4 - 새 샘플링 값으로 일기를 쓴다 (Priority: P2)

일기 생성이 실측 최적값(temperature 0.60, top_p 0.90)을 쓰고, 나머지 값은 그대로다.

**Independent Test**: 설정 값 확인 + 실기기에서 본문·제목 생성 완주.

**Acceptance Scenarios**:

1. **Given** 새 모델, **When** 일기를 쓰면, **Then** 본문과 제목이 판정을 통과해 저장된다.

### Edge Cases

- 받은 파일의 지문이 틀리면 예비 경로로 다시 받지 않고 검증 실패로 알린다(1.2 GB를 또 받지 않는다).
- 옛 단일 스트림 이어받기 기록이 있고 그 재개가 실패하면, 예비 경로는 그 기록을 지우고 처음부터 받는다.
- 예비 경로가 없는 자산(사진 모델)은 지금처럼 한 경로로만 받는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 캐릭터 `quiet`의 모델 자산은 주 경로(R2 공개 주소), 예비 경로(Hugging Face), 기대 크기 1,241,435,520 B, 지문 `dfc35a88fb1f5215f708ea5a348121b8`를 가진다. 자산 키는 `a1` 그대로다.
- **FR-002**: 주 경로 받기가 실패로 끝나고 예비 경로가 있으면, 같은 받기 시도 안에서 예비 경로로 한 번 다시 받는다.
- **FR-003**: 예비 경로로 넘어갈 때 그때까지 끝난 구간 기록이 파일과 맞으면 이어받는다.
- **FR-004**: 사용자 멈춤·검증 실패·공간 부족은 예비 경로로 넘어가지 않는다.
- **FR-005**: 예비 경로도 실패하면 지금과 같은 연결 실패 갈래로 알린다.
- **FR-006**: 받기 시작 시 기대 크기보다 큰 옛 파일과 그 검증 기록을 지운다(기존 규칙 유지·잠금).
- **FR-007**: 받기 시작 시 전체 크기가 지금 기대 크기와 다른 구간 기록과 부분 파일을 지운다(기존 규칙 유지·잠금).
- **FR-008**: 정리 뒤 받기가 멈춘 기기의 다음 받기는 끝난 구간을 지우지 않고 이어받는다.
- **FR-009**: 다시 받기 안내의 받을 양 계산은 기기에 있는 양이 기대 크기보다 크면 기대 크기 전체로 센다.
- **FR-010**: 생성 샘플링은 temperature 0.60, top_p 0.90이며 top_k 40·n_predict 512·문법은 그대로다.
- **FR-011**: 경로·크기·지문은 화면에 나가지 않는다(원칙 III).

### Key Entities

- **모델 자산**: 키·주 경로·예비 경로(선택)·기대 크기·지문. 화면에 나가지 않는 안쪽 값.
- **구간 이어받기 기록**: 자산 키·전체 크기·구간 수·끝난 구간 번호. 경로를 담지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 실기기에서 주 경로로 새 모델 전체를 받아 지문 검증을 통과한다(1회 이상).
- **SC-002**: 받는 도중 앱을 끝낸 뒤 다시 받으면 끝난 구간을 다시 받지 않는다(실기기 1회 이상).
- **SC-003**: 주 경로가 실패하는 조건에서 예비 경로로 받기를 마친다(실기기 1회 이상).
- **SC-004**: 옛 모델이 있던 기기가 한 번의 받기로 새 모델로 바뀌고, 이후 받기 시도에서 다시 지워지지 않는다.
- **SC-005**: 새 모델로 일기 본문과 제목 생성이 끝까지 완료된다(실기기 1회 이상).

## Assumptions

- 두 경로의 파일은 바이트 단위로 같다(같은 크기·지문 확인됨). 그래서 구간을 섞어 받아도 된다.
- r2.dev 주소는 트래픽 제한이 있는 개발용 주소다. 상용 전 커스텀 도메인 결정은 소유자 몫이며 이 기능의 범위 밖이다.
- 기존 사용자가 받기를 시작하는 경로(쓰기 시 「AI 모듈을 준비해야 해요」 → 다시 받기)는 그대로 쓴다.
- 새 외부 호스트(R2)와 바뀐 모델 출처는 개인정보처리방침·라이선스·지원 페이지와 스토어 선언 초안에 함께 반영한다(086 규칙).
- 샘플링·모델 값의 근거는 옆 저장소 실측(terrarium EXP-013~015)이다.
