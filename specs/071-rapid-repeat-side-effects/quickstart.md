# Quickstart: 빠른 반복 재현 절차

계측·조작 스크립트는 저장소에 넣지 않는다(원칙 IV, FR-010). 아래는 손이나 scratchpad 스크립트로 따르는 절차다. 결과는 이 파일 끝 「관측 결과」에 [contracts/side-effect-list.md](./contracts/side-effect-list.md) 형식으로 쌓는다.

## 0. 준비

1. 기기 연결: `adb devices`에 `R3CN60JVNCE`. 잠금이 풀려 있고 화면이 켜져 있다(`adb shell dumpsys trust`의 `deviceLocked=0`).
2. dev 빌드가 설치돼 있고 Metro가 dev 환경으로 떠 있다(`EXPO_PUBLIC_APP_ENV=dev npx expo start --dev-client`, gradle 빌드가 끝난 뒤) — AGENTS 「도구 사용법」 1. `adb reverse tcp:8081 tcp:8081`.
3. 번들 확인: `curl -s "localhost:8081/index.bundle?platform=android&dev=true" | grep -B1 '"EXPO_PUBLIC_APP_ENV"'`.

## 1. 첫 완주 (cold)

1. `adb shell pm clear com.a810labs.pocketlog` (모델·일기 삭제 — 소유자 동의 2026-10-10).
2. 앱을 연다: 로고 → 권한 → 다운로드 동의·진행 → 작명 → liveness → 자동 첫 일기. 이 구간의 `logcat`을 저장한다.
3. 첫 일기가 저장되고 쓴 날 홈이 보이면 점검 기준 상태다.

## 2. 점검 기준 되돌리기 (매 반복 전)

`run-as com.a810labs.pocketlog`로 `files/locks/diary-generation.lock`, `files/preferences/write-failures.json`, 반복 대상 날의 `files/diary/<날짜>.json`·`.json.writing`을 지운다(JSON 쓰기가 필요하면 AGENTS의 `adb push` + `cat | run-as` 방식).
작명·온보딩 단계를 다시 타려면 `files/preferences/onboarding.json`의 플래그를 같은 방식으로 되돌린다(모델은 그대로).

## 3. 반복

시나리오 `S-A`~`S-E`를 여섯 간격으로. 좌표는 `adb shell uiautomator dump`로 먼저 읽는다. `input tap` 사이를 `sleep`으로 띄운다.

- S-A: 「일기 쓰기」 → (간격) → 「그만두기」 → (간격) → 「일기 쓰기」.
- S-B: 「일기 쓰기」 직후 0·300·1400ms에 「그만두기」 연타, 1.6초에 한 번.
- S-C: 쓰기 시작 → 홈 버튼(`input keyevent 3`) → 복귀 / 설정 열고 닫기.
- S-D: 이미 쓴 날에서 「다시 쓰기」 → 덮어쓰기 확인 → 그만두기 → 다시.
- S-E(FR-013): 작명 확정 버튼 연타, 온보딩 단계 연타·도중에 앱 내렸다 올림, 첫 일기 저장 뒤 `onboarding.json` 완료 플래그를 되돌려 작명·온보딩에 다시 들어갔다 나오기(모델은 그대로).
- 저장 경계 점검: 제목 질문이 끝나는 로그 줄 근처에 「그만두기」 — 처음 쓰는 날과 다시 쓰기(옛 파일 해시 전후 비교) 모두. 저장 시작 전 취소에서 파일이 생기거나 바뀌면 증상이다.
- 정상 완주 1회: 간격 10초 시나리오에서 중단하지 않고 끝까지 둔다(저장·알림·완료 홈, R6).

## 4. 점검 (반복 뒤 매번)

lock → diaryDir → failures → screen → log → memory 순서로 읽고 C1 표에 한 줄을 적는다. 어긋남이 있으면 C2에 `SE-n`을 만든다.

## 5. 수정과 확인

1. 코드 결함은 테스트를 먼저 쓴다(`npm run test:logic` / `npm run test:ui`) → 고친다 → 위반 주입(치환이 적용됐는지 먼저 단언) → 되돌렸을 때 실패하는지 확인.
2. 같은 (시나리오, 간격)으로 5회 반복해 재현되지 않음을 확인(SC-003).
3. `npm test`, `npm run lint` 통과(SC-006).

### C3 고친 결함의 기록

- **수정**: `src/ui/DiaryHomeScreen.tsx` — 쓰기 시도마다 번호(`attempt`)를 붙이고 그만두기는 그때까지의 번호를 닫는다(`cancelledThrough`). 늦게 풀린 앞 시도는 자기가 닫혔음을 알아 실패 기록·토스트·화면 전환을 하지 않고, 자기 `finally`가 더 새 시도의 「쓰는 중」·`inFlight`를 끄지 않는다(SE-2). 새 시도는 앞 시도(`inFlight`)가 풀리기를 기다린 뒤 파이프라인을 부른다 — 기다리는 동안 다시 그만두면 시작하지 않는다(SE-1). `src/diary/pipeline.ts` — `PipelineInput.isCancelled?`를 저장 직전에 한 번 보고, 참이면 저장하지 않고 사진 사본을 저장 실패와 같은 규칙(`discardPhotos`, `ownsResizedPath`가 거짓인 원본은 지우지 않는다)으로 정리한 뒤 `generation`/`interrupted`로 돌아온다(SE-3, 새 단계 없음).
- **테스트**: `__tests__/ui/home-rapid-cancel.test.tsx`(R1~R4 여섯), `__tests__/diary/pipeline-cancel-on-save.test.ts`(다섯). 소스 계약 `app-diagnostics-source.test.ts` WF7이 옛 `cancelled.current` 문자열을 읽던 것을 시도별 `isCancelled()`로 옮겼다(그만두기를 거른 뒤에 기록한다는 의도는 같다).
- **위반 주입**(치환 적용을 먼저 단언): ① 파이프라인 저장 전 취소 확인을 `false`로 → `pipeline-cancel-on-save` 4 실패 ② 앞 시도 대기를 끔 → R1 2 실패 ③ 시도별 취소를 항상 거짓으로 → R1·R2·R3 4 실패 ④ `finally`가 시도 번호와 무관하게 `running`·`inFlight`를 끔 → 처음엔 안 잡혔고(R1~R3 통과) **R4(지우기 요청과 맞물림)를 더하자** 잡혔다. 모두 되돌려 `git diff`로 확인했다.
- **재검증(실기기, 같은 간격)**: 레이스 B D=2500·4000·6000 각 5회 = 15/15에서 실패 기록 0, 토스트 0, 둘째 쓰기가 끝까지 가 저장, `.writing` 0. S-A T=1400 5/5에서 끝 6초 안에 잠금이 풀리고 실패 기록 0. 새 쓰기를 누르면 홈 대신 「쓰는 중」이 되어(앞 쓰기가 풀리길 기다린다 — `fix-b-4000-r1-p1.png`) 거절 토스트가 없다.
- **SE-3 남은 창**: 수정 뒤 생성 끝 근처(25.8~27.0초) 그만두기 6회 중 5회는 일기가 저장됐고 모두 잠금이 그만두기 0.14~0.20초 뒤에 풀렸다 — 그만두기가 저장 직전 확인을 지난 뒤(저장 시작 후)에 도착한 것으로 읽힌다(구분은 못 했다). spec Edge Cases가 정한 대로 저장 I/O가 시작된 뒤의 취소는 일기를 남긴다 — **소유자 확정(2026-10-10)**(다시 쓰기에서 옛 일기까지 잃지 않기 위해서). 수정 전 같은 구간은 6회 중 1회.
- **메모리**: 사진 읽기 중 PSS 최대 약 4.1GB, 끝나면 1.26GB — 반복 중 누적 증가 없음. 사진 있는 날(10-09) 그만두기 → 4초 뒤 다시 쓰기는 정상 완주(수정 전 관측).

### 못 고친 것·남은 것

- **SE-4(앱을 내렸다 올림)**: 054·005 FR-014b의 알려진 동작이라 범위 밖.
- **잠금이 그만두기 뒤 5~12초 남는 것**: 모델 적재는 중단할 수 없다(016 FR-013, llama.rn에 로드 취소 API가 없다). 화면은 이제 그동안 새 쓰기를 기다리게 하지만 **그 사이 백그라운드 자동 쓰기는 `already-running`으로 건너뛴다**(범위 밖, 이번에 보지 않았다).
- **미확인**: 반복 속도 0·300ms에서 하단 바 잠금(1.5초)이 첫 그만두기를 막는 것이 의도대로인지는 보았으나(관측 없음) 그 잠금 자체의 UX 판단은 하지 않았다. iOS·release·재부팅 직후는 보지 않았다.
- **방어 수단 질문(소유자)**: 실제 llama.rn 중단 타이밍(H4)은 기기 없는 테스트로 재현할 수 없었다 — 소스 계약 대신 화면 레이스는 `home-rapid-cancel`이 잠그고, 실제 적재 중 중단 타이밍은 e2e 층 2 반복 시나리오로는 옮기지 않는다(소유자 결정 2026-10-10).
