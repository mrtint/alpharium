# 계약: 로스터 — 캐릭터와 모델 자산의 매핑

**대응 요구사항**: FR-001, FR-001a, FR-001b, FR-002, FR-003, FR-004, FR-004a, FR-004b,
FR-005a, FR-005b, FR-005c

**구현 위치**: `src/models/roster.ts`

---

## 이 계약이 지키는 것

**이 파일이 헌법 원칙 III의 유일한 통과 지점이다.** 001의 `policy.ts`가 원칙 I의 방어선을
한 곳에 모은 것과 같은 구조다.

캐릭터와 모델 파일이 이어지는 곳이 저장소 전체에서 **여기 하나뿐**이어야 한다. 다른 곳에서
매핑을 다시 만들면 방어선이 둘로 갈라지고, 갈라진 순간 한쪽이 화면으로 샌다.

---

## 모양

```
roster.ts가 내주는 것:
  assetFor(character): ModelAsset        ← 안쪽에서만 부른다
  CHARACTERS: readonly Character[]       ← 002의 것을 다시 내보낸다

roster.ts가 내주지 않는 것:
  characterFor(asset)                    ← 역방향 (FR-003)
  allAssets()                            ← 전부 훑기 (아래 참조)
  assetKeyOf(character) 같은 부분 노출    ← 조각내도 매핑이다
```

**`allAssets()`를 두지 않는 이유**: 있으면 화면이 "다섯 자산을 다 받자"를 쉽게 쓸 수 있고,
그것이 헌법 로스터가 금지한 구조다(FR-010). 캐릭터를 순회할 일이 있으면 `CHARACTERS`를 돌고
각각에 대해 준비 상태를 물으면 된다 — 자산이 필요 없다.

---

## 불변식

1. **매핑은 코드 안쪽에만 있다**(FR-002). `process.env`·원격 설정·사용자 설정에서 읽지
   않는다. 001이 `process.env`를 `environment.ts`에만 두게 한 것과 같은 이유이며, **여기서는
   더 강해서 어디서도 읽지 않는다.**

2. **한 방향으로만 흐른다**(FR-003). 캐릭터 → 자산은 있고 자산 → 캐릭터는 없다.

3. **`ModelAsset`이 이 모듈 밖으로 통째로 나가지 않는다.** 다른 모듈은 필요한 조각만 인자로
   받는다. 예: 검증 모듈은 "이 경로의 파일이 이 지문과 맞는가"를 묻지 자산을 받지 않는다.

4. **`key`가 캐릭터 식별자와 다르다**(FR-004). 파일명이 `quiet.gguf`이면 파일 관리자에서
   캐릭터가 드러나고, 거꾸로 캐릭터로 파일을 찾을 수 있다.

5. **표시 이름과 설명 문안이 없다**(FR-004a, FR-005c). 헌법이 "캐릭터 이름은 사람이 짓는다"고
   했고, 설명은 실측 관측에 근거해야 하는데 그 관측은 이 저장소의 몫이 아니다(원칙 IV).

6. **추천·기본 캐릭터가 없다**(FR-005b). 추천에는 근거가 필요하고 그 근거가 없다.

## 진단과의 경계 (FR-004b)

진단 경로에서는 모델 정보를 볼 수 있다(MAY). 개발자가 보는 것이고 사용자 화면이 아니다.

**다만 그 경계가 코드에 분명해야 한다**(MUST):

- 진단용 함수는 **이름에 진단임이 드러나야** 한다
- 진단용 함수를 `src/ui/` 아래 화면 컴포넌트가 부르지 않는다 (`DiagnosticsScreen`은 예외이며
  이름 그대로 진단 화면이다)
- 진단이 사용자 화면으로 자라지 않게, 진단 함수가 돌려주는 값을 일반 화면 타입에 섞지 않는다

001이 `fake.ts`를 두되 "제품 경로가 아니다"를 계약에 적은 것과 같은 처리다.

## 다음 기능에 넘기는 것

- **캐릭터 표시 이름** — 사람이 짓는다(헌법 「로스터」)
- **캐릭터 설명 문안** — 실측 관측에 근거해야 하며 별도 저장소의 결과를 들여온다
- **모델의 실제 주소·크기·지문 값** — 코드 안쪽 값이며 저장소 소유자가 채운다
- **추론 설정(샘플링·컨텍스트 길이)** — 실제 생성 기능의 몫. 자산에 담지 않는다
