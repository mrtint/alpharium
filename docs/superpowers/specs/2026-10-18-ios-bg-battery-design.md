# iPhone 충전 없이 백그라운드에서 쓰기 (설계)

날짜: 2026-10-18 · 로드맵: 「iPhone 충전 없이 백그라운드에서 쓰기 — 소유자 필수」 할 일 1·2 (할 일 3 `BGContinuedProcessingTask`는 다음 과제로 뗀다 — 소유자)
선행: 090(충전 중 완주 — 외부 전원 요청 패치, 따라잡기 몫, 보이지 않는 홈, 시도 기록 `launch`·`expired`)

## 목적 (소유자)

충전기에 꽂지 않은 iPhone에서도 iOS가 깨워 준 백그라운드 기회에 일기를 써 둔다. 090의 충전 경로(빠름)는 그대로 둔다.

## 벽 (090 실측)

1. **CPU 감시** — 외부 전원을 요구하지 않는 처리 작업은 「60초 동안 CPU 48초(코어 하나의 80%)」를 넘으면 `cpu_resource_fatal`로 죽는다. CPU 시간은 스레드 수와 무관하게 합산된다. 지금 쓰기(4스레드)는 51초 만에 죽었다.
2. **깨움 빈도** — 충전하지 않을 때 iOS가 처리 작업을 얼마나 깨우는지 재지 않았다(087의 27시간 0회는 네트워크를 요구하던 요청).

## 설계 — 접근 A (소유자 승인)

### 1. 요청 둘 (expo 패치 확장)

- 090 패치를 넓혀 `BackgroundTaskScheduler`가 요청 **둘**을 낸다: 기존 식별자(`com.expo.modules.backgroundtask.processing`, 외부 전원 요구 — 090 그대로)와 새 식별자(`com.expo.modules.backgroundtask.processing.battery`, 외부 전원·네트워크 불요). 둘 다 `earliestBeginDate`는 같다. 취소·재제출도 둘을 함께.
- `BackgroundTaskAppDelegate`가 두 식별자를 같은 처리기로 등록하고, 처리기가 **어느 식별자로 깼는지**를 정적 값에 남긴 뒤 종전대로 JS 태스크를 돌린다.
- 로컬 모듈(`modules/pocketlog-bg-expiry` — 이름은 유지하거나 `pocketlog-bg`로 넓힌다)이 그 값을 JS에 동기 함수로 준다: `"power" | "battery" | null`.
- Info.plist `BGTaskSchedulerPermittedIdentifiers`에 새 식별자를 더한다(작은 config plugin — expo 플러그인이 기존 것을 넣는 방식과 같다).
- 충전 중에는 두 요청이 함께 깰 수 있다 — 080 등록부가 두 번째를 `already-running`으로 막는다(090의 몫 규칙상 몫은 쓰이지만 같은 날 첫 실행이 쓰고 있다).

### 2. 기록

- 시도 기록 시작 줄에 깨운 요청(`wake: "power" | "battery"`, 옵셔널)을 싣고 화면 꼬리에 「· 충전」/「· 배터리」를 붙인다. 이것이 할 일 1의 측정 장치다(앱 동작 기록 — 원칙 IV의 측정이 아니다).

### 3. 배터리 모드의 「느린 쓰기」

배터리 요청으로 깼으면(백그라운드 조립 + iOS + `battery`) 조립이 다음을 고른다(`src/inference/assembly.ts` — 079의 「조립 주체가 값을 정한다」에 축 하나):

- **스레드 1** — 본문·사진 모델 모두.
- **쉼(페이싱)** — 모델 호출 하나가 끝날 때마다 그 호출의 벽시계 시간 × 비율만큼 쉰다. 스레드 1이면 CPU 시간 ≈ 벽시계 시간이므로 비율 0.5면 평균 약 67%(한도 80% 아래). 비율은 사람이 정한 상수, 실측으로 조정.
- **사진 읽기** — 장마다 호출이 따로라 장 사이에 쉰다.
- **본문 나눠 생성** — 한 번의 호출이 길면 쉼 없이 48초를 넘으므로, 본문은 `getFormattedChat`으로 만든 서식 프롬프트에 지금까지 쓴 글을 이어 붙여 `n_predict` 조각(수십 토큰)씩 생성하고 조각 사이에 쉰다. 앞부분 KV 캐시는 재사용된다(018의 원리). 끝은 `eos` 조각 또는 전체 길이(`SAMPLING.n_predict`) 도달. 로마자 차단 문법(077)은 조각마다 싣는다. 결과는 종전대로 4갈래 판정을 지난다. 제목 질문도 같은 방식.
- **생성 시간 한도** — 느린 쓰기는 길어지므로 배터리 모드 한도를 따로 둔다(사람이 정한 값). 실제 상한은 iOS의 예산 만료(090 `expired` 줄)다.
- 충전 모드·화면 조립·안드로이드는 바뀌지 않는다.

### 4. 여러 깨움에 나눠 쓰기 — 조건부

한 번의 배터리 깨움이 예산 만료로 끝나는 것이 실측으로 드러나면, 사진 캡션을 날짜별로 저장해 다음 깨움이 이어 받게 한다. 먼저 재 보고 필요할 때만 만든다(YAGNI).

## 순서

1. 요청 둘·기록(`wake`)을 먼저 넣어 iPhone에 무선으로 설치 → 배터리로 하루 두고 깨움 수를 센다(할 일 1).
2. 그동안 느린 쓰기(3)를 만들고 다시 설치 → 충전 없이 안 쓴 날이 써지는지 본다(할 일 2, 완료 조건).
3. 2에서 예산 만료가 나면 4.

## 테스트

- 조립: 백그라운드·iOS·battery → 스레드 1·페이싱 켬·배터리 한도, 그 밖 조합은 종전.
- 나눠 생성: 가짜 컨텍스트로 조각 이어 붙이기·`eos` 종료·길이 상한·조각 사이 쉼 호출·멈춤(그만두기)이 조각 경계에서 듣는지, 지표가 경계를 넘지 않는지(원칙 IV, 005 FR-011).
- 페이싱: 시계 대역으로 쉼 길이 = 호출 시간 × 비율.
- 패치: 설치된 파일에 두 식별자·두 요청, Info.plist 식별자(소스 계약).
- 기록: `wake` 필드·꼬리·옛 줄 호환.

## 남는 위험

- iOS가 배터리 상태에서 처리 작업을 거의 안 깨우면 2는 기술로 풀 수 없다(측정이 먼저인 까닭).
- 조각 생성은 한 번에 생성한 글과 같지 않을 수 있다(샘플링이 조각마다 다시 시작) — 판정 통과율을 실기기로 본다.
- 프리필(프롬프트 읽기) 한 번은 나눌 수 없다 — 스레드 1의 프리필이 48초를 넘으면 그 자체로 죽는다. 실측해 넘으면 프롬프트 프리필도 나눈다(프롬프트를 조각으로 먼저 채우는 호출).
- 사용자가 휴대폰을 집으면 iOS가 처리 작업을 끝낸다 — 느린 쓰기는 그 확률을 높인다.
- expo 패치가 커진다 — expo를 올릴 때 다시 만든다(090처럼 `--error-on-fail`이 막는다).
