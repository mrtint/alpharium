# Feature Specification: 안드로이드 배터리 예외 인지 — 완성 알림만 오게 하고, 예외를 받게 이끈다

**Feature Branch**: `104-battery-exception-awareness`

**Created**: 2026-10-24

**Status**: Draft

**Input**: User description: "docs/superpowers/specs/2026-10-24-battery-exception-awareness-design.md 를 입력으로 한다. 안드로이드 배터리 예외 인지 — 예외 여부를 읽어(exempt/restricted/unknown), 예외가 있을 때만 쓸 차례 알림을 정각+30분으로 늦춰 완성 알림만 오게 하고(저장된 뒤에만 예약을 거두는 안전장치 유지), 설정 배터리 행에 「허용됨」/「허용 안 함」 꼬리표를 붙이며, 예외가 없는 채 앱 열기 자동 쓰기가 시작되면 홈에 한 줄 안내+[설정 열기](닫으면 7일간 숨김)를 보인다. iOS는 지연 0·변경 없음."

## 근거와 원본

- 설계문서: `docs/superpowers/specs/2026-10-24-battery-exception-awareness-design.md` — 결정·근거·테스트·실기기 확인 계획이 거기 있다.
- 로드맵 「백그라운드 자동 쓰기가 완주하지 못한다 — 안드로이드·iOS」 할 일 2번의 **소유자 결정(2026-10-15, 배터리 예외를 받게 이끄는 쪽을 강화한다)** 과, 소유자 관측(2026-10-24: 안드로이드에서 완성 알림 앞에 「쓸 차례」 알림이 따로 온다)을 닫는다. 할 일 1·3·5·6번과 078 잔여는 건드리지 않는다. 하룻밤 소크(3번)는 이 기능의 실기기 확인과 조건이 같지만 완료 조건에 넣지 않는다.
- **085 FR-019를 뒤집는다**: 085는 「배터리 예외 여부를 읽는 새 통로를 들이지 않는다」고 했다. 소유자가 2026-10-15에 이를 뒤집었고(예외를 읽는다), 이 스펙이 그 변경을 한다. 085의 해당 서술은 구현과 함께 고친다.
- 용어:
  - **배터리 예외** = 안드로이드 배터리 사용 「제한 없음」. 예외가 있으면 화면이 꺼진 채에도 백그라운드 쓰기가 약 4분에 완주한다(079).
  - **예외 상태** = `exempt`(예외 있음) · `restricted`(예외 없음) · `unknown`(읽지 못함, iOS 포함).
  - **쓸 차례 알림** = 목표 시각에 「그 날 몫을 쓸 차례다」를 알려 앱을 열게 하는 날짜별 예약 알림(085).
  - **완성 알림** = 백그라운드가 일기를 다 썼을 때 보내는 알림(057).
  - **앱 열기 자동 쓰기** = 앱을 열 때 쓸 차례가 된 날을 홈이 「쓰는 중」으로 시작하는 기존 동작(057·080·082).
  - **안전장치** = 쓸 차례 알림 예약은 그 날 일기 **파일이 저장된 뒤에만** 거둔다. 쓰기 시작·도중에는 거두지 않는다(085, 설계문서 §2).

## Clarifications

### Session 2026-10-24

- Q: 홈 안내는 쓰는 동안 보이는가, 저장된 뒤 홈에서 보이는가? → A: 저장된 뒤 홈(쓴 날 화면)에서만 보인다. 쓰는 동안은 보이지 않고, 쓰기가 실패하면 보이지 않는다.
- Q: 쓸 차례 알림을 눌러 시작된 쓰기에도 홈 안내를 보이는가? → A: 보인다. 앱을 직접 열어 시작된 쓰기(057)와 쓸 차례 알림을 눌러 시작된 쓰기(085) 모두이고, 홈의 「쓰기」 버튼으로 사람이 시작한 쓰기는 제외한다.
- Q: 홈 안내 한 줄의 문구는? → A: 「배터리 사용 제한을 풀어 두면 화면이 꺼진 채로도 일기를 써드릴 수 있어요」 + [설정 열기] + [닫기]. 실측한 사실(예외를 주면 화면을 꺼도 써진다)만 말하고 시각·완주를 약속하지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 백그라운드가 쓸 수 있는 기기에서는 완성 알림만 받는다 (Priority: P1)

배터리 예외를 준 안드로이드 사용자는 목표 시각에 휴대폰이 스스로 일기를 쓰고 「다 썼어요」 알림 하나만 받는다. 쓰는 동안 「쓸 차례예요」 알림이 먼저 뜨지 않는다. 백그라운드가 어떤 이유로 쓰지 못한 날에는 정각 30분 뒤에 쓸 차례 알림이 대신 온다.

**Why this priority**: 소유자 관측으로 드러난 불편이다. 지금은 쓸 차례 알림이 목표 시각 정각에 먼저 뜨고, 같은 시각에 시작한 백그라운드가 약 4분 뒤 저장하면 그 알림이 사라지고 완성 알림이 뜬다 — 사용자는 한 번에 두 알림을 겪는다.

**Independent Test**: SM-S901N dev에서 배터리 예외를 준 채 목표 시각 직후 강제 잡을 돌려 완주시킨다. 쓸 차례 알림이 한 번도 뜨지 않고 완성 알림만 온다. 이어 잡을 돌리지 않고 정각+30분을 지나면 쓸 차례 알림이 뜬다.

**Acceptance Scenarios**:

1. **Given** 예외 상태가 `exempt`이고 자동 쓰기가 켜져 있다, **When** 쓸 차례 알림을 예약한다, **Then** 울릴 시각은 목표 시각 정각 + 30분이다.
2. **Given** 위 예약이 걸려 있고 백그라운드가 정각 직후 쓰기를 시작해 정각+30분 전에 저장했다, **When** 저장된다, **Then** 그 날 예약이 거둬지고 쓸 차례 알림은 뜨지 않으며 완성 알림이 온다.
3. **Given** 위 예약이 걸려 있고 백그라운드가 그 날을 쓰지 못했다(실패·끊김·잡이 돌지 않음), **When** 정각+30분이 된다, **Then** 쓸 차례 알림이 뜬다.
4. **Given** 백그라운드가 쓰기를 시작했고 정각+30분이 쓰기 도중에 온다, **When** 시각이 된다, **Then** 쓸 차례 알림이 종전처럼 뜨고, 저장되면 거둬진다. 쓰기 시작만으로 예약을 지우지 않는다.

---

### User Story 2 - 예외가 없거나 모르면 알림은 종전처럼 제때 간다 (Priority: P1)

배터리 예외가 없는 안드로이드 사용자, 예외 여부를 읽지 못한 사용자, iOS 사용자는 쓸 차례 알림을 지금과 같은 시각(목표 시각 정각)에 받는다. 이 변경으로 알림이 늦어지지 않는다.

**Why this priority**: 예외가 없으면 백그라운드가 얼어 쓰지 못하므로(079) 쓸 차례 알림이 유일한 경로다. 근거 없이 늦추면 이 경로를 해친다. 모르는 것을 「예외 있음」으로 채우지 않는다(원칙 V).

**Independent Test**: 예외 상태 세 가지(`restricted`·`unknown`·iOS)에서 같은 설정으로 계획을 만들어 모두 정각임을 확인한다. SM-S901N에서 예외를 끈 채 쓸 차례 알림이 정각에 뜨는지 본다.

**Acceptance Scenarios**:

1. **Given** 예외 상태가 `restricted`, **When** 예약한다, **Then** 울릴 시각은 정각이다.
2. **Given** 예외 상태를 읽지 못했다(`unknown`), **When** 예약한다, **Then** 울릴 시각은 정각이고 맞추기는 멈추지 않는다.
3. **Given** iOS, **When** 예약한다, **Then** 울릴 시각은 정각이고 예외 상태를 읽지 않는다.
4. **Given** 사용자가 설정 앱에서 예외를 줬다가 끄거나 반대로 바꿨다, **When** 앱으로 돌아온다, **Then** 예외 상태를 다시 읽고 걸린 예약을 새 상태의 시각으로 다시 맞춘다.
5. **Given** 업데이트 전에 정각으로 걸린 예약이 있다, **When** 업데이트 뒤 처음 맞춘다, **Then** 새 규칙의 시각으로 바뀐다(`exempt`이면 +30분).

---

### User Story 3 - 설정에서 배터리 예외 상태를 본다 (Priority: P2)

설정의 배터리 행에 다른 권한 행처럼 꼬리표가 붙는다. 예외가 있으면 「허용됨」, 없으면 「허용 안 함」, 읽지 못했으면 꼬리표가 없다. 설정 목록에서 예외를 주고 돌아오면 꼬리표가 바뀐다.

**Why this priority**: 읽지 않으면 이미 예외를 준 사용자에게도 계속 권하게 된다. 사용자가 자기 상태를 한눈에 알 수 있어야 한다.

**Independent Test**: SM-S901N에서 예외를 끈 채 꼬리표가 「허용 안 함」인지, [설정 열기] → 「제한 없음」 → 돌아오면 「허용됨」으로 바뀌는지 본다.

**Acceptance Scenarios**:

1. **Given** 안드로이드이고 `exempt`, **When** 설정을 연다, **Then** 배터리 행 꼬리표는 「허용됨」이다.
2. **Given** `restricted`, **When** 설정을 연다, **Then** 꼬리표는 「허용 안 함」이다.
3. **Given** `unknown`, **When** 설정을 연다, **Then** 꼬리표가 없다(기존 보조 줄만).
4. **Given** iOS, **When** 설정을 연다, **Then** 배터리 행은 지금과 같다(꼬리표 없음).
5. **Given** 설정 목록에서 상태를 바꿨다, **When** 앱으로 돌아온다, **Then** 꼬리표가 새 상태로 바뀌고 토스트는 띄우지 않는다.

---

### User Story 4 - 백그라운드가 못 써서 열어야 했던 순간 예외를 권한다 (Priority: P2)

예외가 없는 안드로이드 사용자가 앱을 열었더니 앱 열기 자동 쓰기가 시작된다 — 「백그라운드가 못 써서 열어야 했다」를 막 겪은 순간이다. 그 쓰기가 저장돼 홈이 쓴 날 화면으로 바뀌면 한 줄 안내와 [설정 열기]가 보인다(쓰는 동안은 보이지 않는다). 닫으면 7일 동안 다시 보이지 않고, 예외를 주고 돌아오면 사라진다.

**Why this priority**: 소유자 결정(2026-10-15)의 핵심이다. 예외를 주면 화면을 끈 채 약 4분에 완주하므로(079) 가장 효과가 큰 개선이다. 다만 새 알림 거동(P1)이 먼저다.

**Independent Test**: SM-S901N에서 예외를 끈 채 앱 열기 자동 쓰기가 시작되도록 해 안내가 뜨는지 본다. 닫고 7일 안에 다시 안 뜨는지(시각을 옮겨), [설정 열기] → 예외 → 돌아오면 안내가 사라지는지 본다.

**Acceptance Scenarios**:

1. **Given** 안드로이드이고 `restricted`이며 앱 열기 자동 쓰기가 시작됐다, **When** 쓰기가 저장돼 홈이 쓴 날 화면으로 바뀐다, **Then** 한 줄 안내와 [설정 열기]가 보인다. 쓰는 동안에는 보이지 않는다.
6. **Given** 앱 열기 자동 쓰기가 실패했다, **When** 홈이 보인다, **Then** 안내가 보이지 않는다(실패 토스트만 종전대로).
2. **Given** `exempt` 또는 `unknown` 또는 iOS, **When** 앱 열기 자동 쓰기가 시작된다, **Then** 안내가 보이지 않는다.
3. **Given** 안내가 보인다, **When** 사용자가 닫는다, **Then** 7일 동안 다시 보이지 않고 7일이 지나면 조건이 맞을 때 다시 보인다. 닫은 시각은 앱을 껐다 켜도 남는다.
4. **Given** 안내가 보인다, **When** [설정 열기]를 눌러 목록에서 예외를 주고 돌아온다, **Then** 상태를 다시 읽어 안내가 사라진다.
5. **Given** 앱 열기 자동 쓰기가 시작되지 않았다(사용자가 그냥 홈을 연다), **When** 홈이 보인다, **Then** 안내가 보이지 않는다.

---

### Edge Cases

- 예외 상태를 읽는 도중 오류가 나거나 시간이 걸리면: `unknown`으로 삼키고 정각으로 간다. 읽기 실패가 쓰기·맞추기를 막지 않는다.
- 백그라운드 헤드리스 실행에서 예외 상태가 읽히지 않으면: `unknown` — 동작은 종전과 같다(지연 0). 이 기능의 효과(완성 알림만)는 그 기기에서 일어나지 않는다.
- 정각+30분이 이미 지난 날(오늘 목표 시각 +30분 뒤 앱을 열었다 등): 계획은 지난 시각을 다시 걸지 않는다. 지난 시각이지만 아직 전달 전일 수 있는 예약은 085 RC8대로 둔다.
- 정각은 지났지만 정각+30분 전에 업데이트가 설치된 날: 새 규칙의 예약(+30분)이 걸린다. 이미 정각에 뜬 알림은 건드리지 않는다.
- 정각에 이미 전달된 알림이 있는 날에 예외 상태가 `restricted`→`exempt`로 바뀌어 정각+30분이 아직 오지 않았을 때 맞추면, 같은 날 알림이 한 번 더 걸려 뜰 수 있다. 상태가 정각 직후 30분 안에 바뀌는 드문 경우뿐이고 알림이 중복될 뿐 일기를 잃지 않는다(받아들임).
- 쓰기가 정각+30분 직전에 시작해 저장 전에 알림이 뜬 경우: 알림이 뜨고, 저장되면 트레이에서 걷어 낸다(085 기존).
- 한 번도 쓰지 못한 날(프로세스 사망·얼림): 예약은 OS에 남아 시각에 뜬다(안전장치). 삼성 얼림이 알람을 미루는 한계는 085에서 소유자가 받아들였고 이번에도 달라지지 않는다.
- 사용자가 홈 안내를 닫았는데 7일 안에 예외를 줬다가 다시 끈 경우: 닫은 시각부터 7일이 지나기 전에는 다시 보이지 않는다.
- 안내 기록 파일을 읽지 못하면(통로 예외): 안내를 띄우지 않는다(모르는 것을 「닫지 않았음」으로 채우지 않는다). 파일이 없거나 깨져 내용을 읽을 수 없으면 닫은 적 없는 것으로 보고 안내를 띄우며, 닫으면 새 기록이 깨진 파일을 덮는다.
- 쓸 차례 알림 시각을 사용자가 바꿀 수 있는 설정은 없다(YAGNI).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 안드로이드에서 배터리 예외 상태를 `exempt`·`restricted`·`unknown` 셋으로 읽을 수 있어야 한다. 읽기 실패·iOS는 `unknown`이다. 상태 외의 값(배터리 잔량 등)은 읽지도 남기지도 않는다(원칙 IV).
- **FR-002**: 예외 상태가 `exempt`일 때만 쓸 차례 알림의 울릴 시각은 목표 시각 정각 + 30분이다. 그 밖(`restricted`·`unknown`·iOS)은 정각이다.
- **FR-003**: 알림이 겨냥하는 날(그 날 몫)과 그 계산(하루 경계 00:00, 오전/오후 목표의 「그날/어제」)은 지연과 무관하게 정각 기준으로 같다.
- **FR-004**: 지연은 0 이상 60 미만의 값만 받는다. 범위 밖 값으로 계획을 만들려 하면 거부한다(시를 넘기면 날 계산이 어긋난다).
- **FR-005**: 쓸 차례 알림 예약은 그 날 일기 파일이 저장된 뒤에만 거둔다. 쓰기 시작, 쓰기 도중, 잡 시작에는 거두지 않는다(안전장치 — 085 불변). 지연이 있어도 이 규칙이 같다.
- **FR-006**: 일기 목록·설정을 읽지 못하면 아무것도 바꾸지 않는다는 085 RC6은 그대로다. 예외 상태를 읽지 못한 것은 맞추기를 멈추지 않고 `unknown`(정각)으로 간다.
- **FR-007**: 앱이 앞으로 돌아올 때(설정 목록에서 돌아온 경우 포함) 예외 상태를 다시 읽어 예약을 새 상태의 시각으로 다시 맞춘다. 이미 걸린 예약은 시각이 달라지면 새 시각으로 바뀐다(별도 이전 절차 없음).
- **FR-008**: 앱 훅과 헤드리스 백그라운드 태스크가 같은 조립으로 예외 상태를 읽는다.
- **FR-009**: 설정 배터리 행(안드로이드)에 꼬리표를 붙인다: `exempt`는 「허용됨」(기존 권한 행의 같은 문구), `restricted`는 「허용 안 함」, `unknown`은 꼬리표 없음. iOS는 변경 없다.
- **FR-010**: 설정 배터리 행의 꼬리표는 설정 목록에서 돌아올 때 다시 읽어 바뀐다. 따로 토스트를 띄우지 않는다.
- **FR-011**: 홈 안내는 안드로이드 && `restricted` && 앱 열기 자동 쓰기(앱을 직접 열어 시작된 쓰기와 쓸 차례 알림을 눌러 시작된 쓰기 — 홈의 「쓰기」 버튼으로 사람이 시작한 쓰기는 제외)가 시작됐고 그 쓰기가 **저장된 뒤**의 홈(쓴 날 화면)에서만 보인다. 쓰는 동안과 쓰기 실패 뒤에는 보이지 않는다. 저장 뒤에는 쓰는 중이 아닌 홈 화면이면 날을 옮겨도 닫거나 예외를 줄 때까지 보인다(앱을 껐다 켜면 다시 보이지 않고, 다음 자동 쓰기가 저장될 때 조건이 맞으면 다시 보인다). 한 줄 안내와 [설정 열기](기존 배터리 예외 설정 목록 열기)·[닫기]를 가진다. 문구는 「배터리 사용 제한을 풀어 두면 화면이 꺼진 채로도 일기를 써드릴 수 있어요」다(승인 2026-10-24, 보드 밖).
- **FR-012**: 홈 안내를 닫으면 닫은 시각을 한 파일에 남기고, 그 시각부터 7일 동안 안내를 띄우지 않는다. 앱 재시작 뒤에도 유지된다. 기록을 읽지 못하면 띄우지 않는다.
- **FR-013**: 설정 목록에서 예외를 주고 돌아오면 상태를 다시 읽어 안내가 사라진다.
- **FR-014**: 온보딩 배터리 카드는 바꾸지 않는다. 직접 예외 요청(`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`)을 되살리거나 권한을 새로 선언하지 않는다(065). 이 기능이 매니페스트 권한을 늘리지 않는다.
- **FR-015**: 새 화면 문구(홈 안내 한 줄과 [설정 열기]·[닫기] 버튼 중 기존에 없는 것)는 한국어 카탈로그에만 둔다(062). 꼬리표 「허용됨」·「허용 안 함」은 기존 권한 행의 문구(`permAllowed`·`permDenied`)를 그대로 쓴다. 새 문구는 골든 테스트의 추가 목록에 올린다. 일기 내용·감상을 담지 않는다.
- **FR-016**: 완성 알림을 보낼지 정하는 규칙, 자동 쓰기 판정(쓸 날·시도 창·재료·사흘), 시도·실패 기록의 갈래, 앱 열기 자동 쓰기 규칙(057·080·082·085 FR-023)은 바뀌지 않는다.
- **FR-017**: 설정 화면의 자동 쓰기 시각 미리보기·설정 보조 줄 문구(「○시쯤 … 휴대폰에 따라 늦게 알릴 때가 있어요」)는 바꾸지 않는다 — 30분 지연이 「쯤」과 어긋나지 않는다. 바뀌어야 한다고 드러나면 새 문구를 소유자와 정한다.
- **FR-018**: 085의 FR-019(「예외 여부를 읽는 새 통로를 들이지 않는다」)와 관련 문서 서술을 이 변경에 맞게 고친다.

### Key Entities

- **예외 상태**: `exempt` / `restricted` / `unknown` 중 하나. 읽은 순간의 값이며 저장하지 않는다(매번 읽는다).
- **알림 지연**: 예외 상태에서 정해지는 0 또는 30분. 쓸 차례 알림의 울릴 시각에만 더해진다.
- **홈 안내 기록**: 사용자가 안내를 닫은 시각 하나. 7일의 기준이다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 배터리 예외를 준 기기에서 목표 시각 직후 백그라운드 쓰기가 정각+30분 안에 저장되면, 그 날 쓸 차례 알림이 **한 번도 뜨지 않고** 완성 알림만 온다(실기기 1회 이상).
- **SC-002**: 같은 기기에서 쓰기를 완주시키지 않으면(잡을 돌리지 않음) 정각+30분에 쓸 차례 알림이 뜬다 — 일기 파일이 없는 날에 알림이 지워지는 일이 없다(실기기 1회 이상).
- **SC-003**: 예외 상태가 `restricted`·`unknown`이거나 iOS이면 쓸 차례 알림의 시각이 이 변경 전과 완전히 같다(계획 테스트로 전수 확인).
- **SC-004**: 예외를 끈 기기에서 설정 배터리 행이 「허용 안 함」이고, 설정 목록에서 예외를 주고 돌아오면 「허용됨」으로 바뀐다(실기기 1회).
- **SC-005**: 예외를 끈 기기에서 앱 열기 자동 쓰기가 저장되면 홈 안내가 보이고, 닫은 뒤 7일 안에는 다시 보이지 않으며, 예외를 주고 돌아오면 사라진다(실기기 1회, 7일은 시각을 옮겨 확인).
- **SC-006**: 이 변경이 안드로이드 매니페스트의 권한 목록을 늘리지 않는다(`dumpsys package`로 확인).
- **SC-007**: 예외 상태를 읽다 실패해도 쓸 차례 알림 예약은 걸린다(정각) — 읽기 실패로 하루도 알림이 비지 않는다.

## Assumptions

- 예외 상태를 읽는 안드로이드 API가 백그라운드 헤드리스 실행에서도 답한다. 답하지 못하면 `unknown`이라 이 기능의 효과가 그 기기에서 일어나지 않을 뿐 해롭지 않다. 구현 중 실기기에서 먼저 확인한다.
- 지연 30분은 잡 반복 간격 최대 15분과 쓰기 한도 10분의 합 25분을 덮는 사람이 정한 값이다(측정이 아니다).
- iOS는 백그라운드가 목표 시각 근처에 쓸 것이라는 신호가 없고(090·091) 쓸 차례 알림이 유일한 경로인 사용자가 있어 지연 0이다. 사람이 정한 판단이며 TestFlight 테스터 기록(로드맵 4번 할 일 1)에서 재검토한다.
- 실기기 확인은 SM-S901N 한 대다. 삼성 외 기기에서 같은 값을 주는지는 확인하지 않았다 — 기록에 남긴다.
- 안드로이드 14+ 부분 허용 등 다른 권한 꼬리표 규칙은 이 변경이 건드리지 않는다.
- 설정 앱에서 돌아오는 시점은 앱이 앞으로 돌아오는 이벤트로 잡는다.

## Out of Scope

- iOS TestFlight 기록 수집, 080 잔여(`load()` 경합·018 미리 준비·지운 날 재작성 등), 한도 타이머가 멈춘 시간, 078 잔여(로드맵 4번의 나머지).
- 하룻밤 소크: 이 기능의 실기기 확인과 같은 상태이지만 결과가 늦게 나오므로 완료 조건에 넣지 않고 구현 뒤 별도 단계로 돌린다.
- 쓰기 시작 시 쓸 차례 알림을 거두는 방식: 쓰기 도중 프로세스가 죽거나 얼 때 일기도 알림도 없는 날이 생겨 하지 않는다(설계문서 §2).
- 쓸 차례 알림 시각의 사용자 설정, 직접 예외 요청 권한, 포그라운드 서비스.
- 재부팅·업데이트·강제 중지로 알림 예약이 사라지는 문제(로드맵 4번 할 일 2번 하위 항목).
