# 계약: 내려받기 — 시작·진행·중단·재개·공간

**대응 요구사항**: FR-010~FR-020a

**구현 위치**: `src/models/acquisition.ts`, `src/models/port.ts`

---

## 이 계약이 지키는 것

헌법 「로스터」의 **"사용자가 고른 캐릭터의 모델만 내려받는 구조여야 한다(MUST)"** 가 여기서
성립한다. 구조의 문제이므로 나중에 고칠 수 없다.

**GB 단위 파일을 다루는 유일한 자리**이기도 하다. 002의 저장이 수십 KB였던 것과 다르며,
그래서 진행·중단·재개·공간이 부가 기능이 아니라 본체다.

---

## 모양

```
prepare(character) → 시작하거나 거부한다
pause(character)   → 멈춘다. 이어받을 수 있는 상태로 남긴다
progress 구독      → 캐릭터 단위 진행도
```

**`prepareAll()`을 두지 않는다**(FR-010, FR-011). 있으면 헌법 로스터가 금지한 "전부 받아놓고
고르게 하기"가 한 줄로 가능해진다. `roster.ts`에 `allAssets()`를 두지 않은 것과 같은 판단이다.

---

## 시작하기 전에 보는 것 — 순서가 중요하다

| 순서 | 확인 | 실패하면 | 근거 |
| --- | --- | --- | --- |
| 1 | 다른 캐릭터를 받는 중인가 | `busy` (무엇을 받는 중인지 알린다) | FR-020 |
| 2 | 이미 `ready`인가 | 시작하지 않는다 (할 일이 없다) | — |
| 3 | 공간이 여유까지 있는가 | `insufficient-space` | FR-019, FR-019b |
| 4 | 이어받을 것이 있는가 | 있으면 이어받고 없으면 처음부터 | FR-015, FR-016 |

**3번이 4번보다 앞이다.** 이어받기도 공간을 쓰므로 먼저 본다.

**공간은 예상 크기의 1.15배를 요구한다**(research.md §3). 딱 맞으면 시작하지 않는다
(FR-019b) — 여유 0으로 받으면 안드로이드의 공간 확보 대상이 되어 방금 받은 모델이 지워질 수
있고, 그것은 우리가 만든 실패다. **이 비율은 잠정이며 실기기 실측으로 확정한다**(FR-019c).

## 한 번에 하나 (FR-020)

진행 중인 작업을 **메모리에 하나** 들고, 뒤의 요청은 거부한다.

**저장소에 남기지 않는다.** 002의 파이프라인이 `running` Set을 메모리에만 둔 것과 같은
이유이며, 남기면 앱이 죽었을 때 **영원히 진행 중인 캐릭터**가 생긴다.

**"진행 중"과 "중단됨"은 다른 것이다:**

| | 어디에 | 앱이 죽으면 |
| --- | --- | --- |
| 진행 중 표시 | 메모리 | 사라진다 (정상) |
| 중단 상태 | 기기 | 남는다 (이어받기의 근거) |

이 구분이 흐려지면 002가 피한 함정에 다시 빠진다.

**거부에서 빠져나갈 길이 있어야 한다**(FR-020a). 받던 것을 멈추면(FR-014) 새 요청이 통한다.
거부만 하고 멈출 수 없으면 사용자가 갇힌다.

---

## 진행률 — 원칙 III·IV의 위험 지점

**밖으로 나가는 것은 캐릭터와 `0~1`(또는 모름)뿐이다**(FR-013a).

**담지 않는 것과 그 이유**:

| 담지 않는 것 | 왜 |
| --- | --- |
| `bytesWritten` / `totalBytes` | **`totalBytes`가 곧 모델 크기다** (원칙 III) |
| 파일 이름·파일 개수 | 모델 구성이 드러난다 (원칙 III) |
| 경과 시간·초당 속도 | **모델 비교의 시작점이다** (원칙 IV, FR-034) |
| 남은 시간 추정 | 위와 같다. 보여주고 싶어도 담지 않는다 |

앞의 둘은 명세에 있었고, **뒤의 둘은 설계 중 찾았다** — 진행률을 다루다 보면 자연스럽게
계산하게 되는 값들이다.

**`totalBytes`가 `-1`일 수 있다**(research.md §1). 서버가 `Content-Length`를 주지 않는
경우다. 그때 **백분율을 지어내지 않는다**(원칙 V) — 매핑의 예상 크기로 갈음하되, 그것과도
어긋나면 "모름"으로 둔다. 모르는 것을 그럴듯한 숫자로 채우는 것이 원칙 V 위반이다.

## 완료 판정 (FR-018, FR-001b)

**받은 양이 예상 크기에 이르러야 "받았음"이다.** 미치지 못하면 `partial`이지 완료가 아니다.

완료 후 **곧바로 검증한다**(FR-021a). 검증을 통과해야 `ready`가 되며(FR-007), 검증 전에
사용자에게 "준비됐다"고 말하지 않는다.

**실패한 내려받기가 "받았음"으로 판정되지 않는다**(FR-018) — 네트워크가 끊긴 것과 다 받은
것이 같은 상태가 되면 그 거짓이 다음 기능으로 흘러간다.

---

## 시작은 사용자가 (FR-012)

**앱이 저절로 시작하지 않는다.** GB 단위 데이터를 사용자 모르게 쓰지 않는다.

이동 통신인지 Wi-Fi인지는 판정하지 않는다(범위 밖). 대신 **명시적으로 눌러야만 받아지므로**
모르는 사이에 쓰이지 않는다.
