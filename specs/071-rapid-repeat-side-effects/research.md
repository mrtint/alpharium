# Research: 작명·온보딩·쓰기·그만두기 빠른 반복 부작용 확인

2026-10-10. 이 문서는 (1) 코드를 읽어 만든 경로 지도와 **가설**(관측 전이다), (2) 조작·관측 방식의 결정을 담는다.
**가설은 증상이 아니다** — 실기기에서 관측되기 전에는 부작용 목록에 올리지 않는다(원칙 V, FR-004).

## R1 — 반복 조작의 모양

- **Decision**: 시나리오 다섯을 여섯 간격(0ms·300ms·1.5초 직후·1.6초·3초·10초)으로 돌린다.
  - **S-A** 쓰기 → 그만두기 → 쓰기 (기본)
  - **S-B** 하단 바 잠금(`WRITING.barLockMs` 1.5초) 안의 연타와 직후의 탭
  - **S-C** 쓰기 직후 홈 버튼으로 내렸다 올림 / 설정을 열었다 닫음
  - **S-D** 같은 날 두 번 쓰기(이미 쓴 날의 다시 쓰기 = 덮어쓰기 확인 경로)
  - **S-E** 작명·온보딩 반복 — 확정 버튼 연타, 단계 도중 앱을 내렸다 올림, `onboarding.json` 완료 플래그를 되돌려 다시 진입(FR-013)
- **Rationale**: 스펙 FR-001·FR-002. 간격은 하단 바 잠금 경계(1.5초)를 사이에 둔다 — 잠금이 의도한 대로 연타를 막는지와, 잠금 직후 첫 탭이 정상인지를 가르는 값이다.
- **Alternatives**: Maestro 흐름 — 간격 제어가 거칠고 흐름당 약 35초 기기 정지라 0~300ms 간격이 재현되지 않는다. 기각.

## R2 — 코드를 읽어 세운 가설 (관측 전)

읽은 곳: `DiaryHomeScreen.tsx`(`generate` 758~839행, `cancel` 1037~1044행), `pipeline.ts`(`run` 206~243행, `runStages` 저장 327~371행), `lock-port.ts`.

- **H1 — `cancelled`/`running`/`inFlight`가 한 벌이라 새 쓰기가 옛 쓰기의 상태를 덮는다.**
  `cancel()`은 `cancelled=true` → `await stop()` → 목록으로 돌아간다. 그 사이·직후에 다시 「쓰기」를 눌러 `generate()`가 `cancelled=false`로 되돌리면,
  **먼저 중단된 `generate()`의 `pipeline.run`이 뒤늦게 돌아올 때** `if (cancelled.current) return;`이 거짓이라 옛 쓰기가 자기 결과를 처리한다(실패 기록·`refresh`·토스트).
  그 `finally`가 `running.current=false; inFlight=null`을 새 쓰기가 도는 중에 세운다. 새 쓰기의 `pipeline.run`은 옛 쓰기의 잠금이 아직 놓이지 않았다면 `already-running`을 받는다.
- **H2 — 저장 단계에 취소 점검이 없다.** `runStages`는 `deps.backend.generate` 뒤 곧바로 `extractTitle` → `store.save`로 가고 취소를 보지 않는다.
  화면은 `pipeline.run`이 끝난 뒤에야 `cancelled`를 본다 — 그만두기가 생성 완료와 저장 사이에 오면 **일기 파일이 이미 저장된 채 화면은 그만둔 것으로 보인다.**
  Clarification(그만두기가 이긴다)과 어긋나는 후보 지점이다. **경계(소유자 확정 2026-10-10):** 저장을 시작하기 직전까지만 취소를 확인하고, 저장 I/O가 시작된 뒤의 취소는 일기를 남긴다 — `DiaryStore`에는 하루 단위 삭제가 없고, 다시 쓰기에서 저장 뒤에 지우면 옛 일기까지 잃는다(002 FR-023b — 기존 일기 보존).
- **H3 — 잠금 해제는 `finally`의 `release().catch(() => {})`다.** 해제가 실패해도 삼켜지고 stale(6분)로만 회복된다.
  또 `acquireLock`은 `running.has()` 판정과 `running.add()` 사이에 `await`가 있어 같은 인스턴스에서 매우 빠른 두 번째 `run()`이 `running` 검사를 통과할 수 있는 틈이 있다(파일 잠금이 막는다면 무해).
- **H4 — `stop()`이 본문 엔진보다 먼저 비전 엔진을 멈추고, 멈춘 뒤 `unload()`가 `finally`에서 돈다.** 중단이 모델 적재 도중이면(`engine.load` 대기) 중단이 먹히는 시점과 `unload`가 겹쳐 모델이 열린 채 남거나 이중 적재될 수 있다(`on-device.ts` 403~408·671~684·759행).

- **H5 — `.json.writing` 찌꺼기.** `writeAtomically`는 임시 파일을 만들고 쓴 뒤 대상을 지우고 옮긴다(`store.ts` 418~429행). 옮기기 전에 앱이 죽거나 예외가 나면 `.json.writing`이 남을 수 있다 — 반복 중 앱을 내렸다 올림(S-C)·강제 종료와 겹칠 때 관측한다.

**보강(코드 읽기 2차)**: 어댑터(`on-device.ts`)의 `cancel` 객체는 `let`이라 새 `generate`가 시작되면 새 객체로 교체되고(548행), 옛 생성은 현재 `cancel`을 읽는다(681·739행) — H1이 화면의 ref뿐 아니라 어댑터에도 있을 수 있다. 중단 신호는 모델 적재 직후와 제목 질문 직후 두 곳에서만 확인되고, 제목 이후 `store.save`까지는 확인이 없다(H2). 이 두 가지는 **코드를 읽은 사실**이고 그 결과가 실제로 증상이 되는지는 관측 대상이다.

각 가설은 관측 때 **먼저 볼 점검 항목**을 정해 줄 뿐이다. 관측이 가설과 다른 증상을 보이면 가설이 아니라 관측을 따른다.

## R3 — 기기 상태 되돌리기

- **Decision**: 첫 한 번은 `pm clear` → 작명 → 온보딩 → 모델 내려받기 → 첫 일기 완주(첫 적재·첫 내려받기 경로). 이후 반복은 모델·일기를 보존하고 **일기 폴더의 그 날 파일 삭제 + `preferences/write-failures.json` 삭제 + 잠금 파일 삭제**로 점검 기준을 되돌린다
  (`run-as`, 파일 직접 접근 — AGENTS 「도구 사용법」 4의 JSON 쓰기 주의). 작명·온보딩 단계 자체의 반복은 `onboarding.json` 플래그를 고쳐 재현한다.
- **Rationale**: 소유자가 `pm clear`에 동의했다(2026-10-10). 모델 재다운로드(약 2GB)를 매 반복마다 치르지 않는다.
- **Alternatives**: 매번 `pm clear` — 시간 낭비. 기각.

## R4 — 관측 수단

- **Decision**: `adb logcat -v time`(llama 적재·해제·예외), `run-as`로 파일 읽기, `uiautomator dump`(화면 상태·좌표), `dumpsys meminfo`(반복 전후), `adb shell input tap`(조작).
  릴리스 아닌 debug 빌드라 `run-as`가 된다. 재부팅 직후 잠금 해제 전에는 `run-as`가 실패하므로 기기 잠금이 풀려 있어야 한다(AGENTS 「도구 사용법」 2).
- **Rationale**: 앱 코드를 바꾸지 않고 읽을 수 있는 것만 읽는다(원칙 IV). 생성 중 반복 탭이라 `uiautomator dump`가 「could not get idle state」로 실패할 수 있다 — 그때는 `screencap`.
- **Alternatives**: 앱에 진단 로그 추가 — 원칙 IV 위반 소지(측정 장치). 결함을 고칠 때 필요한 최소한의 로그가 아니면 넣지 않는다.

## R5 — 방어 수단(타이밍 결함)

- **Decision**: 기기 없는 테스트로 재현 가능한 결함(상태 갱신 순서 — H1·H2 류)은 화면 테스트(`.tsx`)나 순수 로직 테스트로 잠근다. jest가 구조적으로 못 잡는 순수 타이밍(실제 `llama.rn` 중단 시점 — H4)은
  소스 계약 테스트로 구조를 잠그고(기본), e2e 반복 시나리오로는 옮기지 않는다(FR-008, 소유자 결정 2026-10-10).
- **Rationale**: 054의 `toWriting()` 키 계약·043의 `busyRef` 같은 선례가 있다. 위반 주입은 치환이 실제로 적용됐는지 먼저 단언한다(AGENTS 「테스트 작성의 함정」).

## R6 — 쓰기가 끝까지 가는 경로

반복 중 대부분의 쓰기는 중단으로 끝난다. 저장·알림·완료 홈까지 가는 정상 경로는 별도로 한 번 확인한다(스펙 Assumptions). 간격 10초 시나리오에서 쓰기를 중단하지 않고 끝까지 둔다.
