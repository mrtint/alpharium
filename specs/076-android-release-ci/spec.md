# Feature Specification: 안드로이드 release 빌드·서명·Play 업로드를 CI로 — 로컬 19분 빌드 없이

**Feature Branch**: `076-android-release-ci`

**Created**: 2026-10-11

**Status**: Draft

**Input**: User description: "docs/superpowers/specs/2026-10-11-android-release-ci-design.md 설계문서를 입력으로: GitHub Actions 수동 워크플로(android-release.yml)로 안드로이드 prebuild → 서명 release AAB → 서명 확인 → Play 내부 테스트 트랙 업로드까지, 비밀은 Environment android-release에만, 직접 쓴 Node 업로드 스크립트, 계약 테스트, AGENTS.md 절 개정."

## 근거와 원본

- **설계**: `docs/superpowers/specs/2026-10-11-android-release-ci-design.md`(저장소 소유자 승인, 2026-10-11).
- **로드맵 과제**: 「안드로이드 release 빌드·서명·보관을 CI로 — 로컬 19분 빌드 없이」(Tier 3: 서명·업로드). iOS 쪽 짝은 075(`.github/workflows/ios-release.yml`).
- **문제**: 안드로이드 release 빌드·서명은 소유자의 개발 기계에서만 된다. 빌드가 약 14분(AAB)~19분(APK)이고 서명 키(`~/.pocketlog-signing/pocketlog.jks`)가 그 기계에만 있다.
- **입력**: 072의 ubuntu 러너 실측(4코어 16GB, debug arm64 gradle 296~601초, 최대 메모리 약 12GB). release 최적화 컴파일은 **잰 적이 없다.**
- **범위 밖**: `src/` 변경, 안드로이드 minify/R8 활성화(꺼진 채 둔다), 새 의존성, 손으로 설치할 APK의 CI 빌드, `versionCode` 자동 올림(사람이 커밋한다), 아티팩트 보관, iOS.

## 용어

- **릴리스 워크플로**: 소유자가 손으로 시작해 빌드·서명·확인·업로드까지 끝내는 CI 워크플로 하나(`android-release.yml`).
- **보호 환경**: 서명·업로드 비밀이 들어 있고 실행 전에 소유자의 승인을 받는 `android-release` 환경.
- **처리 통과**: 업로드된 빌드가 Play Console 내부 테스트 트랙에 해당 `versionCode`로 나타나 테스터가 받을 수 있는 상태(업로드 성공과 다르다 — 075의 교훈).
- **업로드 키**: 소유자의 `pocketlog.jks`. Play 앱 서명을 쓰므로 사용자 기기에는 Google이 보관한 앱 서명 키로 다시 서명된 앱이 간다.

## Clarifications

### Session 2026-10-11 (설계 단계 소유자 결정)

- Q: 업로드 키와 비밀번호를 GitHub 보호 환경 secrets에 올려도 되는가? → A: 올린다. 유출이 의심되면 Play Console에서 업로드 키를 재설정한다(며칠 걸림).
- Q: 결과물은 어디에 남기는가? → A: Play 내부 테스트 트랙에 바로 올리고 아티팩트로 남기지 않는다. 서비스 계정 JSON이 새 비밀이다. 소유자는 서비스 계정을 만들 수 있고 앱 레코드와 내부 테스트 트랙이 이미 있다.
- Q: 손으로 설치할 APK도 CI에서 만드는가? → A: 아니다. AAB만 만든다. APK는 로컬 절차(대안)로 남는다.
- Q: Play 내부 테스트 업로드까지 이번 과제의 완료 조건인가? → A: 그렇다.
- Q: 업로드 방식은? → A: 직접 쓴 Node 스크립트(새 의존성 0, 서드파티 Action 없음).

### Session 2026-10-11 (speckit-clarify)

- Q: CI가 올린 빌드를 테스터에게 바로 공개하는가, 초안으로만 올리는가? → A: 바로 공개한다(내부 트랙에 완료 상태로 올림). 앱 상태 때문에 공개가 거부되면 소유자와 초안으로 바꿀지 정한다.
- Q: 서명 키가 진짜 업로드 키인지 사람이 대조하는가, CI가 자동 비교하는가? → A: 기대 SHA-256 지문을 저장소에 공개 값으로 두고 CI가 비교한다. 다르면 업로드 전에 실패한다. 첫 지문은 소유자가 로컬 키에서 뽑아 커밋한다.

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 개발 기계 없이 서명된 빌드를 Play 내부 테스트에 올린다 (Priority: P1)

저장소 소유자가 개발 기계의 19분 빌드와 키 파일 없이, GitHub에서 릴리스 워크플로를 시작하고 승인하면 서명된 release AAB가 만들어져 Play 내부 테스트 트랙에 올라간다.

**Why this priority**: 이 과제의 존재 이유이자 완료 조건이다.

**Independent Test**: `versionCode`를 올려 커밋한 `main`에서 릴리스 워크플로를 한 번 실행하고 승인한 뒤, 끝까지 성공하는지, Play Console 내부 트랙에 새 `versionCode`가 보이는지, 그 트랙에서 받은 앱이 전용 기기에서 Metro 없이 도는지 본다.

**Acceptance Scenarios**:

1. **Given** 비밀 넷과 보호 환경이 등록되어 있고 `android.versionCode`가 지난 업로드보다 크다, **When** 소유자가 `main`에서 시작하고 승인한다, **Then** 빌드·서명 확인·업로드가 모두 성공하고 단계별 걸린 시간과 최대 메모리가 실행 요약에 남는다.
2. **Given** 업로드가 성공했다, **When** Play Console 내부 테스트 트랙을 본다, **Then** 새 `versionCode`의 릴리스가 올라와 있고 테스터가 받을 수 있다.
3. **Given** 내부 테스트로 받은 앱, **When** 전용 기기에 설치해 연다, **Then** Metro 없이 홈이 뜨고 모델 내려받기와 일기 쓰기 경로가 돈다(원칙 V).
4. **Given** 워크플로가 끝났다(성공이든 실패든), **Then** 러너에는 키스토어 파일이 남지 않고 저장소에도 서명된 결과물이 남지 않는다.

---

### User Story 2 - 서명이 debug 키가 아님을 CI가 스스로 확인한다 (Priority: P1)

빌드가 끝나면 AAB의 서명 인증서를 읽어, debug 키(`CN=Android Debug`)이거나 읽을 수 없거나 저장소에 둔 기대 SHA-256 지문과 다르면 업로드 전에 실패한다. 서명 지문은 실행 요약에도 남는다.

**Why this priority**: 키스토어가 없을 때 조용히 debug 키로 서명되는 것이 이 저장소에서 가장 비싼 실패 유형이다(`with-release-signing.js` 주석). 잘못 서명된 빌드가 Play에 닿으면 안 된다.

**Independent Test**: 서명 확인 단계가 인증서 소유자·지문 문자열을 읽어 판정하는 함수·스크립트를 테스트가 debug 키·빈 출력·지문 불일치·정상 출력으로 각각 확인한다.

**Acceptance Scenarios**:

1. **Given** 서명된 AAB, **When** 서명 확인 단계가 돈다, **Then** 인증서 소유자와 SHA-256 지문이 요약에 쓰이고 통과한다.
2. **Given** debug 키로 서명된 AAB(또는 서명이 없는 AAB), **When** 서명 확인 단계가 돈다, **Then** 업로드 전에 실패한다.
3. **Given** 다른 키(예: 옛 `alpharium.jks`)로 서명된 AAB, **When** 서명 확인 단계가 돈다, **Then** 기대 지문과 달라 업로드 전에 실패하고 두 지문이 요약에 보인다.
4. **Given** 서명 확인이 실패했다, **Then** 업로드 단계는 실행되지 않는다.

---

### User Story 3 - 비밀이 퍼블릭 저장소에서 새지 않는다 (Priority: P1)

저장소가 퍼블릭이어도 업로드 키·배포 권한 비밀은 소유자가 승인한 `main`의 수동 실행에서만 쓰인다. 포크·PR·다른 브랜치·자동 트리거는 비밀에 닿지 못하고, 실행 결과물이나 로그로도 새지 않는다.

**Why this priority**: 키와 서비스 계정 JSON이 퍼블릭 저장소의 CI에 있다는 사실 자체가 가장 큰 위험이다. 서비스 계정은 앱 배포 권한을 가진다.

**Independent Test**: 워크플로 파일과 업로드 스크립트를 읽는 계약 테스트가 트리거·권한·비밀 참조·산출물·출력 규칙을 잠그고, 각 규칙을 어긴 위반 주입이 테스트 실패로 뒤집힌다.

**Acceptance Scenarios**:

1. **Given** 워크플로 파일, **When** 트리거를 읽는다, **Then** 수동 시작 하나뿐이다(PR·push·예약 없음).
2. **Given** 워크플로 파일, **When** 비밀 참조를 센다, **Then** 허용된 넷뿐이고 보호 환경의 잡에서만, 단계의 환경값 자리에서만 참조된다(`run` 본문 보간·잡 수준 환경값·`toJSON(secrets)` 금지).
3. **Given** 워크플로 파일, **When** 산출물·로그 규칙을 읽는다, **Then** 결과물을 아티팩트로 남기지 않고, 캐시를 쓰지 않고, 명령 추적(`set -x`)으로 값을 찍지 않으며, 외부 Action은 `actions/*`뿐이다.
4. **Given** 업로드 스크립트, **When** 어떤 입력으로 실패하든, **Then** 서비스 계정 JSON·토큰·개인 키를 출력하지 않고 HTTP 상태와 API 오류 사유만 출력한다.
5. **Given** `main`이 아닌 브랜치, **When** 릴리스 워크플로를 시작한다, **Then** 보호 환경이 거부한다.
6. **Given** 위 규칙 중 하나를 어긴 변경(예: `pull_request` 추가), **When** 테스트를 돌린다, **Then** 테스트가 실패한다.

---

### User Story 4 - 비밀이 빠졌거나 번호가 틀리면 빨리 안다 (Priority: P2)

필수 비밀이 비었거나 `versionCode`가 올바르지 않으면 긴 빌드를 돌리기 전에 원인이 보이는 메시지로 실패한다.

**Why this priority**: 설정 실수가 가장 흔한 첫 실패다. 빌드 뒤에야 알면 시간을 낭비한다.

**Independent Test**: 비밀 하나를 비운 채 시작하면 사전 점검 단계에서 어느 비밀이 비었는지 말하고 끝난다.

**Acceptance Scenarios**:

1. **Given** 필수 비밀 하나가 비어 있다, **When** 시작한다, **Then** 이름을 밝히며 빌드 전에 실패한다(값은 찍지 않는다).
2. **Given** `android.versionCode`가 정수가 아니다, **When** 시작한다, **Then** 빌드 전에 실패한다.
3. **Given** 같은 `versionCode`가 Play에 이미 있다, **When** 업로드한다, **Then** Play의 거부가 숨겨지지 않고 그대로 실패로 보인다.
4. **Given** 업로드가 중간에 실패했다, **Then** 열려 있던 Play 편집은 커밋되지 않고 버려진다(트랙에 반쪽 릴리스가 남지 않는다).

---

### User Story 5 - 절차 문서가 새 경로를 기본으로 말한다 (Priority: P3)

AGENTS.md의 「release 빌드·서명·Google Play」 절이 이 경로를 기본으로 설명하고 로컬 절차는 대안으로 남는다. 비밀 등록·보호 환경 설정 절차가 문서에 있다.

**Why this priority**: 문서가 옛 절차(로컬 19분)만 말하면 다음 사람이 새 경로를 모른다.

**Independent Test**: 문서만 읽고 비밀 등록부터 실행·확인까지 따라갈 수 있다.

**Acceptance Scenarios**:

1. **Given** 개정된 AGENTS.md, **When** 해당 절을 읽는다, **Then** CI 경로가 기본이고 로컬 절차는 대안이며, 앞 절차가 주석으로 덧대어지지 않고 고쳐져 있다.
2. **Given** 이 기능의 quickstart, **When** 읽는다, **Then** 비밀 넷의 출처, 보호 환경 설정(필수 리뷰어·배포 브랜치), 키스토어를 한 줄 base64로 만드는 법, 기대 지문을 뽑아 커밋하는 법이 있다.

### Edge Cases

- 같은 워크플로를 연달아 시작하면? 동시에 하나만 돌고 앞선 실행은 취소되지 않는다(업로드 도중 취소로 반쪽 상태가 되지 않게).
- 러너 메모리 부족으로 release 컴파일이 죽으면? 실패로 끝나고 정리 단계는 그래도 실행된다. 단계별 시간·메모리 기록으로 어느 단계인지 보인다. 이 경우 빌드 병렬도를 낮춰 이 과제 안에서 통과시킨다(FR-015).
- 기대 지문 파일이 없으면? 서명 확인이 실패해 업로드에 닿지 않는다. 그래서 첫 실행 전에 소유자가 지문을 뽑아 커밋해야 한다.
- 키스토어 비밀번호가 틀리면? 빌드 단계에서 서명 실패로 끝난다(업로드에 닿지 않는다).
- 서비스 계정 권한이 부족하거나 앱 상태 때문에 릴리스 상태가 거부되면? 업로드 단계가 Play의 사유와 함께 실패하고 편집은 버려진다.
- `ubuntu-latest` 이미지가 바뀌면(2026-10-19부터 Ubuntu 26 안내)? 코드 변경 없이 실패할 수 있다 — 알려진 위험이며 실행마다 러너 사양을 요약에 남겨 비교할 수 있게 한다.
- 포크가 워크플로 파일을 고쳐 PR로 올리면? 비밀은 PR에서 보호 환경 밖이라 닿지 못한다.
- 중간 단계가 실패하면? 정리 단계는 성공·실패와 무관하게 실행된다.

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 시스템은 개발 기계 없이 소유자가 수동으로 시작하는 워크플로 하나로 「네이티브 프로젝트 생성 → 서명 release AAB 빌드(arm64 하나) → 서명 확인 → Play 내부 테스트 트랙 업로드」를 끝까지 수행해야 한다.
- **FR-002**: 릴리스 워크플로의 시작 방법은 수동 하나뿐이어야 한다. PR·push·예약 트리거를 두지 않는다(MUST NOT).
- **FR-003**: 서명·업로드 비밀은 보호 환경에만 있고, 보호 환경은 소유자의 승인을 요구하며 배포 브랜치를 `main`으로 제한해야 한다.
- **FR-004**: 워크플로가 참조하는 비밀은 허용 목록의 넷(`ANDROID_KEYSTORE_BASE64`·`ANDROID_KEYSTORE_PASSWORD`·`ANDROID_KEY_PASSWORD`·`PLAY_SERVICE_ACCOUNT_JSON`)뿐이어야 한다. 키 별칭은 비밀이 아니다(이미 선언에 있다).
- **FR-005**: 비밀은 필요한 단계의 환경값으로만 넘기고, 명령 추적·값 출력으로 로그에 찍지 않아야 한다. 키스토어는 러너 위 소유자만 읽는 권한으로 복원하고 비밀번호는 파일에 쓰지 않는다. 임시 파일은 정리 단계에서 지운다.
- **FR-006**: 서명 설정은 기존 `plugins/with-release-signing.js` 선언을 그대로 쓰고(워크플로가 `android/`를 고치지 않는다), 비밀번호는 빌드 단계의 환경값으로만 gradle에 전달한다. 빌드는 `NODE_ENV=production`과 arm64 단독 옵션을 지킨다.
- **FR-007**: 서명 확인 단계는 AAB의 인증서 소유자를 읽어 `CN=Android Debug`이거나 비어 있거나 저장소에 둔 기대 SHA-256 지문(공개 값)과 다르면 실패하고, 읽은 지문을 요약에 남겨야 한다. 기대 지문 파일이 없거나 형식이 틀려도 실패한다(건너뛰지 않는다). 기대 지문 파일을 바꾸는 것은 키를 바꾸는 결정이며 사람이 커밋한다. 이 단계가 통과해야만 업로드가 실행된다.
- **FR-008**: 결과물(AAB 등)을 아티팩트로 남기지 않아야 한다(퍼블릭 저장소라 누구나 내려받는다). 캐시도 쓰지 않는다(서명 키가 열린 빌드).
- **FR-009**: 시작 직후 사전 점검이 필수 비밀이 모두 비어 있지 않은지와 `android.versionCode`가 정수인지 확인하고, 틀리면 빌드 전에 원인을 밝히며 실패해야 한다. 중복 `versionCode`의 확인은 하지 않는다(Play의 거부를 그대로 보인다).
- **FR-010**: 동시에 하나만 실행되어야 하고, 진행 중인 실행을 새 시작이 취소하지 않아야 한다.
- **FR-011**: 단계별 걸린 시간, 빌드 중 최대 메모리 사용량, 러너 사양(OS·CPU·메모리·Java 버전)을 실행 요약에 남겨야 한다(072 방식).
- **FR-012**: Play 업로드는 직접 쓴 스크립트로 하며 새 의존성과 서드파티 Action을 쓰지 않는다. 서비스 계정 JSON은 환경값으로만 읽는다. 실패 시 열린 편집을 버리고, 어떤 경우에도 비밀·토큰을 출력하지 않는다. 업로드 대상은 내부 테스트 트랙이고, 릴리스는 테스터가 바로 받을 수 있는 완료 상태로 올린다(초안으로 두고 사람이 확정하지 않는다). 앱 상태 때문에 이 상태가 거부되면 실패로 보이고, 초안으로 바꿀지는 소유자가 정한다.
- **FR-013**: 계약 테스트가 워크플로 파일의 FR-002~005·008·010과 정리 단계의 항상 실행·마지막 위치를 잠그고, 업로드 스크립트는 네트워크 대역으로 호출 순서·실패 시 편집 폐기·출력에 비밀 없음을 잠근다. 072의 `native-build.yml` 계약 테스트는 그 파일에만 적용되며 이 기능은 별도 파일·별도 테스트로 둔다.
- **FR-014**: AGENTS.md의 「release 빌드·서명·Google Play」 절을 이 경로 기본으로 개정하고(로컬 절차는 대안으로 유지), 비밀 등록·보호 환경 설정 절차를 quickstart에 남겨야 한다.
- **FR-015**: 실제 한 번의 실행으로 서명 확인, Play 트랙 반영, 전용 기기 설치·구동까지 확인해야 한다(기기 없는 테스트로 갈음하지 않는다, 원칙 V). release 컴파일이 러너 메모리 부족으로 실패하면 병렬도를 낮춰 이 과제 안에서 통과시키고, 값과 근거를 quickstart에 실측과 함께 남긴다(안 잰 값을 쓰지 않는다).

### Key Entities

- **서명·배포 비밀 묶음**: 업로드 키스토어(한 줄 base64)와 두 비밀번호, Play 서비스 계정 JSON. 소유자가 보호 환경에 등록하며 코드가 만들지 않는다.
- **릴리스 실행**: 한 번의 수동 시작. 입력은 `main`의 `expo.version`·`android.versionCode`, 출력은 Play 내부 테스트 트랙의 릴리스 하나(처리 통과 여부는 실행 밖에서 확인).

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 소유자는 개발 기계에 손대지 않고 한 번의 시작·승인만으로 서명된 빌드를 Play 내부 테스트 트랙에 올릴 수 있다.
- **SC-002**: 이 경로로 올린 빌드가 내부 트랙에 나타나고 전용 기기에서 Metro 없이 홈이 뜨며 일기를 쓸 수 있다.
- **SC-003**: 필수 비밀이 비었을 때 시작 후 1분 안에 원인을 밝히고 실패한다(빌드까지 가지 않는다).
- **SC-004**: `main`이 아닌 브랜치·포크·PR에서 서명·배포 비밀에 닿는 경로가 0이며, 계약 위반 주입(트리거 추가, 허용 밖 비밀·직접 보간·`toJSON(secrets)`·잡 수준 환경값, 아티팩트·캐시 추가, 명령 추적, 외부 Action 추가, 정리 단계 제거·뒤에 다른 단계 추가, 보호 환경 제거, 권한 확대, 동시 실행 취소)이 각각 테스트 실패로 뒤집힌다.
- **SC-005**: CI가 만든 AAB의 서명 인증서 소유자가 `CN=Android Debug`가 아니고, 그 SHA-256 지문이 소유자가 로컬 `pocketlog.jks`에서 직접 뽑아 커밋한 기대 지문과 같다.
- **SC-006**: 실행이 끝난 뒤(성공·실패 모두) 러너에 키스토어 파일이 남지 않았음을 실행 로그로 확인한다.
- **SC-007**: 문서만 읽고 비밀 등록부터 실행·확인까지 따라갈 수 있다(AGENTS.md 개정 + quickstart).

## Assumptions

- 소유자는 업로드 키를 보호 환경 secrets에 올리기로 정했다(2026-10-11). 에이전트는 키 내용을 열지 않고, 등록 명령은 소유자가 실행한다.
- 기대 지문의 첫 값은 소유자가 로컬 키에서 뽑는다(에이전트는 키 파일을 열지 않는다). 지문은 공개 정보라 퍼블릭 저장소에 둘 수 있다.
- 소유자는 Play 서비스 계정을 만들고 앱 배포 권한을 줄 수 있으며 앱 레코드와 내부 테스트 트랙이 이미 있다(소유자 확인, 2026-10-11). 서비스 계정 권한이 내부 트랙 업로드에 충분한지, 앱 상태에서 `completed` 릴리스가 받아들여지는지는 첫 실행에서 안다.
- ubuntu 러너(4코어 16GB)에서 llama.rn을 포함한 release 최적화 컴파일이 메모리 안에서 끝난다는 보장은 없다 — 미실측이며 첫 실행이 곧 측정이다.
- `versionCode` 올림은 사람이 커밋한다. 중복 방지는 Play의 거부에 맡긴다.
- 첫 실행은 실패할 수 있다고 가정한다(075의 선례). 성공은 실행 결과를 직접 확인한 뒤에만 말한다.
- 워크플로 파일이 `main`에 머지된 뒤에야 실제 실행이 가능하다.
