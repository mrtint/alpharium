# 영수증·문서 사진 — 재료에서 거르고 정직하게 모른다고 쓴다 (설계)

로드맵 「진행 예정 과제」의 같은 제목 항목을 구체화한다. 소유자 결정(2026-11-23): 추론을 더 쓰지 않는 방안 1(메타데이터)·방안 2(캡션 글)만 한다.

## 목적

영수증·문서·화면 캡처가 든 날의 일기가 사진에 없는 금액·날짜·사연을 늘어놓지 않게 한다. 그런 사진은 재료(캡션)에서 빼고, 그런 사진뿐인 날은 「글자가 적힌 사진이 있었으나 내용은 읽지 못했다」고만 쓴다.

## 원인 가름 (2026-11-24, SM-S901N, dev, 실제 사진)

표본: 소유자가 준 실제 사진 11장(카메라로 찍은 의료비 영수증·세부내역서 9장, 앱 화면 스크린샷 2장). 사진은 `scripts/samples/documents/`에 로컬로만 있고 저장소에는 올리지 않는다(공개 저장소). 임시 로그로 캡션 원문을 읽었다(커밋하지 않음).

- **문서·스크린샷 12건(같은 사진 1장 중복 포함): 12/12가 묘사가 아니라 「`**Question:** … **Answer:** …`」 꼴**로, 사진에 없는 값을 지어냈다(「2018-05-01 거래」, 「1,000,000원 결제」, 「G는 Guest」 등).
- 일기 본문은 그 값을 그대로 옮겼다(「총 1,000,000원이 지불되었어요」).
- **보통 사진 4장(같은 기기, 표본 장면): 묘사 2(「The image shows a hotel room with a bed, a table…」)·JSON 라벨 2 — 문답 꼴 0.**
- 결론: 원인은 **(a) 캡션이 지어낸다**. 일기 모델은 옮길 뿐이다((b) 아님). 이 VLM은 글자가 빽빽한 그림에서 묘사 대신 문답으로 바뀌고, 그 꼴이 문서의 표지 역할을 한다. 표본이 작다(문서 12·보통 4) — 사람이 정한 판정이지 측정이 아니다.
- `table`은 호텔방 묘사에도 나와 낱말로 쓰면 오탐이다.
- 범위 밖으로 남기는 관찰: 보통 사진에서 JSON 라벨 캡션(`[{"label":"cake","bbox":…}]`)이 나온다 — 별도 과제.

## 결정

| 결정 | 근거 |
| --- | --- |
| 판정 자리는 `src/vision/caption.ts`의 `captionAll` 한 곳. 읽기 전 판정(방안 1)과 읽은 뒤 판정(방안 2)이 같은 루프 안에 있다 | 방안 2는 캡션 뒤에만 가능하다. 둘을 나누면 「문서류」 규칙이 두 파일에 생긴다 |
| 방안 1: 파일명이 `Screenshot`으로 시작하거나(대소문자 무시), 세로/가로 비율이 2 이상이면 화면 캡처로 보고 리사이즈·캡션 없이 건너뛴다 | `exeForMetadata()`가 `filename`·`width`·`height`를 이미 준다(새 네이티브 없음). 폰 화면은 19.5:9·20:9, 카메라는 4:3·16:9. 파노라마는 가로라 걸리지 않는다. 값이 없으면(`null`) 판정하지 않는다(원칙 V) |
| iOS `mediaSubtypes`는 읽지 않는다 | 사진마다 비동기 호출이 하나 더 든다. iPhone 스크린샷은 비율로 잡힌다 |
| 방안 2: 캡션이 (마크다운 기호를 벗긴 뒤) `Question:`으로 시작하거나, 낱말 `receipt`·`invoice`·`document`·`transaction`을 품으면 그 캡션을 담지 않고 사본을 지운다 | 표본 12/12, 보통 0/4. 낱말 목록·표지는 사람이 정한 값이다(`NON_CAMERA_FOLDERS` 선례). `table`·`text`·`paper`는 넣지 않는다(오탐) |
| 거른 장 수만 `PhotoVision.unreadable`로 센다. 캡션 글·이유·점수는 남기지 않는다 | 원칙 IV(채점 없음). 프롬프트가 쓸 사실은 「몇 장」뿐이다 |
| 거른 장은 일기 사진(`entry.photos`)에 들어가지 않는다 → 캐러셀·`vision-cache/`·백업에서 빠진다 | 소유자 결정 Q2=A. 지금도 캡션이 실린 장만 일기 사진이 된다 |
| 남은 캡션이 0장이고 거른 장이 있는 날: 실패로 끝내지 않고 고정 재료 한 줄을 쓴다(「글자가 적힌 사진이 N장 있었지만 내용은 읽지 못했어요」) | 소유자 결정 Q1=C. `on-device.ts`의 「전량 캡션 실패」(073)는 거른 장이 0일 때만 실패다 |
| 다른 캡션이 남은 날은 거른 장을 말하지 않는다 | 소유자 결정 범위(0장 날만). 흐릿한 한 줄이 지어내기 압력이 되는 것(005)을 피한다 |
| 「오늘 쓸 재료 있음」 판정은 바꾸지 않는다 | 사진은 그대로 있다. C를 고른 이유 |
| 선별(`select.ts`)은 바꾸지 않는다 | 판정 자리를 한 곳으로. 상한 8장을 넘는 날 화면 캡처가 자리를 먹는 손해는 받아들인다 |

## 데이터 흐름

`photosBetween()`(filename·width·height 실음) → `PhotoFacts` → `Photo` → `selectForVision`(변화 없음) → `captionAll`: 장마다 ① 화면 캡처면 건너뜀(`unreadable`+1) ② 캡션 ③ 문서 꼴이면 사본 지우고 건너뜀(`unreadable`+1) → `PhotoVision{captions, considered, available, unreadable}` → `on-device.ts`: 캡션 0·거른 장 0이면 실패(종전), 캡션 0·거른 장 >0이면 `seen` → `prompt.ts`: 캡션 0·거른 장 >0이면 고정 줄.

## 테스트

계약을 먼저 쓴다: 두 판정의 참·거짓 사례(표본에서 옮긴 꼴 — 내용 없이), 값이 없을 때 판정하지 않음, 사본 삭제, `unreadable` 수, 실패가 아님, 고정 줄의 조건(캡션이 남은 날에는 없음), 낱말 목록을 export하지 않음. 위반 주입: 판정을 빼거나 고정 줄을 캡션이 남은 날에도 넣어 테스트가 잡는지 본다.
