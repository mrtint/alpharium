# 디자인 시스템 기반과 웹 재디자인 — 설계

2026-10-17 · 상태: 설계 승인(대화), 설계 문서 검토 대기

## 1. 배경과 목표

최근 추가된 개인정보처리방침·소개·지원 페이지(086)의 디자인이 앱과 전혀 다르고 품질이 낮다는 지적이 계기다.
조사로 확인한 사실(2026-10-17, 워크트리 기준):

- 앱의 토큰은 `src/ui/theme/tokens.ts`(Modernist: `bg #f3f2f2`, `accent #ec3013`, 반경 0, Pretendard)가 단일 출처이고
  `tailwind.config.js`가 이것을 `require`한다. 값은 사람이 정한 상수다(헌법 원칙 V).
- `site/`의 세 페이지는 이 시스템과 **연결이 없다**: 페이지마다 `<style>`을 따로 갖고, 아이보리 `#faf8f5`·`#b3261e`·시스템 서체·자체 다크 값을 쓴다.
- 디자인 리뷰 보드 원본은 저장소 밖에 있고, 저장소 안에는 디자인 규칙 문서가 없다.

**목표**: 앱·웹 등 여러 인터페이스가 같은 토큰과 규칙을 쓰고, 이후 모든 디자인 산출물이 이 시스템을 먼저 참조하게 한다.
**성공 기준**: (1) `site/` 세 페이지가 앱과 같은 시각 언어로 보인다. (2) 토큰 정본과 생성물이 어긋나거나 `site/`가 토큰을 벗어나면 테스트가 실패한다. (3) 디자인 작업이 읽을 규칙 문서가 저장소 안에 있다.

## 2. 범위

**이번 스펙**: 토큰 JSON 정본과 생성, `DESIGN.md`, 하드코딩 방지 계약 테스트, `site/` 세 페이지 재디자인(소개는 내용 그대로 시스템만 적용).

**범위 밖(후속 과제로 로드맵에 올린다)**: 앱 화면의 토큰·부품 이탈 점검과 정리(개인정보·서체 라이선스 화면 포함), 컴포넌트 전용 토큰(`WRITING`·`TOAST`·`DIALOG` 등)의 JSON 이전,
소개 페이지에 새 내용·스크린샷을 넣는 랜딩화, Claude Design 동기화(`/design-sync`).

## 3. 구조

```
design/tokens.json                    정본(사람이 정한 값, 역할 이름 기준)
design/DESIGN.md                      규칙 문서
scripts/design/build-tokens.mts       생성 스크립트(값을 옮기기만 한다)
src/ui/theme/tokens.ts               앱용 — 파일 안의 생성 영역(표식 사이)을 스크립트가 다시 쓴다(plan R4)
site/assets/tokens.css                웹용 CSS 변수(커밋)
site/assets/site.css                  웹 공용 스타일(토큰만 참조)
site/assets/fonts/                    Pretendard woff2(공식 배포본 그대로) + 라이선스
```

- 정본에는 **두 플랫폼이 공유하는 값만** 둔다: 색(라이트·다크), 반경, 타입 스케일, 서체, 간격 스케일.
- `tokens.ts`의 기존 export(`COLORS`·`RADIUS`·`TYPE`·`FONT`)는 이름·모양이 그대로여서 앱 코드와 `tailwind.config.js`는 바뀌지 않는다.
  컴포넌트 전용 값은 `tokens.ts`에 남는다.
- 스크립트는 계산·파생을 하지 않는다(원칙 V — 코드가 색을 만들지 않는다). 새 의존성 0.
- `scripts/design/`을 읽는 쪽(앱·`site/`)은 스크립트를 import하지 않는다.

## 4. 토큰

- 라이트는 현재 앱 값 그대로다.
- **다크(웹 전용, 앱은 라이트 고정 031 유지) 초안** — 같은 역할 이름에 다른 값. 대비는 계산해 확인했다:

| 역할 | 라이트 | 다크 | 다크 대비 |
| --- | --- | --- | --- |
| bg | `#f3f2f2` | `#1a1918` | — |
| surface | `#eae9e9` | `#262423` | — |
| border | `#9f9d9d` | `#6f6b6a` | vs bg 3.33 (UI 경계 3:1) |
| text | `#201e1d` | `#f3f2f2` | vs bg 15.71 |
| textMuted | `#6b6767` | `#a9a5a4` | vs bg 7.19 · vs surface 6.33 |
| accent | `#ec3013` | `#ff6a50` | vs bg 6.21 |
| accentForeground | `#f3f2f2` | `#1a1918` | vs accent 6.21 |
| danger | `#ae1800` | `#ff8f7a` | vs bg 7.91 |

- **웹에서 글자·링크에 accent를 쓰지 않는다** — 라이트 accent는 bg 위 3.76:1로 AA 본문 4.5:1에 못 미친다(앱은 소유자 결정으로 면 위 글자에만 허용, 043).
  웹의 링크·강조 글자는 `danger`(라이트 6.41:1) 역할을 쓰고 accent는 면·표식에만 쓴다. 이 구분을 `DESIGN.md`에 적는다.
- 대비 쌍(글자/배경 쌍 목록은 정본 옆 사람이 정한 표)을 라이트·다크 모두 `contrastRatio`로 검증한다.

## 5. 서체

웹은 Pretendard 공식 woff2(v1.3.9, 앱과 같은 버전)를 **`site/`에 자체 호스팅**한다. CDN을 쓰면 방문자의 IP가 제3자에게 가서 방침의 「휴대폰 밖으로 나가는 것」 서술과 모순된다.
파일은 배포처 그대로(수정·서브셋 금지, OFL — 083과 같은 이유)이고 `LICENSE.txt`를 같이 둔다. 쓰는 굵기는 앱과 같은 다섯 중 필요한 만큼(`FONT.weights`와 짝).
서체 이름·굵기는 정본의 `font` 항목 한 곳에서 정한다. 시스템 서체는 로딩 전 대체로만 쓴다.

## 6. `site/` 재디자인

- 세 페이지는 `tokens.css`·`site.css`를 `<link>`로 쓰고 페이지별 `<style>`을 없앤다.
- 방침(긴 글): 읽기 폭, h1/h2/h3 계층, 요약 박스, 절 구분, 목록 간격, 모바일 폭, 앵커. 소개: 내용 그대로, 같은 틀. 지원: 같은 틀.
- 시각 언어는 앱의 Modernist를 따른다: 오프화이트 면, 단일 레드는 면·표식에, 직선(반경 0), 얇은 구분선, 서체 굵기로 위계.
- **보존**: HTML 구조·`id`·`data-outbound` 표식·`<!-- 근거 -->` 주석·자리표시자는 그대로다. 스타일 층만 바꾼다. `__tests__/privacy/`와 `pages.yml`(자리표시자 검사, `site` 업로드)이 계속 통과해야 한다.
- 다크는 `prefers-color-scheme`을 따른다.

## 7. `DESIGN.md`

토큰과 역할 이름의 뜻, 타입 스케일, 서체 규칙, 색 사용 규칙(accent는 면, 글자 강조는 danger), 공용 부품 목록(앱 `Button`·`Card`·`Dialog`·`SectionHeader`·`NameField`, 웹 공용 클래스),
화면 유형별 패턴(긴 글 문서 페이지, 설정 행, 대화상자), **하지 않는 것**(하드코딩 색·서체·반경, 보드에 없는 장식), 새 값을 더하는 절차(정본 → 생성 → 테스트)를 담는다.
`AGENTS.md`와 `CLAUDE.md`에 「디자인 산출물은 `design/DESIGN.md`를 먼저 읽는다」 한 줄씩을 더한다(헌법 본문은 바꾸지 않는다).

## 8. 검증과 방어

| 방어 | 내용 |
| --- | --- |
| 동기 | 정본에서 다시 생성한 결과가 커밋된 `tokens.generated.ts`·`tokens.css`와 바이트 같다 |
| 값 불변 | 앱의 `COLORS`·`RADIUS`·`TYPE`·`FONT`가 이전 값과 같다(기존 `theme-tokens.test.ts` 유지 + 생성물 대조) |
| 대비 | 라이트·다크 대비 쌍이 기준(본문 4.5:1, 큰 글자·UI 3:1)을 넘는다 |
| 웹 하드코딩 | `site/**`의 HTML·CSS에 `tokens.css` 밖의 색 리터럴·`font-family`·`<style>` 인라인이 없다(소스 계약, 주석 제거 후 검사) |
| 서체 파일 | 넣은 woff2가 배포처 파일과 해시가 같고 `LICENSE.txt`가 있다 |
| 기존 | `__tests__/privacy/*`·`pages-workflow` 통과 |

위반 주입으로 각 방어가 실제로 잡는지 확인한다(치환이 적용됐는지 먼저 단언). 시각 확인은 헤드리스 크롬 캡처(모바일 폭·라이트·다크)로 하고, 실기기 검증(원칙 V)은 앱 쪽 변경이 없음을
확인하는 정도(앱 번들에 생성 파일이 들어가므로 dev 빌드에서 앱이 같은 색으로 뜨는지 한 번 본다).

## 9. 위험과 미확인

- 다크 값은 초안이다(소유자 검토 대상). 앱에서 쓰이지 않는다.
- woff2 용량(굵기 다섯 × 한글 전체)이 페이지 로딩에 큰 영향을 줄 수 있다 — 필요한 굵기만 쓰고 `font-display: swap`, 공식 동적 서브셋(unicode-range 분할판)이 있으면 그것을 쓴다(배포처 파일 그대로이므로 수정이 아니다). 실제 크기는 구현에서 잰다.
- GitHub Pages 게시 뒤 두 URL 200과 서체 로딩은 머지 뒤에야 확인된다.
- 후속 과제(앱 이탈 점검)가 끝나기 전까지 앱 화면의 일부는 시스템을 벗어난 채 남는다.

## 10. 로드맵

「진행 예정 과제」에 이 과제(디자인 시스템 기반과 웹 재디자인)를 올리고, 후속 과제 둘(앱 화면 이탈 점검·정리, 소개 페이지 랜딩화)을 별도 항목으로 올린다. 스펙 번호는 specify 단계에서 정해진 뒤에 적는다.
