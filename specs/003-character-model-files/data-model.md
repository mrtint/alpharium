# Phase 1: 데이터 모델

**기능**: 캐릭터별 모델 파일 확보 | **Date**: 2026-08-13

명세의 Key Entities를 타입으로 옮긴다. 계약의 자세한 규칙은 [contracts/](contracts/)에 있다.

**이 문서의 중심 긴장**: 값 하나하나가 원칙 III의 누출 통로가 될 수 있다. 그래서 아래 타입은
**어느 값이 화면 쪽으로 갈 수 있고 어느 값이 갈 수 없는지**를 타입으로 가른다.

---

## 경계: 안쪽 값과 바깥쪽 값

```
┌─ 코드 안쪽 (화면에 절대 나가지 않는다) ────────────────┐
│  ModelAsset       자산키·주소·예상 크기·지문           │
│  AssetKey         파일 이름이 되는 불투명한 값          │
└────────────────────────────────────────────────────────┘
                          │  roster.ts 만 넘나든다
                          ▼
┌─ 바깥쪽 (화면이 받아도 되는 것) ───────────────────────┐
│  Character        002가 정한 다섯 자리                  │
│  ModelReadiness   넷 중 하나 + 까닭                     │
│  Progress         캐릭터 + 0~1 (또는 모름)              │
│  StorageUsage     캐릭터 + 바이트                       │
└────────────────────────────────────────────────────────┘
```

**규칙: 바깥쪽 타입은 안쪽 타입을 필드로 담지 않는다**(FR-003). 담는 순간 화면이 실수할
여지가 생긴다. 조심해서 안 쓰는 것보다 **못 쓰게 하는 쪽**이 낫다.

## ModelAsset — 캐릭터의 모델 자산 (안쪽)

한 캐릭터가 쓰기 위해 기기에 있어야 하는 것.

| 필드 | 뜻 | 근거 |
| --- | --- | --- |
| `key` | 파일 이름이 되는 불투명한 값 | FR-004 (파일명이 모델명이면 안 된다) |
| `url` | 어디서 받는가 | FR-002 (코드 안쪽) |
| `expectedBytes` | 얼마나 자리를 차지하는가 | FR-001a (공간 판정·완료 판정의 근거) |
| `md5` | 내용이 온전한지 판정하는 지문 | FR-021, FR-024 |

**불변식**:
1. **이 타입이 화면 쪽으로 나가지 않는다**(FR-003). `roster.ts` 밖에서 이 값을 통째로 들고
   다니지 않는다.
2. `key`는 **캐릭터 식별자와 달라야 한다**. 같으면 파일 관리자에서 파일명을 보고 캐릭터를
   알 수 있고, 거꾸로 캐릭터로 파일을 찾을 수 있다 — 매핑이 기기에 드러난 것이다.
3. **추론 설정을 담지 않는다.** 샘플링 파라미터·컨텍스트 길이는 다음 기능의 것이다
   (FR-032). 여기 담으면 "받았으니 돌려보자"가 시작된다.
4. **속도·품질 관련 필드를 담지 않는다**(원칙 IV, FR-034).

## ModelReadiness — 준비 상태 (바깥쪽)

**이 기능이 다른 축에 내주는 핵심 값이다.** 002의 `SignalValue`가 셋을 가른 것과 같은
구조이며, 파일이 *부분적으로* 있는 상태 때문에 넷이 된다.

```
ready                      쓸 수 있다
not-downloaded             받지 않았다
partial     + reason       받다 말았다 (이어받을 수 있는지 함께)
unusable    + reason       받았는데 쓸 수 없다
```

| 갈래 | 언제 | 사용자가 할 수 있는 것 |
| --- | --- | --- |
| `ready` | 검증을 통과했고 파일이 지금도 있다 | 이 캐릭터로 일기를 쓴다 / 지운다 |
| `not-downloaded` | 파일이 없다 | 받기 시작한다 |
| `partial` | 일부만 받았다 | 이어받는다 / 지운다(부분 파일 정리) |
| `unusable` | 파일은 다 있는데 쓸 수 없다 | 다시 받는다(정리 후) |

**`ready`가 되는 조건은 둘 다 참이어야 한다**(FR-007):
1. 검증 결과가 남아 있고 통과했다 (FR-021c)
2. **파일이 지금도 있고 크기가 맞다** (FR-021d, FR-021e)

두 번째가 명확화 세션이 찾아낸 것이다. 검증 결과는 **"그때 온전했다"는 기록이지 "지금도
있다"는 뜻이 아니다.**

**`partial`과 `unusable`을 가르는 이유**(FR-006a): 전자는 **이어받으면 되고** 후자는
**정리하고 다시 받아야 한다.** 뭉개면 사용자에게 무엇을 하라고 말할 수 없다.

**`reason`에 무엇이 담기는가**: 왜 그 상태인지의 사실. `partial`이면 중단됐는지 네트워크가
끊겼는지, `unusable`이면 검증에 실패했는지 파일이 사라졌는지. **모델 정보는 담기지
않는다**(FR-004) — 오류 메시지가 원칙 III의 누출 경로다.

## VerificationVerdict — 검증 결과 (기기에 남는다)

받은 직후 한 번 판정되어 남고(FR-021a~b), 이후 상태 조회가 이것을 근거로 삼는다.

| 필드 | 뜻 | 근거 |
| --- | --- | --- |
| `assetKey` | **무엇을** 검증했는가 | 아래 불변식 2 |
| `verifiedMd5` | 검증할 때 본 지문 | FR-021 |
| `verifiedBytes` | 검증할 때 본 크기 | FR-021e (지금 크기와 견준다) |
| `passed` | 통과했는가 | FR-021c |

**불변식**:
1. **이것이 없으면 `ready`가 아니다**(FR-021c). 파일이 있어도 검증한 기록이 없으면 — 이전
   버전이 남긴 것, 사용자가 넣은 것, 검증 전에 앱이 죽은 것 — 쓸 수 없다.
2. **`assetKey`를 함께 남기는 이유**: 로스터가 바뀌어 캐릭터가 다른 자산을 가리키게 되면,
   옛 결과가 새 자산의 것으로 오독된다. 무엇을 검증했는지 적어 두면 어긋남이 드러난다.
   *(설계 중 발견한 것 — 명세에는 없었다.)*
3. **시각을 담지 않는다.** "언제 검증했나"는 필요 없고, 있으면 "얼마나 걸렸나"로 자라기
   쉽다(원칙 IV).

## DownloadProgress — 진행 상태 (바깥쪽)

| 필드 | 뜻 |
| --- | --- |
| `character` | 어느 캐릭터를 받고 있는가 |
| `fraction` | 얼마나 왔는가: `0~1` 또는 **모름** |

**불변식**:
1. **캐릭터 단위다**(FR-013a). 파일 이름·파일 개수·바이트 수를 담지 않는다 — **바이트를
   담으면 그것이 곧 모델 크기다.** 설계 중 찾은 누출 경로다.
2. **시간 관련 필드를 담지 않는다**(원칙 IV). `elapsed`나 `bytesPerSecond`를 두면 모델 비교의
   시작점이 된다. 남은 시간을 보여주고 싶어도 담지 않는다.
3. **`fraction`이 "모름"일 수 있다**(원칙 V). 서버가 `Content-Length`를 주지 않으면
   `totalBytes`가 `-1`이다(research.md §1). 그때 백분율을 지어내지 않는다 — 매핑의 예상
   크기로 갈음하되, 그것도 확실하지 않으면 모른다고 한다.

## DownloadFailure — 내려받기가 되지 않은 까닭

```
insufficient-space   시작 전에 공간이 모자라다 (FR-019)
network              받다가 끊겼다 (FR-017)
verification-failed  다 받았는데 검증에 실패했다 (FR-022)
busy                 다른 캐릭터를 받는 중이다 (FR-020)
```

**불변식**:
1. **어느 갈래에도 "대신 쓸 자산"이 없다**(FR-035, 원칙 I). 002의 `GenerationFailure`에
   `text` 필드가 없는 것과 같은 구조다 — **타입 수준에서 대체가 불가능해야 한다.**
2. **`busy`가 무엇을 받는 중인지 말한다**(FR-020). 사용자가 멈추고 다시 요청할 수 있어야
   하므로(FR-020a) 무엇을 멈춰야 하는지 알아야 한다. 다만 **캐릭터로 말하지 자산으로 말하지
   않는다.**
3. **`insufficient-space`가 모델 크기를 말하지 않는다**(FR-019a). "이 캐릭터를 두려면 공간이
   더 필요하다"이지 "3.2GB가 필요하다"가 아니다.

## StorageUsage — 저장 공간 사용 (바깥쪽)

| 필드 | 뜻 |
| --- | --- |
| `character` | 어느 캐릭터가 |
| `bytes` | 얼마나 쓰는가 |

**불변식**: **캐릭터 단위로 합산한다**(FR-028a). 파일별로 쪼개 보이면 한 캐릭터가 파일 몇
개를 쓰는지 드러나고, 그것이 모델 구성의 정보다. 한 캐릭터가 여러 파일을 가질 수 있는 모양은
열어 두되(FR-033) 밖으로는 하나의 수로 나간다.

## PausedDownload — 중단된 내려받기 (기기에 남는다)

`DownloadTask.savable()`이 돌려주는 값을 그대로 보관한다(research.md §1).

**불변식**:
1. **우리가 만드는 값이 아니라 보관하는 값이다.** 안을 들여다보거나 고치지 않는다.
2. **여기에 `url`이 들어 있다**(타입 정의상). 그러므로 **이 값도 안쪽 값이다** — 화면으로
   나가지 않는다. 설계 중 찾은 누출 경로다.
3. **앱이 갑자기 죽으면 이 값이 없을 수 있다.** `savable()`은 `paused` 상태에서만 부를 수
   있기 때문이다(research.md §1). 그때도 부분 파일은 남으므로 `partial`이되 이어받기 정보가
   없는 경우가 생기며, 지울 수 있어야 한다(FR-029).

## 기기에 남는 것 — 전체

```
Paths.document/
├── diary/                  002의 것. 건드리지 않는다
└── models/
    ├── <assetKey>.gguf     모델 파일 (FR-001a의 크기, FR-021의 지문 대상)
    └── state.json          VerificationVerdict[] + PausedDownload[]
```

**`state.json`이 사라지면** 검증 결과가 없어지므로 모든 캐릭터가 `ready`가 아니게 된다
(FR-021c). 파일은 남아 있으므로 다시 검증하면 되고, 그 경우 다시 받을 필요는 없다 —
**정리와 재검증은 다른 일이다.**

**`state.json`이 있는데 모델 파일이 없으면** 어긋난 상태다. `ready`가 아니며(FR-021e) 어긋난
결과는 정리된다.
