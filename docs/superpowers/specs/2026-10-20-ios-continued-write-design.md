# 092 — iPhone: 사용자가 시작한 쓰기를 앱을 나가도 끝까지 (설계)

날짜: 2026-10-20 · 브랜치 `092-ios-continued-write`(091 위) · 로드맵 「알림을 눌러 시작한 쓰기를 앱을 나가도 끝까지」

## 왜

091 실측: iOS는 처리 작업(`BGProcessingTask`)을 **충전 중에만** 깨운다(배터리 상태 31시간·13시간 모두 0회). 충전 없이 iPhone이 일기를 쓰는 길은
**사용자가 한 번 눌러 시작한 쓰기를 시스템이 이어 돌리게 하는 것**뿐이다 — iOS 26 `BGContinuedProcessingTask`. 지금은 앱을 나가면 쓰기가 끊긴다(005 FR-014b).

## 소유자 결정 (2026-10-20)

1. **적용 범위: 사용자가 시작한 모든 쓰기** — 「쓰기」 버튼, 앱을 열면 쓰는 중(057), 쓸 차례 알림 누름(085 → 057). 셋 다 홈의 제자리 쓰기(054) 한 통로를 지난다.
2. **진행 표시: 단계 문구 + 자주 움직이는 막대** — 시스템 진행 UI의 보조 줄은 단계만 말하고(「준비하는 중」·「사진을 보는 중」·「글을 쓰는 중」 — 제목은 글 단계에 든다) 숫자를 쓰지 않는다.
   막대는 사진 한 장·글 한 조각마다 실제 일이 끝날 때 움직인다(타이머로 흉내 내지 않는다 — 원칙 V).
3. **헌법 개정 불필요** — 원칙 IV는 「사용자의 기다림을 덜기 위한 진행 인디케이터」를 금지 대상에서 뺀다. 홈 화면의 「진행률은 세지 않아요」(054)는 그대로 둔다(홈은 바꾸지 않는다).

## 사실 (출처)

- [문서·포럼] `BGContinuedProcessingTaskRequest(identifier:title:subtitle:)`은 **앞에 있을 때 사용자 동작에 응해** 제출한다. 식별자는 Info.plist `BGTaskSchedulerPermittedIdentifiers`에 와일드카드(`<접두>.*`)로 선언하고 제출 때 꼬리를 붙인다. 처리기는 제출 전에 등록돼 있어야 한다.
- [문서·포럼] 시스템이 진행 UI를 띄우고 `task.progress`를 보여 준다. **진행 보고가 없으면 만료시킨다**(자원이 모자라면 진행이 적은 작업부터). `strategy` `.fail`(곧바로 못 돌면 제출 실패)·`.queue`.
- [모름] CPU 감시(090의 「80% over 60s」)가 이 작업에 걸리는가, 몇 분짜리 추론을 허용하는가 — **실기기로 잰다.**
- [코드] 배포 대상 iOS 16.4 → `if #available(iOS 26, *)`. 지금 기기 iOS 27.0.1.

## 구조

### 네이티브 — 로컬 Expo 모듈 `modules/pocketlog-continued-write`

- 처리기는 신청마다 꼬리를 붙인 온전한 식별자(`com.a810labs.pocketlog.write.<UUID>`)로 등록한다 — 와일드카드는 Info.plist에만 둔다(구현 중 확인: 와일드카드 처리기 등록은 막혀 있다, research R1).
- `begin(title, subtitle) -> Promise<Bool>`(제출 결과를 기다린다): iOS 26 미만·제출 실패면 거짓(지금처럼 앞을 벗어나면 끊는다). `.fail` 전략으로 `…write.<날짜>` 하나를 제출.
- `report(subtitle, completed, total)`: 처리기가 아직 안 섰으면 값을 들고 있다가 서는 순간 반영.
- `finish(success)`: `setTaskCompleted`. 처리기가 서기 전이면 섰을 때 곧바로 끝낸다.
- 이벤트 `onExpired`: 시스템이 끝냄(만료·사용자가 진행 UI에서 취소) → JS가 그 쓰기를 끊는다.
- Info.plist 식별자는 091 plugin(`with-battery-bg-task.js`)과 같은 자리에서 더한다.

### JS

- `src/app/continued-write-port.ts` — 모듈을 `requireOptionalNativeModule`로 읽는 통로(없으면 늘 「안 됨」 — 안드로이드·시뮬레이터·jest).
- `src/app/continued-progress.ts`(순수) — 단계(`ProgressStage`)·사진 장 수·조각 수 → `{ subtitle, completed, total }`. 문구는 카탈로그(`catalogs/ko/`).
  칸 배분: 사진 단계·본문 단계·제목 단계를 사람이 정한 비율로 나누고, 단계 안에서는 끝난 일만큼만 채운다. 본문은 끝 조각 수를 모르므로 남은 몫의 절반씩 다가간다(100%에 닿지 않는다 — 끝나면 `finish`).
- **홈의 `generate`**: iOS에서 홈이 시작한 쓰기면 `begin` → `onProgress`·심장 박동마다 `report` → `finally`에서 `finish(ok)`.
  `begin`이 참이면 **앞을 벗어나도 끊지 않는다**(005 FR-014b를 이 경우에만 뒤집음). 018 미리 준비 해제는 그대로.
- `onExpired` → 홈의 `stop()`과 같은 길로 끊는다. 기록은 081 「도중에 끊김」(사용자가 그만둔 것이 아니다).
- **앱이 앞에 없을 때 저장에 성공하면 완성 알림**(057 문구·`diary-completed` 채널, 085 맞추기 뒤) — 사용자가 나가 있으니 끝났다고 알린다(소유자 확인 대상, 기본 켬).

### 심장 박동 — 실제 일이 끝날 때만

- 사진: 캡션 한 장이 끝날 때(`vision-port.ts`).
- 본문·제목: iOS에서 이 경로의 생성은 091의 조각 생성(`completePaced`)을 쉼 없이(`pauseRatio: 0`) 쓴다 — 조각이 끝날 때마다 박동. 처음에는 토큰 콜백을 쓰지 않으려 했으나 앱 밖에서 조각 하나가 30초를 넘겨 만료돼(2026-10-21 실측), `llama-port.ts`가 토큰 콜백을 받되 데이터를 경계에서 버리고 인자 없는 「토큰」 박동만 낸다(005 FR-028b의 뜻 — 글을 밖으로 내지 않는다 — 은 그대로).
- CPU 감시가 이 작업을 죽이면(실기기 `cpu_resource_fatal`) 091의 느린 쓰기 값(스레드 1·쉼 0.5)을 이 경로에도 쓴다 — 실측으로 정한다.

### 로드맵의 091 잔여 (같이 고친다)

`stopRequested`를 비우는 자리 · 쉼 도중 그만두기가 쉼을 끊지 못함 · 마지막 호출 뒤의 쉼 · 호출 한 번의 CPU 상한 메모.

## 바뀌지 않는 것

안드로이드 전부(모듈 없음 → 「안 됨」 갈래) · 백그라운드 자동 쓰기(090·091) · 홈 화면 문구 · 판정 갈래 넷 · 091 배터리 요청.

## 완료 조건

실제 iPhone에서 **충전하지 않은 채** 홈에서 시작한 쓰기(사진 있는 날)가 앱을 나간 뒤에도 저장되고, 시스템 진행 UI가 단계 문구와 움직이는 막대를 보이며, 완성 알림이 선다 — 한 번 이상.

## 위험

- 이 API가 몇 분짜리 CPU 추론을 끝까지 두는지 모른다(CPU 감시·자원 압박 만료).
- 조각 생성이 전경 속도를 조금 늦출 수 있다(조각마다 프롬프트 접두 재사용 1토큰 — 091에서 잼).
- 시스템이 같은 앱의 이어 하기 작업 수를 제한한다(포럼) — 쓰기는 한 번에 하나라 겹치지 않는다.
