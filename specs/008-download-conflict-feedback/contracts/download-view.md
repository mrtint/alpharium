# 계약: 내려받기 상태를 화면에 보이는 규칙

**대응 요구사항**: FR-001~FR-017
**관련 계약**: [003 acquisition.md](../../003-character-model-files/contracts/acquisition.md) (FR-020·FR-020a)

이 계약이 정하는 것은 **「무엇을 보일 것인가」의 판정**이다. 내려받기를 어떻게 하는지는
003이 정했고 **이 계약은 그것을 바꾸지 않는다.**

---

## 왜 순수 함수인가

판정해야 할 것이 **상태의 조합**이고, 그중 하나(「거부 안내가 아직 참인가」)가
**시간에 따라 거짓이 된다.** 화면의 `useEffect`로 다루면 타이밍 버그가 들어오고 그
버그는 기기에서만 보인다.

007이 같은 문제를 `resolveSelection()`으로 풀었고, 그 덕에 「옮김」 규칙 전체가 기기
없이 검증됐다. **여기서도 같은 구조를 쓴다.**

```
재료 ──────────────────▶ resolveDownloadView() ──────▶ DownloadView ──▶ 화면은 그리기만
 · 받는 중인 것                (순수)                     · active
 · 마지막 거부                                            · notice
```

---

## 계약 1 — `resolveDownloadView()`

```ts
function resolveDownloadView(
  active: DownloadProgress | null,
  rejection: DownloadRejection | null,
): DownloadView;
```

**입력**: 지금 받는 중인 것(없으면 `null`), 마지막 거부(없거나 이미 닫혔으면 `null`).

**출력**: 화면이 그릴 것 전부.

### 판정 순서

| # | 무엇을 보는가 | 결과 | 요구 |
| --- | --- | --- | --- |
| 1 | 받는 중인 것이 있는가 | 그대로 `active`에 싣는다 | FR-008 |
| 2 | 거부가 있는가 | 없으면 `notice: null` | — |
| 3 | **거부가 아직 참인가** — 받는 중인 것이 있고, 그것이 거부 당시 받던 그것인가 | 아니면 `notice: null` | FR-005 |
| 4 | 거부가 받는 중인 것과 같은 캐릭터를 요청했는가 | 그렇다면 `notice: null` (거부될 수 없는 조합) | FR-010 |
| 5 | 그 외 | `notice`에 그대로 싣는다 | FR-001 |

**3번이 이 계약의 핵심이다.** 「quiet을 받는 중이라 거부했다」는 quiet이 끝나거나
멈추는 순간 **거짓이 된다.** 그래서 안내를 지우는 코드를 따로 두지 않고, **판정이
매번 다시 물어서** 자동으로 사라지게 한다.

**4번이 방어적인 이유**: 003이 같은 캐릭터의 재요청을 허용하므로 이런 거부는 나지
않아야 한다. 그래도 판정이 막는다 — **불변식은 「나지 않는다」가 아니라 「나도
보이지 않는다」여야 한다.**

### 불변식 (테스트가 직접 확인한다)

| # | 불변식 | 요구 |
| --- | --- | --- |
| I1 | 거부가 `active`를 **절대 지우지 않는다** | FR-008 |
| I2 | `notice.requested`와 `active.character`가 **같은 경우가 없다** | FR-010 |
| I3 | `notice`는 **최대 하나**다 (타입이 배열이 아니다) | FR-006 |
| I4 | `active`가 `null`이면 `notice`도 `null`이다 | FR-005 |
| I5 | 출력에 시간·속도·바이트 필드가 **없다** | FR-016, 원칙 IV |
| I6 | 출력에 자산키·주소·크기·모델 식별자가 **없다** | FR-004, 원칙 III |

**I4가 반직관적으로 보일 수 있다**: 「받는 것이 없는데 거부 안내가 남으면?」 —
그때 안내는 **거짓말이다.** 「받는 중이라 거부했다」인데 받는 것이 없으므로.
사용자는 이제 그냥 다시 누르면 된다.

**I5·I6은 타입으로 이미 막혀 있다.** `DownloadProgress`가 003부터 그 필드를 갖지
않고, `src/ui/`는 헌법 검사가 `assetFor`·`roster` import를 막는다. **테스트는 그
방어가 살아 있는지 확인하는 것이지 새로 세우는 것이 아니다.**

## 계약 2 — 화면이 받는 것

```ts
type CharacterListProps = {
  readiness: Record<Character, ModelReadiness>;
  view: DownloadView;              // ★ progress: DownloadProgress | null 을 대체한다
  usage?: StorageUsage[];
  onPrepare: (character: Character) => void;
  onPause: () => void;
  onRemove: (character: Character) => void;
  onDismissNotice: () => void;     // ★ 새로 — FR-005
};
```

### 무엇을 그리는가

| 조건 | 그 줄에 보이는 것 | 요구 |
| --- | --- | --- |
| `view.active?.character === character` | 진행률(또는 「받는 중…」) + **멈추기 버튼** | FR-008·FR-009 |
| 그 외 | 준비 상태 + 평소 버튼 | FR-007·FR-010 |
| `view.notice !== null` | 목록 위에 안내 하나 + 닫는 길 | FR-001·FR-005·FR-006 |

**★ 거부당한 줄이 특별해지지 않는다**(FR-007·FR-010). `notice.requested`인 줄도
평소대로 「받아야 함」 + 「준비하기」다 — 거부는 **그 캐릭터의 상태를 바꾸지 않았다.**

### 안내 문구에 들어가는 것

**들어간다**: 거부되었다는 것, `busyWith` 캐릭터 이름, **멈추면 된다는 것**(FR-003).

**들어가지 않는다**(FR-004, SC-004): 파일 크기·주소·자산키·모델 식별자·양자화·
남은 시간·속도·바이트.

**FR-003을 빠뜨리면 안내가 무의미하다.** 「거부됨」만 말하고 빠져나갈 길을 말하지
않으면 사용자는 여전히 갇힌다 — 003 FR-020a가 막으려던 바로 그 상태다.

## 계약 3 — 배선이 지키는 것

**이 계약이 003의 `Acquisition`을 고치지 않는다.** 고치는 것은 그것을 부르는 쪽이다.

### C3-1. 요청의 결과를 버리지 않는다 (FR-001)

```ts
const result = await acquisition.prepare(character, onProgress);
if (!result.ok && result.failure.kind === "busy") {
  setRejection({ requested: character, busyWith: result.failure.busyWith });
}
```

**지금은 `await acquisition.prepare(...)`로 값을 버린다.** 그것이 버그 ①이다.

### C3-2. 진행 표시는 **자기 요청의 결과로만** 거둔다 (FR-008·FR-012)

```
prepare()가 끝났다
   ├─ busy로 거부됐다  ──▶ 진행 표시를 건드리지 않는다   ★ 버그 ②가 고쳐지는 자리
   └─ 그 외 (완료·멈춤·실패) ──▶ 진행 표시를 거둔다      (FR-012)
```

**지금은 갈래 없이 `setProgress(null)`을 부른다.** 거부는 즉시 반환되므로 받던 것의
진행 표시가 곧바로 지워지고, 멈추기 버튼이 그와 함께 사라진다.

### C3-3. `Acquisition`은 탭보다 오래 산다 (FR-013·FR-014)

**★ research §2가 찾은 셋째 결함.** `Acquisition`·`ModelPorts`·진행 상태·거부 통지를
**`AppFrame`**(탭 상태를 가진 컴포넌트)에서 만들어 내린다.

지금은 `ModelSection`의 `useState`에 있어 **탭을 옮기면 인스턴스가 통째로 사라진다** —
`running`도 `handle`도 함께. 돌아오면 새 인스턴스라 `busyWith()`가 `null`이고, 받던
것을 멈출 방법이 없다.

**`expoModelPorts()`를 위로 올려도 안전하다**(2026-08-21 코드 확인): 클로저 객체를
만들 뿐이고 기기 통로는 메서드 안에서 `await import`로 열린다.

### C3-4. 멈추기는 받는 중인 그것을 멈춘다 (FR-011)

`acquisition.pause()`는 인자를 받지 않고 **지금 받는 중인 것**을 멈춘다. 한 번에
하나뿐이므로(FR-015) 모호하지 않다. **화면에 보이는 멈추기 버튼이 `active`인 줄에만
있으므로** 무엇이 멈추는지 사용자에게도 분명하다.

## 이 계약이 열지 않는 것

- **동시 내려받기** — 003 FR-020이 금지하고 이 기능이 유지한다(FR-015). 열려면 003
  계약을 먼저 고친다
- **`busy` 외의 실패를 알리기** — `insufficient-space`·`network`·`verification-failed`는
  spec의 범위 밖이다. `DownloadRejection`에 얹지 않는다
- **진행 이력·속도·남은 시간** — 원칙 IV
- **거부의 영속 기록** — 앱을 껐다 켜면 참이 아니다
