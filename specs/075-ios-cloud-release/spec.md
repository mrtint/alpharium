**Feature Branch**: `075-ios-cloud-release`

**Created**: 2026-10-11

## 근거와 원본

- **설계**: `docs/superpowers/specs/2026-10-11-ios-cloud-build-upload-design.md`(저장소 소유자 승인, 2026-10-11).
- **로드맵 과제**: 「무료 빌드 머신으로 iOS 빌드·업로드 — 개인 맥 없이」(Tier 3: 서명·업로드).
- **문제**: iOS 빌드·TestFlight 업로드(066 절차)는 회사 맥에서만 된다. 저장소 소유자는 회사 맥 밖에서는 맥이 없다.
- **입력**: 072가 잰 macOS 러너(3코어·7GB, Xcode 26.6)의 시뮬레이터 빌드 시간(잡 전체 9~13분)과 「iOS Pods·DerivedData 캐시는 효과가 없다」는 결론.
- **범위 밖**: 안드로이드 AAB(별도 과제), iOS 시뮬레이터·Maestro 갈래, `ios.buildNumber` 자동 올림(사람이 커밋한다), Xcode Cloud·Codemagic·EAS·fastlane, IPA 보관(아티팩트).

## 용어

- **릴리스 워크플로**: 소유자가 손으로 시작해 아카이브·서명·업로드까지 끝내는 CI 워크플로 하나(`ios-release.yml`).
- **보호 환경**: 서명 비밀이 들어 있고 실행 전에 소유자의 승인을 받는 `ios-release` 환경.
- **처리 통과**: 업로드된 빌드가 App Store Connect의 처리 단계를 거부 없이 통과해 TestFlight 목록에 나타난 상태(업로드 성공과 다르다 — 066의 ITMS-90683).

## Clarifications

### Session 2026-10-11

- Q: App Store Connect API 키(.p8, Key ID, Issuer ID)를 소유자가 직접 발급할 수 있나? → A: 발급 가능. 업로드는 API 키로 확정하고 앱 암호 후퇴안은 두지 않는다.
- Q: 무료 macOS 러너에서 Release 아카이브가 메모리 부족으로 죽으면? → A: 빌드 병렬도를 낮춰 이 과제 안에서 통과할 때까지 조정한다(완료 조건 유지, 유료 러너·맥 절차로 넘기지 않는다).

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 맥 없이 TestFlight 빌드를 올린다 (Priority: P1)

저장소 소유자가 회사 맥 없이, GitHub에서 릴리스 워크플로를 시작하고 승인하면 iOS 빌드가 서명되어 TestFlight로 올라간다. 올린 빌드가 처리 통과해 실제 iPhone에 설치된다.

**Why this priority**: 이 과제의 존재 이유이자 완료 조건이다. 이것만 되어도 회사 맥 의존이 사라진다.

**Independent Test**: `buildNumber`를 올려 커밋한 `main`에서 릴리스 워크플로를 한 번 실행하고, 승인한 뒤 끝까지 성공하는지, App Store Connect가 처리 통과시키는지(ITMS 거부 메일 없음, TestFlight 목록에 나타남), iPhone에 설치되는지 본다.

**Acceptance Scenarios**:

1. **Given** 비밀 여섯 개와 보호 환경이 등록되어 있고 `buildNumber`가 지난 업로드보다 크다, **When** 소유자가 `main`에서 릴리스 워크플로를 시작하고 승인한다, **Then** 아카이브·내보내기·업로드가 모두 성공하고 단계별 걸린 시간이 실행 요약에 남는다.
2. **Given** 업로드가 성공했다, **When** App Store Connect가 빌드를 처리한다, **Then** 거부 메일이 오지 않고 TestFlight 목록에 빌드가 나타나며 실제 iPhone에 설치된다.
3. **Given** 업로드가 끝났다, **When** 워크플로가 종료된다(성공이든 실패든), **Then** 러너에는 서명 키체인·프로파일·API 키 파일이 남지 않는다.

---

### User Story 2 - 비밀이 퍼블릭 저장소에서 새지 않는다 (Priority: P1)

저장소가 퍼블릭이어도 서명 키와 업로드 키는 소유자가 승인한 `main`의 수동 실행에서만 쓰인다. 포크·PR·다른 브랜치·자동 트리거는 비밀에 닿지 못하고, 실행 결과물로도 새지 않는다.

**Why this priority**: 서명 키가 퍼블릭 저장소의 CI에 있다는 사실 자체가 이 기능의 가장 큰 위험이다. 새면 소유주의 개인 개발자 계정이 위험해진다.

**Independent Test**: 워크플로 파일을 읽는 계약 테스트가 트리거·권한·비밀 참조·산출물 규칙을 잠그고, 각 규칙을 어긴 위반 주입이 테스트 실패로 뒤집힌다. 실제 실행에서는 `main`이 아닌 브랜치에서의 시작이 거부된다.

**Acceptance Scenarios**:

1. **Given** 워크플로 파일, **When** 트리거를 읽는다, **Then** 수동 시작 하나뿐이다(PR·push·예약 없음).
2. **Given** 워크플로 파일, **When** 비밀 참조를 센다, **Then** 허용된 여섯 개뿐이고 보호 환경의 잡에서만 참조된다.
3. **Given** 워크플로 파일, **When** 산출물·로그 규칙을 읽는다, **Then** IPA 등 결과물을 아티팩트로 남기지 않고 명령 추적(`set -x`)으로 값을 찍지 않으며 캐시를 쓰지 않는다.
4. **Given** `main`이 아닌 브랜치, **When** 릴리스 워크플로를 시작한다, **Then** 보호 환경이 거부한다.
5. **Given** 위 규칙 중 하나를 어긴 변경(예: `pull_request` 추가), **When** 테스트를 돌린다, **Then** 테스트가 실패한다.

---

### User Story 3 - 비밀이 빠졌거나 번호가 틀리면 빨리 안다 (Priority: P2)

필수 비밀이 비었거나 `buildNumber`가 올바르지 않으면 20분짜리 아카이브를 돌리기 전에 원인이 보이는 메시지로 실패한다.

**Why this priority**: 설정 실수가 가장 흔한 첫 실패다. 비싼 빌드 뒤에야 알면 시간을 낭비한다.

**Independent Test**: 비밀 하나를 비운 채 시작하면 사전 점검 단계에서 어느 비밀이 비었는지 말하고 끝난다.

**Acceptance Scenarios**:

1. **Given** 필수 비밀 하나가 비어 있다, **When** 시작한다, **Then** 이름을 밝히며 빌드 전에 실패한다(값은 찍지 않는다).
2. **Given** `ios.buildNumber`가 정수가 아니다, **When** 시작한다, **Then** 빌드 전에 실패한다.
3. **Given** 같은 버전·번호가 이미 업로드되어 있다, **When** 업로드한다, **Then** 096의 「번호 점검」이 스토어의 마지막 번호를 읽어 빌드 전에 막고, 그것이 막지 못한 경우에도 Apple의 거부가 숨겨지지 않고 그대로 실패로 보인다.

---

### User Story 4 - 절차 문서가 새 경로를 기본으로 말한다 (Priority: P3)

AGENTS.md의 「iOS 빌드·서명·TestFlight」 절이 이 경로를 기본으로 설명하고, 맥 절차는 대안으로 남는다. 비밀 등록·보호 환경 설정·인증서 만료 갱신 절차가 문서에 있다.

**Why this priority**: 문서가 옛 절차(회사 맥)만 말하면 다음 사람이 새 경로를 모른다. 코드는 아니므로 가장 나중이다.

**Independent Test**: 문서만 읽고 비밀 등록부터 실행·확인까지 따라갈 수 있다.

**Acceptance Scenarios**:

1. **Given** 개정된 AGENTS.md, **When** iOS 배포 절을 읽는다, **Then** CI 경로가 기본이고 맥 절차는 「다른 맥에서 올리려면」 옆의 대안이며, 앞 절차가 주석으로 덧대어지지 않고 고쳐져 있다.
2. **Given** 이 기능의 quickstart, **When** 읽는다, **Then** 비밀 여섯 개의 출처, 보호 환경 설정(필수 리뷰어·배포 브랜치), 인증서 만료일(2027-10-08)과 갱신 절차가 있다.

### Edge Cases

- 같은 워크플로를 연달아 시작하면? 동시에 하나만 돌고 앞선 실행은 취소되지 않는다(업로드 도중 취소로 반쪽 상태가 되지 않게).
- 아카이브가 러너 메모리 부족으로 죽으면? 실패로 끝나고 키체인 정리는 그래도 실행된다. 단계별 시간 기록으로 어느 단계인지 보인다. 이 경우 빌드 병렬도를 낮춰 다시 시도해 통과할 때까지 조정한다(FR-015).
- 중간 단계가 실패하면? 정리 단계는 성공·실패와 무관하게 실행된다.
- 러너 이미지의 Xcode 버전이 바뀌면? 코드 변경 없이 실패할 수 있다 — 알려진 위험이며 첫 실행에서 버전을 요약에 남겨 비교할 수 있게 한다.
- 인증서가 만료(2027-10-08)되면? 서명 단계가 실패한다. 갱신 절차는 문서에 있다.
- 포크가 워크플로 파일을 고쳐 PR로 올리면? 비밀은 PR에서 보호 환경 밖이라 닿지 못한다.

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 시스템은 회사 맥 없이 소유자가 수동으로 시작하는 워크플로 하나로 「네이티브 프로젝트 생성 → 아카이브 → 서명 → 내보내기 → App Store Connect 업로드」를 끝까지 수행해야 한다.
- **FR-002**: 릴리스 워크플로의 시작 방법은 수동 하나뿐이어야 한다. PR·push·예약 트리거를 두지 않는다(MUST NOT).
- **FR-003**: 서명·업로드 비밀은 보호 환경에만 있고, 보호 환경은 소유자의 승인을 요구하며 배포 브랜치를 `main`으로 제한해야 한다.
- **FR-004**: 워크플로가 참조하는 비밀은 허용 목록의 여섯 개(`IOS_DIST_P12_BASE64`·`IOS_DIST_P12_PASSWORD`·`IOS_PROFILE_BASE64`·`ASC_API_KEY_P8`·`ASC_KEY_ID`·`ASC_ISSUER_ID`)뿐이어야 한다.
- **FR-005**: 비밀은 필요한 단계에만 환경값으로 넘기고, 명령 추적·값 출력으로 로그에 찍지 않아야 한다. 임시 파일로 풀 때는 러너 임시 영역에 쓰고 단계 끝에서 지워야 한다.
- **FR-006**: 서명은 066의 수동 서명(팀 `PGNGG84B39`, 프로파일 「Pocketlog App Store」, `scripts/ios/ExportOptions.plist`)을 그대로 따라야 한다. 인증서는 잡 동안만 있는 임시 키체인에 넣고, 성공·실패와 무관하게 키체인·프로파일·API 키 파일을 지우는 정리 단계를 두어야 한다.
- **FR-007**: 업로드는 App Store Connect API 키로 해야 한다(앱 암호를 쓰지 않는다).
- **FR-008**: IPA·로그 묶음 등 결과물을 아티팩트로 남기지 않아야 한다(퍼블릭 저장소라 누구나 내려받는다). 빌드 캐시도 쓰지 않는다(072: 효과 없음).
- **FR-009**: 시작 직후 사전 점검이 필수 비밀이 모두 비어 있지 않은지와 `ios.buildNumber`가 정수인지 확인하고, 틀리면 빌드 전에 원인을 밝히며 실패해야 한다. 중복 버전·번호의 확인은 이 사전 점검이 아니라 별도 단계 「번호 점검」이 한다(096).
- **FR-010**: 동시에 하나만 실행되어야 하고, 진행 중인 실행을 새 시작이 취소하지 않아야 한다(대기 중이던 실행이 더 새 시작으로 대체되는 것은 허용).
- **FR-011**: 단계별 걸린 시간과 러너 사양(Xcode 버전 포함)을 실행 요약에 남겨야 한다(072 방식).
- **FR-012**: 워크플로 파일을 읽는 계약 테스트가 FR-002·003(워크플로가 보호 환경을 쓰는 것)·004·005·008·010과 정리 단계의 항상 실행을 잠가야 한다. 072의 `native-build.yml` 계약 테스트는 그 파일에만 적용되며, 이 기능은 별도 파일·별도 테스트로 둔다.
- **FR-013**: AGENTS.md의 iOS 배포 절을 이 경로 기본으로 개정하고(맥 절차는 대안으로 유지), 비밀 등록·보호 환경 설정·인증서 만료 갱신 절차를 quickstart에 남겨야 한다.
- **FR-014**: 실제 한 번의 실행으로 처리 통과와 iPhone 설치까지 확인해야 한다(기기 없는 테스트로 갈음하지 않는다, 원칙 V).
- **FR-015**: 무료 러너의 메모리 부족으로 아카이브가 실패하면 빌드 병렬도를 낮춰 이 과제 안에서 통과시킨다. 낮춘 값과 근거는 quickstart에 실측과 함께 남긴다(안 잰 값을 쓰지 않는다, 원칙 V).

### Key Entities

- **서명 비밀 묶음**: 배포 인증서(개인 키 포함)와 비밀번호, 프로비저닝 프로파일, App Store Connect API 키와 두 식별자. 소유자가 보호 환경에 등록하며 코드가 만들지 않는다.
- **릴리스 실행**: 한 번의 수동 시작. 입력은 `main`의 `version`·`buildNumber`, 출력은 App Store Connect의 빌드 하나(처리 통과 여부는 실행 밖에서 확인).

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 소유자는 회사 맥에 손대지 않고 한 번의 시작·승인만으로 빌드를 TestFlight에 올릴 수 있다.
- **SC-002**: 이 경로로 올린 빌드가 처리 통과해 TestFlight 목록에 나타나고 실제 iPhone에 설치된다(ITMS 거부 메일 0건).
- **SC-003**: 필수 비밀이 비었을 때 빌드 시작 후 1분 안에 원인을 밝히고 실패한다(아카이브까지 가지 않는다).
- **SC-004**: `main`이 아닌 브랜치·포크·PR에서 서명 비밀에 닿는 경로가 0이며, 계약 문서(`contracts/workflow-contract.md`) 위반 주입 표의 모든 주입(트리거 추가, 허용 밖 비밀 참조·직접 보간, 아티팩트·캐시 추가, 명령 추적, 정리 단계의 항상 실행 제거, 보호 환경 제거, 권한 확대, 동시 실행 취소, 앱 암호 업로드)이 각각 테스트 실패로 뒤집힌다.
- **SC-005**: 실행이 끝난 뒤(성공·실패 모두) 러너에 서명 키체인·프로파일·API 키 파일이 남지 않았음을 실행 로그로 확인한다.
- **SC-006**: 문서만 읽고 비밀 등록부터 실행·확인까지 따라갈 수 있다(AGENTS.md 개정 + quickstart).

## Assumptions
