# Feature Specification: 백그라운드 자동 일기 생성 기술 검증

**Feature Branch**: `019-background-diary-feasibility`

**Created**: 2026-08-27

**Status**: Draft

**Input**: User description: "매일 설치된 앱에서 백그라운드로 자동으로 일기를 작성할 수 있는지를 기술적으로 검증한다."

## 이 스펙의 성격

이것은 기능 스펙이 아니라 **기술 검증(스파이크)** 스펙이다. 목표는 "백그라운드
자동 일기 생성"을 만드는 것이 아니라, **만들 수 있는지 없는지, 만들 수 있다면
어떤 제약 아래에서인지를 실기기 실측으로 판정하는 것**이다.

- 산출물은 동작하는 자동 생성 기능이 아니라 **YES / NO / 조건부** 결론과 그
  근거(실측 로그)다.
- 결론이 "조건부 가능"이면 그 조건(배터리 최적화 예외 필요, OS 버전 제약,
  최소 유휴 시간 등)을 구체적으로 남긴다.
- 결론이 "NO"이면 왜 안 되는지(OS가 막는 지점, 실측으로 확인된 실패 양상)를
  남긴다. 이는 실패가 아니라 이 검증이 답해야 할 질문에 대한 유효한 답이다.
- 이 검증에서 실제 자동 생성 기능을 구현할지, 구현한다면 어떤 모양일지는
  **이 스펙의 범위 밖**이며 검증 결과를 근거로 별도 스펙에서 결정한다.
- 헌법 원칙 IV(측정 장치를 제품에 들이지 않는다)와 충돌하지 않는다 — 이 검증은
  모델 출력을 채점하거나 비교하지 않는다. "백그라운드 실행이 완주하는가"라는
  운영체제 수준의 사실을 재는 것이지, 일기 품질을 재는 것이 아니다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 잠긴 상태에서 밤새 자동 완주하는가 (Priority: P1)

기기 소유자가 앱을 열지 않고 하루를 보낸다. 하루 경계(04:00)를 넘긴 뒤,
앱을 열지 않은 상태에서도 전날 일기가 자동으로 완성되어 있는지 확인한다.

**Why this priority**: 이것이 검증 요청의 핵심 질문이다 — "매일 설치된 앱에서
백그라운드로 자동으로" 작성되는 것이 이 기능의 존재 이유이므로, 화면을 열지
않고도 생성이 끝까지 도는지가 다른 무엇보다 먼저 답해져야 한다.

**Independent Test**: 실기기에서 인위적으로 하루 경계를 넘기는 조건을 만들고
(화면을 켜지 않은 채, 기기를 대기 상태로 두고) 정해진 시간 뒤 앱을 열어
전날 일기가 존재하는지, 아니면 왜 없는지(로그로) 확인하는 것만으로 이 질문에
답할 수 있다.

**Acceptance Scenarios**:

1. **Given** 기기가 잠금 상태이고 화면이 꺼져 있으며 앱이 최근에 실행되지
   않았다, **When** 하루 경계(04:00)를 넘기고 몇 시간이 지난 뒤 사용자가
   처음으로 앱을 연다, **Then** 전날 일기가 이미 존재하거나, 존재하지 않는
   구체적인 이유(OS가 실행 자체를 막음 / 실행됐으나 시간 내 못 끝남 / 실행
   시도조차 없었음)가 로그로 남아 있다.
2. **Given** 배터리 최적화가 기본값(제한 있음)으로 설정된 기기, **When** 위와
   같은 대기 후 확인, **Then** 배터리 최적화가 실행 여부에 미치는 영향이
   구체적으로 관측된다(실행됨/지연됨/차단됨 중 하나로 판정 가능).

### User Story 2 - 백그라운드 온디바이스 추론이 완주하는가 (Priority: P2)

OS가 백그라운드 실행 자체는 허용하더라도, 그 안에서 실제로 `llama.rn` 추론
(사진이 있으면 VLM 캡션까지 포함해 최대 180초+캡션 시간)이 끝까지 도는지는
별도 질문이다. 백그라운드 실행 창이 열려도 리소스 제약(CPU 스로틀링, 메모리
회수, 시간 제한)으로 추론이 중단될 수 있다.

**Why this priority**: User Story 1이 "실행 기회 자체가 있는가"를 묻는다면,
이것은 "그 기회 안에서 무거운 추론이 실제로 안전하게 끝나는가"를 묻는다.
이 기능의 실용성은 실행 기회가 있다는 것만으로는 부족하고, 이미 알려진 생성
시간(캐릭터별 최대 관측 242초, 헌법 로스터의 "exaone이 가장 느리다")을
버텨야 확정된다.

**Independent Test**: 화면이 꺼진 채 실제 캐릭터 모델로 온디바이스 생성을
트리거해, 완료까지 걸리는 시간과 완주 여부를 포그라운드에서 측정한 값과
대조하는 것으로 독립적으로 확인할 수 있다.

**Acceptance Scenarios**:

1. **Given** 백그라운드 실행 기회를 OS가 허용한 상태, **When** 가장 느린
   캐릭터로 생성이 시작된다, **Then** 생성이 완주하는지, 중단된다면 어느
   단계(모델 로드/추론 중/캡션 중)에서 어떤 신호로 중단되는지가 로그로
   구분된다.
2. **Given** 사진이 있는 하루(캡션 단계를 거침), **When** 백그라운드에서
   생성이 트리거된다, **Then** 캡션 단계와 생성 단계가 모두 화면 없이
   완주하는지 별도로 확인된다.

### User Story 3 - 검증 결과가 다음 결정에 쓸 수 있게 기록되는가 (Priority: P3)

이 검증의 목적은 결론을 내는 것 자체보다, 그 결론을 근거로 이후 스펙 작성
여부를 사람이 결정할 수 있게 남기는 것이다.

**Why this priority**: 앞의 두 스토리가 실측 자체라면, 이것은 그 실측이
헌법 원칙 V("관측된 사실과 추측을 구분해 기록한다")를 만족하는 형태로
남는지를 보장한다. 실측 없이 "아마 될 것이다"로 다음 스펙을 시작하면 반복된
실패 패턴(원칙 V 위반)을 다시 만든다.

**Independent Test**: 검증 종료 후 별도 문서(조사 결과)만 읽고 제3자가
"이 기기·이 OS 버전에서 배경 자동 생성이 되는지 안 되는지, 되면 어떤
조건에서인지"를 재현 없이 이해할 수 있으면 충족된다.

**Acceptance Scenarios**:

1. **Given** 검증이 끝났다, **When** 결과 문서를 읽는다, **Then** 실측값과
   그 실측이 이뤄진 기기·OS 버전·조건이 함께 적혀 있어 나중에 다른 기기에서
   달라질 수 있음이 구분된다.
2. **Given** 결론이 "조건부 가능"이다, **When** 결과 문서를 읽는다, **Then**
   그 조건이 사람이 판단을 내릴 수 있을 만큼 구체적으로(막연한 "최적화 필요"가
   아니라 어떤 설정·권한·타이밍인지) 적혀 있다.

---

### Edge Cases

- 기기 제조사(삼성 등)의 자체 배터리 관리가 OS 표준 백그라운드 정책 위에 추가
  제약을 얹는 경우, 표준 Android 정책만으로는 예측할 수 없는 결과가 나올 수
  있다 — 이 경우 결론에 "이 기기 제조사에 한정된 관측"임을 명시해야 한다.
- 앱이 최근에 강제 종료(스와이프로 종료)된 경우와 재부팅 직후(Direct Boot로
  저장소가 아직 복호화되지 않은 경우, AGENTS.md 기존 실측)는 서로 다른 실패
  양상을 낼 수 있다 — 두 상태를 구분해 각각 확인한다.
- OS 표준 주기적 작업 예약은 정확한 시각을 보장하지 않는다(설계상의 특성이지
  결함이 아니다) — 하루 경계(04:00) 직후를 노려도 OS가 실제 실행 시각을
  앞뒤로 밀 수 있다. "정확히 몇 시에" 실행되는지가 아니라 "그날 안에"
  실행되는지를 확인 기준으로 삼는다.
- 백그라운드 실행 중 사용자가 기기를 집어 들어 화면을 켜는 경우, 진행 중이던
  생성이 중단 없이 이어지는지, 아니면 재시작되는지도 관측 대상이다(원칙
  IV의 "진행 중 노출 금지"와는 무관한 별도 질문 — 여기서는 완주 여부만 본다).
- 배터리 잔량이 낮아 OS가 절전 모드에 들어간 상태에서의 동작은 이번 검증의
  필수 범위가 아니다(아래 Assumptions 참고) — 관측되면 기록하되, 별도로
  찾아 나서지 않는다.
- 사진·위치 권한이 백그라운드 실행 시점에 회수되어 있으면, 그 하루는 사진이
  0장인 것과 구분되지 않을 수 있다(`none`과 `unknown`이 004부터 이미 값에서
  갈리는 것과 같은 문제가 권한 축에서도 생길 수 있다) — 권한 상태를 실행
  직전에 별도로 확인해 이 둘을 가른다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 검증은 실기기(에뮬레이터 아님)에서 수행해야 한다(MUST) — 헌법
  원칙 V·저장소 관례(AGENTS.md)가 이미 "합성 데이터/시뮬레이터로 온디바이스
  결론을 내지 않는다"를 확립했다.
- **FR-002**: 검증은 최소 하나의 실제 안드로이드 OS 버전과 하나의 배터리
  최적화 설정(기본값)에서 수행해야 한다(MUST). 여러 OS 버전·제조사 조합을
  모두 도는 것은 이 검증의 범위가 아니다(Assumptions 참고).
- **FR-003**: 검증은 화면이 꺼지고 기기가 잠긴 상태에서 트리거된 실행만을
  "백그라운드"로 인정해야 한다(MUST) — 화면이 켜진 채 앱이 뒤로만 간 상태
  (foreground service 급의 약한 백그라운드)는 이 검증이 답하려는 질문과
  다르므로 별도로 구분해 기록한다.
- **FR-004**: 검증은 실행 시도 자체가 있었는지, 있었다면 완주했는지, 중단됐다면
  어느 단계에서 중단됐는지를 구분해 기록해야 한다(MUST) — "일기가 없다"는
  결과 하나로는 원인(스케줄 안 됨/실행됐지만 킬됨/추론 중 실패)을 구분할 수
  없어 다음 결정에 쓸 수 없다.
- **FR-005**: 검증은 헌법이 이미 정한 경계(원칙 IV: `llama-port.ts`가 유일한
  네이티브 지표 경계, 원칙 II: 프롬프트는 `prompt.ts`에만 있음)를 검증
  목적으로도 우회하지 않아야 한다(MUST NOT) — 백그라운드 트리거 방식을
  실험하는 것이지 생성 파이프라인 자체를 다시 만드는 것이 아니다.
- **FR-006**: 검증 중 생성된 일기(성공했다면)는 기존 판정 갈래(원칙 IV, 4갈래)
  를 그대로 거쳐야 한다(MUST) — 백그라운드라는 이유로 판정을 건너뛰거나
  완화하지 않는다.
- **FR-007**: 검증 결과는 사람이 읽을 수 있는 문서(실측 로그 포함)로
  남아야 한다(MUST) — 코드나 커밋 메시지에만 흩어져 있으면 원칙 V의
  "관측된 사실과 추측을 구분해 기록한다"를 만족하지 못한다.
- **FR-008**: 검증은 최소한 하루치(24시간) 이상의 실제 대기 시간을 포함한
  관측을 최소 1회 수행해야 한다(MUST) — 짧은 시간 안에 강제로 트리거하는
  것만으로는 "매일"이라는 요청의 반복 주기 조건을 검증하지 못한다.
- **FR-009**: 검증 도중 앱이나 기기 설정을 바꿔야 한다면(예: 배터리 최적화
  예외 부여) 그 변경 내용과 그것이 없을 때의 결과를 함께 기록해야
  한다(MUST) — "예외를 줘야만 된다"와 "안 줘도 된다"는 결론상 완전히 다른
  조건부 답이다.
- **FR-010**: 검증은 사진·위치 권한이 이미 부여된 기기에서, 앱을 오래 열지
  않은 뒤의 백그라운드 실행 시점에도 그 권한이 여전히 유효한지를 확인해야
  한다(MUST) — 안드로이드는 오래 쓰지 않은 앱의 권한을 자동 회수하거나
  "한 번만 허용"을 만료시킬 수 있으며, 이것이 백그라운드 실행과 겹치면
  사진 신호가 조용히 `unknown`으로 빠지는 실패가 생길 수 있다. 권한 상실이
  관측되면 이는 실행 자체의 실패(FR-004)와 구분되는 별도 실패 양상으로
  기록한다.

### Key Entities

이 검증은 새로운 영속 데이터 엔티티를 도입하지 않는다. 기존 일기 엔티티
(`DiaryEntry`, `src/diary/`)를 그대로 사용해 "백그라운드에서 생성된 일기가
포그라운드 생성과 구별되지 않는 정상적인 일기인지"를 확인한다.

- **검증 실행 기록**: 이 스펙 전용의 임시 관측 기록(트리거 시각, 완주 여부,
  중단 지점, 기기 상태)이다. 제품 데이터가 아니므로 앱 내부에 영속화하지
  않고 검증 문서/로그에만 남긴다(원칙 IV — 측정 장치를 제품에 들이지 않는다).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 검증이 끝나면 "백그라운드 자동 일기 생성이 가능한가"라는
  질문에 대해 YES / NO / 조건부 중 하나의 명확한 결론이 근거(실측 로그)와
  함께 존재한다.
- **SC-002**: 결론이 조건부일 경우, 그 조건은 별도 개발 없이 설정 변경만으로
  재현 가능한 수준으로 구체적이다(예: 특정 배터리 최적화 예외 설정, 특정
  안드로이드 버전 이상).
- **SC-003**: 최소 1회의 24시간 이상 실측에서, 백그라운드 실행이 실제로
  시도됐는지 여부가 (성공/실패와 무관하게) 100% 확인 가능하다 — "시도조차
  안 됐는지 몰랐다"는 결과가 나오지 않는다.
- **SC-004**: 검증 결과 문서만으로, 이 검증에 참여하지 않은 사람이 이후
  "자동 생성 기능을 실제로 만들지" 여부를 결정할 수 있다.
- **SC-005**: 같은 실측에서, 실행이 완주했더라도 사진·위치 권한이 그 사이
  회수되어 있었는지 여부가 구분되어 기록된다 — "일기는 나왔는데 권한이
  죽어 있었는지는 모른다"는 결과가 나오지 않는다.

## Assumptions

- 검증은 저장소가 이미 가진 캐릭터 로스터와 생성 파이프라인을 그대로
  사용한다 — 백그라운드 전용의 더 가볍거나 다른 모델을 새로 만들지 않는다.
- 검증 대상 기기는 저장소가 이미 실기기 검증에 써 온 기기(AGENTS.md 기준
  SM-G986N 등 보유 안드로이드 기기) 중 하나로 충분하다 — 모든 제조사·모든
  OS 버전을 조사하는 것은 범위 밖이며, 결론에는 "이 기기·이 OS 버전 기준"
  임을 명시한다.
- 저전력 모드(배터리 세이버)나 네트워크 상태 등 부차적 변수는 이번 검증의
  필수 확인 항목이 아니다 — 기본 설정(배터리 최적화 기본값, 일반 사용
  패턴)에서의 결과를 우선 확인하고, 저전력 모드는 관측되면 기록하되 별도로
  찾아 나서지 않는다.
- "매일"의 반복 스케줄링은 **OS 표준 주기적 작업 예약**(안드로이드
  WorkManager류의 API)만 시도한다 — 정확한 시각에 깨우는 alarm 계열
  API는 쓰지 않는다(Clarifications 참고). 배터리 최적화를 이미 고려해
  설계된 표준 경로에서의 실행 가능성이 이 검증의 질문이며, 여러
  스케줄링 방식을 비교 평가하는 것은 범위 밖이다. 이 선택 때문에
  결론은 "OS 표준 주기적 작업 예약 경로 기준"으로 한정되며, 더 정확한
  시각 보장이 필요한 방식(alarm 계열)의 가능성은 이 검증이 답하지
  않는다.
- **등록 시 최소 반복 간격은 API가 허용하는 최솟값(15분)으로 설정한다**
  (FR-008의 24시간과는 다른 축) — 24시간 동안 시도가 1~2회뿐이면
  (기본 간격인 12시간 기준) 표본이 너무 적어 "가끔 됐다/가끔 안 됐다"
  같은 우연을 배제하기 어렵다. 간격을 좁히는 것은 **같은 24시간
  방치 구간 안에서 표본 수를 늘리는 것**이지, 방치해야 하는 시간
  자체를 줄이는 것이 아니다 — Doze·앱 대기 버킷 같은 배터리 최적화
  조건은 기기를 실제로 오래 안 건드려야 걸리므로, 간격만 좁히고
  확인하려는 마음에 도중에 화면을 켜면 그 순간 "화면 없이 방치"라는
  전제(FR-003)가 깨진다.
- 검증 중 발견된 실패가 이 저장소의 코드 결함이 아니라 OS/기기 정책에 의한
  근본적 제약으로 보이면, 그것을 우회하는 추가 구현(예: 사용자에게 배터리
  최적화 예외를 요청하는 화면)을 만들지 여부는 이 스펙에서 결정하지 않고
  결론에 "다음 스펙에서 고려할 사항"으로만 남긴다.
