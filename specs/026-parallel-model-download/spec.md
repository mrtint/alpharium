# Feature Specification: 모델 병렬·동시 내려받기

**Feature Branch**: `026-parallel-model-download`

**Created**: 2026-08-31

**Status**: Draft

**Input**: User description: "10번 진행하자. 여기에는 지금 모델을 여러개를 동시에 받을수도 없게 되어있는데 모델을 동시에 받을 수도 있게 만드는 기능을 추가하자."

---

## 배경과 범위

로드맵 10번("LLM 모델 다운로드 속도 개선")을 두 갈래로 구현한다.

1. **여러 모델 동시 내려받기** — 003 FR-020의 "한 번에 하나" 제약을 푼다. 사용자가 여러
   캐릭터를 미리 준비할 때 대기 시간 총합이 줄어든다.
2. **한 파일 세그먼트 병렬 내려받기** — 모델 파일 하나를 여러 구간(HTTP Range)으로 나눠
   병렬 수신해 단일 모델 받는 시간 자체를 줄인다.

**범위 밖**:

- CDN 배포처 튜닝, 압축 전송(로드맵 10번 아이디어의 일부이나 이 저장소가 배포처를 통제하지
  않는다).
- 동시성 상한·큐잉. 사용자가 누른 만큼 전부 동시에 받는다(무제한).
- 세그먼트 개수를 파일 크기·네트워크 상태로 **코드가 정하는 것**. 사람이 상수로 못박는다.

**헌법 점검** (제약이 아니라 이미 지켜지는 것을 확인):

- 원칙 IV — 세그먼트 속도·구간별 처리량을 재서 비교·저장·표시하는 코드를 넣지 않는다.
  진행률 타입은 `{ character, fraction }` 둘로 유지되며 세그먼트 개수가 들어갈 자리가 없다.
- 원칙 III — 세그먼트 계획 계산은 자산키·바이트만 다루고 캐릭터를 모른다. 화면으로 나가는
  것은 기존 `fraction` 하나뿐. 전송 방식(세그먼트/폴백)은 화면·판정 계층에 노출되지 않는다.
- 로스터 MUST("사용자가 고른 캐릭터의 모델만 내려받는다") — 동시 내려받기는 사용자가 각각
  누른 캐릭터만 받는다. `prepareAll()`·`allAssets()` 같은 일괄 경로를 만들지 않는다.
- 원칙 V — 서버가 Range를 지원하는지, `Content-Length`를 주는지는 실기기 실측으로 확인하며,
  모르는 상태를 지어내지 않고 안전한 단일 스트림으로 폴백한다. 세그먼트 개수 상수는 잠정으로
  두고 실기기에서 확정한다(003의 `SPACE_HEADROOM` 전례).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 여러 캐릭터를 동시에 준비한다 (Priority: P1)

사용자가 캐릭터 목록에서 캐릭터 A의 "준비하기"를 누르고, A가 받는 중인 상태에서 캐릭터 B의
"준비하기"도 누른다. 지금까지는 "A를 받는 중이라 지금은 받을 수 없다. A를 멈추면 받을 수
있다"는 거부 안내가 떴다. 이제는 A와 B가 나란히 받아지고, 두 줄 모두에 진행 표시와 "멈추기"
버튼이 보인다.

**Why this priority**: 이 스토리 하나만 구현해도 사용자가 여러 캐릭터를 순차로 기다리지 않고
한꺼번에 준비할 수 있어 즉시 가치가 있다. 세그먼트 병렬 없이도 독립적으로 동작한다.

**Independent Test**: 캐릭터 두 개를 연달아 "준비하기"로 눌러, 둘 다 진행 표시가 뜨고 각각
독립적으로 완료·검증되는지 확인한다. 세그먼트 병렬은 켜지 않아도 된다.

**Acceptance Scenarios**:

1. **Given** 캐릭터 A가 받는 중, **When** 캐릭터 B의 "준비하기"를 누른다, **Then** B도 받기
   시작하고 A·B 두 줄에 진행 표시와 멈추기가 동시에 보인다.
2. **Given** 캐릭터 A가 받는 중, **When** 같은 캐릭터 A의 "준비하기"를 다시 누른다, **Then**
   중복 요청은 거부되고(같은 캐릭터 재요청 방지), A의 진행 표시는 흔들리지 않는다.
3. **Given** 캐릭터 A·B가 동시에 받는 중, **When** A의 "멈추기"만 누른다, **Then** A는 멈추고
   B는 영향 없이 계속 받는다.
4. **Given** 캐릭터 A·B·C가 동시에 받는 중이다가 사용자가 다른 탭으로 이동했다 돌아온다,
   **When** 캐릭터 목록이 다시 뜬다, **Then** 여전히 받는 중인 것 전부에 "받는 중…" 표시가
   복원된다(백분율은 다음 진행 콜백에서 붙는다 — 0%로 채우지 않는다).
5. **Given** 캐릭터 세 개를 동시에 받으려 하는데 셋을 다 두기에는 공간이 부족하다, **When**
   세 번째 "준비하기"를 누른다, **Then** 이미 받는 중인 것들의 남은 용량을 뺀 여유로 판정해
   `insufficient-space`를 알린다(모델 크기는 말하지 않는다).

### User Story 2 - 한 모델을 더 빨리 받는다 (Priority: P2)

사용자가 캐릭터 하나의 "준비하기"를 누른다. 서버가 구간 요청을 지원하면 파일이 여러 조각으로
나뉘어 병렬로 받아지고, 단일 스트림으로 받을 때보다 빨리 완료된다. 사용자에게는 평소와 같은
진행 표시만 보인다 — 조각 개수나 조각별 속도는 드러나지 않는다.

**Why this priority**: 첫 캐릭터를 급히 준비하는 경우(온보딩 직후 등)에 체감이 크다. 다만
Story 1 없이도, Story 1 있이도 각각 독립적으로 가치가 있어 P2다.

**Independent Test**: 같은 모델을 세그먼트 병렬 켬/끔으로 두 번 받아 완료까지 걸린 벽시계
시간을 같은 실행 안에서 대조한다(003의 md5 채록이 같은 실행에서 원본·리사이즈본을 대조한
방식). 세그먼트 켬 쪽이 더 빠르거나 최소한 느리지 않아야 한다.

**Acceptance Scenarios**:

1. **Given** 모델 파일을 받기 시작한다, **When** 서버가 구간 요청과 전체 크기를 준다,
   **Then** 파일이 사람이 정한 개수의 구간으로 나뉘어 병렬로 받아지고, 모든 구간이 끝나면
   하나의 온전한 파일로 합쳐진다.
2. **Given** 세그먼트 병렬로 받는 중, **When** 진행 표시를 본다, **Then** 화면에는 캐릭터
   단위 `fraction` 하나만 보인다 — 구간 개수·구간별 바이트·구간별 속도가 보이지 않는다.
3. **Given** 세그먼트 병렬로 다 받았다, **When** 무결성 지문을 확인한다, **Then** 합쳐진
   파일이 로스터의 지문과 일치한다(불일치면 `verification-failed`, 파일을 남기지 않는다).
4. **Given** 여러 모델을 동시에(Story 1) 세그먼트 병렬로(Story 2) 받는다, **When** 전체가
   진행된다, **Then** 열리는 연결 수는 (동시 모델 수 × 사람이 정한 구간 수)를 넘지 않는다.

---

### User Story 3 - 서버가 구간 요청을 지원하지 않아도 받아진다 (Priority: P1)

사용자가 "준비하기"를 누른다. 서버가 구간 요청을 지원하지 않거나 전체 크기를 알려주지
않으면, 세그먼트 병렬을 시도하지 않고 조용히 기존의 단일 스트림 방식으로 받는다. 사용자는
차이를 알아채지 못하며, 다운로드는 성공한다.

**Why this priority**: 폴백이 없으면 서버가 구간 요청을 거부하는 순간 모델을 아예 못 받게
된다 — 회귀. Story 2보다 우선한다.

**Independent Test**: 구간 요청을 무시하는(전체 본문을 주는) 응답을 대역으로 흉내 내고, 그
경우 단일 스트림 경로로 완주하는지 계약 테스트로 확인한다.

**Acceptance Scenarios**:

1. **Given** 모델 파일을 받기 시작한다, **When** 서버가 구간 요청을 무시하고 전체 본문으로
   응답한다, **Then** 세그먼트 병렬을 포기하고 단일 스트림으로 받아 성공한다.
2. **Given** 모델 파일을 받기 시작한다, **When** 서버가 전체 크기를 주지 않는다, **Then**
   구간을 나눌 수 없으므로 단일 스트림으로 받는다.
3. **Given** 단일 스트림 폴백으로 받는 중, **When** 사용자가 "멈추기"를 누른다, **Then**
   기존 이어받기(003 FR-014~016)가 그대로 동작해 이어받을 수 있는 상태로 남는다.

---

### User Story 4 - 받다 만 세그먼트 다운로드를 이어받는다 (Priority: P2)

사용자가 세그먼트 병렬로 큰 모델을 받는 도중 앱을 종료하거나 "멈추기"를 누른다. 나중에 같은
캐릭터의 "이어받기"를 누르면, 각 구간이 처음부터가 아니라 이미 받은 지점부터 다시 받아진다.

**Why this priority**: GB 단위 파일에서 이어받기를 버리면 003 FR-014~016(모바일에서 큰 파일)의
취지와 정면으로 어긋난다. 다만 세그먼트 병렬(Story 2)에 딸린 기능이라 P2다.

**Independent Test**: 각 구간의 받은 바이트 수를 담은 재개 상태를 만들어 두고, "이어받기"가
각 구간을 남은 구간부터 다시 요청하는지, 완료 후 합쳐진 파일이 온전한지 계약 테스트로
확인한다.

**Acceptance Scenarios**:

1. **Given** 세그먼트 병렬 다운로드가 절반쯤 진행된 상태에서 멈췄다, **When** 같은 캐릭터의
   "이어받기"를 누른다, **Then** 각 구간이 이미 받은 바이트 다음부터 이어져 받아지고, 전부
   끝나면 온전한 파일이 된다.
2. **Given** 세그먼트 재개 상태가 기기에 남아 있고 앱을 껐다 켰다, **When** 캐릭터 목록이
   뜬다, **Then** 그 캐릭터는 "받다 멈춤 — 이어받을 수 있음"으로 보인다.
3. **Given** 세그먼트 재개 상태의 한 구간이 손상됐거나 서버 파일이 바뀌었다, **When**
   이어받아 합친 파일의 지문이 로스터와 어긋난다, **Then** `verification-failed`로 판정하고
   파일을 남기지 않는다(다시 처음부터 받게 한다).

---

### Edge Cases

- **같은 캐릭터를 동시에 두 번 요청**: 두 번째는 거부된다(같은 캐릭터 중복 방지). 서로 다른
  캐릭터의 동시 요청만 허용한다.
- **동시 다운로드 중 하나가 실패**: 실패한 캐릭터만 진행 표시가 걷히고, 나머지는 계속 받는다.
  실패한 캐릭터는 다시 "준비하기"를 누를 수 있다.
- **동시 다운로드 중 공간 소진**: 시작 시점 판정을 통과한 여러 다운로드가 진행 중 공간을 다
  써 버릴 수 있다. 그때는 개별 다운로드가 네트워크/쓰기 실패로 드러나며, 이미 받은 다른
  다운로드는 영향받지 않는다.
- **세그먼트 병렬 중 일부 구간만 실패**: 그 다운로드 전체가 실패로 판정된다. 부분 파일은
  이어받기 대상으로 남거나(재개 정보가 있으면) 정리 대상이 된다.
- **세그먼트 개수보다 파일이 작다**: 파일이 `MIN_SEGMENT_BYTES`(사람이 정한 상수)의 두 배
  미만이면 구간으로 쪼개지 않고 단일 스트림으로 받는다 — 구간 수는 1 또는 `SEGMENT_COUNT`
  둘 중 하나다.
- **비전 모델(011)과 캐릭터 모델을 동시에**: 011은 이미 캐릭터와 동시 수신이 가능했다. 이
  기능으로 비전 모델도 세그먼트 병렬을 얻되, 011의 코드는 바뀌지 않는다.
- **탭 이동 후 복귀**: 받는 중인 것 전부의 "받는 중…" 표시가 복원된다. 백분율은 다음 진행
  콜백에서 붙으며 0%로 채우지 않는다(원칙 V).
- **단일 스트림 폴백과 세그먼트 재개가 섞인 기기 상태**: 한 캐릭터는 단일 스트림 이어받기
  정보를, 다른 캐릭터는 세그먼트 재개 정보를 가질 수 있다. 재개 시 각자의 방식으로 이어받는다.

## Requirements *(mandatory)*

### Functional Requirements — 동시 내려받기

- **FR-001**: 시스템은 서로 다른 캐릭터의 모델을 **동시에** 내려받을 수 있어야 한다. 003
  FR-020의 "한 번에 하나" 제약을 제거한다.
- **FR-002**: 동시 내려받기 개수에 상한을 두지 않는다. 사용자가 "준비하기"를 누른 캐릭터
  전부가 병행 수신된다.
- **FR-003**: 같은 캐릭터에 대한 중복 "준비하기" 요청은 거부되어야 한다. `busy` 거부 갈래를
  이 목적으로 유지한다(무엇을 받는 중인지 알린다 — 그 캐릭터 자신).
- **FR-004**: "멈추기"는 **캐릭터별로** 동작해야 한다. 한 캐릭터를 멈춰도 동시에 받는 다른
  캐릭터는 영향받지 않는다.
- **FR-005**: 진행 상태는 **받는 중인 캐릭터 전부**를 표현할 수 있어야 한다. 화면은 여러 줄에
  동시에 진행 표시와 "멈추기"를 그린다.
- **FR-006**: 탭 이동 후 복귀 시 받는 중인 캐릭터 **전부**의 진행 표시가 복원되어야 한다.
  복원된 표시는 백분율 없이 "받는 중…"으로 시작하며 0%로 채우지 않는다.
- **FR-007**: 공간 판정은 이미 받는 중인 다운로드들의 **남은 용량 합**을 여유에서 뺀 뒤
  수행해야 한다. 부족하면 `insufficient-space`를 알리되 모델 크기는 말하지 않는다.
- **FR-008**: `prepareAll()`·`allAssets()` 같은 "전부 한 번에" 경로를 만들지 않는다(로스터
  MUST).
- **FR-009**: "진행 중" 상태는 메모리에만 둔다(003과 동일). 저장소에 남기면 앱이 죽었을 때
  영원히 진행 중인 캐릭터가 생긴다.
- **FR-010**: 008이 만든 거부 안내(`DownloadRejection`, `download-view.ts`)의 "거부가 아직
  참인가 — 아니면 자동 소멸" 규칙은 유지되어야 한다. 판정이 여러 다운로드를 다루도록만
  확장한다.

### Functional Requirements — 세그먼트 병렬 내려받기

- **FR-011**: 시스템은 서버가 구간 요청(HTTP Range)과 전체 크기를 제공할 때, 모델 파일 하나를
  **사람이 정한 개수의 구간**으로 나눠 병렬로 내려받아야 한다.
- **FR-012**: 구간 개수는 사람이 정한 상수여야 한다. 코드가 파일 크기·네트워크 상태를 보고
  개수를 정하지 않는다(원칙 V, 012·021·023의 상수 못박기 전례). 상수의 초기값은 잠정이며
  실기기 실측으로 확정한다(003 `SPACE_HEADROOM` 전례).
- **FR-013**: 파일이 사람이 정한 **최소 구간 크기**의 두 배보다 작아 나누기 어려우면,
  구간으로 쪼개지 않고 **단일 스트림으로** 내려받아야 한다(구간 수는 1 또는 `SEGMENT_COUNT`
  둘 중 하나이며 중간 값을 만들지 않는다 — research.md §3). 최소 구간 크기도 사람이 정한
  상수다.
- **FR-014**: 서버가 구간 요청을 지원하지 않거나 전체 크기를 주지 않으면, 세그먼트 병렬을
  시도하지 않고 **기존 단일 스트림 방식으로 폴백**해야 한다. 폴백은 조용하다 — 사용자에게
  실패로 보이지 않는다.
- **FR-015**: 세그먼트 병렬로 받은 조각들은 하나의 온전한 파일로 합쳐진 뒤, 003의 무결성 지문
  검증(FR-021)을 그대로 거쳐야 한다. 지문이 어긋나면 `verification-failed`이며 파일을 남기지
  않는다.
- **FR-016**: 세그먼트 병렬 진행률은 캐릭터 단위 `fraction` **하나**로만 밖에 나가야 한다.
  구간 개수·구간별 바이트·구간별 속도가 진행 상태 타입에 들어갈 자리가 없어야 한다(원칙
  III·IV — 003 `DownloadProgress`의 불변식 유지).
- **FR-017**: 전송 방식(세그먼트/폴백) 판정은 기기 통로 계층에 격리되어야 한다. `acquisition.ts`
  (비즈니스 로직)와 `download-view.ts`(순수 판정)는 전송 방식을 몰라야 한다 — 003이 그은
  "판정·규칙은 순수, 기기 통로는 포트 하나" 경계를 유지한다.
- **FR-018**: 세그먼트 계획 계산(전체 크기 → 구간 나누기, 재개 시 남은 구간 계산, 진행 병합,
  완료 판정)은 **순수 함수**로 분리되어 기기 없이 검증 가능해야 한다.
- **FR-019**: 세그먼트 계획·전송 코드는 자산키·바이트·구간 정보만 다루고 **캐릭터를 몰라야**
  한다(원칙 III). `Character` 타입을 import하지 않는다.
- **FR-020**: 열리는 동시 연결 수는 (동시 모델 수 × 구간 수 상수)로 상한이 지어져야 한다.
  구간 수가 상수이므로 이 곱은 통제된다.

### Functional Requirements — 세그먼트 이어받기

- **FR-021**: 세그먼트 병렬 다운로드가 멈추면(사용자 "멈추기" 또는 앱 종료 후 재개 가능한
  경우), 각 구간이 이미 받은 바이트 수를 담은 **재개 상태**가 기기에 남아야 한다.
- **FR-022**: "이어받기"는 재개 상태의 각 구간을 **남은 구간부터** 다시 요청해야 한다. 처음부터
  다시 받지 않는다.
- **FR-023**: 세그먼트 재개 상태가 있는 캐릭터는 003의 준비 상태 판정에서 `partial`(이어받을 수
  있음)로 보여야 한다.
- **FR-024**: 세그먼트 재개로 합쳐진 파일의 지문이 로스터와 어긋나면(구간 손상·서버 파일 변경)
  `verification-failed`로 판정하고 파일을 남기지 않는다 — 처음부터 다시 받게 한다.
- **FR-025**: 세그먼트 재개 상태는 003의 상태 파일(`state.json`) 스키마 안에 담기되, 기존 단일
  스트림 재개 상태(`PausedDownload`)와 구분되는 형태여야 한다. 한 캐릭터가 둘 중 하나만
  가진다.
- **FR-026**: 앱이 갑자기 죽어 재개 상태를 기록하지 못한 경우, 부분 파일은 남되 이어받을 수
  없는 상태(`partial` + `resumable: false`)로 판정되어야 한다 — 003 FR-006a가 이미 구분하는
  갈래.

### Functional Requirements — 회귀·경계

- **FR-027**: `src/vision/acquisition.ts`(011)는 이 기능으로 **코드가 바뀌지 않아야** 한다.
  비전 모델은 `DownloadPort` 계약 뒤에서 세그먼트 병렬과 폴백을 얻는다.
- **FR-028**: 003의 계약 파일(`contracts/acquisition.md`, `contracts/storage.md`)이 정의한
  기존 갈래(`busy`/`insufficient-space`/`network`/`verification-failed`, `ready`/`not-
  downloaded`/`partial`/`unusable`)는 제거되지 않는다. 확장만 한다.
- **FR-029**: 008의 계약(`contracts/download-view.md`)이 정의한 "거부 안내는 하나뿐, 자동
  소멸" 불변식은 유지된다.
- **FR-030**: 새로 도입하는 사람이 정한 상수(구간 수, 최소 구간 크기)는 소스에서 `readonly`
  리터럴로 못박고, 계약 테스트가 소스를 직접 읽어 잠근다(007·009·012의 관례).

### Key Entities

- **동시 진행 슬롯**: 지금 받는 중인 캐릭터들의 집합. 각 캐릭터에 멈추기 핸들이 딸린다.
  **메모리에만** 있다(앱이 죽으면 사라지는 것이 옳다).
- **세그먼트 계획**: 전체 파일 크기와 구간 수로 계산되는 구간 목록(각 구간의 시작·끝
  오프셋). 순수 함수의 산출물이며 캐릭터를 모른다.
- **세그먼트 재개 상태**: 각 구간이 이미 받은 바이트 수. 기기의 상태 파일에 저장되며 003의
  `PausedDownload`(단일 스트림 재개)와 구분된다.
- **전송 결과**: 세그먼트/폴백 어느 경로든 003의 `TransferOutcome`(`completed`/`paused`/
  `failed`) 세 갈래로 수렴한다 — 상위 계층은 방식을 구분하지 못한다.
- **진행 상태**(`DownloadProgress`, 003에서 그대로): `{ character, fraction }`. 세그먼트
  정보가 여기 들어갈 자리가 없다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자가 캐릭터 두 개 이상을 연달아 "준비하기"로 누르면, 두 번째부터 거부되지
  않고 전부 동시에 받아진다(실기기에서 최소 2개 동시 수신 관찰).
- **SC-002**: 동시에 받는 캐릭터 중 하나를 "멈추기"로 멈춰도 나머지는 중단 없이 완료된다.
- **SC-003**: 탭을 이동했다 돌아오면 받는 중인 캐릭터 전부에 "받는 중…" 표시가 복원된다
  (하나라도 누락되지 않는다).
- **SC-004**: 서버가 구간 요청을 지원하는 모델은, 같은 실행 안에서 세그먼트 병렬 켬 쪽이 끔
  쪽보다 완료까지 걸린 벽시계 시간이 **더 짧거나 최소한 길지 않다**(실기기 대조 1회). 켬/끔

- **SC-005**: 세그먼트 병렬로 받은 모델의 무결성 지문이 로스터 값과 일치한다(단일 스트림으로

- **SC-007**: 세그먼트 재개 상태가 주어지면 각 구간이 남은 구간부터 다시 요청되어(처음부터
  받지 않음) 완료되고, 합쳐진 파일이 온전하다(계약 테스트).
- **SC-008**: 사용자 화면·저장된 진행 상태 어디에도 구간 개수·구간별 바이트·구간별 속도·전송
  방식이 노출되지 않는다(계약 테스트가 타입과 화면 문자열에서 검사).
- **SC-009**: `src/vision/acquisition.ts`의 소스가 이 기능 전후로 바이트 단위 동일하다
  (git diff 0줄).
- **SC-010**: 기기 없는 테스트 전부 통과, lint(eslint·tsc·헌법 검사·prettier) 클린.
- **SC-011**: 새로 도입한 상수(구간 수, 최소 구간 크기)를 소스에서 다른 값으로 바꾸면 계약
  테스트가 실패한다(위반 주입으로 확인).

## Assumptions

- 로스터의 모델은 전부 HuggingFace(`huggingface.co/.../resolve/main/...`)에서 받으며, HF는
  302 리다이렉트로 CDN(cloudfront/S3)에 넘긴다. 리다이렉트 후 Range·`Content-Length`가
  유지되는지는 **실기기 실측으로 확인**한다(현 시점 미확인). 유지되지 않으면 폴백 경로가
  기본이 되며, 그 경우에도 동시 내려받기(Story 1)는 독립적으로 유효하다.
- `expo-file-system` 57의 `File.createDownloadTask`는 단일 스트림 다운로드만 제공하며,
  세그먼트 병렬은 이 저장소가 직접 구현한다(여러 Range fetch → 파일 오프셋 쓰기 → 병합).
- 세그먼트 이어받기의 "받는 도중 앱 강제 종료" 타이밍은 실기기에서 정밀 제어가 어렵다
  (012의 "기기 시각 못 바꿔 미확인", 025의 "portrait 고정" 계열). 이 갈래는 계약 테스트로
  잠그고, 실기기에서 재현 불가한 부분은 `findings.md`에 "미확인"으로 명시한다(원칙 V).
- Range 미지원 서버는 실제 로스터에서 만나지 않을 수 있어, 폴백 경로가 실기기에서는 dead
  path로 남을 수 있다 — 계약 테스트가 대역으로 이 경로를 검증한다.
- 새 네이티브 모듈을 추가하지 않는다(HTTP fetch·파일 쓰기는 기존 통로). 따라서 012 기준상
  debug 실기기 확인 1회로 충분하며 release 재확인은 불필요하다. (세그먼트 다운로더가 순수
  JS + 기존 fetch/파일 API이므로 R8·JNI 경계를 건드리지 않는다.)
- 동시 다운로드의 공간 판정은 근사다 — 시작 시점에 "이미 받는 중인 것들의 남은 용량"을
  빼지만, 진행 중 서버가 준 실제 크기가 예상과 다를 수 있다. 그 경우는 개별 다운로드의
  네트워크/쓰기 실패로 드러나며 다른 다운로드를 망가뜨리지 않는다.
