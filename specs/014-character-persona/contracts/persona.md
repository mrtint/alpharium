# 계약: 캐릭터 페르소나

**Feature**: 014-character-persona | **모듈**: `src/diary/persona.ts`

**기기를 모른다.** 순수 데이터와 순수 함수뿐이므로 전부 기기 없이 검증된다.

---

## 이 자리가 무엇을 지키는가

**캐릭터 내부 식별자와 사용자가 보는 이름 사이의 유일한 통과 지점이다.**

003의 `roster.ts`가 캐릭터→모델 파일의 유일한 통과 지점이듯, 이 파일은 캐릭터→
사람이 읽는 이름의 유일한 통과 지점이다. 화면 두 곳(`CharacterListScreen`,
`CharacterPicker`)과 프롬프트(`prompt.ts`)가 전부 이 파일 하나를 통해 이름을 얻는다.
각자 문자열을 따로 들면 하나를 고칠 때 다른 것이 뒤처진다(FR-020).

**여기서 지키는 것**:
1. `Character` 다섯 값 전부에 항목이 있다(P1)
2. `roster.ts`·`ModelAsset`을 import하지 않는다(P2, 원칙 III) — 화면이 이 파일을
   거쳐 캐릭터 정보를 얻어도 모델 자산에는 닿지 않는다
3. 소개 문구는 실측에 근거하며 그 근거가 코드에 남는다(P3, 원칙 III·V)
4. 성격을 "지시"하는 문장을 만들지 않는다 — 이 파일이 주는 것은 이름·소개
   텍스트뿐이고, 프롬프트에 어떻게 쓰일지는 `prompt.ts`가 결정한다(P4)

---

## 함수

```
personaOf(character: Character) → Persona
```

인자가 유효하지 않은 `Character` 값을 받는 경로는 타입 시스템이 막는다(리터럴
유니온이므로 컴파일 타임에 차단) — 런타임 검증이나 기본값 폴백을 두지 않는다.

## 규칙

**P1. 다섯 값 모두 정의된다.**
`CHARACTERS`(diary/types.ts)의 모든 값이 `PERSONAS`에 키로 존재해야 한다. 테스트가
`CHARACTERS.every(c => ...)`로 이것을 직접 검사한다 — 새 캐릭터가 로스터에 추가되고
페르소나를 깜빡하면 여기서 잡힌다.

**P2. 모델 자산에 닿지 않는다.**
이 파일은 `import ... from "../models/roster"`도 `ModelAsset` 타입도 쓰지 않는다.
헌법 검사(`scripts/constitution-rules.ts`)가 `src/ui/`의 `roster.ts` 접근을 막지만,
이 규칙은 그것과 별개로 파일 자체의 설계로 지켜진다 — `persona.ts`가 애초에 그
경로를 열지 않으므로 화면이 이 파일을 거쳐도 모델 자산에 이를 수 없다.

**P3. 소개는 실측 근거를 코드 주석에 남긴다.**
각 `Persona` 값 옆에 어느 실기기 관측(005~012, AGENTS.md의 기록)에서 온 문구인지
주석으로 남긴다. 새 소개를 추가하거나 고칠 때 이 근거 없이는 안 된다(원칙 III
"관측 근거가 없는 모델은 로스터에 들어올 수 없다"의 페르소나 버전).

**P4. 성격을 지시하지 않는다.**
`tagline`은 사용자에게 보이는 소개 문구이지 모델에게 주는 지시문이 아니다.
`prompt.ts`가 이 파일에서 가져가는 것은 `name`뿐이며 `tagline`은 프롬프트에 들어가지
않는다 — 화면 문구와 모델 지시문이 같은 문자열을 공유하면, 소개 문구를 다듬으려는
시도가 의도치 않게 프롬프트를 바꾸는 사고가 날 수 있다(관심사 분리).

## 되지 않는 것

- `allPersonas()`류의 전체 목록 함수는 두지 않는다 — `CHARACTERS.map(personaOf)`로
  충분하며, 별도 함수는 003의 `allAssets()` 금지(FR-010, "다섯을 다 받자가 한 줄로
  가능해지는" 것과 유사한 이유)와 다른 이유이긴 하나(여기선 저장 공간 문제가 아니다),
  단일 진입점을 늘리지 않는다는 관례를 따른다.
- 사용자가 페르소나를 편집·추가하는 API는 두지 않는다(헌법 원칙 III "사용자가 자유롭게
  지어내게 하지 않는다 MUST NOT").
