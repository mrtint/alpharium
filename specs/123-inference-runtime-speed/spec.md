## Clarifications

### Session 2026-11-21

질문 0개 — 사용자만 아는 정보에 달린 갈림길이 없었다. 아래는 에이전트가 정한 것이다.

- Q: 옵션을 켤 때의 판정 기준은? → A: 두 기기 중 어느 한쪽에서도 1+2턴 총 시간이 기준선 대비 5% 넘게 짧아지지 않거나(5%는 3회 표본의 흔들림을 덮으려고 사람이 정한 값이고 측정이 아니다), 크래시·메모리 한도 초과가 나면 그 기기 계열에는 넣지 않는다. 한 기기에서만 이득이면 플랫폼 조건으로만 넣는다 (에이전트 판단 · 근거: 로드맵 「효과가 없거나 크래시가 나는 옵션은 넣지 않는다」, 플랫폼 분기는 `assembly.ts`·`SCREEN_IOS_PACING` 선례)
- Q: 측정 횟수는? → A: 조건당 최소 3회(첫 회는 냉시동 별도 표기), 같은 재료·같은 날, 기준선과 같은 앱 상태 (에이전트 판단 · 근거: 표본이 작다는 점을 표에 숨기지 않기 위한 하한, 사람이 정한 값)
- Q: 최고 RAM은 어디서 읽는가? → A: 개발 중 기기 도구만 — 안드로이드 `dumpsys meminfo` PSS, iOS Xcode/`devicectl`·lldb 계열 도구. 앱에 계측을 넣지 않는다 (에이전트 판단 · 근거: 원칙 IV)
- Q: q8_0 채택 여부는 어디서 정하는가? → A: 효과가 시험 기기에서 실측되고 (강제 설정, 완주·RAM 절감) 저사양 기기 조건이 코드로 잠기면 넣는다. 실제 저사양 기기 확인은 [미확인]으로 남긴다 (에이전트 판단 · 근거: 시험 기기가 2 GiB 이상이라 완주 확인만 가능)
- Q: 2턴 재사용은 상태 파일로 하는가? → A: 아니다. 실측(2026-11-22)에서 `llama.rn` 0.12.9는 같은 컨텍스트의 다음 호출에서 공통 접두어 KV를 이미 재사용한다(안드로이드 제목 호출: 새로 읽은 프롬프트 52토큰 / 캐시 약 850). 상태 파일 저장·복원은 불필요해 넣지 않는다. 반면 iOS 화면 쓰기의 조각 경로는 제목 호출에서 프롬프트 미리 읽기가 KV를 버려 처음부터 다시 읽었다(제목 약 12.7초) — 이 낭비를 고친다 (에이전트 판단 · 근거: quickstart 실측표)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 기준선과 옵션별 실측이 두 기기에서 남는다 (Priority: P1)

변경 전(현재 코드)과 옵션별(flash attention 명시, 2턴 상태 재사용, KV q8_0) 속도·1+2턴 총 시간·최고 RAM이 SM-S901N과 iPhone 14에서 표로 남는다. 어떤 옵션을 제품에 넣고 어떤 옵션을 넣지 않는지는 이 표로만 정한다.

**Why this priority**: 이득이 모바일 ARM에서 유지되는지 모른다는 것이 과제의 출발점이다. 표 없이는 아무 옵션도 넣을 수 없다(헌법 원칙 V).

**Independent Test**: 두 기기에서 같은 하루 재료로 기준선과 옵션별 쓰기를 돌려 `specs/123-*/quickstart.md`의 표를 채운다. 못 본 칸은 [미확인].

**Acceptance Scenarios**:

1. **Given** 새 a1이 든 두 기기, **When** 현재 코드로 사진 있는 하루를 쓰면, **Then** 생성 속도(t/s)·1+2턴 총 시간·최고 RAM이 기록된다.
2. **Given** 같은 재료, **When** 옵션 하나씩 바꿔 쓰면, **Then** 옵션별 같은 세 수치가 기록된다.
3. **Given** 측정을 위한 코드, **When** 제품 소스를 보면, **Then** 측정·채점 장치가 없다(원칙 IV).

---

### User Story 2 - 이득이 실측된 것만 쓰기에 들어간다 (Priority: P2)

표에서 이득이 확인되고 크래시가 없는 것만 제품에 반영된다. 효과가 없거나 크래시가 나는 옵션은 넣지 않고 까닭과 수치를 기록한다. 실측으로 확인된 이득은 iOS 화면 쓰기의 제목 호출이 앞의 KV를 버리고 프롬프트를 다시 읽던 것을 고치는 것이다.

**Why this priority**: 사용자가 얻는 가치(더 빠른 일기)다. 단 P1 없이는 정할 수 없다.

**Independent Test**: 채택한 옵션마다 단위 테스트가 값을 잠그고, 위반을 일부러 넣으면 테스트가 잡는다.

**Acceptance Scenarios**:

1. **Given** flash attention이 이득으로 실측되면, **When** 모델을 열면, **Then** 명시한 값이 `initLlama`에 간다. 이득이 없으면 값을 싣지 않는다(종전 인자 그대로).
2. **Given** iOS 화면 쓰기(조각 생성), **When** 본문 판정 뒤 제목을 물으면, **Then** 프롬프트를 미리 읽지 않고 곧바로 조각 생성하며(본문 직후 같은 컨텍스트의 KV를 쓴다), 본문 쓰기는 종전대로 미리 읽는다.
3. **Given** 이 변경, **When** 쓰기가 끝나거나 그만두거나 실패하면, **Then** 해제는 진행 중 생성이 모두 끝난 뒤에만 일어나고(079), `load()`는 도착 순서대로 직렬화된다(106).
4. **Given** iOS 이어 하기, **When** 제목 구간이 돌면, **Then** 박동이 나온다(092).

---

### User Story 3 - 저사양 기기에서 KV 캐시를 줄일 수 있다 (Priority: P3)

기기 메모리가 2 GiB 미만이면 KV 캐시 종류를 `q8_0`으로 내리는 구성이 있다(검토 결과에 따라 채택 또는 기록만).

**Why this priority**: 시험 기기가 모두 2 GiB 이상이라 실제 이득은 강제 설정으로만 본다. 채택 여부는 실측에 달렸다.

**Independent Test**: 메모리 값을 바꿔 넣는 단위 테스트가 기준 경계(미만·이상·읽지 못함)를 잠그고, 강제 설정으로 두 기기에서 완주를 본다.

**Acceptance Scenarios**:

1. **Given** 기기 메모리가 2 GiB 미만으로 읽히고 q8_0이 채택되었으면, **When** 모델을 열면, **Then** KV 캐시 종류 값이 실린다.
2. **Given** 메모리를 읽지 못했거나 2 GiB 이상이면, **When** 모델을 열면, **Then** KV 값이 실리지 않는다(모르는 것을 기본값으로 채우지 않는다, 원칙 V).

### Edge Cases

- 제목 호출의 새로 읽을 토큰이 예상보다 많아도(KV가 어긋난 경우) 결과는 같고 느려질 뿐이다 — 틀린 일기가 나오지 않는다.
- 그만두기가 본문과 제목 사이에 오면 종전처럼 이긴다(092 FR-010).
- iOS 화면 쓰기의 `use_mmap: false`, 백그라운드 `n_threads: 2`와 함께 켜도 완주해야 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 변경 전후 측정(t/s·1+2턴 총 시간·최고 RAM)은 개발 중 로그·기기 도구로만 하며 제품 코드에 측정 장치를 넣지 않는다.
- **FR-002**: `flash_attn_type` 명시 여부는 `auto`(현재) 대비 실측으로 정한다. 채택하면 모델을 여는 값 한 곳(`contextParams`)에서만 싣는다.
- **FR-003**: 1턴→2턴 KV 재사용은 `llama.rn` 0.12.9에서 같은 컨텍스트의 공통 접두어로 이미 일어남을 실측으로 확인하고, 상태 파일(`save/load_state_path`·`saveSession`)은 쓰지 않는다. 지원하지 않는 옵션(`cache_prompt`·`cache_reuse`)도 쓰지 않는다. iOS 조각 경로에서 제목 호출은 프롬프트 미리 읽기를 하지 않는다.
- **FR-004**: 079의 해제 순서와 106의 `load()` 직렬화는 이 변경이 건드리지 않으며 기존 테스트가 그대로 통과한다.
- **FR-005**: 제목 구간의 박동(092)·조립 주체별 한도(`assembly.ts`)·`SCREEN_IOS_PACING`과 부딪히지 않는다.
- **FR-006**: KV `q8_0`은 채택할 때만, 기기 메모리 2 GiB 미만에서만 싣는다(실측 결과 미채택 — quickstart). 채택한다면 기준값은 사람이 정한 값이며 실측이 아니라고 코드·문서에 적고 메모리를 읽는 자리는 한 곳이다.
- **FR-007**: 효과가 없거나 크래시가 나는 옵션은 제품에 넣지 않고 까닭과 수치를 quickstart에 기록한다.
- **FR-008**: 결과는 `specs/123-inference-runtime-speed/quickstart.md`에 표로 남기고 못 본 항목은 [미확인]으로 적는다.

### Key Entities

- **옵션별 실측 한 줄**: 기기·옵션·t/s·1+2턴 총 시간·최고 RAM·완주 여부(문서에만 있다, 앱 데이터가 아니다).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 두 기기 모두에서 기준선과 채택 후의 세 수치가 표에 있고, 채택 옵션의 1+2턴 총 시간이 기준선보다 5% 넘게 짧거나(실측, 5%는 사람이 정한 값) 넣지 않은 까닭이 기록되어 있다.
- **SC-002**: 채택 후 1+2턴 연속 생성이 두 기기에서 메모리 한도(2 GiB 미만) 안에서 회귀 없이 완주한다.
- **SC-003**: 채택한 옵션마다 위반 주입을 잡는 테스트가 있고 `npm run lint`·`npm test`가 통과한다.
- **SC-004**: 제품 소스에 측정·채점 코드가 없다.

## Assumptions

- a1은 `kanana-v3-dpo-iq4_nl_im.gguf`(1,241,435,520 B), 샘플링 temperature 0.6·top_p 0.9(122).
- `n_gpu_layers`는 0 그대로이며 GPU 오프로드는 범위 밖이다.
- 시험 기기(SM-S901N, iPhone 14)는 2 GiB 이상이라 q8_0은 강제 설정으로만 재현한다. 실제 저사양 기기는 [미확인].
- iPhone 14에는 122 개발 서명 Release 빌드가, SM-S901N에는 122 이전 JS 내장 APK가 있어 새 a1과 맞지 않으므로 Metro(`adb reverse --list` 확인) 또는 main 빌드로 시험한다.
- 데스크톱 `EXP-015` 수치는 근거 참고일 뿐이며 이 과제의 결론은 기기 실측으로만 낸다.
