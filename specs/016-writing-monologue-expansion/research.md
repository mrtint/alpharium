# Research: 쓰는 중 독백 확장

## §1. 콜드/핫 스타트는 실제 재사용인가, 「빠른 콜드」인가

**질문**: `llama-port.ts`의 `load()`가 같은 캐릭터를 다시 요청받으면 정말
로드를 건너뛰는가, 아니면 매번 언로드 후 재로드하되 시간만 짧게 걸리는가?
후자라면 "콜드/핫"이라는 이름 자체가 거짓이 된다(원칙 II의 화면판 위반).

**결정**: **진짜 재사용이다.** 실측(`src/inference/llama-port.ts:118-121`):

```ts
async load(character: Character): Promise<LoadResult> {
  if (context !== null && openFor === character) return { ok: true };
  ...
}
```

같은 캐릭터가 이미 열려 있으면 `loader(path)`(네이티브 모델 적재, 실제
비용이 드는 호출)를 아예 부르지 않고 `{ ok: true }`를 즉시 돌려준다. 이
분기가 "핫 스타트"의 정확한 정의다 — 시간을 재서 짧으면 핫이라고 부르는
것이 아니라, **로드 작업 자체를 생략했는지**로 가른다(측정이 아니라
사실 판정, 원칙 IV·V).

**근거**: `openFor === character` 비교와 `context !== null` 검사가 E1
불변식("같은 캐릭터면 재사용해도 된다", `engine-port.ts` 92-93행)의 실제
구현이다. 이 판정을 새로 만들지 않고, 그 결과값(`context !== null &&
openFor === character`였는지)을 반환값에 실어 밖으로 낸다.

**대안 검토**: `Date.now()`로 로드 소요 시간을 재서 임계값보다 짧으면
"핫"으로 표시하는 방법을 검토했으나 기각했다 — (1) 임계값 자체가 원칙
IV가 금지하는 채점 로직이 되고, (2) 기기마다 콜드 스타트 시간이 다르므로
(로드맵 실측: kanana 2.4초, exaone 242초) 고정 임계값이 캐릭터에 따라
틀린 답을 낼 수 있다.

## §2. 로드 시작 시점에 콜드/핫을 모르는 문제 — 신호를 어떻게 나눌까

**질문**: `warm` 값은 `engine.load()`가 완료된 뒤에만 안다. 그런데
사용자는 로드가 **시작되는 순간**부터(길게는 242초) 화면에 무언가를 보고
싶어 한다. 로드 시작과 콜드/핫 확정 사이의 간극을 어떻게 다루는가?

**결정**: **두 번의 신호로 나눈다.**

1. `engine.load()` 호출 직전 — `onStage("load")`(branch 없음, 콜드/핫
   모르는 중립 상태)를 보낸다.
2. `engine.load()`가 완료되면 — 결과의 `warm` 값으로 `onStage("load",
   warm ? "hot" : "cold")`를 다시 보낸다.

**근거**: 013(리사이즈 여부는 실행 결과로만 안다)과 같은 성격의 "미리
알 수 없는 값" 문제다. 015가 이미 확립한 "실제로 아는 시점에만 말한다"
원칙을 신호 설계에도 그대로 적용한다.

**중립 상태의 문구는 무엇을 보이는가**: 첫 신호(`branch` 없음) 시점에는
콜드/핫 어느 쪽에도 속하지 않는 별도 문구 풀이 필요한가, 아니면 이전
단계(vision)의 마지막 문구를 그대로 유지하는가?

- **문구 풀을 새로 만드는 안**: 세 번째 문구 풀("로드 확인 중" 류)이
  필요해지고, FR-009("각 갈래 10개 이상")를 이 풀에도 적용해야 하는가라는
  하위 질문이 생긴다 — 범위가 조용히 넓어진다.
- **채택**: **화면은 첫 신호를 받아도 즉시 새 문구로 갈아타지 않고, 두
  번째 신호(콜드/핫 확정)가 올 때까지 이전 단계(사진 보기)의 마지막 문구를
  유지한다.** 실측(§3)이 확인하듯 로드 완료까지 걸리는 시간은 캐릭터별로
  천차만별이지만, 그 **간극 자체는** 화면이 "무엇을 하는지 모른 채 잠깐
  멈춘 것"이 아니라 "직전에 하던 일(사진 정리를 막 끝냄)의 인상이 자연스럽게
  이어지는 것"으로 읽힌다 — 015 User Story 2의 "스쳐 지나가는 단계는 화면에
  흔적을 남기지 않는다"는 계약과 같은 정신이다. 콜드 스타트처럼 이 간극이
  길면(로드맵 실측 242초) 두 번째 신호가 곧 도착해 콜드 문구로 넘어가므로
  사용자가 "멈춘 화면"을 오래 보는 일은 없다 — 로드 자체가 사진 보기보다
  훨씬 늦게 끝나는 상황은 없다(readPhotos가 이미 완전히 끝난 뒤에만
  `engine.load()`가 호출되므로, "로드 시작"은 곧 "사진 보기 완전 종료"와
  같은 순간이다).
- **기각한 대안**: 로드 시작 시 별도 중립 문구 풀. 문구 풀 하나를 추가로
  관리해야 하고, 그 풀이 존재하는 시간이 극히 짧아(로드 완료 신호가 거의
  즉시 뒤따름, 특히 핫 스타트에서는 사실상 동시) 사용자가 볼 일이 드물다 —
  관리 비용 대비 체감 가치가 낮다.

**타입 표현**: 로드 시작 신호는 `onStage("load")`(두 번째 인자 `undefined`),
확정 신호는 `onStage("load", "cold" | "hot")`다. `pickMonologue("load",
undefined, previous)`가 호출되면 — 이 경우 화면은 위 결정에 따라 문구를
갱신하지 않으므로(`DiaryHomeScreen.tsx`가 `branch`가 `undefined`이고
`stage`가 `"load"`인 신호에서는 상태 갱신을 생략한다), 이 조합에 대한
문구 풀 자체가 필요 없다.

## §3. 사진 보기 갈래(많음/보통) — 언제, 어떻게 알리는가

**질문**: `selectForVision(photos)`가 고른 장수(≤5, `VISION_PHOTO_LIMIT`)는
`readPhotos()` 진입 시 바로 안다. 그런데 `"vision"` 신호는 015의 설계상
`captionAll()`의 `onPhotoStart`에서만 나간다(이중 발화 방지, 015 C1). 이
`branch`(많음/보통) 값을 어느 호출에 실어야 하는가?

**결정**: **`branch`를 `onPhotoStart`가 아니라 `onStage`형 콜백 자체의
인자로 승격한다.** 015의 `PhotoAdvanceSignal`은 `() => void`(인자 없음)로
설계되어 있었다 — 이 시그니처에 `branch`를 실으려면 015 계약을 깨야 한다.

대신 **`readPhotos()`가 `selectForVision()` 직후, `captionAll()`을 부르기
**전에** `onStage("vision", branch)`를 한 번 보내고, 이후
`captionAll()`의 `onPhotoStart`(장 전환 신호, 여전히 인자 없음)가 오면
화면은 **직전에 받은 `branch` 값을 계속 사용해 다음 문구를 고른다.****

**근거**:
- 015의 `PhotoAdvanceSignal`(`captionAll` 내부의 장 전환 신호)의 계약을
  건드리지 않는다 — 인자 없는 시그니처 그대로 둔다.
- `branch`는 하루 시작 시점에 한 번 정해지고 바뀌지 않는다(spec FR-006) —
  즉 "매번 다시 계산해 실어 보내야 하는 값"이 아니라 "한 번 알리면 화면이
  기억하는 값"이다. 이 성질이 "장 전환마다 재전송" 대신 "최초 1회 전송 +
  화면 기억"을 정당화한다.
- 화면(`app/state.ts`의 `writing` 상태)이 `branch` 필드를 유지하다가,
  `stage === "vision"`이고 `branch`가 함께 온 신호에서만 그 값을 갱신하고,
  이후 `onPhotoStart`발 `stage: "vision"` 신호(장 전환, `branch: undefined`
  인 신호)에서는 **직전에 저장해 둔 `branch`를 계속 쓴다.**

**대안 검토**: `PhotoAdvanceSignal`의 시그니처를 `(branch: VisionBranch) =>
void`로 바꿔 매번 명시적으로 실어 보내는 안을 검토했으나 기각했다 — 015의
계약(인자 없음)을 깨는 것은 015가 "순번을 담지 않는다"를 지키기 위해 세운
타입 방어를 재작업하는 범위이며, 016의 문제(하루 단위로 고정된 값을
반복 재전송)에 비해 과한 변경이다.

## §4. `checkMonologueFile`이 이름 문자열 매개변수를 이미 허용하는가

**질문**: `monologue.ts`가 캐릭터 이름을 `string` 매개변수로 받으면
헌법 검사(`MONOLOGUE_TOUCHES_ROSTER` 정규식)가 위반으로 잡는가?

**결정**: **이미 허용한다. 규칙 변경이 필요 없다.**

```ts
const MONOLOGUE_TOUCHES_ROSTER =
  /\bfrom\s+["'][^"']*(?:models\/roster|\/persona)["']|\bCharacter\b/;
```

이 정규식은 (1) `roster`/`persona` 파일에서의 `import` 문, (2) `Character`
**타입**을 바닥 단어 경계로 찾는다. `function pickMonologue(stage:
ProgressStage, branch: MonologueBranch, previous: string | undefined,
characterName: string, ...)`처럼 이름을 `string`으로 받는 코드는 두 패턴
어디에도 걸리지 않는다 — `characterName: string`은 `Character`(대문자
타입명)와 다른 토큰이다.

**검증 방법**: `scripts/constitution-rules.ts`의 `checkMonologueFile`을
`monologue.ts`의 예상 최종 소스(캐릭터 이름을 `string` 매개변수로 받는
버전)에 대해 유닛 테스트로 돌려 위반 0건을 확인한다(quickstart 절차에
포함). **위반 주입 테스트도 함께 둔다** — `import type { Character } from
"../diary/types"`를 실제로 넣어 헌법 검사가 여전히 잡는지 확인해, "느슨해진
것이 아니라 애초에 이 경로가 안전했다"를 실증한다(AGENTS.md 「위반 주입으로
방어를 검증한다」 관례).

## §5. 조사(이/가) 선택 — 한국어 받침 규칙

**결정**: 이름의 마지막 글자가 한글 완성형(가-힣) 범위인지 확인하고, 그
글자의 유니코드 코드포인트에서 `(코드 - 0xAC00) % 28`을 계산해 받침
유무를 판정한다(0이면 받침 없음, 그 외는 받침 있음) — 한글 조합형 인코딩의
표준 공식이다.

**로스터 5인 이름 검증**(코드로 직접 계산해 확인 — `(codePoint - 0xAC00) %
28`):

| 이름 | 마지막 글자 | 받침 | 조사 |
| --- | --- | --- | --- |
| 금동이 | 이 | 없음 | 가 |
| 루이 | 이 | 없음 | 가 |
| 오드 | 드 | 없음 | 가 |
| 샤오바이 | 이 | 없음 | 가 |
| 모카 | 카 | 없음 | 가 |

**현재 로스터 5인은 전부 "가"를 받는다** — 다섯 이름 모두 마지막 글자가
받침 없는 음절(이·이·드·이·카)이기 때문이다. 이/가가 갈리는 사례가
로스터 안에 아직 없다는 뜻이며, 그래서 **함수 자체는 받침 있는 이름
(예: "훈")에도 대응하도록 일반적으로 구현하되, 계약 테스트는 현재
로스터로는 "이"가 나오는 사례를 실제로 검증할 수 없다** — 받침 있는
가상의 이름(예: "테스트용" 문자열)을 별도 테스트 케이스로 추가해 "이"
분기가 죽은 코드로 남지 않게 한다(quickstart A3).

**대안 검토**: 조사를 캐릭터별로 `persona.ts`에 미리 못박아 두는 안(예:
`Persona`에 `particle: "이" | "가"` 필드 추가)을 검토했으나 기각했다 —
(1) `persona.ts`는 `monologue.ts`가 import할 수 없는 파일이므로(원칙 III
경계) 이 값을 화면이 별도로 읽어 넘겨야 해 배선이 한 겹 늘고, (2) 순수
받침 규칙 함수가 이름 문자열만으로 결정론적으로 계산 가능해 사람이 미리
정할 이유가 없다(캐릭터 이름이 나중에 바뀌어도 자동으로 맞는 조사가
나온다 — 오히려 유지보수 부담이 준다).

## §6. `LoadResult` 확장이 003·기존 계약과 충돌하지 않는가

**확인**: `engine-port.ts`의 `LoadResult`를 참조하는 자리는
`src/inference/llama-port.ts`(구현)와 `src/inference/on-device.ts`(호출자)
둘뿐이다(005·011이 이 타입을 도입한 이후 확장한 적이 없다). `{ ok: true }`
갈래에 `warm: boolean`을 추가하는 것은 기존 `if (!loaded.ok)` 체크(현재
`on-device.ts:307`)를 깨지 않는다 — `loaded.ok`만 보는 코드는 `warm`
필드의 존재를 몰라도 그대로 동작한다(003의 `isModelReady?`, 012의
`day?`/`now?`와 같은 "넓히기" 패턴, 015 Summary가 이미 확립한 방식과
동일).
