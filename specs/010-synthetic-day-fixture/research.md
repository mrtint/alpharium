# Phase 0 — 조사

**기능**: 010 가상의 하루를 기기에 심는 도구
**날짜**: 2026-08-22
**기기**: SM-G986N, Android 13, 무선 adb (`192.168.219.112:37679`)

**이 문서의 값은 전부 위 기기에서 실제로 재 본 것이다**(헌법 원칙 V). 짐작인 것은
그렇게 표시했다.

---

## §1 — 앱은 사진의 날짜를 어디서 읽는가

**결론: MediaStore의 `datetaken` 컬럼이다. EXIF가 아니다.**

[expo-port.ts](../../src/signals/expo-port.ts)의 `photosBetween()`이 이렇게 묻는다:

```
new Query()
  .gte(AssetField.CREATION_TIME, fromMs)
  .lt(AssetField.CREATION_TIME, toMs)
```

`AssetField.CREATION_TIME`이 MediaStore의 `datetaken`으로 내려간다. **그러므로 도구가
해야 할 일은 「그 하루의 `datetaken`을 갖는 행을 MediaStore에 만드는 것」이다.**

이것이 이 기능의 전체 설계를 정한다 — 파일을 기기에 두는 것만으로는 부족하고,
**MediaStore가 그 파일을 그 날짜로 색인해야** 앱이 본다.

### 실측 — 색인되지 않은 파일은 앱에 보이지 않는다

```
adb push probe.jpg /sdcard/Pictures/AlphariumProbe/probe.jpg
adb shell content query --uri content://media/external/images/media \
  --projection _id:_data:datetaken --where "_data LIKE '%AlphariumProbe%'"
→ Row: 0 _id=1000000639, _data=..., datetaken=NULL
```

행은 생겼는데 **`datetaken=NULL`이다.** 앱의 질의는 `datetaken`의 범위를 보므로
**이 사진은 어느 하루에도 걸리지 않는다** — 기기에 멀쩡히 있는데 앱은 못 본다.

**이것이 이 기능에서 가장 위험한 조용한 실패다.** 파일은 있고, `adb push`는 성공했고,
MediaStore에 행도 있다. 그런데 앱은 못 본다. FR-018d(확인한 뒤에 성공을 보고한다)가
바로 이 관측에서 나왔다.

## §2 — 좌표는 어디서 읽는가

**결론: 파일 안의 EXIF다. MediaStore의 `latitude`/`longitude` 컬럼이 아니다.**

### 실측 — 그 컬럼은 언제나 NULL이다

```
adb shell content query --uri content://media/external/images/media \
  --projection _id:datetaken:latitude:longitude
→ Row: 1 _id=1000000230, datetaken=1765685807553, latitude=NULL, longitude=NULL
→ Row: 2 _id=1000000378, datetaken=1775633949566, latitude=NULL, longitude=NULL
```

**진짜 카메라 사진도 `latitude`가 NULL이다.** Android 10부터 이 컬럼이 가려졌고,
그래서 `expo-media-library`의 `getLocation()`이 `ACCESS_MEDIA_LOCATION` 권한으로
**파일의 EXIF를 직접 읽는다.**

004가 이미 이것을 알고 있었다 — `locationOf()`가 권한이 없으면 예외를 던진다는 실측이
그 증거다. 컬럼을 읽는 것이면 예외가 날 이유가 없다.

**귀결: 날짜와 좌표를 서로 다른 자리에 써야 한다.**

| 값 | 어디에 | 누가 읽나 |
| --- | --- | --- |
| 찍힌 시각 | MediaStore `datetaken` (EXIF에서 스캐너가 옮긴다) | `photosBetween()` |
| 좌표 | 파일 안 EXIF GPS IFD | `locationOf()` |

## §3 — `datetaken`을 어떻게 원하는 값으로 만드는가

**결론: EXIF `DateTimeOriginal`에 쓰고 미디어 스캐너를 돌린다. 컬럼을 직접 고치는
길은 막혀 있다.**

### 실패한 길 ① — `content update`가 조용히 아무것도 안 한다

```
adb shell content update --uri content://media/external/images/media \
  --bind datetaken:l:1755750000000 --where "_data LIKE '%AlphariumProbe%'"
→ (출력 없음, 종료 코드 0)

adb shell content query ... --projection _id:datetaken
→ Row: 0 _id=1000000639, datetaken=NULL     ← 안 바뀌었다
```

**오류도 안 나고 값도 안 바뀐다.** 셸의 UID가 다른 앱이 소유한 미디어 행을 고칠 수
없기 때문이며, 그것을 실패로 알려 주지 않는다. **이 저장소가 반복해서 당한 조용한
실패의 또 하나다** — 이 길을 골랐다면 「고쳤다고 믿고 검증」했을 것이다.

### 실패한 길 ② — `MEDIA_SCANNER_SCAN_FILE` 브로드캐스트

```
adb shell am broadcast -a android.intent.action.MEDIA_SCANNER_SCAN_FILE -d file://...
→ Broadcast completed: result=0
```

`result=0`은 **아무도 받지 않았다**는 뜻이다. 이 브로드캐스트는 최신 안드로이드에서
제한됐다. 「완료」라는 글자 때문에 성공으로 오독하기 쉽다.

### 되는 길 — `scan_file` + EXIF

```
adb shell content call --uri content://media/external \
  --method scan_file --arg /sdcard/Pictures/.../x.jpg
→ Result: Bundle[{android.intent.extra.STREAM=...}]     ← URI를 돌려준다
```

**이것이 실제로 스캔한다.** 그리고 스캐너가 파일의 EXIF `DateTimeOriginal`을 읽어
`datetaken`에 넣는다.

### 실측 — 검증된 EXIF면 날짜가 정확히 들어간다

진짜 카메라 사진의 EXIF에서 `DateTimeOriginal`·`DateTimeDigitized` 문자열만
`2026:08:20 09:12:00`으로 덮어쓰고 밀어 넣었다:

```
→ Row: 0 _id=1000000646, datetaken=1787184720553
```

`1787184720553` = **2026-08-20 09:12:00 KST**. 쓴 것과 정확히 같다. ✅

좌표도 같은 방법으로 덮어쓰고 파일을 다시 꺼내 읽으니:

```
lat 37.5665
lon 126.9780
```

**날짜와 좌표 둘 다 왕복한다.** ✅

## §4 — ⚠️ 손으로 만든 EXIF는 안드로이드가 무시한다

**이것이 조사에서 가장 값비싼 발견이며, 설계를 바꿨다.**

의존성 0개로 EXIF를 직접 만들어 봤다. TIFF 헤더·IFD0·ExifIFD·GPS IFD를 규격대로 짰고
**내가 짠 파서로 다시 읽으면 정확히 파싱된다**:

```
ExifIFD entries 3
  tag 0x9000 type 7 count 4              ← ExifVersion
  tag 0x9003 type 2 count 20 => 2026:08:20 09:12:00
  tag 0x9004 type 2 count 20 => 2026:08:20 09:12:00
GPS IFD entries 4
  tag 0x1 => N,  tag 0x2 => 37°33'59.4"
  tag 0x3 => E,  tag 0x4 => 126°58'40.8"
```

**그런데 안드로이드는 `datetaken=NULL`을 준다.** 시도한 것 전부:

| 시도 | 결과 |
| --- | --- |
| 1×1 JPEG + 손으로 만든 EXIF | `datetaken=NULL` |
| `ExifVersion`(0x9000) 추가 | `datetaken=NULL` |
| 4032×2268 실제 크기 이미지에 내 EXIF 이식 | `datetaken=NULL` |
| **진짜 사진의 EXIF를 그대로 두고 날짜 문자열만 덮어씀** | **`datetaken=1787184720553` ✅** |

**차이가 어디서 오는지 정확히는 모른다.** 관측된 것은 「진짜 사진의 EXIF 구조는 받아
들이고 내가 만든 것은 무시한다」이며, 후보는 IFD0의 이미지 태그들(`0x100` 너비,
`0x101` 높이, `0x112` orientation 등 13개)이 없어서일 가능성이다. **확인하지 않았으므로
짐작으로 남긴다**(원칙 V).

**결론: EXIF를 처음부터 만들지 않는다. 검증된 템플릿 파일의 필드만 덮어쓴다.**

이 결정은 원칙 V의 「모델을 의심하기 전에 재는 코드를 확인한다」와 같은 성질이다 —
EXIF 생성기를 완벽하게 만드는 데 시간을 쓰는 대신, **이미 동작이 확인된 것을 고쳐 쓴다.**

### 그래서 템플릿 파일이 필요하다

- 저장소에 **JPEG 템플릿 하나**를 둔다. 안드로이드가 받아들이는 EXIF 구조를 가진 파일이다.
- 도구가 그 파일을 읽어 **`DateTimeOriginal`·`DateTimeDigitized`·GPS 네 태그만**
  덮어쓴다.
- 덮어쓰기는 **길이가 바뀌지 않는 자리 교체**다. 날짜는 20바이트 고정, GPS rational은
  24바이트 고정 — **오프셋이 하나도 움직이지 않으므로** IFD를 다시 계산할 필요가 없다.

**⚠️ 템플릿의 원본 EXIF에 개인정보가 있으면 안 된다.** 실기기의 사진에는 기기 모델·
소프트웨어 버전·원래 좌표가 들어 있다. 템플릿을 만들 때 **좌표를 덮어쓰고, 그것이
저장소에 커밋된다는 것을 인지해야 한다.**

## §5 — 파일을 어디에 두는가

**결론: `/sdcard/Pictures/<전용폴더>/`**

명확화 Q1이 정한 「전용 폴더」의 실제 자리다. 근거:

- `Pictures/`는 미디어 스캐너가 훑는 표준 자리다. 실측에서 그 아래 새 폴더가 정상
  색인됐다.
- **기기의 사진 앱에서 별도 앨범으로 보인다** — FR-016b(사람이 눈으로 구분)를 위치만으로
  충족한다.
- `DCIM/Camera/`에 두지 않는다. 그것은 사용자의 진짜 사진 자리이며, 섞이면 FR-016a
  (폴더 안의 것만 지운다)가 위험해진다.

### 지우기도 같은 방식이 필요하다

```
adb shell rm -rf /sdcard/Pictures/AlphariumProbe
adb shell content call --uri content://media/external --method scan_volume --arg external_primary
→ 이후 질의: No result found.     ← 행까지 사라졌다 ✅
```

**파일만 지우면 MediaStore에 유령 행이 남는다.** 볼륨 스캔이 그것을 치운다.
이것을 안 하면 「지웠는데 앱에는 아직 보인다」가 되고, 그것이 다음 검증을 오염시킨다.

## §6 — 도구를 어디에 두는가

**결론: `scripts/`에 Node 스크립트. 앱과 완전히 분리된다.**

FR-001(앱의 일부가 아니다)·FR-015(배포 빌드에 안 들어간다)를 **구조로** 보장한다:

- `scripts/`는 `src/`가 아니므로 번들에 들어갈 길이 없다. `run-device-tests.mjs`가
  같은 자리에 있는 선례다.
- 의존성을 더하지 않는다 — `node:child_process`로 `adb`를 부르고 `node:fs`로 파일을
  다룬다. 004~009가 전부 그랬듯 **새 의존은 실기기에서 확인해야 하는 부채**다.

### 에이전트가 부른다는 것의 귀결 (명확화 Q2·Q3)

`run-device-tests.mjs`가 이미 그 모양이다 — `PASSED`/`FAILED`를 찍고 종료 코드를 가른다.
같은 결을 따르되 **기계가 읽을 결과를 함께 낸다**(FR-018b). 사람이 읽을 줄과 기계가
읽을 줄을 **표준 출력 한 곳에 섞지 않는다** — 한 줄로 된 JSON을 마지막에 찍고, 그 앞은
사람이 읽는 문장으로 둔다. 에이전트는 마지막 줄만 보면 된다.

## §7 — 고를 수 있는 하루를 도구가 어떻게 아는가 (FR-005b)

**결론: `src/config/day-boundary.ts`의 `selectableDays()`를 그대로 부른다.**

FR-005b가 「도구가 스스로 정하지 않는다」를 요구한다. `selectableDays()`는 순수 함수이고
`now`를 인자로 받으므로 **Node에서 그대로 부를 수 있다** — 기기도 Expo도 필요 없다.

⚠️ **다만 `day-boundary.ts`는 TypeScript다.** `scripts/`의 기존 스크립트는 `.mjs`이고
`check-constitution.mts`는 `node --no-warnings=MODULE_TYPELESS_PACKAGE_JSON`으로 돈다
(Node 22+ 타입 스트리핑). **같은 방식을 쓰면 새 의존 없이 import 할 수 있다** —
`package.json`의 `check:constitution` 스크립트가 선례다.

이것이 **04:00 경계와 「셋」이 저장소에서 한 자리에만 있다**는 002·009의 불변식을
도구까지 확장한다.

## §8 — 기기 시각대와 하루 경계

**결론: 도구는 기기의 시간대를 쓰고, 그것이 개발 기계와 다를 수 있다.**

`dayBounds()`가 **기기 시간대 기준**으로 `[startMs, endMs)`를 만든다. 도구가 개발
기계에서 돌면서 `new Date(year, month-1, date, ...)`를 쓰면 **개발 기계의 시간대**가
쓰인다.

지금은 둘 다 KST라 드러나지 않는다. **다르면 심은 사진이 옆 하루에 걸린다.**

실측으로 확인한 것:

```
datetaken=1787184720553 → 2026-08-20 09:12:00 KST
```

기기가 KST이고 개발 기계도 KST여서 맞았다. **다른 시간대에서 확인하지 않았으므로
짐작으로 남긴다**(원칙 V). 방어는 **도구가 심은 뒤 `datetaken`을 되읽어 그 하루의
구간 안에 있는지 확인하는 것**이며, 그것이 FR-018d가 요구하는 확인의 내용이다.

## §9 — ★ 201장은 심을 수 없다 (2026-08-22 실측)

**구현 뒤 실기기에서 재 본 결과, `over-limit` 모양이 실패한다.**

```
ELAPSED=322s
{"ok":false,"reason":"index-failed",
 "detail":"201장을 심었는데 색인된 것은 150장이다. …"}
```

- **322초**(약 5분 22초) 걸렸다. 사진 한 장당 `adb push` + `scan_file` 왕복이므로
  **장수에 비례한다** — 초당 0.7장쯤이다.
- **201장을 밀어 넣었는데 색인된 것은 150장이다.** 미디어 스캐너가 이 속도의 연속
  요청을 따라오지 못한다.
- **도구가 이것을 잡아냈다.** `ok: false`로 끝났고 **부분 성공으로 보고하지
  않았다**(FR-018c). 확인 단계가 없었다면 「201장을 심었다」로 끝났을 것이고,
  앱에서는 150장만 보여 **왜 다른지 아무도 몰랐을 것이다.**
- **치우기까지 돌았다**(FR-019). 기기에 절반만 심긴 상태가 남지 않았고, 다른 하루에
  심어 둔 것은 그대로였다.

**이것이 FR-018d(확인한 뒤에 성공을 보고한다)가 실제로 값어치를 증명한 자리다.**
research.md §1이 실측으로 예고한 실패가 다른 원인(속도)으로 다시 나타났고, 같은
방어가 잡았다.

**⚠️ `over-limit` 모양은 지금 쓸 수 없다.** 고치려면 색인을 장마다 부르지 않고
**폴더째 한 번 부르는** 쪽을 재 봐야 한다 — 그것이 통하는지는 **아직 확인하지
않았다**(원칙 V). US2의 SC-005는 그때까지 미확인이다.

## §10 — ★ 앱이 심은 사진을 본다 (2026-08-22 실측, release 빌드)

**SC-002가 달성됐다 — 005 이후 처음으로 신호가 있는 하루의 일기가 나왔다.**

`rich`를 2026-08-20에 심고 `quiet`으로 생성하니 상세 화면이 이렇다:

```
이 일기가 본 것
  사진: 4장
  다닌 자리: 3곳
  걸음 수: 모른다
```

**「모른다」도 「없었다」도 아닌 실제 개수다.** 걸음 수는 여전히 `unknown`이며 그것이
정상이다(FR-009a).

### ⚠️ 심은 3장인데 4장으로 나온다 — 결함이 아니다

기기의 그 하루 구간을 조회하니:

```
/DCIM/Camera/20260820_145856.jpg            ← 진짜 사진
/Pictures/AlphariumSeed/2026-08-20-000.jpg  ← 심은 것
/Pictures/AlphariumSeed/2026-08-20-001.jpg
/Pictures/AlphariumSeed/2026-08-20-002.jpg
```

**그 하루에 사람이 찍은 진짜 사진이 하나 있었다.** 심은 3장 + 진짜 1장 = 4장이고,
진짜 사진의 좌표가 자리 하나를 더해 3곳이 됐다.

**이것이 FR-017이 의도한 대로 동작한다는 증거다** — 앱은 심은 사진과 진짜 사진을
구분하지 않으며, 구분해서도 안 된다. 도구가 폴더로 격리하는 것은 **되돌리기를 위한
것이지 앱에게 알리기 위한 것이 아니다.**

**⚠️ 검증할 때 이것을 셈에 넣어야 한다.** 「심은 수 = 화면의 수」를 기대하면 어긋난
것으로 오독한다. `seed:day`의 `existing`은 **심은 폴더 안의 것만** 세므로 진짜 사진은
거기 잡히지 않는다.

### 생성된 일기 (`quiet`, 합성 하루에서의 관측 — FR-020)

> 2026-08-20의 하루는 조용하고 빠르지도 느리지도 않은 속도로 흘러갔다. 주인은 이날
> 사진을 여러 장 찍었고, 그 사진을 바탕으로 장소의 대략적인 이동 경로를 추정할 수
> 있을 뿐이다. (…) 배터리는 거의 소모되지 않았는지 기록에 남지 않았고, 걸음 수 역시
> 기록되지 않았다. 주인이 집을 나서서 어디를 다녔는지는 알 수 없으며 (…)

**관측만 적는다**(FR-021): 「집, 카페, 공원」은 기록에 없는 단언이다(원칙 II 위반이며
005~009에서 반복 관측된 것과 같은 종류). **다만 이것으로 프롬프트의 좋고 나쁨을
결론짓지 않는다** — 그것이 원칙 V가 금지한 것이며 프롬프트는 005의 자리다.

「약 35142m 정도 떨어져 있었다」는 **수치를 그대로 보여준 것**이라 눈에 띈다. 원칙 IV의
「지표를 사용자에게 그대로 보여주지 않는다」에 걸리는지는 **프롬프트·화면의 물음이지
010의 범위가 아니다.** 관측만 남긴다.

## §11 — ★ 「사진 없음」과 「사진 모름」이 한 화면에서 갈린다 (2026-08-22 실측)

**SC-003이 달성됐다.** 2026-08-18(진짜 사진이 0장인 하루)에 `empty`를 심고 생성하니:

```
사진: 없었다        ← 「모른다」가 아니다
```

**그리고 일기의 본문이 그 구분을 그대로 옮겼다** (`quiet`):

> - 사진: **없다.** 주인이 사진을 찍을 때마다 남기는 기록만 볼 수 있다. 오늘은 사진이 없다.
> - 다닌 자리: **모른다.** 주인이 오늘 어디를 다녔는지 기록에 남아 있지 않다.
> - 걸음 수: **모른다.** 안드로이드 운영체제는 특정 기간의 걸음 수만 제공하므로 (…)

**같은 하루 안에서 `none`과 `unknown`이 서로 다른 말로 나왔다.** 004가 값에서 지킨
구분이 화면을 지나 글까지 살아서 도착했고, **지어낸 것이 0건이다.**

**⚠️ 이 하루에는 심은 사진이 0장이고 진짜 사진도 0장이었다.** 그래서 `empty` 모양의
값어치는 「사진을 심지 않는 것」이 아니라 **「그 하루를 의도적으로 고르는 것」**에 있다 —
007이 미확인으로 남기고 009가 우연히 본 갈래를 이제 원할 때 만들 수 있다.
