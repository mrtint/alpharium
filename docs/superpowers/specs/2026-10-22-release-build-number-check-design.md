# 릴리스 빌드 번호 사전 점검 설계

로드맵 「릴리스 빌드 번호 자동 올림」의 구현 설계. 번호를 정하는 방식은 소유자가 후보 (3)으로 정했다 —
**사람이 번호를 올리되, 사전 점검이 스토어의 마지막 번호를 읽어 중복(또는 작거나 같음)이면 빌드 전에 이름을 밝히며 실패한다.** 읽기 권한만 쓴다.

## 이해 (확인용)

- **목적**: 번호를 잘못 알고 긴 빌드(안드로이드 약 11~13분, iOS 더 김)를 돌린 뒤에야 스토어 거부로 실패하는 일을 없앤다.
- **범위**: 안드로이드(076)·iOS(075) 릴리스 워크플로에 같은 모양의 「번호 점검」 단계를 넣는다. 번호를 올리는 일 자체는 사람 몫으로 남는다. `app.json` 번호는 이 작업에서 올리지 않는다.
- **경로 분류**: 비밀을 쥔 워크플로에 읽기 통로를 늘리는 변경이라 **아키텍처 경로**로 다룬다.
- **가정(말하지 않은 것)**: 스토어를 읽지 못하면(권한 부족·네트워크) 빌드 전에 이름을 밝히며 실패한다(조용히 건너뛰지 않는다 — 원칙 V). 소유자가 다르게 정하면 이 줄을 고친다.

## 번호 규칙

|                       | 안드로이드                                                   | iOS                                                                                     |
| --------------------- | ------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| 스토어에서 읽는 것    | 앱의 모든 번들 `versionCode` (`edits.bundles.list`)          | 이 앱·이 `version`의 모든 빌드 `version`(=빌드 번호) (`GET /v1/builds`)                 |
| 통과 조건             | 이번 `versionCode` > 스토어 최댓값                           | 이번 `buildNumber` > 같은 `version`의 스토어 최댓값 (그 `version`의 빌드가 없으면 통과) |
| 실패 문장이 말하는 것 | 이미 있는 번호(최댓값)·이번 번호·올려야 할 값(최댓값+1 이상) | 같음 + 버전 이름                                                                        |

- 안드로이드 `versionCode`는 모든 트랙을 통틀어 단조 증가한다 — 트랙별 조회(`tracks.list`)는 올라가지 않은 번들·다른 트랙을 놓치므로 쓰지 않는다. 번들 목록이 정본이다.
- iOS는 `CFBundleShortVersionString`(= `expo.version`) 안에서 빌드 번호가 증가한다. 정수로 읽히지 않는 스토어 번호는 비교에서 빼고 개수만 알린다.

## 구성

- `scripts/android-release/version-check.ts` / `.mts`, `scripts/ios-release/build-number-check.ts` / `.mts` — 순수 판정(`decide…`)과 스토어 조회를 나눈다. 네트워크·시계는 주입받는다(076·075와 같다). 판정은 순수 함수로 시험한다.
- 조회 함수는 기존 `play-upload.ts`·`testflight-notes.ts`에 두거나 그 안의 인증·호출 도우미(`signJwt`·`call`·`reasonOf`)를 export해 쓴다 — 인증 코드를 복제하지 않는다. 새 의존성은 없다(Node 내장 `crypto`·`fetch`).
- **안드로이드 조회**: 토큰 → `edits.insert` → `bundles` 목록 → **언제나** `edits.delete`(성공·실패 무관, 삼킨다). 편집은 커밋하지 않으므로 Play에 아무것도 남지 않는다.
- **iOS 조회**: `apps` → `builds`(`filter[app]`·`filter[preReleaseVersion.version]`, `limit=200`, `links.next` 따라 모두). 이미 `testflight-notes.ts`가 쓰는 두 호출과 같은 종류다.
- 오류 문장은 기존과 같은 `HTTP <상태> <호출>: <사유>` 꼴 하나뿐이다. 토큰·개인 키·응답 본문 전체를 싣지 않는다. 403은 무엇을 더 줘야 하는지(Play: 앱 정보 보기·릴리스 보기 권한, ASC: 키 역할) 한 줄을 덧붙인다.

## 워크플로 배치

- **안드로이드**: `설정 점검` 바로 뒤, `npm ci`·`expo prebuild` 앞에 단계 `번호 점검`. env로 `PLAY_SERVICE_ACCOUNT_JSON` 하나만 받는다.
- **iOS**: `릴리스 노트 점검` 뒤, `러너 사양`·`npm ci` 앞에 단계 `번호 점검`. env로 `ASC_API_KEY_P8`·`ASC_KEY_ID`·`ASC_ISSUER_ID`만 받는다.
- 이 단계는 **`npm ci` 앞**에서 돌고 저장소 스크립트(`.mts`) 하나만 부른다 — 의존성 설치 스크립트가 비밀을 보지 못하고, 스크립트는 Node 내장만 쓴다. 이미 업로드 단계가 같은 비밀로 저장소 코드를 도는 것과 같은 신뢰 경계다.
- 「사전 점검」 단계는 건드리지 않는다(비밀이 비었는지만 보고 저장소 코드를 부르지 않는다는 076 W17 계약 유지).
- `permissions`는 `contents: read`, 시작은 수동 하나, 허용 secret 목록, 정리 단계는 그대로다.

## 번호 ↔ 커밋 대응

- 번호 점검 출력과 실행 요약에 `버전 <version> · versionCode|빌드 <번호> · 커밋 <GITHUB_SHA 앞 7자> · 스토어 마지막 <번호>` 한 줄을 남긴다. 스토어에 올라간 번호가 어느 커밋에서 나왔는지 실행 기록에서 찾는다.

## 테스트·검증

- 순수 판정과 조회(대역 `fetch`): 더 큼 / 같음 / 작음 / 스토어에 없음 / 정수 아닌 번호 / 403·네트워크 오류 / 페이지 이어 받기 / 편집 삭제가 실패해도 결과 유지 / 오류에 비밀이 실리지 않음.
- 워크플로 계약(`__tests__/ci/*-release-workflow.test.ts`): 번호 점검이 `npm ci`·prebuild보다 앞, 허용 밖 secret 없음, 쓰기 권한 없음, 수동 시작 하나, secret이 번호 점검 단계 env로만 새로 참조됨. 위반 주입으로 각각 어겨 잡히는지 확인한 뒤 되돌린다.
- **실제 응답은 처음 본다**: Play `bundles.list`·ASC `builds` 실응답과 서비스 계정·키 권한은 비밀이 있는 보호 환경에서만 닿는다. 소유자 요청 없이 워크플로를 돌리지 않으므로, 실제 실행은 「못 본 것」으로 남기고 소유자에게 한 번 확인을 요청한다.

## 범위 밖

- 번호 자동 올림(후보 1·2), `app.json` 번호 변경, 릴리스 실행.
- 스토어에서 삭제된 번들·만료 빌드 번호(Play는 삭제된 번들의 번호도 막을 수 있으나 목록에 나오지 않는다 — 남은 위험).
