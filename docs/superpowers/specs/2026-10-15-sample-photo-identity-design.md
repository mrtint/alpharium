# 표본 사진의 정체를 원본 sha1로 — 썸네일 변형이 바뀌어도 층 1이 멈추지 않게

로드맵 과제 「표본 사진 목록의 해시가 어긋났다 — 층 1 전체가 앞단에서 멈춘다」(2026-10-15 brainstorming, 소유자 승인 — B안).

## 무엇이 일어났나 (실측, 2026-10-15 맥)

- 맥에서 `npm run sample:fetch`가 `commons-indoor-13.jpg`의 sha256 불일치로 멈췄고, 캐시에 12장뿐이라 `npm run test:layer1`의 「표본 보장」이
  `missing-cache`로 중단된다. 210장 중 15장(indoor-13·18·26·28, street-06·12·29, people-12·14·18·19·26, night-01·08·22)이 어긋난다.
- **원인은 썸네일 재생성이 아니라 데이터센터마다 다른 썸네일이다.** 같은 URL을 `curl --resolve`로 엣지를 바꿔 받으면 codfw·ulsfo 엣지는
  **목록과 같은 바이트**(Last-Modified 2026-10-10 05:51 — 목록을 만든 날)를, eqiad·eqsin·esams·drmrs·magru 엣지는 다른 바이트(Last-Modified
  2026-08-03 등)를 준다. 15장 모두 codfw = 목록, eqiad = 다름이었다. 썸네일 저장소가 데이터센터마다 따로이고, 목록을 만든 기계는 codfw 계열에,
  이 맥(eqsin 엣지)은 eqiad 계열에 붙는다. 나머지 195장은 두 벌이 우연히 같다.
- **같은 사진이다**: 15장 모두 Commons 원본의 마지막 올림이 2024-04-30 이전(목록 작성 2026-10-10 이후 변경 없음), 받은 썸네일 크기가 원본 비율의
  960폭과 맞고, 라이선스는 지금도 CC0·PD다. 두 벌을 나란히 놓고 눈으로도 같다(소유자 확인).
- **`--record-hashes`로는 못 고친다** — `sha256`이 **비어 있는** 항목만 채우고 기록된 값이 어긋나면 기록 모드에서도 실패한다(070 F-5).
  지금 맥 값으로 해시를 바꾸면 codfw 쪽에 붙는 기계가 반대로 깨진다.

## 목표

1. 같은 원본에서 나온 썸네일이면 어느 데이터센터의 바이트든 받아들여, 썸네일 변형 때문에 층 1이 통째로 멈추지 않는다.
2. 「조용히 다른 사진을 쓰지 않는다」(070 F-2)는 지킨다 — 원본이 바뀌었거나 확인할 수 없으면 지금처럼 실패한다.
3. 맥 + SM-S901N(dev)에서 `npm run sample:fetch`와 `npm run test:layer1`(`sample-days` 포함)이 통과한다.

범위 밖: 사진 교체(15장 모두 같은 사진), `docs/e2e/sample-table.md`(해시가 없다), 「표본 보장」·층 1 실행기, 원본 파일 URL로의 전환(아래 기각안).

## 설계

### 1. 목록 모양 (`scripts/e2e-sample/photos.json`, `catalog.ts`)

- `sha256: string` → `sha256: string[]` — 받아들인 썸네일 변형의 sha256(소문자 hex 64자) 목록. 비어 있으면 안 된다(기록 모드에서만 빈 배열 허용).
  배열 안 중복 금지.
- 새 필드 `originalSha1: string` — Commons 원본 파일의 sha1(소문자 hex 40자, Commons API `imageinfo`의 `sha1`). 사진의 **정체**다.
  기록 모드에서만 빈 문자열 허용.
- 이전: 기존 210개 항목의 해시는 한 칸 배열로 옮기고, `originalSha1`은 `--record-hashes`가 Commons API로 채운다(제목 50개씩 묶음).

### 2. 내려받기 (`fetch.ts`)

받은 썸네일의 sha256을 `got`이라 할 때:

- `got ∈ sha256[]` → 지금처럼 캐시에 둔다(F-1).
- `got ∉ sha256[]` → Commons API로 그 사진(`sourcePage`의 제목)의 현재 원본 sha1을 읽는다.
  - 원본 sha1 == `originalSha1` → **새 변형으로 받아들인다**: 캐시에 두고, 그 항목의 `sha256[]`에 `got`을 덧붙이고, 「새 썸네일 변형을 받아들였다: 파일명」을
    한 줄 출력한다. 실행이 성공으로 끝나면 `photos.json`을 다시 쓴다(사람이 diff를 보고 커밋한다).
  - 원본 sha1이 다르다(원본이 다시 올라왔다 = 다른 사진) → 파일을 남기지 않고 실패한다(이유에 파일명·두 sha1 앞자리).
  - API를 못 읽었다(HTTP 오류·형식 이상·예외) → 파일을 남기지 않고 실패한다. 확인하지 못한 바이트를 받아들이지 않는다.
- 이미 캐시에 있는 파일은 그 sha256이 `sha256[]`에 있으면 건너뛴다. 없으면 지우고 다시 받는다(위 규칙을 탄다).
- API 호출은 처음 보는 해시일 때만 나간다. 같은 UA, 요청 사이 간격(≥ 1.1초)을 지킨다. 네트워크는 주입된 통로로만 나간다(테스트 대역).
- 원본 sha1이 바뀐 사진은 사람이 본다 — 도구가 원본 sha1을 덮어쓰지 않는다.

### 3. `--record-hashes`

「비어 있는 정체 필드를 채운다」로 넓힌다: `originalSha1`이 빈 항목은 Commons API로 채우고(묶음 조회), `sha256`이 빈 배열인 항목은 받은 바이트의
해시로 채운다(그 바이트도 원본 sha1 확인을 거친다). 이미 채워진 값은 바꾸지 않는다.

### 4. 기기 표식 지문 (`plan.ts`)

`fingerprint()`가 쓰는 사진 값을 썸네일 sha256에서 `originalSha1`로 바꾼다. 데이터센터마다 다른 바이트를 받은 두 기계가 같은 지문을 내어,
기계를 바꿀 때마다 기기를 다시 심지 않는다. 바꾼 직후 한 번은 지문이 달라져 다시 심긴다.

### 5. 문서

- `specs/070-e2e-sample-seed/contracts/sample-seeding.md` F-2·F-5와 `sample-manifest.md`(목록 모양)를 고친다.
- AGENTS.md 070 절: 「같은 썸네일 URL이 데이터센터마다 다른 바이트를 준다(codfw·eqiad 실측) — 사진의 정체는 원본 sha1」 한 줄.

### 6. 테스트 (기기 없음)

- `catalog`: 배열 해시·`originalSha1` 모양 검사, 기록 모드의 빈 값 허용.
- `fetch`: 목록에 있는 해시 → API 호출 없음 / 처음 보는 해시 + 원본 일치 → 받아들이고 덧붙임 / 원본 불일치 → 실패·파일 없음 /
  API 실패 → 실패·파일 없음 / 기록 모드의 원본 sha1 채우기.
- `plan`: 지문이 썸네일 해시와 무관하고 `originalSha1`에 따라 바뀐다.

### 7. 실기기 완료 확인

맥 + SM-S901N(dev): `files/diary`·`preferences`·`vision-cache`를 `run-as tar`로 백업 → `npm run sample:fetch` → `npm run test:layer1`
(`sample-days` 포함) → 복원.

## 기각한 안

- **해시만 맥 값으로 다시 기록**: codfw 쪽 기계가 반대로 깨진다.
- **허용 해시 배열만(원본 확인 없음)**: 지금 두 벌은 덮지만 셋째 변형(썸네일 purge 등)이 생기면 다시 통째로 멈춘다.
- **원본 파일 URL**: 210장 약 700MB, EXIF를 걷으면 원본의 방향 정보가 사라져 사진이 눕고, 심기가 느려진다.

## 남는 위험

- Commons API라는 외부 의존이 하나 는다(처음 보는 해시일 때만).
- 도구가 `photos.json`을 스스로 고친다 — diff로 보이지만 사람이 모르는 사이에 목록이 늘 수 있다(출력 줄로 알린다).
- 지문이 원본 sha1이라 두 기계가 심은 바이트가 달라도 표식은 「같다」고 말한다. 층 1은 사진 수·장소 수만 보므로 무해하고, 사진 내용을 읽는
  층 2에서는 VLM 입력이 미세하게 다를 수 있다(같은 사진).
