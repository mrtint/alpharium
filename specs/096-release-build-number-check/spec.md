# Feature Specification: 릴리스 빌드 번호 사전 점검 — 스토어의 마지막 번호보다 크지 않으면 빌드 전에 실패

**Feature Branch**: `096-release-build-number-check`

**Created**: 2026-10-22

**Status**: Draft

**Input**: User description: "docs/superpowers/specs/2026-10-22-release-build-number-check-design.md 설계문서를 입력으로: 안드로이드(076)·iOS(075) 릴리스 워크플로의 사전 점검이 스토어의 마지막 번호를 읽어, 이번 번호가 같거나 작으면 긴 빌드 전에 이름을 밝히며 실패하게 한다. 읽기 권한만 쓴다."

## 근거와 원본

- **설계**: `docs/superpowers/specs/2026-10-22-release-build-number-check-design.md`(소유자 승인, 2026-10-22).
- **로드맵 과제**: 「릴리스 빌드 번호 자동 올림」. 번호를 정하는 방식은 소유자가 후보 (3)으로 정했다 — 사람이 번호를 올리되 사전 점검이 스토어의 마지막 번호를 읽어 중복이면 빌드 전에 실패한다.
- **문제**: 두 릴리스 워크플로의 사전 점검은 번호가 정수인지만 본다. 같은 번호는 Play·Apple이 거부하지만 그것은 긴 빌드(안드로이드 약 11~13분) 뒤 업로드 단계에서야 드러난다.
- **범위 밖**: 번호를 CI가 올리거나 덮어쓰는 방식(후보 1·2), `app.json` 번호 변경, 릴리스 워크플로의 실제 실행(소유자 요청 때만), 스토어 쓰기 권한 추가.

## 용어

- **이번 번호**: 저장소 `app.json`의 `expo.android.versionCode`(안드로이드), `expo.ios.buildNumber`와 `expo.version`(iOS).
- **스토어 마지막 번호**: 안드로이드는 Play에 올라간 모든 번들 `versionCode`의 최댓값. iOS는 같은 `expo.version`으로 App Store Connect에 올라간 모든 빌드 번호의 최댓값.
- **번호 점검**: 이번 번호를 스토어 마지막 번호와 견주는, 빌드 전에 도는 워크플로 단계.

## Clarifications

### Session 2026-10-22 (설계 단계 소유자 결정)

- Q: 번호를 어디서 정하는가? → A: 후보 (3) — 사람이 올리고 사전 점검이 스토어를 읽어 검사한다.
- Q: 스토어를 읽지 못하면(권한 부족·네트워크 오류)? → A: 조용히 건너뛰지 않고 빌드 전에 이름을 밝히며 실패한다.

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 이미 있는 번호로 시작하면 빌드 전에 실패한다 (Priority: P1)

소유자가 번호를 올리는 것을 잊거나 스토어의 번호를 잘못 알고 릴리스 워크플로를 시작하면, 의존성 설치·prebuild·컴파일을 하기 전에 어느 번호가 이미 있고 무엇으로 올려야 하는지 말하며 실패한다.

**Why this priority**: 이 과제의 존재 이유다.

**Independent Test**: 스토어 응답 대역으로 이번 번호가 마지막 번호와 같을 때·작을 때·클 때를 각각 시험하고, 워크플로 계약 테스트가 번호 점검이 빌드 단계보다 앞서 도는 것을 잠근다.

**Acceptance Scenarios**:

1. **Given** Play의 마지막 `versionCode`가 N이고 이번 번호가 N, **When** 릴리스 워크플로를 시작한다, **Then** 번호 점검이 N이 이미 있다고 밝히고 N+1 이상으로 올리라고 말하며 실패하고 이후 단계는 돌지 않는다.
2. **Given** 이번 번호가 마지막 번호보다 작다, **Then** 같은 모양으로 실패하며 문장이 마지막 번호와 이번 번호를 모두 말한다.
3. **Given** 이번 번호가 더 크다, **Then** 번호 점검은 통과하고 마지막 번호·이번 번호·커밋을 한 줄로 남긴다.
4. **Given** iOS에서 같은 `expo.version`에 빌드 번호 M이 이미 있고 이번 번호가 M 이하, **Then** 실패하며 버전 이름과 M을 말한다.
5. **Given** iOS에서 이번 `expo.version`의 빌드가 스토어에 하나도 없다, **Then** 통과한다(새 버전).

---

### User Story 2 - 스토어를 읽지 못해도 이름을 밝히고 멈춘다 (Priority: P1)

서비스 계정·API 키의 권한이 모자라거나 네트워크가 막혀 마지막 번호를 읽지 못하면 건너뛰고 빌드를 시작하지 않고, 무엇이 안 되는지 말하며 실패한다.

**Independent Test**: 403·네트워크 오류·형식이 다른 응답 대역으로 각각 시험한다.

**Acceptance Scenarios**:

1. **Given** 스토어가 403을 준다, **Then** `HTTP 403 <호출>: <사유>`와 어떤 권한을 더 주어야 하는지 한 줄이 나오고 실패한다.
2. **Given** 연결이 실패하거나 응답에 번호 목록이 없다, **Then** 호출 이름을 밝히며 실패한다.

---

### User Story 3 - 새 읽기 통로가 비밀 방어를 약하게 하지 않는다 (Priority: P1)

퍼블릭 저장소의 릴리스 워크플로에 읽기 통로가 생겨도 076·075의 비밀 방어 계약이 그대로다.

**Independent Test**: 계약 테스트와 위반 주입.

**Acceptance Scenarios**:

1. **Given** 두 워크플로, **Then** 시작은 수동 하나, 권한은 `contents: read`뿐, 허용 밖 비밀 참조 없음, 새 단계의 비밀은 단계 `env`로만 받고 값을 출력하지 않는다.
2. **Given** 번호 점검 단계, **Then** 의존성 설치·prebuild·컴파일·서명 키 복원보다 앞에서 돌고 Node 내장 기능만 쓰는 저장소 스크립트 하나를 부른다.
3. **Given** 스토어 조회 중 오류가 나도, **Then** 오류 문장에 토큰·개인 키·응답 본문 전체가 실리지 않는다.

---

### User Story 4 - 번호와 커밋의 대응이 기록에 남는다 (Priority: P2)

릴리스 실행 기록(실행 요약·로그)에 이번 버전·번호·커밋·스토어 마지막 번호가 한 줄로 남는다.

**Acceptance Scenarios**:

1. **Given** 번호 점검을 통과했다, **Then** 실행 요약에 `버전 · 번호 · 커밋 7자리 · 스토어 마지막 번호`가 적힌다.

## Edge Cases

- 안드로이드: 트랙에 올라가지 않은 번들·다른 트랙의 번들도 번호를 차지한다 — 번들 목록 전체를 본다.
- Play 조회가 만드는 편집은 커밋하지 않고 언제나 버린다(성공·실패 무관, 삭제 실패는 결과를 바꾸지 않는다).
- iOS: 빌드 목록이 여러 쪽이면 모두 읽는다. 정수로 읽히지 않는 스토어 번호는 비교에서 빼고 개수를 알린다.
- 스토어에서 삭제·만료된 빌드의 번호는 목록에 안 나올 수 있다 — 남은 위험(스토어가 거부하면 업로드 단계에서 드러난다).
- `app.json` 번호가 정수가 아니면 종전 점검이 먼저 실패한다.

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 안드로이드 릴리스 워크플로는 빌드 전에 Play의 모든 번들 `versionCode` 최댓값을 읽고, 이번 `versionCode`가 그보다 크지 않으면 이미 있는 번호와 올려야 할 값을 밝히며 실패한다.
- **FR-002**: iOS 릴리스 워크플로는 빌드 전에 이번 `expo.version`의 모든 빌드 번호 최댓값을 읽고, 이번 `buildNumber`가 그보다 크지 않으면 버전·이미 있는 번호·올려야 할 값을 밝히며 실패한다. 그 버전의 빌드가 없으면 통과한다.
- **FR-003**: 스토어를 읽지 못하면(권한·네트워크·형식) 호출 이름과 사유로 실패한다. 건너뛰고 계속하지 않는다. 403에는 더 줘야 할 권한을 한 줄 덧붙인다.
- **FR-004**: 번호 점검은 읽기만 한다. 스토어에 쓰는 호출(릴리스·빌드 변경)을 하지 않으며, 안드로이드 편집은 만들되 커밋하지 않고 버린다.
- **FR-005**: 번호 점검 단계는 의존성 설치·prebuild·서명 키 복원·컴파일보다 앞에서 돈다. 기존 「사전 점검」(비밀이 비었는지만 보고 저장소 코드를 부르지 않음)은 그대로다.
- **FR-006**: 두 워크플로의 시작 방법은 수동 하나, 권한은 `contents: read`뿐, 허용된 비밀 목록은 그대로이며 번호 점검은 자신이 쓰는 비밀만 단계 `env`로 받는다. 비밀 값은 어디에도 출력하지 않는다.
- **FR-007**: 오류 문장은 `HTTP <상태> <호출>: <사유>` 또는 `네트워크 오류 <호출>` 꼴이며 토큰·개인 키·응답 본문 전체를 싣지 않는다.
- **FR-008**: 번호 점검 통과 시 버전·이번 번호·커밋(앞 7자)·스토어 마지막 번호를 실행 요약에 남긴다.
- **FR-009**: 판정은 순수 함수로 분리해 스토어 응답 대역으로 시험한다. 새 의존성을 더하지 않는다.
- **FR-010**: 이 변경으로 `app.json`의 번호는 바뀌지 않는다. AGENTS.md의 「사람이 올린다」 서술은 새 사실(사람이 올리되 사전 점검이 스토어 번호와 견준다)로 고친다.

### Key Entities

- **번호 판정**: 입력(이번 번호, 스토어 번호 목록) → 결과(통과 / 실패: 같음·작음, 마지막 번호, 올려야 할 최소값, 무시한 비정수 개수).

## Success Criteria _(mandatory)_

- **SC-001**: 이미 있는 번호로 시작한 릴리스는 의존성 설치 전에 실패하고 그 문장만으로 무엇을 올릴지 알 수 있다(대역 시험).
- **SC-002**: 더 큰 번호는 통과하고 스토어에 쓰기 호출이 하나도 없다(대역 시험).
- **SC-003**: 스토어를 못 읽는 세 경우(403·연결 실패·형식 불일치)가 모두 빌드 전에 이름을 밝히며 실패한다.
- **SC-004**: 076·075의 워크플로 계약 테스트가 모두 통과하고, 새 계약이 위반 주입(순서 뒤바꿈·허용 밖 비밀·쓰기 권한 추가·단계에서 `${{ secrets }}`를 run에 보간)을 각각 잡는다.
- **SC-005**: 실제 스토어 응답과 서비스 계정·API 키의 읽기 권한은 소유자 요청으로 워크플로를 한 번 돌려 확인하기 전까지 「못 본 것」으로 문서에 남는다.

## Assumptions

- Play 서비스 계정은 이미 편집을 만들고 번들을 올릴 수 있어 번들 목록 조회도 같은 권한 범위(`androidpublisher`)에서 되리라 보지만, 실제로 되는지는 처음 돌려 볼 때 안다(원칙 V).
- App Store Connect API 키는 이미 빌드 조회(`builds`)를 쓴다(`testflight-notes`) — 같은 호출 종류다.
- 스토어를 못 읽는 경우의 우회 입력은 두지 않는다(YAGNI). 막히면 소유자가 권한을 주거나 점검을 걷는 PR을 낸다.
