# Phase 0 — Research: 최소버전 일기의 UI/UX 개선

**Date**: 2026-08-20 | **Plan**: [plan.md](plan.md)

원칙 V에 따라 **실측과 짐작을 갈라 적는다.** 「설치본 확인」은 이 기계의
`node_modules`를 직접 읽은 것이고, 「실기기 미확인」은 아직 재지 않은 것이다.

## §1. 회전 표시를 새 의존 없이 그릴 수 있는가 (FR-010, SC-015)

**Decision**: React Native 코어의 `ActivityIndicator`를 쓴다.

**Rationale**: 설치본에서 export를 직접 확인했다(2026-08-20):

- `node_modules/react-native/index.js:34` — `get ActivityIndicator()`
- `node_modules/react-native/types/index.d.ts:83` — 타입도 함께 나온다

**이미 쓰는 패키지의 일부이므로 새 의존이 0개다**(SC-015 통과). 네이티브 뷰이지만
**RN 코어가 이미 링크하는 것**이라 release의 R8·ProGuard에서 새로 위험해지는 표면이
아니다 — 006이 `react-native-safe-area-context`(외부 네이티브 모듈)를 넣고도 release에서
통과한 것보다 낮은 위험이다.

**원칙 IV 관점**: `ActivityIndicator`는 **`animating` 불리언과 크기·색만 받는다.**
진행률을 넣을 파라미터가 **없다** — 담고 싶어도 담을 자리가 없는 것이 이 선택의
부수 효과다.

**Alternatives considered**:

| 대안 | 기각 이유 |
| --- | --- |
| `react-native-progress` 등 외부 패키지 | 새 의존이 생기고(SC-015 위반), **진행률을 담는 API를 함께 들여온다** — 원칙 IV를 어기기 쉬워진다 |
| `Animated`로 직접 회전 구현 | 코어로 되는 것을 직접 만드는 것이며 코드가 늘고 얻는 것이 없다 |
| 문구만 깜빡이기(clarify Option B) | 사용자가 거부. 표시가 약해 「멈췄나」를 여전히 물을 수 있다 |

**Risk**: 없음에 가깝다. 다만 **release에서 눈으로 확인한다**(SC-016) — 006의
SafeAreaView 교훈이 「빌드 통과가 화면 통과가 아니다」였다.

## §2. 캐릭터 선택을 어디에 저장하는가 (FR-003)

**Decision**: `expo-file-system`으로 **문서 자리에 작은 JSON 파일 하나.**
003의 `ModelState` 파일과 **같은 모양·다른 자리**다.

**Rationale**: 설치본 확인 결과 **`@react-native-async-storage/async-storage`가
의존에 없다**(2026-08-20, `package.json`). 흔한 선택이지만 여기서는 새 의존이며
SC-015를 어긴다.

반면 `expo-file-system`은:

- **이미 의존이고**(`~57.0.4`), 일기 저장이 이것으로 돈다
- **실기기에서 왕복이 검증됐다**(2026-08-13) — 저장·조회·덮어쓰기·목록
- **release의 R8에서 살아남는 것이 확인됐다**(2026-08-20) — 일기가 실제로 저장됐다
- 003이 [expo-port.ts:115](../../src/models/expo-port.ts#L115)에서 **임시 파일에 쓰고
  옮기는 방식**으로 원자적 쓰기를 이미 한다 — 그 패턴을 그대로 베낀다

**어느 자리인가**: 일기 디렉터리(`files/diary/`)에 **넣지 않는다.** 넣으면
`listDays()`가 그것을 날짜로 파싱하려 들고, 목록에 정체불명의 줄이 생긴다.
별도 이름의 자리에 둔다.

**앱을 지우면 함께 사라진다** — 그것이 옳다. 캐릭터 파일도 함께 사라지므로
선택만 남아 있으면 준비되지 않은 것을 고른 상태가 된다(FR-005c가 막는 상태).

**Alternatives considered**:

| 대안 | 기각 이유 |
| --- | --- |
| `AsyncStorage` | 새 의존(SC-015 위반). 얻는 것은 편의뿐 |
| 003의 `ModelState` 파일에 함께 넣기 | **선택은 사용자의 뜻이고 `ModelState`는 파일의 사실이다.** 섞으면 「받으면 골라진다」로 흐르기 쉽고 FR-008과 충돌한다. 003의 스키마를 007이 바꾸는 것도 결합을 늘린다 |
| 저장하지 않고 매번 첫 준비된 것 | 그것이 **지금의 결함 그 자체**다(FR-003 위반) |
| `expo-secure-store` | 비밀이 아니다. 새 의존이며 과하다 |

**Risk (원칙 V — 아직 짐작)**: 파일이 깨졌을 때의 동작은 **관측하지 않았다.**
설계는 「읽지 못하면 고른 것이 없다로 떨어진다」로 정한다 — 지어내지 않는다.

## §3. `stop()`을 화면까지 어떻게 잇는가 (FR-013, FR-014b)

**Decision**: `selectBackend()`와 `createAppPipeline()`이 **backend를 함께 돌려주고**,
`App.tsx`가 그것의 `stop`을 화면에 넘긴다.

**Rationale**: **배선이 끊겨 있다는 것을 계획 중에 발견했다**(2026-08-20, 코드 확인):

| 자리 | 상태 |
| --- | --- |
| [on-device.ts:41](../../src/inference/on-device.ts#L41) | `StoppableBackend = InferenceBackend & { stop() }` — **있다** |
| [on-device.ts:122](../../src/inference/on-device.ts#L122) | `async stop()` 구현 — **있다** |
| [DiaryHomeScreen.tsx:49](../../src/ui/DiaryHomeScreen.tsx#L49) | `stop?` prop을 받아 `AppState`에서 부른다 — **있다** |
| [select.ts:60](../../src/inference/select.ts#L60) | `{ ok: true; backend: InferenceBackend }` — **여기서 `stop`이 타입에서 사라진다** |
| [wiring.ts](../../src/app/wiring.ts) | `{ pipeline, location }`만 돌려준다 — **backend를 버린다** |
| [App.tsx](../../App.tsx) | `stop`을 넘기지 않는다 — **넘길 것이 없다** |

**그래서 005 FR-014b(앱이 앞을 벗어나면 끊는다)가 실기기에서 한 번도 돈 적이 없다.**
AGENTS.md는 「생성이 30초라 홈에 다녀오는 사이에 끝나 버려 확인하지 못했다」고 적었는데,
**확인하지 못한 진짜 이유는 배선이 없었다는 것이다.**

**왜 조용히 통과했는가** — 이 결함의 성질이 006의 `GenerationProbe`와 같다:

1. `stop?`이 **옵셔널**이라 넘기지 않아도 타입 검사가 통과한다
2. 화면 테스트는 **prop을 직접 주입**하므로 초록불이다
3. 실기기에서도 **아무 일이 일어나지 않을 뿐** 오류가 나지 않는다

**고치는 방향**: 타입을 좁히는 자리를 넓힌다. `selectBackend`의 온디바이스 갈래가
이미 `StoppableBackend`를 만들고 있으므로 **그것을 `InferenceBackend`로 좁혀 돌려주는
것을 멈추면 된다.** 데스크톱 갈래에는 끊을 것이 없으므로 `stop`이 없을 수 있다 —
그래서 옵셔널로 남는다.

**파이프라인은 이것을 모른 채로 둔다**(005 FR-025의 판단 유지). 끊기는 것은 화면의
일이고, 파이프라인은 `interrupted`를 **결과로 받을 뿐**이다.

**Alternatives considered**:

| 대안 | 기각 이유 |
| --- | --- |
| `InferenceBackend`에 `stop()`을 넣어 넓히기 | 005 FR-025가 명시적으로 거부했다. 데스크톱에는 끊을 것이 없고 파이프라인이 알 필요가 없다 |
| 화면이 `on-device.ts`를 직접 import | `select.ts`를 우회하는 것이며 FR-025(001)를 어긴다 — 어댑터를 직접 만들지 않는다 |
| `AbortController`를 파이프라인에 통과시키기 | 표면이 크게 늘고, 네이티브 `stopCompletion()`은 신호를 받는 모양이 이미 다르다 |

**⚠️ 실기기 미확인**: 끊김이 실제로 도는 것은 **아직 관측되지 않았다.** 007이
그만두기 버튼을 만들면 **사람이 원할 때 끊을 수 있으므로 30초를 기다릴 필요 없이
검증된다** — 이 기능이 처음으로 그것을 확인할 수 있게 한다.

## §4. 그만둔 뒤 부분 결과를 어떻게 버리는가 (FR-014a, FR-014b)

**Decision**: **화면이 `stop()`을 부른 뒤 그 생성의 결과를 무시하고 목록으로 간다.**
결과를 화면 상태에 담지 않는다.

**Rationale**: 실측된 사실이 이 설계를 강제한다(2026-08-17, AGENTS.md):

> `stopCompletion()`은 `completion()`을 거부시키지 않는다. `interrupted: true`인
> 결과로 **정상 resolve된다** — **그 결과에도 거기까지 생성된 `text`가 들어 있다.**

그래서 「끊었으니 글이 없다」가 **성립하지 않는다.** 다만 판정 순서가 이미 방어하고
있다 — `acceptance.ts`가 `unfinished`를 **가장 먼저 보므로**, 끊긴 결과는
`rejected: unfinished`가 되어 **`PipelineResult`에 `entry`가 실리지 않는다**(002 FR-012).

**즉 파이프라인 계층에서 이미 막힌다.** 007이 더할 방어는 화면 쪽이다:

- 그만두기를 누르면 화면은 **`afterGeneration()`을 부르지 않고** 곧장 목록으로 간다
- 부르더라도 `failed`로 갈릴 뿐 글이 없다 — **이중 방어**

**Alternatives considered**: 부분 결과를 보여주는 안(clarify Option B)은 사용자가
거부했다. **006의 「저장 실패 때는 보여준다」 판례를 넓히지 않는다** — 그것은 생성이
*성공한 뒤*의 사건이고, 끊긴 글은 판정을 통과하지 못한 글이다.

## §5. 목록의 사진 신호를 추가 비용 없이 얻는가 (FR-018, FR-020)

**Decision**: `listDiaries()`가 이미 읽는 `DiaryEntry`에서 `signalsUsed.photos`를 꺼낸다.

**Rationale**: clarify 중 코드 확인으로 **전제가 틀렸음이 드러났다**(2026-08-20,
[store.ts:119](../../src/diary/store.ts#L119)):

```
const days = await store.listDays();
... return { day, readable: (await store.load(day)) !== null };
```

**`readable`을 판정하기 위해 이미 날짜마다 전체 일기를 역직렬화하고 있다.**
그래 놓고 `DiaryListItem`은 `{ day, readable }`만 남기고 **나머지를 버린다.**

따라서 사진 신호를 함께 보이는 데 **추가 읽기가 0이다.** 버리던 것을 살리는 것뿐이다.

**006 FR-020의 취지는 유지된다** — 그것이 막으려던 것은 **목록에 전문을 보이는 것**과
그로 인한 비용이었다. 목록은 여전히 전문을 보이지 않으며(FR-020 개정), 사진 갈래
하나만 가져온다.

**Alternatives considered**:

| 대안 | 기각 이유 |
| --- | --- |
| 목록 전용 요약 파일을 따로 만들기 | 같은 사실이 두 곳에 생겨 어긋날 수 있다. 지금 비용이 0인데 캐시를 더하는 것은 이른 최적화다 |
| 전문 미리보기를 함께 | 006 FR-020이 거부했고 007도 유지한다(clarify Q4) |
| 사진 외 신호도 전부 | clarify에서 사용자가 거부. 전부 `unknown`이라 소음이 된다 |

**⚠️ 006 이전 일기와의 호환**: `signalsUsed`는 002부터 `DiaryEntry`에 있었으므로
저장된 일기에 **이미 들어 있다.** 다만 **읽지 못하는 일기**(`readable: false`)에는
신호가 없다 — 그때는 날짜와 「읽을 수 없다」만 보인다. **지어내지 않는다**(원칙 V).

## §6. 캐릭터를 고르는 자리에서 모델 정보가 새지 않게 하려면 (FR-007, 원칙 III)

**Decision**: 003의 `CharacterListScreen`이 쓴 방어를 그대로 베낀다 — **선택 화면이
`roster.ts`·`ModelAsset`·`assetFor()`를 import 하지 않는다.**

**Rationale**: 003이 이 문제를 이미 풀었고 그 방식이 검증됐다:

> 이 파일은 `ModelAsset`을 import 하지 않는다. 자산키·주소·크기·지문에 닿는 경로가
> 아예 없으므로, **조심해서 안 쓰는 것이 아니라 쓸 수 없다.**

007의 선택 화면도 같다. 받는 것은 **`Character` 식별자와 준비 여부(불리언)**뿐이다.
바이트 수도 받지 않는다 — 003은 저장 공간 관리를 위해 `usage`를 받았지만
**007의 선택 화면에는 그 목적이 없다.**

**표시 문안을 짓지 않는다**(FR-009). 헌법이 「캐릭터 이름은 사람이 짓는다」고 했고
성격 설명은 관측 근거가 이 저장소에 없다(원칙 IV). **자리표시 식별자를 그대로 보인다** —
003이 같은 판단을 했고 007이 뒤집을 근거가 없다.

**⚠️ 유일한 예외**: 헌법 로스터가 `imaginative`에 대해 「상상을 섞는다는 것을
사용자에게 알린다(MUST)」고 요구한다. **이것은 헌법 본문이 근거이므로 지어낸 설명이
아니다**(FR-009 예외). 006 실기기 실측이 이것을 뒷받침한다 — 같은 하루·같은 프롬프트에서
`quiet`은 지어낸 것 0건, `imaginative`는 2건이었다.

**Alternatives considered**: 캐릭터마다 성격 소개를 붙이는 안은 **원칙 III 위반**이다.
관측이 별도 저장소의 몫이므로(원칙 IV) 지금 쓸 수 있는 근거가 헌법 본문뿐이다.

## §7. 「옮김」을 어디서 판단하는가 (FR-005, FR-005a~c)

**Decision**: **순수 함수 `resolveSelection()`이 판단하고 화면은 결과를 그린다.**
`src/app/selection.ts`에 둔다.

**Rationale**: 이 규칙이 007에서 **가장 갈래가 많은 판단**이다:

- 고른 것이 준비돼 있다 → 그대로
- 고른 것이 준비를 잃었고 다른 것이 있다 → **옮기고 알린다**(FR-005·005a)
- 고른 것이 준비를 잃었고 다른 것이 없다 → **고른 것 없음**(FR-005c)
- 고른 적이 없다 → 고른 것 없음 (**자동으로 고르지 않는다**, FR-008)

006이 `state.ts`·`readinessOf`·`acceptance`를 순수 함수로 둔 이유가 그대로 적용된다 —
**이 네 갈래 전부가 기기 없이 검증돼야 한다.** 기기에서만 재현되는 상태(캐릭터를 지운
직후)를 대역으로 만들 수 있어야 하기 때문이다.

**「알린다」를 값으로 만든다.** `resolveSelection()`이 「옮겨졌다」는 사실을 **결과에
담아** 돌려주고, 화면은 그것이 있으면 알림을 그린다. 화면이 스스로 비교해 판단하면
같은 규칙이 두 곳에 생긴다.

**Alternatives considered**: 화면의 `useEffect` 안에서 비교하는 안은 **테스트가
기기·렌더 타이밍에 묶인다.** 006이 `initialScreen()`을 순수 함수로 뺀 것과 같은 이유로
기각한다.
