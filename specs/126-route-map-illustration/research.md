# Phase 0 연구 — 126 하루 동선 지도

## R1. 파일 형식 — 격자 칸 + 층별 블록 (결정)

- **결정**: 전국을 0.1도(경도 약 8.8km·위도 약 11km) 격자로 나눠 칸마다 **7개 층 블록**을 둔다. 칸 목록(칸 번호 → 블록 위치 표)은 파일 앞에 둔다. 좌표는 칸 안 상대 정수(1e-5도, 칸 폭 10,000단위 = u16)이고 한 선·면 안에서는 이전 점과의 차를 zigzag 가변길이로 담는다. 선·면은 칸 경계에서 자른다. 자세한 형식은 [contracts/map-file.md](contracts/map-file.md).
- **근거**: ① 600m 상자(칸 하나 안)에는 골목까지, 37km 상자(칸 여럿)에는 주요 도로만 필요하다 — 층별 블록이면 필요한 층만 해석한다 ② 장소 파일(`PLC1`)의 「헤더 + 표 + 순수 파서 + 빌드와 형식 상수 공유」 선례를 따른다 ③ 칸 경계 자르기는 칸 겹침 조회·중복 그림을 피한다.
- **버린 안**: 통짜 선 목록(상세 정도를 못 가른다), 0.01도 칸(전국 40만 칸 표가 파일의 상당 부분), SVG 문자열 그대로(해석은 쉽지만 용량 2배 이상).

## R2. 층과 단순화 (결정 — 값은 사람이 정한 값, 빌드 상수 한 곳)

| 층 | 내용(OSM 태그) | 형태 | 허용 오차(m, 처음 값) | 전국 추정 |
|---|---|---|---|---|
| L0 물 | `natural=water`·`wetland`, 해안선으로 닫힌 바다 | 면 | 20 | 약 1.5MB |
| L1 공원·숲 | `leisure=park`, 1km² 이상 `landuse=forest`·`natural=wood` | 면 | 20 / 40 | 약 0.3MB |
| L2 철도 | `railway=rail·subway` | 선 | 8 | 약 0.4MB |
| L3 강 | `waterway=river` | 선 | 15 | 약 0.2MB |
| L4 주요 도로 | motorway·trunk·primary(+link) | 선 | 8 | 약 0.8MB |
| L5 2·3차 도로 | secondary·tertiary(+link) | 선 | 8 | 약 1.8MB |
| L6 골목 | residential·unclassified·living_street | 선 | 8 | 약 4.9MB |

- 전국 추정은 점당 2.2바이트·선당 2바이트 가정으로 잰 값을 층에 나눠 적은 것이다(합계 약 8.8MB). **실제 팩 크기는 빌드 첫 실행이 정한다.** 상한 `MAP_MAX_BYTES`를 넘으면 허용 오차를 L6부터 올리거나(8→12m) 숲 문턱을 올린다 — 사람이 값을 고쳐 다시 돌린다(자동 튜닝 없음).
- 제외: 보행로·오솔길·건물(소유자 결정), `highway=service`(주차 진입로까지 늘어 용량이 급증).
- 600m 상자에서 8m 허용 오차는 모형(1.1m)보다 거칠어 **모서리가 각져 보일 수 있다.** 실기기에서 보고 L6 허용 오차를 줄일지 정한다(그때 용량이 늘어 상한이 바뀐다 — 소유자 결정 사항).

## R4. 읽기 방식 — 파일 전체 바이트를 한 번 읽어 프로세스에 둔다 (결정)

- `src/map/map-port.ts`가 `prepare()`(자산 경로 얻기)와 `load()`(`File.bytesSync` — **비동기 `File` 호출 금지**, AGENTS)로 바이트를 얻어 프로세스 안에 둔다(지도 열 때마다 9MB를 다시 읽지 않는다). 앱 시작에는 읽지 않고 **첫 쓴 날 지면에서만** 읽는다.
- 부분 읽기(`File.open()`의 `FileHandle`)는 SDK 57에서 동기 부분 읽기 API가 확인되지 않아 쓰지 않는다. 9MB 상주는 장소 파일과 같은 규모이며 R3에서 측정한다.
- `bytesSync`가 지면을 멈추면 `prepare()`에서 읽기를 앞당기는 것이 다음 안이다(결정은 측정 뒤).

## R5. 그리기 — `react-native-svg` 15.15.4 (결정)

- 지도 층만 `Svg`(viewBox `0 0 1000 620`)로 그린다: `Rect`(바탕)·`Path` 여러 개(면·선, 굵기 단계별). 점·번호·직선·라벨은 지금처럼 RN `View`/`AppText`로 그 위에 얹는다 — 번호·라벨 글자가 `Svg` 글자 렌더에 묶이지 않고 dp 크기가 글꼴 배율에 변하지 않는다.
- 한 `Path`의 점이 많아 느린지는 R3에서 잰다. 문턱을 넘으면 길 등급별로 나눠 그린다.
- 새 네이티브 의존성의 위험은 「개발 빌드 재설치」 하나다. 안드로이드: `expo prebuild --clean` 뒤 `adb install -r`(모델·일기 보존), iOS: 개발 서명 빌드.
- 대안(Skia·캔버스)은 더 무겁고 Expo SDK 57 기본 목록에 없다.

## R6. 상자·최소 폭 (결정)

- 125 `project()`의 배율에 상한을 더한다: 프레임 폭 ≥ `MIN_FRAME_METERS`(600m). 자리 1곳·100m 안 몰림이면 프레임이 600m로 고정되고 점은 중앙이거나 합친 점(「1·4」)이다. 퇴화 규칙(`SAME_PLACE_METERS` 안이면 도식 없음)과 「한 곳이면 도식 없음」은 걷는다 — **도식 여부는 `visits`를 읽었고 저장된 자리와 일치하느냐만 정한다**.
- 점 합치기(DU8, 22dp 안)는 그대로다. 600m 상자에서 70m는 약 37dp라 합쳐지지 않고 떨어져 보인다(모형 확인).
- 상세 정도: 프레임 폭 < 3km → L0~L6, 3~15km → L0~L5, ≥ 15km → L0~L4(값은 사람이 정한 값).

## R7. 라벨 배치 (결정)

- 점 옆 이름은 오른쪽(점이 상자 오른쪽 45%에 있으면 왼쪽)을 먼저 놓고, 점·앞 라벨과 겹치면 위·아래 대각선 후보 중 겹치지 않는 첫 자리에 놓는다. 어디도 안 되면 그 라벨만 생략한다(FR-010). 글자 폭은 한글 한 글자 12.5dp(글꼴 12)로 어림한다. 어림과 배치는 순수 함수 `labelPlacement`(`DayRouteSection` 쪽)가 하고 단위 테스트로 잠근다. 글꼴 배율에는 변하지 않는다(범례가 정확한 이름을 맡는다).

## R8. 색 토큰 (결정)

- 지도 전용 색 5개를 `design/tokens.json` `color`에 올린다 — `mapLand`·`mapWater`·`mapPark`·`mapRoad`·`mapRoadMinor`(라이트는 모형 값에서 시작: `#efe9dc`·`#a9cfe2`·`#bfd9a8`·`#fffdf7`·`#fbf6ea`, 다크는 웹 전용이라 어두운 짝을 적는다). 대비 쌍은 `text`/`mapLand`(라벨 후광 면)를 올린다. 건물 색은 건물을 안 넣으므로 올리지 않는다.
- `design/DESIGN.md`에 「지도 전용 색은 동선 지도에서만 쓴다」 한 줄을 더한다.

## R9. 방침·라이선스 (확인 결과)

- 방침(`site/privacy`)은 사진 좌표를 앱에 든 지도 자료(OpenStreetMap)로 장소 이름을 찾는 데 쓴다고 말하고(36행), 일기는 휴대폰 기본 백업에 포함될 수 있다고 말한다(103행). **좌표가 일기에 저장되면 백업에도 방문 위치가 담기므로 이 서술을 보강한다**(FR-018). 외부 전송은 늘지 않아 스토어 「위치 수집 안 함」 선언(`docs/store/privacy-declarations.md`)은 그대로다.
- `__tests__/privacy/`가 방침 문장을 잠그는 곳(`policy-facts`·`declarations`)은 tasks에서 읽어 보고 새 서술에 맞춘다.
- `site/licenses`의 OSM 항목 제목이 「장소 이름 데이터」라 「지도 그림」 용도를 한 줄 더한다(ODbL 표기 의무는 이미 충족, 용도 서술만 맞춘다).

## R12. 좌표 저장 (결정 — 소유자 결정 2026-11-22)

- 일기를 쓸 때 `entry.places[i]`에 `latE5`·`lonE5`를 더한다(약 1m 정밀도, 소유자 선택). 121 R9의 「좌표를 일기 파일에 늘리지 않는다」를 뒤집는다 — 사진을 지우면 지도가 다 사라지기 때문이다.
- 옛 일기는 좌표가 없다. 열 때 일기를 고쳐 쓰는 이행은 하지 않는다(보기만 하는 동작이 파일을 바꾸지 않는다는 125 계약). 옛 일기는 사진을 다시 읽어 일치할 때만 지도가 보이고, 새로 쓰는 일기부터 영구하다.
- 크기: 자리당 정수 둘(JSON 약 20바이트), 12곳이면 약 250바이트로 백업 한도 논의에 닿는 크기가 아니다.

## 실제 빌드 기록 (2026-11-22, T012·T047)

- 첫 실제 빌드는 **14.36MB**였다(처음 추정 약 8.8MB — 점당 2.2바이트 가정이 짧았다: 도형마다 가변 정수 머리·첫 점 4바이트가 있고 OSM은 길을 교차로마다 쪼갠다). 상한 10MB를 넘어 빌드가 실패했다(BM4).
- 사람이 정한 값을 사다리대로 고쳐 **9.74MB**(9,735,426바이트)에 맞췄다: 교차로에서 쪼개진 선을 끝점이 정확히 둘만 만나는 곳에서 잇기(`mergeLines`, 도형 수 49만 → 30만) · 작은 길 허용 오차 8→15m · 60m 미만 작은 길 조각 제외 · 2·3차 도로 허용 오차 10m · 공원 50m · 숲 10km² 이상(허용 오차 60m). (코드 리뷰 뒤 면을 바깥 고리 반시계·구멍 시계로 맞춰 담으면서 공원 층이 커져 숲 문턱을 5→10km²로 올렸다.)
- 층별 칸 블록 바이트: 물 0.80MB · 공원·숲 1.38 · 철도 0.17 · 강·해안선 0.74 · 주요 도로 0.87 · 2·3차 도로 1.64 · 골목 4.07.
- 한계: **해안선은 선(강 층)으로만 담는다 — OSM에 바다 면이 없어 바다 위 프레임은 바닥색으로 보인다.** 600m 상자에서 골목 허용 오차 15m와 60m 미만 조각 제외가 모형(1.1m)보다 거칠다 — 실기기에서 본다(미확인).
- R8 보정: 지도 색은 정본의 별도 묶음 `mapColor`(앱 `MAP_COLORS`)에 있고, `mapRoad`는 큰 길과 골목의 가는 선, `mapRoadMinor`는 중간 길(2·3차)의 선이다(철도 선은 `COLORS.border` 반투명).
