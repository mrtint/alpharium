## Clarifications

### Session 2026-10-31

- Q: 확인 전용 상한은 몇 토큰인가? → A: 16토큰(소유자 선택, 사람이 정한 값 — 측정 아님).
- Q: 상한을 담는 자리는? → A: 이번 호출의 한도를 담는 기존 자리(`RunLimits`)에 선택 필드 하나. (에이전트 판단 · 근거: 「이번 호출의 한도」가 이미 그곳에 있고, 주지 않으면 종전과 같아 일기 경로가 손대지 않은 채 남는다)
- Q: 제목 질문(`ask`)도 이 필드를 따르나? → A: 따른다. 지금 넘기는 곳은 확인 하나뿐이다. (에이전트 판단 · 근거: 같은 한도 타입을 받는 두 메서드가 다르게 굴면 함정이다)
- Q: 조각 생성에서 상한은 어떻게 걸리나? → A: 조각 수를 상한으로 계산하고 마지막 조각을 남은 만큼으로 줄인다 — 16이면 16토큰짜리 조각 하나. 미리 읽기 토막은 생성이 아니라 그대로다. (에이전트 판단 · 근거: iPhone 화면의 확인은 이 경로를 탄다, 상한이 조각 크기에 묻히면 단축이 없다)
- Q: 확인 시간 한도(60초)를 줄이나? → A: 아니다, 근거 주석만 고친다. (에이전트 판단 · 근거: 바꿀 실측이 없다, 원칙 V)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 첫 실행의 정상 동작 확인이 더 빨리 끝난다 (Priority: P1)

새 사용자는 작명 뒤 「확인 중」 화면에서 휴대폰이 실제로 답을 하는지 기다린다. 지금은 확인용 짧은 인사의 답을 일기 한 편 길이까지 받을 수 있어, 모델이 인사를 길게 이어 가면 그만큼 기다린다. 확인은 「답이 오기 시작했는가」만 보므로 답의 앞 몇 토큰이면 충분하다.

**Why this priority**: 이 묶음(G2)의 유일한 목적이다. 첫 일기 분기(G3)의 되돌림이 이 확인을 다시 돌리므로 짧을수록 그 경로도 싸진다.

**Independent Test**: 확인 호출이 받는 생성 길이가 확인 전용 상한으로 제한되는지를 엔진 대역으로 확인한다. 실기기에서는 확인 화면 체류 시간을 전·후로 잰다.

**Acceptance Scenarios**:

1. **Given** 모델이 열린다, **When** 정상 동작 확인이 돈다, **Then** 생성은 확인 전용 상한(16토큰)을 넘지 않고, 답이 비지 않으면 통과한다.
2. **Given** 상한에서 답이 잘렸다, **When** 판정한다, **Then** 잘린 답도 통과다(종전 판정 그대로 — 잘렸다는 것은 말을 시작했다는 뜻).
3. **Given** iPhone 화면 쓰기처럼 조각으로 생성하는 경로, **When** 확인이 돈다, **Then** 같은 상한에서 끊긴다.

---

### User Story 2 - 일기와 제목은 지금 길이 그대로 써진다 (Priority: P1)

확인을 짧게 끊는 상한이 일기 본문·제목 생성으로 새면 일기가 잘린다. 일기 쪽 상한은 바뀌지 않아야 한다.

**Why this priority**: 새면 제품의 핵심(일기)이 망가진다(원칙 I — 일기는 같은 샘플링).

**Independent Test**: 일기 본문·제목·조각 생성 호출의 생성 상한이 종전 값(512)인지 엔진 대역으로 확인한다.

**Acceptance Scenarios**:

1. **Given** 확인이 끝난 뒤, **When** 일기를 쓴다, **Then** 본문·제목 호출의 생성 상한은 512다.
2. **Given** iPhone 조각 생성, **When** 일기를 쓴다, **Then** 조각 수 상한이 종전과 같다(512 ÷ 32).

---

### User Story 3 - 짧게 끊긴 확인도 안전하게 정리된다 (Priority: P2)

확인이 한도에 걸리거나 앱이 정리를 부를 때, 생성이 실제로 끝난 뒤에만 모델을 놓아야 앱이 죽지 않는다(079).

**Why this priority**: 이미 지켜지는 규칙이 짧은 생성에서도 지켜지는지 확인하는 회귀 방어다.

**Independent Test**: 상한을 받은 생성이 도는 중에 정리를 불러, 생성이 끝나기 전에는 해제가 불리지 않는지 엔진 대역으로 본다.

**Acceptance Scenarios**:

1. **Given** 확인 생성이 돌고 있다, **When** 정리를 부른다, **Then** 해제는 생성이 끝난 뒤에 한 번 불린다.

### Edge Cases

- 첫 토큰 몇 개가 공백·줄바꿈뿐이면 상한 안에서 글자가 하나도 안 나올 수 있다 → 상한을 「몇 토큰」(16)으로 둬 여유를 둔다. 그래도 비면 종전대로 「실패」 화면(다시 시도/그냥 시작하기)이 받는다.
- 확인 시간 한도(60초)는 그대로다. 짧아진 생성에서는 한도에 닿을 일이 줄 뿐 한도의 뜻은 같다.
- 모델 적재 시간은 이번 변경으로 줄지 않는다 — 확인 시간 대부분이 적재라면 체감 단축은 작을 수 있다(실기기에서 잰다).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 정상 동작 확인의 생성은 확인 전용 상한 16토큰에서 끊겨야 한다(MUST). 값은 **사람이 정한 값**이다(소유자, 2026-10-31 — 측정 아님).
- **FR-002**: 엔진은 「이번 호출만의 생성 상한」을 받을 수 있어야 하고, 받지 않은 호출은 종전 상한을 써야 한다(MUST). 일기 생성의 샘플링 정본 값은 바뀌지 않는다(MUST NOT 변경).
- **FR-003**: 일기 본문·제목·조각 생성의 생성 상한은 종전 값이어야 하며 테스트로 잠근다(MUST).
- **FR-004**: 판정 규칙(모델이 열렸나 · 한도 안인가 · 답이 비지 않았나)은 바뀌지 않는다(MUST NOT 변경). 답 텍스트는 판정 직후 버린다(L10).
- **FR-005**: 짧게 끊긴 생성에서도 정리는 생성이 끝난 뒤에만 모델을 놓아야 한다(MUST, 079).
- **FR-006**: 사용자에게 보이는 문구는 바뀌지 않는다(MUST NOT 변경).
- **FR-007**: 확인 시간 한도의 근거 설명이 「끝까지 받는다」를 전제로 하면 고친다. 한도 값 자체는 바꾸지 않는다(실측 근거 없음, 원칙 V).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 확인 한 번이 받는 생성 길이가 16토큰 이하다(대역 테스트로 확인).
- **SC-002**: 일기 본문·제목 생성의 상한이 바뀌지 않았다(대역 테스트로 확인), 실기기 첫 일기가 종전처럼 정상 길이로 써진다.
- **SC-003**: 실기기(안드로이드 SM-S901N·iPhone 14) 첫 실행 확인이 통과하고, 확인 화면 체류 시간이 전보다 길어지지 않는다(전·후 각 1회 이상 — **실기기 확인 대기**, 이 세션은 클라우드라 기기가 없다).

## Assumptions

- F3(사진 모듈 적재 확인)은 범위 밖이다(소유자는 F1을 골랐다). G3(첫 일기 분기·실패 되돌림)·G4(설정 창)도 범위 밖이다.
- 확인 시간의 대부분이 생성인지 적재인지는 실측이 없다 — 단축 폭은 짐작이며 실기기에서 잰다.
