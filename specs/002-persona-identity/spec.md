# Feature Specification: 퍼소나 정체성 부여

**Feature Branch**: `002-persona-identity`

**Created**: 2026-08-01

**Status**: Draft

**Input**: User description: "002 퍼소나 스펙 — 퍼소나의 이름과 성격 부여 규칙을 확정한다. ROADMAP의 다섯 질문에만 답한다: 이름 부여 방식, 성격 표현 형태, 성격의 분포, 이름 변경 제약, 최초 부여 시점."

## 이 스펙의 범위 *(먼저 읽을 것)*

[001](../001-persona-diary-contracts/spec.md)이 퍼소나가 **무엇을 보유하는지**(이름·성격)를 못 박았다. 이 스펙이 답하는 것은 **그 이름과 성격이 어디서 오고, 언제 정해지고, 무엇이 바꿀 수 있는가**다.

[ROADMAP](../ROADMAP.md)의 「002 — 퍼소나 스펙」이 요구하는 다섯 질문이 이 문서의 전부다.

| # | 질문 | 답한 곳 |
| --- | --- | --- |
| 1 | 앱이 이름을 **어떻게** 부여하는가 | FR-101~FR-104 |
| 2 | 성격이 **어떤 형태로 표현**되는가 | FR-110~FR-113 |
| 3 | 성격의 **가짓수와 분포** | FR-114~FR-117 |
| 4 | 이름 변경의 **제약** | FR-120~FR-127 |
| 5 | 최초 부여가 **언제** 일어나는가 | FR-130~FR-134 |

### 이 스펙이 답하지 않는 것

| 항목 | 넘기는 곳 |
| --- | --- |
| 성격이 프롬프트에 어떻게 반영되는가, 성격별 문체 | 004 추론 |
| 퍼소나를 화면에 어떻게 보여주는가, 이름 변경 UI | 006 UI |
| 이름·성격을 어떤 형식으로 저장하는가 | 005 저장 |
| 후보 목록·카탈로그에 들어갈 **실제 문자열** | 구현 단계 |

**성격별 문체 예시를 쓰고 있다면 004의 영역을 파고 있는 것이다** — ROADMAP이 정한 이 스펙의 실패 신호다.

## 도메인 개념 *(mandatory)*

퍼소나는 사용자의 아바타가 아니라 **휴대폰 자신**이다. 이름과 성격은 사용자가 자신을 표현하기 위해 고르는 것이 아니라, 휴대폰이 **가지고 태어나는 것**이다. 사용자가 이름만 고쳐 부를 수 있고 성격은 건드릴 수 없는 비대칭은 여기서 나온다 — 이름은 부르는 사람의 것이지만 성격은 그 존재의 것이다.

따라서 부여는 **선택 화면이 아니라 발견**에 가깝다. 사용자는 "어떤 성격을 원하십니까"를 묻는 화면을 만나지 않는다. 앱을 열면 이미 이름과 성격을 가진 휴대폰이 거기 있다.

성격이 무작위로 갈리는 이유도 같다. 모두가 같은 성격을 받으면 "내 휴대폰은 이런 애구나"가 성립하지 않고, 사용자가 고르게 하면 그것은 사용자의 취향이지 휴대폰의 것이 아니다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 앱을 열자 휴대폰이 이미 거기 있다 (Priority: P1)

사용자가 앱을 처음 연다. 이름과 성격을 묻는 화면은 없다. 휴대폰은 이미 자기 이름과 성격을 가지고 있고, 사용자는 그것을 통보받는다.

**Why this priority**: 001 FR-001·FR-002가 요구하는 최소 조건이며, 퍼소나가 존재하지 않으면 001의 P1(일기 생성)이 성립하지 않는다. 004는 이 스토리의 산출물을 입력으로 받는다.

**Independent Test**: 퍼소나가 없는 상태에서 앱을 시작해, 사용자에게 아무것도 묻지 않고 이름과 성격이 부여되며 그것이 이후 조회에서 동일하게 나오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 퍼소나가 아직 없는 상태에서, **When** 사용자가 앱을 시작하면, **Then** 이름 하나와 성격 하나를 가진 퍼소나가 부여되어 있다.
2. **Given** 퍼소나가 부여되는 과정에서, **When** 사용자에게 요구되는 입력을 확인하면, **Then** 이름·성격 중 어느 것도 사용자에게 묻지 않는다.
3. **Given** 퍼소나가 부여된 뒤, **When** 앱을 여러 번 재시작하고 매번 퍼소나를 조회하면, **Then** 이름과 성격이 매번 동일하다 — 재시작이 재부여를 일으키지 않는다.
4. **Given** 퍼소나가 부여된 상태에서, **When** 부여된 성격을 확인하면, **Then** 그것은 앱이 보유한 성격 카탈로그의 항목 중 하나다.
5. **Given** 퍼소나가 부여된 상태에서, **When** 부여된 이름을 확인하면, **Then** 그것은 앱이 보유한 이름 후보 목록의 항목 중 하나다.

---

### User Story 2 - 이름을 고쳐 부르기 (Priority: P2)

부여된 이름이 마음에 들지 않는다. 사용자는 다른 이름으로 고쳐 부른다. 성격은 고칠 수 없다.

**Why this priority**: 001 FR-003이 요구하나, 001 계약 관점에서는 "퍼소나가 존재한다"만 있으면 일기 생성이 성립하므로 P1보다 뒤다. 다만 이름 변경이 퍼소나의 동일성을 깨뜨리면 001 FR-007이 무너지므로 계약은 P1과 함께 확정되어야 한다.

**Independent Test**: 이름을 바꾼 뒤 그 변경이 유지되는지, 성격은 변하지 않았는지, 과거 일기가 여전히 같은 퍼소나에 귀속되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 퍼소나가 존재할 때, **When** 사용자가 유효한 이름으로 변경하면, **Then** 이후 조회와 일기 생성에 변경된 이름이 반영된다.
2. **Given** 이름을 변경한 뒤, **When** 성격을 확인하면, **Then** 성격은 변경 전과 동일하다.
3. **Given** 이름을 여러 번 변경한 뒤, **When** 과거에 생성된 일기를 조회하면, **Then** 그 일기들은 여전히 같은 하나의 퍼소나에 귀속되어 있다.
4. **Given** 사용자가 빈 이름 또는 공백만으로 이루어진 이름을 입력하면, **When** 변경을 시도하면, **Then** 변경은 거부되고 기존 이름이 유지되며 거부 사유가 알려진다.
5. **Given** 사용자가 허용 길이를 넘는 이름을 입력하면, **When** 변경을 시도하면, **Then** 변경은 거부되고 기존 이름이 유지된다.
6. **Given** 사용자가 현재 이름과 완전히 동일한 이름을 입력하면, **When** 변경을 시도하면, **Then** 오류로 취급되지 않으며 퍼소나는 그대로 유지된다.
7. **Given** 퍼소나가 존재할 때, **When** 사용자가 성격을 변경할 방법을 찾으면, **Then** 그러한 수단이 제공되지 않는다.
8. **Given** 사용자가 이름 후보 목록에 있는 다른 이름을 직접 입력하면, **When** 변경을 시도하면, **Then** 변경이 허용된다 — 후보 목록은 부여에만 쓰이고 변경을 제약하지 않는다.

---

### User Story 3 - 전체 삭제 후 다시 만난 휴대폰 (Priority: P3)

사용자가 전체 삭제를 실행했다. 앱을 다시 열면 휴대폰이 처음처럼 이름과 성격을 가지고 나타나는데, 그것이 이전과 같으리라는 보장은 없다.

**Why this priority**: 001 FR-035와 US5 시나리오 6이 "처음 시작하는 것과 동일하게 새로 부여된다"를 요구하므로 계약은 이미 정해져 있다. 이 스펙이 더하는 것은 재부여가 **이전 값을 물려받지 않는다**는 성질이다.

**Independent Test**: 퍼소나가 존재하는 상태에서 전체 삭제를 실행하고 앱을 재시작해, 부여 절차가 최초 실행과 구별되지 않게 다시 일어나는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 퍼소나가 존재하고 사용자가 이름을 변경한 상태에서, **When** 전체 삭제 후 앱을 재시작하면, **Then** 이름과 성격이 새로 부여된다 — 삭제 전의 변경된 이름이 남아 있지 않다.
2. **Given** 전체 삭제 후 재부여된 퍼소나에 대해, **When** 부여 절차를 최초 실행 시의 것과 비교하면, **Then** 두 절차는 구별되지 않는다 — 이전 퍼소나의 존재가 재부여에 영향을 주지 않는다.

---

### User Story 4 - 기기를 바꿔도 같은 이름, 같은 성격 (Priority: P3)

사용자가 휴대폰을 바꿨다. 이름과 성격은 그대로다. 재부여는 일어나지 않는다.

**Why this priority**: 001 FR-005·FR-006과 헌법 원칙 0의 「퍼소나 지속성」이 요구한다. 부여 절차가 기기의 무엇인가를 재료로 쓰면 이 성질이 처음부터 성립하지 않으므로, 우선순위와 무관하게 부여 규칙이 확정되는 시점에 함께 못 박아야 한다.

**Independent Test**: 기기 식별자가 달라진 상태를 만든 뒤 이름·성격이 그대로인지, 부여 절차가 다시 실행되지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 이름과 성격을 가진 퍼소나가 있을 때, **When** 기기 식별자가 달라지면, **Then** 이름과 성격은 그대로이며 부여 절차가 다시 실행되지 않는다.
2. **Given** 부여 절차의 입력을 전수 확인할 때, **When** 그 입력에 기기에서 읽은 값이 있는지 보면, **Then** 하나도 없다.

---

### Edge Cases

- **부여 도중 앱이 종료됨** — 이름과 성격은 함께 정해지거나 함께 정해지지 않는다. 이름만 있고 성격이 없는 퍼소나, 또는 그 반대는 만들지 않는다. 부여가 완결되지 않은 상태로 앱이 다시 시작되면 부여를 처음부터 다시 실행한다.
- **이름 앞뒤에 공백이 붙은 입력** — 앞뒤 공백을 제거한 뒤 판정한다. 제거 결과가 빈 문자열이면 거부한다.
- **이름 중간에 공백이 있는 입력** — 허용한다. 사람이 부르는 이름에 공백이 들어가는 것은 정상이다.
- **이름 후보 목록의 이름과 같은 이름으로 변경** — 허용한다. 후보 목록은 부여 시에만 참조되며 이후 어떤 제약도 만들지 않는다.
- **이름의 중복** — 퍼소나는 동시에 하나뿐이므로(001 FR-007) 중복 검사 대상이 존재하지 않는다. 중복 제약을 두지 않는다.
- **후보 목록·카탈로그가 한 항목뿐인 경우** — 무작위 선택은 그 항목을 반환한다. 부여 실패로 처리하지 않는다.
- **사용자가 이름을 후보 목록의 것으로 되돌리고 싶은 경우** — 직접 입력으로 가능하다. "원래 이름으로 되돌리기" 기능은 두지 않는다.
- **일기 생성 시점에 퍼소나가 없는 경우** — 부여 시점(FR-130)에 따라 발생할 수 없다. 발생한다면 계약 위반이다.

## Requirements *(mandatory)*

### 이름 부여 *(질문 1)*

- **FR-101**: 앱은 **내장된 이름 후보 목록**을 보유해야 한다(MUST). 이 목록은 앱과 함께 배포되며 실행 중에 변하지 않는다(MUST NOT).
- **FR-102**: 최초 부여 시 앱은 후보 목록에서 **하나를 무작위로 선택**해 퍼소나의 이름으로 삼아야 한다(MUST).
- **FR-103**: 이름 선택에는 **기기에서 읽은 어떤 값도 재료로 쓰지 않아야 한다**(MUST NOT) — 기기 식별자, 기기 이름, 설치 시각, 관측된 신호 등. _근거:_ 001 FR-005·FR-006. 기기의 값이 재료로 들어가면 기기가 바뀌었을 때 같은 이름이 나온다는 보장이 사라진다.
- **FR-104**: 후보 목록에 담기는 **실제 이름 문자열과 목록의 크기는 이 스펙에서 확정하지 않는다**. 구현 단계에서 정하되, FR-120~FR-127의 유효성 규칙을 만족해야 한다 — 앱이 스스로 부여한 이름을 사용자가 다시 입력할 수 없는 상태를 만들지 않는다.

### 성격의 형태 *(질문 2)*

- **FR-110**: 앱은 **내장된 성격 카탈로그**를 보유해야 한다(MUST). 카탈로그는 앱과 함께 배포되며 실행 중에 변하지 않는다(MUST NOT).
- **FR-111**: 카탈로그의 각 항목은 **식별자**, **표시명**, **서술** 셋으로 구성되어야 한다(MUST).
  - **식별자** — 항목을 지목하는 값. 표시명이 바뀌어도 같은 성격임을 알 수 있게 하는 것이 목적이다. 퍼소나가 보유하는 것은 이 식별자다.
  - **표시명** — 사람이 읽는 짧은 이름.
  - **서술** — 그 성격이 무엇인지 사람의 말로 적은 것.
- **FR-112**: 퍼소나가 보유하는 성격은 **카탈로그 항목의 식별자 하나**여야 한다(MUST). 여러 항목을 조합하거나 항목 밖의 값을 가지지 않는다(MUST NOT).
- **FR-113**: 서술의 **문면과 길이는 이 스펙에서 확정하지 않는다**. 다만 서술은 **그 성격이 무엇인지를 적을 뿐, 일기를 어떻게 쓰라는 지시를 담지 않는다**(MUST NOT) — 문체·어미·문장 길이 같은 산출물의 형태는 004의 몫이다. _근거:_ 서술에 지시문이 섞이면 그것은 프롬프트 조각이 되고, 002가 004의 영역을 침범한다.

### 성격의 가짓수와 분포 *(질문 3)*

- **FR-114**: 성격 카탈로그는 **둘 이상의 항목**을 가져야 한다(MUST). 항목이 하나뿐이면 모든 사용자가 같은 성격을 받게 되어 FR-115가 무의미해진다.
- **FR-115**: 최초 부여 시 앱은 카탈로그에서 **하나를 무작위로 선택**해 퍼소나의 성격으로 삼아야 한다(MUST). 설치마다 갈린다.
- **FR-116**: 성격 선택에는 **기기에서 읽은 어떤 값도 재료로 쓰지 않아야 한다**(MUST NOT). FR-103과 같은 근거다.
- **FR-117**: 이름 선택과 성격 선택은 **서로를 제약하지 않아야 한다**(MUST NOT). 특정 이름이 특정 성격과만 짝지어지는 대응 관계를 두지 않는다 — 조합의 예측 불가능함이 원칙 0의 유희에 기여한다.
- **FR-118**: 카탈로그 항목의 **개수와 각 항목의 실제 내용은 이 스펙에서 확정하지 않는다**. 구현 단계에서 정하되 FR-111·FR-113·FR-114를 만족해야 한다.

### 성격의 불변 *(001 FR-004·FR-004a 재확인)*

- **FR-119**: 부여된 성격을 변경하는 수단은 **사용자에게도 앱 자신에게도 제공되지 않아야 한다**(MUST NOT). 누적된 일기·신호·시간의 경과는 성격에 관여하지 않는다(MUST NOT).
- **FR-119a**: 앱 갱신으로 성격 카탈로그의 **표시명이나 서술이 바뀌어도, 이미 부여된 퍼소나의 성격 식별자는 바뀌지 않아야 한다**(MUST). 퍼소나는 같은 성격을 계속 보유한다.
- **FR-119b**: 앱 갱신으로 **이미 부여된 식별자가 카탈로그에서 사라지는 상황을 만들지 않아야 한다**(MUST NOT). 카탈로그 항목은 추가할 수 있으나 제거하지 않는다. _근거:_ 제거를 허용하면 성격이 사라진 퍼소나가 생기고, FR-004a의 「성격은 변하지 않는다」를 앱 갱신이 뒤집게 된다.

### 이름 변경의 제약 *(질문 4)*

- **FR-120**: 사용자는 퍼소나의 이름을 **횟수 제한 없이 변경할 수 있어야 한다**(MUST).
- **FR-121**: 입력된 이름은 **앞뒤 공백을 제거한 뒤** 유효성을 판정해야 한다(MUST). 저장되는 것도 제거된 형태다.
- **FR-122**: 앞뒤 공백 제거 후 **빈 문자열이 되는 이름은 거부해야 한다**(MUST).
- **FR-123**: 이름의 길이는 **1자 이상 20자 이하**여야 하며, 이 범위를 벗어나면 거부해야 한다(MUST). 길이는 사용자가 보는 글자 수를 기준으로 세며, 한글 한 글자는 1자다.
- **FR-124**: 줄바꿈 문자와 제어 문자를 포함한 이름은 **거부해야 한다**(MUST). 이름 중간의 공백은 허용한다.
- **FR-125**: 이름의 **중복 검사는 하지 않는다**(MUST NOT). 퍼소나는 동시에 하나뿐이므로(001 FR-007) 비교 대상이 존재하지 않는다.
- **FR-126**: 이름 변경이 거부되면 시스템은 **거부되었다는 사실과 사유를 사용자에게 알려야 하며**(MUST), 기존 이름을 유지해야 한다(MUST). 입력을 임의로 잘라내거나 고쳐서 통과시키지 않는다(MUST NOT). _근거:_ 헌법 원칙 II의 정신 — 요청이 처리되지 않았는데 처리된 것처럼 보이게 하지 않는다.
- **FR-127**: 이름 변경은 **퍼소나의 동일성을 바꾸지 않아야 한다**(MUST). 변경 후에도 퍼소나는 하나이며, 이전에 생성된 일기가 다른 퍼소나에 귀속되거나 귀속이 끊기지 않는다(MUST NOT).
- **FR-128**: 이름을 후보 목록의 항목으로만 제한하지 않아야 한다(MUST NOT). 사용자는 목록 밖의 이름을 자유롭게 쓸 수 있다.

### 최초 부여의 시점 *(질문 5)*

- **FR-130**: 퍼소나 부여는 **앱의 최초 실행 시**, 사용자가 일기 생성이나 그 밖의 어떤 기능을 요청하기 전에 일어나야 한다(MUST). _근거:_ 생성 시점으로 미루면 "퍼소나 없이 앱을 쓰는 상태"가 존재하게 되고, 001 FR-014(추론은 퍼소나 정체성을 입력으로 받는다)가 그 상태에서 성립하지 않는다. 부여를 앞당기면 004는 퍼소나의 존재를 전제로 쓸 수 있다.
- **FR-131**: 부여는 **사용자의 입력을 요구하지 않아야 한다**(MUST NOT). 이름이나 성격을 고르게 하는 화면을 두지 않는다(MUST NOT).
- **FR-132**: 부여는 **한 번만 일어나야 한다**(MUST). 앱 재시작, 앱 갱신, 기기 교체는 재부여를 일으키지 않는다(MUST NOT).
- **FR-133**: 이름과 성격은 **함께 부여되어야 한다**(MUST). 한쪽만 정해진 퍼소나를 만들지 않는다(MUST NOT). 부여가 완결되지 않았으면 퍼소나가 없는 것으로 취급하고 다음 실행에서 처음부터 다시 부여한다.
- **FR-134**: 전체 삭제(001 FR-035) 후 앱을 다시 시작하면 **최초 실행과 동일한 절차로 부여가 일어나야 한다**(MUST). 삭제 전의 이름·성격을 물려받지 않는다(MUST NOT).
- **FR-135**: 부여는 **네트워크 없이 완결되어야 한다**(MUST). _근거:_ 헌법 원칙 I. 후보 목록과 카탈로그가 앱에 내장되므로(FR-101·FR-110) 외부 조회가 필요하지 않다.

### 004에 넘기는 것 *(경계면)*

- **FR-140**: 퍼소나가 추론 축에 넘기는 것은 **이름**과 **성격 카탈로그 항목**(식별자·표시명·서술) 두 가지가 전부여야 한다(MUST). 그 외의 값을 함께 넘기지 않는다(MUST NOT).
- **FR-141**: 성격을 넘길 때 **식별자만이 아니라 표시명과 서술을 함께 전달할 수 있어야 한다**(MUST). 004가 카탈로그를 따로 조회하지 않고 이 문서가 정한 것만으로 입력을 구성할 수 있어야 한다. _근거:_ ROADMAP의 002 완료 조건 — 004가 이 문서만 읽고 퍼소나가 무엇을 넘겨주는지 확정할 수 있어야 한다.
- **FR-142**: 넘기는 값에 **기기 정보, 관측 신호, 과거 일기, 이름 변경 이력이 포함되지 않아야 한다**(MUST NOT). 001 FR-001이 정한 고정 정체성은 이름과 성격뿐이다.

### Key Entities

- **이름 후보 목록 (Name Pool)** — 앱에 내장된 이름들의 집합. 최초 부여 시 무작위 선택의 모집단으로만 쓰이며, 부여 이후에는 어떤 제약도 만들지 않는다. 실행 중 변하지 않는다.

- **성격 카탈로그 (Trait Catalog)** — 앱에 내장된 성격 항목들의 집합. 둘 이상의 항목을 가진다. 각 항목은 식별자·표시명·서술로 구성된다. 항목은 추가될 수 있으나 제거되지 않는다.

- **성격 (Trait)** — 카탈로그의 한 항목. 퍼소나가 보유하는 것은 그 식별자이며, 004에 전달될 때는 표시명·서술이 함께 간다. 부여 후 어떤 경로로도 변하지 않는다.

- **이름 (Name)** — 퍼소나를 부르는 값. 최초에는 후보 목록에서 무작위로 오지만 이후 사용자가 목록과 무관하게 바꿀 수 있다. 유일성 제약이 없다.

**엔티티 간 관계**: 퍼소나 1 — 이름 1, 성격 1. 이름과 성격은 서로를 제약하지 않는다. 성격은 카탈로그 항목을 가리키고, 이름은 부여 이후 후보 목록과의 연결이 끊긴다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-101**: 퍼소나가 없는 상태에서 앱을 시작하면, **사용자에게 아무것도 묻지 않고** 이름 하나와 성격 하나를 가진 퍼소나가 존재하는 상태에 도달한다.
- **SC-102**: 부여된 성격을 100회 반복 관측했을 때, **모든 결과가 카탈로그 항목 안에 있고 둘 이상의 서로 다른 항목이 나타난다** — 한 항목만 반복해서 나오는 경우가 없다.
- **SC-103**: 부여된 이름을 반복 관측했을 때, **모든 결과가 후보 목록 안에 있다** — 목록 밖의 이름이 부여되는 경우가 없다.
- **SC-104**: 기기 식별자를 달리한 상태에서 퍼소나를 조회하면 **이름과 성격이 변경 전과 동일하며, 부여 절차가 실행된 흔적이 없다**.
- **SC-105**: 부여 절차의 입력을 전수 조사했을 때, **기기에서 읽은 값이 하나도 발견되지 않는다**.
- **SC-106**: 이름을 100회 변경한 뒤 과거에 생성된 모든 일기를 조회하면, **전부 같은 하나의 퍼소나에 귀속되어 있다** — 귀속이 끊기거나 갈라진 일기가 없다.
- **SC-107**: 유효하지 않은 이름(빈 값, 공백만, 21자 이상, 줄바꿈 포함)을 입력한 모든 경우에 **변경이 거부되고 기존 이름이 그대로 남는다** — 잘라내기나 자동 교정으로 통과되는 경우가 없다.
- **SC-108**: 앱 전체를 조사했을 때 **성격을 변경하는 경로가 하나도 발견되지 않는다** — 사용자 조작에 의한 것도, 일기 누적이나 시간 경과에 의한 것도 없다.
- **SC-109**: 성격 카탈로그의 표시명·서술을 바꾼 앱 갱신 후 기존 퍼소나를 조회하면, **성격 식별자가 갱신 전과 동일하다**.
- **SC-110**: 전체 삭제 후 앱을 재시작하면 **부여가 다시 일어나며, 삭제 전의 이름이 남아 있는 경우가 없다**.
- **SC-111**: 비행기 모드에서 앱을 최초 실행하면 **부여가 정상적으로 완결된다**.
- **SC-112**: 004 스펙 작성자가 이 문서만 읽고 **퍼소나가 추론 축에 넘기는 값의 구성을 확정할 수 있다** — 002의 다른 문서나 구현을 참조할 필요가 없다.

## Assumptions

- **후보 목록·카탈로그의 실제 내용** — 이름 문자열과 성격 항목의 문면은 구현 단계에서 채운다. 이 스펙이 정한 것은 그것들이 **내장되어 있고, 실행 중 변하지 않고, 무작위 선택의 모집단이 된다**는 성질뿐이다. 목록을 스펙에 박으면 문구를 다듬는 작업이 스펙 작업으로 위장된다.
- **무작위의 품질** — 통계적 균등성을 요구하지 않는다. 요구하는 것은 설치마다 갈린다는 성질(SC-102)뿐이며, 암호학적 난수 여부는 구현 판단이다.
- **이름 길이 20자** — 한국어 이름·별명이 들어가는 일반적 상한을 기준으로 정했다. 001에 근거가 없으므로 이 스펙의 결정이며, 변경 시 이 문서를 고친다.
- **표시명·서술의 언어** — 한국어를 가정한다. 다국어는 범위 밖이다.
- **사용자에게 성격을 알리는 시점** — 부여 시 알릴지, 조회 시에만 보일지는 006의 몫이다. 이 스펙은 **성격이 조회 가능하다**까지만 정한다.
- **단일 사용자·단일 퍼소나** — 001 FR-007과 001 Assumptions를 그대로 따른다. 한 기기 한 사용자, 동시에 하나의 퍼소나.
- **성격의 시간적 변화** — 001 FR-004b에 따라 범위 밖이다. 도입을 판단하려면 회상 슬롯과 마찬가지로 별도의 실측과 판단이 선행되어야 한다.
