# 작명·온보딩·쓰기·그만두기 빠른 반복 부작용 확인 — 설계

2026-10-10. 로드맵 「작명·온보딩·쓰기·그만두기를 빠르게 반복했을 때의 문제 확인과 부작용 개선」의 설계다.

## 목적과 성공 기준

첫 실행(작명 → 온보딩)을 지난 뒤 일기 쓰기와 그만두기를 빠르게 되풀이하면 무슨 일이 생기는지 **처음으로 관측**한다. 관측한 증상은 목록으로 남기고, 코드 결함은 고친다.

- 증상이 재현 방법(간격)·근거 로그와 함께 한 줄씩 목록으로 남는다.
- 코드 결함은 고쳐져 같은 반복에서 재현되지 않고, 못 고치는 것은 이유와 함께 문서에 남는다.
- dev 실기기에서 한 번 본다(원칙 V).

## 제약

- **추측으로 고치지 않는다.** 아래 의심 지점은 짐작이며 관측한 것이 아니다.
- **한 축(예: 잠금)을 깊게 파지 않는다**(AGENTS 작업 습관).
- **측정·계측 코드를 제품에 넣지 않는다**(원칙 IV). 재현 스크립트는 저장소 밖에 둔다.
- 타이밍 결함은 jest가 못 잡는다 — 관측이 먼저다.

## 의심 지점 (짐작)

- 쓰기 잠금(020, `locks/diary-generation.lock`)이 풀리지 않거나 stale(6분)로만 풀린다.
- `stop()`이 `interrupted`로 정상 resolve되어(AGENTS) 중단이 늦게 도착하면 저장·토스트·실패 기록이 어긋난다.
- 하단 바 잠금(`WRITING.barLockMs` 1.5초)과 쓰기/그만두기 연타가 어긋난다.
- 모델 중복 적재·메모리.
- 일기 폴더의 `.json.writing` 찌꺼기.

읽어 본 코드: `src/diary/pipeline.ts`의 잠금 취득·해제(`acquireLock`, 227~241행), `src/ui/DiaryHomeScreen.tsx`의 `cancelled`·`inFlight`·`barLockMs`.

## 접근

`adb shell input tap` + `sleep` 스크립트로 간격을 직접 제어하고 `logcat`·`run-as`로 상태를 찍는다. 좌표는 `uiautomator dump`로 먼저 읽는다.
기각: Maestro 반복(간격 제어가 거칠고 흐름당 약 35초 기기 정지), 앱 안 계측 코드(원칙 IV).

## 1. 조작

- 기기: SM-G986N(`R3CN60JVNCE`), dev 빌드. `pm clear`로 완전 초기화하고 작명 → 온보딩 → 모델 내려받기 → 첫 일기 저장까지 한 번 완주한다(모델·일기가 지워지는 것을 소유자가 확인했다). 완주 뒤의 반복은 플래그 파일만 되돌려 빠르게 한다.
- 홈의 「쓰기」·「그만두기」를 `input tap`으로 누른다. 간격: 0ms·300ms·1.5초 직후·1.6초·3초·10초.
- 하단 바 잠금 안의 연타와 잠금 직후의 탭을 따로 본다.
- 쓰기 직후 홈 버튼으로 내렸다 올리기, 설정 열었다 닫기, 같은 날 두 번 쓰기.

## 2. 관측 (매 반복 뒤 같은 항목)

- `adb logcat`: llama 적재·해제 횟수, `already-running`, 예외.
- `run-as`: `files/locks/diary-generation.lock`(남았는지·소유자), `files/diary/`(새 파일·`.json.writing`·같은 날 중복), `files/preferences/write-failures.json`(갈래·개수).
- 화면: 토스트 문구, 하단 바 상태(`uiautomator dump`).
- 메모리: `dumpsys meminfo`를 반복 전후 한 번씩.

## 3. 산출물

- `specs/NNN-*/quickstart.md` 끝에 부작용 목록(증상·재현 간격·근거 로그 한 줄씩).
- 관측된 코드 결함은 TDD로 고치고 위반 주입으로 방어를 확인한다. jest가 못 잡는 타이밍은 소스 계약 테스트로 잠그거나, e2e 반복 시나리오로 넣을지 소유자에게 묻는다.
- 계측 스크립트는 저장소에 넣지 않고 절차만 문서에 남긴다.
