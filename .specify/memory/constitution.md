# Alpharium Constitution

스마트폰의 일상 신호(위치, 걸음 수, 사진, 캘린더, Wi-Fi)를 재료로, **휴대폰이 자기
주인의 하루를 추측해 쓰는 1인칭 한국어 일기** 앱. 일기의 화자는 사용자가 아니라
휴대폰이다. 현재 저장소는 컨셉 검증 PoC 단계이다.

## Core Principles

### 0. 휴대폰 퍼소나 (NON-NEGOTIABLE)

**화자**(MUST) — 일기의 1인칭 화자는 휴대폰이다. 사용자가 아니다. 휴대폰이 관찰한
신호를 근거로 "주인은 이랬을 것이다"를 추측해 서술한다. 사용자를 화자로 삼는
출력은 이 앱의 산출물이 아니다(MUST NOT).

**목적**(MUST) — 이 앱이 겨냥하는 가치는 기록의 정확성이 아니라 **유희**다. 휴대폰의
추측이 실제와 어긋나는 것은 결함이 아니라 콘텐츠다. 따라서 일기의 사실 일치도를
품질 기준이나 수용 기준으로 삼지 않는다(MUST NOT). 평가 기준은 "그럴듯하게 엉뚱한가",
"휴대폰이 볼 수 있었던 것만으로 쓰였는가"이다.

**근거의 한계**(MUST) — 휴대폰은 자신이 관측한 신호 범위 밖의 사실을 아는 것처럼
쓰지 않는다. 관측되지 않은 것에 대한 서술은 추측임이 드러나는 형태여야 한다.

**퍼소나 지속성**(MUST) — 퍼소나는 기기가 아니라 주인에게 귀속된다. 기기를 교체해도
이름·성격 등 고정 정체성은 이어지며, 바뀌는 것은 환경뿐이다. 따라서 퍼소나 정체성은
기기 식별자에 종속시켜 저장하지 않는다(MUST NOT).

**회상 범위**(현재 비활성) — 과거 일기를 추론 입력으로 사용하는 기능은 계약상
자리만 두고 첫 구현에서는 비활성으로 둔다. _근거:_ 온디바이스 소형 모델에서 입력이
길어지면 오늘의 신호가 과거 문장에 묻히고, 검증되지 않은 추측 위에 추측이 누적된다.
활성화는 "오늘의 신호가 묻히지 않는가"를 실측으로 확인한 뒤에 판단한다.

_근거:_ 사람의 하루를 정확히 복원하는 것은 이 신호들만으로 불가능하고, 애초에 그것을
목표로 하지도 않는다. 화자를 휴대폰으로 두는 순간 추측의 빗나감이 실패가 아니라
재미가 되며, 이 전환이 앱 전체의 성립 조건이다.

### I. 온디바이스 우선 프라이버시

프로덕션 빌드는 AI 추론을 위한 네트워크 호출 없이 동작해야 한다(MUST) — 비행기
모드에서 일기 생성 성공이 수용 기준이다. 클라우드 어댑터는 프로덕션 번들에 포함되지
않는다(MUST NOT). 로그·크래시 리포트에 일기 본문이나 원시 신호를 남기지 않는다(MUST
NOT).

**개발 예외:** 온디바이스 이식 전까지 `.env.development`에서만 클라우드 추론을
허용한다. 단, 이 예외가 유의미한 테스트가 되려면(MUST):

1. 페이로드는 온디바이스와 동일한 `DeviceSignalPackage` 스키마여야 한다 — 클라우드
   전용 필드로 스펙을 분기시키지 않는다.
2. 사진 원본은 전송하지 않는다. Stage 1 비전 캡션 텍스트만 보낸다.
3. 클라우드 모드임을 UI에 표시한다.

_근거:_ 이 조건이 없으면 클라우드로 검증한 프롬프트·UX가 이식 시점에 무너진다.

### II. 진실한 기록 (NON-NEGOTIABLE)

이 원칙이 규율하는 대상은 **일기의 내용이 아니라 일기의 출처**다. 휴대폰이 신호를
근거로 지어낸 추측은 이 앱의 정상 산출물이며 원칙 0이 보장한다. 여기서 금지하는 것은
**추론이 실제로 일어나지 않았는데 일어난 것처럼 보이게 하는 일**이다.

AI 추론 실패는 사용자에게 명시적으로 알린다(MUST). 조용한 fallback은 금지한다(MUST
NOT). 추론에 실패한 날은 일기를 저장하지 않는다(MUST NOT) — 실패를 미리 준비된
문장으로 메워 기록에 남기는 것이 이 원칙의 핵심 위반이다.
`EXPO_PUBLIC_ENABLE_MOCK_FALLBACK=true`는 development에서만 허용하며, mock 결과물은
UI에 mock임을 라벨링한다(MUST).

_근거:_ 휴대폰의 빗나간 추측은 재미지만, 그날 휴대폰이 아무것도 추론하지 않았는데
남아 있는 문장은 기록 전체의 신뢰를 무너뜨린다. 사용자가 나중에 일기를 볼 때 "이건
그날 휴대폰이 실제로 생각한 것"이라는 전제가 성립해야 한다. 현재 PoC의
[aiService.ts](../../src/services/aiService.ts) catch 블록이 반환하는 고정 문구는 이
원칙에 따라 폐기 대상이다.

### III. 어댑터 경계

모든 추론 접근은 `AIEngine` 인터페이스를 통과한다(MUST). 화면 코드에서 `fetch`나
네이티브 추론 모듈을 직접 호출하지 않는다(MUST NOT). 프롬프트와 출력 파싱은 엔진
구현체(`src/services/`)의 책임이며, 엔진 교체는 어댑터 선택 지점 한 곳의 변경으로
끝나야 한다.

_근거:_ 이 경계가 무너지면 Cloud → OnDevice 이식이 앱 전면 재작성이 된다.

### IV. 계약 우선 테스트

다음은 구현 전 테스트를 먼저 작성한다(MUST): `AIEngine` 구현체(정상·실패·형식 불량
응답), 신호/일기 스키마 검증, 신호 정제 계약(원시 로그 → 추론 입력), 퍼소나 지속성
(기기 식별자가 바뀌어도 정체성이 유지되는가), 로컬 저장·조회·삭제, 권한 거부 분기.
순수 스타일링과 레이아웃은 면제한다. Maestro E2E는 주 경로 1개 이상을 유지한다(MUST).

일기 본문의 품질은 자동 검사 대상이 아니다 — 원칙 0에 따라 사실 일치도를 기준으로
삼지 않으므로 단정적 통과·실패 판정이 성립하지 않는다. 대신 형식 계약(필수 필드,
파싱 가능성, 화자 일관성)만 검사한다.

_근거:_ 조용히 깨져 사용자 기록을 잃게 만드는 지점만 선별 방어한다. 전면 TDD는 UI
반복 속도를 불필요하게 희생시킨다.

### V. 사용자 소유 데이터

일기는 기기 로컬에 저장하며 사용자 동의 없이 외부 동기화하지 않는다(MUST NOT).
사용자는 개별·전체 데이터를 즉시 완전히 삭제할 수 있어야 한다(MUST). 권한 요청은
사용 시점에 목적과 함께 하고, 거부는 크래시가 아닌 기능 축소로 처리한다(MUST).
스키마 변경 시 기존 일기를 파괴하지 않는 마이그레이션을 제공한다(MUST).

## 플랫폼 제약

- **Expo SDK 54 고정** (`~54.0.36`) — 대상 기기의 Expo Go가 54만 지원하므로, 54를
  벗어나면 APK 사이드로딩 없이 실행할 수 없다. SDK 상향은 헌법 개정 사안이다.
- **패키지 버전 추측 금지**(MUST) — `expo install`은 npm이 아닌 Expo API에서 버전을
  해석한다. 버전별 공식 문서 또는 context7(`/expo/expo`, `sdk-54`)로 확인하고
  `npx expo install --check`로 검증한다.
- **문서-현실 일치**(MUST) — 문서에 기재된 스택 버전은 실제 설치본과 일치해야 한다.

## 개발 워크플로

Spec-First 순서를 따른다: 퍼소나 정의 → 신호 수집·정제 규격 → AI 입출력 계약 →
어댑터 인터페이스 → 저장 규격 → UI 사양 → 검증 하네스.

**경계면 우선**(SHOULD) — 네 축(퍼소나·수집/정제·추론·저장) 중 하나의 내부를 깊게
파기 전에, 축 사이에 오가는 데이터의 형태를 먼저 확정한다. 한 축을 먼저 완성하면
그 축이 자신에게 편한 입출력을 상정하게 되고, 나머지 축과 어긋난 사실은 구현 단계에
가서야 드러난다.

병합 전 테스트·타입 검사·포맷이 통과해야 하며(CI가 강제), 원칙 I·II 위반 여부를
확인한다. 새 의존성이나 추상화 계층을 도입할 때는 그것이 해결하는 구체적 문제를
기술한다 — "나중에 필요할 것 같아서"는 사유가 되지 않는다.

### 커밋 컨벤션

**형식**(MUST) — Conventional Commits를 따른다: `type(scope): 제목`.
사용 타입은 `feat`, `fix`, `docs`, `style`, `refactor`, `test`, `chore`.

**언어**(MUST) — 제목과 본문은 한글로 작성한다. 고유명칭(라이브러리, 함수, 파일,
타입, 환경 변수 이름 등)은 영문 원문을 그대로 쓴다.

**본문**(MUST) — 제목만 있는 커밋을 만들지 않는다. 단, `docs`·`style`·`chore`는
제목만으로 충분하다.

**본문의 눈높이**(SHOULD) — 본문은 비개발 직군이 읽어도 이해할 수 있는 수준을
지향한다. "무엇을 바꿨나"보다 **"무엇이 달라지나, 왜 필요했나"**를 쓴다. 코드를 읽지
않은 사람이 변경의 의미를 파악할 수 있으면 충분하다.

_근거:_ 형식·언어·본문 유무는 도구로 검사할 수 있으나, 글의 눈높이는 검사할 수 없다.
따라서 전자는 규칙(MUST)으로, 후자는 지향점(SHOULD)으로 둔다. 지킬 수 없는 것을
MUST로 적으면 헌법 전체의 구속력이 약해진다.

## Governance

이 헌법은 다른 모든 관행과 문서에 우선하되, 저장소 소유자의 명시적 지시가 이 문서보다
우선한다. 런타임 개발 지침은 `AGENTS.md`를 따르며, AGENTS.md가 헌법과 모순되면
헌법에 맞춰 수정한다.

**개정:** 사유와 영향 범위를 기술하고, 버전을 증가시키고, 상단 Sync Impact Report를
갱신한다. **MAJOR** = 원칙 삭제·재정의, **MINOR** = 원칙/섹션 추가 또는 실질적 변경,
**PATCH** = 문구 명확화.

**준수:** 원칙 0, I, II를 위반하는 변경은 병합할 수 없다. 예외 없음.
