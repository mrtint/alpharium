# Feature Specification: Modernist 디자인 시스템 적용 2차 — 첫 만남 및 캐릭터 작명

**Feature Branch**: `044-welcome-naming-modernist`

**Created**: 2026-09-19

**Status**: Draft

**Input**: User description: "Modernist 디자인 시스템 적용 2차 — 첫 만남 및 캐릭터 작명. 권한 요청
완료 후 나타나는 첫 만남 화면(WelcomeScreen.tsx)을 Modernist 브랜드 타이포그래피와
오프화이트/레드 테마로 이관한다. WelcomeScreen.tsx의 3가지 상태(checking, welcome,
failed) 레이아웃을 Modernist로 새로 작성한다. 035의 작명 규칙(상한 10자, 빈 이름 시
기본값 폴백)과 040의 백그라운드 병렬 다운로드 트리거 계약을 그대로 준수한다."

## 배경 및 범위

043이 스플래시(`LogoScreen`)와 권한 요청 흐름(`OnboardingScreen`)을 Modernist로
이관했다. 이번 스펙은 그 바로 다음 화면인 `WelcomeScreen`(035가 만들고 040이
호출 시점을 조율한 첫 만남·작명 화면) 하나만 다룬다 — 043이 세운 "범위를 화면
하나로 좁힌다"는 교훈을 그대로 잇는다.

**범위 안**: `src/ui/WelcomeScreen.tsx`의 세 단계(`checking`/`welcome`/`failed`)
시각 레이아웃 재작성.

**범위 밖**:
- `WelcomeScreen`을 호출하는 조립 로직(`App.tsx`의 `resolveFirstRunStage`
  판정, `firstRunStage`가 `"naming"`/`"liveness"`가 되는 조건) — 040이 이미
  검증했고 이번 스펙은 무변경.
- `"waiting-for-download"` 단계의 전용 화면 — 045(로드맵 29번)가 다룬다.
- 035의 이름 검증 로직(`src/welcome/naming.ts`)·040의 병렬 다운로드 트리거
  로직(`src/firstrun/`) 자체 — 화면은 이 계층에 닿지 않는다(원칙 III, W14).
- 다중 페르소나 어미 변형(디자인 리뷰 보드 화면 `1u`/`1v`/`1w`의 로봇/고양이/
  강아지 예시) — 037 기준 로스터가 하나(금동이)뿐이라 이번 스펙에서 다루지
  않는다. 레이아웃·타이포그래피만 옮기고 어미 변형 로직은 만들지 않는다.
- `src/ui/theme/tokens.ts`에 새 색 토큰을 추가하는 것 — 043이 이미 이관한
  9개 역할(`COLORS.*`)만 재사용한다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 새로 깨어난 캐릭터가 Modernist 화면으로 인사한다 (Priority: P1)

권한 요청을 마친 사용자가 작명 화면에 도달하면, 043과 같은 오프화이트 배경
위에 굵은 타이포그래피로 된 인사말과 이름 입력창을 본다 — 이전의 기본 시스템
폰트·둥근 카드 스타일이 아니라 043이 정한 각진 레이아웃과 레드 액센트다.

**Why this priority**: 사용자가 캐릭터에게 처음으로 상호작용하는 화면이라
Modernist 시각 언어가 이어지는지 여부가 여기서 갈린다. 043 스플래시 다음
화면이 이전 스타일로 남아 있으면 디자인 이관이 중간에 끊긴 것처럼 보인다.

**Independent Test**: 온보딩·권한 결정을 마치고 작명 화면에 진입해 배경색·
텍스트 굵기·버튼 스타일이 043의 팔레트와 일치하는지 눈으로 확인하는 것만으로
독립적으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 권한 스텝을 모두 결정한 상태, **When** 작명 화면(`welcome`
   단계)에 진입한다, **Then** 오프화이트 배경 위에 굵은 제목·본문 텍스트와
   레드 액센트가 적용된 이름 확정 버튼이 보인다.
2. **Given** 작명 화면이 표시된 상태, **When** 화면을 관찰한다, **Then**
   캐릭터 이름 외에 모델 식별자·자산 키·내부 진행률 등 원칙 III·IV가 금지하는
   정보가 전혀 보이지 않는다(기존 계약 W13·W16 유지).

---

### User Story 2 - 이름을 짓거나 건너뛴다 (Priority: P1)

사용자는 이름 입력창에 원하는 이름을 쓰고 확정 버튼을 누르거나, 건너뛰기를
눌러 기본 이름을 그대로 쓴다. 입력 상한(12자)과 빈 이름 처리 등 기존 규칙은
시각 스타일 변경과 무관하게 그대로 동작한다.

**Why this priority**: 이 화면의 핵심 기능이며, 시각 개편이 그 위에 있는
로직(035)을 깨뜨리지 않는다는 것을 보여야 한다.

**Independent Test**: 이름을 입력해 확정하는 경로와, 입력 없이 건너뛰기를
누르는 경로 둘 다 눌러보며 기존과 같은 결과(이름 확정 또는 기본 이름 유지)가
나오는지 확인하는 것으로 독립적으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 작명 화면, **When** 사용자가 이름을 입력하고 확정 버튼을
   누른다, **Then** 그 이름이 캐릭터 이름으로 확정되고 다음 단계로 넘어간다.
2. **Given** 작명 화면, **When** 사용자가 아무것도 입력하지 않고 확정
   버튼을 누르려 한다, **Then** 버튼이 비활성 상태로 보여 누를 수 없다(기존
   FR-012 유지, 시각적으로도 비활성 스타일이 구분된다).
3. **Given** 작명 화면, **When** 사용자가 건너뛰기를 누른다, **Then** 이름을
   짓지 않고 기본 이름으로 다음 단계로 넘어간다.
4. **Given** 작명 화면, **When** 사용자가 12자를 초과해 입력하려 한다,
   **Then** 13번째 글자부터 더 이상 입력되지 않는다.

### User Story 3 - 확인 중이거나 실패했을 때도 같은 시각 언어를 본다 (Priority: P2)

작명을 마친 뒤 백그라운드 정상 동작 확인(liveness)이 진행되거나 실패하면,
사용자는 그 상태에도 Modernist 스타일로 통일된 화면(로딩 표시 또는 실패
안내와 재시도/건너뛰기 버튼)을 본다.

**Why this priority**: 작명 화면(P1)만큼 자주 보이지는 않지만, 실패 시
사용자가 막다른 길에 갇히지 않고 계속 진행할 수 있어야 하며 그 화면도 새
디자인 언어를 따라야 이관이 일관된다.

**Independent Test**: 확인이 진행 중인 상태와 실패로 확정된 상태 둘 다를
재현해 로딩 표시·실패 안내·재시도/건너뛰기 버튼이 Modernist 스타일로
보이는지 확인하는 것으로 독립적으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 작명을 마친 상태, **When** 정상 동작 확인이 진행 중이다,
   **Then** Modernist 배경 위에 장식적 로딩 표시와 안내 문구만 보이고
   숫자로 된 진행률은 보이지 않는다(기존 원칙 IV 유지).
2. **Given** 정상 동작 확인이 실패로 확정된 상태, **When** 화면을 본다,
   **Then** 오류 사유 없이 고정된 안내 문구와 [다시 시도]/[그냥 시작하기]
   버튼 둘 다가 보인다(기존 W11·W16 유지, 막다른 길 없음).

### Edge Cases

- 이름 입력 중 화면 회전이나 키보드가 화면 대부분을 가리는 좁은 기기에서도
  확정/건너뛰기 버튼에 닿을 수 있어야 한다(043이 겪은 "리뷰 보드 20개 화면을
  한 번에 옮기려다 실패"를 반복하지 않기 위해 스크롤 가능한 레이아웃을
  기본으로 삼는다).
- 캐릭터 이름 표시 문자열이 매우 짧거나(1자) 길 때(표시 이름 상한과 무관하게
  기존 캐릭터명 문자열 자체가 다국어일 가능성) 레이아웃이 깨지지 않는다.
- 시스템 폰트 크기 설정이 커진 사용자 환경에서도 텍스트가 잘리지 않고
  줄바꿈된다(043의 `word-break: keep-all` 스타일 계승).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 작명 화면(`welcome` 단계)을 오프화이트 배경, 레드
  액센트, 굵은 타이포그래피의 Modernist 시각 언어로 표시해야 한다(043이
  이관한 `COLORS.*` 토큰만 사용).
- **FR-002**: 시스템은 확인 중 화면(`checking` 단계)과 실패 화면(`failed`
  단계)을 043 `LogoScreen`과 같은 중앙 정렬 미니멀 레이아웃(카드·테두리 없이
  화면 중앙에 로딩 인디케이터 또는 안내 문구와 버튼을 배치)으로 표시해야
  하며, 좌측 정렬 카드형인 작명 화면(`welcome` 단계)과 시각적으로 구분되어야
  한다.
- **FR-003**: 시스템은 기존 화면 계약(`WelcomeScreenProps` — `phase`,
  `characterName`, `onSubmitName`, `onSkip`, `onRetry`)을 변경하지 않아야
  한다(MUST NOT) — 이 스펙은 시각 레이어만 재작성한다.
- **FR-004**: 시스템은 이름 입력 상한(12자)을 기존 값 그대로 유지해야 한다
  (MUST NOT 변경) — 035 계약(`src/welcome/naming.ts`의 `NAME_MAX_LENGTH`)과
  화면 상수가 이미 일치한다(아래 Assumptions 참고).
- **FR-005**: 시스템은 화면에 캐릭터 이름 외의 모델 식별자·자산 키·경과
  시간·진행률 수치를 노출하지 않아야 한다(MUST NOT, 원칙 III·IV, 기존
  W13·W16 유지).
- **FR-006**: 시스템은 실패 화면에서 오류 사유를 표시하지 않고, [다시
  시도]와 [그냥 시작하기] 두 버튼을 항상 함께 제공해야 한다(기존 W11·W16
  유지).
- **FR-007**: 시스템은 확인 중 화면에서 진행률·경과 시간을 계산하지 않는
  장식적 로딩 표시만 사용해야 한다(MUST NOT 수치화, 043의 R4와 같은 원칙).
- **FR-008**: 시스템은 `src/welcome/`을 직접 import하지 않아야 한다(MUST
  NOT, 기존 W14 유지) — 이름 검증은 조립부가 하고 화면은 `maxLength` 같은
  UI 속성만 갖는다.
- **FR-009**: 시스템은 기존 Maestro 회귀 흐름(`.maestro/welcome-naming.yml`)이
  같은 시나리오(이름 입력→확정, 건너뛰기, 실패→재시도)를 통과하도록 화면
  구조(`testID`)의 의미를 유지해야 한다 — `testID` 문자열 값 자체는 이번
  스펙에서 바뀔 수 있으나, 그 경우 Maestro 흐름도 함께 갱신한다. (044
  계획 단계에서 "바꾸지 않는다"로 확정했다 — research.md R5.)

### Key Entities

- **작명 화면 단계(`WelcomePhase`)**: `"checking"` | `"welcome"` | `"failed"`
  세 값 중 하나. 기존 타입 그대로, 이번 스펙에서 값이 늘거나 줄지 않는다.

## Success Criteria *(mandatory)*

  **실기기 검증 결과(2026-09-19)**: `npm test`는 154개 스위트 전부
  통과했다. `welcome-naming.yml`은 `author-rename-input-0` 단계에서

  경로를 각각 1회 이상 눈으로 확인해 막다른 길이 없음을 검증한다(원칙 V).

## Clarifications

### Session 2026-09-19

- Q: 확인 중(checking)과 실패(failed) 화면의 레이아웃 스타일을 어느 쪽에
  맞출까요? → A: 중앙 정렬 미니멀 — 043 `LogoScreen`과 같은 여백 중심
  레이아웃(로딩 인디케이터/안내 문구가 화면 중앙에 홀로 배치, 카드나 테두리
  없음). 작명 화면(좌측 정렬 카드형)과는 시각적으로 구분되어 "지금은 사용자
  입력이 아니라 시스템 상태"임이 직관적으로 전달된다.

## Assumptions

- **이름 입력 상한은 12자다.** 사용자 설명은 "035의 작명 규칙(상한 10자)"라고
  요약했으나, 실측 결과 `src/welcome/naming.ts`의 `NAME_MAX_LENGTH`(035의 실제
  검증 로직)와 현재 `WelcomeScreen.tsx`의 `NAME_INPUT_MAX_LENGTH` 둘 다 12이고
  디자인 리뷰 보드 문구(`nameHint` "12자까지")도 12를 명시한다 — **셋이 이미
  일치하므로 이번 스펙은 값을 바꾸지 않는다.** 화면이 `src/welcome/`을 import할
  수 없으므로(FR-008) 상수는 계속 화면 파일에 복제된 채로 남고, 기존 계약
  테스트가 두 값의 일치를 계속 검사한다.
- 디자인 리뷰 보드(`Alpharium Mobile Screens (standalone).html`) 화면 ID
  `1a`의 레이아웃(아바타 자리·제목·본문·구분선·이름 입력줄·하단 버튼 2개
  가로 배치)을 기본 참조로 삼되, 아바타 이미지 자체(로봇 이모지 등)는 037
  기준 로스터가 하나뿐이므로 만들지 않는다 — 캐릭터별 아바타가 필요해지면
  후속 스펙에서 다룬다.
- 확인 중(`checking`)·실패(`failed`) 화면은 리뷰 보드에 전용 마크업이 없으므로
