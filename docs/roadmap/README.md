# 로드맵

포켓로그(옛 이름 알파리움)의 개선 과제 로드맵이다. 2026-09-26에 다시 짰다 — 완료된 과제는 아래 이력표로
줄였고, 남아 있던 계획은 전부 걷어냈다. **앞으로의 과제는 UI/UX에 집중한다.**

> [!NOTE]
> **우선순위 없음**: 과제에는 고정된 우선순위가 없다. 어느 과제를 언제 열지는 저장소
> 소유자가 정한다.
>
> **진행 전 항목에는 스펙킷 번호·차수·순서를 적지 않는다**: 스펙킷 번호(`specs/NNN-*`)는
> 스펙을 실제로 여는 순간에만 매겨진다. 진행 전 항목에 「NNN 예정」 같은 번호도, 「N차」
> 같은 차수도, 다른 항목 뒤에 와야 한다는 순서도 적지 않는다. 스펙이 열린 뒤에만 그 번호를
> 기록한다.

## 진행 예정 과제

### iOS 설정·개발자·진단 화면 재검증과 고장 수정

**배경**: 066은 iOS에서 첫 실행 → 일기 저장 경로만 봤고 설정·개발자·진단 화면은 「미확인」으로
남겼다. TestFlight 빌드 2(1.0.0 (2), iPhone 17 Pro Max, iOS 27.0.1)에서 2026-10-08 오후 5시 16~17분에
테스터 피드백 셋이 들어왔다 — 설정의 **사진·위치·알림 권한 행을 누르면 앱이 튕긴다.**

**이미 한 것 (기기에서는 미확인)**: 같은 날 `a994379`가 원인으로 본 `await import("react-native")`
(iOS에서 `PushNotificationIOS` getter가 던져 try/catch를 지나침)를 `os-settings-port.ts`·
`battery-exception-port.ts`에서 호출 시점 `require`로 바꿨고 `ios.buildNumber`를 3으로 올렸다.
**빌드 3을 실제 iPhone에 올려 세 행이 튕기지 않는 것을 보기 전까지는 고쳐진 것이 아니다**(원칙 V) —
피드백 셋은 이 과제의 첫 확인 항목이다.

**할 일**:

1. **빌드 3(이상)을 TestFlight로 올려 피드백 셋을 다시 본다** — 사진·위치·알림 행이 iOS 설정 앱의
   포켓로그 화면을 여는가, 돌아오면 꼬리표가 다시 읽히는가(`AppState → active`).
2. **설정 화면 전체를 iOS에서 한 줄씩 누른다** — 이름 바꾸기, 자동으로 쓰기 토글·매일 쓰는 시각·장소
   이름 대화상자, 권한 행 넷, 이 휴대폰(모듈 용량·일기 모두 지우기), 버전 7번 탭.
3. **개발자 메뉴·진단·상태 흉내를 iOS에서 누른다**(개발 빌드 또는 시뮬레이터 — 배포 빌드는 7번 탭 뒤) —
   모듈 상태·모듈 다시 받기·온보딩부터 다시·끄기, 진단 일곱 묶음·한 번 써 보기·자동 쓰기 지금 실행,
   상태 흉내 날짜 대화상자.
4. **안드로이드 전제를 그대로 탄 자리를 판정한다** — 지금 보이는 후보(전부 미확인):
   - **배터리 행**: iOS에는 배터리 최적화 예외가 없다. `expo-intent-launcher`가 iOS에서 던지고 앱 설정으로
     떨어지는데, 그 행이 iOS에 있어야 하는가부터 정한다(`PERMISSION_REQUIREMENTS`·온보딩 배터리 단계도 같은 질문).
   - **자동 쓰기 토글·매일 쓰는 시각**: iOS BGTask는 시각을 약속하지 않는다 — 「매일 22시」 문구가 iOS에서 사실인가.
   - **모듈 다시 받기의 셀룰러 문구**(`expo-network`), 뒤로 가기(`BackHandler`는 iOS에 없다 — 겹 닫기 수단이 있는가),
     「사진의 위치 정보」 꼬리표(`photoLocationProbe`가 iOS에서 무엇을 주는가).
   - **남은 동적 `await import(...)`**: `expo-*` 패키지(`expo-file-system`·`expo-media-library`·`expo-notifications`·
     `expo-location`·`expo-background-task`)는 066 원인(`react-native` index의 getter 훑기)과 모양이 다르지만
     iOS에서 각 경로가 한 번은 실제로 돌았는지 확인한다.
5. 튕기거나 동작하지 않는 것을 고치고, 고칠 수 없는 것(플랫폼에 기능이 없음)은 iOS에서 행을 감출지·문구를 바꿀지를
   저장소 소유자에게 묻는다 — 코드가 정하지 않는다.

**완료 조건**: 실제 iPhone(TestFlight)에서 설정의 모든 행을 눌러 튕김 0건, 개발자·진단 화면은 iOS 개발 빌드(또는
시뮬레이터 + 한계 명기)에서 모든 버튼이 의도대로 동작하거나 의도적으로 감춰져 있다. 시뮬레이터에서만 본 것은 「실제
iPhone 미확인」으로 적는다. 안드로이드는 바뀐 자리만 dev 실기기로 다시 본다.

**위험**: 이 과제는 「iOS 대응」 전반으로 번지기 쉽다(백그라운드 자동 쓰기 실측, 메모리 한도, GPU 캡션 되돌리기).
그것들은 이 과제의 범위가 아니다 — 설정·개발자·진단 화면에서 누를 수 있는 것만 본다.



### 홈의 가로 스와이프를 세로로 — 사진 캐러셀·주간 스트립, 그리고 사진 확대

**배경**: 홈의 두 가로 스와이프 — 쓴 날 지면의 사진 캐러셀(`PhotoCarousel.tsx`, 051)과 위쪽 주간 스트립
(`DayPicker.tsx`, 049) — 을 세게 넘기면 아이폰·안드로이드 모두에서 OS 뒤로 가기가 걸리는 일이 잦다(저장소 소유자
관측). 그리고 사진을 눌러도 아무 반응이 없다 — 025의 풀스크린 갤러리는 051이 캐러셀로 대체하면서 사라졌다.

**할 일**:

1. **사진 캐러셀을 세로 넘김으로** 바꾼다.
2. **주간 스트립을 세로 넘김으로** 바꾼다(위·아래가 각각 지난 주·다음 주 중 어느 쪽인지 정한다).
3. **사진을 누르면 확대해 보여 준다** — 풀스크린 겹, 닫기 수단(뒤로 가기·닫기 버튼·아래로 끌기 중 무엇),
   그 안에서 다음 사진으로 넘기는 방향.

**먼저 풀어야 할 질문 (설계 전에 소유자 결정)**:

- **세로 넘김은 지면 스크롤과 같은 축이다.** 쓴 날의 지면은 세로로 스크롤되고(051), 그 스크롤이 052 접힘·펼침과 하단 바
  올라옴(`reachedEnd`)을 움직인다. 지면 안의 세로 캐러셀은 「사진을 넘기려 했는데 본문이 내려감」 또는 「본문을 읽으려
  했는데 사진이 넘어감」 중 하나를 반드시 만든다 — 051이 가로 캐러셀에 `.failOffsetY([-10, 10])`을 단 이유가 정확히 이
  충돌이었다. 052는 지면 프레임 경계가 손가락 아래에서 움직이면 접힘이 되풀이되는 결함도 겪었다. 판정 방식(예: 사진 영역
  안에서는 캐러셀이 우선하고 마지막 장에서 지면으로 넘김, 또는 캐러셀은 넘기지 않고 확대 화면에서만 넘김)을 먼저 정한다.
- **주간 스트립의 세로 넘김은 052 접힘과 겹친다.** 지면을 8px 내리면 스트립이 접히는데, 스트립 위에서 시작한 세로 끌기가
  주를 넘기는지 지면을 스크롤하는지 손가락 시작 위치로만 갈라야 한다. 스트립이 접힌(높이가 줄어든) 상태에서는 끌 자리가 거의 없다.
- **뒤로 가기가 정말 걸리는 자리를 먼저 잰다.** 안드로이드 제스처 내비게이션의 뒤로 가기는 화면 **양쪽 가장자리**에서 안으로
  끄는 동작이다 — 캐러셀·스트립 한가운데서 시작한 넘김은 걸리지 않아야 한다. 아이폰은 루트 화면에 뒤로 가기가 없고 가장자리
  넘김은 설정 겹 위에서만 의미가 있다. 「과한 스와이프」가 가장자리에서 시작했는지, 아이폰에서 무엇이 실제로 일어났는지
  (앱 전환 막대? 설정 겹 닫힘?) `screenrecord`·화면 녹화로 한 번 확인한다. 가장자리 시작이 원인이라면 축을 바꾸지 않고
  좌우 여백(가장자리 제스처 영역 밖에서만 팬을 세움)으로 끝날 수도 있다 — 그 경우가 더 싸다.
- **확대 화면은 핀치 줌까지 하는가.** 「누르면 크게」만이면 코어 `Modal` + `Image`로 충분하다. 핀치·이동까지면
  gesture-handler로 직접 짜거나 새 의존성이 필요하다(YAGNI 기준으로 첫 조각은 핀치 없이 시작할 것을 권한다).

**완료 조건**: 안드로이드 dev 실기기와 아이폰(TestFlight 또는 시뮬레이터 + 한계 명기)에서 — 캐러셀·스트립을 세게 넘겨도
뒤로 가기·앱 종료가 0건, 사진을 넘기다 본문이 스크롤되거나 그 반대가 되는 경우를 녹화 프레임으로 확인, 사진을 누르면
확대 화면이 뜨고 닫힌다. 손맛은 jest가 못 잡는다(팬 배선만 검증된다 — 「테스트 작성의 함정」) — 문턱 판정은 순수 함수로 잠근다.

### 주요 기능별 e2e 테스트 — 화면 흐름 층과 실제 생성 스모크 층

**배경**: `.maestro/`에 흐름이 23개 있지만 기능 단위로 무엇을 지키는지 대응표가 없고, 설정·개발자·진단 화면은
거의 비어 있으며, iOS에서 돈 흐름은 사실상 없다(TestFlight 빌드 2의 권한 행 튕김은 화면 흐름 e2e가 잡았어야 했다).
반면 이 앱의 e2e는 일반 앱과 조건이 다르다 — 일기 본문은 비결정적이라 내용을 단언할 수 없고(채점 코드는 원칙 IV로
금지), 모델 2GB·생성 50~240초·`pm clear`가 모델까지 지우므로 「매번 깨끗한 상태」가 비싸며, arm64 전용 빌드라 CI
에뮬레이터에서 실제 추론을 돌리기 어렵다. 가짜 추론으로 초록을 만들면 042의 교훈(「검증 경로가 제품과 다르면 검증이
아니다」)에 걸린다.

**도구는 Maestro를 유지한다** — Detox·Appium으로 옮기거나 클라우드 기기 팜을 들이지 않는다(흐름 23개를 옮기는 비용에
비해 얻는 것이 적고, 기기 팜에서도 2GB 모델 문제는 그대로다).

**할 일**:

1. **기능 → 흐름 대응표**를 만든다 — 주요 기능(첫 실행·쓰기·쓴 날 읽기·날 고르기·달력·설정 각 행·개발자·진단·
   상태 흉내·자동 쓰기·지우기 등)마다 어느 흐름이 무엇을 보는지, 빈 칸·중복·`FLOWS` 밖 흐름을 드러낸다.
   대응표의 자리(문서 또는 `run-device-tests.mjs` 주석)도 정한다.
2. **층 1 — 화면 흐름 e2e (빠름, 자주)**: 생성 없이 끝나는 흐름만(설정·개발자·진단·달력·스트립·권한 행·대화상자).
   - **기기 상태 고정**: 모델이 받아진 상태를 기준으로 삼고 `pm clear` 대신 플래그 파일(`preferences/*.json`)만
     되돌리는 초기화 경로를 만든다(iOS는 `simctl get_app_container`의 `Documents/`).
   - **같은 YAML을 안드로이드 실기기와 iOS 시뮬레이터에서** 돌린다 — 플랫폼 차이(권한 창 문구, 뒤로 가기 없음)는
     흐름 안의 분기 또는 플랫폼별 하위 흐름으로 가른다. 실행기(`run-device-tests.mjs`)에 iOS 갈래를 더한다.
3. **층 2 — 실제 생성 스모크 (느림, 릴리스 전)**: 실제 모델로 기능당 하나 — 「쓰기 → 저장 → 쓴 날 홈」, 첫 실행 자동
   첫 일기, 앱 열면 쓰는 중(057), 진단 한 번 써 보기. 단언은 상태 전이까지이고 본문은 사람이 읽는다. 실기기에서
   사람이 돌리며, 릴리스(Play 내부 테스트·TestFlight) 전 체크리스트에 넣는다.
4. **CI에 넣을지는 층 1만, 그리고 실측 뒤에 정한다** — macOS 러너의 iOS 시뮬레이터에서 층 1이 몇 분에 도는지,
   모델 없이 닿는 화면이 어디까지인지(첫 실행 게이트가 막는다) 먼저 잰다. 안 되면 로컬 실행으로 둔다.

**완료 조건**: 대응표의 모든 주요 기능에 층 1 또는 층 2 흐름이 있거나 「사람이 본다」가 이유와 함께 적혀 있다. 층 1은
안드로이드 dev 실기기와 iOS 시뮬레이터에서 각각 한 번 전부 통과한다. 층 2는 실기기에서 한 번 완주한다. 새 흐름은
`FLOWS`에 등록한다(등록 안 된 흐름은 초록불인데 아무것도 검증하지 않는다).

**위험**: 흐름을 늘리는 것 자체가 목표가 되기 쉽다 — Maestro 흐름은 행 높이·문구·좌표에 깨지기 쉬워(「Maestro」 절)
유지 비용이 흐름 수에 비례한다. 대응표에서 「이미 계약 테스트가 지키는 것」은 e2e로 다시 만들지 않는다.
