# 받기 전에 먼저 검증한다 — 모델 끝 무렵 사고 복구

로드맵 「모델 내려받기의 끝 무렵에 앱이 죽으면 처음부터 다시 받는다」의 설계. 경량 트랙(새 데이터 모델 없음, 코드 변경 5개 파일 이하, 수용 기준 3개).

## 목적

iPhone 13 mini에서 언어 모델을 다 받은 직후 앱이 메모리 한도로 죽었고, 다시 뜬 앱이 같은 1.5GB를 처음부터 받았다(2026-11-01). 이미 온전히 받은 파일을 다시 받지 않게 하고, 검증 자체가 앱을 죽이지 않게 한다.

## 사실

- **검증 메모리(후보)**: expo-file-system 57.0.7의 iOS MD5 루프에 `autoreleasepool`이 없다. 같은 루프를 맥(macOS 27.0.1)에서 1.5GB 파일로 돌리면 footprint가 약 1.3GB까지 늘고, 풀을 넣으면 2MB다. 13 mini의 종료 기록(약 2.4GB)과 시점·규모가 맞지만 iOS에서 잰 값이 아니고, 같은 기기의 두 번째 검증이 통과한 까닭은 설명하지 못한다.
- **언어 모델**: `prepare`는 파일 상태를 보지 않고 받는다. 이미 준비된 파일도 다시 받는다(사진 모델만 없을 때 「모듈 다시 받기」).
- **사진 모델**: `fetchOne`은 크기만 맞으면 검증 없이 성공을 돌려준다. 검증 기록 전에 죽으면 다시 받지도, 준비 상태가 되지도 못한다(소스 읽기, 재현하지 않음).
- **중간이 빈 파일**: 구간은 끝나는 차례대로 제 오프셋에 쓰이므로, 다 합치기 전에도 파일 크기가 기준과 같을 수 있다. 크기만으로 온전하다고 볼 수 없다.
- **이어받기**: `src/`에 `Acquisition.pause()`를 부르는 곳이 없어 이어받기 기록이 실제로 생기지 않는다. 받는 도중 끊기거나 죽으면 처음부터다.

## 결정

| 결정 | 근거 | 뒤집으면 바뀌는 것 |
|---|---|---|
| 받는 도중의 이어받기는 이번에 하지 않고 별도 과제로 올린다(소유자) | 구간 4개가 같은 크기로 동시에 받아져 끝난 구간만 기록해도 효과가 작고, 받던 구간의 데이터는 죽으면 사라진다. 잘게 나누는 방식은 전송 구조와 저장 형식이 바뀐다 | 전체 트랙으로 승격 |
| 검증 메모리는 `patch-package`로 고친다 | 패치 선례가 있고 변경이 가장 작다. 패치가 iOS 빌드에 닿지 않으면 로컬 네이티브 모듈로 바꾼다 | 로컬 모듈 하나가 늘어난다 |
| 검증 실패 파일은 지우고 공간을 본 뒤 처음부터 받는다 | 깨진 파일을 남기면 공간을 먹고, 이어받기 기록도 없다 | 실패로 끝내면 사용자가 눌러야 다시 받는다 |
| 이어받기 기록이 있으면 먼저 검증하지 않고 이어받는다 | 기록은 아직 다 받지 않았다는 사실이고 그 파일은 크기가 맞아도 중간이 비어 있다 | 낭비되는 해시 계산이 생긴다 |
| 검증 중 진행 표시는 움직이지 않는다 | 해시는 진행을 보고하지 않아 숫자를 지어내야 한다(원칙 V) | 잠깐 멈춰 보이는 대신 거짓 진행 |

## 동작

받기 전에 언어 모델과 사진 모델이 같은 순서로 판단한다.

1. 파일·검증 기록이 이미 준비 상태(`readinessOf` = `ready`)면 해시 계산 없이 끝낸다.
2. 크기가 기준과 같으면 해시로 검증한다. 통과하면 기록하고 끝낸다 — 공간 검사도 다운로드도 없다.
3. 검증에 실패하면 지우고, 공간을 보고, 처음부터 받는다.
4. 그 밖에는 지금과 같다.

## 수용 기준

1. 받기가 끝난 뒤 검증 기록 전에 죽어도, 다시 열면 받지 않고 검증만 해서 준비 상태가 된다. 사진 모델도 같다.
2. 크기는 맞지만 내용이 깨진 파일은 다시 받고, 통과시키지 않는다.
3. MD5 계산 중 메모리가 파일 크기만큼 늘지 않는다. iOS 시뮬레이터에서 먼저 재고, 13 mini에서는 기기가 비면 새로 설치해 첫 일기까지 강제 종료 없이 가는지 본다. 그 전까지 완료로 닫지 않는다.
