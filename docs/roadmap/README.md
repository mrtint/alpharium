# 로드맵

포켓로그(옛 이름 알파리움)의 개선 과제 로드맵이다. 2026-09-26에 다시 짰다 — 완료된 과제는 아래 이력표로
줄였고, 남아 있던 계획은 전부 걷어냈다. 홈·설정의 UI/UX 개편(067), 안드로이드 e2e 기반(069~073), 첫 실행 모바일 데이터 동의(074), 회사 맥 없는 iOS 빌드·업로드(075), 개발 기계 없는 안드로이드 release 빌드·서명·Play 업로드(076)까지 끝났다 — **앞으로의 과제는 iOS 검증과 테스트·빌드 기반에 집중한다**(2026-10-10 방향을 옮겼다).

> [!NOTE]
> **우선순위 없음**: 과제에는 고정된 우선순위가 없다. 어느 과제를 언제 열지는 저장소
> 소유자가 정한다.
>
> **진행 전 항목에는 스펙킷 번호·차수·순서를 적지 않는다**: 스펙킷 번호(`specs/NNN-*`)는
> 스펙을 실제로 여는 순간에만 매겨진다. 진행 전 항목에 「NNN 예정」 같은 번호도, 「N차」
> 같은 차수도, 다른 항목 뒤에 와야 한다는 순서도 적지 않는다. 스펙이 열린 뒤에만 그 번호를
> 기록한다.

## 진행 예정 과제

### 주요 기능별 e2e 테스트 — 화면 흐름 층과 실제 생성 스모크 층

**진행**: 첫 조각(할 일 1번 대응표 + 2번의 안드로이드 쪽)은 스펙 069로 끝났다 — 대응표는 `docs/e2e/feature-flow-map.md`, 층 1은 `npm run test:layer1`(전용 테스트 기기, 8개 흐름 7분 37초 통과). 표본(30일치 MediaStore 사진)은 스펙 070으로 끝났다 — `docs/e2e/sample-table.md`, 층 1이 표본 위에서 9개 흐름 11분 47초 통과. **스펙 073으로 낡은 흐름 셋 정리와 3번 층 2(안드로이드)가 끝났다** — 낡은 셋은 문구 변경이라 고쳐 층 1로 올렸고(층 1 12개 흐름 13분 26초 통과), 층 2는 `npm run test:layer2`(흐름 넷, 실제 모델, 전체 약 10분)와 `docs/e2e/layer2-release-checklist.md`다. **남은 것**: 2번의 iOS 시뮬레이터 갈래(표본 심기는 `simctl addmedia` — 070 표는 플랫폼 중립), 4번 CI 판단, 층 2의 iOS 갈래.

**배경**: `.maestro/`에 안드로이드 흐름이 23개 있지만 기능 단위로 무엇을 지키는지 대응표가 없고, 설정·개발자·진단 화면은
거의 비어 있으며, iOS 흐름은 068이 `.maestro/ios/`에 둔 시뮬레이터 훑기 셋(설정, 개발자·진단, 첫 실행에서 홈까지)과 보조 하나뿐이고 `FLOWS`에 등록돼 있지 않다
(TestFlight 빌드 2의 권한 행 튕김은 화면 흐름 e2e가 잡았어야 했다).
반면 이 앱의 e2e는 일반 앱과 조건이 다르다 — 일기 본문은 비결정적이라 내용을 단언할 수 없고(채점 코드는 원칙 IV로
금지), 모델 2GB·생성 50~240초·`pm clear`가 모델까지 지우므로 「매번 깨끗한 상태」가 비싸며, arm64 전용 빌드라 CI
에뮬레이터에서 실제 추론을 돌리기 어렵다. 가짜 추론으로 초록을 만들면 042의 교훈(「검증 경로가 제품과 다르면 검증이
아니다」)에 걸린다.

**도구는 Maestro를 유지한다** — Detox·Appium으로 옮기거나 클라우드 기기 팜을 들이지 않는다(흐름 23개를 옮기는 비용에
비해 얻는 것이 적고, 기기 팜에서도 2GB 모델 문제는 그대로다).

**할 일**:

1. **기능 → 흐름 대응표**를 만든다 — 주요 기능(첫 실행·쓰기·쓴 날 읽기·날 고르기·달력·설정 각 행·개발자·진단·
   상태 흉내·자동 쓰기·지우기 등)마다 어느 흐름이 무엇을 보는지, 빈 칸·중복·`FLOWS` 밖 흐름을 드러낸다.
   대응표의 자리(문서 또는 `run-device-tests.mjs` 주석)도 정한다.
2. **층 1 — 화면 흐름 e2e (빠름, 자주)**: 생성 없이 끝나는 흐름만(설정·개발자·진단·달력·스트립·권한 행·대화상자).
   - **기기 상태 고정**: 모델이 받아진 상태를 기준으로 삼고 `pm clear` 대신 플래그 파일(`preferences/*.json`)만
     되돌리는 초기화 경로를 만든다(iOS는 `simctl get_app_container`의 `Documents/`).
   - **같은 YAML을 안드로이드 실기기와 iOS 시뮬레이터에서** 돌린다 — 플랫폼 차이(권한 창 문구, 뒤로 가기 없음)는
     흐름 안의 분기 또는 플랫폼별 하위 흐름으로 가른다. 실행기(`run-device-tests.mjs`)에 iOS 갈래를 더한다.
     출발점은 068의 `.maestro/ios/` 훑기 흐름과 AGENTS 068이 적은 함정(`launchApp`의 `stopApp: false`, 개발 클라이언트 재진입 확인 창)이다.
3. **층 2 — 실제 생성 스모크 (느림, 릴리스 전)** — *안드로이드는 스펙 073으로 끝났다(`npm run test:layer2`, `docs/e2e/layer2-release-checklist.md`); iOS 갈래만 남음*: 실제 모델로 기능당 하나 — 「쓰기 → 저장 → 쓴 날 홈」, 첫 실행 자동
   첫 일기, 앱 열면 쓰는 중(057), 진단 한 번 써 보기. 단언은 상태 전이까지이고 본문은 사람이 읽는다. 실기기에서
   사람이 돌리며, 릴리스(Play 내부 테스트·TestFlight) 전 체크리스트에 넣는다.
4. **CI에 넣을지는 층 1만, 그리고 실측 뒤에 정한다** — macOS 러너의 iOS 시뮬레이터에서 층 1이 몇 분에 도는지,
   모델 없이 닿는 화면이 어디까지인지(첫 실행 게이트가 막는다) 먼저 잰다. 안 되면 로컬 실행으로 둔다.

**완료 조건**: 대응표의 모든 주요 기능에 층 1 또는 층 2 흐름이 있거나 「사람이 본다」가 이유와 함께 적혀 있다. 층 1은
안드로이드 dev 실기기와 iOS 시뮬레이터에서 각각 한 번 전부 통과한다. 층 2는 실기기에서 한 번 완주한다. 새 흐름은
`FLOWS`에 등록한다(등록 안 된 흐름은 초록불인데 아무것도 검증하지 않는다).

**위험**: 흐름을 늘리는 것 자체가 목표가 되기 쉽다 — Maestro 흐름은 행 높이·문구·좌표에 깨지기 쉬워(「Maestro」 절)
유지 비용이 흐름 수에 비례한다. 대응표에서 「이미 계약 테스트가 지키는 것」은 e2e로 다시 만들지 않는다.

### 백그라운드 자동 쓰기가 완주하지 못한다 — 안드로이드·iOS

**진행**: 안드로이드의 원인 가르기와 첫 대응은 스펙 079로 끝났다(2026-10-13) — `llama.rn` 기본 4스레드가 백그라운드 cpuset의 작은 코어 3개를 나눠 쓴 것이 주원인이었고, 백그라운드 조립을 스레드 2로 열자 SM-S901N에서 화면을 끈 강제 잡이 약 4분에 `백그라운드 · 썼음`과 완성 알림까지 갔다(두 번 — 4분 7초·3분 58초; 수정 전 26분 7초 또는 30분 한도 초과). 같은 스펙이 백그라운드 조립의 생성 시간 한도를 600초로 두고, 생성이 도는 중에 모델을 내려 앱이 죽던 결함(iOS 시뮬레이터 SIGSEGV)을 막았다. 실측·결론은 `specs/079-bg-auto-write-threads/quickstart.md`와 AGENTS 「079」. **아래는 남은 일이다.**

**배경**: 「매일 쓰는 시각」에 휴대폰이 스스로 일기를 쓰고 알림을 보내는 것이 이 앱의 약속이다. 079 뒤에도 그 약속이 성립한다고 말할 수 있는 것은 「배터리 예외를 준 안드로이드 한 기종에서, 강제로 돌린 잡」까지다.

- **배터리 예외가 없는 안드로이드**: 화면이 꺼지면 삼성 `FreecessController`가 프로세스를 얼린다(`FZ … reason: LEV`, `freezer:/frozen` — 079에서 두 번 봤다). 강제로 돌린 잡이 시작조차 못 하거나 진행하지 않았고 시도 기록에 줄이 남지 않았다. 스레드 수로는 풀리지 않는다. 065가 Play 정책 때문에 「한 번 눌러 허용」을 걷었으므로 삼성 밖 기기는 사용자가 목록에서 직접 꺼야 한다.
- **OS가 스스로 깨운 잡**: 079의 확인은 `cmd jobscheduler run -f`와 살아 있는 프로세스 기준이다. 죽은 프로세스를 OS가 깨우는 콜드 스타트, 잡 실행 최소 보장(이 기기 10분) 안에 드는지, 실제로 목표 시각 근처에 깨우는지는 보지 않았다.
- **다른 기기**: 값 2는 한 기기에서 쟀다. 백그라운드 cpuset의 코어 수는 기기마다 다르다(이 기기는 0–2, 실행 중 0–3으로 옮겨지기도 했다). SM-G986N(077 헤드리스 18분 45초)은 079 뒤로 다시 재지 않았다.
- **iOS**: 실제 iPhone이 없어 한 번도 재지 못했다. 시뮬레이터는 BGTask를 등록하지 않는다. 079가 시뮬레이터에서 본 것은 「쓰는 도중 멈췄다 돌아와도 앱이 죽지 않는다」까지다.

**할 일**:

1. **iOS는 기록부터 모은다.** 079가 든 빌드를 TestFlight에 올리고(`ios.buildNumber` 올림 — 079 이전 빌드는 멈췄다 180초 넘겨 돌아오면 앱이 죽을 수 있으므로 그 빌드로 모으지 않는다), 테스터의 개발자 화면(설정 → 「버전」을 1초 안에 7번 탭 → 「개발자」 맨 아래) 스크린샷을 받는다. 함께 물을 것은 백그라운드 앱 새로 고침·저전력 모드·앱을 밀어서 끄는 습관이다. `시작한 뒤 끝나지 않음`이나 밤 시각의 `실패`가 되풀이되면 예산·메모리 문제다 — iPhone이 생기면 debug 빌드를 Xcode로 붙여 `_simulateLaunchForTaskWithIdentifier:`로 강제 실행해 잰다. iOS에 스레드 값을 줄지는 그 기록으로 판단한다(지금은 주지 않는다).
2. **배터리 예외가 없는 사용자를 어떻게 할지 정한다**(소유자 결정). 후보: 설정 문구를 사실대로 고친다(「배터리 예외가 없으면 앱을 열 때 써요」) / 온보딩·설정에서 예외를 더 분명히 권한다 / 포그라운드 서비스로 돌린다(새 네이티브 코드와 Play 서비스 유형 신고가 따르고, 얼림을 피하는지는 재지 않았다 — 이 기기에서 포그라운드 서비스 상태의 다른 앱들은 `/foreground` cpuset에 있다) / 그 사용자에게는 백그라운드 완주를 약속하지 않고 「제때 알림으로 열게 한 뒤 앱을 열 때 쓴다」로 둔다. 끊기거나 얼어붙은 실행이 사용자에게 아무것도 남기지 않는 것도 여기서 정한다.
3. **OS가 스스로 깨운 잡을 한 번 본다**(소크). 배터리 예외를 준 기기를 하룻밤 두고 시도 기록의 `백그라운드 · 썼음`과 시각을 읽는다. 절차의 함정은 AGENTS 「백그라운드 작업 소크·헤드리스 관찰」.
4. 078에서 미룬 것을 같이 본다: 층 1 전체(`npm run test:layer1`), 오전 목표에서 어제가 기다리는 것, `autoWriteDay`가 비워지지 않는 것(설정에서 켰다 끄고 닫아도 쓴다), iOS 백그라운드 재실행에서 보이지 않는 홈이 쓰기를 가져가는 경합(AGENTS 078 읽는 법).
5. **쓰기 잠금이 「이 프로세스가 지금 쥔 것」과 「죽은 실행이 남긴 것」을 가르지 못한다**(079 코드 리뷰). 잠금은 쓰기 시작 때 한 번 잡고 갱신하지 않으며 나이만으로 낡음을 판정한다(079가 6분 → 10분으로 올렸다). 그래서 (a) 10분을 넘겨 도는 백그라운드 실행(사진 읽기 + 본문 600초 + 제목), (b) iOS에서 오래 멈췄다 돌아온 실행의 잠금은 낡은 것으로 보여 앱을 열 때 쓰는 경로가 두 번째 쓰기를 시작할 수 있고(모델 둘이 잠깐 함께 열린다), (c) 반대로 OS에 죽은 실행의 잠금은 10분 동안 쓰기를 막는다. 후보: 같은 프로세스가 쥐고 있는 잠금은 나이와 무관하게 살아 있다고 보고, 다른 프로세스 실행이 남긴 잠금은 곧바로 죽은 것으로 본다(020 `contracts/generation-lock.md` 개정 — 그때 「앞 실행이 정리될 때까지 홈의 쓰기를 어떻게 할지」도 정한다). 078의 「보이지 않는 홈이 쓰기를 가져가는 경합」과 같이 본다. 같은 계열로, 엔진의 `load()` 둘이 동시에 오면 둘 다 모델을 연다(018부터 — 미리 준비가 아직 여는 중에 「쓰기」를 누른 경우).
6. 한도 타이머가 멈춰 있던 시간까지 세는 것(079가 손대지 않았다) — 백그라운드 본문이 시작된 지 600초가 지난 뒤 사용자가 앱을 열면 그 실행은 `실패`로 끝난다. 기록에 이 모양이 되풀이되면 본다.

**완료 조건**: iOS는 테스터의 기록을 한 건 이상 읽어 다음 조치를 정했다. 안드로이드는 OS가 스스로 깨운 잡의 `백그라운드 · 썼음`을 한 번 봤고, 배터리 예외가 없는 사용자에 대한 제품 동작(설정 문구 포함)을 소유자가 정해 반영했다.

### 릴리스 빌드 번호 자동 올림 — `versionCode`·`buildNumber`를 사람이 안 올리게

**Tier 3(서명·업로드)** — 안드로이드(076)와 iOS(075) 릴리스 워크플로의 마지막 수동 단계를 없애는 과제다.

**배경**: 두 릴리스 워크플로는 `app.json`의 `android.versionCode`·`ios.buildNumber`를 **사람이 올려 커밋**해야 돈다. 같은 번호는 Play·Apple이 거부한다.
076의 첫 실행에서는 `versionCode`를 올리는 PR(9 → 10)을 따로 만들어 머지해야 했다. 사전 점검은 정수 여부만 보고 중복은 스토어의 거부에 맡겨서, 번호를 잘못 알면 긴 빌드(안드로이드 약 11분)를 돌린 뒤에야 실패한다.

**먼저 풀어야 할 질문 (설계 전에 소유자 결정)**:

- **번호를 어디서 정하는가.** 후보: (1) CI가 `main`에 번호 올림 커밋을 push한다 — `contents: write`가 필요해 비밀을 쥔 워크플로에 쓰기 권한을 주게 되고, `main` 직접 커밋을 막는 훅·브랜치 규칙과 부딪힌다.
  (2) 빌드 때만 번호를 덮어쓰고 커밋하지 않는다 — 번호의 원천이 필요하다(스토어에 올라간 마지막 번호 + 1, 또는 `GITHUB_RUN_NUMBER` + 오프셋). 저장소의 `app.json` 번호와 스토어 번호가 어긋나고 로컬 빌드(대안 절차)와 충돌할 수 있다.
  (3) 지금처럼 사람이 올리되 **사전 점검이 스토어의 마지막 번호를 읽어 중복이면 빌드 전에 실패**하게 한다 — 읽기 권한만 필요하다(Play는 서비스 계정에 이미 있는 권한 범위 안인지 확인, App Store Connect는 API 키로 조회). 번호를 올리는 일 자체는 남는다.
- **두 플랫폼을 같은 방식으로 할 것인가.** 안드로이드는 `versionCode`가 단조 증가해야 하고, iOS는 `version` 안에서 `buildNumber`가 단조 증가한다. 번호의 규칙이 다르다.
- **스토어 번호를 읽는 통로를 쓸 것인가.** Play 쪽은 `edits.tracks` 조회가 필요하고 서비스 계정 권한을 더 줘야 할 수 있다 — 안 잰 권한을 추측하지 않는다(원칙 V).

**할 일**: 소유자가 후보를 고른 뒤, 고른 방식을 두 워크플로에 같은 모양으로 넣는다. 사전 점검에서 번호 문제를 빌드 전에 알리는 것이 최소한의 성과다. 계약 테스트(`__tests__/ci/*-release-workflow.test.ts`)와 위반 주입으로 새 경로가 비밀을 더 노출하지 않음을 잠그고, AGENTS의 「release 빌드·서명·Google Play」·「iOS 빌드·서명·TestFlight」의 「`versionCode`/`buildNumber`는 사람이 올린다」를 새 방식으로 고친다.

**완료 조건**: 번호를 사람이 PR로 올리지 않고도 두 워크플로가 한 번씩 성공하거나(방식 1·2), 스토어에 이미 있는 번호로 시작하면 빌드 전에 이름을 밝히며 실패한다(방식 3). 실제 실행 결과를 눈으로 확인한다.

**위험**: 번호를 자동으로 정하는 순간 「어느 빌드가 어느 번호인가」의 추적이 코드 쪽으로 넘어간다 — 번호와 커밋의 대응이 문서·로그에 남아야 한다. 퍼블릭 저장소에서 쓰기 권한이나 읽기 통로를 늘리는 변경이므로 076·075의 비밀 방어 계약(수동 시작 하나, 허용된 비밀만, 정리 단계)을 약하게 하지 않는다.
