# 자동 쓰기 빠른 주기(개발 빌드 전용)와 080 잔여 결함 — 설계

## 문제

1. **자동 쓰기는 하루 한 번이라 다음 날에야 확인된다.** 판정 규칙(목표 시각·시도 창·쓸 차례 알림·완성 알림)이 모두 「하루」 단위라 하루에 여러 번 시험할 수 없다. 진단의 「자동 쓰기 지금 실행」(`manual.ts`)은 설정 입력만 덮어 한 번 돌릴 뿐, OS가 스스로 깨운 잡·시도 창·쓸 차례 알림의 예약 시각은 지나가지 못한다.
2. **080에서 드러난 코드 결함이 로드맵 「백그라운드 자동 쓰기」 할 일 5번에 남아 있다.**

## 목표

- 개발 빌드에서 「하루」를 N분으로 줄인 주기가 **폰을 두기만 해도 계속 돌아** 하루에 여러 번 같은 규칙을 확인할 수 있다. 실제 판정·알림·OS 깨움 경로를 그대로 탄다(우회로를 만들지 않는다).
- 080 잔여 결함 다섯 가지를 아래 결정대로 닫는다.

## 소유자 결정 (2026-10-26)

1. 범위는 로드맵 1번 과제의 5번 항목(080 잔여)과 빠른 주기 모드다. iOS TestFlight 기록·하룻밤 소크는 이 모드가 만들어 주는 **수단**일 뿐 이번 완료 조건이 아니다.
2. 가속 방식은 **타이밍 해석기 한 곳**이다. 판정 함수에 시간 상수를 넘겨주는 모듈 하나를 둔다. 가상 시계 오프셋은 쓰지 않는다(미래 날짜 일기가 실제 데이터를 오염시킨다).
3. 반복은 **주기가 시작될 때 앱이 테스트 날의 일기를 자동으로 지워** 매 주기를 새 하루처럼 시작한다.
4. 기본 주기 프리셋은 10분 / 30분 / 60분이고 직접 입력도 허용한다(5~180분의 정수).
5. **테스트 날은 오늘로 고정**한다. 따라서 창 밖 따라잡기(지난 날 대상) 규칙은 이 모드로 확인하지 못한다 — 기존 단위 테스트의 몫으로 남긴다.

## 설계 1 — 빠른 주기

### 의미

| 실제 규칙 | 빠른 주기에서 |
|---|---|
| 하루 한 번 목표 시각 | 하루 시작(00:00)부터 N분 격자마다 주기가 시작된다(주기 번호 = ⌊자정 이후 분 / N⌋). 마지막 주기는 자정에서 잘려 짧을 수 있다. |
| 시도 창 = 목표 +3시간 | 주기 시작부터 ⌊N/2⌋분 |
| 후보 날 = 사흘 | **오늘 하나**(창 안에서만 후보, 창 밖은 `not-near-target`) |
| 쓸 차례 알림 = 앞으로 7일 | **다음 주기 시작 시각 하나** |
| 배터리 예외 알림 지연 30분 | min(30, ⌊창 분 / 2⌋) — 지연된 알림이 창 안에 울리게 한다(코드 리뷰에서 창 끝에 닿는 문제를 바로잡음) |
| 쓴 날은 다시 쓰지 않는다 | **주기가 바뀌면 오늘의 일기를 지운다** |

### 구성

- **`src/schedule/timing.ts`(새)** — `ScheduleTiming`(목표 분·창 분·후보 날 목록·알림 지연 상한)을 돌려주는 유일한 곳. 배포 값은 종전과 같다(목표 = 시×60, 창 180분, 사흘). `decideSchedule`·`planReminders`·`resolveAutoWrite`·`manual`·`task.ts`의 창 판정이 `targetHour`를 직접 읽는 대신 이것을 받는다. 판정 규칙 자체는 바꾸지 않는다.
- **`preferences/dev-fast-cycle.json`** — `{ periodMinutes, resetCycle }`. 기록은 켠 것만 담고 없으면 꺼짐이다(064 `simulation.json`과 같은 방식). **`showsOnScreen(resolution)`이 참일 때만 읽는다.** prod는 파일이 있어도 무시한다. 읽지 못하면 꺼짐이다(원칙 V). 헤드리스 잡도 같은 해석기로 읽는다.
- **주기 리셋 한 함수** — 모든 자동 쓰기 경로(백그라운드 `task.ts`, 앱 열기 `useAutoWriteHandoff`, 알림 누름 `useAutoWriteClaim`)가 판정 직전에 같은 함수를 부른다. 경로마다 복제하지 않는다. 현재 주기 번호가 `resetCycle`과 다르면 (a) 살아 있는 쓰기 등록부의 칸을 `beginWipe`로 차지하고(못 차지하면 이번에는 리셋하지 않는다), (b) 오늘의 일기를 지우고, (c) 그 날의 완성 알림 확인 기록·건너뜀 기록·창 밖 따라잡기 기록을 비우고, (d) 트레이의 알림을 거두고, (e) `resetCycle`을 갱신한다. 일기 파일 하나를 지우는 `DiaryStore.removeDay(day)`를 새로 둔다(`removeAll`은 그대로). 다른 날의 일기는 건드리지 않는다.
- **켤 때** — 오늘 일기가 이미 있으면 확인창을 거친다(지운다고 말한다). 「자동으로 쓰기」가 꺼져 있으면 모드를 켜도 쓰지 않으므로 그 사실을 화면에 알린다(설정 토글은 그대로 실제 설정이다).
- **화면(개발자 메뉴 「빠른 주기」)** — 켬/끔, 프리셋 세 개와 직접 입력, 지금 주기 번호·다음 주기 시작 시각. 진단 화면 머리에 「빠른 주기 켜짐 · 주기 N분」 한 줄(시도 기록이 평소와 다른 이유를 읽을 수 있게). 문구는 `src/i18n/catalogs/ko/`에만 둔다.
- **잡 등록은 그대로 15분** — 안드로이드 WorkManager 하한이다. 모드를 켜거나 끌 때 `reschedule()`로 주기 타이머를 다시 시작한다.

### 한계 (문서·화면에 그대로 적는다)

- 안드로이드는 15분 간격이 하한이고 OS가 더 미룰 수 있다. 권장 주기는 30분 이상이다. 10분 주기는 앱 열기(057) 경로나 강제 잡(`cmd jobscheduler run -f`)으로 확인하며, OS가 스스로 깨우는 빈도는 못 줄인다.
- iOS는 OS가 깨우는 시각을 앱이 정하지 못한다. 주기는 판정 쪽만 줄인다.
- 창 안 15분 간격 잡이 주기 안에 한 번도 안 올 수 있다 — 그 주기는 「쓴 일기 없음」으로 끝나며 이것도 관찰 결과다.
- 창 밖 따라잡기와 사흘 후보는 이 모드로 확인되지 않는다.
- 값(창 = N/2, 지연 상한)은 **사람이 정한 값이다 — 측정이 아니다**(원칙 V).

### 헌법·경계

- 원칙 I: 추론은 그대로 온디바이스다. 이 모드는 미리 만든 응답을 두지 않는다.
- 원칙 IV: 측정·채점이 없다. 시도 기록의 갈래를 늘리지 않는다.
- `process.env`는 `environment.ts`에서만 읽는다. 환경 판정은 호출부가 `showsOnScreen`으로 한 값을 넘긴다(`simulation`과 같다).
- `check-constitution`에 규칙을 더한다: `dev-fast-cycle` 읽기·리셋은 해석기와 리셋 한 곳, `showsOnScreen` 가드 뒤에서만. 위반 주입으로 잡히는지 확인한다.

## 설계 2 — 080 잔여 결함

| 항목 | 결정 | 내용 |
|---|---|---|
| ① `load()` 동시 호출 경합 | 고친다 | `llama-port.ts`에 진행 중 적재 약속을 둔다. 같은 캐릭터면 합류하고, 다른 캐릭터면 앞 적재가 끝난 뒤 닫고 연다. 둘이 동시에 `context === null`을 보고 모델 둘을 여는 틈을 닫는다(E1). 재현 테스트가 먼저. |
| ② 018 미리 준비 | 걷는다 | `App.tsx`가 `prepare`·`release`·`captionDay`를 홈에 넘기지 않음을 먼저 확인한다. 확인되면 `DiaryHomeScreen`의 props·effect·관련 테스트를 지운다. 연결하면 ①이 실제 경로가 되고 파이프라인이 어차피 적재한다. |
| ③ 지운 날 백그라운드 재작성 | 고치지 않는다(의도된 동작) | 자동 쓰기를 켜면 안 쓴 날을 따라잡는 것이 약속이다. 이유를 로드맵 완료 이력·AGENTS에 한 줄로 남긴다. |
| ④ iOS 합류 쓰기 실패 시 이어 쓰기 | 고친다 | 「한 번」을 시작이 아니라 저장될 때 소비하도록 옮긴다. 정확한 자리는 `useAutoWriteHandoff`·`useAutoWriteClaim`·`live-write` 조립을 읽고 계획에서 정하며, 실제 파이프라인·등록부를 묶은 조립 테스트로 잠근다(080·081·082 규칙). |
| ⑤ 「지우기 막힘」 문구 | 문구를 맞춘다 | 지금 지우기는 남의 쓰기를 끊고 지우므로 「쓰는 중이라」는 사실과 다르다. 막힘은 다른 지우기가 겹칠 때뿐이다. 새 문구는 소유자가 확정하고, 골든은 다시 쓰지 않고 `CHANGED_AFTER_GOLDEN`에 올린다. |

원인 불명인 「백그라운드 쓰기가 본문 49초 뒤 실패」(080 합류 첫 실행)는 재현되지 않아 이번에 다루지 않는다. 빠른 주기로 돌리다 다시 나면 개발자 화면의 `백그라운드 · 실패`를 같은 시각의 「최근 실패」 줄과 짝지어 읽는다.

## 테스트 (TDD)

- **해석기** — 배포 값이 종전과 같다(회귀), 주기 번호·창·다음 주기 시작 시각의 경계(자정 잘림 포함), prod 환경에서 파일이 있어도 배포 값, 파일이 깨졌으면 꺼짐.
- **판정** — 빠른 주기에서 창 안은 오늘을 쓰고 창 밖은 `not-near-target`, 기존 `decideSchedule`·`resolveAutoWrite` 테스트는 한 줄도 바꾸지 않고 통과.
- **리셋** — 주기가 바뀌면 오늘 일기·알림 확인 기록·건너뜀·따라잡기 기록이 지워지고 다른 날은 남는다 / 쓰기가 살아 있으면 리셋하지 않는다 / 같은 주기에는 두 번 지우지 않는다 / 세 경로가 같은 함수를 부른다(소스 계약).
- **알림** — 빠른 주기 계획은 다음 주기 시작 한 개 / 지연 상한.
- **조립** — 실제 판정·리셋·기록을 묶어 한 주기가 「리셋 → 쓰기 → 저장 → 다음 주기 리셋」으로 도는 것을 한 번 잠근다.
- **위반 주입** — 가드(`showsOnScreen`)를 빼면 prod 테스트가 실패하는지, 리셋을 한 경로에서 빼면 소스 계약이 잡는지.
- 080 잔여 ①④⑤: 각각 재현 테스트가 먼저 실패해야 한다. ②는 지운 뒤 `tsc` 0과 전체 테스트.

## 실기기 (SM-S901N, dev 빌드)

- 빠른 주기 30분: 자동 쓰기를 켠 채 화면을 끄고 두어 세 주기 이상. 시도 기록에서 주기마다의 결과(`백그라운드 · 썼음`, 못 깨운 주기 포함)를 읽고, 쓸 차례 알림이 주기 시작에 뜨고 쓰기 저장 뒤 거둬지는지 본다.
- 10분 주기: 앱 열기와 강제 잡으로 판정·리셋·알림 한 바퀴.
- ① 적재 경합은 쓰기와 진단 수동 실행을 겹쳐 확인한다. 못 본 것은 못 봤다고 적는다.

## 사용자에게 보이는 변화

배포 사용자에게 보이는 변화는 ⑤의 문구 하나뿐이다(드물게 보임). 빠른 주기는 개발 빌드 전용이라 릴리스 노트에 쓰지 않는다. 노트는 번호를 올릴 때 사람이 정한다.
