# Feature Specification: 필수 자산 다운로드 동의 안내와 진행 슬라이드

**Feature Branch**: `045-onboarding-download-consent`

**Created**: 2026-09-19

**Status**: Draft

**Input**: User description: "Modernist 디자인 시스템 적용 3차 — 필수 자산(VLM·LLM) 다운로드
동의 안내 및 진행 슬라이드. 권한 확인(043) 완료 직후, 다운로드 시작 전에 반드시
NativeWind Dialog로 VLM·LLM을 받아야 한다는 확인/동의 안내가 먼저 와야 한다.
사용자가 확인해야 다운로드가 시작되고, 다운로드 중에는 디자인 리뷰 보드의 `1o`~
`1q`(슬라이드 1~4 + 완료) 5개 화면이 보여야 한다. 044(작명 화면)는 이 구간을
전혀 다루지 않고 그냥 넘어갔다."

## 배경 및 경위

043(스플래시·권한 요청)과 044(작명 화면)가 Modernist로 이관됐지만, 그 사이에
있어야 할 화면 하나가 통째로 비어 있었다. 지금 `App.tsx`의 첫 실행 게이트는:

```
LogoScreen → OnboardingScreen(권한) → (작명 WelcomeScreen ∥ 다운로드) →
  WaitingForDownloadScreen(작명이 먼저 끝났는데 다운로드가 안 끝났을 때만
  조건부 등장 — 회전 인디케이터 + 진행바 하나뿐) → 홈
```

040이 "작명이 다운로드를 기다리지 않고 먼저 뜨게 해서 대기 체감을 줄인다"는
근거로 이 병렬 순서를 설계했다. 이번 스펙은 그 결정을 **되돌린다** — 저장소
소유자가 확정한 순서는 다음과 같다:

```
LogoScreen → OnboardingScreen(권한, 043) →
  [동의 Dialog: VLM·LLM을 받아야 한다] →
  [다운로드 진행 슬라이드 1~4 + 완료 (리뷰 보드 1o~1q)] →
  WelcomeScreen(작명, 044)
```

다운로드는 더 이상 작명과 병렬로 조용히 진행되지 않는다 — 사용자가 동의
Dialog에서 확인을 눌러야 시작되고, 진행 중에는 전용 슬라이드 화면이 보인다.
작명은 다운로드가 끝난 뒤에만 나타난다.

**디자인 리뷰 보드에는 이 동의 Dialog가 없다** — 화면 7개 섹션(`Launch`·
`Onboarding`·`First run`·`Persona picked`·`Home`·`Writing`·`Diary detail`)을
전수 확인했고 VLM·LLM을 고르는 화면도, 동의를 구하는 화면도 없다. Dialog는
이 스펙에서 새로 정의하는 요소다 — VLM·LLM을 선택하는 것이 아니라(029
`ESSENTIAL_ASSET_KEYS`가 이미 셋을 다 받는 것으로 고정돼 있고 이 스펙은
그 값을 바꾸지 않는다), 무엇을·왜 받는지 사용자에게 알리고 동의를 구하는
안내문이다.

## Clarifications

### Session 2026-09-19

- Q: 사용자가 동의 Dialog에서 거부하면 어떻게 되는가? → A: 거부 버튼이
  없다 — [확인/시작] 하나만 있다. 필수 자산이라 앱이 동작하려면 결국
  받아야 하므로, `WaitingForDownloadScreen`(040)이 이미 "그만두기 경로가
  없다"고 정한 것과 같은 논리를 Dialog에도 적용한다.
- Q: 슬라이드 자동 전환 간격은 얼마인가? → A: 슬라이드당 4초 고정. 리뷰
  보드 CSS의 `onbfade 14s`(4장 크로스페이드 순환 애니메이션, 14초/4 ≈
  3.5초 간격)에 가장 가까운 사람이 읽기 편한 값으로 반올림한다 — 정밀한
  다운로드 속도 측정과 무관한 장식적 타이머다(FR-006).
- Q: 완료 화면(`1q`)의 CTA 버튼 문구는 무엇인가? → A: "시작할게요". 044
  작명 화면(`WelcomeScreen`)의 기존 문구 톤(`TEXT.submit` = "이 이름으로
  할래요" 등, 1인칭 반말 캐릭터 화법)과 어울리는 짧은 확언형으로 고른다.
- Q: 리뷰 보드의 `onbProg1`~`onbProg4`(바이트·용량 노출) 문구는 무엇으로
  대체하는가? → A: "받는 중이에요" 한 문장 고정 — 슬라이드 1~4 전부
  동일 문구(슬라이드가 이미 스토리를 전달하므로 진행 문구는 상태만
  알리면 충분하다). 퍼센트·바이트·속도 수치를 계산하지 않는다(FR-006).
- Q: 041 재개 시 슬라이드가 정확히 어느 단계에서 다시 보이는가? → A: 항상
  슬라이드 1(`1o`)부터 다시 보인다 — Edge Cases가 이미 "정확한 슬라이드
  번호는 복원하지 않아도 됨"이라 명시했으므로, 가장 단순한 구현(단계
  상태를 저장하지 않음)을 확정한다. 다운로드 자체의 재개(바이트 이어받기)
  와는 무관하다(FR-010).

## 범위

**범위 안**:
- 권한 확인 완료 직후, 다운로드 시작 전에 뜨는 동의 Dialog 신설.
- 리뷰 보드 `1o`(슬라이드1)·`1p`(슬라이드2)·`1r`(슬라이드3)·`1s`(슬라이드4)·
  `1q`(완료) 5개 화면을 다운로드 진행 화면으로 이관.
- 첫 실행 게이트 순서를 "권한 → 동의 → 다운로드 슬라이드 → 작명"으로 재배치
  (040의 "작명 ∥ 다운로드 병렬" 설계를 되돌림).

**범위 밖**:
- 044(`WelcomeScreen` 작명 화면) 자체의 시각 재작업 — 별도로 진행 중이며 이
  스펙 완료 후에도 044 산출물(문구·레이아웃)은 그대로 유지된다.
- `OnboardingScreen`(권한 요청, 043) 자체 변경.
- `essential-assets.ts`의 `ESSENTIAL_ASSET_KEYS`(`["v1","v2","a1"]`) 값 변경 —
  VLM·LLM을 고를지 말지는 이 스펙이 다루지 않는다. 무조건 셋 다 받는다.
- 재부팅·앱 강제 종료 중 다운로드 중단 후 재개 로직 — 041이 이미 세운 재개
  가능한 다운로드 포트를 그대로 재사용하고, 이 스펙은 새 중단·재개 정책을
  만들지 않는다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 무엇을 왜 받는지 알고 동의한다 (Priority: P1)

권한 요청을 마친 사용자는 곧바로 다운로드가 시작되는 대신, "일기를 쓰려면
사진을 읽는 모델과 글을 쓰는 모델을 내려받아야 한다"는 안내를 먼저 보고
확인을 눌러야 다운로드가 시작된다.

**Why this priority**: 지금은 사용자 동의 없이 대용량 모델(수백 MB~수 GB)이
조용히 받아지기 시작한다 — 041이 겪은 것처럼 대용량 다운로드는 실패
가능성(OOM 등)이 있는 무거운 동작이라, 시작 전에 사용자가 그것을 인지하고
동의하는 절차가 있어야 한다.

**Independent Test**: 권한 스텝을 모두 결정한 직후 화면에 동의 안내가
나타나는지, 그 안내를 확인하기 전에는 다운로드가 시작되지 않는지 확인하는
것으로 독립적으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 권한 스텝을 모두 결정한 상태, **When** 다음 화면으로 넘어간다,
   **Then** 다운로드 진행 화면이 아니라 동의 안내 Dialog가 먼저 보인다.
2. **Given** 동의 안내 Dialog가 보이는 상태, **When** 사용자가 아직 확인을
   누르지 않았다, **Then** 다운로드가 시작되지 않는다(진행률이 0에서
   움직이지 않는다).
3. **Given** 동의 안내 Dialog가 보이는 상태, **When** 사용자가 확인 버튼을
   누른다, **Then** Dialog가 닫히고 다운로드 진행 화면(User Story 2)으로
   넘어간다.
4. **Given** 동의 안내 Dialog, **When** 화면을 본다, **Then** 모델
   식별자·파일 크기(바이트·GB)·내부 자산 키는 보이지 않고, 사람이 이해할
   문장(사진을 읽는 모델, 글을 쓰는 모델을 받는다는 뜻)만 보인다(원칙 III·IV).
5. **Given** 동의 안내 Dialog, **When** 화면을 본다, **Then** [확인/시작]
   조작 하나만 있고 거부·나중에·건너뛰기 등 다운로드를 미루는 조작은
   없다(필수 자산이므로, 040 `WaitingForDownloadScreen`과 같은 논리).

---

### User Story 2 - 다운로드가 진행되는 동안 이야기를 본다 (Priority: P1)

사용자는 다운로드가 끝날 때까지 빈 화면이나 단순 스피너가 아니라, 이
앱에서 무엇을 할 수 있게 되는지 알려주는 4장짜리 슬라이드와 완료 화면을
순서대로 본다.

**Why this priority**: 지금의 `WaitingForDownloadScreen`은 회전 인디케이터
하나뿐이라 사용자가 무엇을 기다리는지, 앱이 뭘 해줄지 전혀 알 수 없다.
리뷰 보드가 이미 이 구간을 4장짜리 스토리텔링 슬라이드로 설계해 뒀는데
지금까지 이관되지 않았다. 다운로드는 043·044 이관 완료 직후 사용자가
반드시 거치는 첫 경험의 일부이며, 대기 시간이 수십 초~수 분(모델
크기에 따라)일 수 있어 그 시간의 인상이 앱 전체 인상을 좌우한다.

**Independent Test**: 다운로드가 진행되는 동안 화면을 관찰해 슬라이드가
차례로 넘어가는지, 다운로드가 끝나면 완료 화면으로 바뀌는지 확인하는
것으로 독립적으로 검증된다.

**Acceptance Scenarios**:

1. **Given** 동의 안내를 확인해 다운로드가 시작된 상태, **When** 화면을
   본다, **Then** 리뷰 보드 슬라이드 1(`1o`)의 레이아웃 — 진행 인디케이터
   (예: "01/04"), 헤드라인, 본문, 그림 자리, 진행 표시 4칸 — 이 보인다.
2. **Given** 다운로드가 진행 중이다, **When** 시간이 지난다, **Then**
   슬라이드가 2·3·4(`1p`·`1r`·`1s`) 순서로 자동 전환되며 각기 다른
   헤드라인·본문을 보인다.
3. **Given** 다운로드가 실제로 완료됐다, **When** 화면을 본다, **Then**
   완료 화면(`1q`)으로 전환되고 다음 단계(작명)로 넘어갈 수 있는 버튼이
   보인다.
4. **Given** 다운로드 진행 화면, **When** 화면을 본다, **Then** 바이트·
   퍼센트·전송 속도 등 수치화된 진행 정보는 보이지 않는다(원칙 IV) — 4칸
   진행 표시는 슬라이드 순서(1~4)를 나타낼 뿐 다운로드 완료율의 정밀한
   측정치가 아니다.
5. **Given** 슬라이드가 3번째(`1r`)까지 넘어갔는데 다운로드가 아직 안
   끝났다, **When** 시간이 더 지난다, **Then** 화면이 멈추지 않고 4번째
   슬라이드에 머무르며 다운로드가 끝나기를 기다린다(막다른 길이나 빈
   화면이 되지 않는다).

### User Story 3 - 다운로드가 끝나야 작명으로 넘어간다 (Priority: P2)

사용자는 다운로드가 완전히 끝난 뒤에만 작명 화면(044)에 도달한다 — 이전
(040)처럼 작명을 먼저 마치고 다운로드가 뒤에서 계속되는 상태가 아니다.

**Why this priority**: 저장소 소유자가 명시적으로 확정한 순서이며, User
Story 1·2가 존재해야 의미가 있는 전제 조건이다. P1 둘보다 우선순위가
낮은 이유는 이 스토리 자체는 "언제 넘어가는가"라는 게이트 판정 하나뿐이라
독립 시연 가치가 상대적으로 작기 때문이다.

**Independent Test**: 다운로드가 끝나기 전에는 작명 화면에 도달할 수
없고, 끝난 뒤에는 바로 작명 화면이 뜨는지 확인하는 것으로 독립적으로
검증된다.

**Acceptance Scenarios**:

1. **Given** 다운로드가 아직 끝나지 않았다, **When** 화면을 본다, **Then**
   작명 화면(이름 입력창)이 보이지 않는다.
2. **Given** 다운로드가 방금 완료됐다, **When** 완료 화면(`1q`)에서 다음
   버튼을 누른다, **Then** 작명 화면으로 넘어간다.

### Edge Cases

- 동의 안내를 보기 전에 앱을 강제 종료했다가 다시 열면, 다시 동의 안내부터
  시작한다(진행 중이던 다운로드가 없으므로 자연스럽다).
- 다운로드 슬라이드가 보이는 도중 앱을 강제 종료했다가 다시 열면, 041이
  세운 재개 가능한 다운로드 상태를 그대로 이어받아 이미 받은 만큼은 다시
  받지 않고, 슬라이드 화면은 항상 1번(`1o`)부터 다시 보인다(슬라이드
  단계 자체는 저장하지 않는다) — 처음부터 동의를 다시 구하지 않는다(이미
  동의했으므로, Clarifications 참고).
- 다운로드가 네트워크 실패 등으로 완주하지 못하는 경우의 재시도 안내는
  041이 이미 다루는 다운로드 계층의 실패 처리를 그대로 따르고, 이 스펙은
  화면이 그 실패를 막다른 길 없이 보여주기만 한다(재시도 경로가 있어야
  한다).
- 이미 필수 자산을 전부 받은 기존 사용자(업그레이드 케이스)는 동의
  Dialog도 다운로드 슬라이드도 보지 않고 곧장 다음 단계로 넘어간다 — 이미
  받은 것을 다시 동의받지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 권한 스텝이 모두 결정된 직후, 필수 자산이 아직
  전부 준비되지 않았다면, 다운로드를 시작하기 전에 동의 안내 Dialog를
  표시해야 한다.
- **FR-002**: 시스템은 사용자가 동의 안내에서 확인 조작을 하기 전에는
  다운로드를 시작하지 않아야 한다(MUST NOT).
- **FR-002a**: 시스템은 동의 안내에 [확인/시작] 외의 거부·건너뛰기 조작을
  제공하지 않아야 한다(MUST NOT) — 필수 자산이므로 미루는 경로 자체가
  없다(Clarifications, 040 `WaitingForDownloadScreen`과 같은 논리).
- **FR-003**: 시스템은 동의 안내에서 모델 내부 식별자·자산 키·파일 크기
  (바이트·GB 단위)·서버 주소를 노출하지 않아야 한다(MUST NOT, 원칙 III·
  IV) — 사람이 이해할 문장(사진을 읽는 모델, 글을 쓰는 모델을 받는다)만
  보여야 한다.
- **FR-004**: 시스템은 동의 확인 후 다운로드가 진행되는 동안, 리뷰 보드
  `1o`~`1s`에 대응하는 4장의 슬라이드를 순서대로 표시해야 한다.
- **FR-005**: 시스템은 각 슬라이드에 사람이 쓴 고정 헤드라인·본문 문구를
  표시해야 한다(추론이 생성한 텍스트를 섞지 않는다).
- **FR-005a**: 시스템은 슬라이드를 4초 간격으로 자동 전환해야 한다
  (Clarifications, 리뷰 보드 `onbfade 14s` 4장 순환에 가장 가까운 값).
- **FR-006**: 시스템은 슬라이드 진행 표시(4칸)를 다운로드의 정밀한 완료
  비율이 아니라 슬라이드 순서(1~4)로만 다뤄야 한다(MUST NOT, 진행률
  수치·바이트·전송 속도를 계산하거나 노출하지 않는다, 원칙 IV) — 각
  슬라이드의 진행 문구는 "받는 중이에요" 고정 한 문장이며 슬라이드마다
  달라지지 않는다(Clarifications).
- **FR-007**: 시스템은 다운로드가 실제로 완료되면 리뷰 보드 `1q`에
  대응하는 완료 화면으로 전환해야 하며, 이 화면에서 다음 단계(작명)로
  넘어갈 수 있는 "시작할게요" 버튼을 제공해야 한다(Clarifications).
- **FR-008**: 시스템은 다운로드가 완료되기 전에는 작명 화면(044
  `WelcomeScreen`)에 도달할 수 없어야 한다(MUST NOT) — 040이 도입한
  "작명이 다운로드보다 먼저 뜨는" 병렬 배치를 대체한다.
- **FR-009**: 시스템은 필수 자산이 이미 전부 준비된 사용자(업그레이드
  등)에게는 동의 안내와 다운로드 슬라이드 둘 다 표시하지 않고 다음
  단계로 곧장 진행해야 한다.
- **FR-010**: 시스템은 다운로드 진행 중 앱이 종료됐다가 재개되는 경우,
  이미 받은 만큼을 다시 받지 않아야 한다(MUST NOT, 041의 재개 가능한
  다운로드 포트를 재사용) — 다만 동의는 이미 받았으므로 Dialog를 다시
  보이지 않는다. 슬라이드 화면은 항상 1번부터 다시 시작한다(슬라이드
  단계는 저장하지 않는다, Clarifications).
- **FR-011**: 시스템은 다운로드가 실패해도 사용자가 재시도할 수 있는
  경로를 제공해야 하며, 막다른 길(재시도도 종료도 못 하는 상태)을 만들지
  않아야 한다(MUST NOT, 원칙 I).
- **FR-012**: 시스템은 `essential-assets.ts`의 `ESSENTIAL_ASSET_KEYS`
  값을 변경하지 않아야 한다(MUST NOT) — 이 스펙은 무엇을 받을지가 아니라
  받는다는 사실을 어떻게 안내하고 보여줄지만 다룬다.

### Key Entities

- **다운로드 동의 상태**: 사용자가 동의 안내를 확인했는지 여부. 앱을
  재설치하지 않는 한 한 번만 필요하다(FR-010).
- **다운로드 진행 슬라이드 단계**: 1~4 중 하나 또는 완료. 다운로드의
  정밀한 바이트 진행률과는 독립적인 값이다(FR-006).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 권한 확인 완료 후 다운로드가 시작되기 전, 100%의 세션에서
  동의 안내가 먼저 보인다(필수 자산이 이미 준비된 경우 제외).
- **SC-002**: 다운로드 진행 중 화면에 모델 식별자·바이트·전송 속도 수치가
  전혀 노출되지 않는다(육안 검사 + 소스 검사로 검증).
- **SC-003**: 사용자는 다운로드가 완료되기 전에는 작명 화면에 도달할 수
  없다(실기기 검증 + 계약 테스트로 확인).
- **SC-004**: 이미 필수 자산을 받은 사용자는 동의 안내·다운로드 슬라이드
  없이 다음 단계로 진행하는 데 걸리는 시간이 이 스펙 적용 전과 차이가
  없다(회귀 없음).

## Assumptions

- 동의 안내는 RN 코어(`Modal` 등)로 구현하고 새 네이티브 의존성을
  추가하지 않는다(043·044 관례 계승, `react-native-svg` 등 아이콘
  라이브러리도 도입하지 않는다).
- 리뷰 보드 원본의 `onbProg1`~`onbProg4` 문구("받는 중 · 310MB / 1.2GB"
  형태)는 원칙 IV 위반이므로 그대로 옮기지 않고 "받는 중이에요" 고정
  문구로 대체한다(Clarifications, FR-006).
- `1q`(완료 화면)의 CTA 버튼 텍스트는 원본에 "???"로 미정 표시돼 있어
  이 스펙이 "시작할게요"로 정한다(Clarifications, FR-007).
- 슬라이드 자동 전환 간격은 4초 고정이며 다운로드 실제 속도와 무관하게
  흐른다(Clarifications, FR-005a·FR-006 — 슬라이드는 스토리텔링이지
  진행률 지표가 아니다). 슬라이드가 4번째에 도달했는데 다운로드가 안
  끝났으면 거기 머무른다(Edge Cases).
- 041이 만든 구간별 다운로드(임시 파일 + 청크 복사) 로직은 이 스펙에서
  변경하지 않는다 — 화면이 소비하는 진행률 값(`essentialDownloadFraction`)
  계약도 그대로 재사용한다.
- **구현 중 발견**: 다운로드가 완료된 순간(`downloadReady: true`) 곧바로
  다음 단계로 넘어가면 FR-007의 완료 화면 버튼이 사용자가 누를 틈도 없이
  사라진다. 이를 막기 위해 "완료 화면의 버튼을 실제로 눌렀는가"라는 별도
  세션 로컬 상태(`downloadProceedConfirmed`)를 추가했다 — `namingDone`과
  같은 성격(파일에 저장하지 않음, 009 원칙)이며, `resolveFirstRunStage`는
  `downloadReady`와 `downloadProceedConfirmed`가 모두 참이어야 다음
  단계로 넘어간다(data-model.md "구현 중 발견한 갭", 계약 C10).
