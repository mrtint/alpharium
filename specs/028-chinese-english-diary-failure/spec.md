# Feature Specification: 샤오바이·모카 일기 생성 실패 조사

**Feature Branch**: `028-chinese-english-diary-failure`

**Created**: 2026-09-01

**Status**: Draft

**Input**: User description: "17번 — 샤오바이·모카 일기 생성 실패 조사"

## 이 스펙의 성격

이것은 새 기능 스펙이 아니라 **결함 조사(진단) 스펙**이다. 019(백그라운드
스파이크)·027(024 잔여 실측)와 같은 계열 — 목표는 새 화면·새 저장 계층을
만드는 것이 아니라, **사용자가 보고한 구체적 증상의 실패 갈래를 실기기
실측으로 특정하고**, 그 갈래에 따라 **최소한의 교정**만 하는 것이다.

- 산출물은 동작하는 새 기능이 아니라 **실패 갈래 확정 + 근거(실기기 로그) +
  교정 결정**이다. `specs/028-chinese-english-diary-failure/findings.md`에
  실측 수치를 남긴다.
- 코드 변경은 **조건부**다. 조사 결과가 가리키는 최소 수정만 한다:
  - `acceptance.ts`의 언어 판정이 오탐이면 그 판정 함수를 고친다 —
    **판정 갈래는 늘리지 않는다**(헌법 원칙 IV, `REJECT_REASONS` 4개 고정).
  - 모델 출력이 깨진 인코딩(mojibake)이면 그것은 이 저장소의 판정·저장
    코드로 고칠 수 없다 — 로드맵 14번(자동 생성용 서술형 모델 재검토)과
    병합하고, 이 스펙은 "GGUF/`llama.rn` 조합 문제"라는 결론과 근거만
    남긴다.
  - `prompt.ts`의 출력 언어 지시문이 약해 모델이 엉뚱한 언어를 내면 그
    한 줄을 강화한다 — 캐릭터에서 오는 것은 이름과 출력 언어뿐이라는 경계
    (헌법 원칙 III)는 유지한다.
- 헌법 원칙 IV(측정 장치를 제품에 들이지 않는다)와 충돌하지 않는다 — 이
  조사는 모델 출력을 채점하거나 여러 모델을 비교하지 않는다. "이 캐릭터의
  생성이 어느 실패 갈래에서 멈추는가"라는 사실 하나를 실기기 로그로 재는
  것이지, 일기 품질을 재는 것이 아니다. 거부된 본문을 사람이 눈으로 읽어
  mojibake 여부를 확인하는 것도 채점이 아니다.
- 검증용으로 쓰는 합성 하루·모델 재배치는 010 원칙대로 "경로가 도는가"만
  확인하는 데 쓰고, 출력 품질을 결론짓는 데 쓰지 않는다.

## 배경 — 이미 관측·배제된 것

**증상 (2026-09-01, 사용자 보고, SM-S901N / Galaxy S22, dev, Metro 실행 중)**:
샤오바이(`chinese`)·모카(`english`)로 일기를 쓰면 **"일기를 다시 쓸 수 있을
것 같다 (실패)"** 계열 화면이 뜨고 목록에 남지 않는다. 금동이(`quiet`)는
정상. 오드(`imaginative`)·루이(`narrative`)는 이 보고에 포함되지 않았다
(루이는 024 §10에서 별도로 EXAONE mojibake·헤드리스 미완주가 관측됨).

**1차 실측으로 배제된 것**:

- **모델 파일 존재·크기 일치**: `files/models/`에 `a4`(1,107,409,472
  바이트)·`a5`(806,058,272 바이트)가 있고, `roster.ts`의 `expectedBytes`와
  정확히 일치한다.
- **검증(verdict) 통과**: `state.json`에 `a4`
  (`verifiedMd5: dc4836c71a28a136d2a5b782b8465b6f`)·`a5`
  (`b00db505c25aa7178848ed1b4aa7af34`) 둘 다 `passed: true`.
  `roster.ts`의 `md5`는 여전히 `""`이지만 `readinessOf`는 `state.json`
  verdict을 보므로 판정상 두 캐릭터는 `ready`.
- **다운로드·준비 계층 아님**: `model-not-ready` 단계에서 멈추는 것이
  아니다 — 파이프라인은 `generation` 단계까지 도달한다.

**사용자 화면 문구가 가리키는 것**: "다시 시도해 볼 만하다" 계열은
`describeFailure()`에서 `rejected`·`timed-out`·`generation-failed` 세
갈래가 공유하는 문구다(`failure-text.ts`). 즉 실패는 생성 파이프라인의
`generation` 단계에서 일어나며, 세 갈래 중 하나다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 샤오바이·모카의 실패 갈래를 특정한다 (Priority: P1)

조사자가 실기기에서 `adb logcat`(`ReactNativeJS`·`llama` 태그)을 건 채
샤오바이·모카로 "사진을 보지 않음" 설정의 일기를 생성한다. 실패가 어느
갈래(`rejected: <why>` / `timed-out` / `generation-failed`)에서 나는지,
그리고 그 시점까지 생성된(거부된) 본문이 무엇인지 로그에서 확인한다.

**Why this priority**: 이것이 조사 요청의 핵심 질문이다. 실패 갈래를 모르면
교정 방향(판정 수정 / 프롬프트 수정 / 모델 교체)을 정할 수 없다. 다른
무엇보다 먼저 답해져야 한다.

**Independent Test**: 실기기에서 두 캐릭터로 "보지 않음" 생성을 각각 1회
이상 돌리고, 로그에서 실패 갈래 문자열과 거부된 본문 텍스트를 채록하는
것만으로 이 질문에 답할 수 있다. 신호가 빈약한 "보지 않음" 하루를 쓰는
이유는 VLM·사진 변수를 제거해 생성 경로만 남기기 위해서다.

**Acceptance Scenarios**:

1. **Given** 샤오바이(`chinese`) 모델이 `ready`이고 "사진을 보지 않음"
   설정, **When** 과거 하루(신호 빈약)로 일기를 3회 생성한다, **Then**
   로그에 매 회 실패 갈래(`rejected: <empty|echo|language|unfinished>` /
   `timed-out` / `generation-failed`)가 남고, 3회의 갈래 분포가
   findings.md에 기록된다.
2. **Given** 모카(`english`) 모델이 `ready`이고 같은 설정, **When** 같은
   하루로 3회 생성한다, **Then** 모카의 실패 갈래 분포도 같은 방식으로
   기록된다 — 두 캐릭터가 같은 갈래인지 다른 갈래인지 명시된다.
3. **Given** 실패 갈래가 `rejected`, **When** 거부된 본문을 로그에서
   확인한다, **Then** 그 본문이 (a) 비었는지 (b) 지시문을 되뱉었는지
   (c) 기대 언어(중국어/영어)가 아닌지 (d) 깨진 UTF-8(mojibake)인지가
   사람이 읽어 판정되어 기록된다.
4. **Given** 실패 갈래가 `timed-out`, **When** 로그의 `writingMs` 또는
   `engine.run()` 경과를 확인한다, **Then** 실제 소요 시간이
   `GENERATION_TIMEOUT_MS`(180초, `engine.run()` 구간)와 대비되어
   기록되고, 이 캐릭터가 이 기기에서 한도 안에 끝나는지가 판정된다.

### User Story 2 - 원인이 판정 오탐이면 언어 판정을 교정한다 (Priority: P2)

조사에서 모델은 올바른 언어(중국어/영어)로 정상 본문을 냈는데
`isWrongLanguage`가 그것을 거부한 것으로 밝혀지면, 그 판정 함수를 고쳐
정상 본문이 통과하도록 한다.

**Why this priority**: 이 갈래가 로드맵이 "유력"으로 지목한 것이다
(`isWrongLanguage` 오탐). 사실이면 두 캐릭터가 동시에 못 쓰는 것이 한
함수의 수정으로 풀리는, 비용 대비 효과가 가장 큰 교정이다. P1의 결과가
이 갈래가 아니면 이 스토리는 발동하지 않는다.

**Independent Test**: 교정 후 기기 없는 계약 테스트(`acceptance.test.ts`)에
"모델이 중국어/영어로 정상 본문을 낸 경우"를 추가해 통과를 확인하고,
실기기에서 두 캐릭터로 재생성해 일기가 저장·목록 반영되는 것을 확인한다.

**Acceptance Scenarios**:

1. **Given** 조사에서 채록한 "정상적인 중국어 본문"과 "정상적인 영어
   본문", **When** 현재 `judge()`에 그 텍스트를 넣는다, **Then** 현재
   코드가 `language`로 거부하는 것이 재현되고, 거부 조건이 소스에서
   특정된다(예: 한자 판정 범위 누락, 특정 문자 클래스 오분류).
2. **Given** 언어 판정을 교정한 코드, **When** 같은 정상 본문을 넣는다,
   **Then** `{ ok: true }`가 나오고, 기존 4갈래(`empty`/`echo`/
   `language`/`unfinished`)의 다른 케이스는 회귀 없이 그대로 동작한다.
3. **Given** 교정된 코드, **When** `REJECT_REASONS` 배열과
   `acceptance.test.ts`의 갈래 수 검사(A-7)를 확인한다, **Then** 갈래는
   여전히 정확히 4개다 — 다섯 번째가 추가되지 않았다.
4. **Given** 교정된 코드, **When** 위반 주입(정상 중국어/영어 본문이
   다시 거부되도록 판정을 되돌림)을 한다, **Then** 새로 추가한 계약
   테스트가 그것을 잡는다.

### User Story 3 - 원인이 프롬프트면 출력 언어 지시문을 강화한다 (Priority: P3)

조사에서 모델이 실제로 엉뚱한 언어(예: 한국어, 또는 중국어여야 하는데
영어)를 낸 것으로 밝혀지면, `prompt.ts`의 출력 언어 지시 한 줄을 강화해
모델이 캐릭터 언어로 쓰도록 한다.

**Why this priority**: 판정은 옳고 모델 출력이 계약을 어긴 경우다. 프롬프트
한 줄 강화로 풀릴 수 있으나, 실기기 대조 생성으로 재발하지 않는지 확인해야
하므로 P2보다 뒤다. P1 결과가 이 갈래가 아니면 발동하지 않는다.

**Independent Test**: 강화된 지시문으로 두 캐릭터를 실기기에서 재생성해
출력이 캐릭터 언어인지, 그리고 다른 캐릭터(금동이·오드·루이)의 출력이
회귀 없이 그대로인지 대조한다.

**Acceptance Scenarios**:

1. **Given** 조사에서 채록한 "캐릭터가 낸 잘못된 언어의 본문", **When**
   현재 프롬프트를 확인한다, **Then** 출력 언어 지시가 어느 줄인지, 왜
   약한지가 특정된다.
2. **Given** 강화된 프롬프트, **When** 샤오바이·모카로 실기기 재생성,
   **Then** 두 캐릭터의 출력이 각각 중국어·영어이고 일기가 저장된다.
3. **Given** 강화된 프롬프트, **When** 금동이·오드·루이로 실기기 재생성,
   **Then** 세 캐릭터의 출력이 여전히 한국어이고 되뱉기·지어내기 위반이
   새로 생기지 않는다(005~017이 각 지시 줄을 추가한 근거의 역검증).
4. **Given** 강화된 프롬프트, **When** `promptPrefix()`/`fixedHead()`의
   바이트 동일성(018 KV 캐시 프리필)과 `instructionLines()`의 되뱉기 판정
   비교 대상 일치(P7 계약)를 확인한다, **Then** 둘 다 깨지지 않는다.

### User Story 4 - 원인이 mojibake면 결론을 남기고 로드맵 14번과 병합한다 (Priority: P3)

조사에서 거부된 본문이 깨진 UTF-8 surrogate(024 §10의 EXAONE와 같은
양상)로 확인되면, 이 저장소의 판정·저장·프롬프트 코드로는 고칠 수 없다는
결론과 근거를 findings.md에 남기고, 로드맵 14번(자동 생성용 서술형 모델
재검토)의 범위로 넘긴다.

**Why this priority**: 이 경우 이 스펙에서 할 수 있는 것은 진단 결론을
정확히 남기는 것뿐이다. 코드 변경이 없으므로 우선순위가 낮지만, 잘못된
교정(예: 판정을 느슨하게 해 깨진 글을 통과시키기)을 막기 위해 명시적으로
스토리로 둔다.

**Independent Test**: 채록한 깨진 본문의 바이트를 findings.md에 남기고,
qwen3·gemma3·exaone 중 어느 조합에서 재현되는지, `llama.rn` 버전과 함께
기록한다. 코드 변경 없음을 `git diff src/`로 확인한다.

**Acceptance Scenarios**:

1. **Given** 거부된 본문이 mojibake, **When** 그 바이트/문자를 확인한다,
   **Then** findings.md에 깨짐 양상(surrogate 범위, `###`·`**` 등 금지
   기호 혼입 여부)과 재현 모델 조합이 기록된다.
2. **Given** mojibake 결론, **When** 이 스펙의 교정 범위를 확인한다,
   **Then** `acceptance.ts`·`prompt.ts`·`store.ts` 어디에도 변경이 없고,
   `judge()`를 느슨하게 하는 수정이 없다.
3. **Given** mojibake 결론, **When** 로드맵 문서를 확인한다, **Then**
   17번 항목이 "mojibake로 확인 — 14번과 병합"으로 갱신되고 14번에
   qwen3·gemma3가 추가된다.

---

### Edge Cases

- **두 캐릭터가 서로 다른 갈래에서 실패하면?** 예: 샤오바이는 `language`,
  모카는 `generation-failed`. 각각 독립적으로 P2/P3/P4 스토리를 적용한다 —
  findings.md가 캐릭터별로 갈래를 분리해 기록한다.
- **"보지 않음" 하루에서는 성공하는데 사진 있는 하루에서만 실패하면?**
  이 조사의 1차 재현은 "보지 않음"이다. 사진 있는 하루에서만 실패하면
  그것은 VLM→캐릭터 모델 전환 문제(011 계열)이며 findings에 별도로
  기록하고 이 스펙의 교정 범위를 벗어난 것으로 표시한다.
- **재현이 안 되면?** (사용자 보고 후 Metro 재시작·모델 재배치로 증상이
  사라진 경우) 024·026·027이 반복 관측한 "스테일 Metro가 오류 없이
  깨진 번들을 서빙" 계열일 수 있다. 그 경우 findings에 "환경 요인으로
  추정, 클린 Metro에서 재현 불가"를 남기고 교정 없이 종료한다.
- **3회가 서로 다른 갈래로 갈리거나 세 원인 갈래 어디에도 안 맞으면?**
  최빈 갈래 하나만 교정하고, 나머지는 findings.md "미확인 잔여"로 후속
  스펙에 넘긴 뒤 종료한다(Clarifications 2026-09-01). 조사자가 한 갈래를
  무한히 파고들지 않는다.
- **`isEcho`가 `MIN_ECHO_LENGTH`(12자) 때문에 중국어 짧은 지시문을
  되뱉기로 오탐하면?** 중국어는 글자당 정보 밀도가 높아 12자 경계가
  한국어와 다르게 작동할 수 있다 — 이 가능성도 P1에서 확인 대상에 넣는다.
- **`ending.kind`가 `eos`가 아니어서 `unfinished`로 거부되면?**
  qwen3/gemma3의 EOS 토큰이 `llama.rn` 채팅 템플릿에서 다르게 잡히는
  경우다. 로그의 `ending` 값을 채록한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 조사자는 샤오바이(`chinese`)·모카(`english`) 각각에 대해
  실기기에서 "사진을 보지 않음" 설정의 일기 생성을 **3회** 실행하고,
  `adb logcat`으로 실패 갈래를 채록할 수 있어야 한다.
- **FR-002**: 실패 갈래는 `rejected: <empty|echo|language|unfinished>` /
  `timed-out` / `generation-failed` 중 캐릭터별로 확정되어야 한다 — 3회
  모두 같으면 그 갈래로, 갈리면 "N회 중 M회 `<갈래>`" 분포로 기록하고
  최빈 갈래를 우선 교정 대상으로 삼는다.
- **FR-003**: 실패 갈래가 `rejected`이면, 거부된 본문 텍스트가 로그에서
  채록되고 사람이 읽어 (비었는지 / 되뱉었는지 / 언어가 다른지 / 깨진
  인코딩인지) 판정되어야 한다. 이 판정은 자동 채점이 아니라 사람의
  눈으로 한다(헌법 원칙 IV).
- **FR-003a**: 거부된 본문 전문을 채록하기 위해 `on-device.ts`의 거부
  분기에 `run.run.text`를 흘리는 **임시 로그**를 한시적으로 추가한다.
  이 로그는 조사 기간에만 존재하며, `Verdict`·`GenerationFailure` 타입에
  `text`를 추가하지 않는다(헌법 원칙 IV). findings.md에 로그 삽입 위치와
  제거를 기록하고, 조사·교정이 끝난 뒤 `src/`의 최종 diff에는 이 임시
  로그가 남지 않아야 한다.
- **FR-004**: 실패 갈래가 `timed-out`이면, `writingMs`(또는 동등한
  `engine.run()` 경과)가 채록되어 `GENERATION_TIMEOUT_MS`(180초)와
  대비되어야 한다.
- **FR-005**: 조사 결과는 `specs/028-chinese-english-diary-failure/findings.md`에
  캐릭터별로 (3회 실패 갈래 분포 / 각 회차 거부된 본문 / 소요 시간 /
  사람의 육안 판정 / 기기·빌드·Metro 상태 / `llama.rn` 버전 / 임시 로그
  삽입·제거 사실 / 미확인 잔여)가 기록되어야 한다.
- **FR-006**: 원인이 `isWrongLanguage` 오탐(모델은 올바른 언어로 정상
  본문을 냈으나 판정이 거부)이면, `acceptance.ts`의 언어 판정 함수만
  수정하여 정상 본문이 통과하도록 해야 한다.
- **FR-007**: FR-006의 수정 후에도 `REJECT_REASONS`는 정확히 4개
  (`empty`/`echo`/`language`/`unfinished`)여야 하며, `acceptance.test.ts`의
  갈래 수 검사가 그것을 지켜야 한다(헌법 원칙 IV).
- **FR-008**: FR-006의 수정 후 한국어 캐릭터(`quiet`/`narrative`/
  `imaginative`)의 언어 판정은 회귀 없이 동작해야 한다 — 한국어 캐릭터가
  다른 문자를 금지하지 않는 비대칭(고유명사·영어 낱말 허용)이 유지되어야
  한다.
- **FR-009**: 원인이 모델이 엉뚱한 언어를 낸 것이면, `prompt.ts`의 출력
  언어 지시 한 줄만 강화해야 한다. 프롬프트는 `prompt.ts`에만 있어야
  하고(005 FR-013b), 캐릭터에서 오는 것은 이름과 출력 언어뿐이어야
  한다(헌법 원칙 III).
- **FR-010**: FR-009의 수정 후 `promptPrefix()`/`fixedHead()`의 바이트
  동일성(018)과 `instructionLines()`의 되뱉기 판정 비교 대상 일치(P7)가
  유지되어야 한다.
- **FR-011**: 원인이 깨진 인코딩(mojibake)이면, 이 스펙은 `src/` 코드를
  변경하지 않고 findings.md에 결론과 근거(깨짐 양상, 재현 모델 조합,
  `llama.rn` 버전)를 남기며, 로드맵 14번 항목에 qwen3·gemma3를 추가하고
  17번 항목을 "14번과 병합"으로 갱신해야 한다.
- **FR-012**: 어떤 원인이든, `judge()`를 느슨하게 하여 깨졌거나 언어가
  다른 본문을 통과시키는 수정은 하지 않아야 한다(헌법 원칙 I — 거부는
  거부로 둔다).
- **FR-013**: 조사에 쓴 합성 하루·재배치 모델은 "경로가 도는가"만
  확인하는 데 쓰고, 출력 품질을 결론짓는 데 쓰지 않아야 한다(010 원칙).
- **FR-014**: 교정이 있었다면(US2 또는 US3), 교정 후 두 캐릭터로 실기기
  재생성하여 일기가 저장되고 목록에 반영되는 것을 확인해야 한다(헌법
  원칙 V — 건너뛴 실기기 테스트는 통과가 아니다). 교정이 순수 로직·
  프롬프트 문자열이고 새 네이티브 모듈·빌드 설정을 건드리지 않으므로
  debug 실기기 확인 1회로 충분하다(012 기준).
- **FR-015**: 교정이 없었다면(US4), `git diff src/`가 0줄임을 확인하고
  종료해야 한다 — FR-003a의 임시 로그도 제거되어 있어야 이 확인이
  성립한다.

### Key Entities *(include if feature involves data)*

- **실패 갈래 (Failure Branch)**: `generation` 단계에서 나오는 실패의
  종류. `rejected`(4개 하위 갈래)·`timed-out`·`generation-failed` 중
  하나. 캐릭터별로 정확히 하나가 붙는다.
- **거부된 본문 (Rejected Body)**: `rejected` 갈래에서, 거부되기까지
  모델이 생성한 텍스트. `Verdict`·`GenerationFailure`에는 담기지
  않으므로(FR-017c) 로그로만 채록한다. 사람이 읽어 육안 판정한다.
- **findings.md**: 이 조사의 산출물. 캐릭터별 실패 갈래, 거부된 본문,
  소요 시간, 육안 판정, 환경 메타, 교정 결정을 담는다.
- **언어 판정 (`isWrongLanguage`)**: `acceptance.ts`의 순수 함수.
  캐릭터별로 기대 문자 클래스(한글/한자/라틴)의 유무를 불리언으로
  조합한다. 이 조사의 유력 수정 대상.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 샤오바이·모카 각각 3회 생성의 실패 갈래 분포가 실기기
  로그로 확정되어 findings.md에 기록된다 — "아마 언어 판정일 것이다"가
  아니라 "3회 중 3회 `rejected: language` (로그 첨부)" 수준으로.
- **SC-002**: 거부된 본문이 채록되고, (비었음 / 되뱉음 / 언어 다름 /
  mojibake) 중 어느 것인지가 사람의 육안 판정으로 기록된다.
- **SC-003**: 조사 결과에 따라 정확히 하나의 경로가 선택된다 — 언어 판정
  수정(US2) / 프롬프트 강화(US3) / 코드 변경 없이 14번 병합(US4) / 환경
  요인으로 재현 불가. 갈래가 갈리면 **최빈 갈래**의 경로를 택하고 나머지는
  findings.md "미확인 잔여"로 넘긴다.
- **SC-004**: 교정이 있었다면, 교정 후 두 캐릭터로 생성한 일기가 실기기
  목록에 남는다(생성 → 저장 → 목록 반영 전체 경로).
- **SC-005**: 교정이 있었다면, 금동이(`quiet`)를 포함한 다른 캐릭터의
  생성이 회귀 없이 동작한다 — 이 조사 전에 정상이던 것이 조사 후에도
  정상.
- **SC-006**: `REJECT_REASONS`는 조사 전후로 정확히 4개다.
- **SC-007**: 교정이 없었다면 `git diff src/`가 0줄이고(FR-003a의 임시
  로그 포함 제거), findings.md에 "왜 코드로 못 고치는가"가 근거와 함께
  남는다.

## Assumptions

- 조사는 SM-S901N(Galaxy S22) 실기기, dev(debug) 빌드에서 수행한다 —
  사용자가 증상을 본 것과 같은 환경. 다른 기기에서의 재현 여부는 범위 밖.
- `a4`(qwen3-1.7b)·`a5`(gemma3-1b) 모델은 `files/models/`에 배치되어
  있고 `state.json` verdict이 `passed: true`다 — 없으면 개발 기계에서
  재다운로드 + `run-as` 배치 + verdict 수동 기록으로 시작한다(024 T037
  선례).
- 1차 재현은 "사진을 보지 않음" 설정의 과거 하루(신호 빈약)로 한다 —
  VLM·사진·위치 변수를 제거해 생성 경로만 남긴다.
- 이 조사는 로드맵 14번(자동 생성용 서술형 모델 재검토)의 선행 또는
  병합 대상이 될 수 있다 — 결론이 mojibake이면 두 항목이 합쳐진다.
- 헌법 원칙 IV·I은 이 조사에서도 그대로다 — 채점 코드를 만들지 않고,
  판정 갈래를 늘리지 않고, 거부를 통과로 바꾸지 않는다.
- 조사 중 Metro가 스테일이면(024·027 계열: 오류 없이 깨진 번들 서빙)
  `npx expo start --dev-client --clear`로 재시작한 뒤 재현을 다시 한다.
